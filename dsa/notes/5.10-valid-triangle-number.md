**Link:** https://leetcode.com/problems/valid-triangle-number
**Difficulty:** Medium | **LeetCode #611**
**Bloomberg frequency:** 38% at three months.

Sorting reduces three triangle inequalities to **one**, and then the counting is a two-pointer
sweep - with a binary-search alternative that explains why it sits in Part 5. The key idea is
the **counting shortcut**: when a pair works, every pair between the pointers works too.

## 1. Problem statement

Given an integer array `nums`, return the number of **triplets** chosen from the array that
can form a triangle when taken as side lengths.

```
nums = [2,2,3,4]  ->  3
    (2,3,4) using the first 2, (2,3,4) using the second 2, and (2,2,3)

nums = [4,2,3,4]  ->  4
```

Constraints: `0 <= nums[i] <= 1000`, so **zeros are possible**.

## 2. Clarifying questions

1. **Count triplets by index or by value?** By **index** - `[2,2,3,4]` counts `(2,3,4)`
   twice, once for each `2`. Confirm it; this is the opposite convention from 3Sum (2.1) and
   getting it wrong halves or doubles the answer.
2. **Degenerate triangles?** A valid triangle needs the sum of any two sides to be
   **strictly** greater than the third. Equality means the points are collinear and it does
   **not** count.
3. **Can sides be zero?** Yes, the constraints allow it - and a zero can never be part of a
   valid triangle, since `0 + b > c` fails whenever `b <= c`. The algorithm handles it, but
   check it.
4. **Return the count, not the triplets?** The count. Listing them could be `O(n^3)`.
5. **May I sort the input?** Sorting is what makes it tractable; ask, or sort a copy.
6. **Sizes?** Up to 1000, so `O(n^2)` is comfortable and `O(n^3)` would be about 10^9 - too
   slow.

## 3. Intuition

### Three inequalities become one

A triangle with sides `a <= b <= c` requires all three of:

```
a + b > c        b + c > a        a + c > b
```

But if `a <= b <= c`, the last two are **automatic**: `b + c >= b + b >= a + b > a` and
similarly for the other. So after sorting, **only `a + b > c` needs checking.**

That reduction is the first thing to say, and it is the reason to sort.

### The counting shortcut

Fix the **largest** side `c` at index `k`, and two pointers `lo = 0`, `hi = k - 1` over the
smaller elements.

> **If `nums[lo] + nums[hi] > nums[k]`, then every element between `lo` and `hi` also works
> as the smaller side** - because they are all at least `nums[lo]`. So there are
> `hi - lo` valid triplets with this `hi`, and you can count them all at once and move `hi`
> down.
>
> **Otherwise the sum is too small**, and `lo` is too small to pair with *any* `hi` at or
> below the current one, so advance `lo`.

That `count += hi - lo` line is the whole efficiency gain - it turns an `O(n)` inner scan
into `O(1)` per step, making the sweep linear per `k` and the total `O(n^2)`.

Fixing the **largest** side (rather than the smallest) is what makes this work: it puts the
single inequality in the form `a + b > c` with `c` constant, which is exactly what two
pointers can sweep.

## 4. Approach

1. Sort `nums`.
2. For `k` from `n-1` down to `2` (the largest side):
   - `lo, hi = 0, k - 1`
   - while `lo < hi`:
     - if `nums[lo] + nums[hi] > nums[k]`: `count += hi - lo`; `hi -= 1`
     - else: `lo += 1`
3. Return `count`.

## 5. Solution

```python
def triangle_number(nums):
    """Number of index triplets that can form a triangle.

    After sorting, only a + b > c needs checking for a <= b <= c. Fixing the largest
    side and sweeping two pointers over the rest lets a whole block be counted at
    once: if nums[lo] + nums[hi] > nums[k], every index between lo and hi works too.
    """
    nums = sorted(nums)
    n = len(nums)
    count = 0

    for k in range(n - 1, 1, -1):       # k indexes the largest side
        lo, hi = 0, k - 1
        while lo < hi:
            if nums[lo] + nums[hi] > nums[k]:
                # Every index in [lo, hi-1] also pairs with hi, since all are >= nums[lo].
                count += hi - lo
                hi -= 1
            else:
                lo += 1                 # nums[lo] is too small for any partner <= hi

    return count
```

```python
triangle_number([2, 2, 3, 4])           # 3
triangle_number([4, 2, 3, 4])           # 4
triangle_number([])                     # 0
triangle_number([1, 2])                 # 0
triangle_number([1, 1, 1])              # 1
triangle_number([1, 2, 3])              # 0
triangle_number([0, 0, 0])              # 0
triangle_number([0, 1, 1])              # 0
triangle_number([2, 2, 2, 2])           # 4
triangle_number([1, 1, 3, 4])           # 0
triangle_number([7, 0, 0, 0])           # 0
```

Four to narrate:

- **`[1,2,3]` -> 0.** `1 + 2 = 3` is not **strictly** greater, so it is degenerate. This is
  the strictness test and it is the most likely place to be wrong.
- **`[0,0,0]` and `[0,1,1]` -> 0.** Zeros can never form a triangle. Worth checking, since
  the constraints allow them and many people assume positive sides.
- **`[2,2,2,2]` -> 4.** All four choices of three equal sides work, which is `C(4,3) = 4`.
  It confirms the counting is by index.
- **`[2,2,3,4]` -> 3.** The given example, and it shows the same *values* counted twice.

### The binary search alternative

Since the array is sorted, you can fix the two **smaller** sides and binary search for how
many valid largest sides exist - which is why this problem is filed under Part 5:

```python
import bisect


def triangle_number_binary(nums):
    """O(n^2 log n): fix the two smaller sides, binary search the upper limit.

    For sides nums[i] <= nums[j], any k > j with nums[k] < nums[i] + nums[j] works,
    so bisect_left finds the first index that is too large.
    """
    nums = sorted(nums)
    n = len(nums)
    count = 0

    for i in range(n - 2):
        if nums[i] == 0:
            continue                    # a zero side can never form a triangle
        for j in range(i + 1, n - 1):
            limit = nums[i] + nums[j]
            # First index whose value is >= limit; everything strictly before it works.
            k = bisect.bisect_left(nums, limit, j + 1, n)
            count += k - j - 1

    return count


triangle_number_binary([2, 2, 3, 4])    # 3
triangle_number_binary([4, 2, 3, 4])    # 4
triangle_number_binary([1, 2, 3])       # 0
triangle_number_binary([2, 2, 2, 2])    # 4
triangle_number_binary([0, 0, 0])       # 0
triangle_number_binary([])              # 0
```

`O(n^2 log n)` versus the two-pointer `O(n^2)` - **slower**, and worth saying so. Offer it as
"the binary search framing", then explain that two pointers removes the log factor because
the boundary moves monotonically as `j` advances. That observation - *a binary search whose
answer moves monotonically can be replaced by a pointer* - is a genuinely transferable idea
and the best thing to take from this question.

### The brute force

```python
import itertools


def triangle_number_brute(nums):
    """O(n^3): check every triplet directly. The validation oracle."""
    count = 0
    for a, b, c in itertools.combinations(sorted(nums), 3):
        if a + b > c:                   # sorted, so the other two inequalities are free
            count += 1
    return count


triangle_number_brute([2, 2, 3, 4])     # 3
triangle_number_brute([4, 2, 3, 4])     # 4
triangle_number_brute([2, 2, 2, 2])     # 4
triangle_number_brute([1, 2, 3])        # 0
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force over all triplets | `O(n^3)` | `O(1)` |
| Sort + binary search | `O(n^2 log n)` | `O(n)` for the sorted copy |
| **Sort + two pointers** | **`O(n^2)`** | `O(n)` for the sorted copy |

The sort is `O(n log n)`, dominated. The outer loop runs `n` times and each inner sweep is
`O(k)` since `lo` only rises and `hi` only falls - so `O(n^2)` overall.

Space is `O(n)` because `sorted()` copies; sorting in place makes it `O(1)` extra if mutating
the input is allowed.

## 7. How to present it

1. **Restate**, and **confirm counting is by index**, not by distinct value. `[2,2,3,4]` -> 3
   is the evidence.
2. **Confirm strictness**: `1 + 2 > 3` is false, so `[1,2,3]` contributes nothing.
3. **State the reduction first** - it is the key insight: *"If I sort so that `a <= b <= c`,
   then `b + c > a` and `a + c > b` hold automatically. Only `a + b > c` needs checking."*
   Prove one of them in a line.
4. **Say you will fix the largest side**, and why: it leaves `a + b > c` with `c` constant,
   which two pointers can sweep.
5. **State the counting shortcut**: *"If `nums[lo] + nums[hi]` beats `nums[k]`, so does
   everything between them - so I can add `hi - lo` at once instead of testing each."* This
   is the second insight and the one that makes it `O(n^2)`.
6. **Announce**, then write it.
7. **Test** `[1,2,3]` (degenerate), `[0,0,0]` (zeros), and `[2,2,2,2]` (index counting).
8. **Offer the binary-search version** and note it is *slower*, then explain why two pointers
   wins - the boundary moves monotonically.
9. **Close**: `O(n^2)` time, `O(n)` space for the sorted copy.

## 8. Follow-ups and variations

- **"Why not binary search?"** It works and is `O(n^2 log n)`. Two pointers removes the log
  because the boundary is monotone in `j`. **Be ready for this**, since the problem is filed
  under binary search.
- **"Count degenerate triangles too."** Change `>` to `>=`.
- **"Return the triplets rather than the count."** Output can be `O(n^3)`; output-bound.
- **"Largest perimeter triangle"** (LC 976). Sort descending and take the first valid
  consecutive triple - `O(n log n)`, greedy. A nice contrast: counting needs the sweep,
  maximising does not.
- **"3Sum"** (2.1). Same sort-then-two-pointer skeleton, but there uniqueness is by **value**
  and here by **index**. Knowing which convention each problem uses is the transferable part.
- **"Count triplets with sum less than a target"** (LC 259). The identical `count += hi - lo`
  shortcut. If you have seen one, say so.
- **"What if sides could be equal to zero or negative?"** Zeros are handled; negatives are not
  physical, so ask.
- **"What if the array is huge?"** `O(n^2)` on 10^5 elements is 10^10 - too slow. You would
  need the value range to be small and count by frequency instead.

## 9. Pitfalls

- **Checking all three inequalities** after sorting. Correct but it shows you missed the
  reduction.
- **Using `>=` instead of `>`**, counting degenerate triangles. `[1,2,3]` is the test.
- **Counting one triplet per successful pair** instead of `hi - lo`, which makes it `O(n^3)`
  and, if you also break, gives the wrong answer.
- **Fixing the smallest side** instead of the largest, which leaves two free variables in the
  inequality and does not sweep cleanly.
- **Counting by distinct value** rather than by index.
- **Forgetting to sort**, which invalidates the whole reduction.
- **`lo <= hi`** instead of `lo < hi`, reusing an element as two sides.
- **Not handling zeros**, or assuming all sides are positive.
- **Mutating the caller's array** with an in-place sort without asking.
