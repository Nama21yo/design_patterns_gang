**Lower bound and upper bound, side by side.** This is the question that forces you to
understand the difference, and once you do, `bisect_left` / `bisect_right` stop being magic
and become tools you can reimplement on demand.

> Read [[5.4 Search Insert Position]] first - this is that template, twice.

## 1. Problem statement

Given an array of integers `nums` sorted in **non-decreasing** order, find the starting and
ending position of a given `target`.

If the target is not found, return `[-1, -1]`.

You must write an algorithm with `O(log n)` runtime.

```
nums = [5,7,7,8,8,10], target = 8   ->  [3,4]
nums = [5,7,7,8,8,10], target = 6   ->  [-1,-1]
nums = [], target = 0               ->  [-1,-1]
```

## 2. Clarifying questions

1. **Duplicates allowed?** Yes - that is the entire point. The array is *non-decreasing*, not
   strictly increasing.
2. **Return `[-1,-1]` when absent?** Yes, both entries.
3. **Must it be `O(log n)`?** Stated. That rules out finding one occurrence and then scanning
   outwards, which is `O(n)` when every element equals the target.
4. **Is the array definitely sorted ascending?** Yes.
5. **Can it be empty?** Yes - given as an example.
6. **Inclusive positions?** Yes - `[first, last]` are both actual indices of the target.

## 3. Intuition

The tempting approach - find any occurrence with a standard binary search, then walk left and
right to the ends of the run - is `O(n)` in the worst case. On `[8,8,8,...,8]` with
`target = 8` the walk covers the whole array. **Say this**; it is why two binary searches are
needed rather than one plus a scan.

Two searches, two predicates:

> **First position = the first index `i` with `nums[i] >= target`** (lower bound).
> **Last position = (the first index `i` with `nums[i] > target`) − 1** (upper bound − 1).

Both predicates are monotone on a sorted array, so both are ordinary binary searches using
the template from 5.4. The **only** difference between them is `>=` versus `>`:

| predicate | name | finds |
|---|---|---|
| `nums[i] >= target` | lower bound, `bisect_left` | first position **at or after** the target's run |
| `nums[i] > target` | upper bound, `bisect_right` | first position **strictly after** the run |

That one character is the whole distinction, and it is the thing to be able to explain.

### The existence check

Lower bound returns an insertion point even when the target is absent. So after computing
`first`, verify:

```
if first == len(nums) or nums[first] != target:  return [-1, -1]
```

Both halves matter: `first == n` when the target exceeds everything, and `nums[first] !=
target` when it would be inserted in the middle. Missing either gives an `IndexError` or a
wrong answer.

Once existence is confirmed, `last = upper_bound - 1` needs no separate check.

## 4. Approach

1. `first = lower_bound(nums, target)`.
2. If `first == n` or `nums[first] != target`, return `[-1, -1]`.
3. `last = upper_bound(nums, target) - 1`.
4. Return `[first, last]`.

Write one helper parameterised by the comparison, rather than two nearly identical functions
- it makes the single-character difference explicit.

## 5. Solution

```python
def search_range(nums, target):
    """First and last index of target in a sorted array, or [-1, -1].

    Two binary searches with the same template; they differ only in >= versus >.
    Lower bound gives the first position at or after the run; upper bound gives the
    first position strictly after it, so the last index is upper bound - 1.
    """
    def bound(strict):
        """First index i with nums[i] > target (strict) or nums[i] >= target."""
        lo, hi = 0, len(nums)       # hi = n: the answer may be one past the end
        while lo < hi:
            mid = (lo + hi) // 2
            if (nums[mid] > target) if strict else (nums[mid] >= target):
                hi = mid
            else:
                lo = mid + 1
        return lo

    first = bound(strict=False)     # lower bound
    # Lower bound returns an insertion point even when the target is absent.
    if first == len(nums) or nums[first] != target:
        return [-1, -1]

    last = bound(strict=True) - 1   # upper bound minus one
    return [first, last]
```

```python
search_range([5, 7, 7, 8, 8, 10], 8)    # [3, 4]
search_range([5, 7, 7, 8, 8, 10], 6)    # [-1, -1]
search_range([], 0)                     # [-1, -1]
search_range([1], 1)                    # [0, 0]
search_range([1], 2)                    # [-1, -1]
search_range([2, 2], 2)                 # [0, 1]
search_range([1, 2, 3], 1)              # [0, 0]
search_range([1, 2, 3], 3)              # [2, 2]
search_range([1, 1, 1, 1], 1)           # [0, 3]
search_range([1, 2, 3], 0)              # [-1, -1]
search_range([1, 2, 3], 4)              # [-1, -1]
```

`[1,1,1,1]` with `target = 1` -> `[0,3]` is the case that proves you did not scan: an
expand-outwards solution would touch every element. `[1,2,3]` with targets `0` and `4` are
the two out-of-range cases, exercising both halves of the existence check.

### The two separate helpers, if the flag feels awkward

The ternary inside the loop is compact but reads poorly aloud. Two plain functions are often
better in an interview:

```python
def lower_bound(nums, target):
    """First index with nums[i] >= target (bisect_left)."""
    lo, hi = 0, len(nums)
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] >= target:
            hi = mid
        else:
            lo = mid + 1
    return lo


def upper_bound(nums, target):
    """First index with nums[i] > target (bisect_right). The ONLY difference is >."""
    lo, hi = 0, len(nums)
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > target:
            hi = mid
        else:
            lo = mid + 1
    return lo


def search_range_two_helpers(nums, target):
    first = lower_bound(nums, target)
    if first == len(nums) or nums[first] != target:
        return [-1, -1]
    return [first, upper_bound(nums, target) - 1]


search_range_two_helpers([5, 7, 7, 8, 8, 10], 8)    # [3, 4]
search_range_two_helpers([5, 7, 7, 8, 8, 10], 6)    # [-1, -1]
search_range_two_helpers([1, 1, 1, 1], 1)           # [0, 3]
search_range_two_helpers([], 0)                     # [-1, -1]
```

Writing them side by side makes the `>=` versus `>` difference impossible to miss - which is
exactly what you want the interviewer to see.

### Using `bisect`

```python
import bisect


def search_range_bisect(nums, target):
    """What you would write in production."""
    first = bisect.bisect_left(nums, target)
    if first == len(nums) or nums[first] != target:
        return [-1, -1]
    return [first, bisect.bisect_right(nums, target) - 1]


search_range_bisect([5, 7, 7, 8, 8, 10], 8)     # [3, 4]
search_range_bisect([5, 7, 7, 8, 8, 10], 6)     # [-1, -1]
search_range_bisect([1, 1, 1, 1], 1)            # [0, 3]
```

Mention this, then hand-roll it. Most interviewers want the implementation, but knowing the
library primitive by name is a plus.

### Counting occurrences, for free

```python
def count_occurrences(nums, target):
    """upper bound - lower bound, with no existence check needed: it is 0 when absent."""
    return upper_bound(nums, target) - lower_bound(nums, target)


count_occurrences([5, 7, 7, 8, 8, 10], 8)   # 2
count_occurrences([5, 7, 7, 8, 8, 10], 7)   # 2
count_occurrences([5, 7, 7, 8, 8, 10], 6)   # 0
count_occurrences([1, 1, 1, 1], 1)          # 4
```

Worth offering unprompted - it is one line and it shows the two bounds are a general tool,
not a trick for this problem.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(n)` | `O(1)` |
| One binary search plus expand | `O(n)` worst case | `O(1)` |
| **Two binary searches** | **`O(log n)`** | **`O(1)`** |

Two independent searches, each `O(log n)`, so `2 log n` - still `O(log n)`. The
expand-outwards version is the trap: it looks logarithmic but is linear when the run is long.

## 7. How to present it

1. **Restate**, and stress that duplicates are the point.
2. **Name and reject the obvious approach**: *"I could find one occurrence and walk outwards,
   but on an array of all equal values that's `O(n)` - and the problem asks for `O(log n)`."*
   Saying this first shows you understood why the problem is a Medium.
3. **State the reformulation**: *"The first position is lower bound - the first index with
   value >= target. The last position is upper bound minus one, where upper bound is the
   first index with value strictly greater."*
4. **Emphasise that the only difference is `>=` versus `>`.** Write both predicates next to
   each other.
5. **Say the range is `[0, n]`** for both, since upper bound can legitimately be `n`.
6. **Write the helpers**, then the four-line wrapper.
7. **Explain the existence check** and why both halves are needed.
8. **Test** `[1,1,1,1]` (full run), target below and above everything, and the empty array.
9. **Close**: `O(log n)` time, `O(1)` space; offer `count_occurrences` as a one-line bonus,
   and mention these are `bisect_left` / `bisect_right`.

## 8. Follow-ups and variations

- **"Count the occurrences of the target."** `upper - lower`, one line, no existence check.
- **"How many elements are strictly less than the target?"** Lower bound, directly.
- **"Find the insertion point."** That is 5.4.
- **"What if the array is rotated?"** First find the rotation point (5.17), then binary search
  the appropriate segment - or use the 5.2 technique.
- **"What if the array is 2D, sorted row-wise and column-wise?"** Staircase search from the
  top-right, `O(m + n)`. A different technique worth naming.
- **"Find the k-th occurrence."** `lower_bound + k - 1`, with a bounds check against
  `upper_bound`.
- **"Find the closest element to the target."** Lower bound, then compare `nums[lo-1]` and
  `nums[lo]`. The boundary guards are the fiddly part.
- **"Do it with one binary search instead of two?"** Not cleanly - you need both ends, and
  they are independent. You *can* find one occurrence and then binary search within the two
  halves, but that is still two searches. Worth saying plainly.
- **"What if elements are inserted between queries?"** A sorted list costs `O(n)` per insert;
  use a balanced BST or a Fenwick tree over value counts.

## 9. Pitfalls

- **Finding one occurrence and expanding outwards.** Correct but `O(n)`, and the problem
  explicitly forbids it.
- **Omitting the `first == len(nums)` guard**, giving an `IndexError` when the target exceeds
  everything.
- **Omitting the `nums[first] != target` guard**, returning an insertion point as if it were
  a real position.
- **Using `>=` in both searches**, or `>` in both - then `first == last` always.
- **Forgetting the `- 1` on the upper bound**, returning one past the last occurrence.
- **Setting `hi = len(nums) - 1`**, so upper bound cannot return `n` and the last position is
  wrong when the run reaches the end of the array. `[1,1,1,1]` catches it.
- **Mixing the inclusive and exclusive templates** between the two searches.
- **Returning a tuple when a list is expected**, or `(-1, -1)` instead of `[-1, -1]` - minor,
  but check the required shape.
