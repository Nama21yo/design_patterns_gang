**Link:** https://leetcode.com/problems/search-insert-position
**Difficulty:** Easy | **LeetCode #35**
**Bloomberg frequency:** 50% at three months.

**The binary search template in its purest form.** Every other question in Part 5 is this
plus a wrinkle, so get the boundary handling exactly right here and the rest become
mechanical.

## 1. Problem statement

Given a **sorted array of distinct integers** and a `target`, return the index if the target
is found. If not, return **the index where it would be inserted** to keep the array sorted.

You must write an algorithm with `O(log n)` runtime.

```
nums = [1,3,5,6], target = 5  ->  2
nums = [1,3,5,6], target = 2  ->  1
nums = [1,3,5,6], target = 7  ->  4
```

## 2. Clarifying questions

1. **Are the values distinct?** Stated. With duplicates you must decide between the first and
   last valid insertion point - that is `bisect_left` versus `bisect_right`, and it is 5.3.
2. **Is the array definitely sorted ascending?** Yes.
3. **Can the array be empty?** Then the answer is 0. LeetCode guarantees at least one
   element; ask anyway.
4. **Can the target be smaller than everything or larger than everything?** Yes - both are
   given as examples and they are the boundary cases (0 and `n`).
5. **Must it be `O(log n)`?** Stated explicitly, which rules out a linear scan.
6. **Return the index only?** Yes.

## 3. Intuition

This is **lower bound**: the first index `i` such that `nums[i] >= target`.

> **Define the predicate `P(i) = nums[i] >= target`. Because the array is sorted, `P` is
> `False` then `True` - an `F F F T T T` pattern. Binary search finds the boundary, and that
> boundary is both the location of the target (if present) and its insertion point (if not).**

That unification is the reason this problem is worth understanding rather than memorising:
**you do not need two cases.** The "found" and "not found" answers are the same number.

Check it against the examples:
- `target = 5` in `[1,3,5,6]`: the first index with `nums[i] >= 5` is 2, which is where 5 is.
- `target = 2`: the first index with `nums[i] >= 2` is 1, which is where 2 belongs.
- `target = 7`: no element satisfies it, so the boundary is `n = 4` - the insertion point at
  the end.

The last case is why the search range must be `[0, n]`, not `[0, n-1]`: the answer can be
`n`, one past the last element. **That is the single most common bug in this problem.**

### The template

```
while lo < hi:
    mid = (lo + hi) // 2
    if nums[mid] >= target:  hi = mid        # mid might be the answer - keep it
    else:                    lo = mid + 1    # mid definitely is not - discard it
return lo
```

Three things make it safe, and they are worth saying as you write:

1. **`while lo < hi`** - the loop ends with `lo == hi`, so there is no final comparison and
   no ambiguity about which to return.
2. **`hi = mid`, never `mid - 1`** - because `mid` is still a candidate.
3. **`mid` rounds down**, so `mid < hi` whenever `lo < hi`, so `hi = mid` strictly shrinks
   the range. No infinite loop.

## 4. Approach

1. `lo, hi = 0, len(nums)` - note `hi` is `n`, **not** `n - 1`.
2. While `lo < hi`: `mid = (lo + hi) // 2`; if `nums[mid] >= target`, `hi = mid`, else
   `lo = mid + 1`.
3. Return `lo`.

No special case for "found", and no special case for the empty array - `lo` and `hi` both
start at 0 and the loop does not run.

## 5. Solution

```python
def search_insert(nums, target):
    """Index of target, or where it would be inserted to keep the array sorted.

    This is lower bound: the first index i with nums[i] >= target. That single value
    answers both cases - if the target is present it is its index, and if not it is
    the insertion point. hi starts at len(nums), because the answer can be n.
    """
    lo, hi = 0, len(nums)           # hi = n, not n - 1: the answer may be one past the end

    while lo < hi:
        mid = (lo + hi) // 2        # rounds down, so mid < hi and the range shrinks
        if nums[mid] >= target:
            hi = mid                # mid might be the answer, so keep it in range
        else:
            lo = mid + 1            # mid is too small, so discard it

    return lo
```

```python
search_insert([1, 3, 5, 6], 5)      # 2
search_insert([1, 3, 5, 6], 2)      # 1
search_insert([1, 3, 5, 6], 7)      # 4
search_insert([1, 3, 5, 6], 0)      # 0
search_insert([1], 1)               # 0
search_insert([1], 0)               # 0
search_insert([1], 2)               # 1
search_insert([], 5)                # 0
search_insert([1, 3, 5, 6], 1)      # 0
search_insert([1, 3, 5, 6], 6)      # 3
```

The four boundary cases - target below everything (0), above everything (`n`), equal to the
first element, equal to the last - are the whole test suite for this problem. Run them out
loud; they take fifteen seconds and they exercise every branch.

### Verifying against `bisect`

```python
import bisect

nums = [1, 3, 5, 6]
[search_insert(nums, t) for t in range(0, 8)]           # [0, 0, 1, 1, 2, 2, 3, 4]
[bisect.bisect_left(nums, t) for t in range(0, 8)]      # [0, 0, 1, 1, 2, 2, 3, 4]
```

`search_insert` **is** `bisect_left`. Saying that - "this is lower bound, which the standard
library calls `bisect_left`" - shows you recognise the primitive rather than just the
problem.

### The inclusive-bounds variant

Many people learn the `lo <= hi` form. It is also correct, but it needs a different return:

```python
def search_insert_inclusive(nums, target):
    """The other common template: hi = n - 1 and `while lo <= hi`. The loop ends with
    lo == hi + 1, and `lo` is the insertion point - which is why it is returned."""
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return lo                       # lo has crossed past hi and marks the insertion point


search_insert_inclusive([1, 3, 5, 6], 5)    # 2
search_insert_inclusive([1, 3, 5, 6], 2)    # 1
search_insert_inclusive([1, 3, 5, 6], 7)    # 4
search_insert_inclusive([1, 3, 5, 6], 0)    # 0
search_insert_inclusive([], 5)              # 0
```

Both work. **Pick one template and use it everywhere** - the errors come from mixing them
(`lo <= hi` with `hi = mid` is an infinite loop). The exclusive form is recommended in this
course because it generalises directly to "binary search on the answer", where there is no
array to index and no "found" case at all.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(n)` | `O(1)` |
| **Binary search** | **`O(log n)`** | **`O(1)`** |
| Recursive binary search | `O(log n)` | `O(log n)` stack |

The range halves each iteration, so `ceil(log2(n + 1))` iterations at most. Iterative, so
constant space - prefer it over recursion, which adds stack frames for no benefit.

## 7. How to present it

1. **Restate**, and immediately note the unification: *"If the target is present I return its
   index; if not, its insertion point. Those are the same number - the first index whose
   value is at least the target."* That observation is the answer, and stating it first
   means you write no special cases.
2. **Name it**: "This is lower bound, `bisect_left`."
3. **State the predicate and its monotonicity**: *"`nums[i] >= target` is False then True
   because the array is sorted, so I'm finding the boundary."*
4. **Say the range is `[0, n]`, not `[0, n-1]`**, and why: the answer can be `n` when the
   target exceeds everything. **This is the line to say out loud** - it is the bug this
   problem exists to catch.
5. **Write the template**, narrating the three safety properties as you go: `while lo < hi`,
   `hi = mid` keeps the candidate, `mid` rounds down so the range shrinks.
6. **Test the four boundaries**: below everything, above everything, first element, last
   element. Plus empty if allowed.
7. **Close**: `O(log n)` time, `O(1)` space; mention it is exactly `bisect_left`.

## 8. Follow-ups and variations

- **"What if there are duplicates?"** Now lower bound and upper bound differ. `bisect_left`
  gives the first valid position, `bisect_right` the last. That is 5.3 *Find First and Last
  Position*.
- **"Return -1 if not found"** (LC 704, plain binary search). Same search, then check
  `lo < n and nums[lo] == target`.
- **"Count how many elements are less than the target."** That is exactly the answer - the
  lower bound **is** the count of strictly smaller elements. A nice reframing to offer.
- **"Find the largest element less than the target."** `lower_bound - 1`, guarding for 0.
- **"Do it recursively."** Straightforward, but note the `O(log n)` stack and that iterative
  is preferred.
- **"What if the array is rotated?"** 5.2 - the sortedness is local, so you first determine
  which half is sorted.
- **"What if the array were a linked list?"** Binary search needs `O(1)` random access, so it
  degrades to `O(n)` - you would use a skip list or a balanced tree instead. Worth saying.
- **"What if insertions happen between queries?"** A sorted array costs `O(n)` per insert;
  use a balanced BST or a skip list for `O(log n)` both ways.
- **"Search in an infinite sorted array."** Exponential search: double the bound until you
  overshoot, then binary search in that window. `O(log position)`. A nice one to name.

## 9. Pitfalls

- **Initialising `hi = len(nums) - 1`** with the exclusive template, so an answer of `n` is
  unreachable. `target = 7` on `[1,3,5,6]` returns 3 instead of 4. **The defining bug.**
- **Mixing templates**: `while lo <= hi` with `hi = mid` loops forever.
- **`lo = mid` without biasing the midpoint upward** - also an infinite loop.
- **Returning `mid` from inside the loop** in the exclusive template, which breaks the
  lower-bound guarantee when duplicates exist.
- **Adding a separate "not found" branch** when none is needed.
- **Using `>` instead of `>=`** in the predicate, which returns upper bound instead.
- **Forgetting the empty array**, though the template handles it naturally.
- **Writing `(lo + hi) // 2` and being asked about overflow** - say `lo + (hi - lo) // 2` is
  the portable form; Python integers do not overflow.
