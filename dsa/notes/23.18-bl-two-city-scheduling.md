> Reported once in R1 on 2025-10-17, with a warning worth quoting: *"The twist was that the
> number of people could be odd, and the interviewer may not mention this at the beginning -
> you have to ask for clarifying questions yourself."*
>
> **The question is a clarifying-questions test wearing a greedy algorithm's clothes.**

## Prompt as given

```
There are two cities NY and SF and we want to send n participants to the two cities.
Both cities have a capacity of half of the total number of participants
  ("which in this case you would think n is even by default, but you should always ask")
The cost of flying one person is given by <costNY, costSF>.
What will be the minimum cost to fly all participants?
```

Link: [Two City Scheduling](https://leetcode.com/problems/two-city-scheduling/) (LC 1029)

The reported clarification: **one of the cities could take half + 1 people**, and after
sorting, the middle person must be checked separately.

## Clarifying questions to ask first

1. **Is `n` guaranteed even?** *Ask this one.* The report is explicit that the interviewer
   will not volunteer it. If odd, ask which city takes the extra person - or whether you get
   to choose (you do, and choosing is what makes it interesting).
2. **Must the split be exactly half/half**, or is that an upper bound on capacity?
3. **Can costs be negative or zero?** Does not break the greedy, but ask.
4. **Return the cost, or the assignment?** Offer both.
5. **Exactly two cities?** Yes - and note that three or more is a genuinely different
   problem (see the follow-ups).

## Intuition

The brute force is choosing which half goes to NY: `C(n, n/2)` possibilities, astronomically
many. So you need structure.

The key reframing:

> **Send everybody to city A first, then pick which ones to "upgrade" to city B.**

If everyone flies to NY, the cost is `sum(costNY)`. Moving person `i` to SF changes the cost
by `costSF[i] - costNY[i]`. Call that the person's **refund** (negative is a saving). We must
move exactly `n/2` people, and to minimise the total we move the `n/2` people with the
smallest (most negative) refunds.

Sorting by `costSF - costNY` ascending puts the people who *most want to go to SF* at the
front. Take the first half for SF, the second half for NY. Done.

**Why the greedy is correct (the exchange argument to say out loud):** suppose an optimal
solution sends person `p` to NY and person `q` to SF, where `p` has a smaller
`costSF - costNY` than `q`. Swap them. The cost changes by
`(costSF[p] - costNY[p]) - (costSF[q] - costNY[q])`, which is negative - so the swap strictly
improves the solution, contradicting optimality. Hence in any optimal solution, everyone sent
to SF has a difference at least as small as everyone sent to NY, which is exactly what
sorting produces.

Have that argument ready. "Prove the greedy" is the most likely follow-up and this is a
clean two-sentence proof.

## The odd case

With `n` odd, one city gets `floor(n/2)` and the other `ceil(n/2)`. Since you may choose
which, compute both and take the cheaper:

- Sort by `costSF - costNY` ascending.
- **Option A:** the first `ceil(n/2)` go to SF, the rest to NY.
- **Option B:** the first `floor(n/2)` go to SF, the rest to NY.

These differ only in where the **middle person** goes - which is exactly what the report
describes. Everyone before the middle prefers SF more strongly, everyone after prefers NY
more strongly, so the only open question is the one at the boundary, and you answer it by
trying both.

Equivalently and more simply: the middle person goes to whichever city is cheaper *for them*.
But computing both totals is harder to get wrong and is what you should write.

## Approach

1. Sort people by `costSF - costNY` ascending.
2. If `n` is even: first `n/2` to SF, rest to NY.
3. If `n` is odd: compute the total for `k = n//2` and for `k = n//2 + 1` going to SF, return
   the minimum.

## Solution

```python
def two_city_cost(costs):
    """costs: list of (costNY, costSF). Returns the minimum total flight cost with the
    two cities splitting the people as evenly as possible.

    Handles an odd number of people by trying both ways to place the middle person.
    """
    n = len(costs)
    if n == 0:
        return 0

    # Sort by how much cheaper SF is than NY for this person. The most negative values
    # are the people who most want SF.
    ordered = sorted(costs, key=lambda c: c[1] - c[0])

    def total_with(sf_count):
        """Cost when the first sf_count people (by preference) fly SF, the rest NY."""
        return (sum(sf for _, sf in ordered[:sf_count])
                + sum(ny for ny, _ in ordered[sf_count:]))

    if n % 2 == 0:
        return total_with(n // 2)
    # Odd: one city takes the extra person, and we may choose which.
    return min(total_with(n // 2), total_with(n // 2 + 1))


def two_city_assignment(costs):
    """Same, but returns (total, assignment) where assignment[i] is 'NY' or 'SF'
    for the ORIGINAL index i."""
    n = len(costs)
    if n == 0:
        return 0, []

    order = sorted(range(n), key=lambda i: costs[i][1] - costs[i][0])

    def total_with(sf_count):
        return (sum(costs[i][1] for i in order[:sf_count])
                + sum(costs[i][0] for i in order[sf_count:]))

    candidates = [n // 2] if n % 2 == 0 else [n // 2, n // 2 + 1]
    best_count = min(candidates, key=total_with)

    assignment = [None] * n
    for rank, i in enumerate(order):
        assignment[i] = "SF" if rank < best_count else "NY"
    return total_with(best_count), assignment
```

```python
# LeetCode's example: costs = [[10,20],[30,200],[400,50],[30,20]]
two_city_cost([(10, 20), (30, 200), (400, 50), (30, 20)])        # 110

two_city_cost([(259, 770), (448, 54), (926, 667), (184, 139),
               (840, 118), (577, 469)])                          # 1859

# Odd number of people
two_city_cost([(10, 20), (30, 200), (400, 50)])                  # 90
two_city_assignment([(10, 20), (30, 200), (400, 50)])
# (90, ['NY', 'NY', 'SF'])
```

Check that odd example by hand, because it is the one the interviewer cares about.
Differences `costSF - costNY` are `+10`, `+170`, `-350`, so the order is person 2 (-350),
person 0 (+10), person 1 (+170).

- `sf_count = 1`: person 2 to SF (50), persons 0 and 1 to NY (10 + 30 = 40). Total **90**.
- `sf_count = 2`: persons 2 and 0 to SF (50 + 20 = 70), person 1 to NY (30). Total **100**.

So 90, with SF taking one person and NY taking two. The choice of which city gets the extra
person mattered - it is a 10-unit difference. **That is the demonstration to give.**

## Complexity

| | Time | Space |
|---|---|---|
| Brute force over all splits | `O(C(n, n/2) * n)` | `O(n)` |
| Sort by difference | `O(n log n)` | `O(n)` for the sorted copy |
| Quickselect instead of a full sort | `O(n)` average | `O(1)` if in place |

The sort dominates. Mention quickselect: you do not need the full order, only the `n/2`
smallest differences, so `numpy.partition` / `nth_element` gives `O(n)` average. Say it as
an aside - it is a nice sign you know sorting is overkill for a selection problem.

Computing `total_with` twice in the odd case is `O(n)` each, so it does not change the
bound.

## How to present it

1. **Ask whether `n` is even. Out loud. Early.** This is the single scored moment in the
   question and the report says so explicitly. Even if they say yes, you have shown the
   instinct.
2. **State the brute force and why it is hopeless** (`C(n, n/2)`).
3. **Give the reframing**: "send everyone to NY, then choose `n/2` people to move to SF; the
   cost of moving person `i` is `costSF[i] - costNY[i]`, so move the `n/2` cheapest to move."
4. **Give the exchange argument** for correctness without waiting to be asked. Two sentences.
5. **Then handle the odd case**: "if `n` is odd, only the middle person's placement is in
   doubt, so I try both and take the minimum."
6. **Code it**, keeping `total_with` as a named helper so both branches read identically.
7. **Trace the three-person example** and show that the two options differ - proving the odd
   case is not a formality.

## Follow-ups and variations

- **"The number of people is odd."** The stated twist. Try both placements of the middle
  person. Ask who gets the extra person if they have a preference; if they do not, choosing
  optimally is the right call and you should say you are choosing.
- **"Prove the greedy."** The exchange argument above. This is the most common follow-up on
  any greedy question - have the shape memorised: *assume an optimal solution violates the
  greedy order, swap the offending pair, show the cost does not increase, conclude.*
- **"Arbitrary capacities rather than half/half."** If city A must take exactly `k` people,
  the same sort works - take the first `k`. If capacities are ranges, it is still the same
  sort with `k` chosen over the feasible range, so `O(n log n + range)`.
- **"More than two cities."** The difference trick collapses, because there is no single
  "refund" per person. This becomes an assignment / min-cost-flow problem, or a DP over
  `(person, counts per city)` which is exponential in the number of cities. Say that
  explicitly - recognising when a greedy stops working is worth as much as applying one.
- **"Return the assignment, not just the cost."** `two_city_assignment` above. Note that you
  must sort **indices**, not the cost pairs, to recover the original positions.
- **"Costs arrive as a stream."** You need the `n/2` smallest differences - a max-heap of
  size `n/2`, `O(n log n)` time and `O(n)` space.
- **"What if someone cannot fly to one of the cities?"** Model as infinite cost; the greedy
  still works as long as the capacities remain feasible - check feasibility first.
- **"Minimise the maximum cost per person instead of the total."** Different objective:
  binary search on the answer plus a feasibility check.

## Pitfalls

- **Assuming `n` is even.** The whole point of the question.
- **Sorting by `costNY` or by `costSF` alone.** It is the *difference* that matters - a
  person with costs `(1000, 1010)` is barely a candidate for SF despite a low SF cost
  relative to others.
- **In the odd case, sending the middle person to the city that is cheaper in absolute
  terms** rather than comparing the two totals. They coincide here, but reasoning from the
  totals is what generalises.
- **Sorting the cost pairs when you need the assignment**, losing the original indices.
- **`n // 2` versus `n / 2`** - the latter is a float and will fail as a slice index.
- **Stating the greedy without a justification.** "Prove it" is coming.
- **Off-by-one in the slice**: `ordered[:k]` to SF and `ordered[k:]` to NY - check the sizes
  sum to `n`.
