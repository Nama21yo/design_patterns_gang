title: "23.14 Can a customer trade during the whole order window"
---

> Reported once in R1 on 2025-10-20, and the report is a cautionary tale worth reading
> twice: *"I misinterpreted 'at least one bank open' as finding a bank that can fit the
> whole time window, and implemented it. When she gave me a test case I knew my approach
> was wrong, and just when I realised it was basically merge intervals, the time was up."*
>
> The algorithm here is easy. **The failure mode is requirements comprehension**, and that
> is what this page is really about.

## Prompt as given

```
Your trading platform aggregates multiple banks, each with its own trading hours. Customers
can place trades anytime during the day, but trades can only be executed when AT LEAST ONE
bank is open. Given the operating hours of the banks, verify whether a customer can trade at
every minute of the given order window.

  order1 = 15:00 - 20:00

  Banks:  03:30 - 09:30  JP Morgan
          08:00 - 12:00  Bank of America
          10:00 - 15:00  National Bank
          14:00 - 18:30  HSBC
          16:00 - 20:00  Citi Bank
          19:00 - 23:00  Deutsche Bank

  canTrade(banks, order1) = True
```

Related: [Merge Intervals](https://leetcode.com/problems/merge-intervals/) (LC 56).

## Why the example returns True

No single bank covers 15:00-20:00. The coverage is a **relay**:

```
order:                    |===============================|
                         15:00                          20:00

National   10:00-15:00  ==|
HSBC       14:00-18:30 ===|=========================|
Citi       16:00-20:00    |        |==============================|
Deutsche   19:00-23:00    |                  |===================|====...
```

HSBC covers 15:00 to 18:30, Citi opens at 16:00 (before HSBC closes) and runs to 20:00. So
the union is continuous across the whole window. **That relay is the entire question**, and
the candidate who read it as "one bank must cover the window" answered a different question.

## Clarifying questions to ask first

Ask these. The reported failure was not knowing the answer to the first one.

1. **"At least one bank open" - does one bank have to cover the whole window, or can
   coverage hand off between banks?** Hand off. Restate it back: *"so if HSBC covers the
   first half and Citi the second, and they overlap, that is a yes?"*
2. **Is coverage required at every instant, or only at the start and end?** Every minute.
3. **Are the endpoints inclusive?** If bank A closes at 16:00 and bank B opens at 16:00, is
   16:00 covered? Treat intervals as closed and touching as contiguous, but **ask** - this is
   the only real edge case.
4. **Can bank hours wrap past midnight** (22:00 - 02:00)? Ask; it is a natural follow-up.
5. **How many banks, how many orders?** One order against `n` banks is `O(n log n)`. Many
   orders means preprocess once.
6. **Do I return a boolean, or the gaps?** Boolean first; gaps are more useful and a good
   thing to offer.

## Intuition

"Is this window fully covered by the union of those intervals?" The union of intervals is
the merge-intervals problem, so:

> **Merge the bank hours into maximal disjoint intervals, then check whether any single
> merged interval contains the order window.**

That is the clean two-step answer and it is what you should say.

There is a leaner one-pass version that avoids materialising the merge: sort the banks by
opening time, walk a pointer `covered_until` starting at the order's start, and repeatedly
extend it by the furthest-closing bank that opens at or before `covered_until`. If you can
never extend, there is a gap. This is the *jump game / minimum number of taps* greedy, and
it is the same shape as "Video Stitching".

Either is fine. The merge version is easier to state and harder to get wrong under pressure;
the greedy is a touch more elegant. Lead with merge, mention the greedy.

The key insight to verbalise either way: **sort by start time**. Once sorted, a bank can only
extend the current coverage if it opens at or before the point already covered; otherwise
there is a hole and no later bank can fill it, because every later bank opens even later.

## Approach

**Merge version.**
1. Convert times to minutes since midnight.
2. Sort the bank intervals by start.
3. Merge: walk through, extending the current interval while the next one starts at or
   before the current end; otherwise start a new one.
4. Return True if some merged interval satisfies `start <= order_start` and
   `end >= order_end`.

**Greedy version.**
1. Sort by start.
2. `covered_until = order_start`.
3. Repeatedly, among banks opening at or before `covered_until`, take the maximum close time
   and set `covered_until` to it. If no progress is possible, return False.
4. Stop when `covered_until >= order_end`.

## Solution

```python
def to_minutes(hhmm):
    """'15:00' -> 900. Times as minutes since midnight make the arithmetic trivial."""
    hours, minutes = hhmm.split(":")
    return int(hours) * 60 + int(minutes)


def merge_intervals(intervals):
    """Union of intervals as a sorted list of maximal disjoint intervals.
    Touching intervals (end == next start) are treated as contiguous."""
    if not intervals:
        return []
    intervals = sorted(intervals)
    merged = [list(intervals[0])]
    for start, end in intervals[1:]:
        # <= not < : a bank opening exactly when another closes keeps coverage unbroken.
        if start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return merged


def can_trade(banks, order):
    """banks: list of (open, close) as 'HH:MM'. order: (start, end) as 'HH:MM'.

    True when the union of the bank hours covers every minute of the order window -
    coverage may hand off between banks, it need not come from a single one.
    """
    order_start, order_end = to_minutes(order[0]), to_minutes(order[1])
    if order_start >= order_end:
        return True                       # empty window is trivially covered

    hours = [(to_minutes(o), to_minutes(c)) for o, c in banks]
    for start, end in merge_intervals(hours):
        if start <= order_start and end >= order_end:
            return True
    return False
```

```python
banks = [("03:30", "09:30"), ("08:00", "12:00"), ("10:00", "15:00"),
         ("14:00", "18:30"), ("16:00", "20:00"), ("19:00", "23:00")]

can_trade(banks, ("15:00", "20:00"))   # True
can_trade(banks, ("15:00", "23:00"))   # True
can_trade(banks, ("00:00", "05:00"))   # False  (nothing open before 03:30)
can_trade(banks, ("09:00", "12:00"))   # True
```

Worth printing the merge to show the relay explicitly:

```python
merge_intervals([(to_minutes(o), to_minutes(c)) for o, c in banks])
# [[210, 1380]]   i.e. 03:30 to 23:00, one continuous block
```

Everything merges into a single block here, which is why the answer is True for any window
inside 03:30-23:00. Say that - it is a satisfying way to confirm the reading of the question.

### The greedy one-pass version

```python
def can_trade_greedy(banks, order):
    """Same answer without materialising the merge. Extend the covered point by the
    furthest-reaching bank that is already open; if nothing extends it, there is a gap."""
    order_start, order_end = to_minutes(order[0]), to_minutes(order[1])
    if order_start >= order_end:
        return True

    hours = sorted((to_minutes(o), to_minutes(c)) for o, c in banks)

    covered_until = order_start
    i = 0
    while covered_until < order_end:
        furthest = covered_until
        # Every bank that opens at or before the point we have covered is usable now.
        while i < len(hours) and hours[i][0] <= covered_until:
            furthest = max(furthest, hours[i][1])
            i += 1
        if furthest == covered_until:
            return False                  # nothing extends the coverage: a gap
        covered_until = furthest
    return True
```

### Returning the gaps instead of a boolean

More useful in a real product, and a good thing to offer unprompted:

```python
def trading_gaps(banks, order):
    """The sub-intervals of the order window during which no bank is open."""
    order_start, order_end = to_minutes(order[0]), to_minutes(order[1])
    merged = merge_intervals([(to_minutes(o), to_minutes(c)) for o, c in banks])

    gaps = []
    cursor = order_start
    for start, end in merged:
        if end <= cursor:
            continue
        if start >= order_end:
            break
        if start > cursor:
            gaps.append((cursor, min(start, order_end)))
        cursor = max(cursor, end)
        if cursor >= order_end:
            break
    if cursor < order_end:
        gaps.append((cursor, order_end))
    return gaps
```

```python
trading_gaps(banks, ("00:00", "05:00"))   # [(0, 210)]      00:00 - 03:30 uncovered
trading_gaps(banks, ("15:00", "20:00"))   # []
```

## Complexity

Let `n` be the number of banks and `q` the number of orders.

| | Time | Space |
|---|---|---|
| Merge version, one order | `O(n log n)` | `O(n)` |
| Greedy version, one order | `O(n log n)` | `O(n)` |
| Many orders, preprocessed | `O(n log n)` once, then `O(log n)` per order | `O(n)` |

The sort dominates both. For many orders, merge once and binary search the merged list for
the interval containing `order_start` - that is the answer to the "many orders" follow-up
and it is `O(log n)` per query.

## How to present it

The lesson from the report is that **the first ninety seconds decide this question**.

1. **Restate the requirement in your own words, and give a concrete relay example.** "So if
   HSBC covers 15:00 to 18:30 and Citi covers 16:00 to 20:00, together they cover the whole
   window - that counts as yes?" Wait for confirmation. This one sentence is what the
   reported candidate was missing.
2. **Work the given example by hand** and point out that no single bank covers it, yet the
   answer is True. If your reading of the problem does not explain the provided example,
   your reading is wrong - say this out loud as your check.
3. **Name the problem**: "this is the union of intervals - merge intervals - then a
   containment test."
4. **Say why sorting by start time is the move**: after sorting, a bank that opens later than
   the point you have covered leaves a hole no later bank can fill.
5. **Ask about touching endpoints** before coding, and put your choice in a comment.
6. **Code the merge**, then the containment check.
7. **Offer the gaps version and the many-orders preprocessing** as improvements.

## Follow-ups and variations

- **"Many orders against the same bank set."** Merge once, then binary search
  (`bisect_right` on the merged starts) to find the candidate interval and test containment.
  `O(log n)` per order.
- **"Banks whose hours wrap past midnight"** (22:00 - 02:00). Split such an interval into
  `[22:00, 24:00)` and `[00:00, 02:00)` before merging. If **orders** can also wrap, split
  the order too and require both halves covered. State the assumption about whether the
  schedule repeats daily - if it does, working modulo 1440 with a doubled timeline
  (`[t, t+1440)`) is the clean trick.
- **"Return the gaps where trading is impossible."** Shown above.
- **"Which banks are needed?"** The greedy version naturally yields a minimal covering set -
  record which bank provided each `furthest` extension. This is
  *Minimum Number of Taps to Water a Garden* / *Video Stitching*.
- **"Banks have capacity or cost - pick the cheapest covering set."** Now it is weighted
  interval covering; the simple greedy no longer works and it becomes a DP.
- **"Streaming bank schedule updates."** Keep the merged set in a sorted container and
  insert/merge on update, `O(log n)` amortised.
- **"At least K banks open, not just one."** The merge trick no longer applies. Use a line
  sweep with +1/-1 events and check that the running count never drops below K inside the
  window - a genuinely different and better tool. Worth naming.

## Pitfalls

- **Reading it as "one bank must cover the whole window."** The reported failure. The given
  example disproves it in ten seconds if you check.
- **Not checking your interpretation against the provided example.** This is the general
  lesson: a worked example is a test of your *understanding*, not just of your code.
- **Using `<` instead of `<=`** when merging, so banks that touch exactly at an endpoint are
  treated as leaving a gap. Decide deliberately and comment it.
- **Comparing `"15:00"` as a string.** It happens to sort correctly for zero-padded 24-hour
  times, but arithmetic does not work. Convert to minutes.
- **Forgetting to sort** before merging.
- **Checking only that the order start and order end are each covered**, which passes when
  there is a hole in the middle.
- **Spending the round coding the wrong problem.** If you realise mid-interview that you
  misread, say so immediately and state the correct approach - the reported candidate ran
  out of time at exactly that moment. Naming the right algorithm out loud is worth far more
  than silently starting over.
