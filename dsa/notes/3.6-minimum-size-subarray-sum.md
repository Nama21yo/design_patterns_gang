**Link:** https://leetcode.com/problems/minimum-size-subarray-sum
**Difficulty:** Medium | **LeetCode #209**
**Bloomberg frequency:** 38% at three months.

The **shortest**-window problem, as opposed to the longest-window problems elsewhere in this
Part. That single difference moves where you record the answer, which is the thing to get
right. It is also the cleanest illustration of why the window needs **positive** values.

## 1. Problem statement

Given an array of **positive** integers `nums` and a positive integer `target`, return the
**minimal length** of a contiguous subarray whose sum is **greater than or equal to**
`target`. If there is no such subarray, return `0`.

```
nums = [2,3,1,2,4,3], target = 7  ->  2    the subarray [4,3]
nums = [1,4,4],       target = 4  ->  1
nums = [1,1,1,1,1,1,1,1], target = 11 -> 0
```

Follow-up: if you have figured out the `O(n)` solution, try an `O(n log n)` one.

## 2. Clarifying questions

1. **Are all values strictly positive?** Yes - stated, and it is **essential**. With
   negatives or zeros the window argument collapses; see below. **Ask this**, because it is
   the difference between this problem and 1.2.
2. **Is the condition `>= target` or `> target`?** `>=`.
3. **Return the length or the subarray?** The length; `0` when none exists.
4. **Contiguous?** Yes.
5. **Sizes?** Up to 10^5, so `O(n^2)` will time out.
6. **Can `target` be larger than the total sum?** Yes - example 3. Return 0.

## 3. Intuition

Brute force: every subarray, `O(n^2)` with a running sum.

The window works because all values are **positive**, which gives monotonicity:

> **Growing the window strictly increases the sum; shrinking strictly decreases it.**

So for each right end, there is a well-defined leftmost start that still satisfies
`sum >= target`, and it only moves forward as `right` advances. That is exactly the
precondition from the primer.

The shape:

1. Grow `right`, adding to the running sum.
2. **While** the sum is `>= target`, the window is **valid** - record its length, then shrink
   from the left to look for something shorter.
3. Continue.

### Where to record - the key difference

In the longest-window problems (3.1, 3.4) you record **after** the shrink loop, when the
window has just become valid again. Here you record **inside** the shrink loop, **before**
shrinking, because that is where the window is valid and you want the smallest valid one.

> **Record wherever the window satisfies what you are optimising for.** Longest: record when
> valid, after restoring validity. Shortest: record while valid, before destroying validity.

Getting this backwards silently produces wrong answers rather than crashes, so state it
deliberately as you write.

### Why negatives break it

If `nums` could contain a negative, then extending the window might *decrease* the sum, so
"the sum is big enough, shrink to find something shorter" is unsound - a longer window might
be the only valid one. With negatives you would need prefix sums plus a **monotonic deque**
(LC 862, *Shortest Subarray with Sum at Least K*), which is a genuinely harder problem.
Naming that is a strong close.

## 4. Approach

1. `left = 0`, `total = 0`, `best = infinity`.
2. For each `right`, `x`:
   - `total += x`
   - while `total >= target`: `best = min(best, right - left + 1)`; `total -= nums[left]`;
     `left += 1`
3. Return `best` if it changed, else `0`.

## 5. Solution

```python
def min_subarray_len(target, nums):
    """Shortest contiguous subarray with sum >= target, or 0 if none exists.

    All values are positive, so the sum is monotonic in the window size: that is what
    makes shrinking sound. The answer is recorded INSIDE the shrink loop, where the
    window is valid, because we want the smallest valid window.
    """
    left = 0
    total = 0
    best = float("inf")

    for right, x in enumerate(nums):
        total += x
        # While valid, record and then shrink to look for something shorter.
        while total >= target:
            best = min(best, right - left + 1)
            total -= nums[left]
            left += 1

    return best if best != float("inf") else 0
```

```python
min_subarray_len(7, [2, 3, 1, 2, 4, 3])         # 2
min_subarray_len(4, [1, 4, 4])                  # 1
min_subarray_len(11, [1, 1, 1, 1, 1, 1, 1, 1])  # 0
min_subarray_len(11, [1, 2, 3, 4, 5])           # 3
min_subarray_len(15, [1, 2, 3, 4, 5])           # 5
min_subarray_len(16, [1, 2, 3, 4, 5])           # 0
min_subarray_len(4, [])                         # 0
min_subarray_len(1, [1])                        # 1
min_subarray_len(5, [1])                        # 0
min_subarray_len(213, [12, 28, 83, 4, 25, 26, 25, 2, 25, 25, 25, 12])   # 8
```

`[1,2,3,4,5]` with three targets is the trio to check: `11` needs three elements (`3+4+5`),
`15` needs all five, and `16` is impossible. They exercise the general case, the
whole-array case, and the no-answer case.

### The O(n log n) follow-up

The stated follow-up. Since the values are positive, the **prefix sums are strictly
increasing**, which means you can binary search them.

```python
import bisect
import itertools


def min_subarray_len_binary(target, nums):
    """O(n log n). Positive values make the prefix sums strictly increasing, so for
    each start we can binary search for the first prefix that is large enough."""
    prefix = list(itertools.accumulate(nums, initial=0))     # prefix[i] = sum of nums[:i]
    best = float("inf")

    for start in range(len(nums)):
        # We want the smallest end with prefix[end] - prefix[start] >= target.
        needed = prefix[start] + target
        end = bisect.bisect_left(prefix, needed)
        if end <= len(nums):
            best = min(best, end - start)

    return best if best != float("inf") else 0


min_subarray_len_binary(7, [2, 3, 1, 2, 4, 3])          # 2
min_subarray_len_binary(4, [1, 4, 4])                   # 1
min_subarray_len_binary(11, [1, 1, 1, 1, 1, 1, 1, 1])   # 0
min_subarray_len_binary(11, [1, 2, 3, 4, 5])            # 3
min_subarray_len_binary(16, [1, 2, 3, 4, 5])            # 0
min_subarray_len_binary(4, [])                          # 0
```

Offer this when asked for the `O(n log n)` version, and point out the irony: it is **worse**
than the `O(n)` window. The follow-up exists to check you understand *why* binary search is
applicable - monotone prefix sums - not because it is an improvement. Saying that explicitly
is a good move.

### The brute force

```python
def min_subarray_len_brute(target, nums):
    """O(n^2) with a running inner sum."""
    best = float("inf")
    for i in range(len(nums)):
        total = 0
        for j in range(i, len(nums)):
            total += nums[j]
            if total >= target:
                best = min(best, j - i + 1)
                break               # extending only makes it longer
    return best if best != float("inf") else 0


min_subarray_len_brute(7, [2, 3, 1, 2, 4, 3])   # 2
min_subarray_len_brute(11, [1, 2, 3, 4, 5])     # 3
min_subarray_len_brute(16, [1, 2, 3, 4, 5])     # 0
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` |
| Binary search on prefix sums | `O(n log n)` | `O(n)` |
| **Sliding window** | **`O(n)`** | **`O(1)`** |

The window is linear by the usual argument: `left` only moves forward, so the inner `while`
performs at most `n` total iterations across the whole run. Say that - the nested loop always
invites the question.

## 7. How to present it

1. **Restate**, and **ask about positivity immediately.** Then say what it buys: *"Because
   every value is positive, the sum increases as the window grows - so the constraint is
   monotonic and a sliding window is valid."*
2. **Give the brute force** with its `O(n^2)`.
3. **Announce the window**, and **explicitly flag where the answer is recorded**: *"This is a
   shortest-window problem, so unlike the usual longest-window shape I record inside the
   shrink loop, while the window is still valid."* That sentence is the differentiator on
   this question.
4. **Write it.** Six lines.
5. **Handle the no-answer case** with the infinity sentinel and convert to `0` at the end.
6. **Trace `[2,3,1,2,4,3]`, target 7**: the window grows to `[2,3,1,2]` (sum 8) and records
   4, shrinks; later `[4,3]` records 2.
7. **Give the amortised argument** for linearity.
8. **Offer the follow-up** - and point out that the `O(n log n)` version is slower, and that
   it works because the prefix sums are increasing, which is again the positivity.
9. **Close by naming the negative-values variant** (LC 862) and that it needs a monotonic
   deque. That is a strong finish.

## 8. Follow-ups and variations

- **"Try the O(n log n) solution."** Binary search over prefix sums, shown above. Note it is
  a demonstration, not an improvement.
- **"What if the values can be negative?"** LC 862 - *Shortest Subarray with Sum at Least K*.
  The window is invalid; you need prefix sums plus a **monotonic deque** that keeps indices
  with increasing prefix values. Naming it precisely is the right answer; deriving it in the
  room is a big ask.
- **"Longest subarray with sum at most target."** The mirror problem, and still a window -
  but now you record after the shrink, because you want the longest valid window. A great
  question to check you understood the record-placement rule.
- **"Return the subarray, not the length."** Track the best start index.
- **"Exact sum instead of at least."** With positives, still a window (grow while too small,
  shrink while too big). With negatives, prefix sums plus a hash map - which is 1.2.
- **"Minimum size subarray with sum exactly target, values may be negative."** Prefix sums
  plus a hash map storing the **latest** index of each prefix value.
- **"2D version: smallest submatrix with sum at least target."** Fix a row pair, compress the
  columns, and run this algorithm - `O(rows^2 * cols)`.
- **"What if `target` changes across many queries?"** Precompute the prefix array once and
  binary search per query - here the `O(n log n)` version finally earns its keep.

## 9. Pitfalls

- **Recording the answer after the shrink loop** instead of inside it. Produces wrong
  answers silently. The defining bug for shortest-window problems.
- **Using `if` instead of `while`** for the shrink, so only one element is removed per step.
- **Initialising `best` to `0`** - then `min` never updates. Use infinity and convert at the
  end.
- **Returning `float("inf")`** when no subarray qualifies; the spec says `0`.
- **Applying the window to arrays with negative values.** Ask.
- **Computing the length as `right - left`.**
- **Forgetting to subtract `nums[left]`** before advancing `left`.
- **Claiming `O(n^2)`** because of the nested `while`; give the amortised argument.
