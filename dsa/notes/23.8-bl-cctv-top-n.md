> Reported 3 times in R2 on 2025-10-22 and 2025-10-30. One candidate's report lists the
> exact optimisations the interviewer walked them through - they are reproduced below, and
> they are the scoring rubric for this question.

## Prompt as given

```
Implement a module for a CCTV camera by a highway. It logs traffic events (a car passes
by) and provides aggregate on-demand statistics about the traffic so far.

  record(brand)
      log the brand of a vehicle passing under the camera

  printStatistics(n, start_time, end_time)
      print the top n most frequently detected brands in [start_time, end_time],
      together with their counts.

E.g. if between 9:00 and 10:00 there were 500 Sedans, 5 motorcycles, 200 SUVs and
50 trucks, then

  for N=1:  Sedan: 500
  for N=2:  Sedan: 500
            SUV: 200
```

Related LeetCode problems:
[Top K Frequent Elements](https://leetcode.com/problems/top-k-frequent-elements/),
[Design Hit Counter](https://leetcode.com/problems/design-hit-counter/).

## Clarifying questions to ask first

1. **Is the timestamp supplied, or taken from the clock inside `record`?** The prompt implies
   `datetime.now()` inside `record`. Ask - taking it as a parameter makes the class testable
   and you should say that.
2. **Is the range inclusive at both ends?** Assume `[start, end]` inclusive; confirm.
3. **How many distinct brands?** Small (tens), versus how many events (millions). This ratio
   decides the whole design, so **ask it explicitly**.
4. **How often is `printStatistics` called relative to `record`?** Write-heavy or read-heavy
   changes the answer.
5. **Are the queries always recent windows, or arbitrary historical ranges?** A "last hour"
   query has a much cheaper solution than an arbitrary range.
6. **Ties?** If two brands have the same count, which comes first? Pick alphabetical and say so.
7. **Does the log have to be retained forever?**

## Intuition

Two separate problems dressed as one:

**(a) Finding the events in `[start, end]`.** Events are appended in real time, so the log is
**already sorted by timestamp**. That is the key observation - and it is the one the
interviewer explicitly asked a candidate to justify. Because it is sorted, you binary search
for the range boundaries instead of scanning: `bisect_left(start)` and `bisect_right(end)`.
The justification to say out loud: *"events are recorded as they happen, so timestamps are
non-decreasing by construction, which is exactly the precondition binary search needs."*

**(b) Finding the top n of the counts.** Once you have the slice, you build a frequency map.
Sorting the whole map is `O(m log m)` for `m` distinct brands. But you only want `n` of
them, so a **size-n min-heap** gives `O(m log n)`. With `m` brands and `n` small, that is
the better bound - and `heapq.nlargest` does exactly this for you.

Note the honest caveat, which is worth raising yourself: binary search removes the scan over
*irrelevant* events, but you still scan every event *inside* the window to build the counts.
So a query over a wide window is still linear in the window size. If they push on that, you
need prefix counts or a segment tree - see the follow-ups.

## Approach

1. `self.events`: a list of `(timestamp, brand)`, appended in order.
2. `record(brand)`: append `(now, brand)`. `O(1)`.
3. `printStatistics(n, start, end)`:
   - `lo = bisect_left(events, (start,))`, `hi = bisect_right(events, (end, HIGH))`
   - `Counter(brand for _, brand in events[lo:hi])`
   - `heapq.nlargest(n, counter.items(), key=...)` with the tie-break
   - print

The bisect keys need care: tuples compare lexicographically, so `(start,)` sorts before any
`(start, brand)`, which is what `bisect_left` wants for an inclusive start. For an inclusive
end you need a sentinel that sorts after every brand at that timestamp - searching on the
timestamps alone with a parallel list is cleaner.

## Solution

```python
import bisect
import heapq
from collections import Counter
from datetime import datetime


class TrafficMonitor:
    """Logs vehicles passing a CCTV camera and reports the top-N brands in a time range."""

    def __init__(self):
        # Two parallel lists rather than a list of tuples: `times` can then be bisected
        # directly, with no sentinel gymnastics for the inclusive upper bound.
        self.times = []
        self.brands = []

    def record(self, brand, timestamp=None):
        """O(1). Timestamp is injectable so the class is testable; defaults to now."""
        timestamp = timestamp or datetime.now()
        # Events arrive in real time, so `times` stays sorted - which is the precondition
        # that makes the binary search in printStatistics valid.
        self.times.append(timestamp)
        self.brands.append(brand)

    def statistics(self, n, start_time, end_time):
        """Top n brands in the inclusive range, as a list of (brand, count),
        most frequent first, ties broken alphabetically."""
        lo = bisect.bisect_left(self.times, start_time)
        hi = bisect.bisect_right(self.times, end_time)

        counts = Counter(self.brands[lo:hi])

        # nlargest keeps a heap of size n, so this is O(m log n) for m distinct brands,
        # rather than the O(m log m) of a full sort. Take the n largest by COUNT only,
        # then order that short list properly - see the note on ties below.
        top = heapq.nlargest(n, counts.items(), key=lambda kv: kv[1])
        top.sort(key=lambda kv: (-kv[1], kv[0]))
        return top

    def printStatistics(self, n, start_time, end_time):
        for brand, count in self.statistics(n, start_time, end_time):
            print(f"{brand}: {count}")
```

**Why the tie-break is two steps.** `nlargest` sorts *descending* by the key, so a single
key of `(count, brand)` would rank ties by brand **descending** - putting `"Zeta"` before
`"Alpha"`. You cannot express "count descending, brand ascending" in one `nlargest` key
without inverting the string, which is ugly. So: select by count alone, then sort the
short result list with `(-count, brand)`. That final sort is over at most `n` items, so it
costs nothing asymptotically, and it states the ordering rule in a form you can read aloud.

```python
from datetime import datetime, timedelta

m = TrafficMonitor()
base = datetime(2025, 1, 1, 9, 0)
for i in range(500): m.record("Sedan",      base + timedelta(seconds=i))
for i in range(200): m.record("SUV",        base + timedelta(seconds=i))
for i in range(50):  m.record("Truck",      base + timedelta(seconds=i))
for i in range(5):   m.record("Motorcycle", base + timedelta(seconds=i))
m.printStatistics(2, base, base + timedelta(hours=1))
# Sedan: 500
# SUV: 200
```

Note that this example records out of timestamp order (all Sedans, then all SUVs), which
**breaks the sorted invariant**. In the real class `record` is called as vehicles pass, so
the order is naturally correct - but it is worth an `assert` if you want to be defensive:

```python
        if self.times and timestamp < self.times[-1]:
            raise ValueError("events must be recorded in non-decreasing time order")
```

Raising this in the interview - "my binary search depends on an invariant, so let me state
it" - is exactly the kind of thing that earns the round.

## Complexity

Let `E` be total events, `W` the events inside the queried window, and `m` the distinct
brands inside it.

| Operation | Time | Space |
|---|---|---|
| `record` | `O(1)` amortised | `O(1)` |
| `printStatistics`, naive scan + sort | `O(E + m log m)` | `O(m)` |
| `printStatistics`, bisect + nlargest | `O(log E + W + m log n)` | `O(m)` |

Total space is `O(E)` for the log.

The improvement the interviewer was driving at is the two separate `log` terms: binary
search replaces the `O(E)` scan with `O(log E)`, and the heap replaces `O(m log m)` with
`O(m log n)`. Say both, separately - they are two different optimisations and the report
lists them as two different follow-ups.

## How to present it

1. **Write the two method signatures and their target complexity.** `record` must be cheap
   (it is on the hot path, one call per vehicle); `printStatistics` is on demand.
2. **Start with the naive version and say its cost**: append on record, scan the whole log
   and sort on query. Get it working first - it is eight lines.
3. **Then optimise, in the order the interviewer will ask:**
   - "The log is sorted by time, because I append in real time - so I can binary search the
     range instead of scanning." **Volunteer the justification of the invariant**, do not
     wait to be asked; one report shows the interviewer asking precisely that.
   - "I only need the top n, not a full ordering, so a size-n heap beats a sort."
4. **Mention the remaining weakness yourself**: you still touch every event in the window.
   Then offer bucketing, below.
5. **Close** on the tie-break rule and the empty-range case.

## Follow-ups and variations

- **"Use a min-heap to get the top N instead of sorting."** `heapq.nlargest(n, ...)`, or
  hand-roll it: push onto a heap, pop when it exceeds size `n`. Be ready to write the manual
  version - it is a common request:
  ```python
  heap = []                                  # min-heap of (count, brand), size <= n
  for brand, count in counts.items():
      heapq.heappush(heap, (count, brand))
      if len(heap) > n:
          heapq.heappop(heap)                # evict the smallest count seen so far
  return sorted(heap, key=lambda kv: (-kv[0], kv[1]))
  ```
- **"Use binary search for the event range."** `bisect_left` / `bisect_right`, as above.
- **"How can you guarantee binary search works on the events list?"** Asked verbatim.
  Answer: events occur sequentially and are appended on arrival, so timestamps are
  non-decreasing by construction. Add the assertion. If events could arrive out of order,
  binary search is invalid and you would need a sorted container or a buffer with a
  watermark.
- **"What if the log does not fit in memory?"** Stop storing raw events. Bucket by time
  (say one `Counter` per minute) and keep a rolling window; a range query then merges the
  buckets it covers, which is `O(buckets)` not `O(events)`. Memory becomes
  `O(buckets * distinct brands)`. This is the right answer and it also fixes the "still
  linear in the window" weakness.
- **"What if you need statistics continuously, not on demand?"** Maintain the counts
  incrementally with a sliding window: a deque of events plus a live `Counter`, evicting
  from the front as time advances. Then the top-n is a query against a much smaller
  structure, and you can keep a heap alongside with lazy deletion.
- **"Arbitrary historical ranges, fast."** Prefix counts per brand, or a segment tree /
  Fenwick tree over time buckets holding per-brand counts. Query becomes
  `O(log buckets * brands)`. Say that this only pays off when brands are few.
- **"Millions of distinct brands, approximate is fine."** Count-Min Sketch plus a heap of
  heavy hitters - the classic streaming top-k. Naming it is enough.
- **"Retention policy."** Drop buckets older than the retention period; `O(1)` per eviction.
- **This is a bridge into the system design round** - the Bloomberg "Top-K most popular news
  in the past 8 hours" design question is the distributed version of exactly this. Say so if
  the conversation drifts that way.

## Pitfalls

- **Scanning all events on every query.** Works, but the round is about removing that.
- **Sorting the whole frequency map** when `n` is 1 or 2.
- **`bisect` on a list of tuples without thinking about the second element**, which makes the
  inclusive upper bound wrong. Parallel lists sidestep it.
- **Getting the tie-break backwards** with `nlargest` and a `(count, brand)` key.
- **Mutating the events list on eviction while bisect indices are live.**
- **Forgetting the empty-range case**, where `Counter` is empty and `nlargest` returns `[]` -
  which is fine, but `printStatistics` should not crash.
- **`self.vehicle_store.append((type, datetime.now()))` then sorting on query.** If you are
  going to sort, the sorted invariant was never real; decide which it is.
- In the circulating version, `store.append(vehicle_type, frequency)` - `list.append` takes
  one argument. And reusing the loop variable name `frequency` for both the dict and the
  count shadows it. Small things, but they are what a reviewer notices.
