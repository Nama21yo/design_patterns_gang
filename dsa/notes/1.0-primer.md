*Trade memory for time: a dict or a running total turns a nested loop into one pass.*

This is the largest and most fundamental pattern in the course - 82 Bloomberg-tagged
questions - and it underpins several others. Two Sum is the single most frequently reported
Bloomberg question of all time, and Subarray Sum Equals K is near the top of the 30-day
window.

## The core trade

Almost every question in this Part is the same move:

> **A brute force recomputes something it has already seen. Store it instead.**

| What you keep re-deriving | What you store | Cost |
|---|---|---|
| "have I seen this value?" | a `set` | `O(1)` lookup, `O(n)` memory |
| "how many times have I seen it?" | a `Counter` | same |
| "where did I see it?" | a `dict` value -> index | same |
| "what is the sum of `a[i..j]`?" | prefix sums | `O(1)` range query after `O(n)` setup |
| "what is the sum of a *window*?" | a running total | `O(1)` per step (Part 3) |

`O(n)` extra memory for an `O(n)` factor of time is almost always the right trade in an
interview. Say it explicitly: *"I'll trade linear space for linear time."*

## What a hash table actually is

Asked verbatim in these loops - *"how does hashing work in a set and a hash map?"* - so this
is not background, it is examinable. The full answer is in [[0.6 Python toolkit for
interviews]]; the short version:

A hash function maps the key to an integer; that integer is reduced to a bucket index;
collisions are resolved by chaining or open addressing (CPython uses open addressing);
when the load factor passes about two-thirds the table is resized and everything rehashed,
which is `O(n)` but rare enough that insertion is **amortised `O(1)`**. Worst case is
`O(n)` per operation if everything collides.

Consequences that actually affect your code:

- **Keys must be hashable**, i.e. immutable. A `list` cannot be a key; a `tuple` can. This is
  why the counting-based anagram key is `tuple(counts)` and not `counts`.
- **`x in some_list` is `O(n)`; `x in some_set` is `O(1)`.** The single most common
  accidental quadratic in interview code.
- Say **"average"** when you quote `O(1)`.

## Recognition signals

Reach for a hash map when the problem says any of:

- "have we seen", "already exists", "duplicate", "unique"
- "count of", "frequency", "most common", "appears k times"
- "pair / triple that sums to", "complement", "difference of"
- "group by", "anagrams", "same when normalised"
- "first non-repeating", "first occurrence"

Reach for prefix sums when it says:

- "subarray sum", "range sum", "sum between i and j"
- "equal number of X and Y" (map to +1/-1 and look for a repeated prefix)
- "average of a subarray", "pivot index", "balance point"
- repeated range queries on a static array

## Technique 1: the complement trick

The engine behind the entire Two Sum family.

For `a + b == target`, rearrange to `b == target - a`. So each element has **exactly one**
partner value, and a hash map finds it in `O(1)`.

```python
def two_sum(nums, target):
    """Indices of the two numbers adding to target."""
    seen = {}                       # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return (seen[target - x], i)
        seen[x] = i                 # recorded AFTER the lookup
    return None


two_sum([2, 7, 11, 15], 9)          # (0, 1)
two_sum([3, 3], 6)                  # (0, 1)
two_sum([3], 6)                     # None
```

**The ordering of those two lines is the whole correctness argument**, and it recurs
throughout this Part:

> Look up first, record second. That way the current element can never pair with itself,
> and every pair is found exactly once - at the moment you reach its *second* member.

Test it with `[3]` and target `6`: if you recorded first, `3 + 3 == 6` would match the same
element and return a bogus pair.

For a **difference** rather than a sum, `b - a == target` gives `b == a + target` - still one
complement, but subtraction is not commutative, so you must check **both** `x - target` and
`x + target` (see 23.17).

## Technique 2: frequency maps

```python
from collections import Counter

c = Counter("mississippi")
c["s"]                              # 4
c["z"]                              # 0   -- no KeyError, and no insertion
c.most_common(1)                    # [('i', 4)]
```

`Counter` beats `defaultdict(int)` on read paths because reading a missing key does **not**
create it. With `defaultdict`, `if d[k] > 0:` silently grows the dict forever.

Counter arithmetic is multiset arithmetic and is worth memorising:

```python
Counter("aab") - Counter("ab")                              # Counter({'a': 1})
sum((Counter("leetcode") - Counter("practice")).values())   # 5
Counter("listen") == Counter("silent")                      # True
```

The subtraction drops non-positive counts, which is exactly "what do I still need".

## Technique 3: canonical keys ("group by")

To group things that are "the same" under some normalisation, build a **key** that is equal
exactly when they should be grouped:

```python
from collections import defaultdict


def group_anagrams(words):
    groups = defaultdict(list)
    for word in words:
        groups["".join(sorted(word))].append(word)      # sorted letters = canonical form
    return list(groups.values())


group_anagrams(["dog", "god", "oak"])       # [['dog', 'god'], ['oak']]
```

Two standard anagram keys:
- **sorted string** - `O(L log L)` per word, compact, easy to say;
- **26-count tuple** - `O(L)` per word, bigger key, better for long words.

Crucially, a canonical key is **not a hash**. A hash can collide and group unrelated items;
a canonical form cannot. This distinction is the actual bug in the reported App Store
ingestion question (23.22) - say it if the word "hash" appears in a prompt.

## Technique 4: prefix sums

Define `prefix[i]` = sum of the first `i` elements, with `prefix[0] = 0`. Then

> **sum of `a[i..j)` = `prefix[j] - prefix[i]`**

One `O(n)` pass buys `O(1)` range queries forever.

```python
import itertools

a = [3, 1, 4, 1, 5]
prefix = list(itertools.accumulate(a, initial=0))
prefix                                  # [0, 3, 4, 8, 9, 14]
prefix[4] - prefix[1]                   # 6    -- sum of a[1:4] = 1 + 4 + 1
```

The `initial=0` matters: without the leading zero you need a special case for `i == 0`.
Off-by-one errors in prefix sums almost always trace back to a missing sentinel.

### Prefix sums plus a hash map - the important one

For "how many subarrays sum to `k`", combine the two techniques. If
`prefix[j] - prefix[i] == k`, then `prefix[i] == prefix[j] - k`. So as you sweep, count how
many earlier prefixes equal `current - k`:

```python
from collections import defaultdict


def subarray_sum_count(nums, k):
    """Number of contiguous subarrays summing to k. Works with negatives."""
    counts = defaultdict(int)
    counts[0] = 1                   # the empty prefix, so a prefix equal to k itself counts
    total = running = 0
    for x in nums:
        running += x
        total += counts[running - k]
        counts[running] += 1
    return total


subarray_sum_count([1, 1, 1], 2)        # 2
subarray_sum_count([1, -1, 0], 0)       # 3
```

`counts[0] = 1` is the sentinel and it is the most commonly forgotten line in this pattern.
Without it you miss every subarray that starts at index 0.

**Why this and not a sliding window?** A sliding window needs the sum to move *monotonically*
as the window grows, which requires non-negative values. With negatives, growing the window
can decrease the sum, so the window is invalid and prefix-sum-plus-hashmap is the correct
tool. Knowing which of the two applies is the single most useful distinction between this
Part and Part 3.

### The +1/-1 trick

"Equal numbers of X and Y in a subarray" becomes "subarray summing to 0" if you map X to
`+1` and Y to `-1`:

```python
def longest_balanced(nums):
    """Longest subarray with equal 0s and 1s."""
    first_seen = {0: -1}            # prefix value -> earliest index
    running = best = 0
    for i, x in enumerate(nums):
        running += 1 if x == 1 else -1
        if running in first_seen:
            best = max(best, i - first_seen[running])
        else:
            first_seen[running] = i     # keep the EARLIEST index, for the longest span
    return best


longest_balanced([0, 1, 0])             # 2
longest_balanced([0, 1, 1, 0, 1, 1])    # 4
```

Note the asymmetry with the counting version: here you keep the **earliest** index and do
**not** overwrite, because you want the longest span. In the counting version you accumulate
all of them. Getting this backwards is a classic bug.

### Difference arrays

The dual of prefix sums: for many **range updates** and one final read, add `+v` at `start`
and `-v` at `end+1`, then prefix-sum once at the end.

```python
def apply_ranges(n, updates):
    """updates: (start, end_inclusive, value). O(1) per update, O(n) once at the end."""
    diff = [0] * (n + 1)
    for start, end, value in updates:
        diff[start] += value
        diff[end + 1] -= value
    out, running = [], 0
    for i in range(n):
        running += diff[i]
        out.append(running)
    return out


apply_ranges(5, [(1, 3, 2), (2, 4, 3)])     # [0, 2, 5, 5, 3]
```

## Template: the one-pass hash scan

Most questions in this Part are this shape.

```python
def one_pass(items):
    state = {}                      # or Counter(), or a running total
    answer = init
    for i, x in enumerate(items):
        # 1. QUERY the state for what x needs
        # 2. UPDATE the answer
        # 3. RECORD x in the state   <- after the query, not before
        pass
    return answer
```

Query, update, record. In that order.

## How to talk about it

- "I'll trade O(n) space for O(n) time by keeping a hash map of what I've seen."
- "Each element has exactly one complement, `target - x`, so the lookup is constant time."
- "I record the element *after* the lookup, so it can't pair with itself."
- "Because I count at the second element of each pair, every pair is counted exactly once
  and I don't need any deduplication."
- "The sum of a range is the difference of two prefix sums, so one pass buys me O(1) queries."
- "I seed the prefix count with `{0: 1}` for the empty prefix - otherwise subarrays starting
  at index 0 are missed."
- "With negative values a sliding window isn't valid, because growing the window doesn't
  monotonically increase the sum. So it's prefix sums plus a hash map."
- "That's O(1) *average* - it rests on hashing."

## Common pitfalls across this Part

- **`x in list` instead of `x in set`.** Quietly quadratic.
- **Recording before querying**, letting an element pair with itself.
- **Forgetting `counts[0] = 1`** in the prefix-sum-plus-hashmap counting pattern.
- **Overwriting a first-seen index** when you wanted the earliest (longest span), or keeping
  the earliest when you wanted a count.
- **Using `defaultdict` on a read path** and silently growing it.
- **Using a `set` when multiplicity matters** - `[1,1,1,1]` breaks it.
- **Unhashable keys** - a `list` cannot be a dict key; use a `tuple`.
- **Assuming a sliding window works with negative numbers.**
- **Mutating a dict while iterating it.**
- **Quoting `O(1)` without saying "average".**
