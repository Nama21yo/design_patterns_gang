---
title: "23.13 Find the process that caused a cascade of aborts"
---

> Reported once in R1 on 2025-11-04. A small problem with a sharp follow-up: the clean
> answer is three lines, and the follow-up asks you to detect that the input is not actually
> a tree.

## Prompt as given

```
Assume an operating system. Processes can have children, grandchildren and so on. Every
process has a parent except one root process. A process knows its children but NOT its
parent. When a process is aborted all of its descendants are aborted with it. A log records
every aborted process. Find the initial process that caused all the aborts.

  log = [{id: 1, children: [2, 3]}, {id: 2, children: [4]},
         {id: 3, children: []},     {id: 4, children: []}]

        1
       / \
      2   3
      |
      4

  answer = 1
```

Follow-up as given: *what if a process has multiple parents, or there are cycles? Return
None / stop your computation.*

Related: [Minimum Number of Vertices to Reach All Nodes](https://leetcode.com/problems/minimum-number-of-vertices-to-reach-all-nodes/),
[Find the Town Judge](https://leetcode.com/problems/find-the-town-judge/).

## Clarifying questions to ask first

1. **Does the log contain exactly the aborted processes, or the whole process table?** It
   says "a log that logs all the processes that are aborted", so it is the aborted set only.
   This matters: it means the root of the *log* is what we want, not the root of the system.
2. **Is every process in the log guaranteed to appear as a top-level entry**, or can a child
   id be mentioned without its own entry? In the sample, `4` is both a child of `2` and its
   own entry. Ask - it decides whether you iterate entries or ids.
3. **Is there exactly one culprit?** The prompt implies yes. Ask what to do if the log
   contains two unrelated aborted subtrees.
4. **Can the log be empty?** Return `None`.
5. **Are ids unique?** Assume yes.
6. **Do I need to validate the structure, or trust it?** The follow-up says validate - so ask
   up front and you will have framed the whole answer.

## Intuition

Forget trees for a second and look at it as a counting problem.

Every process in the log has exactly one parent **except the culprit**, because the culprit
is the one that was aborted directly and everything else was aborted *by* its parent. And
the log tells you, for each process, who its children are.

> **So: the culprit is the only id that never appears in anybody's children list.**

One pass to collect all ids, one pass to collect all ids that appear as someone's child, and
the answer is the single element of the difference. No traversal, no recursion, no depth
tracking. `O(n)` time and `O(n)` space.

This reframing - "find the node with in-degree zero" - is the whole question, and it is
worth saying in exactly those words, because it also sets up the follow-up: if the structure
is a genuine tree there is **exactly one** node with in-degree zero, so checking the size of
that set is how you detect a malformed input.

People reach for "build the tree, find the deepest / traverse from each node and see which
one reaches everything". Both work and both are worse: `O(n^2)` for the second, and the
first needs the parent pointers you were explicitly told you do not have.

## Approach

1. Collect `all_ids` - every id that has an entry in the log.
2. Collect `has_parent` - every id that appears in some entry's `children` list.
3. `roots = all_ids - has_parent`.
4. Exactly one root: return it. Zero roots: there is a cycle. More than one: disconnected
   forest. Both are the follow-up.

## Solution

```python
def find_culprit(log):
    """The process that was aborted directly, causing all the others.

    Every aborted process has exactly one parent except the one that started it, so the
    culprit is the unique id that never appears in any children list - in-degree zero.
    """
    all_ids = {entry["id"] for entry in log}
    has_parent = {child for entry in log for child in entry["children"]}

    roots = all_ids - has_parent
    if len(roots) != 1:
        return None                 # zero roots means a cycle; more than one is a forest
    return roots.pop()
```

```python
log = [{"id": 1, "children": [2, 3]}, {"id": 2, "children": [4]},
       {"id": 3, "children": []},     {"id": 4, "children": []}]
find_culprit(log)          # 1
```

### The validating version - the answer to the follow-up

The follow-up asks for `None` when a process has multiple parents or there are cycles.
In-degree zero alone does not catch "multiple parents": a node can have two parents and the
root is still unique. So count in-degrees rather than just collecting a set, and check
reachability.

```python
from collections import defaultdict, deque


def find_culprit_validated(log):
    """Returns the culprit, or None if the abort log is not a valid tree.

    Rejects: no root, several roots, any process with more than one parent, cycles,
    and any process not reachable from the root.
    """
    children = {entry["id"]: list(entry["children"]) for entry in log}
    if not children:
        return None

    # Every id mentioned anywhere, so a child with no entry of its own still counts.
    all_ids = set(children)
    for kids in children.values():
        all_ids.update(kids)

    in_degree = defaultdict(int)
    for kids in children.values():
        for child in kids:
            in_degree[child] += 1
            if in_degree[child] > 1:
                return None          # multiple parents: not a tree

    roots = [node for node in all_ids if in_degree[node] == 0]
    if len(roots) != 1:
        return None                  # 0 roots => a cycle exists; >1 => disconnected forest
    root = roots[0]

    # Walk from the root. If we cannot reach everything, there is a disjoint cycle
    # sitting off to the side that the in-degree check alone would not have caught.
    seen = {root}
    queue = deque([root])
    while queue:
        node = queue.popleft()
        for child in children.get(node, ()):
            if child in seen:
                return None          # revisiting inside a tree walk means a cycle
            seen.add(child)
            queue.append(child)

    return root if seen == all_ids else None
```

```python
ok       = [{"id": 1, "children": [2, 3]}, {"id": 2, "children": [4]},
            {"id": 3, "children": []},     {"id": 4, "children": []}]
two_dads = [{"id": 1, "children": [2, 3]}, {"id": 2, "children": [4]},
            {"id": 3, "children": [4]},    {"id": 4, "children": []}]
cycle    = [{"id": 1, "children": [2]},    {"id": 2, "children": [3]},
            {"id": 3, "children": [1]}]
forest   = [{"id": 1, "children": [2]},    {"id": 2, "children": []},
            {"id": 3, "children": []}]
side_cyc = [{"id": 1, "children": [2]},    {"id": 2, "children": []},
            {"id": 3, "children": [4]},    {"id": 4, "children": [3]}]

find_culprit_validated(ok)        # 1
find_culprit_validated(two_dads)  # None  (4 has two parents)
find_culprit_validated(cycle)     # None  (no in-degree-zero node)
find_culprit_validated(forest)    # None  (two roots)
find_culprit_validated(side_cyc)  # None  (root 1 does not reach the 3-4 cycle)
```

The `side_cyc` case is the one worth pointing at: there *is* a unique in-degree-zero node
(`1`), and no node has two parents, yet the log is still not a tree because `3` and `4` form
a separate cycle. Only the reachability walk catches it. Finding that case yourself, before
the interviewer constructs it, is the strongest move available here.

## Complexity

Let `n` be the number of log entries and `E` the total number of child references.

| | Time | Space |
|---|---|---|
| Set-difference version | `O(n + E)` | `O(n + E)` |
| Validating version | `O(n + E)` | `O(n + E)` |
| "Traverse from every node" | `O(n * (n + E))` | `O(n)` |

Both good versions are a small constant number of linear passes. Say "linear in the size of
the log" rather than quoting `n` alone, since `E` can exceed `n`.

## How to present it

1. **Draw the sample tree.** It takes five seconds and makes the in-degree idea visible.
2. **State the reframing immediately**: "every aborted process has exactly one parent except
   the culprit, and the log gives me children lists - so the culprit is the id with
   in-degree zero." That single sentence is the solution.
3. **Say what you are *not* doing and why**: no need to build parent pointers, no need to
   traverse, no need to measure depth. Explicitly rejecting the more obvious approaches is a
   signal.
4. **Write the three-line version.** Then pause on `len(roots) != 1` and say: "this is
   already where the malformed cases will show up."
5. **Pre-empt the follow-up** by asking whether the log is trusted. When they ask for
   multiple parents and cycles, extend to in-degree counting plus a reachability walk.
6. **Construct the side-cycle case yourself** and show why the first two checks miss it.
7. **Close** on linear complexity and the empty-log behaviour.

## Follow-ups and variations

- **"What if a process has multiple parents, or there are cycles? Return None."** The stated
  follow-up. Three distinct failure modes, and you need all three checks: in-degree > 1, no
  in-degree-zero node, and unreachable-from-root. Enumerate them explicitly.
- **"What if several independent roots aborted? Return all of them."** Drop the `len(roots)
  != 1` rejection and return the list. This is exactly
  *Minimum Number of Vertices to Reach All Nodes* - name it.
- **"What if the log is incomplete"**, i.e. a child id appears with no entry of its own? The
  validating version already handles it by seeding `all_ids` from both sources. Ask whether
  a mentioned-but-unlogged child means the log is corrupt or just terse.
- **"Do it without extra space."** Not really possible in one pass without the id set, but if
  ids are `1..n` you can use an in-degree array of size `n`, which is `O(n)` but with a tiny
  constant and no hashing. Worth mentioning.
- **"What if you only had parent pointers instead of children?"** Then it is the opposite
  walk: follow parents up until you reach one with no parent, with a visited set to catch
  cycles. Trivial, and the contrast is worth a sentence.
- **"Now the log has timestamps - find who aborted first."** Then it is a `min` over the log
  and the tree structure is irrelevant. A nice reminder to ask what data you actually have.
- **"Return the whole aborted subtree in order."** BFS or DFS from the culprit.
- **"The process table is huge and streamed."** You cannot hold `all_ids`; you would need two
  passes over the stream, or a Bloom filter for the has-parent set with a verification pass.

## Pitfalls

- **Building the tree and searching for the deepest node.** Depth has nothing to do with it,
  and it is more code and more ways to be wrong.
- **Assuming the root id is the smallest**, or that it is the first entry in the log. Neither
  is stated.
- **Using only `all_ids - has_parent` for the follow-up.** It catches cycles that swallow the
  whole graph and it catches forests, but it does **not** catch multiple parents, and it does
  **not** catch a cycle sitting beside a valid tree.
- **Iterating only over entry ids** when collecting `all_ids`, so a child mentioned without
  its own entry is invisible.
- **Infinite recursion** on the cyclic input if you traverse without a visited set.
- **Returning `roots.pop()` without checking the size first** - it will happily return an
  arbitrary element of a two-element set.
- **Mutating `entry["children"]`** while iterating, if you try to build parent pointers in
  place.
