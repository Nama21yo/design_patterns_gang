The third answer-search question in Part 5, and the one where the **monotonicity is least
obvious** - so it is the best test of whether you understood the technique or memorised the
shape. The feasibility check also has a genuine detail: bouquets need **adjacent** flowers.

> Read [[5.6 Koko Eating Bananas]] first.

## 1. Problem statement

You are given an array `bloomDay`, an integer `m` and an integer `k`.

You want to make `m` bouquets. Each bouquet needs `k` **adjacent** flowers from the garden.
The `i`-th flower blooms on day `bloomDay[i]` and can only be used **on or after** that day.

Return the **minimum number of days** you need to wait to make `m` bouquets, or `-1` if it is
impossible.

```
bloomDay = [1,10,3,10,2], m = 3, k = 1  ->  3
    after day 3, flowers 0, 2 and 4 have bloomed - three bouquets of one

bloomDay = [1,10,3,10,2], m = 3, k = 2  ->  -1
    only 5 flowers, so 3 bouquets of 2 would need 6

bloomDay = [7,7,7,7,12,7,7], m = 2, k = 3  ->  12
```

## 2. Clarifying questions

1. **Must the `k` flowers in a bouquet be adjacent in the array?** **Yes** - this is the
   detail that makes the counting non-trivial. Without adjacency you would just count bloomed
   flowers and divide.
2. **Can bouquets share flowers?** No - each flower is used at most once, so runs are
   consumed greedily.
3. **When is it impossible?** When `m * k > len(bloomDay)`. Check this **first** - it is the
   `-1` case and it also guarantees a solution exists afterwards.
4. **Do flowers stay usable after blooming?** Yes, so "bloomed by day `d`" is
   `bloomDay[i] <= d`.
5. **Sizes?** Up to 10^5 flowers with bloom days up to 10^9, so a scan over days is
   impossible.
6. **Return the day, or the number of days to wait?** The day number.

## 3. Intuition

### Why it is an answer-search

The quantity to minimise is a **day**, and:

> **If you can make `m` bouquets by day `d`, you can also make them by any later day -
> flowers that have bloomed stay bloomed, so waiting never removes options.**

So `feasible(d)` is monotone: `F F F T T T` in the day. Binary search on the day.

That "flowers stay bloomed" observation is the monotonicity proof, and it is worth one
explicit sentence - it is less obvious here than "a faster speed never hurts".

### The feasibility check

Given a day `d`, a flower is available iff `bloomDay[i] <= d`. Walk the array counting the
current run of consecutive available flowers; every time the run reaches `k`, take a bouquet
and **reset the run to 0**.

```
run = 0, bouquets = 0
for day in bloomDay:
    if day <= d:  run += 1
                  if run == k:  bouquets += 1; run = 0
    else:         run = 0
feasible(d) = bouquets >= m
```

Two details that matter:

- **Reset the run to 0 after taking a bouquet**, not to `run - k`. They coincide here because
  you take a bouquet the instant the run hits `k`, but writing `run = 0` makes the
  "flowers are consumed" semantics explicit.
- **Reset the run on an unbloomed flower.** A gap breaks adjacency entirely.

The greedy (take a bouquet as soon as `k` adjacent flowers are available) is optimal because
runs are independent: a run of length `L` yields exactly `L // k` bouquets no matter how you
carve it. Saying that is the justification.

### The search range

- **`lo = min(bloomDay)`.** Before the first bloom nothing is available, so no earlier day
  can ever work.
- **`hi = max(bloomDay)`.** By then every flower has bloomed, which is the best the garden
  ever gets. If that is not enough, nothing is - but the `m * k > n` check has already ruled
  that out.

Using `[1, max]` also works and costs one extra iteration; `min` is tighter and shows you
thought about it.

### The impossibility check

`m * k > len(bloomDay)` means there are not enough flowers, full stop. Do this **before** the
search - otherwise the binary search runs to `max(bloomDay)` and returns a day at which the
requirement still is not met, giving a wrong answer rather than `-1`.

**Guard against overflow in `m * k`** in a fixed-width language; in Python it is fine.

## 4. Approach

1. If `m * k > len(bloomDay)`, return `-1`.
2. `lo, hi = min(bloomDay), max(bloomDay)`.
3. While `lo < hi`: `mid = (lo + hi) // 2`; if `feasible(mid)`, `hi = mid`, else
   `lo = mid + 1`.
4. Return `lo`.

## 5. Solution

```python
def min_days(bloom_day, m, k):
    """Earliest day on which m bouquets of k adjacent flowers can be made, or -1.

    Flowers stay bloomed, so feasibility is monotone in the day - which makes the day
    itself binary searchable. A run of L adjacent available flowers yields exactly
    L // k bouquets, so taking one as soon as the run reaches k is optimal.
    """
    # Not enough flowers at all - no day helps. Must be checked before searching.
    if m * k > len(bloom_day):
        return -1

    def feasible(day):
        bouquets = 0
        run = 0                     # consecutive flowers bloomed by `day`
        for bloom in bloom_day:
            if bloom <= day:
                run += 1
                if run == k:
                    bouquets += 1
                    run = 0         # those k flowers are consumed
                    if bouquets >= m:
                        return True     # early exit once the target is met
            else:
                run = 0             # an unbloomed flower breaks adjacency
        return bouquets >= m

    # lo: nothing is available before the first bloom.
    # hi: by the last bloom every flower is available, which is the best case.
    lo, hi = min(bloom_day), max(bloom_day)

    while lo < hi:
        mid = (lo + hi) // 2
        if feasible(mid):
            hi = mid
        else:
            lo = mid + 1

    return lo
```

```python
min_days([1, 10, 3, 10, 2], 3, 1)           # 3
min_days([1, 10, 3, 10, 2], 3, 2)           # -1
min_days([7, 7, 7, 7, 12, 7, 7], 2, 3)      # 12
min_days([1, 10, 2, 9, 3, 8, 4, 7, 5, 6], 4, 2)     # 9
min_days([1000000000, 1000000000], 1, 1)    # 1000000000
min_days([1, 1, 1], 3, 1)                   # 1
min_days([5], 1, 1)                         # 5
min_days([1, 2, 3], 1, 3)                   # 3
min_days([1, 2, 3], 2, 2)                   # -1
```

The two to narrate:

- **`[7,7,7,7,12,7,7]` with `m=2, k=3` -> 12.** By day 7 there are two runs, of lengths 4 and
  2, giving `4//3 + 2//3 = 1` bouquet - not enough. Only when the `12` blooms do the runs
  merge into one of length 7, giving `7//3 = 2`. This case is the whole point: **adjacency
  and merging**, and a solution that just counts bloomed flowers gets it wrong.
- **`[1,2,3]` with `m=2, k=2` -> -1.** `m*k = 4 > 3`. The impossibility check, and it fires
  before any search.

### Tracing the third example

`bloomDay = [7,7,7,7,12,7,7]`, `m = 2`, `k = 3`. `lo = 7`, `hi = 12`.

| day | available runs | bouquets | >= 2? |
|---|---|---|---|
| 9 | `[7,7,7,7]` and `[7,7]` -> lengths 4, 2 | 1 + 0 = 1 | no -> `lo = 10` |
| 11 | same | 1 | no -> `lo = 12` |

`lo == hi == 12`. Answer **12**.

### The linear scan, as the oracle

```python
def min_days_linear(bloom_day, m, k):
    """O(range * n). Only for small inputs - a correctness oracle."""
    if m * k > len(bloom_day):
        return -1

    def feasible(day):
        bouquets = run = 0
        for bloom in bloom_day:
            if bloom <= day:
                run += 1
                if run == k:
                    bouquets += 1
                    run = 0
            else:
                run = 0
        return bouquets >= m

    for d in range(min(bloom_day), max(bloom_day) + 1):
        if feasible(d):
            return d
    return -1


min_days_linear([1, 10, 3, 10, 2], 3, 1)        # 3
min_days_linear([7, 7, 7, 7, 12, 7, 7], 2, 3)   # 12
min_days_linear([1, 2, 3], 2, 2)                # -1
```

## 6. Complexity

Let `n` be the number of flowers and `D = max(bloomDay) - min(bloomDay)`.

| | Time | Space |
|---|---|---|
| Scan every day | `O(D * n)` | `O(1)` |
| **Binary search on the day** | **`O(n log D)`** | **`O(1)`** |

With bloom days up to 10^9, `log D` is about 30, so around 30 linear passes. Again the log is
over the **value range**, not the array length - state it that way.

An alternative worth mentioning: you could sort the distinct bloom days and binary search over
that list instead, giving `O(n log n)` - better when the value range is huge but `n` is
small. Either is defensible.

## 7. How to present it

1. **Restate**, and **confirm the adjacency requirement** - it is the detail that makes the
   check interesting. *"The `k` flowers have to be next to each other in the array?"*
2. **Handle impossibility first**: `m * k > n` means `-1`, and say that you are checking it
   before searching so the search's postcondition is sound.
3. **State the monotonicity, with its reason**: *"Flowers stay bloomed, so if I can do it by
   day `d` I can do it by any later day. That makes feasibility monotone in the day, so I can
   binary search on the answer."* The *reason* is what distinguishes this from reciting.
4. **Describe the feasibility check**: walk the array, count runs of available flowers, take a
   bouquet whenever a run hits `k` and reset.
5. **Justify the greedy**: a run of length `L` gives exactly `L // k` bouquets however you
   carve it, so taking greedily is optimal.
6. **Derive the range**: `min(bloomDay)` to `max(bloomDay)`, with the reason for each.
7. **Write it**, including the early exit once `bouquets >= m`.
8. **Trace `[7,7,7,7,12,7,7]`** and show why day 7 is not enough - the runs do not merge
   until the `12` blooms. **This is the most convincing thing you can do here.**
9. **Close**: `O(n log D)`, `O(1)` space; note the log is over the bloom-day range, and offer
   the sort-the-distinct-days alternative.

## 8. Follow-ups and variations

- **"Koko Eating Bananas" / "Ship Packages"** (5.6, 5.12). Same technique. If one has already
  come up, name the connection and move faster.
- **"What if the flowers need not be adjacent?"** Much easier: count flowers bloomed by day
  `d` and check `count >= m * k`. The binary search stays; the check becomes trivial. **A
  good question to be asked**, because it isolates which constraint created the difficulty.
- **"Return which flowers form each bouquet."** Re-run the greedy at the answer day and
  record the indices.
- **"What if bouquets may have different sizes?"** The clean `L // k` argument breaks and it
  becomes a partitioning problem.
- **"Maximise the bouquets by a fixed day."** No search needed - just run the greedy once.
- **"What if flowers wilt after `w` days?"** Availability becomes an interval
  `bloomDay[i] <= d <= bloomDay[i] + w`, which **destroys monotonicity** - a later day can
  lose options. Binary search no longer applies, and saying exactly that is a strong answer.
- **"Minimum days with `m` bouquets of varying `k` per bouquet."** Harder; likely DP.

## 9. Pitfalls

- **Forgetting the `m * k > n` check**, so an impossible case returns `max(bloomDay)` instead
  of `-1`.
- **Ignoring adjacency** and simply counting bloomed flowers. `[7,7,7,7,12,7,7]` exposes it.
- **Not resetting the run on an unbloomed flower**, so bouquets are formed across gaps.
- **Not resetting the run after taking a bouquet**, reusing flowers.
- **Setting `lo = 0` or `lo = 1`** - harmless but sloppy; `min(bloomDay)` is the real floor
  and justifying it is the point.
- **Setting `hi` below `max(bloomDay)`**, making a valid answer unreachable.
- **Overflow in `m * k`** in a fixed-width language.
- **Mixing binary search templates**, or returning `mid` instead of `lo`.
- **Claiming `O(log n)`** - the log is over the day range.
