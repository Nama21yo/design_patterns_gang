**Link:** https://leetcode.com/problems/frequency-of-the-most-frequent-element
**Difficulty:** Medium | **LeetCode #1838**
**Bloomberg frequency:** 38% at three months.

A window over a **sorted** array, which is unusual - most of Part 3 works on the array as
given. Sorting is the move that turns an apparently global optimisation into a local window
condition, and explaining why it is safe to sort is the interview.

## 1. Problem statement

The **frequency** of an element is the number of times it occurs in an array.

You are given an integer array `nums` and an integer `k`. In one operation you may choose an
index and **increment** the element there by 1. You may perform at most `k` operations.

Return the **maximum possible frequency** of an element after performing at most `k`
operations.

```
nums = [1,2,4],     k = 5  ->  3    raise 1->4 (3 ops) and 2->4 (2 ops), giving [4,4,4]
nums = [1,4,8,13],  k = 5  ->  2
nums = [3,9,6],     k = 2  ->  1
```

## 2. Clarifying questions

1. **Increment only - no decrements?** Yes, only `+1`. This is what makes the target have to
   be the **largest** element of the chosen group, and it is what makes sorting work.
2. **Must the target value already be present in the array?** It is optimal for it to be -
   raising everything to an existing element is never worse than raising past it, because
   overshooting wastes operations. Worth stating rather than assuming.
3. **Is `k` a total budget across all operations?** Yes, shared.
4. **Return the frequency or the value?** The frequency - a count.
5. **May I reorder the array?** Sorting does not change the answer, since frequency does not
   depend on position. **Confirm this out loud** - it is the key licence.
6. **Sizes?** Up to 10^5, so `O(n log n)` is expected and `O(n^2)` is not.

## 3. Intuition

### Why sorting is safe, and why it is the whole idea

Frequency is about *values*, not positions, so reordering the array cannot change the answer.
That is the licence to sort.

Once sorted, the group of elements you raise to a common target must be **contiguous**. Why:
if you raise `nums[i]` and `nums[j]` to a target `T` with `i < j`, then any element between
them is between their values, so it costs *less* to raise it to `T` than it cost for
`nums[i]`. Including it is free improvement. So an optimal group is always a contiguous run
in the sorted array, ending at the target.

> **After sorting, the answer is the longest window `[left, right]` such that raising every
> element in it up to `nums[right]` costs at most `k`.**

That is now a sliding-window condition, and the cost is computable in `O(1)`:

```
cost(left, right) = nums[right] * (right - left + 1) - sum(nums[left..right])
```

- `nums[right] * width` is what the window would sum to if everything equalled the target.
- subtract what it actually sums to, and the difference is the total number of `+1`s needed.

Maintain the window sum incrementally and the cost is one multiplication and one subtraction
per step.

### Is the window valid?

Yes, and worth checking explicitly: the array is sorted and all costs are non-negative.
Growing the window to the right raises the target (weakly) and adds an element, so the cost
weakly increases. Shrinking from the left removes the cheapest-to-raise element... which
actually **decreases** the cost. So the cost is monotonic in the window for a fixed right
end, which is exactly what the shrink rule needs.

## 4. Approach

1. Sort `nums`.
2. `left = 0`, `window_sum = 0`, `best = 1`.
3. For each `right`:
   - `window_sum += nums[right]`
   - while `nums[right] * (right - left + 1) - window_sum > k`: `window_sum -= nums[left]`,
     `left += 1`
   - `best = max(best, right - left + 1)`
4. Return `best`.

## 5. Solution

```python
def max_frequency(nums, k):
    """Maximum achievable frequency using at most k increment operations.

    Sorting is safe because frequency does not depend on position, and after sorting
    the optimal group is contiguous: any element between two chosen elements is
    cheaper to raise than the lower one, so excluding it is never better.

    Cost to raise the whole window to nums[right]:
        nums[right] * width - window_sum
    """
    nums.sort()
    left = 0
    window_sum = 0
    best = 1                        # a single element always has frequency 1

    for right, x in enumerate(nums):
        window_sum += x

        # Too expensive: drop the smallest (leftmost) element, which is the costliest
        # one to raise to the current target.
        while x * (right - left + 1) - window_sum > k:
            window_sum -= nums[left]
            left += 1

        best = max(best, right - left + 1)

    return best
```

```python
max_frequency([1, 2, 4], 5)                 # 3
max_frequency([1, 4, 8, 13], 5)             # 2
max_frequency([3, 9, 6], 2)                 # 1
max_frequency([1, 1, 1], 0)                 # 3
max_frequency([1, 2, 3], 0)                 # 1
max_frequency([9, 4, 8, 7], 100)            # 4
max_frequency([1], 5)                       # 1
max_frequency([1, 10], 9)                   # 2
max_frequency([1, 10], 8)                   # 1
max_frequency([3, 3, 3, 2, 1], 2)           # 4
```

`[1,10]` with `k = 9` versus `k = 8` is the boundary pair: raising `1` to `10` costs exactly
9, so `k = 9` succeeds and `k = 8` fails. Having a test at the exact cost boundary is worth
volunteering.

`[3,3,3,2,1]` with `k = 2` -> **4**: sorted it is `[1,2,3,3,3]`; raising the `2` to `3` costs
1, leaving budget 1, which is not enough to also raise the `1` (cost 2). So the window is
`[2,3,3,3]`, frequency 4.

### The brute-force check

```python
def max_frequency_brute(nums, k):
    """O(n^2): for each right end, extend left while affordable. Correct, and the
    baseline to validate the window against."""
    nums = sorted(nums)
    best = 1
    for right in range(len(nums)):
        total = 0
        for left in range(right, -1, -1):
            total += nums[left]
            if nums[right] * (right - left + 1) - total <= k:
                best = max(best, right - left + 1)
            else:
                break
    return best


max_frequency_brute([1, 2, 4], 5)           # 3
max_frequency_brute([1, 4, 8, 13], 5)       # 2
max_frequency_brute([3, 3, 3, 2, 1], 2)     # 4
```

### Binary search alternative

Since the answer is monotone (if a frequency `f` is achievable, so is `f - 1`), you can
binary search the answer and check each candidate window size with a fixed-size sweep:

```python
def max_frequency_binary(nums, k):
    """O(n log n) via binary search on the answer. Same complexity as sorting, but a
    useful framing when the window condition is harder to express directly."""
    nums = sorted(nums)
    n = len(nums)
    prefix = [0] * (n + 1)
    for i, x in enumerate(nums):
        prefix[i + 1] = prefix[i] + x

    def feasible(width):
        """Can some window of this width be levelled within budget k?"""
        for right in range(width - 1, n):
            left = right - width + 1
            cost = nums[right] * width - (prefix[right + 1] - prefix[left])
            if cost <= k:
                return True
        return False

    lo, hi = 1, n
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if feasible(mid):
            lo = mid
        else:
            hi = mid - 1
    return lo


max_frequency_binary([1, 2, 4], 5)          # 3
max_frequency_binary([1, 4, 8, 13], 5)      # 2
max_frequency_binary([3, 3, 3, 2, 1], 2)    # 4
max_frequency_binary([1, 1, 1], 0)          # 3
```

This is `O(n log n)` for the search plus `O(n)` per feasibility check, so `O(n log n)`
overall - the same as the sort. Offer it as an alternative framing, and note that the
sliding window is simpler; binary-search-on-the-answer earns its keep in Part 5 where the
condition is harder to slide.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force after sorting | `O(n^2)` | `O(1)` |
| **Sort + sliding window** | **`O(n log n)`** | `O(1)` extra |
| Sort + binary search on the answer | `O(n log n)` | `O(n)` for prefix sums |

The sort dominates; the window itself is `O(n)` with `left` only moving forward. Space is
`O(1)` beyond the sort (`O(log n)` for the sort's own stack).

**Overflow**: `nums[right] * width` with values up to `10^5` and width up to `10^5` gives
`10^10`, which exceeds 32-bit. Python is fine; in C++/Java you need 64-bit. Worth a sentence.

## 7. How to present it

1. **Restate**, and confirm increments only.
2. **State the sorting licence explicitly**: *"Frequency doesn't depend on position, so I can
   sort without changing the answer."* Get a nod before proceeding - everything rests on it.
3. **Argue that the optimal group is contiguous**: *"If I'm raising two elements to a common
   target, anything between them is cheaper to raise than the lower one, so I might as well
   include it."* This is the actual insight and it is what makes a window applicable.
4. **Derive the cost formula on the board**:
   `cost = nums[right] * width - window_sum`. Say what each term means.
5. **Announce** the window: grow right, shrink while the cost exceeds `k`, record.
6. **Write it**, maintaining `window_sum` incrementally.
7. **Test the boundary**: `[1,10]` with `k = 9` and `k = 8`.
8. **Mention overflow** in fixed-width languages.
9. **Close**: `O(n log n)` dominated by the sort, `O(1)` extra space - and optionally offer
   the binary-search-on-the-answer framing.

## 8. Follow-ups and variations

- **"What if you could also decrement?"** Then the optimal target is the **median** of the
  chosen window, not the maximum, and the cost formula changes to the sum of absolute
  deviations. The window still works but the cost bookkeeping needs prefix sums on both
  sides of the median - this is LC 462 / LC 2448 territory. A genuinely good follow-up.
- **"Return the value achieving that frequency, not just the count."** Record `nums[right]`
  when `best` improves.
- **"What if each operation costs differently per index?"** The contiguity argument fails;
  it becomes a weighted selection problem.
- **"Maximum frequency after at most k operations, where an operation sets an element to any
  value."** Much easier - the answer is `max(count) + k`, capped at `n`.
- **"Minimum operations to make all elements equal."** The same cost formula applied to the
  whole array with the maximum as target, or the median if decrements are allowed.
- **"Why is binary search on the answer valid here?"** Because achievability is monotone in
  the frequency. That is the Part 5 framing - see [[5.0 Binary Search - pattern primer]].
- **"Can you avoid sorting?"** Not really - the contiguity argument needs order. You could
  counting-sort if the value range is small, giving `O(n + range)`.

## 9. Pitfalls

- **Not sorting**, or sorting and not justifying it.
- **Getting the cost formula backwards** (`window_sum - nums[right] * width`), which gives
  negative costs.
- **Using `nums[left]` as the target** instead of `nums[right]`. Only increments are allowed,
  so the target must be the **largest** in the window.
- **Recomputing the window sum** each step, making it `O(n^2)`.
- **Initialising `best` to 0** - the minimum achievable frequency is 1 for a non-empty array.
- **`if` instead of `while`** when shrinking.
- **Integer overflow** in `nums[right] * width` in a fixed-width language.
- **Forgetting that the window must be contiguous in the sorted array**, and trying to pick
  arbitrary subsets.
