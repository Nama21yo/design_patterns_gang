**Link:** https://leetcode.com/problems/move-zeroes
**Difficulty:** Easy | **LeetCode #283**
**Bloomberg frequency:** 50% at three months.

Same read/write skeleton as 2.2 and 2.9, with one extra requirement - **relative order must
be preserved** - which is exactly what rules out the tempting swap-with-the-end trick.

## 1. Problem statement

Given an integer array `nums`, move all `0`s to the **end** while maintaining the **relative
order** of the non-zero elements.

Do this **in place**, without making a copy.

```
nums = [0,1,0,3,12]  ->  [1,3,12,0,0]
nums = [0]           ->  [0]
```

## 2. Clarifying questions

1. **Must the relative order of the non-zero elements be preserved?** Yes - and it is the
   only thing that makes this more than trivial. Ask, because if order did *not* matter you
   could swap each zero with the last element and stop early, which is fewer writes.
2. **Does the order of the zeros matter?** They are indistinguishable, so no.
3. **In place, no copy?** Yes.
4. **Minimise the number of operations?** The stated follow-up. Worth asking up front -
   see the two-variant discussion below.
5. **Can the array be empty or all zeros?** Yes; both should work without a special case.
6. **Only zeros, or an arbitrary value to move?** Zeros here; generalising is a one-line
   change (and is 2.9).

## 3. Intuition

Do not think of it as "moving the zeros". Think of it as:

> **Compact the non-zero elements to the front, then fill the rest with zeros.**

That is the read/write pointer again: `write` marks where the next non-zero value belongs,
and `read` scans. Every non-zero value is copied to `nums[write]` and `write` advances.
Zeros are simply skipped.

After the scan, positions `write..n-1` hold stale leftovers, so overwrite them with `0`.

The invariant to state: **`nums[0:write]` holds the non-zero elements seen so far, in their
original order.** Preserving order is automatic, because you copy them in the order you meet
them - which is precisely why this approach is correct and the swap-with-the-end trick is
not.

### The one-pass swap variant

You can avoid the second loop by **swapping** instead of copying:

```
nums[write], nums[read] = nums[read], nums[write]
```

Since everything between `write` and `read` is zero, the swap sends a zero forward to
`read`'s old position - exactly where it belongs relative to the other zeros. So the array is
finished in one pass.

Both are `O(n)`. The swap version does at most `n` swaps (three writes each in principle,
though Python's tuple assignment is one operation); the copy version does at most `n` copies
plus the zero-fill. The follow-up asks to *minimise operations*, and the honest answer is
that the swap version avoids re-writing zeros that are already in place - worth saying, and
worth noting the guard `if write != read` to skip no-op swaps.

## 4. Approach

**Two-phase (clearest):**
1. `write = 0`; for each `x` in `nums`: if `x != 0`, `nums[write] = x`, `write += 1`.
2. For `i` in `write..n-1`: `nums[i] = 0`.

**One-pass swap:**
1. `write = 0`; for `read` in `0..n-1`: if `nums[read] != 0`, swap `nums[write]` and
   `nums[read]`, `write += 1`.

## 5. Solution

```python
def move_zeroes(nums):
    """Move all zeros to the end, preserving the order of the non-zero elements.

    Compact the non-zeros forward (which preserves their order automatically, since
    they are copied in the order encountered), then zero-fill the tail.
    """
    write = 0
    for x in nums:
        if x != 0:
            nums[write] = x
            write += 1

    # Everything from `write` onwards is a stale leftover; it must all become zero.
    for i in range(write, len(nums)):
        nums[i] = 0

    return nums
```

```python
move_zeroes([0, 1, 0, 3, 12])       # [1, 3, 12, 0, 0]
move_zeroes([0])                    # [0]
move_zeroes([1, 2, 3])              # [1, 2, 3]
move_zeroes([0, 0, 0])              # [0, 0, 0]
move_zeroes([1, 0])                 # [1, 0]
move_zeroes([0, 1])                 # [1, 0]
move_zeroes([])                     # []
move_zeroes([4, 0, 5, 0, 0, 6])     # [4, 5, 6, 0, 0, 0]
```

### The one-pass swap version

```python
def move_zeroes_swap(nums):
    """One pass. Everything between `write` and `read` is zero, so swapping sends a
    zero backwards into exactly the right place."""
    write = 0
    for read in range(len(nums)):
        if nums[read] != 0:
            if write != read:           # skip the no-op swap when nothing has moved
                nums[write], nums[read] = nums[read], nums[write]
            write += 1
    return nums


move_zeroes_swap([0, 1, 0, 3, 12])      # [1, 3, 12, 0, 0]
move_zeroes_swap([0, 0, 0])             # [0, 0, 0]
move_zeroes_swap([1, 2, 3])             # [1, 2, 3]
move_zeroes_swap([4, 0, 5, 0, 0, 6])    # [4, 5, 6, 0, 0, 0]
move_zeroes_swap([])                    # []
```

Note `[1,2,3]` with the `write != read` guard performs **zero** swaps - which is the point of
the "minimise operations" follow-up.

### What NOT to do - and why

```python
def move_zeroes_unstable(nums):
    """Swapping each zero with the LAST element is fewer writes, but it destroys the
    relative order of the non-zero elements - so it answers a different question."""
    last = len(nums) - 1
    i = 0
    while i <= last:
        if nums[i] == 0:
            nums[i], nums[last] = nums[last], nums[i]
            last -= 1                   # do not advance i: the swapped-in value is new
        else:
            i += 1
    return nums


move_zeroes_unstable([0, 1, 0, 3, 12])      # [12, 1, 3, 0, 0]
```

`[12, 1, 3, 0, 0]` has the zeros in the right place but the non-zeros in the **wrong order** -
`12` has jumped to the front. It is a perfectly good answer to "move zeros to the end" and a
wrong answer to *this* problem. Mentioning it, and saying why it is rejected, is a strong way
to show you noticed the order requirement.

Also note the `last -= 1` without advancing `i`: the element swapped in from the end has not
been examined. That is the same asymmetry as Dutch national flag in the primer.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Build a new list and copy back | `O(n)` | `O(n)` - disallowed |
| `nums.remove(0)` in a loop | `O(n^2)` | `O(1)` |
| **Compact + fill** | **`O(n)`** | **`O(1)`** |
| **One-pass swap** | **`O(n)`** | **`O(1)`** |

The two-phase version touches each slot at most twice; the swap version once. Both are
optimal asymptotically; the swap version wins on constant factors and on the
"minimise operations" follow-up.

## 7. How to present it

1. **Restate, and stress the order requirement.** "The non-zero elements keep their relative
   order - so I can't just swap each zero with the last element." Saying this first shows you
   read the constraint that makes the problem non-trivial.
2. **Reframe it**: "Rather than moving zeros, I'll compact the non-zeros to the front and
   then fill the tail with zeros."
3. **State the invariant**: `nums[0:write]` is the compacted, order-preserving prefix.
4. **Write the two-phase version** - it is the clearest.
5. **Then offer the one-pass swap**, explaining why it works: everything between `write` and
   `read` is zero, so the swap puts a zero exactly where it belongs.
6. **Answer the follow-up before it is asked**: "if you want to minimise writes, the swap
   version with a `write != read` guard does nothing at all on an array with no zeros."
7. **Test** `[0,0,0]`, `[1,2,3]`, `[]`, and `[4,0,5,0,0,6]`.
8. **Close**: `O(n)` time, `O(1)` space.

## 8. Follow-ups and variations

- **"Minimise the total number of operations."** The swap version with the `write != read`
  guard. Quantify it: zero swaps when there are no zeros, at most `n` otherwise.
- **"Move zeros to the *front* instead."** Run the same compaction from the right, or
  reverse, solve, reverse again.
- **"Move all instances of an arbitrary value."** That is LC 27, which is 2.9 here - and
  there the order of the *remaining* elements does **not** need preserving, which is the
  interesting contrast between the two problems.
- **"Remove duplicates from a sorted array."** LC 26, at 2.2 - same skeleton, different
  predicate.
- **"Partition into negatives then positives, preserving order."** Stable partition; the same
  compaction twice, or an `O(n log n)` stable in-place partition if `O(1)` space is demanded.
- **"Sort by parity"** (LC 905). Order need not be preserved, so the two-ended swap works and
  is fewer operations.
- **"What if the array is a linked list?"** Splice the zero nodes out into a second list and
  concatenate. `O(n)`, `O(1)`, and order falls out naturally.
- **"Sort the array so that all zeros are at the end and the rest are sorted."** Now it is
  just a sort with a custom key.

## 9. Pitfalls

- **Swapping each zero with the last element**, which breaks the order requirement.
- **Forgetting the zero-fill loop** in the two-phase version, leaving stale values in the
  tail.
- **Using `nums.remove(0)` then `nums.append(0)`** in a loop - `O(n^2)` and it mutates the
  length mid-iteration.
- **Building a new list** and rebinding `nums`, which leaves the caller's array untouched.
- **Advancing `i` after swapping in a value from the end**, in the unstable variant.
- **Counting zeros and rebuilding** (`[x for x in nums if x] + [0]*count`) - correct, but
  `O(n)` extra space, which the problem forbids.
- **Assuming `0` cannot be a legitimate value you must keep.** Here it is the thing being
  moved; in a generalised version, read the spec.
