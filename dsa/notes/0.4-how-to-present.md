title: "0.4 How to present a solution out loud"
---

The framework in 0.3 tells you *what* to do. This page is the *wording* - the actual
sentences, so that the first time you say them is not in the interview.

This matters more at Bloomberg than the raw algorithm work. Every Round 2 report describes a
round spent on discussion, edge cases and follow-ups rather than on whether the code ran.

## The uncomfortable truth about narration

Most people cannot think hard and talk at the same time. That is normal, and the fix is not
to talk *while* thinking - it is to **alternate**, and to say what you are doing in the gaps.

The thing that kills rounds is undifferentiated silence, because the interviewer cannot tell
whether you are working or stuck, so they cannot help. Buy yourself silence explicitly:

> "Let me think about this for a moment - I'm trying to work out whether sorting first
> helps here."

Now the silence is legible, it has a topic, and the interviewer can step in if you are going
the wrong way. Thirty to sixty seconds of that is completely fine. Three minutes is not.

## Phrases worth having ready

### Opening

- "Let me restate that to make sure I have it right..."
- "Before I start, can I ask a few things about the input?"
- "Let me work through your example by hand first."
- "Just to check my reading is right - with `aab` and `ab`, would you want `a` or nothing?"

### Moving from brute force to the real answer

- "The obvious approach is X, which is O(n squared). Let me see if I can do better."
- "The wasteful part is that I'm rescanning for the complement each time."
- "That suggests a hash map, which makes the lookup constant time."
- "Let me flip it around: instead of finding the enclosed islands, I'll find the ones
  reachable from the border."

### Announcing (do not skip this)

- "Here's my plan before I write it: ..."
- "I'll do this in three steps: group, sort, sweep."
- "This should come out to O(n log n), dominated by the sort. Does that sound reasonable?"

### While coding

- "I'm using a dict here because I need O(1) membership."
- "I'm recording the index *after* the lookup - that's what stops an element pairing with
  itself."
- "I'll come back to this helper; let me get the main shape down first."
- "I'm going to name this `covered_until` because it's the point up to which we have
  coverage."

### Closing

- "Let me trace this on your example."
- "Let me go through the edge cases." **(Say this every time. Do not wait to be asked.)**
- "Time is O(n log n), space is O(n) for the map."
- "One thing I haven't handled is X - I'd do Y about it."
- "If the input were guaranteed sorted, this would drop to linear."

## Handling a hint

Interviewers in these reports were repeatedly described as helpful. A hint is not a failure
signal - **failing to use it is.**

When you get one:

1. **Stop typing.**
2. **Say it back**: "So you're suggesting I look at the order the events arrive in?"
3. **Say what it implies**: "...which would mean the list is already sorted by time, so I
   could binary search instead of scanning."
4. **Then act on it.**

Do not thank them and carry on with your original plan. Do not pretend you were about to say
it. Both are obvious and both are worse than just taking the hint well.

## Recovering when your approach is wrong

This is the single most valuable skill on this page, and there is a reported round that
turned on it: the candidate realised their reading of the trading-hours problem was wrong
*just* as time ran out, having implemented the wrong thing.

**Say it the moment you suspect it:**

> "I think I've misread this. Can I restate the requirement? ... Right - so coverage can hand
> off between banks, which means this is a union-of-intervals problem, not a
> single-interval-containment problem. Let me redo it."

Three things make this land well:
- **You noticed**, which is what senior engineers do.
- **You named the correct approach**, which proves the round was not wasted.
- **You did it early enough to act.**

Announcing the correct algorithm with five minutes left is worth far more than silently
finishing the wrong one. The interviewer is scoring your engineering judgement, and catching
your own mistake *is* engineering judgement.

## Volunteering edge cases

The highest-leverage habit for Bloomberg specifically. When the code is written:

> "Let me go through the edge cases. Empty input - the loop doesn't run, returns zero,
> that's right. Single element - can't form a pair, returns zero. All duplicates - `[1,1,1,1]`
> with target 2 gives 6, which is 4 choose 2, correct. And the self-pairing case,
> `[3]` with target 6 - the element shouldn't pair with itself, and it doesn't, because I
> record the value after the lookup."

That paragraph took twenty seconds and demonstrated more than the code did. Design
Underground System was asked four times and the round was this paragraph, every time.

## What not to do

| Don't | Do |
|---|---|
| Silence for minutes | "Let me think for a second - I'm considering whether to sort first." |
| Reading your code aloud line by line | Explain the *decisions*, not the syntax |
| "This is easy, I've seen it" | Solve it fresh; the variant is usually different |
| Writing code before stating a plan | Announce, get a nod, then type |
| Arguing when corrected | "Let me re-check that... you're right." |
| Apologising repeatedly | Fix it and continue |
| Stopping when the code works | "Let me trace it and go through the edge cases." |
| Pretending to know something | "I don't remember the exact API; I'd look it up. The idea is..." |
| One-letter variable names | Names you can say out loud |

## If you have genuinely seen the question before

Say so. It costs nothing and hiding it goes badly:

> "I've seen something close to this before, so I know the shape of the answer - I'll walk
> through the reasoning rather than just writing it down."

Then actually walk through the reasoning. And be careful: the Bloomberg versions are usually
*variants*. The lottery system is Insert Delete GetRandom with weighted duplicates; the
trading hours is merge intervals with a containment test; the desert grid is BFS with an
extra state dimension. Recognising the base problem is step one, not the answer.

## Practising this

Narration is a physical skill and it does not transfer from reading about it.

1. **Record yourself.** 45 minutes, one medium question, talking the whole time. Watch it
   back. It will be uncomfortable and it is the fastest improvement available.
2. **Count your silences.** Any gap over 60 seconds with nothing said is a problem to fix.
3. **Practise the closing paragraph** until it is automatic: trace, edge cases, complexity,
   what you did not handle.
4. **Use the "How to present it" section** of each question page as a script. They are
   written as literal scripts for exactly this.
5. **Solve in a plain editor**, no autocomplete, no running the code. That is the interview
   environment.
