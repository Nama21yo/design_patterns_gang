*Two indices moving under an invariant, usually on a sorted array or from both ends.*

53 Bloomberg-tagged questions. Where Part 1 trades **memory** for time (store what you have
seen), Part 2 trades **order** for time (sort, then exploit the ordering to never look at a
candidate that cannot win). Knowing which of the two a problem wants is most of the skill.

## The three shapes

Almost every question in this Part is one of three.

### 1. Opposite ends (converging)

```
lo ->                     <- hi
[ . . . . . . . . . . . . . ]
```

Start at both ends, move inward. Used when the array is **sorted** and the quantity you care
about is **monotonic** in the pointer positions.

```python
def two_sum_sorted(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        total = nums[lo] + nums[hi]
        if total == target:
            return (lo, hi)
        if total < target:
            lo += 1             # need more: only the left can increase the sum
        else:
            hi -= 1             # need less: only the right can decrease it
    return None


two_sum_sorted([2, 7, 11, 15], 9)       # (0, 1)
two_sum_sorted([1, 2, 3, 4], 100)       # None
```

**Why the move is safe** - this is the argument you must be able to give:

> If `nums[lo] + nums[hi] < target`, then `nums[lo]` paired with *anything* at or below
> `hi` is also too small, since `hi` is the largest remaining. So `lo` can never be part of
> a solution with any remaining partner, and discarding it loses nothing.

That is an **exchange argument**, and every opposite-ends solution needs one. Say it out
loud; "I move the smaller one" without justification is the difference between a memorised
answer and a reasoned one.

### 2. Same direction (fast and slow)

```
      slow ->
[ . . . . . . . . . . . . . ]
            fast ->
```

Both move forward, at different rates or under different conditions. Used for **in-place
compaction** (write index trails read index) and for **cycle detection** in linked lists.

```python
def remove_value(nums, value):
    """Compact in place: write only the elements to keep. Returns the new length."""
    write = 0
    for read in range(len(nums)):
        if nums[read] != value:
            nums[write] = nums[read]
            write += 1
    return write


data = [3, 2, 2, 3]
remove_value(data, 3)                   # 2
data[:2]                                # [2, 2]
```

The invariant to state: **everything before `write` is final and correct; everything from
`read` onwards is unexamined.** That single sentence justifies the whole loop.

### 3. Two sequences

```
[ a a a a a ]   i ->
[ b b b b b b ]   j ->
```

One pointer per array, advancing whichever is behind. Used for merging, intersection, and
subsequence checks.

```python
def merge_sorted(a, b):
    out, i, j = [], 0, 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    out.extend(a[i:])
    out.extend(b[j:])
    return out


merge_sorted([1, 3, 5], [2, 3, 6])      # [1, 2, 3, 3, 5, 6]
```

## Recognition signals

Reach for two pointers when you see:

- "**sorted** array" plus "find a pair / triple"
- "in place", "O(1) extra space", "modify the array"
- "remove / move / partition the elements such that..."
- "palindrome", "reverse", "from both ends"
- "container", "area", "the widest / closest pair"
- "merge two sorted...", "intersection of two sorted..."
- "is one string a subsequence of another"

**If the array is not sorted but order does not matter to the answer, consider sorting.**
`O(n log n)` to sort then `O(n)` to scan beats `O(n^2)`, and sorting is what unlocks the
whole pattern.

But note the trade: **sorting destroys the original indices.** If the answer must be
indices into the input, either keep `(value, index)` pairs or use a hash map instead
(Part 1). That is precisely the "does reordering matter?" follow-up reported in 23.17.

## Part 1 or Part 2?

| | Hash map (Part 1) | Two pointers (Part 2) |
|---|---|---|
| Input sorted? | irrelevant | required (or sort first) |
| Time | `O(n)` | `O(n)` after an `O(n log n)` sort |
| Extra space | `O(n)` | `O(1)` |
| Preserves indices? | yes | no, if you sort |
| Handles "count of" | naturally | needs care with duplicate blocks |
| Handles k-sum | awkward past k=2 | naturally, by recursion |

Say this trade-off out loud when both apply. "A hash map gives me O(n) but costs O(n) space
and I'd keep the original indices; two pointers after a sort is O(n log n) but O(1) space.
Which do you prefer?" is a strong sentence.

## The k-sum ladder

Worth learning as one idea rather than three problems.

- **2Sum on a sorted array**: opposite-ends, `O(n)`.
- **3Sum**: sort, fix `i`, two-pointer the rest, `O(n^2)`.
- **4Sum**: sort, fix `i` and `j`, two-pointer the rest, `O(n^3)`.
- **kSum**: recurse down to 2Sum, `O(n^(k-1))`.

The dedup rule is the part people get wrong, and it changes between problems:

- In **2Sum** (LC 1) you return indices and uniqueness is by index, so no dedup.
- In **3Sum/4Sum** you return *values* and must not emit the same triple twice, so you skip
  over equal neighbours **after** committing a pointer.

```python
def three_sum(nums):
    """All unique triples summing to zero."""
    nums.sort()
    out = []
    n = len(nums)
    for i in range(n - 2):
        if i > 0 and nums[i] == nums[i - 1]:
            continue                        # skip duplicate first elements
        if nums[i] > 0:
            break                           # sorted: no way back to zero
        lo, hi = i + 1, n - 1
        while lo < hi:
            total = nums[i] + nums[lo] + nums[hi]
            if total < 0:
                lo += 1
            elif total > 0:
                hi -= 1
            else:
                out.append([nums[i], nums[lo], nums[hi]])
                lo += 1
                hi -= 1
                # Skip duplicates only AFTER recording the triple.
                while lo < hi and nums[lo] == nums[lo - 1]:
                    lo += 1
                while lo < hi and nums[hi] == nums[hi + 1]:
                    hi -= 1
    return out


three_sum([-1, 0, 1, 2, -1, -4])        # [[-1, -1, 2], [-1, 0, 1]]
three_sum([0, 0, 0, 0])                 # [[0, 0, 0]]
three_sum([1, 2, 3])                    # []
```

## Partitioning: Dutch national flag

Three pointers, one pass, `O(1)` space - the general tool for "group the array into
categories in place".

```python
def sort_colors(nums):
    """0s, 1s, 2s sorted in one pass. low/mid/high partition the array into
    [0s | 1s | unexamined | 2s]."""
    low, mid, high = 0, 0, len(nums) - 1
    while mid <= high:
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1
            mid += 1
        elif nums[mid] == 1:
            mid += 1
        else:
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1           # NOT mid += 1: the swapped-in value is unexamined
    return nums


sort_colors([2, 0, 2, 1, 1, 0])         # [0, 0, 1, 1, 2, 2]
sort_colors([2, 0, 1])                  # [0, 1, 2]
```

The asymmetry in the last branch is the whole trick: a value swapped down from `high` has
never been looked at, so `mid` must not advance past it. Explain that when you write it.

## Templates

**Opposite ends:**
```python
# fragment
lo, hi = 0, len(arr) - 1
while lo < hi:
    # evaluate arr[lo], arr[hi]
    # move exactly one pointer, justified by an exchange argument
    pass
```

**Same direction / compaction:**
```python
# fragment
write = 0
for read in range(len(arr)):
    if keep(arr[read]):
        arr[write] = arr[read]
        write += 1
return write
```

**Two sequences:**
```python
# fragment
i = j = 0
while i < len(a) and j < len(b):
    # advance whichever is behind
    pass
```

## How to talk about it

- "The array is sorted, so I can use two pointers from the ends and get O(1) space."
- "If the sum is too small, the only way to increase it is to move the left pointer -
  pairing this left element with anything smaller than `hi` is even worse, so I can discard
  it."
- "Both pointers only ever move inward, so the total work is linear."
- "I keep a write pointer for the compacted prefix; everything before it is final."
- "I skip duplicates *after* recording the answer, so I don't miss a valid triple."
- "Sorting costs O(n log n) but buys me O(1) space - though it destroys the original
  indices, so if you want indices I'd use a hash map instead."

## Common pitfalls across this Part

- **`while lo <= hi` when the two pointers must not meet** (pair problems need `lo < hi`).
- **Moving both pointers** when only one move is justified.
- **Moving neither**, producing an infinite loop.
- **Skipping duplicates before recording an answer**, losing a valid triple.
- **Sorting when indices are required.**
- **Advancing `mid` after a swap with `high`** in Dutch national flag.
- **Assuming the array is sorted** when it was not stated.
- **Forgetting the leftover tail** in a two-sequence merge.
- **Off-by-one in `hi = len(arr) - 1` versus `len(arr)`.**
