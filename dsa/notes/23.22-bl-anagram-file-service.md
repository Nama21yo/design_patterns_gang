> Reported once in R3 on 2025-11-05. This is a **hybrid round**: a small coding problem
> (group anagrams), a code review of someone else's pseudocode, and a service design - with
> the interviewer explicitly role-playing *"your colleague and mentor on the team"*.
>
> It is not the usual distributed-design round. Treat it as a design conversation where you
> are expected to ask, critique and propose, not to silently produce an answer.

## Prompt as given

```
An analyst has written a tool that helps with a step in a data ingestion pipeline. It has
greatly increased their productivity and they have been sharing it around. You, as a
Bloomberg engineer, have been asked to formalise this tool into a service. (The interviewer
plays your colleague and mentor on the team.)

Data files arrive by email from many external providers, as text files with one word per
line and anagrams grouped onto consecutive lines. The file name is a unique provider id
plus a date, e.g. GS1234.20230525.txt. If the content is not correct an error alert email
goes to the data analysts, who repair the file and give feedback to the provider. Corrected
files land in a network folder monitored by the pipeline. Files vary in size and priority.
Throughput is limited by the number of analysts and the backlog is growing fast.

The analyst's tool takes a file of words, one per line, and writes a file where anagrams are
grouped on consecutive lines.

  sample in:        sample out:      (or)    sample out:
    dog               oak                      dog
    oak               god                      god
    god               dog                      oak

The analyst has implemented the following logic:
  // Open file for input
  // Create a HASHMAP with a string key, and a list of strings as the value
  // While there is a new line in the file
  //     Read a line into a string VALUE
  //     hash the value to give a KEY
  //     add the KEY, VALUE pair to the HASHMAP
  // Close the input file
  // Open an output file for writing
  // for each KEY in the HASHMAP
  //     for each string VALUE in the value list
  //         Write the VALUE to the output file
  // Close the output file

  C:> python convertfile.py in.txt out.txt
  C:> cp out.txt z:\next_stage\input_files\
```

Core algorithm: [Group Anagrams](https://leetcode.com/problems/group-anagrams/) (LC 49).

## How to run this round

The interviewer is your "colleague and mentor". That framing is a strong hint:

- **Ask questions constantly.** A mentor expects a junior to ask.
- **Critique the analyst's code kindly and specifically.** They wrote it and it helped; the
  job is to productionise it, not to dunk on it.
- **Separate the three layers out loud**: the algorithm, the tool's correctness, and the
  service around it. Say which you are talking about at any moment.

## Clarifying questions to ask first

**About the algorithm**
1. **What is "the hash" of a word?** The pseudocode says "hash the value to give a KEY" and
   does not say how. This is the central question - see below.
2. **Is the grouping case sensitive? What about whitespace, punctuation, non-ASCII?**
3. **Does the order of groups matter? The order within a group?** The two sample outputs
   differ, so apparently not - confirm.
4. **Can a word appear twice?**

**About the tool**
5. **What does "the file content is not correct" mean?** What are the validation rules? This
   is never stated and it drives the whole error path.
6. **How large can a file be?** Does it fit in memory?

**About the service**
7. **What is the actual bottleneck?** The report says throughput is limited by the *number of
   analysts*, and the backlog is growing. So the goal is to **reduce analyst work**, not to
   make the script faster. Say this - it reframes the whole design.
8. **Who are the users - analysts, providers, or the pipeline?**
9. **What are the SLAs? How quickly must a file be processed?**
10. **Can we change the contract with providers?**

## Part 1: the algorithm

Two words are anagrams iff they have the same multiset of letters. The two standard keys:

- **Sorted letters.** `"dog"` and `"god"` both give `"dgo"`. `O(L log L)` per word.
- **Letter counts.** A 26-tuple, or a `Counter` frozen into a tuple. `O(L)` per word, at the
  cost of a bigger key.

For ordinary words, sorting wins on simplicity and the log factor is irrelevant (`L` is
small). For very long strings or a large alphabet, counting wins. **Say both and justify the
choice** - "the hash" in the analyst's pseudocode is exactly this decision, left unspecified.

```python
from collections import defaultdict


def group_anagrams(words):
    """Group words that are anagrams of each other.

    The key is the sorted letters: two words are anagrams exactly when their sorted
    forms are equal. A 26-letter count tuple is the O(L) alternative, better when
    words are long.
    """
    groups = defaultdict(list)
    for word in words:
        groups["".join(sorted(word))].append(word)
    return list(groups.values())


def anagram_key_counts(word):
    """O(L) alternative key, for long words or large alphabets."""
    counts = [0] * 26
    for ch in word:
        counts[ord(ch) - ord("a")] += 1
    return tuple(counts)
```

```python
group_anagrams(["dog", "oak", "god"])
# [['dog', 'god'], ['oak']]

group_anagrams(["eat", "tea", "tan", "ate", "nat", "bat"])
# [['eat', 'tea', 'ate'], ['tan', 'nat'], ['bat']]
```

## Part 2: reviewing the analyst's code

This is the part most candidates skip, and it is explicitly set up for you. Findings, in the
order you would raise them with a colleague:

1. **"Hash the value to give a KEY" is underspecified, and the obvious reading is wrong.**
   If `KEY` is a hash *of the word itself*, then `dog` and `god` get **different** keys and
   nothing is grouped. The key must be a canonical form of the *letter multiset*, not of the
   word. This is the actual bug, and finding it is the single highest-value thing you can do
   in this round.
2. **Using a raw hash value as the key invites collisions.** Two non-anagram words could
   share a hash and be grouped incorrectly. The sorted string or the count tuple are exact
   keys, not hashes - no collision risk. Worth stating the distinction explicitly: *a hash is
   lossy, a canonical form is not.*
3. **The whole file is read into memory**, via the hashmap. For a large file this is a
   problem. It is also *unavoidable* if the output must be fully grouped - you cannot emit a
   group until you have seen the whole input. Say that, then offer external sorting (below).
4. **No validation.** The spec says invalid files trigger an alert, but the tool does not
   check anything or report anything. It has no exit code discipline and no error output.
5. **No handling of blank lines, trailing whitespace or case.** `"Dog\n"` and `"dog"` will
   not group.
6. **The manual `cp` to a network drive is not part of the tool**, so the process is
   two steps, not atomic, and a partially copied file may be picked up by the monitoring
   pipeline mid-write. Write to a temporary name and rename atomically.
7. **No idempotency.** Re-running on the same file overwrites output silently; there is no
   record of what was processed.

### The improved tool

```python
import os
import sys
from collections import defaultdict


def canonical_key(word):
    """Exact canonical form of the letter multiset - not a hash, so no collisions."""
    return "".join(sorted(word))


def normalise(line):
    """One place for every input-cleaning decision, so the rules are reviewable."""
    return line.strip().lower()


def group_file(in_path, out_path):
    """Group anagrams onto consecutive lines. Writes atomically: a reader watching the
    output directory never sees a partially written file."""
    groups = defaultdict(list)
    for lineno, line in enumerate(open(in_path, encoding="utf-8"), 1):
        word = normalise(line)
        if not word:
            continue                       # skip blank lines rather than grouping them
        if not word.isalpha():
            raise ValueError(f"{in_path}:{lineno}: {line.strip()!r} is not a word")
        groups[canonical_key(word)].append(word)

    tmp_path = out_path + ".tmp"
    with open(tmp_path, "w", encoding="utf-8") as out:
        for words in groups.values():
            for word in words:
                out.write(word + "\n")
    os.replace(tmp_path, out_path)        # atomic on POSIX and on Windows
    return sum(len(v) for v in groups.values()), len(groups)
```

The `os.replace` is the detail worth pointing at: it fixes finding 6, and it is the standard
answer to "how do you publish a file to a watched directory safely".

## Part 3: the service design

**Restate the goal first.** The bottleneck is analyst time and the backlog is growing. So the
service should: (a) remove the manual steps entirely for files that are already valid,
(b) auto-repair what can be safely auto-repaired, and (c) for the rest, make the analyst's
job as fast as possible and push feedback to the provider automatically.

A design to sketch:

```
   provider email ──► ingest gateway ──► object store (raw)
                            │                  │
                            └──► job queue ◄───┘
                                    │
                        ┌───────────┴───────────┐
                        ▼                       ▼
                    validator               grouper workers
                        │                       │
             ┌──────────┴─────────┐             ▼
             ▼                    ▼      output store ──► atomic publish
        auto-repairable       needs human            to z:\next_stage\
             │                    │
             ▼                    ▼
         repair rules      analyst review UI ──► provider feedback (templated)
```

Points to make, roughly in priority order:

- **A priority work queue, not a folder.** Files vary in size and priority, so the queue needs
  priority classes. Small high-priority files should not sit behind a huge low-priority one -
  so run separate worker pools per size class, or use a fair-share scheduler. This is the
  direct answer to "files vary in size and priority".
- **Validation as a first-class stage** with machine-readable error codes, not an email body.
  The error code is what drives auto-repair, the analyst UI, and the provider report.
- **Auto-repair the mechanical failures**: trailing whitespace, case, blank lines, BOM,
  duplicate words, wrong line endings. Each repair is logged. This is what actually shrinks
  the backlog, and it is the highest-leverage idea in the whole design - say it early.
- **An analyst review UI** instead of email round-trips: show the file, highlight the invalid
  lines, offer one-click fixes, and let one analyst clear many files quickly. Email is the
  bottleneck as much as the analysts are.
- **Automated provider feedback**: a scheduled report per provider with their error rate and
  the specific failures, plus a published spec and ideally a validator the provider can run
  themselves before sending. Fixing the source is the only thing that makes the backlog stop
  growing.
- **Idempotency and dedup** keyed on `(provider_id, date)` from the filename, plus a content
  hash. Re-sending the same file must not create duplicate work.
- **At-least-once processing with idempotent writes.** Workers can die; the queue redelivers;
  the atomic rename makes a retry harmless.
- **Observability**: backlog depth, age of the oldest item, per-provider error rates,
  time-to-resolution. The metric that matters is *analyst minutes per file*.
- **Retention and audit**: keep the raw file, the repaired file and the diff. Financial data
  ingestion needs an audit trail.

### If the file does not fit in memory

The grouping itself forces you to see all input before emitting any group, but you do not
have to hold the *words* in memory:

1. Stream the file, writing `canonical_key \t word` to a temporary file.
2. **External sort** that file by key (GNU `sort` does this, spilling to disk).
3. Stream the sorted file, emitting words and starting a new group whenever the key changes.

Memory is then `O(1)` in the number of words and the cost is `O(n log n)` I/O. This is the
standard answer and naming "external merge sort" is enough.

For a genuinely huge corpus, the same idea shards: hash the key to `k` buckets, write each
word to its bucket file, then process each bucket independently - which is exactly a
MapReduce shuffle, and is worth naming since it parallelises across workers.

## Complexity

Let `n` be the number of words and `L` the maximum word length.

| | Time | Space |
|---|---|---|
| In-memory grouping, sorted key | `O(n * L log L)` | `O(n * L)` |
| In-memory grouping, count key | `O(n * L)` | `O(n * L)` |
| External sort | `O(n log n)` I/O | `O(1)` memory, `O(n L)` disk |

## How to present it

1. **Say what kind of round you think this is**: "this looks like it spans the algorithm, a
   code review and a service design - shall I take them in that order?" Getting agreement on
   the structure is worth a lot in an ambiguous round.
2. **Solve the algorithm quickly** - it is Group Anagrams, five lines - and **name the key
   choice** explicitly, since that is the ambiguity in the analyst's code.
3. **Review the pseudocode out loud.** Lead with the real bug (hashing the word rather than
   its canonical form), then the collision point, then the operational issues. Frame each as
   "one thing I'd want to check with you" rather than a verdict.
4. **Restate the business problem before designing**: the constraint is analyst throughput,
   not CPU. If you design a faster grouper you have optimised the wrong thing, and saying so
   is the strongest single observation available in this round.
5. **Sketch the pipeline**, then go deep on whichever box they poke.
6. **Volunteer the memory/external-sort question** - it is the natural "what if it is big"
   follow-up.
7. **Close on what you would measure**: backlog age and analyst minutes per file.

## Follow-ups and variations

- **"What IS the hash key?"** Sorted letters or a 26-count tuple; exact, not a hash. Give the
  trade-off: `O(L log L)` and compact, versus `O(L)` and larger.
- **"What is wrong with the analyst's logic?"** The seven findings above; lead with the key.
- **"The file does not fit in RAM."** External sort, then shard/MapReduce.
- **"Files have varying sizes and priorities."** Priority queue plus size-class worker pools,
  so a huge file cannot starve small urgent ones.
- **"How do you stop the backlog growing?"** Auto-repair plus provider feedback plus a
  self-service validator. Processing faster only treats the symptom.
- **"How do you know a file is correct?"** A versioned, published schema; validation returns
  structured error codes; the same validator runs on the provider side.
- **"What if a provider sends the same file twice?"** Dedup on `(provider, date, content
  hash)`; the pipeline must be idempotent.
- **"How do you publish to the watched folder safely?"** Write a temp file, then atomic
  rename. Never write in place into a monitored directory.
- **"What if the grouping must be stable or reproducible?"** Sort the groups by key and the
  words within a group, so the output is deterministic - which also makes diffing and
  testing possible.
- **"Can we move off email?"** Yes, and you should propose it: SFTP drop, an API, or a signed
  upload URL, with email as a fallback. Email is the root of the operational pain.

## Pitfalls

- **Treating it as a pure coding question.** Group Anagrams takes three minutes; the round is
  45.
- **Missing the actual bug** in the pseudocode. It is the thing the prompt is built around.
- **Confusing a hash with a canonical key.** Hashes collide; sorted letters do not.
- **Designing a faster script** when the stated bottleneck is analyst headcount.
- **Being harsh about the analyst's code.** They are your colleague in the framing, and the
  interviewer is watching how you give feedback. "Here's what I'd want to check" beats
  "this is broken".
- **Forgetting the atomic publish**, leaving a race with the monitoring pipeline.
- **Claiming you can stream the grouping in `O(1)` memory without sorting.** You cannot emit a
  group before seeing the whole input.
- **Not asking what "not correct" means.** The entire error path, and therefore most of the
  design, hangs on it.
