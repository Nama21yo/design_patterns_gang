title: "23.9 Min Stack with top-k minimums"
---

> Reported twice in R1 on 2025-10-20 and 2025-11-07. The base problem is a warm-up; the
> round is the three follow-ups, one of which is a pure Python-semantics probe.

## Prompt as given

```
Design a stack that supports push, pop, top and retrieving the minimum element in
constant time.
```

Link: [Min Stack](https://leetcode.com/problems/min-stack/) (LC 155)

## Clarifying questions to ask first

1. **What should `pop`/`top`/`getMin` do on an empty stack?** This matters here, because one
   of the reported follow-ups is specifically about error behaviour. Say "I will raise
   `IndexError`, matching what a list does" and get agreement.
2. **Duplicates allowed?** Yes, and they are the classic bug - ask so you can flag it.
3. **Is `getMin` the minimum of the *whole* stack, or of some window?** Whole stack.
4. **Does `pop` return the value?** LeetCode's does not; a Pythonic one would. Ask.
5. **Integers only, or any comparable?** Does not change the code, but worth a sentence.

## Intuition

`push`, `pop` and `top` are trivially `O(1)` on a list. The only hard requirement is
`getMin` in `O(1)`.

Scanning for the minimum is `O(n)`. Keeping a single `self.min` variable fails on `pop`: if
you pop the current minimum, you have no idea what the new minimum is, and recomputing is
`O(n)`.

The observation that fixes it:

> **The minimum of the stack is itself a stack-shaped quantity.** As elements are pushed the
> minimum only ever decreases or stays the same; as they are popped it retraces exactly the
> path it came by.

So keep a second stack holding the minimum *as of each push*. `mins[i]` is the minimum of
the first `i+1` elements. Push and pop the two stacks in lockstep and `getMin` is
`mins[-1]`.

There are two variants worth knowing:

- **Push always.** `mins` is the same length as the main stack. Simplest, `O(n)` extra space.
- **Push only on `<=`.** `mins` holds only the record-setting values. Less memory when the
  data is mostly increasing. **The comparison must be `<=`, not `<`** - with `<`, pushing
  `2, 2` records the minimum once, and the first `pop` removes it, leaving `getMin` wrong
  while a `2` is still on the stack. This is the duplicates pitfall, and it is exactly what
  the "what if there are duplicates" follow-up is testing.

## Approach

1. `self.stack`: the values.
2. `self.mins`: the running minimum, one entry per push (variant 1).
3. `push(x)`: append `x`; append `min(x, self.mins[-1] if self.mins else x)`.
4. `pop()`: pop both.
5. `top()`: `self.stack[-1]`.
6. `getMin()`: `self.mins[-1]`.

## Solution

```python
class MinStack:
    """Stack with O(1) push, pop, top and getMin.

    `mins[i]` holds the minimum of stack[0..i], so the minimum is always mins[-1]
    and it unwinds correctly on pop.
    """

    def __init__(self):
        self.stack = []
        self.mins = []

    def push(self, x) -> None:
        self.stack.append(x)
        # The new running minimum is the smaller of x and the previous running minimum.
        self.mins.append(x if not self.mins else min(x, self.mins[-1]))

    def pop(self):
        if not self.stack:
            raise IndexError("pop from empty stack")
        self.mins.pop()
        return self.stack.pop()

    def top(self):
        if not self.stack:
            raise IndexError("top from empty stack")
        return self.stack[-1]

    def getMin(self):
        if not self.mins:
            raise IndexError("getMin from empty stack")
        return self.mins[-1]
```

### The space-saving variant, and the duplicates trap

```python
class MinStackCompact:
    """Only record-setting minima are stored. Uses less memory on mostly-increasing data."""

    def __init__(self):
        self.stack = []
        self.mins = []

    def push(self, x):
        self.stack.append(x)
        # '<=' not '<': with duplicates of the minimum, each one must be recorded,
        # otherwise popping the first leaves getMin reporting a value that is gone.
        if not self.mins or x <= self.mins[-1]:
            self.mins.append(x)

    def pop(self):
        value = self.stack.pop()
        if self.mins and value == self.mins[-1]:
            self.mins.pop()
        return value

    def top(self):
        return self.stack[-1]

    def getMin(self):
        return self.mins[-1]
```

Trace the trap out loud: push `2`, push `2`, pop, `getMin()`. With `<` the `mins` stack is
`[2]`; the pop sees `value == mins[-1]` and removes it, so `getMin` raises even though a `2`
is still on the stack. With `<=` it is `[2, 2]` and everything lines up.

### Follow-up: top k minimums

Ask what "top k minimums" means before coding - the two readings need different structures:

**(a) The k smallest values currently in the stack.** A running-minimum stack cannot answer
this; it only tracks a prefix minimum. You need the multiset of live values. Keep a sorted
container alongside the stack:

```python
import sortedcontainers          # or a skip list / balanced BST


class MinStackTopK:
    """Adds kMin(k): the k smallest values currently in the stack, ascending."""

    def __init__(self):
        self.stack = []
        self.sorted_values = sortedcontainers.SortedList()

    def push(self, x):
        self.stack.append(x)
        self.sorted_values.add(x)              # O(log n)

    def pop(self):
        value = self.stack.pop()
        self.sorted_values.remove(value)       # O(log n)
        return value

    def top(self):
        return self.stack[-1]

    def getMin(self):
        return self.sorted_values[0]           # O(1)

    def kMin(self, k):
        return list(self.sorted_values[:k])    # O(k)
```

If `sortedcontainers` is not available (it is not in the standard library - say so), the
honest alternatives are: a heap with lazy deletion (`getMin` amortised `O(log n)`, but
deletion of arbitrary popped values is the problem), or accept `O(n log n)` for `kMin` by
sorting a copy. State the trade-off rather than pretending the import exists.

**(b) The k most recent values of `getMin` over time**, i.e. the last k entries of the
`mins` stack. That is just `self.mins[-k:]`, `O(k)`. Cheap - which is why you must ask which
one they mean.

## Complexity

| | push | pop | top | getMin | kMin | space |
|---|---|---|---|---|---|---|
| Two stacks | `O(1)` | `O(1)` | `O(1)` | `O(1)` | - | `O(n)` |
| Compact variant | `O(1)` | `O(1)` | `O(1)` | `O(1)` | - | `O(n)` worst, less typically |
| With a sorted list | `O(log n)` | `O(log n)` | `O(1)` | `O(1)` | `O(k)` | `O(n)` |

Note that supporting `kMin` **costs you the O(1) push**. That trade is the answer to
"optimally" in the follow-up: you cannot have `O(1)` push and `O(k)` arbitrary order
statistics at once, and saying that explicitly is better than hand-waving.

## How to present it

1. **Say which operation is the hard one.** "push, pop and top are free on a list; the only
   constraint that bites is `getMin` in `O(1)`."
2. **Explain why one `min` variable fails** - the `pop` case. Show it with three values.
3. **State the insight**: "the minimum retraces its own history as we pop, so it is itself a
   stack."
4. **Write the simple two-stack version.** It is ten lines and it is correct.
5. **Volunteer the compact variant and the `<=` trap** without being asked. That is the
   duplicates follow-up, pre-empted.
6. **Ask what `kMin` means** before writing it, then give the sorted-container answer and
   name the cost you are paying for it.
7. **Close** on the empty-stack behaviour - which sets you up for the third follow-up.

## Follow-ups and variations

- **"Return the top k minimums, optimally."** See above. The key move is asking which of the
  two readings they want, then naming the push/query trade-off.
- **"What if there are duplicates?"** The `<=` rule in the compact variant. Trace `2, 2, pop`.
- **"What happens if you use `raise` instead of `return`?"** A Python-semantics probe, asked
  verbatim. Answer: `return` hands a value back to the caller and unwinds one frame
  normally; `raise` propagates an exception up the call stack until something catches it,
  and if nothing does, the program terminates with a traceback. For an empty stack, raising
  is the right choice, because there is no in-band value that could mean "empty" without
  colliding with a legitimate element - returning `None` would be ambiguous if `None` (or
  `-1`) can be a real stack value. Mention that `list.pop()` itself raises `IndexError`, so
  raising is also the *consistent* choice. If they push further: a custom exception subclass
  makes the failure catchable without swallowing unrelated `IndexError`s.
- **"Can you do it with O(1) extra space?"** Yes, with the encoding trick: store
  `2*x - current_min` on the stack when a new minimum arrives, so the previous minimum is
  recoverable as `2*min - stored`. Show it if asked, but say plainly that it trades clarity
  and overflow-safety for a constant factor, and that you would not ship it. Interviewers
  usually want to hear the judgement, not the trick.
- **"Max stack too?"** Symmetric second stack. Or one stack of `(value, running_min,
  running_max)` tuples.
- **"Make it a queue instead of a stack (min queue)."** Much harder, and worth naming: two
  stacks simulating a queue, each carrying its own running minimum, or a monotonic deque for
  a sliding-window minimum. Different problem, and saying so is correct.
- **"Thread safety."** A lock around the pair of stacks - they must be updated atomically or
  the invariant `len(stack) == len(mins)` breaks.

## Pitfalls

- **A single `min` variable.** Fails on `pop`.
- **`<` instead of `<=`** in the compact variant. The duplicates bug.
- **Pushing to `mins` but forgetting to pop it**, so the two stacks drift apart.
- **Comparing with `self.mins[-1]` when `mins` is empty** on the first push - `IndexError`.
- **Returning `-1` or `None` for an empty stack** and then being unable to distinguish it
  from a real value.
- **Using a heap for `getMin`.** `heap[0]` is `O(1)`, but removing the element that `pop`
  just took off the stack is `O(n)` in a heap - the structures do not line up.
- **Claiming the `kMin` version is still O(1) push.** It is not, and the interviewer will
  check.
