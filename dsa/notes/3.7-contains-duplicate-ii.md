**Link:** https://leetcode.com/problems/contains-duplicate-ii
**Difficulty:** Easy | **LeetCode #219**
**Bloomberg frequency:** 38% at three months.

A short question with two equally good solutions - a **fixed-size window of a set**, and a
**hash map of last-seen indices**. Knowing both and being able to say when each is preferable
is the whole answer. It also sets up the much harder Contains Duplicate III.

## 1. Problem statement

Given an integer array `nums` and an integer `k`, return `True` if there are two **distinct
indices** `i` and `j` such that `nums[i] == nums[j]` and `abs(i - j) <= k`.

```
nums = [1,2,3,1],     k = 3  ->  True    indices 0 and 3, distance 3
nums = [1,0,1,1],     k = 1  ->  True    indices 2 and 3, distance 1
nums = [1,2,3,1,2,3], k = 2  ->  False   the repeats are all 3 apart
```

## 2. Clarifying questions

1. **Is the distance condition `<= k` or `< k`?** `<=`. Example 1 has distance exactly 3 with
   `k = 3` and returns `True`.
2. **Must the indices be distinct?** Yes, so `k = 0` can never produce a match - worth
   stating as an edge case.
3. **Return a boolean, or the pair?** A boolean.
4. **Any constraint on the values?** Arbitrary integers, possibly negative. Nothing to
   exploit.
5. **Sizes?** Up to 10^5, so `O(n^2)` will time out. `k` may exceed `n`.
6. **Is this the "within k of each other in value too" variant?** No - that is Contains
   Duplicate III (LC 220), a much harder problem. Confirm which one.

## 3. Intuition

Brute force: for each `i`, compare against the next `k` elements. `O(n * k)`, which is
`O(n^2)` when `k` is large.

Two clean linear solutions.

### (a) Sliding window of a set

Maintain a set holding the values in the last `k` positions.

> **If the incoming value is already in that window, a qualifying pair exists. Otherwise add
> it, and evict the value that has just fallen out of range.**

The window has **fixed size `k`**, so there is no shrink decision - just add the entering
element and remove the one `k+1` positions back. That makes it the simplest shape from the
primer.

Note the window holds at most `k` elements, so space is `O(min(n, k))` - better than the map
version when `k` is small and `n` is huge.

### (b) Hash map of last-seen indices

For each value, remember the **most recent** index at which it appeared.

> **When you meet a value again, check the gap against the stored index. Then overwrite the
> stored index with the current one.**

Overwriting is the subtle part, and worth justifying: the most recent occurrence is always
the best candidate for a future match, because it is the closest. Keeping an older index
could only give a larger gap. So you never need a list of positions - one index per value
suffices.

Space is `O(distinct values)`, which can be `O(n)`.

### Which to prefer

| | Time | Space | Best when |
|---|---|---|---|
| Set window | `O(n)` | `O(min(n, k))` | `k` is small relative to `n` |
| Last-index map | `O(n)` | `O(distinct values)` | `k` is large, or you want the indices |

Offer both and name the trade. That is a better answer than either solution alone on a
question this small.

## 4. Approach

**Set window:**
1. `window = set()`.
2. For each `i`, `x`: if `x in window` return `True`; add `x`; if `len(window) > k` remove
   `nums[i - k]`.
3. Return `False`.

**Index map:**
1. `last = {}`.
2. For each `i`, `x`: if `x in last and i - last[x] <= k` return `True`; `last[x] = i`.
3. Return `False`.

## 5. Solution

```python
def contains_nearby_duplicate(nums, k):
    """True if some value repeats within a distance of k.

    A fixed-size window of the last k values: if the incoming value is already in the
    window, a qualifying pair exists. The window never needs to shrink adaptively, so
    the element falling out of range is simply evicted each step.
    """
    if k <= 0:
        return False                # indices must be distinct, so k = 0 can never match

    window = set()
    for i, x in enumerate(nums):
        if x in window:
            return True
        window.add(x)
        if len(window) > k:
            # nums[i - k] has just fallen out of range.
            window.discard(nums[i - k])
    return False
```

```python
contains_nearby_duplicate([1, 2, 3, 1], 3)          # True
contains_nearby_duplicate([1, 0, 1, 1], 1)          # True
contains_nearby_duplicate([1, 2, 3, 1, 2, 3], 2)    # False
contains_nearby_duplicate([1, 1], 0)                # False
contains_nearby_duplicate([1, 1], 1)                # True
contains_nearby_duplicate([], 1)                    # False
contains_nearby_duplicate([1], 1)                   # False
contains_nearby_duplicate([1, 2, 1], 2)             # True
contains_nearby_duplicate([1, 2, 1], 1)             # False
contains_nearby_duplicate([99, 99], 2)              # True
```

`[1,1]` with `k = 0` returning `False` is the edge case worth stating - the indices must be
distinct, so a distance of 0 is impossible. The guard also prevents `nums[i - k]` from
evicting the element you just added.

### The last-index map version

```python
def contains_nearby_duplicate_map(nums, k):
    """Equivalent. Overwriting the stored index is safe: the most recent occurrence is
    always the closest candidate for any future match."""
    last = {}                       # value -> most recent index
    for i, x in enumerate(nums):
        if x in last and i - last[x] <= k:
            return True
        last[x] = i                 # keep only the latest index
    return False


contains_nearby_duplicate_map([1, 2, 3, 1], 3)          # True
contains_nearby_duplicate_map([1, 0, 1, 1], 1)          # True
contains_nearby_duplicate_map([1, 2, 3, 1, 2, 3], 2)    # False
contains_nearby_duplicate_map([1, 1], 0)                # False
contains_nearby_duplicate_map([1, 2, 1], 1)             # False
contains_nearby_duplicate_map([], 1)                    # False
```

Note this version needs no `k <= 0` guard: with `k = 0`, `i - last[x]` is at least 1 for
distinct indices, so it can never satisfy `<= 0`. That is a small elegance worth pointing
out.

### The brute force

```python
def contains_nearby_duplicate_brute(nums, k):
    """O(n * k): compare each element against the next k."""
    for i in range(len(nums)):
        for j in range(i + 1, min(i + k + 1, len(nums))):
            if nums[i] == nums[j]:
                return True
    return False


contains_nearby_duplicate_brute([1, 2, 3, 1], 3)        # True
contains_nearby_duplicate_brute([1, 2, 3, 1, 2, 3], 2)  # False
contains_nearby_duplicate_brute([1, 1], 0)              # False
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n * k)` | `O(1)` |
| **Set window** | **`O(n)` average** | `O(min(n, k))` |
| **Last-index map** | **`O(n)` average** | `O(distinct values)` |

"Average" because both rest on hashing. The set window's `O(min(n, k))` space is the reason
to prefer it when `k` is small - worth saying, because it is the only real difference between
the two.

## 7. How to present it

This is a five-minute question; use the spare time on the comparison and the follow-up.

1. **Restate**, and confirm `<= k` and that the indices must be distinct.
2. **Ask which variant it is** - LC 219 (index distance only) or LC 220 (index *and* value
   distance). They are very different problems.
3. **State the brute force** - `O(n*k)`.
4. **Give both linear solutions**, one sentence each, then **name the trade-off**: "The set
   window uses `O(min(n,k))` space, which is better when `k` is small; the map uses
   `O(distinct values)` but gives me the indices for free."
5. **Write one** - the map version is shorter and needs no `k <= 0` guard.
6. **Justify overwriting the index**: *"The most recent occurrence is always the closest
   candidate, so an older index can never be more useful."*
7. **Test** `k = 0`, `k` larger than the array, no duplicates, and adjacent duplicates.
8. **Close**: `O(n)` average, and offer the LC 220 generalisation as the harder cousin.

## 8. Follow-ups and variations

- **"Contains Duplicate III"** (LC 220). Now the **values** must also be within `t` of each
  other, not just equal. The set no longer works - you need a structure with a "nearest
  neighbour" query over the window. Two standard answers: a **bucketing** scheme (bucket
  width `t+1`, so a match is in the same bucket or an adjacent one - `O(n)`), or an ordered
  set / balanced BST over the window (`O(n log k)`). Naming both is a strong answer.
- **"Return the indices, not a boolean."** The map version already has them.
- **"Find all such pairs."** Now a single last-index is not enough; keep a list of indices
  per value, or emit as you scan. Output can be `O(n^2)`.
- **"Contains Duplicate I"** (LC 217) - just `len(set(nums)) != len(nums)`.
- **"What if the array is a stream?"** The set window is ideal - bounded `O(k)` memory and no
  lookback. The map version grows without bound, which is a real argument for the window.
- **"Minimum distance between any two equal elements."** Same map, but track the minimum gap
  rather than returning early.
- **"What if `k` is larger than the array?"** Then it degenerates to Contains Duplicate I.
  The code handles it; check it.
- **"Memory is extremely tight."** A Bloom filter over the window gives false positives but
  bounded memory - mention only if pushed, since exactness usually matters.

## 9. Pitfalls

- **Using `<` instead of `<=`** for the distance. Example 1 has distance exactly `k`.
- **Forgetting the `k <= 0` guard** in the set version, where `nums[i - k]` with `k = 0`
  evicts the element just inserted - making it always return `False`, which happens to be
  right, but for the wrong reason, and `k < 0` would index from the end of the list.
- **Keeping the first index instead of the most recent** in the map version, which misses
  closer pairs.
- **Storing a list of all indices per value** when the latest suffices.
- **Evicting `nums[i - k - 1]`** or `nums[i - k + 1]` - off by one in the window.
- **Using `remove` instead of `discard`**, which raises if the value was already evicted as a
  duplicate.
- **Confusing this with LC 220** and trying to compare values.
- **Comparing every pair** and calling it linear.
