**Difficulty:** Medium | **LeetCode #167**
**Bloomberg frequency:** 38% at six months.

Two Sum with the array **sorted** and an `O(1)`-space requirement. The point of the question
is the contrast: the sortedness lets two pointers replace the hash map, trading `O(n)` space
for nothing. It also has a **1-indexed** return value, which is the most common way people
get it wrong.

> See [[1.1 Two Sum]] for the hash-map original.

## 1. Problem statement

Given a **1-indexed** array of integers `numbers` sorted in **non-decreasing** order, find
two numbers that add up to a specific `target`.

Return the indices of the two numbers, `index1` and `index2`, **added by one**, as an array
`[index1, index2]` where `1 <= index1 < index2 <= numbers.length`.

There is **exactly one solution**, and you may not use the same element twice.

Your solution must use only **constant extra space**.

```
numbers = [2,7,11,15], target = 9   ->  [1,2]
numbers = [2,3,4],     target = 6   ->  [1,3]
numbers = [-1,0],      target = -1  ->  [1,2]
```

## 2. Clarifying questions

1. **1-indexed or 0-indexed return?** **1-indexed.** Stated explicitly, and it is the single
   most common mistake on this problem. Say it back.
2. **Exactly one solution guaranteed?** Yes, so no "not found" case and no ambiguity about
   which pair to return.
3. **Constant extra space?** Yes - that is what rules out the hash map and forces two
   pointers.
4. **Can values be negative?** Yes - example 3. The two-pointer logic is unaffected, but any
   "sum only grows" reasoning must be about *moving the pointers*, not about the values'
   signs.
5. **Are duplicates possible?** Yes, the array is non-decreasing. With exactly one solution
   guaranteed, this does not complicate anything.
6. **Sorted ascending?** Yes.

## 3. Intuition

The hash map from 1.1 works and is `O(n)` time - but it costs `O(n)` space, which is
forbidden. The sortedness gives you something better.

Start with the two extreme candidates: the smallest and largest elements.

> **If the sum is too small, the only way to increase it is to move the left pointer right.
> If it is too large, move the right pointer left.**

### The exchange argument - say this

Suppose `numbers[lo] + numbers[hi] < target`. Consider every pair that uses `lo`:

- its partner is at most `numbers[hi]`, since `hi` is the largest remaining index;
- so its sum is at most `numbers[lo] + numbers[hi]`, which is already too small.

Therefore `lo` cannot be part of **any** solution among the remaining elements, and
discarding it loses nothing. Symmetrically when the sum is too large.

That is the justification, and it is what an interviewer wants to hear. "Move the smaller
one" without the reason is a memorised answer; this is a reasoned one.

Each step eliminates exactly one element, so the loop runs at most `n - 1` times.

### Why not binary search?

You *can*: for each `i`, binary search the remainder for `target - numbers[i]`. That is
`O(n log n)` time and `O(1)` space - correct, and worse than the two-pointer `O(n)`. It is
worth mentioning precisely because this problem sits in the Binary Search part: the sorted
input suggests binary search, but two pointers beats it here. Knowing when *not* to reach for
the obvious tool is the lesson.

## 4. Approach

1. `lo, hi = 0, n - 1`.
2. While `lo < hi`:
   - `total = numbers[lo] + numbers[hi]`
   - if `total == target`: return `[lo + 1, hi + 1]`
   - if `total < target`: `lo += 1`
   - else: `hi -= 1`
3. (Unreachable, given the guarantee.)

## 5. Solution

```python
def two_sum_sorted(numbers, target):
    """Indices (1-indexed) of the two numbers summing to target, in a sorted array.

    Starting at the extremes, a sum that is too small means the left element cannot
    pair with anything remaining - its best partner is already the largest available.
    So it can be discarded. Symmetrically for the right. O(1) space.
    """
    lo, hi = 0, len(numbers) - 1

    while lo < hi:
        total = numbers[lo] + numbers[hi]
        if total == target:
            return [lo + 1, hi + 1]     # the problem is 1-indexed
        if total < target:
            lo += 1                     # need a bigger sum; only lo can grow it
        else:
            hi -= 1                     # need a smaller sum; only hi can shrink it

    return []                           # unreachable given "exactly one solution"
```

```python
two_sum_sorted([2, 7, 11, 15], 9)       # [1, 2]
two_sum_sorted([2, 3, 4], 6)            # [1, 3]
two_sum_sorted([-1, 0], -1)             # [1, 2]
two_sum_sorted([1, 2, 3, 4, 5], 9)      # [4, 5]
two_sum_sorted([1, 2, 3, 4, 5], 3)      # [1, 2]
two_sum_sorted([0, 0, 3, 4], 0)         # [1, 2]
two_sum_sorted([-5, -3, 0, 2, 8], -3)   # [1, 4]
two_sum_sorted([5, 25, 75], 100)        # [2, 3]
```

`[0,0,3,4]` with target 0 is the duplicates-and-zero case; `[-5,-3,0,2,8]` with target `-3`
exercises negatives on both sides. `[1,2,3,4,5]` with targets 9 and 3 puts the answer at each
end, so between them they confirm both pointers move correctly.

### The binary search alternative

```python
import bisect


def two_sum_sorted_binary(numbers, target):
    """O(n log n), O(1) space. Correct, and strictly worse than two pointers -
    included because the sorted input makes it the tempting first idea."""
    n = len(numbers)
    for i in range(n):
        need = target - numbers[i]
        # Search only to the right of i, so an element cannot pair with itself.
        j = bisect.bisect_left(numbers, need, i + 1, n)
        if j < n and numbers[j] == need:
            return [i + 1, j + 1]
    return []


two_sum_sorted_binary([2, 7, 11, 15], 9)        # [1, 2]
two_sum_sorted_binary([2, 3, 4], 6)             # [1, 3]
two_sum_sorted_binary([-1, 0], -1)              # [1, 2]
two_sum_sorted_binary([0, 0, 3, 4], 0)          # [1, 2]
two_sum_sorted_binary([5, 25, 75], 100)         # [2, 3]
```

Note the search range starts at `i + 1`, which is what prevents an element pairing with
itself - the analogue of the "record after the lookup" ordering in 1.1.

### The hash-map version, and why it is disallowed

```python
def two_sum_sorted_hashmap(numbers, target):
    """O(n) time but O(n) space - which the problem forbids. It also ignores the
    sortedness entirely, which is the point of the question."""
    seen = {}
    for i, x in enumerate(numbers):
        if target - x in seen:
            return [seen[target - x] + 1, i + 1]
        seen[x] = i
    return []


two_sum_sorted_hashmap([2, 7, 11, 15], 9)       # [1, 2]
two_sum_sorted_hashmap([2, 3, 4], 6)            # [1, 3]
two_sum_sorted_hashmap([-1, 0], -1)             # [1, 2]
```

Mention it to show you know 1.1, then reject it on the space constraint. That sequence -
"here is the unsorted solution, here is why the sortedness lets me do better" - is the
cleanest way to present this question.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force, all pairs | `O(n^2)` | `O(1)` |
| Hash map | `O(n)` | `O(n)` - **disallowed** |
| Binary search per element | `O(n log n)` | `O(1)` |
| **Two pointers** | **`O(n)`** | **`O(1)`** |

Each iteration eliminates exactly one element, so at most `n - 1` iterations. Optimal on both
axes given the constraint, and the only approach that achieves `O(n)` time *and* `O(1)`
space.

## 7. How to present it

1. **Restate**, and **say "1-indexed" out loud.** Then say it again when you write the
   `return`. It is the most common error on this problem and it costs nothing to avoid.
2. **Connect to 1.1**: *"Unsorted, I'd use a hash map for `O(n)` time - but that's `O(n)`
   space, which is ruled out here. The array being sorted lets me do better."*
3. **State the approach**: two pointers at the extremes, moving inward.
4. **Give the exchange argument**, properly: *"If the sum is too small, then this left
   element paired with anything still available is also too small, because its best available
   partner is the current right element. So it can never be part of a solution and I can
   discard it."* **This is the scoring moment.**
5. **Write it.** Eight lines.
6. **Mention the binary-search alternative and reject it**: `O(n log n)` versus `O(n)`.
   Doing this shows you considered the tool the problem's placement suggests.
7. **Test** an answer at each end, the negatives case, and the duplicates case.
8. **Close**: `O(n)` time, `O(1)` space, at most `n-1` iterations since each step eliminates
   one element.

## 8. Follow-ups and variations

- **"What if the array were not sorted?"** That is 1.1 - hash map, `O(n)` time and space. Or
  sort first for `O(n log n)` and `O(1)`, **but sorting destroys the original indices**,
  which is exactly the reported Bloomberg follow-up in 23.17.
- **"Find all pairs summing to the target."** Continue after a hit, moving **both** pointers
  and skipping duplicates - the 3Sum dedup pattern from 2.1.
- **"Count the pairs rather than finding one."** Handle duplicate blocks
  combinatorially - see 23.16, which is the reported Bloomberg counting variant.
- **"Find two numbers whose difference is the target."** Both pointers move **forward** here,
  not inward, because you are growing or shrinking a gap. See 23.17.
- **"3Sum on a sorted array."** Fix one element, two-pointer the rest - 2.1.
- **"Two Sum in a BST"** (LC 653). Inorder traversal gives a sorted sequence, so the same two
  pointers apply with two iterators - or use a hash set while traversing.
- **"What if the array is enormous and on disk?"** Two pointers is ideal: two sequential
  scans from opposite ends, `O(1)` memory, which a hash map could not do.
- **"What if no solution exists?"** Return `[]` or `[-1,-1]`; the loop exits when the pointers
  meet.

## 9. Pitfalls

- **Returning 0-indexed positions.** `[0,1]` instead of `[1,2]`. **The defining mistake.**
- **`while lo <= hi`**, which lets an element pair with itself when `lo == hi`.
- **Moving both pointers on a mismatch**, which can skip the answer.
- **Moving the wrong pointer** - if the sum is too small you must move `lo` up, not `hi`
  down.
- **Using a hash map** despite the constant-space requirement.
- **Sorting the array** when it is already sorted, or sorting an unsorted variant without
  preserving indices.
- **Giving the algorithm without the exchange argument.** The justification is the graded
  part.
- **Reaching for binary search** because the problem is filed under binary search. It works
  and it is slower; say so deliberately rather than by accident.
