## 1. Problem statement

Given an array of integers `nums` and an integer `target`, return the **indices** of the two
numbers such that they add up to `target`.

You may assume each input has **exactly one solution**, and you may not use the same element
twice. You may return the answer in any order.

```
nums = [2,7,11,15], target = 9   ->  [0,1]    because nums[0] + nums[1] == 9
nums = [3,2,4],     target = 6   ->  [1,2]
nums = [3,3],       target = 6   ->  [0,1]
```

## 2. Clarifying questions

Even on an easy question, ask. It costs 30 seconds and it is scored.

1. **Indices or values?** LeetCode wants indices. Bloomberg variants have wanted both.
2. **Is exactly one solution guaranteed?** If not, return the first pair, all pairs, or a
   count? The reported Bloomberg variant asks for a **count** (23.16).
3. **Can I use the same element twice?** No - `[3]` with target `6` is not a solution.
4. **Is the array sorted?** Not in general. If it is, the two-pointer solution is `O(1)`
   space (see 5.18).
5. **Can values be negative? Zero? Duplicated?** Yes to all. `[3,3]` is a given test case.
6. **Can I modify the input?** Matters if you want to sort.
7. **How large is the array?** Decides whether `O(n^2)` is even acceptable as a fallback.

## 3. Intuition

The brute force checks every pair: for each `i`, scan every `j > i`. That is `O(n^2)` and the
waste is obvious - for each `i` you re-scan the whole array looking for one specific value.

Rearrange the equation:

```
nums[i] + nums[j] == target      becomes      nums[j] == target - nums[i]
```

So you are not searching for "some element that works" - you are searching for **one exact
value**, the complement. Looking up an exact value is what a hash map does in `O(1)`.

That gives a one-pass algorithm: walk the array; for each element, ask whether its
complement has already been seen; if yes you are done, if no, record this element and
continue.

> **The subtle part: look up first, record second.**

If you record `nums[i]` before checking, then for `target == 2 * nums[i]` the element finds
*itself* and you return `(i, i)`. Checking first makes self-pairing impossible without any
special case, because the map only ever contains strictly earlier elements.

This "query, then record" ordering is the reusable idea. It recurs in 23.16, 23.17 and
throughout Part 1.

## 4. Approach

**Brute force** - state it, do not code it.
```
for i in range(n):
    for j in range(i+1, n):
        if nums[i] + nums[j] == target: return (i, j)
```
`O(n^2)` time, `O(1)` space.

**Two-pass hash.** Build `value -> index` for everything, then scan looking for complements.
Works, but needs a guard so an element does not match itself, and it is strictly worse than
the one-pass version. Mention it only to discard it.

**One-pass hash - the answer.**
1. `seen = {}` mapping value to the index where it was found.
2. For each index `i` with value `x`:
   - if `target - x` is in `seen`, return `(seen[target - x], i)`;
   - otherwise set `seen[x] = i`.
3. If the loop finishes, there is no answer.

## 5. Solution

```python
def two_sum(nums, target):
    """Indices of the two numbers in `nums` that add up to `target`.

    One pass. For each element the partner is a single known value, target - x,
    so a hash map answers "have I already seen that?" in O(1) average.
    """
    seen = {}                        # value -> the index it was first seen at
    for i, x in enumerate(nums):
        complement = target - x
        if complement in seen:
            # Found at the SECOND element of the pair, so the first index is the
            # stored one and this one is later.
            return (seen[complement], i)
        # Recorded only after the lookup, so x can never pair with itself.
        seen[x] = i
    return None                      # no pair (LeetCode guarantees this cannot happen)
```

```python
two_sum([2, 7, 11, 15], 9)      # (0, 1)
two_sum([3, 2, 4], 6)           # (1, 2)
two_sum([3, 3], 6)              # (0, 1)
two_sum([3], 6)                 # None
two_sum([], 0)                  # None
two_sum([0, 4, 3, 0], 0)        # (0, 3)
two_sum([-1, -2, -3, -4], -6)   # (1, 3)
```

Two of those are the ones to mention aloud: `[3]` with target `6` proves no self-pairing, and
`[0,4,3,0]` with target `0` proves duplicates and zeros work.

### The variant where the array is sorted

If the input is sorted, two pointers do it in `O(1)` extra space:

```python
def two_sum_sorted(nums, target):
    """O(1) extra space, requires nums to be sorted ascending."""
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        current = nums[lo] + nums[hi]
        if current == target:
            return (lo, hi)
        if current < target:
            lo += 1                  # need a larger sum: only the left can grow
        else:
            hi -= 1                  # need a smaller sum: only the right can shrink
    return None


two_sum_sorted([2, 7, 11, 15], 9)       # (0, 1)
two_sum_sorted([2, 3, 4], 6)            # (0, 2)
two_sum_sorted([-3, 3, 4], 0)           # (0, 1)
```

The move is justified by monotonicity: if the sum is too small, increasing `hi` is impossible
(it only shrinks the sum further), so `lo` must move. That argument is the whole of Part 2
and is worth practising here. Full note at 5.18.

**But**: if you sort an unsorted input yourself, you destroy the original indices. Carry them
along or sort `(value, index)` pairs. This is exactly what the reported "does reordering
matter?" follow-up (23.17) is probing.

## 6. Complexity

| Approach | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` |
| One-pass hash | **`O(n)` average** | `O(n)` |
| Sort + two pointers | `O(n log n)` | `O(1)` extra (or `O(n)` to keep indices) |

Say **average** for the hash version: it rests on hashing, and the worst case is `O(n)` per
lookup if every key collides, making it `O(n^2)` overall. Volunteering that is what sets up
the hashing follow-up on your terms rather than theirs.

Space is `O(n)` for the map in the worst case (no pair found until the end).

## 7. How to present it

1. **Restate**: "Return the indices of the two numbers summing to the target, exactly one
   solution, can't reuse an element."
2. **Ask** at minimum: indices or values, sorted or not, what if no solution.
3. **Brute force in one sentence** with its complexity. "For each element I scan the rest -
   that's O(n squared). The waste is that I'm rescanning for one specific value each time."
4. **Derive the complement on the board**: `nums[i] + nums[j] == target` becomes
   `nums[j] == target - nums[i]`. "So it's an exact-value lookup, which is a hash map."
5. **Announce**: "One pass, a dict from value to index. For each element I check if its
   complement is already in the dict."
6. **Write it**, and as you type the last line say: *"I record after the lookup - that's what
   stops an element pairing with itself."* Point at the two lines.
7. **Test out loud**: `[2,7,11,15]` walks through; `[3,3]` shows duplicates work; `[3]` with
   target 6 shows the self-pairing guard.
8. **Close**: "O(n) average time, O(n) space. Average because it's hashing - worst case is
   O(n) per lookup if everything collides."

That last clause is bait for the follow-up you have prepared for.

## 8. Follow-ups and variations

- **"How does hashing work in a set and a hash map?"** Asked verbatim in this loop. Full
  answer in [[0.6 Python toolkit for interviews]]: hash function to integer, reduce to a
  bucket, collisions by chaining or open addressing, load factor triggers an `O(n)` resize
  and rehash, so amortised `O(1)`, worst case `O(n)`. CPython uses open addressing with a
  perturbation probe and randomises string hashes per process.
- **"Count all pairs that sum to the target."** Reported as its own question (23.16). Ask
  **unique by index or by value** - the answers differ. By index it is the same loop with
  `total += counts[target - x]` before recording.
- **"Find two numbers whose difference is the target."** Reported (23.17). `b == a + target`,
  but subtraction is not commutative so check **both** `x - target` and `x + target`.
- **"What if the array is sorted?"** Two pointers, `O(1)` space. Then: **"does reordering
  matter?"** Yes - existence is unchanged but the reported indices are not.
- **"Return the values instead of the indices."** Then sorting is free and two pointers is
  the better answer.
- **"3Sum."** Sort, fix one element, two-pointer the rest - `O(n^2)`. Note the dedup rule
  changes to *by value*. See 2.1.
- **"4Sum / kSum."** Recursive reduction to 2Sum, `O(n^(k-1))`. See 2.8.
- **"What if no solution exists?"** Return `None`; decide and state it.
- **"What if there are multiple solutions?"** Ask which one they want - first, all, or best
  by some measure.
- **"It's a stream and you can't hold it all."** The one-pass version already works: it never
  revisits an element and memory is `O(distinct values seen)`.
- **"Two Sum with a BST / sorted linked list."** Inorder traversal plus two pointers, or a
  set while traversing.
- **"Memory is tight."** Sort in place and use two pointers - `O(n log n)` time, `O(1)` extra.

## 9. Pitfalls

- **Recording before the lookup**, allowing `(i, i)`. Test `[3]` with target `6`.
- **Returning values when indices were asked for** (or vice versa).
- **Sorting without preserving indices**, then returning indices into the sorted array.
- **Using a `set` instead of a `dict`** - you get "does a pair exist" but lose the index.
- **Assuming distinct values.** `[3,3]` is an explicit test case; a `dict` handles it because
  the first `3` is stored and the second finds it.
- **Assuming positive values.** Negatives and zero are legal; the complement arithmetic is
  unaffected, but any "sum only grows" reasoning is not.
- **The two-pass version without a self-match guard**, which returns `(i, i)`.
- **Quoting `O(1)` for the lookup without saying "average".**
- **Treating it as trivial and going quiet.** The question is a vehicle for the follow-ups;
  narrate as you would on a hard one.
