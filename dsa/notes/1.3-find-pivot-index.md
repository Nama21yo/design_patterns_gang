**Link:** https://leetcode.com/problems/find-pivot-index
**Difficulty:** Easy | **LeetCode #724**
**Bloomberg frequency:** 62% in the **30-day** window.

The cleanest possible demonstration that you do not need a prefix *array* - a running total
plus the total sum is enough. Also identical to LC 1991, *Find the Middle Index in Array*.

## 1. Problem statement

Given an array of integers `nums`, return the **leftmost pivot index**: the index where the
sum of everything strictly to its left equals the sum of everything strictly to its right.

If the index is at either edge, the sum on that side is `0`. Return `-1` if no such index
exists.

```
nums = [1,7,3,6,5,6]  ->  3     left = 1+7+3 = 11, right = 5+6 = 11
nums = [1,2,3]        ->  -1
nums = [2,1,-1]       ->  0     left = 0, right = 1 + (-1) = 0
```

Note `-1000 <= nums[i] <= 1000` - **values can be negative**, which kills any "sums only
grow" shortcut.

## 2. Clarifying questions

1. **Is the pivot element itself included in either sum?** No - "strictly to the left" and
   "strictly to the right". The pivot is excluded from both.
2. **Leftmost if several qualify?** Yes, return the first.
3. **Can values be negative?** Yes. Example 3 has `-1`, and it means a later index can become
   a pivot even after the left sum has grown past the right sum.
4. **What if the array is empty or has one element?** LeetCode guarantees at least one. A
   single element is always a pivot at index 0 (both sides empty, `0 == 0`) - worth stating.
5. **Return the index or the value?** The index.

## 3. Intuition

Brute force: for each index, sum everything left and everything right. `O(n^2)`.

The waste is re-summing the same prefixes. But the improvement people reach for first -
"build a prefix array and a suffix array" - is more than you need. Observe:

```
left + nums[i] + right == total
```

so **`right = total - left - nums[i]`**. You only ever need two numbers: the total (computed
once) and a running left sum. The condition `left == right` becomes

```
left == total - left - nums[i]
```

or equivalently `2 * left + nums[i] == total`, which avoids any subtraction ordering worry.

> **One pass for the total, one pass with a running left sum. `O(1)` extra space.**

The general lesson is the one to voice: *a prefix array is the default tool, but if you only
need one prefix at a time, a running scalar replaces it.* That observation carries into
1.5 Product of Array Except Self and most of Part 3.

## 4. Approach

1. `total = sum(nums)`.
2. `left = 0`.
3. For each index `i` with value `x`:
   - the right sum is `total - left - x`;
   - if `left == total - left - x`, return `i`;
   - `left += x`.
4. Return `-1`.

The update `left += x` happens **after** the check, because the pivot element is not part of
the left sum. Same query-then-record discipline as Two Sum.

## 5. Solution

```python
def pivot_index(nums):
    """Leftmost index where the sum strictly left equals the sum strictly right.

    right = total - left - nums[i], so a running left sum and the total are enough -
    no prefix array is needed.
    """
    total = sum(nums)
    left = 0
    for i, x in enumerate(nums):
        # The pivot itself belongs to neither side.
        if left == total - left - x:
            return i
        left += x                   # updated after the check, not before
    return -1
```

```python
pivot_index([1, 7, 3, 6, 5, 6])     # 3
pivot_index([1, 2, 3])              # -1
pivot_index([2, 1, -1])             # 0
pivot_index([0])                    # 0
pivot_index([-1, -1, -1, 0, 1, 1])  # 0
pivot_index([1, -1, 0])             # 2
pivot_index([])                     # -1
```

`[-1,-1,-1,0,1,1]` is the case worth saying aloud: left of index 0 is empty (0) and the rest
sums to 0, so index 0 wins even though nothing looks balanced. It is also a reminder that
negatives make "keep scanning until left exceeds right" wrong.

### The prefix-array version, for contrast

```python
import itertools


def pivot_index_prefix(nums):
    """Same answer via an explicit prefix array. Correct, but O(n) space for no gain."""
    prefix = list(itertools.accumulate(nums, initial=0))
    total = prefix[-1]
    for i in range(len(nums)):
        left = prefix[i]                        # sum of nums[0:i]
        right = total - prefix[i + 1]           # sum of nums[i+1:]
        if left == right:
            return i
    return -1


pivot_index_prefix([1, 7, 3, 6, 5, 6])          # 3
pivot_index_prefix([2, 1, -1])                  # 0
```

Show this only to say you considered it and chose the scalar version. The `initial=0`
sentinel and the `prefix[i+1]` are exactly the places an off-by-one would live, which is a
second reason to prefer the running total.

## 6. Complexity

| Approach | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` |
| Prefix array | `O(n)` | `O(n)` |
| Running total | **`O(n)`** | **`O(1)`** |

Two passes over the array (one for `sum`, one for the scan), which is still `O(n)`. If the
interviewer asks for a single pass, you cannot - you need the total before you can evaluate
the first index. Say that; it is a real constraint, not an oversight.

## 7. How to present it

1. **Restate**, emphasising that the pivot belongs to neither side, and check example 3 where
   the answer is index 0 with an empty left side.
2. **Ask about negatives** - and having confirmed it, note that it rules out any
   monotonic/early-exit reasoning.
3. **Brute force**: "for each index, sum both sides - O(n squared), and I'm re-summing the
   same prefixes."
4. **Derive the identity**: write `left + nums[i] + right == total` on the board and
   rearrange to `right = total - left - nums[i]`. "So I don't need a prefix array at all -
   the total plus one running scalar is enough."
5. **Announce**: "Sum once, then one pass maintaining the left sum, checking before I add the
   current element."
6. **Write it**, calling out that `left += x` comes after the check.
7. **Trace `[1,7,3,6,5,6]`** to index 3.
8. **Close**: `O(n)` time, `O(1)` space; two passes are necessary because the total must be
   known first; single element returns 0; no pivot returns -1.

## 8. Follow-ups and variations

- **"Return all pivot indices, not just the leftmost."** Collect instead of returning early;
  same complexity.
- **"Find the middle index"** (LC 1991) - literally the same problem, different name.
- **"Left sum equals right sum *including* the pivot on one side."** Re-derive; the condition
  becomes `left + x == total - left` or similar. The point of deriving rather than memorising
  is that this variant costs you nothing.
- **"Split the array into two parts with equal sums."** Now the pivot is a *boundary* rather
  than an element: find `i` with `prefix[i] == total - prefix[i]`. Note that this needs
  `total` to be even only if the values are integers with no element excluded.
- **"Three equal parts"** (LC 1013). Two boundaries; `total` must be divisible by 3, then
  scan for the two cut points.
- **"What if there are many queries on a static array?"** Now the prefix array earns its
  keep - precompute once, answer each query in `O(1)`.
- **"2D version: find a pivot row or column."** Row sums, then the same scalar trick.
- **"What if the array is streamed and you can't do two passes?"** You cannot answer
  online - the right sum depends on the future. You would need the total up front, or buffer.
- **"Overflow?"** Not in Python. In C++ or Java the running sum of 10^4 values up to 1000
  fits comfortably in a 32-bit int, but say you would check.

## 9. Pitfalls

- **Including the pivot in a sum.** The most common error. Check example 3 by hand.
- **Updating `left` before the comparison**, which shifts every answer by one.
- **Assuming non-negative values** and breaking early once `left > right`. Negatives make
  that invalid - `[-1,-1,-1,0,1,1]` has its pivot at index 0.
- **Returning the value at the pivot instead of the index.**
- **Returning the rightmost pivot** by continuing to scan and overwriting - the spec says
  leftmost, so return immediately.
- **Building both a prefix and a suffix array** - correct, `O(n)` space, and twice the
  opportunity for an off-by-one.
- **Off-by-one in `prefix[i+1]`** if you do use the prefix array.
- **Forgetting the single-element case**, which should return 0.
