**Link:** https://leetcode.com/problems/valid-parentheses
**Difficulty:** Easy | **LeetCode #20**
**Bloomberg frequency:** 62% at three months, 88% at six months.

The archetypal stack question. Eight lines, and the whole signal is in the **two failure
modes** - wrong closer, and unclosed openers at the end. Candidates who miss the second one
fail on the input `"("`.

## 1. Problem statement

Given a string `s` containing only the characters `'('`, `')'`, `'{'`, `'}'`, `'['` and
`']'`, determine if the input string is valid.

A string is valid if:
1. Open brackets are closed by the **same type** of bracket, and
2. Open brackets are closed in the **correct order**, and
3. Every close bracket has a corresponding open bracket of the same type.

```
s = "()"        ->  True
s = "()[]{}"    ->  True
s = "(]"        ->  False
s = "([)]"      ->  False
s = "{[]}"      ->  True
```

## 2. Clarifying questions

1. **Only these six characters?** Stated. If other characters could appear, ask whether they
   are ignored or invalid - it changes the loop.
2. **Is the empty string valid?** Conventionally yes (vacuously balanced). LeetCode's
   constraints say length >= 1, but ask - it is a one-word answer and it shows care.
3. **Must types match, or just counts?** Types - `"(]"` is invalid.
4. **Must nesting be respected?** Yes - `"([)]"` is invalid even though the counts balance.
   That example exists specifically to rule out a counter-based solution.
5. **Return a boolean?** Yes.
6. **Length limits?** Up to 10^4; nothing exotic.

## 3. Intuition

Why counting does not work: `"([)]"` has one of each bracket, perfectly balanced by count,
and is still invalid. Order matters, and specifically **the most recently opened bracket must
be the first to close**. That is LIFO, which is a stack.

> **Push every opener. On a closer, the top of the stack must be its matching opener - pop it
> if so, fail if not. At the end the stack must be empty.**

The three failure modes map exactly onto the three rules in the statement:

| Rule violated | How it is detected |
|---|---|
| Wrong type (`"(]"`) | top of stack is not the matching opener |
| Wrong order (`"([)]"`) | same check - `)` sees `[` on top |
| Closer with no opener (`"]"`) | stack is empty when a closer arrives |
| Opener never closed (`"("`) | **stack is non-empty at the end** |

The last row is the one people forget. It is not detected inside the loop at all - it is the
`return not stack` at the end.

Using a **dict from closer to opener** keeps the code short and avoids a chain of `if`s. It
also makes "is this a closer?" a single membership test.

## 4. Approach

1. `pairs = {")": "(", "]": "[", "}": "{"}`.
2. `stack = []`.
3. For each character:
   - if it is a closer: if the stack is empty or `stack.pop()` is not `pairs[ch]`, return
     `False`.
   - else: push it.
4. Return `not stack`.

## 5. Solution

```python
def is_valid(s):
    """True if the bracket string is balanced and correctly nested.

    The stack holds openers still waiting to be closed. A closer must match the most
    recent opener (LIFO), and anything left on the stack at the end was never closed.
    """
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []

    for ch in s:
        if ch in pairs:
            # A closer: the top must be its matching opener.
            # `not stack` catches a closer with nothing open at all.
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)

    # Anything still open was never closed - this is the check people forget.
    return not stack
```

```python
is_valid("()")          # True
is_valid("()[]{}")      # True
is_valid("(]")          # False
is_valid("([)]")        # False
is_valid("{[]}")        # True
is_valid("")            # True
is_valid("(")           # False
is_valid(")")           # False
is_valid("((")          # False
is_valid("))")          # False
is_valid("([{}])")      # True
is_valid("(()")         # False
```

The four one- and two-character cases are the ones to run out loud: `"("` fails only because
of the final check, `")"` fails only because of the empty-stack guard, and together they
prove both guards are doing work.

### A variant worth having ready: return the first invalid index

```python
def first_invalid_index(s):
    """Index of the first character that makes the string invalid, or -1 if valid.
    A natural follow-up, and it shows the stack is holding positions as well as types."""
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []                      # (character, index)

    for i, ch in enumerate(s):
        if ch in pairs:
            if not stack or stack[-1][0] != pairs[ch]:
                return i            # unmatched or mismatched closer
            stack.pop()
        else:
            stack.append((ch, i))

    return stack[0][1] if stack else -1     # first opener never closed


first_invalid_index("()[]{}")       # -1
first_invalid_index("([)]")         # 2
first_invalid_index("(")            # 0
first_invalid_index(")")            # 0
first_invalid_index("(()")          # 0
first_invalid_index("()(")          # 2
```

Storing `(char, index)` rather than just the character is the small change that makes this
possible, and it is the bridge to 4.14 *Minimum Remove to Make Valid Parentheses*.

### Why a counter fails - worth demonstrating

```python
def is_valid_counting_broken(s):
    """Counts only. Correct for a single bracket type, wrong for several."""
    depth = 0
    for ch in s:
        if ch in "([{":
            depth += 1
        else:
            depth -= 1
            if depth < 0:
                return False
    return depth == 0


is_valid_counting_broken("([)]")    # True   -- but the real answer is False
is_valid_counting_broken("()")      # True
is_valid_counting_broken("(]")      # True   -- also wrong
```

Showing that `"([)]"` passes the counting version is a ten-second way to justify the stack.
Note that for a **single** bracket type a counter *is* sufficient and uses `O(1)` space -
which is exactly the follow-up below.

## 6. Complexity

| | Time | Space |
|---|---|---|
| **Stack** | **`O(n)`** | `O(n)` worst case |
| Counter (single bracket type only) | `O(n)` | `O(1)` |

Space is `O(n)` because a string like `"((((("` pushes everything. You cannot do better in
general: with three bracket types you must remember the *sequence* of open types, and that is
`n` bits of information in the worst case. Saying that is a good answer to "can you do it in
`O(1)` space?" - the answer is no, and here is why.

## 7. How to present it

1. **Restate the three rules**, and point at `"([)]"`: *"the counts balance, so this isn't
   just counting - the nesting order matters."*
2. **Name the structure**: "Most recent opener must close first - that's LIFO, so a stack."
3. **Enumerate the failure modes before coding.** All four rows of the table above. Doing
   this first makes the code obviously complete rather than hopefully complete.
4. **Announce** the dict-from-closer-to-opener, which keeps it to one branch.
5. **Write it** - eight lines - and as you type `return not stack` say: *"this is the case
   people miss: `'('` alone never fails inside the loop."*
6. **Test out loud**: `"("`, `")"`, `""`, `"([)]"`. Four cases, ten seconds, and each one
   exercises a different guard.
7. **Close**: `O(n)` time, `O(n)` space - and pre-empt the space question: *"you can't do
   better than O(n) with multiple bracket types, because you have to remember the sequence of
   open types. With one type, a counter is O(1)."*
8. **Offer a follow-up** rather than stopping - the minimum-removals variant is the natural
   next step and is a real LeetCode Medium.

## 8. Follow-ups and variations

- **"What if there were only one bracket type?"** A counter, `O(1)` space: increment on `(`,
  decrement on `)`, fail if it goes negative, and require zero at the end.
- **"Return the minimum number of insertions to make it valid"** (LC 921). Track `open_needed`
  and `close_needed` with a counter - no stack required.
- **"Remove the minimum number of characters to make it valid"** (LC 1249, at 4.14). Stack of
  indices, mark the unmatched ones, rebuild. The natural harder version.
- **"Longest valid parentheses substring"** (LC 32). Much harder - stack of indices with a
  sentinel base, or DP. Name it.
- **"Valid Parenthesis String with wildcards `*`"** (LC 678, also on the Bloomberg list).
  Track a **range** `[min_open, max_open]` rather than a single count, or use two passes.
  A good follow-up that defeats the plain stack.
- **"Generate all valid combinations of n pairs"** (LC 22). Backtracking, Part 13.
- **"Check balance in a stream, reporting validity after each character."** The stack version
  already does this incrementally - just report `not stack` after each step.
- **"What if other characters appear?"** Decide: ignore them (add an `elif ch in "([{"`
  guard) or reject. The current code would *push* them, which is wrong - worth noticing.

## 9. Pitfalls

- **Forgetting the final `return not stack`**, so `"("` returns `True`. **The defining bug.**
- **Not guarding `stack.pop()` on an empty stack**, so `")"` raises `IndexError` instead of
  returning `False`.
- **Using a counter** with multiple bracket types - `"([)]"` passes.
- **Comparing the closer to the popped value directly** instead of mapping through `pairs`.
- **Pushing closers onto the stack** by writing the `if`/`else` the wrong way round.
- **Assuming only the listed characters appear**, when the current `else` branch pushes
  anything unrecognised as if it were an opener.
- **Using `if ch in "([{"`** to detect openers and then having no `else` for unexpected
  characters - either is fine, but be deliberate about which set you test.
- **Claiming `O(1)` space is achievable** for the multi-type version.
