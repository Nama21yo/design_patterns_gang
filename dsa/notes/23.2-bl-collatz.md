title: "23.2 Collatz steps (3n+1) with memoisation"
---

> Reported 6 times in R1 on 2025-10-09, 2025-10-17, 2025-10-20, 2025-10-28 and 2025-11-10.
> Tied for the most-repeated Bloomberg coding question. The follow-ups matter more than
> the base problem - the base problem is five lines.

## Prompt as given

```
If x is even then x = x / 2.
If x is odd  then x = 3 * x + 1.

Calculate the number of steps taken to reach 1.

For example x = 3 takes 7 steps:  3 -> 10 -> 5 -> 16 -> 8 -> 4 -> 2 -> 1
```

Wrapped as a LeetCode problem this is
[Sort Integers by The Power Value](https://leetcode.com/problems/sort-integers-by-the-power-value/)
(LC 1387), where the step count is called the "power value".

## Clarifying questions to ask first

1. **Is the step count the number of transitions, or the number of values visited?** For
   `x = 3` the chain has 8 values and 7 arrows; the expected answer is 7, so it is
   transitions. Confirm with the given example.
2. **What is `steps(1)`?** Zero.
3. **Range of x?** Are we told `1 <= x <= 10^6`, or is it unbounded? This decides whether a
   list cache or a dict cache is right.
4. **Will there be many calls, or one?** Ask this *before* coding - it is the follow-up that
   always comes, and pre-empting it is a strong signal.
5. **Is x always positive?** Zero and negatives never reach 1; decide whether to raise.

## Intuition

The sequence is a deterministic walk: every number has exactly one successor. So the whole
structure is a **forest of chains all flowing into 1** - in effect a tree rooted at 1 with
edges reversed. `steps(x)` is the depth of `x` in that tree.

That single observation gives you everything:

- One call: just walk the chain.
- Many calls: the chains **overlap heavily** (every chain ends `... -> 4 -> 2 -> 1`), so
  cache `steps(v)` for every `v` you touch. This is memoisation on a tree, and each node's
  value is computed once ever.

The naive memoisation mistake is caching only the *input*, `cache[x] = result`. That throws
away all the intermediate work. Caching every value on the path is what the interviewer is
driving at when they ask the third follow-up.

## Approach

**1. Single query, recursive.**

```
steps(1) = 0
steps(x) = 1 + steps(x / 2)      if x even
steps(x) = 1 + steps(3x + 1)     if x odd
```

**2. Single query, iterative.** Same recurrence as a `while` loop. The interviewer in one
report *forced* this version, because the recursion depth is unbounded - `x = 27` reaches
9232 and takes 111 steps, and the chain for large x can go much deeper than Python's
default recursion limit of 1000.

**3. Many queries: memoise every value on the path.** Walk the chain pushing each value onto
a stack until you hit a value already in the cache (or 1). Then unwind the stack, assigning
`cache[v] = cache[successor] + 1`. Now a single call for `x = 10` populates
`{10:6, 5:4, 16:7, 8:3, 4:2, 2:1, 1:0}` - exactly the cache contents the interviewer asked
for.

## Solution

### The iterative single-query version

```python
def collatz_steps(x):
    """Number of steps for x to reach 1. Iterative: no recursion depth limit."""
    if x < 1:
        raise ValueError("Collatz is only defined here for positive integers")
    steps = 0
    while x != 1:
        x = x // 2 if x % 2 == 0 else 3 * x + 1
        steps += 1
    return steps
```

Use `//` not `/`. In Python 3 `/` returns a float, and the chain silently turns into
floating point - a real bug that shows up as `16.0` in the cache keys.

### The version the follow-ups are asking for

```python
class Collatz:
    """Caches the step count for EVERY value seen, not just the queried ones."""

    def __init__(self):
        self.cache = {1: 0}

    def steps(self, x):
        if x < 1:
            raise ValueError("x must be a positive integer")

        # Walk forward until we reach a value we already know, recording the path.
        path = []
        while x not in self.cache:
            path.append(x)
            x = x // 2 if x % 2 == 0 else 3 * x + 1

        # Unwind: each value is exactly one step further from 1 than its successor.
        known = self.cache[x]
        for value in reversed(path):
            known += 1
            self.cache[value] = known
        return known
```

```python
c = Collatz()
c.steps(10)      # 6
c.cache          # {1: 0, 10: 6, 5: 4, 16: 7, 8: 3, 4: 2, 2: 1}
c.steps(16)      # 7, answered straight from the cache with no walking at all
```

### Wrapped as Sort Integers by The Power Value

```python
def get_kth(lo, hi, k):
    """LC 1387: sort [lo, hi] by Collatz step count, ties broken by the value itself,
    then return the k-th (1-indexed)."""
    c = Collatz()
    return sorted(range(lo, hi + 1), key=lambda x: (c.steps(x), x))[k - 1]
```

The `(steps, x)` tuple key is the whole tie-break rule. Python's `sorted` is stable, so
`key=c.steps` alone would also work here since `range` is already ascending - but say the
tuple version out loud, because it states the rule explicitly instead of relying on
stability.

For "the k-th smallest" specifically you can do better than a full sort with a size-k
max-heap, `O(n log k)` instead of `O(n log n)`. Mention it; code it only if asked.

## Complexity

Let `L(x)` be the length of x's Collatz chain. There is no known closed form - this is the
open Collatz conjecture, and saying so is a good signal.

| | Time | Space |
|---|---|---|
| Single query, iterative | `O(L(x))` | `O(1)` |
| Single query, recursive | `O(L(x))` | `O(L(x))` stack |
| Cached, `q` queries over `[lo, hi]` | `O(total distinct values ever visited)` | same, in the cache |

The point about the cached version: across many queries, each distinct value is computed
**exactly once**, so total work is proportional to the number of distinct values in the
union of all chains - not to the sum of the chain lengths. That is the whole win, and it is
the sentence to say.

Empirically, for `lo..hi` up to 10^4 the cache holds a few hundred thousand entries,
because chains overshoot well above `hi`. Mention that memory is the trade: you can bound
it by only caching values `<= hi`.

## How to present it

1. **Restate and confirm the count.** "For 3 you showed 7 arrows, so steps counts
   transitions, and steps(1) is 0." Getting this confirmed in ten seconds prevents an
   off-by-one later.
2. **Ask whether there will be many calls** before writing anything. If yes, go straight to
   the cached class and say why.
3. **Write the recurrence on the board** in three lines before coding. It is the whole
   solution and it fits in three lines.
4. **Write the iterative version first**, and volunteer the reason: "recursion is the
   natural shape here, but the chain depth is unbounded and Python's limit is 1000, so I
   will write it iteratively."
5. **Then extend to the cache**, narrating the two phases: walk forward collecting the
   path, unwind backwards assigning. Trace `x = 10` out loud and show the cache filling.
6. **Close** on complexity plus the honest statement that termination is unproven.

## Follow-ups and variations

- **"What are the drawbacks of the recursive solution? Convert it to iterative."** Stack
  depth is unbounded (Collatz overshoots hugely before descending), Python's default limit
  is 1000, and each frame costs memory. The iterative version is `O(1)` space. Note that
  `functools.lru_cache` on a recursive version has the *same* depth problem.
- **"Optimise for multiple calls."** Memoise. First instinct is `cache[x] = result`; say
  that, then immediately improve it to caching the whole path.
- **"Store every number reached during the calculation."** This is the exact ask reported:
  after `steps(10)` the cache should be `{10:6, 5:4, 16:7, 8:3, 4:2, 2:1, 1:0}`. The
  two-phase walk-then-unwind above produces precisely that. This is the crux of the
  question - practise typing it cold.
- **"Can you do it with `lru_cache` instead?"** Yes, on a recursive helper, and it is two
  lines - but it only caches values that appear as *arguments*, which with the natural
  recursion is in fact every value on the path. Show it, then note the recursion-depth
  caveat:
  ```python
  import functools, sys
  sys.setrecursionlimit(10**6)

  @functools.lru_cache(maxsize=None)
  def steps(x):
      return 0 if x == 1 else 1 + steps(x // 2 if x % 2 == 0 else 3 * x + 1)
  ```
- **"Bound the memory."** Only cache values `<= hi` (or under some ceiling); values above it
  are visited rarely and recomputing them is cheap.
- **"Sort a range by step count."** LC 1387, shown above. Then: "return the k-th" -
  introduce the size-k heap.
- **"Which number under N has the longest chain?"** Same cache, one pass, track the max.
  This is Project Euler 14 and is a natural extension.
- **"Is it guaranteed to terminate?"** No. The Collatz conjecture is open; it is verified by
  computer up to about 2^68. Say this plainly - inventing a proof is the wrong move.
- **"What if the rules change, e.g. 5x+1?"** Then it may genuinely cycle. The cached walk
  must detect a repeat on the current path (a value in `path` but not in `cache`) and
  handle it, otherwise it loops forever.

## Pitfalls

- **`x / 2` instead of `x // 2`.** Floats leak into the chain and the cache keys.
- **Caching only the queried value**, discarding the path. This is the single most common
  miss, and it is exactly what the third follow-up probes.
- **Recursing** when the interviewer has signalled they want iteration - one report says the
  interviewer explicitly forced it.
- **Unwinding in the wrong direction.** The path must be assigned from the end nearest 1
  backwards; assigning forwards gives every value the same number.
- **Forgetting to seed the cache with `{1: 0}`**, which makes the walk loop forever at 1.
- **Not handling `x = 1`** (answer 0) and `x < 1` (undefined).
- Claiming the complexity is `O(log x)`. It is not, and it is not known to be anything; say
  `O(chain length)`.
