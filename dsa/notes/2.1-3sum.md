**Link:** https://leetcode.com/problems/3sum
**Difficulty:** Medium | **LeetCode #15**
**Bloomberg frequency:** 75% in the **30-day** window, 50% at three months, 75% at six
months - consistently high across every window.

The canonical "sort then two-pointer" problem. The algorithm is straightforward; the
**deduplication** is what people get wrong, and it is what the interviewer watches.

## 1. Problem statement

Given an integer array `nums`, return all **unique** triples `[nums[i], nums[j], nums[k]]`
such that `i != j`, `i != k`, `j != k` and `nums[i] + nums[j] + nums[k] == 0`.

The solution set must not contain duplicate triples.

```
nums = [-1,0,1,2,-1,-4]  ->  [[-1,-1,2],[-1,0,1]]
nums = [0,1,1]           ->  []
nums = [0,0,0]           ->  [[0,0,0]]
```

## 2. Clarifying questions

1. **Unique by index or by value?** By **value** - `[-1,0,1,2,-1,-4]` contains two `-1`s and
   `[-1,0,1]` must appear only once. This is the opposite of Two Sum and of the reported
   Bloomberg counting variant (23.16), so **ask**.
2. **Return the values or the indices?** Values. That is what permits sorting.
3. **Does the order of the triples matter? Within a triple?** No to both, typically.
4. **Can I modify the input?** Sorting mutates it. Ask, or sort a copy.
5. **Is the target always zero?** In LC 15 yes; the generalisation to an arbitrary target is
   a one-line change and a likely follow-up.
6. **Array size?** Up to 3000 on LeetCode, so `O(n^2)` is fine and `O(n^3)` is not.

## 3. Intuition

Brute force is three nested loops, `O(n^3)`, plus a set to dedupe. State it and move on.

The reduction that makes it tractable:

> **Fix one element, and the rest is Two Sum.** For each `i`, look for two numbers in the
> remainder summing to `-nums[i]`.

If you do that with a hash map you get `O(n^2)` time and `O(n)` space, but deduplication is
awkward. If you **sort first**, you get `O(n^2)` time, `O(1)` extra space, *and*
deduplication becomes easy - because duplicates are now adjacent, so skipping them is a
local check.

That is the trade to state out loud: sorting costs `O(n log n)`, which is dominated by the
`O(n^2)` scan anyway, so it is free - and it buys both the two-pointer scan and cheap dedup.

### The deduplication rule

Three places need it, and they are not symmetric:

1. **The fixed element `i`**: skip if `nums[i] == nums[i-1]` - we already did every triple
   starting with that value. Note the guard `i > 0`, so index 0 is never skipped.
2. **After recording a triple**, advance `lo` past any equal values and `hi` back past any
   equal values. Crucially this happens **after** appending, not before - skipping first
   would lose the triple entirely.
3. There is no separate rule for `hi` alone; moving both pointers after a hit and then
   skipping duplicates on both sides covers it.

### Two early exits worth knowing

Because the array is sorted:
- If `nums[i] > 0`, every remaining element is positive, so no triple can sum to zero -
  `break` out entirely.
- If `nums[i] + nums[i+1] + nums[i+2] > 0`, the smallest possible triple with this `i`
  already overshoots - `break`.
- If `nums[i] + nums[n-2] + nums[n-1] < 0`, the largest possible triple with this `i`
  undershoots - `continue` to the next `i`.

The first is enough for an interview; mention the others as pruning.

## 4. Approach

1. Sort `nums`.
2. For `i` from `0` to `n-3`:
   - skip if `i > 0 and nums[i] == nums[i-1]`
   - break if `nums[i] > 0`
   - `lo, hi = i+1, n-1`
   - while `lo < hi`:
     - `total = nums[i] + nums[lo] + nums[hi]`
     - `total < 0` -> `lo += 1`
     - `total > 0` -> `hi -= 1`
     - else record, move both, then skip duplicates on both sides
3. Return the collected triples.

## 5. Solution

```python
def three_sum(nums):
    """All unique triples summing to zero.

    Sorting does three jobs: it enables the two-pointer scan, it makes duplicates
    adjacent so deduplication is a local check, and it allows the early break.
    """
    nums.sort()
    n = len(nums)
    result = []

    for i in range(n - 2):
        # Every triple starting with this value has already been generated.
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        # Sorted, so from here on everything is positive: no triple can reach zero.
        if nums[i] > 0:
            break

        lo, hi = i + 1, n - 1
        while lo < hi:
            total = nums[i] + nums[lo] + nums[hi]
            if total < 0:
                lo += 1                 # need a bigger sum
            elif total > 0:
                hi -= 1                 # need a smaller sum
            else:
                result.append([nums[i], nums[lo], nums[hi]])
                lo += 1
                hi -= 1
                # Skip duplicates only AFTER recording, or the triple is lost.
                while lo < hi and nums[lo] == nums[lo - 1]:
                    lo += 1
                while lo < hi and nums[hi] == nums[hi + 1]:
                    hi -= 1

    return result
```

```python
three_sum([-1, 0, 1, 2, -1, -4])        # [[-1, -1, 2], [-1, 0, 1]]
three_sum([0, 1, 1])                    # []
three_sum([0, 0, 0])                    # [[0, 0, 0]]
three_sum([0, 0, 0, 0])                 # [[0, 0, 0]]
three_sum([-2, 0, 1, 1, 2])             # [[-2, 0, 2], [-2, 1, 1]]
three_sum([])                           # []
three_sum([1, 2, 3])                    # []
three_sum([-4, -2, -2, -2, 0, 1, 2, 2, 2, 3, 3, 4, 4, 6, 6])
# [[-4, -2, 6], [-4, 0, 4], [-4, 1, 3], [-4, 2, 2], [-2, -2, 4], [-2, 0, 2]]
```

`[0,0,0,0]` is the case to say aloud: without the `i` dedup you would emit `[0,0,0]` twice.
And the long final example exercises duplicates on both pointers simultaneously.

### The hash-map alternative

```python
def three_sum_hashmap(nums):
    """O(n^2) time, O(n) space. Sorting is still needed for cheap deduplication,
    which is why the two-pointer version is preferred."""
    nums.sort()
    n = len(nums)
    result = []
    for i in range(n - 2):
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        seen = set()
        for j in range(i + 1, n):
            complement = -nums[i] - nums[j]
            if complement in seen:
                triple = [nums[i], complement, nums[j]]
                if not result or result[-1] != triple:
                    result.append(triple)
            seen.add(nums[j])
    return result


three_sum_hashmap([-1, 0, 1, 2, -1, -4])    # [[-1, 0, 1], [-1, -1, 2]]
three_sum_hashmap([0, 0, 0, 0])             # [[0, 0, 0]]
```

Same triples, but note they come out in a **different order** from the two-pointer version -
the set of answers is what matters, not the order, and it is worth saying so if you show
both.

Same complexity in time, worse in space, and the dedup is more delicate: `result[-1] !=
triple` only compares against the most recent triple, which happens to be sufficient here
because within a fixed `i` the sorted scan emits duplicates consecutively. Relying on that
is exactly the kind of subtlety you do not want under time pressure. Mention this version
exists; do not lead with it.

## 6. Complexity

| Approach | Time | Space |
|---|---|---|
| Brute force + set | `O(n^3)` | `O(n)` for the dedup set |
| Sort + hash map per `i` | `O(n^2)` | `O(n)` |
| **Sort + two pointers** | **`O(n^2)`** | **`O(1)`** extra (`O(log n)` for the sort's stack) |

The sort is `O(n log n)`, dominated by the `O(n^2)` double scan, so it does not appear in the
final bound. Space excludes the output, which can itself be `O(n^2)` in the worst case - say
so, because it means no algorithm can be better than `O(n^2)` on adversarial input.

**Can you do better than `O(n^2)`?** Not by any known general method; 3SUM is conjectured to
require `O(n^2)` (the "3SUM-hardness" conjecture). Saying this is a strong close.

## 7. How to present it

1. **Restate, and ask the dedup question immediately**: "The triples are unique by *value*,
   right? So with two `-1`s in the input, `[-1,0,1]` appears once." That distinction is the
   whole problem and asking it first shows you have read the examples.
2. **Brute force** in one sentence, `O(n^3)`.
3. **State the reduction**: "If I fix one element, the rest is Two Sum on the remainder."
4. **Justify sorting**, and give all three reasons: it enables two pointers, it makes
   duplicates adjacent, and it allows an early break. "It costs O(n log n) which is dominated
   by the O(n^2) scan, so it's effectively free."
5. **Announce** the loop structure before writing it.
6. **Write it**, and narrate the two dedup sites separately:
   - at `i`: "skip if it equals the previous, because those triples are already done";
   - after a hit: "**record first, then skip** - if I skipped first I'd lose the triple."
7. **Give the exchange argument** for the pointer moves: "if the total is too small, pairing
   `lo` with anything below `hi` is even smaller, so `lo` can be discarded."
8. **Trace `[-4,-1,-1,0,1,2]`** (the sorted first example) for `i = 0` and `i = 1`.
9. **Close**: `O(n^2)` time, `O(1)` extra space, output can be `O(n^2)`, and 3SUM is
   conjectured to be `O(n^2)`-hard.

## 8. Follow-ups and variations

- **"3Sum Closest"** (LC 16). Same scan, but track the triple whose sum is nearest the
  target; no dedup needed since only one answer is returned. Move the pointer that reduces
  the gap.
- **"3Sum Smaller"** (LC 259). Count triples with sum `< target`. When
  `nums[i]+nums[lo]+nums[hi] < target`, **all** `hi - lo` pairings with that `lo` qualify, so
  add `hi - lo` and advance `lo`. That counting shortcut is the insight.
- **"4Sum"** (LC 18, which is 2.8 here). Fix two elements, two-pointer the rest, `O(n^3)`.
  Dedup at both fixed positions.
- **"kSum in general."** Recurse: `kSum` fixes one element and calls `(k-1)Sum`, bottoming
  out at 2Sum. `O(n^(k-1))`.
- **"Arbitrary target instead of zero."** Replace `total` against `target`; the `nums[i] > 0`
  early break only holds for target zero, so guard it or drop it.
- **"Unique by index instead of by value."** Now it is a counting problem and the dedup
  logic inverts - you would count duplicate blocks combinatorially, as in 23.16.
- **"Count the triples rather than listing them."** Avoids the `O(n^2)` output, but the scan
  is still `O(n^2)`. Handle duplicate blocks with multiplication.
- **"What if the input can't be modified?"** Sort a copy, `O(n)` extra space.
- **"Find triples summing to zero in a stream."** You cannot, without buffering - the
  algorithm is inherently offline.
- **"Why sort at all - couldn't a hash map do it?"** It can, at `O(n)` space, but
  deduplication without sortedness requires a set of canonical triples, which is more memory
  and more code. Good question to be asked and to have an answer for.

## 9. Pitfalls

- **Skipping duplicates before recording the triple**, which drops valid answers.
- **Forgetting the `i > 0` guard** on the first dedup check, causing an `IndexError` or
  skipping index 0.
- **Deduping with a `set` of tuples** and calling it done. It works but is `O(n^2)` memory in
  the worst case, and it signals you did not see why sorting helps.
- **Using `lo <= hi`** instead of `lo < hi`, letting one element be used twice.
- **Moving only one pointer after recording a triple.** Both must move: keeping one fixed
  with the other advancing can only give a worse sum, so the next candidate needs both.
- **`range(n)` instead of `range(n - 2)`**, running the inner loop with fewer than two
  elements left.
- **Sorting when indices are required.** Ask first.
- **Forgetting that the output itself can be `O(n^2)`** and claiming `O(1)` total space.
- **Applying the `nums[i] > 0` break to a non-zero target**, which is simply wrong.
