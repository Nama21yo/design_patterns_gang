**Link:** https://leetcode.com/problems/search-in-rotated-sorted-array
**Difficulty:** Medium | **LeetCode #33**
**Bloomberg frequency:** 62% in the **30-day** window, 75% at three months, 62% at six
months - consistently high across every window.

Binary search where the array is **not** globally sorted. The insight is that **at least one
half of any split is still sorted**, and identifying which one lets you discard the other
half as usual.

## 1. Problem statement

There is an integer array `nums` sorted in ascending order with **distinct** values. It has
been **rotated** at some unknown pivot, so that the array becomes
`[nums[k], ..., nums[n-1], nums[0], ..., nums[k-1]]`.

Given the rotated array and a `target`, return the index of the target, or `-1`.

You must write an algorithm with `O(log n)` runtime.

```
nums = [4,5,6,7,0,1,2], target = 0  ->  4
nums = [4,5,6,7,0,1,2], target = 3  ->  -1
nums = [1],             target = 0  ->  -1
```

## 2. Clarifying questions

1. **Are the values distinct?** Yes in LC 33. **This matters enormously** - with duplicates
   (LC 81) the worst case degrades to `O(n)`. Ask, because the interviewer may be planning
   that follow-up.
2. **Is the rotation amount known?** No - that is the challenge.
3. **Can the rotation be zero?** Yes, so a plain sorted array is a valid input and must still
   work.
4. **Return the index or a boolean?** The index, or `-1`.
5. **Must it be `O(log n)`?** Stated, which rules out a linear scan and rules out "sort it
   first".
6. **Ascending before rotation?** Yes.

## 3. Intuition

### The key structural fact

Split the array at any `mid`. Because the original array was sorted and rotated once, the
pivot lies in exactly one half - so:

> **At least one of `[lo..mid]` and `[mid..hi]` is entirely sorted.**

You can tell which by a single comparison:

```
if nums[lo] <= nums[mid]:   the LEFT half is sorted
else:                       the RIGHT half is sorted
```

(`<=` rather than `<` handles the two-element case where `lo == mid`.)

### The decision

Once you know which half is sorted, you can test **exactly** whether the target lies inside
it, because a sorted range is fully described by its endpoints:

- **Left half sorted** (`nums[lo] <= nums[mid]`):
  if `nums[lo] <= target < nums[mid]`, the target must be in the left half -> `hi = mid - 1`.
  Otherwise -> `lo = mid + 1`.
- **Right half sorted**:
  if `nums[mid] < target <= nums[hi]`, go right -> `lo = mid + 1`.
  Otherwise -> `hi = mid - 1`.

Each step halves the range, so it is `O(log n)`.

The thing to be careful about is **which comparisons are strict**. The target-equals-`mid`
case is handled by an early return, so the range tests exclude `nums[mid]` on both sides.
Getting one boundary wrong produces a solution that works on most inputs and fails on a
specific rotation, which is the worst kind of bug.

### Why the naive alternatives are worse

- **Find the pivot first, then binary search the right segment.** Perfectly valid, two
  `O(log n)` searches, and arguably easier to reason about. Offer it as an alternative - some
  interviewers prefer it.
- **Scan linearly.** `O(n)`, forbidden.
- **Sort and search.** `O(n log n)` and destroys the indices.

## 4. Approach

1. `lo, hi = 0, n - 1`.
2. While `lo <= hi`:
   - `mid = (lo + hi) // 2`; if `nums[mid] == target`, return `mid`.
   - If `nums[lo] <= nums[mid]`: left half sorted.
     - if `nums[lo] <= target < nums[mid]`: `hi = mid - 1` else `lo = mid + 1`.
   - Else: right half sorted.
     - if `nums[mid] < target <= nums[hi]`: `lo = mid + 1` else `hi = mid - 1`.
3. Return `-1`.

This problem uses the **inclusive** `lo <= hi` template, because there is a genuine "found"
case with an early return.

## 5. Solution

```python
def search(nums, target):
    """Index of target in a rotated sorted array of distinct values, or -1.

    Splitting anywhere leaves at least one half fully sorted, because the single
    rotation point can only be in one of them. Comparing nums[lo] with nums[mid]
    identifies the sorted half; its endpoints then decide exactly whether the target
    lies inside it.
    """
    lo, hi = 0, len(nums) - 1

    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid

        # '<=' not '<': when lo == mid (a two-element range) the left half is
        # trivially sorted and must be treated as such.
        if nums[lo] <= nums[mid]:
            # Left half [lo..mid] is sorted; its endpoints fully describe it.
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:
            # Right half [mid..hi] is sorted.
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1

    return -1
```

```python
search([4, 5, 6, 7, 0, 1, 2], 0)    # 4
search([4, 5, 6, 7, 0, 1, 2], 3)    # -1
search([1], 0)                      # -1
search([1], 1)                      # 0
search([], 1)                       # -1
search([3, 1], 1)                   # 1
search([5, 1, 3], 3)                # 2
search([4, 5, 6, 7, 0, 1, 2], 4)    # 0
search([4, 5, 6, 7, 0, 1, 2], 2)    # 6
search([1, 2, 3, 4, 5], 4)          # 3
search([1, 3], 3)                   # 1
search([3, 5, 1], 3)                # 0
```

The cases to run out loud:

- **`[3,1]` with target 1 -> 1** and **`[1,3]` with target 3 -> 1.** Two-element arrays in
  both rotations. These are what the `<=` in `nums[lo] <= nums[mid]` exists for, and they
  are the classic failure.
- **`[1,2,3,4,5]` -> works unchanged.** Rotation of zero must still function.
- **`[4,5,6,7,0,1,2]` with targets 4 and 2** - the first and last elements, exercising both
  ends of both halves.

### The find-the-pivot alternative

```python
def find_rotation_index(nums):
    """Index of the smallest element - the rotation point. O(log n), distinct values."""
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        # If nums[mid] > nums[hi], the minimum must be strictly right of mid.
        if nums[mid] > nums[hi]:
            lo = mid + 1
        else:
            hi = mid
    return lo


def search_via_pivot(nums, target):
    """Locate the rotation point, then binary search the segment that can contain
    the target. Two O(log n) searches - easier to reason about, same complexity."""
    if not nums:
        return -1

    pivot = find_rotation_index(nums)

    def plain_search(lo, hi):
        while lo <= hi:
            mid = (lo + hi) // 2
            if nums[mid] == target:
                return mid
            if nums[mid] < target:
                lo = mid + 1
            else:
                hi = mid - 1
        return -1

    # The target is in the left segment if it is at least the first element.
    if pivot == 0 or target >= nums[0]:
        return plain_search(0, pivot - 1 if pivot > 0 else len(nums) - 1)
    return plain_search(pivot, len(nums) - 1)


search_via_pivot([4, 5, 6, 7, 0, 1, 2], 0)      # 4
search_via_pivot([4, 5, 6, 7, 0, 1, 2], 3)      # -1
search_via_pivot([4, 5, 6, 7, 0, 1, 2], 4)      # 0
search_via_pivot([1, 2, 3, 4, 5], 4)            # 3
search_via_pivot([3, 1], 1)                     # 1
search_via_pivot([1], 1)                        # 0
search_via_pivot([], 1)                         # -1
```

Two clean searches instead of one search with four branches. If the one-pass version's
boundary conditions feel risky under pressure, **write this instead** - it is the same
complexity and much easier to defend.

### With duplicates (LC 81)

```python
def search_with_duplicates(nums, target):
    """LC 81: values may repeat, so return a boolean and accept O(n) worst case.

    When nums[lo] == nums[mid] == nums[hi] neither half can be identified as sorted,
    and the only safe move is to shrink the range by one - which is why an array like
    [1,1,1,1,1,0,1] costs O(n).
    """
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return True

        if nums[lo] == nums[mid] == nums[hi]:
            lo += 1                 # no information: give up one element
            hi -= 1
        elif nums[lo] <= nums[mid]:
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1

    return False


search_with_duplicates([2, 5, 6, 0, 0, 1, 2], 0)    # True
search_with_duplicates([2, 5, 6, 0, 0, 1, 2], 3)    # False
search_with_duplicates([1, 1, 1, 1, 1, 0, 1], 0)    # True
search_with_duplicates([1, 0, 1, 1, 1], 0)          # True
search_with_duplicates([1, 1], 2)                   # False
```

**Be able to explain the degradation.** With `[1,1,1,1,1,0,1]`, the three probe points are
all `1`, so you cannot tell which side holds the rotation - and skipping one element per
iteration is the only sound response. Worst case `O(n)`; average still close to `O(log n)`.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(n)` | `O(1)` |
| **One-pass rotated search** | **`O(log n)`** | **`O(1)`** |
| Find pivot + plain search | `O(log n)` | `O(1)` |
| With duplicates (LC 81) | `O(log n)` average, **`O(n)` worst** | `O(1)` |

Each iteration halves the range in the distinct-values case, so `O(log n)`. Iterative, so
constant space.

## 7. How to present it

1. **Restate**, and **confirm the values are distinct.** Then say why you asked: *"with
   duplicates the worst case becomes linear, so I want to know which problem this is."* That
   single question signals you know the family.
2. **State the structural fact**: *"Wherever I split, one half is still fully sorted, because
   there is only one rotation point and it can only be on one side."* Draw
   `[4,5,6,7,0,1,2]` and split it to show this.
3. **Say how you identify the sorted half**: compare `nums[lo]` with `nums[mid]`.
4. **Say why that helps**: *"a sorted range is fully described by its endpoints, so I can
   test exactly whether the target is inside it - and if it isn't, it must be in the other
   half."*
5. **Announce**, then write it. Call out the `<=` in `nums[lo] <= nums[mid]` as you type it,
   and why: the two-element case where `lo == mid`.
6. **Trace `[4,5,6,7,0,1,2]` with target 0**: `mid = 3` (value 7), left half `[4..7]` is
   sorted, 0 is not in `[4,7)`, so go right.
7. **Test the two-element rotations** `[3,1]` and `[1,3]`, and the un-rotated array.
8. **Offer the pivot-first alternative** as the version with simpler boundaries.
9. **Close**: `O(log n)` time, `O(1)` space - and volunteer the duplicates degradation with
   `[1,1,1,1,1,0,1]` as the witness.

## 8. Follow-ups and variations

- **"What if there are duplicates?"** LC 81. Shown above, with the `O(n)` worst case and the
  reason for it. **This is the most likely follow-up.**
- **"Find the minimum in a rotated sorted array"** (LC 153, at 5.17). `find_rotation_index`
  above is exactly that.
- **"Find the minimum with duplicates"** (LC 154). Same degradation to `O(n)`.
- **"How many times was the array rotated?"** The index of the minimum - the same function.
- **"Check whether an array is a rotated sorted array"** (LC 1752, at 1.8). Counting
  descents circularly; **not** binary searchable, and knowing why is the contrast worth
  drawing.
- **"What if it was rotated more than once?"** Rotating twice is still a single rotation by
  the combined amount, so nothing changes. A nice observation to offer.
- **"What if it was sorted descending before rotation?"** Mirror all the comparisons, or
  negate the values and reuse.
- **"Search in a rotated 2D matrix."** Flatten conceptually and apply the same idea, if the
  matrix is row-major sorted.

## 9. Pitfalls

- **Using `<` instead of `<=`** in `nums[lo] <= nums[mid]`, which misclassifies two-element
  ranges where `lo == mid`. `[3,1]` and `[1,3]` are the tests. **The defining bug.**
- **Getting the strictness wrong** in the range tests - `nums[lo] <= target < nums[mid]` has
  one inclusive and one exclusive bound, and the `mid` case is already handled by the early
  return.
- **Comparing `nums[mid]` with `nums[hi]`** to identify the sorted half while using
  `lo`-based range tests. Both conventions work, but mixing them is subtly wrong.
- **Using the exclusive `while lo < hi` template** here. This problem has a genuine early
  return on `nums[mid] == target`, so the inclusive form is the natural fit.
- **Assuming `O(log n)` with duplicates.**
- **Forgetting the empty array.**
- **Sorting the array first** - destroys the indices and is `O(n log n)`.
- **Finding the pivot with an off-by-one**, so the two segments overlap or leave a gap.
