**Bloomberg frequency:** 62% in the **30-day** window.

Expression parsing with a stack - the arithmetic cousin of 4.6 Decode String. The version
with `+`, `-` and parentheses has a surprisingly clean solution built on **one idea: carry a
running sign**. The version with `*` and `/` needs a different trick. Know both, and know
which problem you have been handed.

## 1. Problem statement

Given a string `s` representing a valid expression, implement a basic calculator to evaluate
it and return the result.

The expression contains digits, `'+'`, `'-'`, `'('`, `')'` and spaces. **No multiplication or
division** in LC 224; unary minus **is** allowed.

You may **not** use any built-in function that evaluates strings as expressions (no `eval`).

```
s = "1 + 1"                 ->  2
s = " 2-1 + 2 "             ->  3
s = "(1+(4+5+2)-3)+(6+8)"   ->  23
```

## 2. Clarifying questions

1. **Which operators?** LC 224 is `+`, `-` and parentheses only. **LC 227** adds `*` and `/`
   with no parentheses, and **LC 772** has everything. **Ask which**, because the three have
   genuinely different solutions and starting the wrong one wastes the round.
2. **Is unary minus allowed?** Yes - `"-2 + 1"` and `"-(3+4)"` are both valid. This is the
   main edge case.
3. **Can numbers be multi-digit?** Yes. Accumulate `num = num * 10 + digit`.
4. **Are there spaces anywhere?** Yes, and they must be skipped, including inside numbers'
   surroundings.
5. **Is the expression guaranteed valid?** Yes - no unmatched parentheses, no malformed
   numbers.
6. **Integer division semantics, if `/` is involved?** Truncation **towards zero**, not
   Python's floor. `-7 // 2` is `-4` in Python but the expected answer is `-3`. Ask.

## 3. Intuition

### The running-sign idea (LC 224: `+`, `-`, parentheses)

The naive plan is to build a parse tree, or to recurse on parentheses. Both work. But there
is a much simpler framing:

> **Keep a running `result` and a current `sign` (+1 or -1). Every number is added as
> `sign * num`. Parentheses only change what the sign should be *outside* the bracket.**

Because there is no `*` or `/`, there is **no precedence to worry about** - the expression is
just a sum of signed terms, some of which are parenthesised sub-sums. So:

| token | action |
|---|---|
| digit | `num = num * 10 + int(ch)` |
| `+` | `result += sign * num`; `num = 0`; `sign = 1` |
| `-` | `result += sign * num`; `num = 0`; `sign = -1` |
| `(` | push `result` and `sign`; reset `result = 0`, `sign = 1` |
| `)` | `result += sign * num`; `num = 0`; `result = result * saved_sign + saved_result` |
| space | skip |

At the end, add the last pending `sign * num`.

The `(` case is the same "push the context you will restore" idea as 4.6: the bracket starts
a fresh sub-expression, and on `)` the finished sub-total is multiplied by the sign that
preceded the bracket and folded into the outer result.

**Unary minus falls out for free.** `"-2+1"` starts with `sign = 1` and `num = 0`; the `-`
adds `1 * 0` (nothing), sets `sign = -1`, and then `2` is added as `-2`. Likewise `"-(3+4)"`
sets `sign = -1` before the `(`, which is pushed and applied on `)`. No special case needed -
point that out, because most people expect to need one.

### The precedence idea (LC 227: `*` and `/`, no parentheses)

Different problem, different trick:

> **Keep a stack of terms. On `+`/`-`, push the signed number. On `*`/`/`, pop the last term,
> combine, and push the result. The answer is the sum of the stack.**

Multiplication and division bind tighter, so they modify the **most recent term** rather than
starting a new one. Summing the stack at the end applies the additions.

### Combining them (LC 772)

Both ideas at once: the stack-of-terms handles precedence, and recursion (or a second stack)
handles parentheses. Mention that it exists; write it only if asked.

## 4. Approach (LC 224)

1. `result = 0`, `num = 0`, `sign = 1`, `stack = []`.
2. Scan characters, applying the table above.
3. Return `result + sign * num`.

## 5. Solution

```python
def calculate(s):
    """Evaluate an expression with +, -, parentheses and spaces. No * or /.

    With no precedence to resolve, the expression is a sum of signed terms. `sign`
    carries the sign of the term being built; parentheses push the outer context
    (running result and the sign in front of the bracket) and restore it on ')'.
    """
    result = 0
    num = 0
    sign = 1
    stack = []                      # (result so far, sign in front of this bracket)

    for ch in s:
        if ch.isdigit():
            num = num * 10 + int(ch)        # multi-digit accumulation
        elif ch in "+-":
            result += sign * num            # close off the pending term
            num = 0
            sign = 1 if ch == "+" else -1
        elif ch == "(":
            # Start a fresh sub-expression; remember how to fold it back in.
            stack.append((result, sign))
            result, sign = 0, 1
        elif ch == ")":
            result += sign * num            # close the last term inside the bracket
            num = 0
            prev_result, prev_sign = stack.pop()
            result = prev_result + prev_sign * result
        # spaces and anything else are skipped

    return result + sign * num              # the final pending term
```

```python
calculate("1 + 1")                  # 2
calculate(" 2-1 + 2 ")              # 3
calculate("(1+(4+5+2)-3)+(6+8)")    # 23
calculate("1")                      # 1
calculate("-2+1")                   # -1
calculate("2-(5-6)")                # 3
calculate("-(3+4)")                 # -7
calculate("10-(2+3)")               # 5
calculate("100")                    # 100
calculate("- (3 + (4 + 5))")        # -12
calculate("2-4-(8+2-6+(8+4-(1)+8-10))")     # -15
calculate("1-(-2)")                 # 3
```

The ones to say out loud:

- **`"-2+1"` -> -1** and **`"-(3+4)"` -> -7**: unary minus, handled with no special case
  because `num` is 0 at that point.
- **`"1-(-2)"` -> 3**: a unary minus *inside* a bracket, which works for the same reason.
- **`"2-4-(8+2-6+(8+4-(1)+8-10))"` -> -15**: deep nesting with mixed signs, and the case to
  run if you want a single convincing test.

### LC 227 - with `*` and `/`, no parentheses

```python
def calculate_ii(s):
    """Evaluate with +, -, *, / and no parentheses. Integer division truncates
    towards zero, which is NOT Python's // for negative values.

    A stack of terms: * and / modify the most recent term because they bind tighter;
    + and - start a new one. The answer is the sum of the stack.
    """
    stack = []
    num = 0
    op = "+"                        # the operator preceding the current number

    for i, ch in enumerate(s):
        if ch.isdigit():
            num = num * 10 + int(ch)
        if (not ch.isdigit() and ch != " ") or i == len(s) - 1:
            if op == "+":
                stack.append(num)
            elif op == "-":
                stack.append(-num)
            elif op == "*":
                stack.append(stack.pop() * num)
            else:
                prev = stack.pop()
                # Truncate towards zero: int() on the float-free quotient.
                stack.append(int(prev / num))
            num = 0
            op = ch

    return sum(stack)


calculate_ii("3+2*2")               # 7
calculate_ii(" 3/2 ")               # 1
calculate_ii(" 3+5 / 2 ")           # 5
calculate_ii("1")                   # 1
calculate_ii("14-3/2")              # 13
calculate_ii("2*3*4")               # 24
calculate_ii("0-2147483647")        # -2147483647
```

Two details worth calling out:

- **`int(prev / num)` rather than `prev // num`.** For `-7 / 2`, Python's `//` floors to
  `-4`, but the expected truncation-towards-zero answer is `-3`. This is a real and very
  commonly missed bug. (`int(prev / num)` uses float division, which is exact for the
  magnitudes in these problems; `-(-prev // num)` style tricks or `math.trunc` are alternatives
  if float precision is a concern.)
- **The `i == len(s) - 1` clause** flushes the last number, since there is no trailing
  operator to trigger it.

### The recursive version of LC 224

Some find this clearer, and it makes the parallel with 4.6 explicit:

```python
def calculate_recursive(s):
    """Same problem, recursive descent. Each '(' recurses; each ')' returns."""
    def helper(i):
        """Evaluate from index i until ')' or the end. Returns (value, next index)."""
        result, num, sign = 0, 0, 1
        while i < len(s):
            ch = s[i]
            if ch.isdigit():
                num = num * 10 + int(ch)
            elif ch in "+-":
                result += sign * num
                num = 0
                sign = 1 if ch == "+" else -1
            elif ch == "(":
                num, i = helper(i + 1)      # the bracket's value becomes the term
            elif ch == ")":
                return result + sign * num, i
            i += 1
        return result + sign * num, i

    return helper(0)[0]


calculate_recursive("(1+(4+5+2)-3)+(6+8)")      # 23
calculate_recursive("-(3+4)")                   # -7
calculate_recursive("2-(5-6)")                  # 3
calculate_recursive("1-(-2)")                   # 3
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| **LC 224, iterative** | **`O(n)`** | `O(depth)` for the stack |
| LC 224, recursive | `O(n)` | `O(depth)` call stack |
| LC 227 | `O(n)` | `O(terms)` |

One pass over the string; each character is handled in `O(1)`. Space is the nesting depth,
which is `O(n)` in the worst case (`"((((((1))))))"`).

## 7. How to present it

1. **Ask which variant it is** - `+`/`-`/parentheses, or `*`/`/`, or both. This is the single
   most important question here, and the three have different solutions.
2. **Confirm unary minus and multi-digit numbers.**
3. **State the key simplification** for LC 224: *"With no multiplication or division there's
   no precedence - the expression is just a sum of signed terms. So I'll carry a running sign
   and add each number as `sign * num`."* That sentence is the insight.
4. **Say what parentheses do**: *"a bracket starts a fresh sub-expression, so I push the
   running result and the sign in front of the bracket, and fold the sub-total back in on
   the closing bracket."* Same shape as Decode String.
5. **Write the token table** before coding. Five rows, and it makes the code mechanical.
6. **Write it**, and **volunteer that unary minus needs no special case** - explain why
   (`num` is 0 at that moment).
7. **Test** `"-2+1"`, `"1-(-2)"`, and the deeply nested example.
8. **Close**: `O(n)` time, `O(depth)` space - and offer the `*`/`/` variant with the
   stack-of-terms idea and the truncation-towards-zero warning.

## 8. Follow-ups and variations

- **"Now add `*` and `/`"** (LC 227). The stack-of-terms solution. **Flag the integer
  division semantics** - truncate towards zero, not floor.
- **"Now add parentheses as well"** (LC 772). Combine: recursion for brackets, stack of terms
  for precedence. Describe it rather than writing it unless asked.
- **"Support unary minus explicitly."** Already handled; explain why.
- **"Support floating point."** Change the number accumulation and drop the integer-division
  special case.
- **"Support `^` or right-associative operators."** Now precedence and associativity need a
  general framework - name the **shunting-yard algorithm** and precedence-climbing. That is
  the grown-up answer and naming it is worth real credit.
- **"Evaluate reverse Polish notation"** (LC 150). Much easier - a single stack, no
  precedence, no parentheses. Worth contrasting: RPN exists precisely to remove the problems
  this question is about.
- **"Convert infix to postfix."** Shunting-yard again.
- **"What if the input might be invalid?"** Now you need error handling: unmatched brackets
  (stack empty on `)`, non-empty at the end), operator with no operand, division by zero.
- **"Basic Calculator IV"** (LC 770) - symbolic evaluation with variables. Much harder; name
  it only.

## 9. Pitfalls

- **Starting the wrong variant.** Ask first.
- **Parsing digits one at a time**, breaking multi-digit numbers.
- **Forgetting the final `result + sign * num`**, dropping the last term. `"1"` returns 0.
- **Mishandling unary minus** by adding a special case that then double-counts. It needs
  none.
- **Not resetting `num = 0`** after closing a term, so it is added twice.
- **On `)`, forgetting to close the pending term** before folding into the outer result.
- **Using `//` for integer division** in LC 227. `int(a / b)` truncates towards zero;
  `//` floors. `"14-3/2"` and any negative dividend are the tests.
- **Using `eval`.** Explicitly forbidden.
- **Not skipping spaces**, which corrupts number accumulation.
- **Pushing only the result and not the sign** at `(`, so `"2-(5-6)"` comes out wrong.
