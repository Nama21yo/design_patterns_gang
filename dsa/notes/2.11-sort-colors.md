title: "2.11 Sort Colors"
---

**Link:** https://leetcode.com/problems/sort-colors
**Difficulty:** Medium | **LeetCode #75**
**Bloomberg frequency:** 62% at three months.

The **Dutch national flag** partition, invented by Dijkstra. The one-pass version has a
single asymmetric line that everyone gets wrong the first time, and explaining that line
correctly is the whole interview.

## 1. Problem statement

Given an array `nums` with `n` objects coloured red, white or blue - represented by the
integers `0`, `1` and `2` - sort them **in place** so that objects of the same colour are
adjacent, in the order red, white, blue.

You must **not** use the library's sort function.

Follow-up: can you do it in **one pass** with **O(1)** extra space?

```
nums = [2,0,2,1,1,0]  ->  [0,0,1,1,2,2]
nums = [2,0,1]        ->  [0,1,2]
```

## 2. Clarifying questions

1. **Only three distinct values?** Yes - `0`, `1`, `2`. That is what makes a linear solution
   possible; with arbitrary values you would be back to comparison sorting.
2. **In place?** Yes, `O(1)` extra space.
3. **One pass, or are two acceptable?** Two passes (counting sort) is the easy answer and is
   often accepted; one pass is the stated follow-up. **Ask which they want** - if they want
   one pass, go straight there.
4. **Are the objects just integers, or records with a colour field?** If records, counting
   sort's "overwrite by count" trick is invalid because you would destroy the payload, and
   only the swapping version works. Worth asking - it is a genuinely good question.
5. **Must it be stable?** The swapping version is **not** stable. For plain integers that is
   invisible; for records it matters.
6. **Can the array be empty?** Should work without a special case.

## 3. Intuition

### The easy two-pass answer

Count how many 0s, 1s and 2s there are, then overwrite the array with that many of each.
`O(n)` time, `O(1)` space, two passes. Say this first - it is correct and it takes twenty
seconds.

Its weakness, worth naming: it **overwrites** rather than moves, so it only works when the
elements carry no data beyond their colour.

### The one-pass answer

Maintain three regions with three pointers, and an invariant:

```
[ 0 0 0 | 1 1 1 | ? ? ? ? | 2 2 2 ]
         ^       ^        ^
        low     mid      high
```

> - everything **before `low`** is `0`
> - everything from `low` to `mid - 1` is `1`
> - everything from `mid` to `high` is **unexamined**
> - everything **after `high`** is `2`

Process `nums[mid]`:

- **`0`** - swap it with `nums[low]`. The value coming back from `low` is necessarily a `1`
  (it came from the middle region), so it is already correctly placed at `mid`. Advance
  **both** `low` and `mid`.
- **`1`** - already in the right region. Advance `mid` only.
- **`2`** - swap it with `nums[high]` and decrement `high`. **Do not advance `mid`**, because
  the value pulled in from `high` comes from the *unexamined* region and has not been
  classified yet.

The loop runs while `mid <= high`.

**That last asymmetry is the entire question.** Being able to say *why* `mid` advances in the
`0` case but not the `2` case - because the value swapped in from `low` is known to be a `1`,
whereas the value swapped in from `high` is unknown - is what an interviewer is listening
for.

## 4. Approach

1. `low, mid, high = 0, 0, n - 1`.
2. While `mid <= high`:
   - `nums[mid] == 0`: swap `low`/`mid`; `low += 1`; `mid += 1`
   - `nums[mid] == 1`: `mid += 1`
   - `nums[mid] == 2`: swap `mid`/`high`; `high -= 1`
3. Done.

## 5. Solution

```python
def sort_colors(nums):
    """Dutch national flag partition: sort 0s, 1s and 2s in one pass, in place.

    Invariant:
        nums[0:low]        all 0
        nums[low:mid]      all 1
        nums[mid:high+1]   unexamined
        nums[high+1:]      all 2
    """
    low, mid, high = 0, 0, len(nums) - 1

    while mid <= high:
        if nums[mid] == 0:
            # The value coming back from `low` is necessarily a 1 (it came from the
            # middle region), so it is already correct at mid - safe to advance both.
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1
            mid += 1
        elif nums[mid] == 1:
            mid += 1
        else:
            # The value pulled in from `high` is UNEXAMINED, so mid must not advance.
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1

    return nums
```

```python
sort_colors([2, 0, 2, 1, 1, 0])     # [0, 0, 1, 1, 2, 2]
sort_colors([2, 0, 1])              # [0, 1, 2]
sort_colors([0])                    # [0]
sort_colors([2, 2, 2])              # [2, 2, 2]
sort_colors([0, 0, 0])              # [0, 0, 0]
sort_colors([1, 1, 1])              # [1, 1, 1]
sort_colors([2, 1, 0])              # [0, 1, 2]
sort_colors([])                     # []
sort_colors([1, 2, 0, 2, 1, 0, 1])  # [0, 0, 1, 1, 1, 2, 2]
```

Trace `[2,0,1]` to show the trap:

| step | array | low | mid | high | action |
|---|---|---|---|---|---|
| start | `[2,0,1]` | 0 | 0 | 2 | `nums[0]` is 2: swap with index 2, `high` -> 1. **`mid` stays 0.** |
| | `[1,0,2]` | 0 | 0 | 1 | `nums[0]` is 1: advance `mid`. |
| | `[1,0,2]` | 0 | 1 | 1 | `nums[1]` is 0: swap with `low`, both advance. |
| | `[0,1,2]` | 1 | 2 | 1 | `mid > high`, stop. |

Had `mid` advanced on the first step, the `1` swapped in from the end would never have been
examined and the result would be wrong. **Walk this trace in the interview** - it is three
steps and it proves you understand the line.

### The two-pass counting version

```python
def sort_colors_counting(nums):
    """Two passes: count, then overwrite. Simpler, but it destroys the objects -
    only valid when the elements carry no data beyond their colour."""
    counts = [0, 0, 0]
    for x in nums:
        counts[x] += 1

    i = 0
    for colour in range(3):
        for _ in range(counts[colour]):
            nums[i] = colour
            i += 1
    return nums


sort_colors_counting([2, 0, 2, 1, 1, 0])    # [0, 0, 1, 1, 2, 2]
sort_colors_counting([2, 0, 1])             # [0, 1, 2]
sort_colors_counting([])                    # []
```

## 6. Complexity

| | Time | Passes | Space | Stable |
|---|---|---|---|---|
| Library sort | `O(n log n)` | - | `O(n)` | yes - but disallowed |
| Counting sort | `O(n)` | 2 | `O(1)` | n/a (overwrites) |
| **Dutch national flag** | **`O(n)`** | **1** | **`O(1)`** | no |

In the one-pass version, each iteration either advances `mid` or decrements `high`, and the
gap between them shrinks by at least one every time - so the loop runs at most `n` times.
That is the termination argument, and it is worth stating because the `2` branch does not
advance `mid` and can otherwise look like it might loop.

## 7. How to present it

1. **Restate**, confirm only three values, and **ask whether one pass is required**.
2. **Give the counting-sort answer immediately** - it is `O(n)`, `O(1)`, two passes, and it
   takes twenty seconds. Then name its limitation: it overwrites, so it fails for records.
3. **Introduce the one-pass version by its invariant**, drawing the four regions on the
   board. Do this *before* any code - the code is meaningless without the picture.
4. **Walk the three cases**, and spend your time on the `2` case: *"the value I pull in from
   `high` hasn't been looked at yet, so `mid` must not advance. In the `0` case the value
   coming back from `low` is guaranteed to be a `1`, so it is fine to advance."*
5. **Write it.**
6. **Trace `[2,0,1]`** using the table above - it is exactly three steps and it demonstrates
   the trap.
7. **Give the termination argument**: the `mid`-to-`high` gap shrinks every iteration.
8. **Close**: `O(n)`, one pass, `O(1)` space, not stable - and mention that a stable version
   needs `O(n)` extra space.

## 8. Follow-ups and variations

- **"One pass and O(1) space."** The stated follow-up - the DNF partition.
- **"What if there are `k` colours instead of 3?"** DNF does not generalise to a single pass.
  Use counting sort with a `k`-element histogram (`O(n + k)`, two passes), or a full sort if
  the values are unbounded. Say this - recognising that the trick is specific to three
  values is a real insight.
- **"What if the elements are objects with a colour field?"** Counting sort is out, because
  you cannot fabricate the objects. DNF still works, since it only swaps. This is the best
  reason to know both.
- **"Make it stable."** Not possible in `O(1)` space with swapping. Use a stable counting
  sort into an auxiliary array, `O(n)` space.
- **"Partition around a pivot"** - the same three-way split (`< pivot`, `== pivot`,
  `> pivot`) is the heart of **3-way quicksort**, which is what makes quicksort fast on
  arrays with many duplicates. Naming that connection is worth real credit.
- **"Sort an array of 0s and 1s only."** Two pointers from the ends, or simple compaction -
  and note DNF degenerates to it.
- **"Move all negatives before all positives."** Same partition with a predicate instead of
  a value.
- **"Wiggle sort", "sort by parity"**, and similar - all partition variants.

## 9. Pitfalls

- **Advancing `mid` in the `2` branch.** The defining bug. `[2,0,1]` catches it.
- **`while mid < high`** instead of `mid <= high`, leaving the final element unprocessed.
- **Advancing only `mid` (not `low`) in the `0` branch**, which breaks the invariant that
  `nums[low:mid]` is all 1s.
- **Using the library sort** when it is explicitly forbidden.
- **Two-pass counting when they asked for one pass** - correct but it does not answer the
  follow-up. Ask first.
- **Claiming the one-pass version is stable.** It is not.
- **Forgetting to justify termination**, leaving the interviewer to wonder whether the `2`
  branch can loop forever.
- **Hard-coding three colours in a solution presented as general.** Be explicit that DNF is
  specifically a three-way partition.
