*A contiguous window that grows on the right and shrinks on the left while a condition holds.*

61 Bloomberg-tagged questions, and one of them - Longest Substring Without Repeating
Characters - was reported from real Bloomberg rounds **twice**. This is a high-yield Part.

Sliding window is a specialisation of the same-direction two-pointer shape from Part 2. What
makes it its own pattern is that the window carries **state** (a count, a sum, a frequency
map) which is updated **incrementally** rather than recomputed.

## The core idea

A brute force over all subarrays is `O(n^2)` or `O(n^3)`. The window earns its linearity from
one observation:

> **When the window moves by one position, its contents change by one element at each end.
> So the state can be updated in `O(1)` instead of recomputed in `O(k)`.**

And the reason it is `O(n)` overall rather than `O(n^2)`, despite the nested loop:

> **`left` only ever moves forward. Across the entire run it advances at most `n` times, so
> the inner `while` does `O(n)` total work, not `O(n)` per iteration.**

Memorise that sentence. You will need it on every variable-window question, because the
nested `while` always *looks* quadratic.

## The precondition - when a window is valid at all

This is the most important thing in this primer, and it is what 1.2 Subarray Sum Equals K
exists to teach.

A sliding window works when the quantity you are tracking is **monotonic in the window
size**: growing the window can only push you further from (or no closer to) satisfying the
constraint, and shrinking can only help.

- **Sums with non-negative values**: valid. Growing increases the sum, shrinking decreases it.
- **Sums with negative values**: **invalid.** Growing can *decrease* the sum, so "I overshot,
  therefore shrink" is unsound. Use prefix sums plus a hash map (Part 1).
- **Distinct-character counts**: valid. Growing can only add distinct characters, shrinking
  can only remove them.
- **Product with values below 1, or with zeros**: needs care.

**Ask about negatives** whenever a window over sums is on the table. Recognising that the
window does *not* apply is worth as much as applying it.

## The two shapes

### Fixed-size window

The size `k` is given. Slide it along, adding the entering element and removing the leaving
one.

```python
def max_sum_fixed(nums, k):
    """Maximum sum of any k consecutive elements."""
    if len(nums) < k:
        return None
    window = sum(nums[:k])          # build the first window explicitly
    best = window
    for right in range(k, len(nums)):
        window += nums[right] - nums[right - k]     # add entering, remove leaving
        best = max(best, window)
    return best


max_sum_fixed([1, 12, -5, -6, 50, 3], 4)        # 51
max_sum_fixed([2, 3], 3)                        # None
```

The one line `window += nums[right] - nums[right - k]` is the whole pattern. Note it works
fine with negatives, because the window size is fixed - there is no shrink decision to make.

### Variable-size window

The size is whatever the constraint allows. This is the common case.

```python
# fragment
def longest_valid(nums):
    """Skeleton: grow right always; shrink left only while the window is invalid."""
    left = 0
    best = 0
    state = {}                      # whatever describes the window
    for right, x in enumerate(nums):
        # 1. ADD x to the state
        while INVALID(state):       # noqa - skeleton
            # 2. REMOVE nums[left] from the state
            left += 1
        # 3. RECORD, now that the window is valid
        best = max(best, right - left + 1)
    return best
```

**Grow, violate, contract, record.** Every variable-window solution is this skeleton with
three blanks filled in. Write the skeleton first in an interview, then fill it - it prevents
most bugs.

Two variants of the record step:
- **Longest valid window**: record *after* the `while`, when the window is valid.
- **Shortest valid window**: record *inside* the `while`, just before shrinking, because the
  window is valid there and you want the smallest such one.

Getting those backwards is a common error. The rule: record wherever the window satisfies
what you are optimising for.

## Window state, by problem type

| What the window must track | Structure | Update cost |
|---|---|---|
| Sum | an integer | `O(1)` |
| Count of a character | `Counter` | `O(1)` |
| Number of **distinct** characters | `Counter` plus a `distinct` integer | `O(1)` |
| Whether all of a target is covered | `Counter` plus a `missing` counter | `O(1)` |
| Maximum in the window | **monotonic deque** | `O(1)` amortised |
| Most frequent character count | `Counter` plus a running max | `O(1)` |

The distinct-count trick is worth spelling out, since it recurs:

```python
from collections import Counter


def longest_k_distinct(s, k):
    """Longest substring with at most k distinct characters."""
    counts = Counter()
    left = 0
    best = 0
    for right, ch in enumerate(s):
        counts[ch] += 1
        # More than k distinct: shrink until we are back within budget.
        while len(counts) > k:
            counts[s[left]] -= 1
            if counts[s[left]] == 0:
                del counts[s[left]]     # delete, so len(counts) IS the distinct count
            left += 1
        best = max(best, right - left + 1)
    return best


longest_k_distinct("eceba", 2)          # 3
longest_k_distinct("aa", 1)             # 2
longest_k_distinct("abc", 0)            # 0
```

**`del` when the count hits zero.** Otherwise `len(counts)` counts characters that are no
longer in the window, and the answer is silently wrong. This is the single most common
sliding-window bug.

## The at-most-K trick

For problems asking for **exactly K**, the window usually cannot express it directly -
"exactly K distinct" is not monotonic in the window size. The fix:

> **exactly(K) = atMost(K) - atMost(K - 1)**

`atMost` *is* monotonic, so it slides. Run the window twice and subtract.

```python
def subarrays_with_k_distinct(nums, k):
    """Number of subarrays with exactly k distinct values (LC 992)."""
    def at_most(limit):
        counts = Counter()
        left = 0
        total = 0
        for right, x in enumerate(nums):
            counts[x] += 1
            while len(counts) > limit:
                counts[nums[left]] -= 1
                if counts[nums[left]] == 0:
                    del counts[nums[left]]
                left += 1
            # Every subarray ending at `right` and starting at or after `left` is valid.
            total += right - left + 1
        return total

    return at_most(k) - at_most(k - 1)


subarrays_with_k_distinct([1, 2, 1, 2, 3], 2)       # 7
subarrays_with_k_distinct([1, 2, 1, 3, 4], 3)       # 3
```

Note also the **counting** idiom: `total += right - left + 1` counts all valid subarrays
ending at `right`, because any start from `left` to `right` works. That one line turns a
"longest" window into a "how many" window, and it appears in several questions in this Part.

## Monotonic deque - the maximum in a window

When the window must report its **maximum**, a counter is not enough, because removing the
current maximum leaves you with no idea what the new one is. A monotonic deque solves it in
`O(1)` amortised.

```python
from collections import deque


def max_sliding_window(nums, k):
    """Maximum of every window of size k (LC 239)."""
    dq = deque()                    # indices, values strictly decreasing
    out = []
    for i, x in enumerate(nums):
        # Anything smaller than the incoming value can never be a future maximum.
        while dq and nums[dq[-1]] <= x:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:          # front has slid out of the window
            dq.popleft()
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out


max_sliding_window([1, 3, -1, -3, 5, 3, 6, 7], 3)   # [3, 3, 5, 5, 6, 7]
max_sliding_window([1], 1)                          # [1]
```

Each index is pushed once and popped once, so it is `O(n)` amortised - the same argument as
for monotonic stacks in Part 4.

## Recognition signals

- "**contiguous** subarray / substring", "consecutive"
- "longest / shortest / maximum / minimum ... such that ..."
- "at most k", "at least k", "exactly k"
- "containing all of", "permutation of", "anagram of"
- "window of size k"
- "with at most one replacement / k flips"

And the negative signals - **not** a sliding window:
- the array may contain **negative numbers** and you are constraining a sum
- the elements need not be contiguous (that is a subsequence, usually DP)
- you need the count of subarrays with an exact sum (prefix sums plus hash map)

## How to talk about it

- "This is a contiguous-subarray problem with a constraint, so I'll slide a window."
- "Growing the window only increases the sum, so the constraint is monotonic in the window
  size - that's what makes the window valid here."
- "Can the values be negative? Then a window doesn't work, because growing it can decrease
  the sum - I'd use prefix sums with a hash map instead."
- "`left` only moves forward, so across the whole run the inner loop does O(n) total work -
  it's linear, not quadratic."
- "I delete the key when its count reaches zero, so `len(counts)` is exactly the number of
  distinct characters in the window."
- "For 'exactly k' I'd compute at-most-k minus at-most-(k-1), because at-most is monotonic
  and exactly-k isn't."
- "To count subarrays rather than measure them, I add `right - left + 1` at each step."

## Common pitfalls across this Part

- **Using a window when values can be negative.**
- **Not deleting zero-count keys**, so the distinct count is wrong.
- **`if` instead of `while`** when shrinking - sometimes several elements must leave.
- **Recording the answer in the wrong place** (inside versus after the shrink loop).
- **Off-by-one in the window length** - it is `right - left + 1`.
- **Rebuilding the window state from scratch** each step, making it `O(n*k)`.
- **Forgetting to build the first window** in the fixed-size version.
- **Claiming `O(n^2)`** because of the nested `while`; give the amortised argument.
