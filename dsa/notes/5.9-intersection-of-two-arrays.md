title: "5.9 Intersection of Two Arrays"

**Link:** https://leetcode.com/problems/intersection-of-two-arrays
**Difficulty:** Easy | **LeetCode #349**
**Bloomberg frequency:** 50% at three months.

Trivial with a set. It is on the list because of the **follow-up questions**, which are
genuinely good: what if the arrays are sorted, what if one is huge and the other tiny, and
what if one does not fit in memory. Those three answers are the interview.

## 1. Problem statement

Given two integer arrays `nums1` and `nums2`, return their **intersection**. Each element in
the result must be **unique**, and you may return the result in any order.

```
nums1 = [1,2,2,1], nums2 = [2,2]     ->  [2]
nums1 = [4,9,5], nums2 = [9,4,9,8,4] ->  [9,4]   (or [4,9])
```

## 2. Clarifying questions

1. **Unique elements in the result?** Yes - `[2,2]` in both arrays yields a single `2`. This
   is the whole difference from LC 350 (*Intersection of Two Arrays II*), which keeps
   multiplicities. **Ask which**, because the solutions differ.
2. **Does the output order matter?** No, any order.
3. **Are the arrays sorted?** **No** in the base problem - but "what if they were" is the main
   follow-up, so ask.
4. **Any constraint on the values?** `0 <= nums[i] <= 1000` on LeetCode, small enough that a
   boolean array would work - worth noting as an option.
5. **Can either be empty?** Yes; the result is then empty.
6. **Relative sizes?** If one array is far smaller, that changes the best approach - the
   second follow-up.

## 3. Intuition

### The base solution

Put one array in a `set`, then filter the other by membership, collecting into a set to
deduplicate.

> **`set(nums1) & set(nums2)`** - one line, `O(n + m)` time, `O(min(n, m))` space if you are
> careful which array you convert.

Building the set from the **smaller** array is the small optimisation that matters: space
becomes `O(min(n, m))` rather than `O(n)`. Say it, because it is the same idea as the
follow-up about one array being tiny.

### If both arrays are sorted - two pointers

The sortedness lets you drop the hash set entirely:

> **Walk both arrays with one pointer each, advancing whichever value is smaller. When they
> match, record it and skip past all duplicates of that value in both.**

`O(n + m)` time and `O(1)` extra space beyond the output. That `O(1)` space is the reason to
prefer it when the input is sorted, and it is exactly the same shape as the merge in 2.6.

### If one array is much smaller - binary search

If `nums1` has `n` elements and `nums2` has `m` with `n << m`, and `nums2` is sorted, then
binary searching `nums2` for each element of `nums1` costs `O(n log m)`. When `n` is tiny
that beats `O(n + m)` - because you never touch most of `nums2`.

This is why the problem sits in Part 5. The decision rule to state: **`O(n log m)` beats
`O(n + m)` when `n log m < m`**, i.e. when the small array is much smaller.

## 4. Approach

1. **Base:** convert the smaller array to a set, filter the other, deduplicate.
2. **Both sorted:** two pointers.
3. **One tiny, other sorted:** binary search each element of the small one.

## 5. Solution

```python
def intersection(nums1, nums2):
    """Unique values present in both arrays, in any order.

    The set is built from the SMALLER array, so the extra space is O(min(n, m))
    rather than O(n).
    """
    if len(nums1) > len(nums2):
        nums1, nums2 = nums2, nums1     # ensure nums1 is the smaller one

    small = set(nums1)
    return list({x for x in nums2 if x in small})
```

```python
sorted(intersection([1, 2, 2, 1], [2, 2]))          # [2]
sorted(intersection([4, 9, 5], [9, 4, 9, 8, 4]))    # [4, 9]
sorted(intersection([], [1, 2]))                    # []
sorted(intersection([1, 2], []))                    # []
sorted(intersection([1, 2, 3], [4, 5, 6]))          # []
sorted(intersection([1, 1, 1], [1, 1]))             # [1]
sorted(intersection([1, 2, 3], [1, 2, 3]))          # [1, 2, 3]
```

Results are wrapped in `sorted(...)` because the order is unspecified - that is the honest
way to test a function with a non-deterministic output order, and saying so is worth a
moment.

The one-liner `list(set(nums1) & set(nums2))` is equivalent and is what you would actually
write; the version above just makes the space choice explicit.

### Both sorted - two pointers, O(1) space

```python
def intersection_sorted(nums1, nums2):
    """Both inputs sorted: two pointers, O(n + m) time and O(1) extra space.

    Advance whichever value is smaller; on a match, record it once and skip every
    duplicate of that value on BOTH sides so the output stays unique.
    """
    i = j = 0
    result = []

    while i < len(nums1) and j < len(nums2):
        if nums1[i] < nums2[j]:
            i += 1
        elif nums1[i] > nums2[j]:
            j += 1
        else:
            value = nums1[i]
            result.append(value)
            # Skip duplicates on both sides - the result must be unique.
            while i < len(nums1) and nums1[i] == value:
                i += 1
            while j < len(nums2) and nums2[j] == value:
                j += 1

    return result


intersection_sorted([1, 1, 2, 2], [2, 2])           # [2]
intersection_sorted([4, 5, 9], [4, 4, 8, 9, 9])     # [4, 9]
intersection_sorted([1, 2, 3], [4, 5, 6])           # []
intersection_sorted([], [1, 2])                     # []
intersection_sorted([1, 1, 1], [1, 1])              # [1]
intersection_sorted([1, 2, 3], [1, 2, 3])           # [1, 2, 3]
```

Note this returns the result **already sorted and unique**, for free - a small bonus worth
pointing out.

### One array much smaller - binary search

```python
import bisect


def intersection_binary(small, large_sorted):
    """O(n log m): binary search the large sorted array for each element of the small
    one. Wins when the small array is tiny, because most of the large one is never
    touched."""
    result = set()
    for x in set(small):
        i = bisect.bisect_left(large_sorted, x)
        if i < len(large_sorted) and large_sorted[i] == x:
            result.add(x)
    return list(result)


sorted(intersection_binary([4, 9, 5], [4, 4, 8, 9, 9]))     # [4, 9]
sorted(intersection_binary([1, 2, 2], [2, 2, 3]))           # [2]
sorted(intersection_binary([7], [1, 2, 3]))                 # []
sorted(intersection_binary([], [1, 2, 3]))                  # []
```

Deduplicating the small array first (`set(small)`) avoids searching for the same value
repeatedly - a free improvement worth mentioning.

## 6. Complexity

Let `n = len(nums1)`, `m = len(nums2)`, with `n <= m`.

| | Time | Space |
|---|---|---|
| Nested loops | `O(n * m)` | `O(1)` |
| **Hash set** | **`O(n + m)`** | `O(n)` |
| Sort both, then two pointers | `O(n log n + m log m)` | `O(1)` extra |
| **Both already sorted, two pointers** | **`O(n + m)`** | **`O(1)` extra** |
| **Small array + binary search on the large sorted one** | **`O(n log m)`** | `O(n)` |

The comparison to state: the hash set is the best general answer; two pointers wins on space
when the input is already sorted; and binary search wins on time when one array is
dramatically smaller, since `n log m < m` for small `n`.

## 7. How to present it

Solve it in thirty seconds, then spend the time on the follow-ups - they are the question.

1. **Restate**, and **confirm the result must be unique** (LC 349, not 350).
2. **Give the set solution immediately** and its complexity, and mention building the set
   from the **smaller** array to keep space at `O(min(n, m))`.
3. **Then volunteer the follow-ups yourself**, one sentence each:
   - *"If both were sorted, I'd use two pointers - same time, but `O(1)` extra space."*
   - *"If one array were much smaller and the other sorted, I'd binary search the large one
     for each element of the small one - `O(n log m)`, which beats `O(n + m)` when `n` is
     tiny."*
   - *"If one array didn't fit in memory, I'd load the small one into a set and stream the
     large one past it."*
   Producing all three unprompted is what turns this Easy into a good answer.
4. **Write whichever they want.**
5. **Test** empty inputs, disjoint inputs, and duplicates on both sides.
6. **Close**: `O(n + m)` time, `O(min(n,m))` space, and note the output order is
   unspecified.

## 8. Follow-ups and variations

- **"What if the arrays are sorted?"** Two pointers, `O(1)` extra space. The main follow-up.
- **"What if `nums1`'s size is small compared to `nums2`'s?"** Binary search `nums2` (if
  sorted) for each element of `nums1`: `O(n log m)`.
- **"What if `nums2` is so large it cannot fit in memory?"** Load the **small** array into a
  set and **stream** the large one, emitting matches. Memory is `O(n)`, independent of `m`.
  If *both* are too large, sort both externally and do the two-pointer merge on disk - an
  external sort-merge join, which is exactly how a database does it. Naming that connection
  is a strong close.
- **"Keep the multiplicities"** (LC 350, *Intersection of Two Arrays II*). Use a `Counter`
  and take `min(count1[x], count2[x])` for each value. Different problem; ask which.
- **"Intersection of `k` arrays."** Intersect pairwise, smallest first, or count occurrences
  across all `k` and keep values seen `k` times.
- **"Union instead of intersection."** `set(nums1) | set(nums2)`.
- **"Values are bounded to `[0, 1000]`."** A boolean array of size 1001 replaces the hash
  set - `O(1)` space by the alphabet argument, and no hashing.
- **"Intersection of two sorted linked lists."** Two pointers again, no random access needed
  - which is why binary search would not apply there.

## 9. Pitfalls

- **Returning duplicates.** `[1,2,2,1]` and `[2,2]` must give `[2]`, not `[2,2]`.
- **Confusing LC 349 with LC 350**, which keeps multiplicities.
- **Building the set from the larger array**, wasting space.
- **Nested loops**, `O(n*m)`.
- **In the sorted two-pointer version, skipping duplicates on only one side**, which emits
  the value more than once.
- **Applying binary search to an unsorted array.** Ask first, or sort - and note that sorting
  costs `O(m log m)`, which usually defeats the point.
- **Comparing against a fixed expected order** in your own tests. The order is unspecified;
  sort before comparing.
- **Forgetting the empty-array cases.**
