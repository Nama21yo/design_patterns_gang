title: "1.5 Product of Array Except Self"
---

**Link:** https://leetcode.com/problems/product-of-array-except-self
**Difficulty:** Medium | **LeetCode #238**
**Bloomberg frequency:** 50% at three months.

The multiplicative twin of prefix sums, and a favourite because the obvious solution is
banned by the constraints. Two rules make it interesting: **no division**, and **O(1) extra
space** (the output array does not count).

## 1. Problem statement

Given an integer array `nums`, return an array `answer` where `answer[i]` is the product of
**all elements of `nums` except `nums[i]`**.

- The algorithm must run in **O(n)** time.
- You must write it **without using the division operator**.
- Follow-up: do it in **O(1) extra space** (the output array does not count towards this).
- The product of any prefix or suffix is guaranteed to fit in a 32-bit integer.

```
nums = [1,2,3,4]    ->  [24,12,8,6]
nums = [-1,1,0,-3,3] -> [0,0,9,0,0]
```

## 2. Clarifying questions

1. **Why no division?** Ask if it is not stated - it is the entire constraint. The reason is
   zeros: division breaks when any element is 0.
2. **Can the array contain zeros?** Yes. Example 2 has one, and this is what makes the
   division shortcut fail.
3. **Does the output array count towards the space bound?** No, by convention - confirm it.
4. **Can values be negative?** Yes. Signs take care of themselves in a product.
5. **Array length?** At least 2 on LeetCode.
6. **Overflow?** LeetCode guarantees products fit in 32 bits. Python has unbounded ints; say
   you would check in another language.

## 3. Intuition

Start with the banned solution, because naming it and explaining why it is banned is part of
the answer:

```
total = product of everything
answer[i] = total / nums[i]
```

That is `O(n)` and wrong for two reasons. It uses division, and with a zero in the array it
breaks completely - `total` is 0 and you cannot recover the other elements' values.

Now the real idea. The product of everything except `nums[i]` splits cleanly:

```
answer[i] = (product of everything to the LEFT of i) * (product of everything to the RIGHT of i)
```

Those are **prefix and suffix products** - exactly prefix sums with `*` in place of `+` and
`1` in place of `0` as the identity.

So a first solution is two arrays: `left[i]` = product before `i`, `right[i]` = product after
`i`, then multiply them pointwise. `O(n)` time and `O(n)` extra space.

The `O(1)`-space refinement is the nice part:

> **Use the output array to hold the left products, then sweep right to left carrying the
> suffix product in a single scalar and multiplying it in as you go.**

That is the same "a running scalar replaces a prefix array" move as 1.3 Find Pivot Index,
applied twice.

## 4. Approach

**Two-array version** (write this first if you like, then compress):
1. `left[0] = 1`; `left[i] = left[i-1] * nums[i-1]`.
2. `right[n-1] = 1`; `right[i] = right[i+1] * nums[i+1]`.
3. `answer[i] = left[i] * right[i]`.

**O(1)-space version:**
1. First pass, left to right: fill `answer[i]` with the product of everything *before* `i`,
   carrying a running `prefix` scalar.
2. Second pass, right to left: carry a running `suffix` scalar; multiply it into
   `answer[i]`, then fold `nums[i]` into `suffix`.

In both passes the **update happens after the write**, because position `i` must not include
`nums[i]` itself. Same discipline as Two Sum's query-then-record.

## 5. Solution

```python
def product_except_self(nums):
    """answer[i] = product of every element except nums[i], with no division.

    answer[i] = (product of everything left of i) * (product of everything right of i).
    The output array holds the left products, then a single scalar carries the right
    products backwards, so only O(1) extra space is used.
    """
    n = len(nums)
    answer = [1] * n

    # Pass 1, left to right: answer[i] = product of nums[0..i-1].
    prefix = 1
    for i in range(n):
        answer[i] = prefix
        prefix *= nums[i]           # folded in AFTER the write, so i is excluded

    # Pass 2, right to left: multiply in the product of nums[i+1..n-1].
    suffix = 1
    for i in range(n - 1, -1, -1):
        answer[i] *= suffix
        suffix *= nums[i]           # again, after the write

    return answer
```

```python
product_except_self([1, 2, 3, 4])           # [24, 12, 8, 6]
product_except_self([-1, 1, 0, -3, 3])      # [0, 0, 9, 0, 0]
product_except_self([2, 3])                 # [3, 2]
product_except_self([0, 0])                 # [0, 0]
product_except_self([1, 0])                 # [0, 1]
product_except_self([5])                    # [1]
product_except_self([-1, -2, -3])           # [6, 3, 2]
```

Trace `[1,2,3,4]` to show the two passes composing:

| i | after pass 1 (`answer`) | pass 2 `suffix` before | `answer[i] *= suffix` |
|---|---|---|---|
| 0 | 1 | 24 | 24 |
| 1 | 1 | 12 | 12 |
| 2 | 2 | 4 | 8 |
| 3 | 6 | 1 | 6 |

After pass 1, `answer == [1, 1, 2, 6]` - the running prefix products. Pass 2 walks backwards
multiplying in `4`, `4*3`, `4*3*2`.

The zero cases are the ones to say out loud, because they are exactly what division cannot
handle:

- `[1,0]` gives `[0,1]`. Index 0's answer is the product of everything *else*, which
  includes the `0`, so it is `0`. Index 1's answer excludes the `0` and is just `1`.
- `[0,0]` gives `[0,0]`, because each position still has the *other* zero on its far side.

Neither falls out of `total / nums[i]`, and the prefix/suffix method needs no special case
for them at all.

### The two-array version, for the first pass of the explanation

```python
def product_except_self_two_arrays(nums):
    """Clearer, O(n) extra space. Write this if the space follow-up has not been asked."""
    n = len(nums)
    left = [1] * n
    right = [1] * n

    for i in range(1, n):
        left[i] = left[i - 1] * nums[i - 1]
    for i in range(n - 2, -1, -1):
        right[i] = right[i + 1] * nums[i + 1]

    return [left[i] * right[i] for i in range(n)]


product_except_self_two_arrays([1, 2, 3, 4])        # [24, 12, 8, 6]
product_except_self_two_arrays([-1, 1, 0, -3, 3])   # [0, 0, 9, 0, 0]
```

### The division solution, and why it is not acceptable

```python
def product_except_self_division(nums):
    """Banned, and broken. Kept here to be able to explain both faults precisely."""
    total = 1
    for x in nums:
        total *= x
    return [total // x for x in nums]       # ZeroDivisionError if any x is 0
```

Even ignoring the ban, it raises on `[1,0]`. You can patch it by counting zeros and
special-casing one zero versus two or more - but that is three branches to get right, and it
still uses division. Mention the patch to show you thought it through, then discard it.

## 6. Complexity

| Approach | Time | Space (excl. output) |
|---|---|---|
| Brute force, product per index | `O(n^2)` | `O(1)` |
| Division | `O(n)` | `O(1)` - but banned and wrong on zeros |
| Two arrays | `O(n)` | `O(n)` |
| **Two passes, one scalar** | **`O(n)`** | **`O(1)`** |

Two passes over `n`, so `2n` operations - still `O(n)`. You cannot do it in one pass: the
value at index 0 depends on elements you have not yet read.

## 7. How to present it

1. **Restate, and immediately name the division solution and why it is excluded.** "The
   one-liner is total product divided by `nums[i]`, but division is banned - and it also
   breaks on zeros, which is presumably why."
2. **State the decomposition** on the board:
   `answer[i] = (product left of i) * (product right of i)`. This is the insight and it is
   one line.
3. **Name it**: "These are prefix and suffix products - the same idea as prefix sums with
   multiplication."
4. **Offer the two-array version first**, `O(n)` space, and say you can compress it.
5. **Then compress**: "I can store the left products directly in the output array, then make
   a backwards pass carrying the right product in a single variable."
6. **Write it**, and as you type each pass say: *"I fold `nums[i]` in **after** writing, so
   position `i` never includes itself."*
7. **Trace `[1,2,3,4]`** using the table above - show `answer == [1,1,2,6]` after pass 1.
8. **Close**: `O(n)` time, `O(1)` extra space, and volunteer the zero cases `[1,0]` and
   `[0,0]` as proof that no division is hiding anywhere.

## 8. Follow-ups and variations

- **"Do it in O(1) extra space."** The standard follow-up - the solution above. Confirm that
  the output array is excluded from the bound.
- **"What if division were allowed?"** Count the zeros:
  - **0 zeros**: `answer[i] = total // nums[i]`.
  - **1 zero**: every position is 0 except the zero's own index, which gets the product of
    everything else.
  - **2 or more zeros**: all zeros.
  Three branches, and worth writing out only if asked - it demonstrates you understand
  *why* division is fragile rather than merely that it is banned.
- **"Sum instead of product."** `total - nums[i]`, trivially - and worth noting the contrast:
  subtraction has an inverse that works for every value, division does not (0 has no
  inverse). That is the real reason this problem exists.
- **"What about overflow?"** LeetCode guarantees 32-bit fits. In C++/Java you would use
  `long`, or note that the prefix/suffix guarantee is exactly what makes it safe.
- **"Return the product except self *modulo* p."** Fine if `p` is prime and no element is
  divisible by it (use modular inverses), but the prefix/suffix approach works with **no**
  such assumption - a good argument for it.
- **"Except self in a 2D grid"**, i.e. product of every cell except this one. Same idea with
  row and column prefix/suffix products, or just total-with-zero-counting.
- **"Sliding window product except self."** Now positions enter and leave; a running product
  cannot divide out a departing zero, so you need a monotonic structure or recomputation -
  a nice illustration of the same fragility.
- **"Maximum product subarray"** (LC 152) - unrelated technique despite the name, since
  negatives can flip. Do not confuse them.

## 9. Pitfalls

- **Using division.** Explicitly banned, and broken on zeros.
- **Folding `nums[i]` into the running product before writing `answer[i]`**, so each position
  includes itself. The single most common bug; trace index 0.
- **Initialising the running products to 0** instead of `1`. The multiplicative identity is
  1; this mirrors "prefix sums start at 0".
- **Getting the second loop's bounds wrong** - it must be `range(n-1, -1, -1)`, inclusive of
  index 0.
- **Allocating a second array and claiming O(1) space.**
- **Counting the output array towards the space bound** and concluding the follow-up is
  impossible - ask.
- **Special-casing zeros** in the prefix/suffix solution. It needs none; zeros propagate
  correctly on their own. Adding branches here is a sign you have not trusted the method.
- **Assuming at least two elements** if the interviewer allows `n == 1`, where the answer is
  `[1]` (the empty product).
