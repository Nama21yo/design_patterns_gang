**Link:** https://leetcode.com/problems/find-peak-element
**Difficulty:** Medium | **LeetCode #162**
**Bloomberg frequency:** 50% at six months.

**Binary search on an array that is not sorted at all.** This is the question that proves the
technique is about a monotone *predicate*, not about sorted data - and it is the best single
argument for the framing in the Part 5 primer.

## 1. Problem statement

A **peak element** is an element that is **strictly greater than its neighbours**.

Given an integer array `nums`, find a peak element and return its **index**. If the array
contains multiple peaks, return the index of **any** of them.

You may imagine `nums[-1] = nums[n] = -infinity` - the elements just outside the array are
negative infinity, so the boundaries are never an obstacle.

It is guaranteed that `nums[i] != nums[i + 1]` for all valid `i`.

You must write an algorithm that runs in `O(log n)`.

```
nums = [1,2,3,1]        ->  2      the element 3 is a peak
nums = [1,2,1,3,5,6,4]  ->  1 or 5 (both are peaks - either is accepted)
```

## 2. Clarifying questions

1. **Any peak, or a specific one?** **Any** - that freedom is exactly what makes `O(log n)`
   possible. Finding the *global* maximum would require looking at every element, hence
   `O(n)`. **Say this**; it is the key observation.
2. **Are adjacent elements guaranteed different?** Yes, stated. Without that guarantee (a
   plateau) the binary search breaks, and it becomes `O(n)` - worth knowing.
3. **What happens at the boundaries?** Treat out-of-range neighbours as `-infinity`, so
   `nums[0]` is a peak if `nums[0] > nums[1]`, and the last element is a peak if it exceeds
   its predecessor.
4. **Return the index or the value?** The index.
5. **Is a single-element array a peak?** Yes - index 0, with both neighbours at `-infinity`.
6. **Must it be `O(log n)`?** Stated explicitly, which rules out a scan.

## 3. Intuition

### Why a peak must exist

Start at any element and always walk **uphill**. You cannot walk forever, because the array
is finite and the boundaries are `-infinity`. So you must stop somewhere - and the place you
stop is, by definition, greater than both neighbours. **A peak always exists.** That argument
is worth thirty seconds; it is why the problem is well posed.

### Why binary search applies

Look at `mid` and compare it with its right neighbour:

> **If `nums[mid] < nums[mid + 1]`, then the right half `[mid+1, hi]` is guaranteed to
> contain a peak.** The sequence is rising at `mid`, so keep walking right: either it keeps
> rising to the end (making the last element a peak, since `nums[n] = -infinity`) or it turns
> down somewhere, and the turning point is a peak.
>
> **Otherwise `nums[mid] > nums[mid + 1]`**, the sequence is falling, so by the mirror
> argument a peak exists in `[lo, mid]` - and `mid` itself might be it.

So the predicate *"is the sequence descending at this position?"* - `nums[i] > nums[i+1]` -
is exactly the `F F F T T T` pattern the template needs, **even though the array is not
sorted**. The first `True` is a peak.

That reframing is the whole question, and it is what you should say before writing anything.
The array has no global order; what is monotone is the *existence of a peak to one side*.

### The template fits exactly

There is no target and no early return, so the exclusive template is the natural fit:

- `while lo < hi`, ending with `lo == hi`, which is the answer.
- `hi = mid` when descending, because `mid` may be the peak.
- `lo = mid + 1` when ascending, because `mid` definitely is not.
- `mid` rounds down, so `mid + 1` is always a valid index when `lo < hi`. **That is why no
  bounds check is needed on `nums[mid + 1]`** - worth pointing out, since it looks unsafe.

## 4. Approach

1. `lo, hi = 0, n - 1`.
2. While `lo < hi`:
   - `mid = (lo + hi) // 2`
   - if `nums[mid] < nums[mid + 1]`: `lo = mid + 1` (rising: a peak is to the right)
   - else: `hi = mid` (falling: a peak is here or to the left)
3. Return `lo`.

## 5. Solution

```python
def find_peak_element(nums):
    """Index of any element strictly greater than both neighbours.

    Not a sorted array - but "the sequence is descending here" is a monotone
    predicate: once it holds, a peak exists at or before this point. Walking uphill
    must terminate because the boundaries are -infinity, so a peak always exists.
    """
    lo, hi = 0, len(nums) - 1

    while lo < hi:
        mid = (lo + hi) // 2        # rounds down, so mid + 1 <= hi is always valid
        if nums[mid] < nums[mid + 1]:
            lo = mid + 1            # rising here: a peak must lie strictly to the right
        else:
            hi = mid                # falling here: a peak is at mid or to its left

    return lo
```

```python
find_peak_element([1, 2, 3, 1])         # 2
find_peak_element([1])                  # 0
find_peak_element([1, 2])               # 1
find_peak_element([2, 1])               # 0
find_peak_element([1, 2, 3, 4, 5])      # 4
find_peak_element([5, 4, 3, 2, 1])      # 0
find_peak_element([1, 3, 2, 4, 1])      # 3   -- index 1 is also a peak; either is accepted
find_peak_element([1, 2, 1, 3, 5, 6, 4])    # 5
```

The monotonic cases are the ones to run first: `[1,2,3,4,5]` -> index 4 (the last element,
peaking against the `-infinity` boundary) and `[5,4,3,2,1]` -> index 0. They confirm the
boundary convention is doing its job without any explicit boundary handling.

`[1,2,1,3,5,6,4]` has peaks at indices 1 and 5; this implementation returns 5. **Both are
correct** - the problem says any peak. If an interviewer's expected output is 1, that is not
a bug; say so, and verify your answer really is a peak.

### Verifying an answer is a peak

Worth writing in an interview to check yourself, and it makes the boundary convention
explicit:

```python
def is_peak(nums, i):
    """True if nums[i] is strictly greater than both neighbours, treating
    out-of-range neighbours as -infinity."""
    left = nums[i - 1] if i > 0 else float("-inf")
    right = nums[i + 1] if i < len(nums) - 1 else float("-inf")
    return left < nums[i] > right


is_peak([1, 2, 3, 1], 2)            # True
is_peak([1, 2, 3, 1], 1)            # False
is_peak([1, 2, 1, 3, 5, 6, 4], 1)   # True
is_peak([1, 2, 1, 3, 5, 6, 4], 5)   # True
is_peak([1], 0)                     # True
is_peak([1, 2, 3, 4, 5], 4)         # True
is_peak([5, 4, 3, 2, 1], 0)         # True
```

Note `left < nums[i] > right` is Python's chained comparison - readable, and it states the
peak condition in one expression.

### The linear scan, to state and reject

```python
def find_peak_element_linear(nums):
    """O(n): the first position where the sequence stops rising. Correct, but the
    problem demands O(log n)."""
    for i in range(len(nums) - 1):
        if nums[i] > nums[i + 1]:
            return i
    return len(nums) - 1


find_peak_element_linear([1, 2, 3, 1])      # 2
find_peak_element_linear([1, 2, 3, 4, 5])   # 4
find_peak_element_linear([5, 4, 3, 2, 1])   # 0
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(n)` | `O(1)` |
| **Binary search** | **`O(log n)`** | **`O(1)`** |
| Find the global maximum | `O(n)` - unavoidable | `O(1)` |

The last row is the contrast worth drawing: **finding *a* peak is logarithmic; finding *the
highest* peak is linear**, because any unexamined element could be larger. That distinction
is exactly what the "any peak" freedom buys, and stating it shows you understood why the
problem is phrased that way.

## 7. How to present it

1. **Restate**, and **confirm that any peak will do.** Then immediately say what that buys:
   *"If you wanted the global maximum I'd have to look at everything - `O(n)`. Returning any
   peak is what makes `O(log n)` possible."* **This is the first and best scoring moment.**
2. **Argue that a peak always exists**: walk uphill, the array is finite, the boundaries are
   `-infinity`, so you must stop somewhere.
3. **State the reframing**: *"The array isn't sorted, but 'the sequence is descending here'
   is monotone in the sense binary search needs - once it's true, a peak exists at or before
   that point. So I can binary search on that predicate."*
4. **Justify both branches** in one sentence each: rising means a peak lies to the right;
   falling means `mid` itself might be the peak.
5. **Note the `mid + 1` is always safe** because `mid` rounds down and `lo < hi`. It looks
   like a bounds bug and is not - pre-empt it.
6. **Write it.** Six lines.
7. **Test the monotonic arrays** in both directions, and the single element.
8. **Mention multiple peaks**: `[1,2,1,3,5,6,4]` returns 5, and 1 would be equally valid.
9. **Close**: `O(log n)` time, `O(1)` space, and restate the "any peak vs global max"
   contrast.

## 8. Follow-ups and variations

- **"What if adjacent elements can be equal?"** The plateau case. `nums[mid] == nums[mid+1]`
  gives no information about which side holds a peak, so you must scan - worst case `O(n)`.
  Same degradation as rotated arrays with duplicates, and a good connection to draw.
- **"Peak Index in a Mountain Array"** (LC 852, at 5.11). A guaranteed single peak with a
  strictly increasing then strictly decreasing shape. **Identical code**, and the guarantee
  simply means there is exactly one answer.
- **"Find a peak in a 2D grid"** (LC 1901). Binary search on **columns**: pick the middle
  column, find its maximum, and move towards whichever horizontal neighbour is larger.
  `O(rows log cols)`. Naming it is worth real credit.
- **"Find the global maximum."** `O(n)` - and explain why binary search cannot help.
- **"Find all peaks."** `O(n)` - the output can be `O(n)` large, so it is output-bound.
- **"Validate that an array is a mountain"** (LC 941, at 1.10). A global property, so `O(n)`
  and **not** binary searchable - the contrast is worth naming.
- **"What if the array is circular?"** Then the `-infinity` boundary argument disappears, and
  a strictly monotone circular array would have no peak - except that circularity makes that
  impossible for distinct values. Worth thinking aloud about.
- **"Ternary search instead?"** Only valid for genuinely unimodal functions. This array may
  have many peaks, so ternary search can land in the wrong valley. Good to know why it does
  not apply.

## 9. Pitfalls

- **Assuming the array must be sorted** for binary search, and rejecting the approach.
- **Trying to find the global maximum**, which forces `O(n)`.
- **Comparing `nums[mid]` with `nums[mid - 1]`** instead of `mid + 1`, which needs different
  bounds and usually an off-by-one.
- **Adding bounds checks around `nums[mid + 1]`.** Unnecessary - `mid < hi` always holds
  inside the loop - and the extra branch often introduces a bug.
- **Using `while lo <= hi` with `hi = mid`** - infinite loop.
- **`hi = mid - 1`** when descending, which can skip a peak at `mid`.
- **Returning `mid` from inside the loop** rather than `lo` at the end.
- **Treating a different-but-valid peak as wrong.** Verify with `is_peak` rather than
  comparing against one expected index.
- **Assuming adjacent equality is impossible** in a variant where it is not.
