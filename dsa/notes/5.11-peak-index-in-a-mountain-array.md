**Identical code to 5.5 Find Peak Element**, with a stronger guarantee: the array is a
genuine mountain, so there is exactly **one** peak rather than possibly many. The interest is
in what that guarantee does and does not change.

> Read [[5.5 Find Peak Element]] first. This note is short on purpose.

## 1. Problem statement

An array `arr` is a **mountain array** if:
- `len(arr) >= 3`, and
- there exists an index `i` with `0 < i < len(arr) - 1` such that
  `arr[0] < arr[1] < ... < arr[i]` and `arr[i] > arr[i+1] > ... > arr[len(arr)-1]`.

Given a mountain array, return the index `i` of the peak.

You must solve it in `O(log n)`.

```
arr = [0,1,0]       ->  1
arr = [0,2,1,0]     ->  1
arr = [0,10,5,2]    ->  1
```

## 2. Clarifying questions

1. **Is the input guaranteed to be a mountain?** Yes - that is the whole difference from 5.5.
   So there is exactly one peak, it is strictly interior (never at index 0 or `n-1`), and no
   validation is needed. **If the guarantee were absent, you would first have to verify it in
   `O(n)`** - which is 1.10 Valid Mountain Array.
2. **Strictly increasing then strictly decreasing?** Yes, no plateaus. That is what keeps the
   binary search logarithmic.
3. **Minimum length?** Three, so the peak always has neighbours on both sides.
4. **Return the index or the value?** The index.
5. **Could there be several peaks?** No - the mountain shape forbids it, which is why the
   answer is unique here and not in 5.5.
6. **Must it be `O(log n)`?** Stated.

## 3. Intuition

Exactly the same predicate as 5.5:

> **`nums[mid] < nums[mid + 1]`** means you are still on the **ascent**, so the peak is
> strictly to the right.
> **Otherwise** you are on the **descent**, so the peak is at `mid` or to its left.

Because the array rises then falls, this predicate is `F F F T T T` in the cleanest possible
way: "am I on the descending side?" is false for every index before the peak and true from
the peak onwards. Binary search finds the first `True`, which is the peak.

### What the guarantee changes

- **The answer is unique.** In 5.5 any peak was acceptable; here there is only one, so there
  is no ambiguity about the expected output. That makes testing easier but the code identical.
- **No boundary special cases.** The peak is strictly interior, so you never have to reason
  about `-infinity` neighbours. The code did not need them anyway.
- **The complexity is unchanged.** `O(log n)` either way.

### What it does *not* change

The algorithm. Say this plainly: *"this is Find Peak Element with a guarantee that there is
exactly one peak - the same binary search works unchanged."* There is no credit in
pretending to rediscover it, and recognising the identity is itself the signal.

## 4. Approach

1. `lo, hi = 0, n - 1`.
2. While `lo < hi`: `mid = (lo + hi) // 2`; if `arr[mid] < arr[mid + 1]`, `lo = mid + 1`,
   else `hi = mid`.
3. Return `lo`.

You can tighten the range to `lo, hi = 1, n - 2` since the peak is interior, but it changes
nothing and adds a chance to get the bounds wrong. Mention it, do not do it.

## 5. Solution

```python
def peak_index_in_mountain_array(arr):
    """Index of the unique peak of a mountain array.

    Same binary search as Find Peak Element: "am I on the descending side?" is false
    before the peak and true from the peak onwards, so the first True is the answer.
    The mountain guarantee makes that peak unique; it does not change the code.
    """
    lo, hi = 0, len(arr) - 1

    while lo < hi:
        mid = (lo + hi) // 2        # rounds down, so mid + 1 is always a valid index
        if arr[mid] < arr[mid + 1]:
            lo = mid + 1            # still ascending: the peak is strictly to the right
        else:
            hi = mid                # descending: the peak is at mid or to its left

    return lo
```

```python
peak_index_in_mountain_array([0, 1, 0])             # 1
peak_index_in_mountain_array([0, 2, 1, 0])          # 1
peak_index_in_mountain_array([0, 10, 5, 2])         # 1
peak_index_in_mountain_array([3, 4, 5, 1])          # 2
peak_index_in_mountain_array([24, 69, 100, 99, 79, 78, 67, 36, 26, 19])     # 2
peak_index_in_mountain_array([1, 2, 3, 4, 5, 3])    # 4
peak_index_in_mountain_array([1, 5, 4, 3, 2])       # 1
```

`[1,2,3,4,5,3]` (peak near the end) and `[1,5,4,3,2]` (peak near the start) are the two
asymmetric cases - they confirm the search converges from both directions rather than
accidentally favouring one.

### The linear scan, as the oracle

```python
def peak_index_linear(arr):
    """O(n): the first index where the ascent stops. Correct, but the problem
    demands O(log n) - useful as a validation oracle."""
    for i in range(len(arr) - 1):
        if arr[i] > arr[i + 1]:
            return i
    return len(arr) - 1


peak_index_linear([0, 1, 0])            # 1
peak_index_linear([0, 2, 1, 0])         # 1
peak_index_linear([1, 2, 3, 4, 5, 3])   # 4
```

### Verifying the answer

```python
def is_mountain_peak(arr, i):
    """True if i is the peak of a mountain array: strictly interior and strictly
    greater than both neighbours."""
    return 0 < i < len(arr) - 1 and arr[i - 1] < arr[i] > arr[i + 1]


is_mountain_peak([0, 1, 0], 1)              # True
is_mountain_peak([0, 1, 0], 0)              # False
is_mountain_peak([1, 2, 3, 4, 5, 3], 4)     # True
is_mountain_peak([1, 5, 4, 3, 2], 1)        # True
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(n)` | `O(1)` |
| **Binary search** | **`O(log n)`** | **`O(1)`** |

The range halves each iteration. Iterative, so constant space.

## 7. How to present it

This should take three minutes. Do not pad it.

1. **Restate**, and confirm the mountain guarantee: strictly up then strictly down, peak
   strictly interior, exactly one.
2. **Name the identity immediately**: *"This is Find Peak Element with a uniqueness
   guarantee - the same binary search applies, and the guarantee just means the answer is
   unambiguous."*
3. **State the predicate**: *"`arr[mid] < arr[mid+1]` means I'm still ascending, so the peak
   is to the right; otherwise it's at `mid` or to the left."*
4. **Note that `mid + 1` is always safe** because `mid` rounds down and `lo < hi`.
5. **Write it.** Six lines.
6. **Test** a peak near each end.
7. **Close**: `O(log n)`, `O(1)`, and mention that without the mountain guarantee you would
   need `O(n)` just to *validate* the shape (1.10), even though *finding* a peak stays
   logarithmic.

That last point is the most interesting thing you can say here, so save it for the close.

## 8. Follow-ups and variations

- **"Find Peak Element"** (LC 162, at 5.5) - the general version with possibly many peaks.
  Same code.
- **"Valid Mountain Array"** (LC 941, at 1.10) - *validating* the shape is `O(n)`, because it
  is a global property. The contrast between "find a peak in `O(log n)`" and "check it is a
  mountain in `O(n)`" is the sharpest idea in this pair of problems.
- **"Find in Mountain Array"** (LC 1095). Given a mountain array behind an API, find the
  index of a target. Three binary searches: find the peak, search the ascending half, then
  search the descending half. **The natural harder follow-up**, and worth being able to
  describe in one sentence.
- **"Longest mountain in an array"** (LC 845). `O(n)` scan - not binary searchable, since you
  do not know where the mountains are.
- **"What if plateaus were allowed?"** `arr[mid] == arr[mid+1]` gives no direction, so the
  search degrades to `O(n)`. Same failure mode as duplicates in rotated arrays.
- **"Find the valley instead"** (a valley array). Mirror the comparison.
- **"Peak in a 2D grid"** (LC 1901). Binary search over columns, `O(rows log cols)`.

## 9. Pitfalls

- **Pretending it is a new problem.** Recognise it as 5.5 and say so.
- **Comparing `arr[mid]` with `arr[mid - 1]`**, which needs different bounds and invites an
  off-by-one.
- **Adding bounds checks around `arr[mid + 1]`** - unnecessary, since `mid < hi` inside the
  loop.
- **`while lo <= hi` with `hi = mid`** - infinite loop.
- **`hi = mid - 1`** on the descent, which can skip the peak.
- **Returning `mid` from inside the loop** rather than `lo` at the end.
- **Tightening the range to `[1, n-2]`** and getting the bounds wrong for no benefit.
- **Attempting to validate the mountain shape** when it is guaranteed - that would make it
  `O(n)` and defeat the point.
