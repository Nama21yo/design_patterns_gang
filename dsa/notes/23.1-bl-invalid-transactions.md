> Reported 6 times across R1 and R2 on 2025-10-13, 2025-10-21, 2025-10-23 and 2025-10-28.
> This is currently the most-repeated Bloomberg coding question. Expect it.

## Prompt as given

```
Given a list of transactions (each with a trader name, amount, time and location):

A transaction is invalid if:
  1. its amount > 1000, or
  2. it happens within 60 minutes (before OR after) of another transaction by the
     same person in a DIFFERENT city.

Return all invalid transactions, sorted by time.

example_input = [
  {"trader_name": "Matt", "amount": 1001, "time": 10,   "location": "NYSE"},
  {"trader_name": "Matt", "amount": 1500, "time": 1100, "location": "London SE"},
  {"trader_name": "sss",  "amount": 1500, "time": 102,  "location": "NYSE"},
  {"trader_name": "Matt", "amount": 1050, "time": 1003, "location": "London SE"}
]
```

Closest LeetCode problem: [Invalid Transactions](https://leetcode.com/problems/invalid-transactions/)
(LC 1169). **It is not identical.** Read the section "The variant that trips people up" below.

## Clarifying questions to ask first

Ask these before writing a line. Several candidates lost the round by not asking.

1. **Is the input sorted by time?** The examples above are *not*. This changes everything.
2. **Is "within 60 minutes" inclusive?** Is a gap of exactly 60 a violation? (LC 1169 says
   `<= 60` is invalid.)
3. **Do I compare against every other transaction by that name, or only the neighbouring
   ones?** This is the fork in the road. Some interviewers want all pairs; at least one
   wanted only the immediately previous and next transaction for that name.
4. **When a pair violates rule 2, are both transactions invalid, or only the later one?**
   Both.
5. **Can the same transaction appear in the output twice** if it breaks both rules? No -
   dedupe.
6. **What is the input format?** One candidate was handed a CSV file path and had to parse
   it. Another got a list of lists. Ask.
7. **Are times minutes-since-midnight, or timestamps?** In the example they are plain ints.

## Intuition

Rule 1 is a filter - one pass, no state.

Rule 2 is the real problem: "is there another transaction by the same person, in a
different city, within 60 minutes". The naive reading is "compare every transaction with
every other one", which is O(n^2). The observation that collapses it:

> **Group by name, sort each group by time, and the only candidates that matter are
> neighbours in that sorted group.**

That is *not* quite true in general - within a 60-minute window there can be many
transactions - but it is true with a sliding window over the sorted group: as you advance,
you only need to look at transactions still inside the 60-minute window, and each one
enters and leaves the window once. That gives O(n log n) overall, dominated by the sort.

A second observation makes it even cheaper: within the window you do not care *which*
other transactions exist, only whether **any of them is in a different city**. So you only
have to track the distinct cities currently in the window. If the window holds two or more
distinct cities, every transaction in it is invalid.

## Approach

**Brute force (state it, then improve it).** For each transaction, scan all others with the
same name; if any is within 60 minutes and in a different city, mark both. `O(n^2)` time,
`O(1)` extra space. Say this out loud, give the complexity, then say "the bottleneck is
re-scanning the same name repeatedly, so let me group by name".

**Optimal.**

1. Tag every transaction with its original index so we can report them in the required
   order at the end.
2. Bucket transactions by `trader_name` into a dict.
3. Sort each bucket by time. (Total sort cost across buckets is `O(n log n)`.)
4. Sweep each bucket with a two-pointer window `[lo, hi]` holding every transaction whose
   time is within 60 of `t[hi]`. Maintain a `Counter` of cities in the window.
   - Advance `lo` while `t[hi] - t[lo] > 60`, decrementing that city's count.
   - If the window now contains more than one distinct city, every transaction in
     `[lo, hi]` is invalid.
5. Separately mark anything with `amount > 1000`.
6. Collect the marked indices, sort by time, return.

Step 4 has a subtlety: when the window gains a second city at index `hi`, the *earlier*
members of the window also become invalid. Marking "everything currently in the window"
each time would be `O(n^2)` in the worst case. The fix is to note that once a window ever
holds two cities, we can mark from `lo` to `hi` and remember the furthest index we have
already marked, so each index is marked at most once - amortised `O(n)`.

## Solution

```python
from collections import defaultdict, Counter


def invalid_transactions(transactions):
    """transactions: list of dicts with trader_name, amount, time, location.

    Returns the invalid ones, sorted by time.
    """
    n = len(transactions)
    bad = [False] * n

    # Rule 1: amount over the limit. One pass, no state needed.
    for i, t in enumerate(transactions):
        if t["amount"] > 1000:
            bad[i] = True

    # Rule 2: same name, different city, within 60 minutes (either direction).
    by_name = defaultdict(list)
    for i, t in enumerate(transactions):
        by_name[t["trader_name"]].append(i)

    for indices in by_name.values():
        # Sort this trader's transactions by time so the window is meaningful.
        indices.sort(key=lambda i: transactions[i]["time"])

        cities = Counter()       # cities currently inside the window
        lo = 0                   # left edge of the window
        marked_upto = 0          # every index < marked_upto is already flagged

        for hi in range(len(indices)):
            cities[transactions[indices[hi]]["location"]] += 1

            # Shrink from the left until the window spans at most 60 minutes.
            while transactions[indices[hi]]["time"] - transactions[indices[lo]]["time"] > 60:
                city = transactions[indices[lo]]["location"]
                cities[city] -= 1
                if cities[city] == 0:
                    del cities[city]
                lo += 1

            # Two or more distinct cities inside a 60-minute window: all of them are bad.
            if len(cities) > 1:
                start = max(lo, marked_upto)
                for k in range(start, hi + 1):
                    bad[indices[k]] = True
                marked_upto = max(marked_upto, hi + 1)

    result = [transactions[i] for i in range(n) if bad[i]]
    result.sort(key=lambda t: t["time"])
    return result
```

### The variant that trips people up

Several candidates were told, after starting, that only the **previous and next**
transaction of the same trader need to be checked - not all transactions in the window.
That is a *different, simpler* problem, and it is not LeetCode 1169. If the interviewer
says that, the inner loop collapses to a single comparison:

```python
def invalid_transactions_neighbours_only(transactions):
    """Variant: compare each transaction only with the immediately previous and next
    transaction by the SAME trader (after sorting that trader's transactions by time).
    """
    n = len(transactions)
    bad = [False] * n

    by_name = defaultdict(list)
    for i, t in enumerate(transactions):
        if t["amount"] > 1000:
            bad[i] = True
        by_name[t["trader_name"]].append(i)

    for indices in by_name.values():
        indices.sort(key=lambda i: transactions[i]["time"])
        for a, b in zip(indices, indices[1:]):
            ta, tb = transactions[a], transactions[b]
            if ta["location"] != tb["location"] and tb["time"] - ta["time"] <= 60:
                bad[a] = bad[b] = True     # both sides are flagged

    out = [transactions[i] for i in range(n) if bad[i]]
    out.sort(key=lambda t: t["time"])
    return out
```

### If you are handed a CSV

```python
import csv


def load(path):
    """File has a header row: name,amount,time,location."""
    with open(path, newline="") as f:
        rows = []
        for row in csv.DictReader(f):
            rows.append({
                "trader_name": row["name"].strip(),
                "amount": int(row["amount"]),
                "time": int(row["time"]),
                "location": row["location"].strip(),
            })
        return rows
```

Note the two things the version circulating in the chat got wrong: `csvReader.reader()` is
not a method of a `DictReader`, and the fields arrive as **strings**, so `amount` and
`time` must be cast before comparing. Casting inside the comparison (`int(x) > 1000`) works
but reads badly; cast at the boundary.

## Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(n)` |
| Grouped sliding window | `O(n log n)` | `O(n)` |
| Neighbours-only variant | `O(n log n)` | `O(n)` |

The `n log n` is entirely the sorts (per-name sort plus the final sort by time). The sweep
itself is `O(n)` amortised: `lo` only moves forward, and `marked_upto` only moves forward.

If you are told the input is already sorted by time, drop both sorts and it is **`O(n)`** -
this is exactly the answer one interviewer was pushing for when a candidate reported that
"the interviewer specifically wanted the O(n) solution".

## How to present it

1. **Restate**: "So a transaction is bad if it is over 1000, or if the same trader has
   another transaction in a different city within 60 minutes either side. I return all bad
   ones sorted by time."
2. **Ask the clarifiers**, especially "is the input sorted by time" and "all pairs or just
   neighbours". Write the answers down in a comment.
3. **Walk the example by hand.** Matt at t=10 is over 1000, so bad. Matt at t=1003 in London
   and t=1100 in London are the same city, so rule 2 does not fire between them - but both
   are over 1000. Say which rule catches each one.
4. **Give the brute force and its cost** in one sentence, then name the bottleneck:
   "rescanning the same trader".
5. **Announce the plan** before coding: "group by name, sort by time, sliding window of 60
   minutes, track distinct cities in the window".
6. **Code it**, narrating the window shrink and the "more than one city" test.
7. **Close** with complexity, then immediately: "and if the input were guaranteed sorted by
   time this drops to linear."

## Follow-ups and variations

- **"Make it O(n)."** Ask whether the input is sorted by time. If yes, skip the sorts. If
  not, you can still get `O(n)` with bucket/radix sort on time when times are bounded
  integers (minutes in a day is 1440 buckets).
- **"Only compare with the previous and next transaction."** Use the second solution above.
  Point out that it can *miss* violations the full version catches, and confirm that is
  intended.
- **"What if it is a stream and you cannot hold everything in memory?"** Keep, per trader, a
  deque of transactions from the last 60 minutes plus a city counter. Evict from the front
  as time advances. Memory is `O(active traders x transactions per 60 min)`. Note that you
  can no longer retroactively mark an already-emitted transaction, so you either emit with
  a 60-minute delay or emit corrections.
- **"What if transactions arrive out of order?"** Buffer with a watermark: hold events for a
  grace period, then finalise. This is the same idea as watermarks in stream processing -
  a nice place to connect to the system design round.
- **"Different thresholds per trader, or per city."** Replace the constant with a lookup;
  the algorithm does not change.
- **"Find the traders with the most invalid transactions."** Counter over the result, then
  top-k with a heap.
- **"What if 'different city' becomes 'more than 100 km apart'?"** The distinct-city counter
  no longer works, because distance is not an equivalence relation. You fall back to
  comparing pairs within the window, or to a spatial index.

## Pitfalls

- **Forgetting that rule 2 marks BOTH transactions.** The later one is obvious; the earlier
  one is easy to miss. The circulating chat solution handles this with a `was_invalid`
  flag - that is exactly what the flag is for.
- **Assuming the input is sorted by time.** In the given example it is not.
- **Storing only one previous transaction per trader.** The chat version keeps
  `previous_transactions[name] = [amount, time, location, is_invalid]`, a single entry. One
  candidate noticed this "failed leetcode 1169", and they were right: with three or more
  transactions in a window, one stored predecessor is not enough.
- **Comparing strings as numbers.** `"1500" > 1000` raises a `TypeError` in Python 3.
- **Returning duplicates** when a transaction breaks both rules. Mark a boolean, collect at
  the end.
- **Marking the whole window on every step** without the `marked_upto` guard, quietly
  turning the solution back into `O(n^2)`.
- Not asking whether the 60-minute boundary is inclusive, then getting an off-by-one on the
  interviewer's hidden test.
