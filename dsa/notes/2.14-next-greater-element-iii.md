**This is 2.5 Next Permutation applied to the digits of an integer**, plus a 32-bit overflow
check. If you know 2.5, this is a five-minute question - and the only new content is the
boundary handling, which is where people lose it.

> Read [[2.5 Next Permutation]] first. This note assumes it.

## 1. Problem statement

Given a positive 32-bit integer `n`, find the **smallest** 32-bit integer that has exactly
the same digits as `n` and is **greater** than `n`.

If no such integer exists, or if the answer does not fit in a **signed 32-bit** integer,
return `-1`.

```
n = 12   ->  21
n = 21   ->  -1
n = 230  ->  302
```

## 2. Clarifying questions

1. **Same digits, i.e. a permutation of the digits?** Yes, exactly the same multiset.
2. **Strictly greater?** Yes.
3. **What is the 32-bit limit?** `2^31 - 1 = 2147483647`. Exceeding it returns `-1`, **even
   though a valid permutation exists**. This is the part unique to this problem.
4. **Is `n` positive?** Yes, `1 <= n <= 2^31 - 1`.
5. **May the result have a leading zero?** Not an issue - the result is a permutation of a
   positive number's digits, and the algorithm never places a `0` first unless `n` already
   started with one, which it cannot.
6. **May I convert to a string?** Almost always yes, and it makes the digit manipulation far
   easier. Ask, and be ready to do it arithmetically if not.

## 3. Intuition

"The smallest number greater than `n` with the same digits" **is** the next permutation of
its digit sequence. So:

1. Convert `n` to a list of digits.
2. Run the Next Permutation algorithm: find the rightmost ascent, swap with the smallest
   larger successor, reverse the tail.
3. If no ascent exists, the digits are in descending order - `n` is already the largest
   arrangement - return `-1`.
4. Convert back, and return `-1` if the result exceeds `2^31 - 1`.

> **Two distinct reasons to return `-1`: no larger permutation exists, and the larger
> permutation overflows.** Both are real, and conflating them is the most common error.

For `n = 230`:
- digits `[2,3,0]`
- rightmost ascent: `2 < 3` at index 0
- smallest larger successor in the suffix `[3,0]`: the `3`
- swap: `[3,2,0]`; reverse the tail `[2,0]` -> `[0,2]`
- result `[3,0,2]` = `302`. Correct.

The overflow case is worth having a concrete example for: `n = 2147483486` permutes to
`2147483648`, which is `2^31` - one past the limit - so the answer is `-1` despite a valid
permutation existing.

## 4. Approach

1. `digits = list(str(n))`.
2. Find the rightmost `i` with `digits[i] < digits[i+1]`. If none, return `-1`.
3. Find the rightmost `j` with `digits[j] > digits[i]`; swap.
4. Reverse `digits[i+1:]`.
5. `result = int("".join(digits))`; return `result` if `result <= 2**31 - 1` else `-1`.

Digits compare correctly as single-character strings, since `'0' < '1' < ... < '9'`
lexicographically. That saves converting to ints and back, and is worth mentioning.

## 5. Solution

```python
def next_greater_element(n):
    """Smallest 32-bit integer greater than n using exactly the same digits, or -1.

    This is Next Permutation on the digit sequence, with two failure modes:
    no larger arrangement exists, or the arrangement overflows signed 32 bits.
    """
    digits = list(str(n))
    length = len(digits)

    # Step 1: rightmost ascent. Single-character strings compare correctly.
    i = length - 2
    while i >= 0 and digits[i] >= digits[i + 1]:
        i -= 1
    if i < 0:
        return -1                   # digits are descending: already the largest permutation

    # Step 2: smallest suffix digit still greater than digits[i]. The suffix is
    # descending, so scanning from the right finds it first.
    j = length - 1
    while digits[j] <= digits[i]:
        j -= 1
    digits[i], digits[j] = digits[j], digits[i]

    # Step 3: the suffix is still descending, so reversing makes it minimal.
    digits[i + 1:] = reversed(digits[i + 1:])

    result = int("".join(digits))
    # Second failure mode: a valid permutation exists but does not fit in 32 bits.
    return result if result <= 2 ** 31 - 1 else -1
```

```python
next_greater_element(12)            # 21
next_greater_element(21)            # -1
next_greater_element(230)           # 302
next_greater_element(1)             # -1
next_greater_element(1999999999)    # -1
next_greater_element(2147483476)    # 2147483647
next_greater_element(2147483486)    # -1
next_greater_element(12222333)      # 12223233
next_greater_element(11)            # -1
next_greater_element(534976)        # 536479
```

The pair `2147483476` and `2147483486` is the one to show:

- `2147483476` -> `2147483647`, which is exactly `2^31 - 1`, the largest valid answer. It
  fits, so it is returned.
- `2147483486` -> `2147483648`, which is `2^31`, one past the limit. A perfectly valid
  permutation, but it overflows, so `-1`.

Having those two side by side proves the boundary is `<=`, not `<`, and that you tested it.

`1999999999` is the other good case: the digits are `1` followed by nine `9`s, so the only
larger permutation is `9199999999`, which is ten digits and far over the limit.

### The arithmetic version, if strings are banned

```python
def next_greater_element_arithmetic(n):
    """Same algorithm without converting to a string."""
    digits = []
    x = n
    while x:
        digits.append(x % 10)
        x //= 10
    digits.reverse()                # most significant first

    length = len(digits)
    i = length - 2
    while i >= 0 and digits[i] >= digits[i + 1]:
        i -= 1
    if i < 0:
        return -1

    j = length - 1
    while digits[j] <= digits[i]:
        j -= 1
    digits[i], digits[j] = digits[j], digits[i]
    digits[i + 1:] = reversed(digits[i + 1:])

    result = 0
    for d in digits:
        result = result * 10 + d
    return result if result <= 2 ** 31 - 1 else -1


next_greater_element_arithmetic(230)            # 302
next_greater_element_arithmetic(21)             # -1
next_greater_element_arithmetic(2147483486)     # -1
next_greater_element_arithmetic(534976)         # 536479
```

Note that in a language with fixed-width integers, `result = result * 10 + d` **itself**
overflows before you can test it. The standard fixes are to accumulate in a 64-bit type, or
to check `result > (INT_MAX - d) / 10` before each step. Raising that is a strong point,
because it is a bug the Python version hides completely.

## 6. Complexity

Let `d` be the number of digits - at most 10 for a 32-bit integer.

| | Time | Space |
|---|---|---|
| Generate all permutations | `O(d! * d)` | `O(d)` |
| **Next permutation on the digits** | **`O(d)`** | `O(d)` |

Since `d <= 10`, this is effectively `O(1)` - worth saying, because it reframes the whole
problem as constant-time. Three partial scans of a ten-element list.

## 7. How to present it

1. **Name it immediately**: "This is next permutation applied to the digits of the number."
   There is no credit for pretending to discover it, and naming it buys you time for the
   parts that are actually specific to this problem.
2. **Confirm the two `-1` cases** out loud: no larger permutation, **and** overflow. Ask for
   the exact bound - `2^31 - 1`.
3. **Walk `230` by hand** in three steps: find the ascent, swap, reverse.
4. **Announce**, then write it. Mention that single-character strings compare correctly, so
   there is no need to map to ints.
5. **Handle the overflow check explicitly** and say `<= 2**31 - 1`, not `<`.
6. **Give the boundary pair** `2147483476` -> fits, `2147483486` -> overflows. Volunteering
   a test at the exact boundary is the strongest thing you can do here.
7. **Mention the fixed-width caveat**: in C++/Java the accumulation itself overflows, so you
   would build in a 64-bit type or check before multiplying.
8. **Close**: `O(d)` with `d <= 10`, so constant time in practice.

## 8. Follow-ups and variations

- **"Next Greater Element I / II."** Completely different problems despite the shared name -
  they are **monotonic stack** questions over arrays, and they are 4.3 and 4.4 in this
  course. Do not confuse them; knowing that III is the odd one out is itself worth saying.
- **"Previous smaller number with the same digits."** Mirror every comparison, as in 2.5.
- **"The k-th greater number with the same digits."** Apply next-permutation `k` times
  (`O(k*d)`), or compute directly with the factorial number system.
- **"Count how many permutations of the digits exceed `n`."** Combinatorics with repeated
  digits - a genuinely different problem.
- **"64-bit instead of 32-bit."** Change the bound; the algorithm is unchanged.
- **"What if the input is given as a digit array?"** Then it is literally 2.5 and there is no
  conversion.
- **"What if leading zeros were allowed?"** They are not reachable here, but if the input
  were a digit array containing a leading zero, the "smallest greater arrangement" question
  would need a rule about whether `012` is a legal output.

## 9. Pitfalls

- **Forgetting the overflow check entirely.** The most common failure; `2147483486` is the
  test.
- **Using `<` instead of `<=`** against `2^31 - 1`, wrongly rejecting `2147483647`.
- **Confusing this with Next Greater Element I/II** and reaching for a monotonic stack.
- **Comparing digits as characters in a language where that is unsafe** - it is fine in
  Python and for ASCII digits generally, but say why it works.
- **Sorting the suffix instead of reversing.** Correct output, but it misses the invariant
  (see 2.5) and is `O(d log d)`.
- **Scanning from the left for the pivot**, giving a much larger number rather than the next
  one.
- **Returning the digit list** rather than an integer.
- **In a fixed-width language, overflowing during the accumulation** before the check can
  run.
