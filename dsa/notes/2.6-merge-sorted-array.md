**Difficulty:** Easy | **LeetCode #88**
**Bloomberg frequency:** 50% at three months.

The single best small example of **"if writing forwards overwrites data you still need,
write backwards"**. That idea reappears in string manipulation, in-place matrix work, and
array resizing, so it is worth more than the problem itself.

## 1. Problem statement

You are given two integer arrays `nums1` and `nums2`, sorted in non-decreasing order, and
integers `m` and `n` - the number of real elements in each.

Merge `nums2` into `nums1` so that `nums1` becomes one sorted array. `nums1` has length
`m + n`: the first `m` entries are its real elements and the last `n` are `0` placeholders.

The result must be stored **in `nums1`**.

```
nums1 = [1,2,3,0,0,0], m = 3, nums2 = [2,5,6], n = 3  ->  [1,2,2,3,5,6]
nums1 = [1],           m = 1, nums2 = [],     n = 0  ->  [1]
nums1 = [0],           m = 0, nums2 = [1],    n = 1  ->  [1]
```

## 2. Clarifying questions

1. **Are the trailing zeros real data or padding?** Padding - `nums1` has exactly `m` real
   elements. Do not merge the zeros in. This is the most common misreading.
2. **Must the result be in `nums1`, or may I return a new array?** In `nums1`, which is the
   whole constraint.
3. **Is `nums1` guaranteed to be big enough?** Yes, exactly `m + n`.
4. **Are duplicates possible across the arrays?** Yes - example 1 has `2` in both.
5. **Can either be empty?** Yes, both edge cases are given.
6. **Stability?** Irrelevant for plain integers, but worth a word if the elements were
   records.

## 3. Intuition

The natural merge writes from the front, taking the smaller head each time. But writing to
`nums1[0]` would **clobber** `nums1`'s own first element, which you still need. You would
have to shift, making it `O(m*n)`.

The fix:

> **Fill from the back.** The last slot of `nums1` is padding, so writing there destroys
> nothing. Take the **larger** of the two tails and place it at the end, then move inward.

Three pointers, all moving left:
- `i` - the last real element of `nums1`, starting at `m - 1`
- `j` - the last element of `nums2`, starting at `n - 1`
- `write` - the destination, starting at `m + n - 1`

The key safety property, worth stating: **`write` is always at least as far right as `i`**.
There are `n` padding slots and `write` starts `n` positions ahead of `i`, and each step
advances `write` by one while advancing at most one of `i`/`j`. So `write` never overtakes
`i`, and we never overwrite an unread element. That is the proof the approach is safe.

### The tail cleanup

When the loop ends, one array is exhausted.
- If `nums1` ran out (`i < 0`), the remaining `nums2` elements still need copying.
- If `nums2` ran out (`j < 0`), the remaining `nums1` elements are **already in place** -
  nothing to do.

That asymmetry is a nice detail to volunteer. Only one of the two leftovers needs handling.

## 4. Approach

1. `i, j, write = m - 1, n - 1, m + n - 1`.
2. While `i >= 0 and j >= 0`:
   - if `nums1[i] > nums2[j]`: `nums1[write] = nums1[i]`, `i -= 1`
   - else: `nums1[write] = nums2[j]`, `j -= 1`
   - `write -= 1`
3. While `j >= 0`: `nums1[write] = nums2[j]`, `j -= 1`, `write -= 1`.
4. No step for leftover `nums1` - already correct.

## 5. Solution

```python
def merge(nums1, m, nums2, n):
    """Merge nums2 into nums1 in place. nums1 has m real elements then n padding slots.

    Filling from the BACK is what makes it in place: the tail of nums1 is padding, so
    writing there destroys nothing, and `write` provably never overtakes `i`.
    """
    i = m - 1               # last real element of nums1
    j = n - 1               # last element of nums2
    write = m + n - 1       # where the next (largest) value goes

    while i >= 0 and j >= 0:
        # Take the LARGER tail, because we are filling the array from the right.
        if nums1[i] > nums2[j]:
            nums1[write] = nums1[i]
            i -= 1
        else:
            nums1[write] = nums2[j]
            j -= 1
        write -= 1

    # Only nums2's leftovers need copying: anything still in nums1 is already in place.
    while j >= 0:
        nums1[write] = nums2[j]
        j -= 1
        write -= 1

    return nums1
```

```python
merge([1, 2, 3, 0, 0, 0], 3, [2, 5, 6], 3)      # [1, 2, 2, 3, 5, 6]
merge([1], 1, [], 0)                            # [1]
merge([0], 0, [1], 1)                           # [1]
merge([4, 5, 6, 0, 0, 0], 3, [1, 2, 3], 3)      # [1, 2, 3, 4, 5, 6]
merge([1, 2, 3, 0, 0, 0], 3, [4, 5, 6], 3)      # [1, 2, 3, 4, 5, 6]
merge([2, 2, 0, 0], 2, [2, 2], 2)               # [2, 2, 2, 2]
merge([0, 0, 0], 0, [1, 2, 3], 3)               # [1, 2, 3]
merge([1, 2, 3], 3, [], 0)                      # [1, 2, 3]
```

Two worth narrating:

- `[4,5,6] + [1,2,3]` -> every `nums2` element is smaller, so the loop copies all of
  `nums1` to the back first, then the tail loop copies `nums2` into the front. It exercises
  step 3 fully.
- `[1,2,3] + [4,5,6]` -> the opposite: `nums2` is consumed entirely, `j` hits `-1`, and the
  remaining `nums1` elements are already where they belong, so nothing happens. This is the
  case that proves the missing fourth step is deliberate.

### The version that does not work

```python
def merge_forwards_broken(nums1, m, nums2, n):
    """Writing forwards clobbers nums1's own unread elements."""
    i = j = 0
    for write in range(m + n):
        if j >= n or (i < m and nums1[i] <= nums2[j]):
            nums1[write] = nums1[i]     # may overwrite an element i has not reached
            i += 1
        else:
            nums1[write] = nums2[j]
            j += 1
    return nums1


merge_forwards_broken([1, 2, 3, 0, 0, 0], 3, [2, 5, 6], 3)      # [1, 2, 2, 2, 5, 6]
merge_forwards_broken([4, 5, 6, 0, 0, 0], 3, [1, 2, 3], 3)      # [1, 1, 1, 1, 2, 3]
```

Both are wrong, and the second spectacularly so. Writing `1` to index 0 destroys the `4`
that `i` has not yet consumed; `i` then reads the `1` it just wrote, writes it again, and
the corruption feeds on itself. Even the first case, which looks nearly right, has lost the
original `3`.

**Showing a case where the obvious approach breaks is much stronger than asserting that it
does** - and it takes ten seconds on the whiteboard.

### Sorting instead, and why not

```python
def merge_by_sorting(nums1, m, nums2, n):
    nums1[m:] = nums2[:n]
    nums1.sort()
    return nums1


merge_by_sorting([1, 2, 3, 0, 0, 0], 3, [2, 5, 6], 3)       # [1, 2, 2, 3, 5, 6]
```

Two lines and correct, but `O((m+n) log(m+n))` - it throws away the fact that both inputs are
already sorted. Mention it as the "if you want it in one line" answer and then give the
linear one, saying exactly that.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Concatenate and sort | `O((m+n) log(m+n))` | `O(1)` extra (Timsort is close to `O(n)` here) |
| Forward merge with shifting | `O(m * n)` | `O(1)` |
| Merge into a new array, copy back | `O(m + n)` | `O(m + n)` |
| **Backward merge** | **`O(m + n)`** | **`O(1)`** |

Each of the `m + n` slots is written exactly once. Optimal on both counts.

## 7. How to present it

1. **Restate, and pin down the padding**: "the last `n` entries of `nums1` are placeholders,
   not data - so I am merging `m` real elements with `n`."
2. **Start with the natural forward merge and say why it fails**: "if I write to the front of
   `nums1` I overwrite elements I still need. I could shift, but that's `O(m*n)`."
3. **State the fix**: "So I fill from the back, where the padding is - writing there destroys
   nothing."
4. **Give the safety argument**: "`write` starts `n` slots ahead of `i` and advances one per
   step while `i` advances at most one, so `write` can never overtake `i`." This is the part
   that turns a remembered trick into a justified one.
5. **Announce** the three pointers and that you take the **larger** tail.
6. **Write it**, then explain the asymmetric cleanup: only `nums2`'s leftovers need copying.
7. **Trace `[4,5,6] + [1,2,3]`**, which is the case that uses the cleanup loop.
8. **Close**: `O(m+n)` time, `O(1)` space; mention that sorting would be the one-liner but
   discards the sortedness you were given.

## 8. Follow-ups and variations

- **"Merge k sorted arrays."** LC 23 in linked-list form. A min-heap of the `k` heads,
  `O(N log k)`; or pairwise merging. Name the heap approach.
- **"Merge two sorted linked lists."** LC 21 - the same logic forwards, with a dummy head,
  and no clobbering problem because you relink rather than overwrite.
- **"What if `nums1` had no spare room?"** Then in-place is impossible without shifting;
  allocate, or use an `O(1)`-space rotation-based merge (complex and rarely wanted - say it
  exists, do not attempt it).
- **"Merge and remove duplicates."** Add a comparison against the last written value, as in
  2.2.
- **"The arrays are descending."** Flip the comparison, or fill from the front.
- **"Find the median of the merged array without merging."** LC 4, which is 5.1 here -
  binary search on the partition, `O(log(min(m,n)))`. A much harder problem that shares the
  setup.
- **"Intersection of two sorted arrays."** Same two-pointer skeleton with a different action
  on equality. LC 349 is 5.9 here.
- **"What if the elements are records and stability matters?"** Take from `nums1` on ties to
  keep its elements first - change `>` to `>=` appropriately and say which you chose.

## 9. Pitfalls

- **Merging forwards**, clobbering unread `nums1` elements. Demonstrate with `[4,5,6]` and
  `[1,2,3]`.
- **Treating the padding zeros as data**, so they end up sorted into the result.
- **Starting `write` at `m + n`** instead of `m + n - 1` - off by one, `IndexError`.
- **Adding a fourth loop for leftover `nums1` elements.** Harmless but it reveals you have
  not seen why they are already correct.
- **Taking the smaller tail** instead of the larger when filling backwards.
- **Forgetting the `n == 0` or `m == 0` cases**; both are given as examples and both work
  with the code above, but check them.
- **Returning a new list** instead of mutating `nums1`.
- **Using `nums1 = sorted(nums1[:m] + nums2)`**, which rebinds the local name and leaves the
  caller's array untouched - a genuinely nasty Python-specific bug.
