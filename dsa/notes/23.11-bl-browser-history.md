---
title: "23.11 Browser history: print most-recent-first, deduplicated"
---

> Reported once in R1 on 2025-10-14. The candidate's own framing - *"it's like an LRU cache
> but there is no limit"* - is the right instinct, and saying it is most of the answer.

## Prompt as given

```
Whenever you visit a website you save it in your History. When asked for the history you
print it from most recently visited to least recently visited.

  visits:  bbc.com, bloomberg.com, msn.com, bloomberg.com

  history: bloomberg.com
           msn.com
           bbc.com

For duplicates you print only the most recent occurrence. It is like an LRU cache, but with
no size limit.
```

Related: [LRU Cache](https://leetcode.com/problems/lru-cache/) (LC 146),
[Design Browser History](https://leetcode.com/problems/design-browser-history/) (LC 1472).

Check the example: `bloomberg.com` was visited first at position 2 and again at position 4.
It appears **once**, at the top, in its most recent position - and crucially, its earlier
position does **not** hold a slot. `bbc.com` sinks to the bottom.

## Clarifying questions to ask first

1. **Is there a size limit?** The prompt says no - which means this is *not* an LRU cache,
   it is the recency list without the eviction. Confirm, and ask whether a limit might be
   added later (it is the obvious follow-up).
2. **What must be fast?** Visiting is the hot path (every page load); printing is rare. Ask
   which they want optimised - it changes the answer completely.
3. **Do we need the full history, or the last k?** Printing everything is `O(n)` no matter
   what you do.
4. **Is `visit` idempotent for the same page twice in a row?** Should `a, a` leave one entry?
   Yes, by the dedup rule.
5. **Do we ever need "when" as well as "what"?** If timestamps are required the design
   changes.
6. **Back / forward buttons?** That is LC 1472 and a *different* data structure. Ask, because
   "browser history" is ambiguous between the two.

## Intuition

The requirement is exactly: **a sequence, ordered by recency, with at most one entry per
key, where re-visiting moves an existing entry to the front.**

That is the recency list at the heart of an LRU cache, minus eviction. The classic structure
is a **doubly linked list plus a hash map from key to node**:

- the list holds the order, most recent at the head;
- the map finds a node in `O(1)` so you can unlink it without scanning;
- a doubly linked list is required (not singly) because unlinking a node needs its
  *predecessor*, and only a `prev` pointer gives you that in `O(1)`.

That is the textbook answer and you should be able to write it. But in Python there is a
much better one to lead with:

> **`dict` preserves insertion order (guaranteed since 3.7), so a plain dict *is* the
> ordered structure. `move_to_end` on an `OrderedDict` does the reordering in `O(1)`.**

`OrderedDict` is literally implemented as a hash map over a doubly linked list. Saying
"I'll use `OrderedDict`, which is a hash map plus a doubly linked list, and here is what it
is doing underneath" gets you both marks: the idiomatic answer and the proof you know the
structure.

## Approach

**Version 1 - `OrderedDict`, most recent last.**
1. `visit(url)`: `self.history[url] = True` then `move_to_end(url)`. Or `pop` then
   re-insert.
2. `get_history()`: `reversed(self.history)`.

**Version 2 - hand-rolled doubly linked list**, for when they ask you to implement it.
1. Sentinel `head` and `tail` nodes so there are no null checks.
2. `nodes: dict[url] -> Node`.
3. `visit`: if present, unlink; then insert right after `head`.
4. `get_history`: walk from `head.next` to `tail`.

## Solution

### The idiomatic version

```python
from collections import OrderedDict


class BrowserHistory:
    """Visit order with duplicates collapsed to their most recent occurrence.

    OrderedDict is a hash map over a doubly linked list, so move_to_end is O(1):
    it unlinks the node and relinks it at the tail, with no shifting.
    """

    def __init__(self):
        # Keys in insertion order, oldest first. The value is unused; only order matters.
        self._visits = OrderedDict()

    def visit(self, url):
        # last=True moves an existing key to the end (most recent) without
        # disturbing anything else. If the key is new, it is simply appended.
        self._visits[url] = None
        self._visits.move_to_end(url, last=True)

    def history(self):
        """Most recently visited first."""
        return list(reversed(self._visits))

    def print_history(self):
        for url in self.history():
            print(url)
```

```python
b = BrowserHistory()
for url in ["bbc.com", "bloomberg.com", "msn.com", "bloomberg.com"]:
    b.visit(url)
b.history()
# ['bloomberg.com', 'msn.com', 'bbc.com']
```

A note to volunteer: `self._visits[url] = None` on an **existing** key does *not* move it -
assigning to an existing key preserves its position. That is why the explicit `move_to_end`
is needed and not redundant. Getting this wrong is silent and produces the un-deduplicated
order, so say it.

If you would rather not rely on `move_to_end`, `self._visits.pop(url, None)` followed by
`self._visits[url] = None` is equivalent and arguably clearer.

### The hand-rolled version

```python
class Node:
    __slots__ = ("url", "prev", "next")

    def __init__(self, url=None):
        self.url = url
        self.prev = None
        self.next = None


class BrowserHistoryLinked:
    """Hash map + doubly linked list. Head side is most recent.

    Doubly linked, not singly: unlinking a node in O(1) needs its predecessor.
    """

    def __init__(self):
        # Sentinels remove every null check from the link/unlink code.
        self.head = Node()
        self.tail = Node()
        self.head.next = self.tail
        self.tail.prev = self.head
        self.nodes = {}

    def _unlink(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _push_front(self, node):
        node.prev = self.head
        node.next = self.head.next
        self.head.next.prev = node
        self.head.next = node

    def visit(self, url):
        node = self.nodes.get(url)
        if node is not None:
            self._unlink(node)          # it already exists: take it out of its old slot
        else:
            node = Node(url)
            self.nodes[url] = node
        self._push_front(node)          # and put it at the most-recent end

    def history(self):
        out = []
        node = self.head.next
        while node is not self.tail:
            out.append(node.url)
            node = node.next
        return out
```

```python
b = BrowserHistoryLinked()
for url in ["bbc.com", "bloomberg.com", "msn.com", "bloomberg.com"]:
    b.visit(url)
b.history()
# ['bloomberg.com', 'msn.com', 'bbc.com']
```

### What NOT to do, and why

```python
    # Do not do this.
    def visit(self, url):
        if url in self.history_list:
            self.history_list.remove(url)     # O(n) scan, then O(n) shift
        self.history_list.insert(0, url)      # O(n) shift
```

It is correct and it is `O(n)` per visit. On the hot path of a browser that is the wrong
trade. Mention this version, give its cost, and then improve it - that sequence is worth
more than jumping straight to the answer.

## Complexity

| | `visit` | `history()` | space |
|---|---|---|---|
| List with `remove` + `insert(0, ...)` | `O(n)` | `O(n)` | `O(n)` |
| `OrderedDict` | `O(1)` | `O(n)` | `O(n)` |
| Hash map + doubly linked list | `O(1)` | `O(n)` | `O(n)` |

`history()` is `O(n)` in every design, because the output is `n` items - it is
output-bound, not algorithm-bound. Say that, so the `O(n)` does not look like a weakness.

## How to present it

1. **Restate with the example**, and specifically call out that the *earlier* occurrence of
   `bloomberg.com` vanishes rather than staying in place. That is the dedup rule and it is
   the only subtle part of the spec.
2. **Name it**: "this is the recency list from an LRU cache without the eviction - so hash
   map plus doubly linked list."
3. **Say which operation you are optimising** and why: visits are frequent, prints are rare.
4. **Give the naive list version and its `O(n)`**, then improve.
5. **Write the `OrderedDict` version**, and immediately say what it is underneath. Do not let
   it look like you only know the library call.
6. **Offer to hand-roll the linked list** - many interviewers want exactly that, and this is
   where the `prev` pointer justification earns its marks.
7. **Close** by noting the one-line change that turns it into a real LRU, which is the
   follow-up you are inviting.

## Follow-ups and variations

- **"Now add a capacity."** It becomes LRU: after inserting, if `len > capacity`, pop the
  least recent end. With `OrderedDict` that is `self._visits.popitem(last=False)`. One line -
  and note that `functools.lru_cache` is built on exactly this.
- **"Support back() and forward()."** This is a **different** structure - LC 1472. Recency
  order and navigation order are not the same thing: pressing back does not make the
  previous page "most recent" in the dedup sense, and visiting a new page after going back
  **truncates** the forward history. Use two stacks (back and forward) or a list with a
  cursor. Say explicitly that this is a different problem from the one just solved;
  conflating them is the trap.
- **"Search the history by prefix."** A trie over the URLs, with each node caching the most
  recent visit under it - which is the autocomplete question (`23.12`).
- **"Keep counts as well as recency"**, i.e. most-visited rather than most-recent. Then you
  want a frequency map plus a heap, or the LFU structure. Different problem, name it.
- **"Persist across sessions."** Append-only log on disk, replayed at startup; or a small
  database with an index on last-visited-time. Mention that replaying the log rebuilds the
  exact structure, which is why an append-only log is attractive.
- **"Group by day, like a real browser."** Store timestamps too and bucket on read.
- **"Millions of URLs - is memory a problem?"** Yes, unbounded history grows forever. Cap by
  count or by age; that is the capacity follow-up wearing a different hat.
- **"Thread safety."** The unlink/relink pair must be atomic; a single lock is the right
  first answer.

## Pitfalls

- **Assigning to an existing `OrderedDict` key and expecting it to move.** It does not.
  `move_to_end` (or pop-and-reinsert) is required.
- **Using a plain list with `remove`/`insert(0, ...)`** and calling it done. Correct but
  `O(n)`; the question is about the structure.
- **Using a singly linked list.** You cannot unlink in `O(1)` without the predecessor.
- **Forgetting the sentinel nodes** and then writing six null checks that are each a chance
  to be wrong.
- **Printing oldest-first.** The spec says most recent first; `reversed` or insert-at-head.
- **Keeping both occurrences** of a repeated URL.
- **Assuming a size limit.** There is none - and noticing that it is an LRU *without*
  eviction is the observation that shows you understood, rather than pattern-matched.
- **Confusing this with back/forward navigation.** Ask which they mean before designing.
