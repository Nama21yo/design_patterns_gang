**Link:** https://leetcode.com/problems/container-with-most-water
**Difficulty:** Medium | **LeetCode #11**
**Bloomberg frequency:** 62% at three months, 75% at six months.

The cleanest **exchange argument** in the whole course. The code is six lines and almost
everyone can write it; what separates candidates is being able to prove that moving the
shorter line is safe. Expect to be asked "why is that correct?" and have the proof ready.

## 1. Problem statement

You are given an integer array `height` of length `n`. There are `n` vertical lines, the
`i`-th drawn from `(i, 0)` to `(i, height[i])`.

Find two lines that, together with the x-axis, form a container holding the most water.
Return that maximum amount.

You may **not** slant the container.

```
height = [1,8,6,2,5,4,8,3,7]  ->  49    lines at index 1 and 8: min(8,7) * (8-1) = 49
height = [1,1]                ->  1
```

## 2. Clarifying questions

1. **Is the water level the *minimum* of the two heights?** Yes - the shorter line is what
   the water spills over. This is the key formula and it is worth stating back.
2. **Do the lines between the two chosen ones matter?** **No** - we are choosing exactly two
   walls for one container, and whatever stands between them is irrelevant. This is the
   crucial difference from *Trapping Rain Water* (4.1), where the interior is the entire
   point.
3. **Return the area or the indices?** The area.
4. **Can heights be zero?** Yes; such a line holds nothing.
5. **Can `n` be less than 2?** LeetCode guarantees at least 2. With fewer, the answer is 0.
6. **Array size?** Up to 10^5, so `O(n^2)` will time out.

## 3. Intuition

The area of the container formed by indices `lo` and `hi` is

```
area = min(height[lo], height[hi]) * (hi - lo)
```

width times the **shorter** of the two walls. Brute force tries every pair: `O(n^2)`.

Start with the two pointers at the extreme ends, which gives the **maximum possible width**.
From there, any other candidate is narrower, so it can only win by being taller.

> **Move the pointer at the *shorter* line inward. Moving the taller one can never help.**

### The proof - say this out loud

Suppose `height[lo] <= height[hi]`. Consider every container that uses `lo` as one wall:

- its width is at most `hi - lo` (we are already at the widest such pairing);
- its height is `min(height[lo], height[other])`, which is at most `height[lo]`.

So **no container using `lo` can beat `min(height[lo], height[hi]) * (hi - lo)`**, which we
have just computed. Therefore `lo` cannot participate in any better answer, and discarding
it loses nothing. Move `lo` inward.

If instead we moved `hi` (the taller line), we would lose width while the height stays capped
by the same short line `height[lo]`, so the area can only shrink or stay equal - we would
gain nothing and might skip the true optimum.

That argument is the question. Practise saying it in three sentences.

### Why the interior does not matter

Worth pre-empting, because people confuse this with Trapping Rain Water. Here you pick **two
walls and one container**; a tall line in between is simply not part of this container, and
it will be considered when the pointers reach it. In Trapping Rain Water you are filling
**every** position, so the surrounding maxima matter everywhere. Different problem, different
tool (4.1 uses a monotonic stack or two-pointer maxima).

## 4. Approach

1. `lo, hi = 0, n - 1`; `best = 0`.
2. While `lo < hi`:
   - `area = min(height[lo], height[hi]) * (hi - lo)`; `best = max(best, area)`
   - if `height[lo] < height[hi]`: `lo += 1` else `hi -= 1`
3. Return `best`.

On a tie (`height[lo] == height[hi]`) either pointer may move - both walls are equally
limiting, and neither can do better with a narrower width. Moving one is enough.

## 5. Solution

```python
def max_area(height):
    """Maximum water held between two vertical lines.

    Start at the widest pair and always move the SHORTER line inward: no container
    using that line can beat the one just measured, because any other pairing with it
    is narrower and still capped by its height.
    """
    lo, hi = 0, len(height) - 1
    best = 0

    while lo < hi:
        # The shorter line sets the water level; the gap sets the width.
        area = min(height[lo], height[hi]) * (hi - lo)
        if area > best:
            best = area

        if height[lo] < height[hi]:
            lo += 1                 # lo can never do better, so discard it
        else:
            hi -= 1                 # on a tie either may move; both are capped alike

    return best
```

```python
max_area([1, 8, 6, 2, 5, 4, 8, 3, 7])   # 49
max_area([1, 1])                        # 1
max_area([4, 3, 2, 1, 4])               # 16
max_area([1, 2, 1])                     # 2
max_area([2, 3, 4, 5, 18, 17, 6])       # 17
max_area([0, 0])                        # 0
max_area([1, 2, 4, 3])                  # 4
max_area([])                            # 0
```

`[4,3,2,1,4]` is the one to narrate: the answer `16` comes from the two `4`s at the ends,
width 4. The pointers start there, record 16 immediately, and everything after is narrower.
It also exercises the tie branch, since both ends are equal.

`[2,3,4,5,18,17,6]` gives `17` - from indices 4 and 5, `min(18,17) * 1`. That one is worth
checking because the intuition "wide is good" fails: the best answer here is the narrowest
possible container.

### The brute force, to state first

```python
def max_area_brute(height):
    """O(n^2): every pair. State this, give the bound, then improve it."""
    best = 0
    for i in range(len(height)):
        for j in range(i + 1, len(height)):
            best = max(best, min(height[i], height[j]) * (j - i))
    return best


max_area_brute([1, 8, 6, 2, 5, 4, 8, 3, 7])     # 49
max_area_brute([4, 3, 2, 1, 4])                 # 16
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` |
| **Two pointers** | **`O(n)`** | **`O(1)`** |

Each step moves exactly one pointer inward and they start `n - 1` apart, so the loop runs at
most `n - 1` times. One pass, constant space, and `O(n)` is optimal since every line must at
least be looked at.

## 7. How to present it

1. **Write the area formula on the board** first: `min(h[lo], h[hi]) * (hi - lo)`. Stating it
   explicitly prevents the most common error, which is using the wrong height.
2. **Say the brute force and its cost.**
3. **Say where you start and why**: "I start at both ends because that is the widest possible
   container - from here every alternative is narrower, so it has to be taller to win."
4. **Give the exchange argument in full.** Do not wait to be asked:
   *"Suppose the left line is the shorter one. Any container using it is at most this wide
   and at most this tall, so none of them can beat what I have just measured. So I can
   discard it."* This is the scored moment of the question.
5. **Mention the tie case** - either pointer may move.
6. **Write the loop.**
7. **Trace `[1,8,6,2,5,4,8,3,7]`** for the first three steps: `(0,8)` gives `min(1,7)*8 = 8`,
   move `lo`; `(1,8)` gives `min(8,7)*7 = 49`; and 49 turns out to be the answer.
8. **Pre-empt the confusion**: "note this is different from Trapping Rain Water - there the
   lines in between matter, here they do not, because we are choosing exactly two walls."
9. **Close**: `O(n)` time, `O(1)` space, one pointer moves per iteration so at most `n-1`
   steps.

## 8. Follow-ups and variations

- **"Prove that moving the shorter line is correct."** The most likely follow-up. The
  argument above.
- **"Return the indices, not the area."** Record `(lo, hi)` whenever `best` improves.
- **"What if the container may be slanted?"** Then the shorter-line constraint disappears and
  the problem changes completely - worth noting that the "may not slant" line in the prompt
  is what creates the `min`.
- **"Trapping Rain Water"** (LC 42, which is 4.1 here). Superficially similar, genuinely
  different: you compute water above *every* index using the max to its left and right.
  Solvable with a two-pointer variant or a monotonic stack. Knowing the distinction cold is
  worth more than either solution.
- **"Largest Rectangle in Histogram"** (LC 84, at 4.9). Also similar-looking, also different:
  the rectangle's height is the minimum over a *contiguous range*, so it needs a monotonic
  stack. Three problems about bars, three different techniques - name all three.
- **"Container with three walls / in 3D."** The exchange argument does not generalise
  cleanly; say so rather than inventing something.
- **"What if the widths between lines are not uniform?"** Given an `x` coordinate array, the
  width becomes `x[hi] - x[lo]` and everything else is unchanged - a good check that you
  understood the formula rather than memorised `hi - lo`.
- **"Find the k best containers."** Two pointers gives no easy ordering; you would need a
  heap over candidates, or accept `O(n^2)`.

## 9. Pitfalls

- **Using `max` instead of `min`** for the height. The water spills over the shorter wall.
- **Moving the taller pointer**, or moving both. Moving both can skip the optimum.
- **Moving neither on a tie**, causing an infinite loop.
- **Trying to sum the interior**, confusing this with Trapping Rain Water.
- **`while lo <= hi`**, which computes a zero-width container and can index oddly.
- **Recomputing the width as `hi - lo + 1`.** The width is the *gap* between the lines,
  `hi - lo`, not the number of positions.
- **Believing wider is always better** - `[2,3,4,5,18,17,6]` disproves it.
- **Giving the algorithm without the proof.** On this question the proof *is* the answer.
