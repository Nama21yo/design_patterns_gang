## Prompt as given

```
Design an autocomplete system. You are given raw data such as

  data = [['i','am','lost'], ['lost','i','am'], ['i','gain','weight']]

Train a model so that when the user types one word you recommend the next one, choosing the
highest-frequency successor.

For 'i' the successors are (am, 2) and (gain, 1), so you recommend 'am'.
```

Related: [Design Search Autocomplete System](https://leetcode.com/problems/design-search-autocomplete-system/) (LC 642).

## Clarifying questions to ask first

1. **One recommendation or top-k?** The example gives one; top-k is the obvious follow-up.
   Ask so you can size the structure correctly.
2. **How are ties broken?** Two successors with the same count - alphabetical? Most recent?
   Pick alphabetical, say so, and make it explicit in the key.
3. **Condition on one word, or on the last n words?** The prompt says one word - a bigram
   model. Say the word "bigram" and note that n-grams are the natural generalisation.
4. **Does the model update as new sentences arrive, or is training a one-off batch?** This is
   the question that opens the systems conversation. Ask it.
5. **Is this next-*word* prediction or prefix completion?** They are different problems and
   the prompt is the first one. If the interviewer drifts to "the user is typing `am...`",
   that is a trie problem - handle the pivot.
6. **Vocabulary size?** Tens of thousands of words with a long tail changes whether you can
   store every successor.
7. **Do sentence boundaries matter?** Does the last word of one sentence predict the first
   word of the next? Almost certainly not - say you will treat each sentence independently.

## Intuition

The model is a **bigram frequency table**: for each word, a count of which words followed it.

```
i     -> {am: 2, gain: 1}
am    -> {lost: 1}
lost  -> {i: 1}
gain  -> {weight: 1}
```

Prediction is then "argmax over the successor counts of this word", and the only design
question is how to make that fast.

The naive answer stores `word -> Counter(successors)` and calls `most_common(1)` at query
time, which is `O(distinct successors)` per query. That is fine, and you should write it
first.

The improvement - and the thing worth saying - is that **queries are far more frequent than
updates** in an autocomplete system, so you should move the work to write time:

> **Cache the current best successor (or the top-k heap) alongside the counter, and update
> it on each training increment. Queries become `O(1)`.**

Maintaining a top-1 on increment is genuinely `O(1)`: a count only ever goes up, so after
incrementing `w`, the new best is either the old best or `w` itself - a single comparison.
Top-k is slightly harder but the same idea with a small sorted list or heap.

That asymmetry - cheap reads bought with slightly more expensive writes - is the systems
point the interviewer was after.

## Approach

1. `train(sentence)`: for each adjacent pair `(a, b)`, increment `counts[a][b]`, then update
   `best[a]`.
2. `predict(word)`: return `best[word]`.
3. For top-k, keep `counts[a]` and answer with `heapq.nlargest(k, ...)`, or maintain a
   cached sorted top-k per word if k is fixed and queries dominate.

## Solution

```python
from collections import defaultdict, Counter


class NextWordModel:
    """Bigram next-word recommender.

    counts[a][b] = how many times b directly followed a.
    best[a]      = the current best recommendation for a, cached so predict() is O(1).
    """

    def __init__(self):
        self.counts = defaultdict(Counter)
        self.best = {}

    def train(self, sentences):
        for sentence in sentences:
            self.train_sentence(sentence)

    def train_sentence(self, words):
        """Sentences are independent: the last word of one does not predict the
        first word of the next."""
        for a, b in zip(words, words[1:]):
            self.counts[a][b] += 1
            self._update_best(a, b)

    def _update_best(self, a, b):
        """A count only ever increases, so the new best is either the old best or the
        word we just incremented. One comparison, O(1)."""
        current = self.best.get(a)
        if current is None:
            self.best[a] = b
            return
        new_count = self.counts[a][b]
        best_count = self.counts[a][current]
        # Higher count wins; ties broken alphabetically so the result is deterministic.
        if new_count > best_count or (new_count == best_count and b < current):
            self.best[a] = b

    def predict(self, word):
        """The single best next word, or None if the word was never seen."""
        return self.best.get(word)

    def predict_top_k(self, word, k):
        """Top k successors, most frequent first, ties broken alphabetically."""
        successors = self.counts.get(word)
        if not successors:
            return []
        return [w for w, _ in sorted(successors.items(), key=lambda kv: (-kv[1], kv[0]))[:k]]
```

Note the shape of `_update_best`: one condition with two plainly readable clauses. Resist
the temptation to compress it into a tuple comparison - you have to *say this line out loud*
while typing it, and "higher count wins, ties go alphabetically" should map one-to-one onto
what is on the screen.

```python
data = [["i", "am", "lost"], ["lost", "i", "am"], ["i", "gain", "weight"]]
m = NextWordModel()
m.train(data)

m.predict("i")            # 'am'
m.predict_top_k("i", 2)   # ['am', 'gain']
dict(m.counts["i"])       # {'am': 2, 'gain': 1}
m.predict("weight")       # None
```

### The pivot to prefix autocomplete

If the interviewer shifts to *"the user has typed `ga` - complete it"*, that is a different
structure: a **trie over the vocabulary**, with each node caching the top-k completions
beneath it so a query is `O(len(prefix))` rather than a subtree walk.

```python
class AutocompleteTrie:
    """Prefix completion with the top-k cached at every node, so a lookup is
    O(len(prefix)) and does not walk the subtree."""

    def __init__(self, k=3):
        self.k = k
        self.root = {"children": {}, "top": []}     # top: [(count, word)], best first

    def insert(self, word, count):
        node = self.root
        nodes = [node]
        for ch in word:
            node = node["children"].setdefault(ch, {"children": {}, "top": []})
            nodes.append(node)
        # Refresh the cached top-k on every node along the path.
        for node in nodes:
            top = [(c, w) for c, w in node["top"] if w != word]
            top.append((count, word))
            # Sort by count descending, then word ascending.
            top.sort(key=lambda cw: (-cw[0], cw[1]))
            node["top"] = top[:self.k]

    def complete(self, prefix):
        node = self.root
        for ch in prefix:
            node = node["children"].get(ch)
            if node is None:
                return []
        return [w for _, w in node["top"]]
```

```python
t = AutocompleteTrie(k=3)
for word, count in [("gain", 1), ("game", 5), ("gate", 3), ("good", 7)]:
    t.insert(word, count)
t.complete("ga")   # ['game', 'gate', 'gain']
t.complete("g")    # ['good', 'game', 'gate']
t.complete("z")    # []
```

Note the cost: `insert` now touches every node on the path and re-sorts a `k`-element list,
so it is `O(len(word) * k log k)`. Again, writes pay so reads are cheap. Say that trade out
loud - it is the same sentence as before and it is the theme of the question.

## Complexity

Let `V` be the vocabulary, `S` the total training tokens, `d` the distinct successors of a
word, `k` the requested list size.

| | Time | Space |
|---|---|---|
| `train` (whole corpus) | `O(S)` | `O(distinct bigrams)` |
| `predict` (cached best) | `O(1)` | - |
| `predict` (uncached, `most_common(1)`) | `O(d)` | - |
| `predict_top_k` (sort) | `O(d log d)` | `O(d)` |
| `predict_top_k` (heap) | `O(d log k)` | `O(k)` |
| Trie `insert` | `O(len(word) * k log k)` | `O(total characters * k)` |
| Trie `complete` | `O(len(prefix) + k)` | - |

Memory is the real constraint and worth raising: the number of distinct bigrams grows close
to linearly in corpus size for natural language, so a full table over a large corpus is
large. Pruning (drop successors seen once, keep only the top-k per word) bounds it at
`O(V * k)`.

## How to present it

This one is different from the rest of the bank: **budget more time for talking than for
typing.** The report says the interviewer spent most of the round on the system.

1. **Restate and name the model**: "this is a bigram model - for each word, a frequency
   distribution over the words that followed it."
2. **Write the table for their example by hand** before any code. `i -> {am: 2, gain: 1}`.
   It takes twenty seconds and it proves you have the right model.
3. **Ask the training/serving question**: "is this trained once over a corpus, or updated
   continuously as users type?" Then say which way each answer pushes the design.
4. **Write the simple version** - `defaultdict(Counter)` and `most_common(1)`.
5. **Then state the asymmetry**: reads massively outnumber writes, so cache the best
   successor at write time and make `predict` `O(1)`. Show the one-comparison update and
   why it is valid (counts only increase).
6. **Raise the memory question yourself** and offer pruning.
7. **Offer the extensions**: top-k, n-grams, prefix completion via a trie. Let them pick.
8. **If it drifts to full system design**, go with it: training pipeline, model store,
   serving layer, cache, update cadence. That is what they wanted.

## Follow-ups and variations

- **"Recommend the top-k successors rather than one."** `predict_top_k` above. Note
  `heapq.nlargest(k, ...)` is `O(d log k)` and better than sorting when `d` is large.
- **"Extend to n-grams (condition on the last two words)."** Key the outer dict by a
  **tuple** of the previous `n-1` words. Then raise the real issue: data sparsity. Most
  trigrams are never seen, so you need **backoff** - if the trigram is unseen, fall back to
  the bigram, then to the unigram. Naming backoff (or Katz/stupid backoff) is a strong
  signal.
- **"Prefix autocomplete instead of next-word."** The trie above.
- **"How do you update the model online as new sentences arrive?"** `train_sentence` is
  already incremental and `O(1)` per bigram. The systems answer: batch the increments,
  apply them to a write-ahead structure, and periodically snapshot; or keep counts in a
  key-value store with atomic increments and a separate job that recomputes the cached
  top-k.
- **"Recent data should count more."** Exponential decay: multiply all counts by a factor
  periodically, or store `(count, last_updated)` and decay on read. Note that decay breaks
  the "counts only increase" invariant, so the `O(1)` best-update is no longer valid and you
  need a heap.
- **"Vocabulary is huge and memory is tight."** Prune successors below a threshold, cap at
  top-k per word, or use a Count-Min Sketch for approximate counts plus a heavy-hitters heap.
- **"How would you evaluate it?"** Held-out perplexity, or top-k accuracy on a test split.
  Worth one sentence.
- **"Cold start: an unseen word."** Fall back to the global unigram distribution - the most
  common word overall. `predict` returning `None` is a bad user experience; say what you
  would show instead.
- **"Make it serve millions of users."** Shard by the conditioning word, keep the model
  read-only in memory on each server, rebuild and hot-swap periodically. This is the point
  where it becomes the system design round.

## Pitfalls

- **Training across sentence boundaries**, so the last word of one sentence predicts the
  first of the next. Use `zip(words, words[1:])` *per sentence*.
- **Non-deterministic tie-breaking.** `Counter.most_common` ties are ordered by insertion,
  which is stable but arbitrary. Make the rule explicit.
- **Rebuilding the top-k on every query** when queries dominate.
- **Recomputing `most_common` over the whole counter** to find one element, which is `O(d)`
  when a cached best is `O(1)`.
- **`counts[word]` on a `defaultdict` inside `predict`**, which silently *creates* an empty
  entry for every unknown word queried - a slow memory leak. Use `.get()` on read paths.
- **Treating it as pure coding.** The report is explicit that the conversation was the
  round. Narrate.
- **Confusing next-word prediction with prefix completion.** Ask which.
