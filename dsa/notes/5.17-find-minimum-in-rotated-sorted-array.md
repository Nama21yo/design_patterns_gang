The companion to 5.2, and in some ways the cleaner problem: **no target**, so there is no
early return and the exclusive `while lo < hi` template fits perfectly. The whole question is
choosing the right comparison point.

> Read [[5.2 Search in Rotated Sorted Array]] for the rotation structure.

## 1. Problem statement

Suppose an array of length `n` sorted in ascending order with **distinct** values is rotated
between `1` and `n` times. Given the rotated array, return the **minimum element**.

You must write an algorithm that runs in `O(log n)`.

```
nums = [3,4,5,1,2]        ->  1     rotated 3 times
nums = [4,5,6,7,0,1,2]    ->  0     rotated 4 times
nums = [11,13,15,17]      ->  11    rotated 4 times (back to sorted)
```

## 2. Clarifying questions

1. **Are the values distinct?** Yes in LC 153. With duplicates (LC 154) the worst case
   degrades to `O(n)` - ask, since it is the standard follow-up.
2. **Can the rotation be a full turn (i.e. the array is sorted)?** Yes - example 3. The
   answer is then `nums[0]`, and the code must handle it without a special case.
3. **Return the value or its index?** The value here; the index is the rotation count and is
   a trivial variant.
4. **Can the array be empty?** LeetCode guarantees at least one element. Guard it anyway.
5. **Must it be `O(log n)`?** Stated.
6. **Ascending before rotation?** Yes.

## 3. Intuition

### Compare against `hi`, not `lo`

The minimum is the **only** element smaller than its predecessor - the rotation point. The
question is how to binary search for it.

> **Compare `nums[mid]` with `nums[hi]`:**
> - if `nums[mid] > nums[hi]`, the rotation point is **strictly to the right** of `mid`, so
>   the minimum is in `(mid, hi]` -> `lo = mid + 1`.
> - otherwise `nums[mid] <= nums[hi]`, so `mid..hi` is sorted and `mid` **could be** the
>   minimum -> `hi = mid`.

Why this is sound: in a rotated ascending array, `nums[mid] > nums[hi]` can only happen if
the descent (the rotation point) lies between them. If instead `nums[mid] <= nums[hi]`, the
segment from `mid` to `hi` is in order, so nothing in it beats `nums[mid]` - and the minimum
is at `mid` or to its left.

**Comparing against `lo` instead does not work as cleanly.** With `[3,4,5,1,2]`, `nums[lo]`
is 3 and `nums[mid]` is 5, and `nums[lo] < nums[mid]` - which suggests "left half sorted", but
the minimum is on the right. You would need an extra check against `nums[hi]` anyway. **Using
`hi` as the reference is the trick**, and saying why is the substance of the answer.

### The exclusive template fits exactly

There is no "found it" moment - you never compare against a target - so:

- `while lo < hi` (not `<=`), and the loop ends with `lo == hi`, which is the answer.
- `hi = mid` (not `mid - 1`), because `mid` may be the minimum.
- `lo = mid + 1` when `mid` is definitely not the minimum.
- `mid` rounds down, so the range always shrinks.

This is the textbook use of the 5.0 template, and the sorted case falls out for free: if the
array is not rotated, `nums[mid] <= nums[hi]` always holds, `hi` marches down to 0, and the
answer is `nums[0]`.

## 4. Approach

1. `lo, hi = 0, n - 1`.
2. While `lo < hi`:
   - `mid = (lo + hi) // 2`
   - if `nums[mid] > nums[hi]`: `lo = mid + 1`
   - else: `hi = mid`
3. Return `nums[lo]`.

## 5. Solution

```python
def find_min(nums):
    """Minimum of a rotated sorted array of distinct values.

    Compare against nums[hi], not nums[lo]: nums[mid] > nums[hi] can only happen when
    the rotation point lies strictly between them, so the minimum is to the right.
    Otherwise mid..hi is in order and mid itself is still a candidate.
    """
    if not nums:
        raise ValueError("empty array has no minimum")

    lo, hi = 0, len(nums) - 1

    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:
            lo = mid + 1        # the descent is to the right; mid cannot be the minimum
        else:
            hi = mid            # mid..hi is sorted, so mid is still a candidate

    return nums[lo]
```

```python
find_min([3, 4, 5, 1, 2])           # 1
find_min([4, 5, 6, 7, 0, 1, 2])     # 0
find_min([11, 13, 15, 17])          # 11
find_min([1])                       # 1
find_min([2, 1])                    # 1
find_min([1, 2])                    # 1
find_min([3, 1, 2])                 # 1
find_min([2, 3, 1])                 # 1
find_min([5, 1, 2, 3, 4])           # 1
find_min([])                        # ValueError
```

The three two- and three-element cases are the test suite: `[2,1]` and `[1,2]` cover both
rotations of a pair, and `[3,1,2]` versus `[2,3,1]` put the minimum at index 1 and 2
respectively. They exercise every branch in four seconds.

`[11,13,15,17]` (un-rotated) must return `nums[0]` without a special case - worth pointing
at, because it is what the `else: hi = mid` branch is quietly doing.

### Returning the rotation count instead

```python
def rotation_count(nums):
    """How many times the array was rotated - the index of the minimum."""
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:
            lo = mid + 1
        else:
            hi = mid
    return lo


rotation_count([3, 4, 5, 1, 2])         # 3
rotation_count([4, 5, 6, 7, 0, 1, 2])   # 4
rotation_count([11, 13, 15, 17])        # 0
rotation_count([2, 1])                  # 1
```

Same function, returning the index. This is the helper 5.2 uses in its pivot-first
alternative, so writing it once serves both problems - say so if you have done 5.2.

### With duplicates (LC 154)

```python
def find_min_with_duplicates(nums):
    """LC 154: values may repeat, so the worst case is O(n).

    When nums[mid] == nums[hi] we cannot tell which side holds the rotation, and the
    only safe move is to shrink hi by one - discarding a duplicate of a value we still
    have at mid, so the minimum is never lost.
    """
    lo, hi = 0, len(nums) - 1

    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:
            lo = mid + 1
        elif nums[mid] < nums[hi]:
            hi = mid
        else:
            hi -= 1             # ambiguous: nums[hi] is duplicated at mid, so drop it

    return nums[lo]


find_min_with_duplicates([1, 3, 5])         # 1
find_min_with_duplicates([2, 2, 2, 0, 1])   # 0
find_min_with_duplicates([3, 3, 1, 3])      # 1
find_min_with_duplicates([1, 1, 1, 1])      # 1
find_min_with_duplicates([10, 1, 10, 10])   # 1
```

**Be able to explain why `hi -= 1` is safe**, since it looks like it could skip the answer:
when `nums[mid] == nums[hi]`, the value at `hi` also exists at `mid`, which is still inside
the range. So discarding index `hi` cannot lose the minimum *value*. That argument is the
point of the follow-up.

`[1,1,1,1]` and `[10,1,10,10]` are the worst cases - every step is ambiguous and the search
degrades to a linear scan.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan / `min()` | `O(n)` | `O(1)` |
| **Binary search, distinct** | **`O(log n)`** | **`O(1)`** |
| With duplicates (LC 154) | `O(log n)` average, **`O(n)` worst** | `O(1)` |

Each iteration halves the range in the distinct case. Iterative, so constant space.

## 7. How to present it

1. **Restate**, and **confirm the values are distinct** - then say why: *"with duplicates the
   worst case becomes linear, so I want to know which version this is."*
2. **Characterise the target**: *"the minimum is the one element smaller than its
   predecessor - the rotation point."*
3. **State the comparison rule and justify it**: *"I compare `nums[mid]` with `nums[hi]`. If
   `nums[mid]` is bigger, the descent must be between them, so the minimum is strictly to the
   right. Otherwise `mid..hi` is in order and `mid` is still a candidate."*
4. **Say why you compare against `hi` rather than `lo`.** Give `[3,4,5,1,2]`: `nums[lo] <
   nums[mid]` there, which tells you nothing useful. **This is the scoring moment.**
5. **Note the template fits exactly** because there is no target and no early return, so
   `while lo < hi` with `hi = mid` is natural.
6. **Write it**, then point out that the un-rotated case needs no special handling.
7. **Test** `[2,1]`, `[1,2]`, `[3,1,2]`, `[2,3,1]`, and the single element.
8. **Close**: `O(log n)`, `O(1)` - and volunteer the duplicates variant with the `hi -= 1`
   move and why it is safe.

## 8. Follow-ups and variations

- **"What if there are duplicates?"** LC 154, shown above. **The most likely follow-up** -
  have the safety argument for `hi -= 1` ready.
- **"How many times was the array rotated?"** `rotation_count` - the index of the minimum.
- **"Find the maximum instead."** It is the element just before the minimum:
  `nums[(index_of_min - 1) % n]`. Or mirror the comparisons.
- **"Search for a target in the rotated array."** That is 5.2 - and you can now do it as
  "find the pivot, then binary search the right segment".
- **"What if it were rotated right instead of left?"** A right rotation by `k` is a left
  rotation by `n - k`, so nothing changes.
- **"What if it was sorted descending before rotation?"** Mirror all comparisons, or negate
  and reuse.
- **"Is the array rotated at all?"** Check `nums[0] <= nums[-1]` - `O(1)`. Nice contrast with
  1.8, which asks the same thing about an arbitrary array and needs `O(n)`.
- **"Find the k-th smallest in a rotated array."** Find the pivot, then index arithmetic
  modulo `n`.

## 9. Pitfalls

- **Comparing `nums[mid]` with `nums[lo]`** and building the logic around that. It needs an
  extra case and is the usual source of wrong answers here.
- **Using `while lo <= hi` with `hi = mid`** - infinite loop.
- **Using `hi = mid - 1`**, which can skip the minimum when `mid` is the answer.
- **Returning `nums[mid]` from inside the loop** rather than `nums[lo]` at the end.
- **Adding a special case for the un-rotated array.** None is needed, and adding one usually
  introduces a bug.
- **In the duplicates version, using `lo += 1` instead of `hi -= 1`** - unsafe, because
  `nums[lo]` might be the unique minimum. The `hi` side is the safe one precisely because
  `nums[hi]` is known to be duplicated at `mid`.
- **Assuming `O(log n)` with duplicates.**
- **Using `min(nums)`** - correct but `O(n)`, and the problem demands logarithmic.
