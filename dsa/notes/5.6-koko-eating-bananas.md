**Difficulty:** Medium | **LeetCode #875**
**Bloomberg frequency:** 50% at six months.

**The cleanest example of "binary search on the answer" in the course.** There is no sorted
array anywhere in the problem, and yet it is a binary search. If you take one technique from
Part 5, take this one - 5.12 and 5.14 are the same idea in different clothing.

## 1. Problem statement

Koko has `n` piles of bananas; `piles[i]` is the number in the `i`-th pile. The guards return
in `h` hours.

Koko chooses an eating speed `k` (bananas per hour). Each hour she picks one pile and eats
`k` bananas from it; **if the pile has fewer than `k` left, she eats it all and does not eat
again that hour**.

Return the **minimum integer `k`** such that she can finish all the piles within `h` hours.

```
piles = [3,6,7,11],       h = 8   ->  4
piles = [30,11,23,4,20],  h = 5   ->  30
piles = [30,11,23,4,20],  h = 6   ->  23
```

## 2. Clarifying questions

1. **Can she eat from more than one pile in an hour?** **No** - and that is what makes each
   pile cost `ceil(pile / k)` hours independently. This is the single most important detail;
   say it back.
2. **Is `h` at least the number of piles?** Yes, guaranteed - otherwise it would be
   impossible at any speed.
3. **Must `k` be an integer?** Yes.
4. **Return the speed or the time?** The **speed**.
5. **Pile sizes?** Up to 10^9, and up to 10^4 piles. So `k` can be up to 10^9 and a linear
   scan over `k` is hopeless - which is the hint that the answer itself is the search space.
6. **Is the answer guaranteed to exist?** Yes - `k = max(piles)` always finishes in exactly
   `n` hours, and `n <= h`.

## 3. Intuition

### Why this is a search problem at all

The naive approach is to try `k = 1, 2, 3, ...` until one works. That is `O(max(piles) * n)`
and far too slow. But notice:

> **If speed `k` finishes in time, then so does any speed greater than `k`. And if `k` is too
> slow, every speed below it is also too slow.**

So the predicate `feasible(k) = "can Koko finish at speed k within h hours?"` is
**monotone**: `F F F F T T T`. That is exactly the precondition for binary search - and the
thing being searched is not an array index but **the answer itself**.

**Say this out loud.** "Feasibility is monotone in the speed, so I can binary search on the
answer" is the sentence that gets you the question.

### The feasibility check

At speed `k`, a pile of size `p` takes `ceil(p / k)` hours - because she cannot move to
another pile mid-hour, so a partial pile still consumes a whole hour.

```
hours(k) = sum(ceil(p / k) for p in piles)
feasible(k) = hours(k) <= h
```

Use integer arithmetic: `ceil(p / k)` is `(p + k - 1) // k`, or in Python `-(-p // k)`.
Avoid `math.ceil(p / k)` with floats - with `p` up to 10^9 the float division is fine here,
but integer arithmetic is exact and is the habit to keep.

### The search range

This is the part people get wrong, so reason it out rather than guessing:

- **`lo = 1`.** Speed 0 makes no progress, so 1 is the smallest meaningful speed.
- **`hi = max(piles)`.** At this speed every pile takes exactly one hour, so the total is `n`
  hours - and `n <= h` is guaranteed. Any larger speed gives the same `n` hours, so nothing
  above `max(piles)` can ever be needed.

Justifying `hi = max(piles)` is a good moment: *"anything faster than the biggest pile is
wasted, because she still can't start a second pile in the same hour."*

## 4. Approach

1. `lo, hi = 1, max(piles)`.
2. While `lo < hi`:
   - `mid = (lo + hi) // 2`
   - if `feasible(mid)`: `hi = mid` (mid might be the answer)
   - else: `lo = mid + 1`
3. Return `lo`.

The lower-bound template from 5.0, with `feasible` in place of an array comparison.

## 5. Solution

```python
def min_eating_speed(piles, h):
    """Smallest integer speed k at which all piles can be eaten within h hours.

    Koko cannot switch piles mid-hour, so a pile of size p costs ceil(p / k) hours.
    Feasibility is monotone in k - a faster speed never hurts - so the answer can be
    binary searched directly, with no sorted array involved.
    """
    def hours_needed(k):
        # ceil(p / k) with integer arithmetic; a partial pile still costs a full hour.
        return sum((p + k - 1) // k for p in piles)

    # lo = 1: speed 0 makes no progress.
    # hi = max(piles): at that speed every pile takes exactly one hour, which is the
    # fewest hours achievable, so nothing faster is ever needed.
    lo, hi = 1, max(piles)

    while lo < hi:
        mid = (lo + hi) // 2
        if hours_needed(mid) <= h:
            hi = mid                # fast enough - but maybe slower would do
        else:
            lo = mid + 1            # too slow - discard mid and everything below

    return lo
```

```python
min_eating_speed([3, 6, 7, 11], 8)          # 4
min_eating_speed([30, 11, 23, 4, 20], 5)    # 30
min_eating_speed([30, 11, 23, 4, 20], 6)    # 23
min_eating_speed([1], 1)                    # 1
min_eating_speed([1000000000], 2)           # 500000000
min_eating_speed([312884470], 968709470)    # 1
min_eating_speed([3, 6, 7, 11], 4)          # 11
min_eating_speed([1, 1, 1, 1], 4)           # 1
min_eating_speed([100, 100], 2)             # 100
```

Three to narrate:

- **`[30,11,23,4,20]` with `h = 5` -> 30.** Exactly as many hours as piles, so she must
  finish each pile in one hour, which forces `k = max(piles)`. It is the upper-boundary case
  and it validates your choice of `hi`.
- **`[1000000000]` with `h = 2` -> 500000000.** One huge pile in two hours. It shows why a
  linear scan over `k` is impossible and why the range must go up to `max(piles)`.
- **`[312884470]` with a huge `h` -> 1.** The lower boundary: with enough time, speed 1 is
  enough. It validates `lo = 1`.

### Tracing the first example

`piles = [3,6,7,11]`, `h = 8`, so `lo = 1`, `hi = 11`.

| k | hours = ceil(3/k)+ceil(6/k)+ceil(7/k)+ceil(11/k) | <= 8? |
|---|---|---|
| 6 | 1 + 1 + 2 + 2 = 6 | yes -> `hi = 6` |
| 3 | 1 + 2 + 3 + 4 = 10 | no -> `lo = 4` |
| 5 | 1 + 2 + 2 + 3 = 8 | yes -> `hi = 5` |
| 4 | 1 + 2 + 2 + 3 = 8 | yes -> `hi = 4` |

`lo == hi == 4`. Answer **4**. Working two or three rows of that table on the board is the
clearest way to show the search working.

### The linear scan, to state and reject

```python
def min_eating_speed_linear(piles, h):
    """O(max(piles) * n). Correct, hopeless at the real constraints - but it is the
    baseline that motivates the search, and a useful validation oracle on small inputs."""
    for k in range(1, max(piles) + 1):
        if sum((p + k - 1) // k for p in piles) <= h:
            return k
    return max(piles)


min_eating_speed_linear([3, 6, 7, 11], 8)           # 4
min_eating_speed_linear([30, 11, 23, 4, 20], 6)     # 23
min_eating_speed_linear([1, 1, 1, 1], 4)            # 1
```

## 6. Complexity

Let `n` be the number of piles and `M = max(piles)`.

| | Time | Space |
|---|---|---|
| Linear scan over `k` | `O(M * n)` | `O(1)` |
| **Binary search on the answer** | **`O(n log M)`** | **`O(1)`** |

`log2(10^9)` is about 30, so roughly 30 feasibility checks, each `O(n)`. That is the shape to
state: **`O(n log M)` - log iterations, each doing a linear check.**

Note the `log` is over the **value range**, not the array length. That is characteristic of
answer-search problems and worth calling out, because it is the first time in Part 5 that
`log n` does not refer to the input size.

## 7. How to present it

1. **Restate**, and **confirm the one-pile-per-hour rule.** *"So if a pile has fewer than `k`
   bananas left, she finishes it and waits - she can't start the next pile in the same
   hour?"* That detail is what makes the cost `ceil(p/k)`, and getting it confirmed early is
   essential.
2. **Note the scale**: piles up to 10^9 means trying every `k` is impossible.
3. **State the monotonicity** - this is the insight and the whole question: *"If speed `k`
   works, any faster speed also works. So feasibility is monotone in `k`, which means I can
   binary search on the answer rather than on an array."*
4. **Define the predicate explicitly**: `feasible(k) = sum(ceil(p/k)) <= h`.
5. **Justify the range**: `lo = 1` because slower is meaningless; `hi = max(piles)` because
   at that speed every pile takes one hour and nothing faster helps.
6. **Announce** the lower-bound template, then write it.
7. **Show the integer ceiling** `(p + k - 1) // k` and say you are avoiding floats.
8. **Trace two rows** of the table above.
9. **Test the boundaries**: `h == len(piles)` (forces `max`), and a huge `h` (gives 1).
10. **Close**: `O(n log M)`, `O(1)` space - and note the log is over the **value range**.

## 8. Follow-ups and variations

- **"Capacity To Ship Packages Within D Days"** (LC 1011, at 5.12). Identical structure: the
  answer is a capacity, feasibility is "can we ship in D days", and the range is
  `[max(weight), sum(weights)]`. **If you understand Koko, you understand that one.**
- **"Minimum Number of Days to Make m Bouquets"** (LC 1482, at 5.14). Same again, searching
  over days.
- **"Split Array Largest Sum"** (LC 410) - minimise the maximum subarray sum over `k` splits.
  The canonical "minimise the maximum" problem, same technique.
- **"What if `k` could be a real number?"** Binary search on floats with a tolerance, or note
  that the answer is `max over piles of (p / hours allocated)`, which becomes an optimisation
  problem. Worth a sentence.
- **"What if she can switch piles mid-hour?"** Then the total time is just
  `ceil(sum(piles) / k)` and the answer is a direct formula - no search needed. **A great
  question to be asked**, because it isolates exactly which rule created the problem.
- **"Return the actual schedule."** Once `k` is known, the assignment is forced.
- **"Multiple monkeys eating in parallel."** Now it is a scheduling / bin-packing problem and
  the simple monotone check breaks down.
- **"Why not ternary search?"** Because the objective is not unimodal - it is a monotone
  boolean, which is binary search's exact shape.

## 9. Pitfalls

- **Not realising the answer itself is the search space**, and looking for something to sort.
- **Computing the cost as `sum(piles) / k`**, which assumes she can switch piles mid-hour.
  That is the trap the problem is built around.
- **Using `math.ceil(p / k)` with floats** on values near 10^9 - exact here, but integer
  arithmetic is the correct habit and avoids any argument.
- **`hi = sum(piles)`** instead of `max(piles)`. Correct but wasteful; more importantly, it
  shows you did not reason about the bound.
- **`lo = 0`**, which makes `hours_needed(0)` divide by zero.
- **Mixing binary search templates** - `while lo <= hi` with `hi = mid` is an infinite loop.
- **Returning `mid` from inside the loop** rather than `lo` at the end, which can return a
  feasible but non-minimal speed.
- **Claiming `O(log n)`** where `n` is the number of piles. It is `O(n log M)`.
