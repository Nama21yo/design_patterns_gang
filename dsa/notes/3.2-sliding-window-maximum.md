**Link:** https://leetcode.com/problems/sliding-window-maximum
**Difficulty:** Hard | **LeetCode #239**
**Bloomberg frequency:** 62% in the **30-day** window.

The **monotonic deque**. This is the hardest question in Part 3 and the most mechanical once
you have the idea: the whole difficulty is realising that a plain max or a heap is not good
enough, and then trusting the deque invariant.

## 1. Problem statement

You are given an array `nums` and a window of size `k` sliding from the very left to the very
right. You can only see the `k` numbers in the window; each time it moves right by one
position. Return an array of the **maximum** of each window.

```
nums = [1,3,-1,-3,5,3,6,7], k = 3  ->  [3,3,5,5,6,7]

  [1  3  -1] -3  5  3  6  7     ->  3
   1 [3  -1  -3] 5  3  6  7     ->  3
   1  3 [-1  -3  5] 3  6  7     ->  5
   1  3  -1 [-3  5  3] 6  7     ->  5
   1  3  -1  -3 [5  3  6] 7     ->  6
   1  3  -1  -3  5 [3  6  7]    ->  7
```

## 2. Clarifying questions

1. **Is `k` guaranteed `<= len(nums)`?** LeetCode guarantees `1 <= k <= n`. Ask - otherwise
   you need a guard.
2. **Return maxima only, or also the indices?** Maxima.
3. **How many windows are there?** `n - k + 1`. Getting that count right is the first
   off-by-one.
4. **Can values be negative?** Yes - the example has them. That rules out using `0` as a
   sentinel initial maximum.
5. **Are duplicates possible?** Yes, and they affect whether the deque comparison is `<` or
   `<=`. Either works here; see below.
6. **Size limits?** Up to 10^5, so `O(n*k)` will time out.

## 3. Intuition

### Why the obvious approaches fail

- **Recompute `max` per window**: `O(n*k)`. Correct, too slow, but *say it* - it is your
  baseline.
- **Keep a running maximum**: fails on removal. When the element leaving the window *is* the
  current maximum, you have no idea what the new maximum is, so you must rescan. This failure
  is worth stating explicitly, because it is what motivates everything else.
- **Max-heap of the window**: `heap[0]` gives the max in `O(1)`, but **removing an arbitrary
  element** (the one sliding out) is `O(n)` in a heap. You can patch it with **lazy
  deletion** - push `(-value, index)` and discard stale entries from the top when they fall
  outside the window - giving `O(n log n)`. That is a perfectly respectable answer and worth
  offering.

### The deque idea

The key observation:

> **If `nums[i] <= nums[j]` and `i < j`, then `nums[i]` can never be the maximum of any
> window that contains `j`. It is both smaller and older, so it is dominated forever.**

So maintain a **deque of indices whose values are strictly decreasing**. Then:
- the **front** is always the index of the window's maximum;
- the **back** is where new candidates enter, after evicting everything they dominate.

Per element:
1. Pop from the **back** while the incoming value is `>=` the value at the back - those can
   never win again.
2. Push the incoming index at the back.
3. Pop from the **front** if it has slid out of the window (`front <= i - k`).
4. Once `i >= k - 1`, the front is this window's maximum.

The deque holds *candidates*: the current maximum, then the best candidate after it expires,
and so on. That framing - "a queue of future maxima in waiting" - is the clearest way to
explain it.

**Why it is `O(n)`**: each index is pushed exactly once and popped at most once, so the total
work across the whole run is `O(n)` - even though a single iteration can pop many elements.
Same amortised argument as monotonic stacks in Part 4.

### Store indices, not values

You need the index to know when an element leaves the window. Storing values alone loses that
information. This is the second most common bug.

## 4. Approach

1. `dq = deque()` holding indices, values strictly decreasing front to back.
2. For each index `i`:
   - while `dq` and `nums[dq[-1]] <= nums[i]`: `dq.pop()`
   - `dq.append(i)`
   - if `dq[0] <= i - k`: `dq.popleft()`
   - if `i >= k - 1`: append `nums[dq[0]]` to the output.
3. Return the output.

## 5. Solution

```python
from collections import deque


def max_sliding_window(nums, k):
    """Maximum of every window of size k.

    `dq` holds INDICES whose values are strictly decreasing. An element that is both
    smaller and older than a newcomer can never be a future maximum, so it is evicted.
    The front is therefore always the current window's maximum.
    """
    dq = deque()
    out = []

    for i, x in enumerate(nums):
        # Evict from the back: anything <= the newcomer is dominated forever.
        while dq and nums[dq[-1]] <= x:
            dq.pop()
        dq.append(i)

        # Evict from the front if it has slid out of the window.
        if dq[0] <= i - k:
            dq.popleft()

        # The first complete window ends at index k - 1.
        if i >= k - 1:
            out.append(nums[dq[0]])

    return out
```

```python
max_sliding_window([1, 3, -1, -3, 5, 3, 6, 7], 3)   # [3, 3, 5, 5, 6, 7]
max_sliding_window([1], 1)                          # [1]
max_sliding_window([1, -1], 1)                      # [1, -1]
max_sliding_window([9, 11], 2)                      # [11]
max_sliding_window([4, -2], 2)                      # [4]
max_sliding_window([1, 3, 1, 2, 0, 5], 3)           # [3, 3, 2, 5]
max_sliding_window([7, 2, 4], 2)                    # [7, 4]
max_sliding_window([-7, -8, 7, 5, 7, 1, 6, 0], 4)   # [7, 7, 7, 7, 7]
max_sliding_window([1, 1, 1, 1], 2)                 # [1, 1, 1]
max_sliding_window([], 1)                           # []
```

Trace `[1,3,-1,-3,5,3,6,7]` with `k = 3` for the first four steps - this is what to put on
the board:

| i | x | deque (indices) | values | window max |
|---|---|---|---|---|
| 0 | 1 | `[0]` | `[1]` | - (window incomplete) |
| 1 | 3 | `[1]` | `[3]` | - (1 was evicted: smaller and older) |
| 2 | -1 | `[1,2]` | `[3,-1]` | **3** |
| 3 | -3 | `[1,2,3]` | `[3,-1,-3]` | **3** |
| 4 | 5 | `[4]` | `[5]` | **5** (5 evicted everything) |

Step 4 is the one to highlight: `5` arrives and evicts `-3`, `-1` **and** `3`, because all
are smaller and older. One iteration did three pops - and that is exactly why the amortised
argument is needed.

`[1,1,1,1]` with `k=2` is the duplicates test. With `<=` in the eviction, equal values evict
each other and the deque stays size 1; with `<` they accumulate. Both produce the right
answer, because any of the equal maxima is a valid answer and the front one is always still
in the window. Worth mentioning if asked.

### The heap version with lazy deletion

```python
import heapq


def max_sliding_window_heap(nums, k):
    """O(n log n). A max-heap of (-value, index); stale entries are discarded lazily
    from the top, because removing from the middle of a heap is O(n)."""
    heap = []
    out = []
    for i, x in enumerate(nums):
        heapq.heappush(heap, (-x, i))
        # Discard anything at the top that has slid out of the window.
        while heap[0][1] <= i - k:
            heapq.heappop(heap)
        if i >= k - 1:
            out.append(-heap[0][0])
    return out


max_sliding_window_heap([1, 3, -1, -3, 5, 3, 6, 7], 3)  # [3, 3, 5, 5, 6, 7]
max_sliding_window_heap([1, 3, 1, 2, 0, 5], 3)          # [3, 3, 2, 5]
max_sliding_window_heap([1, 1, 1, 1], 2)                # [1, 1, 1]
```

Offer this if you are stuck on the deque, or as a stepping stone. It is much easier to derive
under pressure, and `O(n log n)` on `n = 10^5` still passes. Note the heap can grow to `O(n)`
because stale entries are only removed when they reach the top.

### The brute force

```python
def max_sliding_window_brute(nums, k):
    """O(n*k). State it, give the bound, then improve."""
    return [max(nums[i:i + k]) for i in range(len(nums) - k + 1)]


max_sliding_window_brute([1, 3, -1, -3, 5, 3, 6, 7], 3)     # [3, 3, 5, 5, 6, 7]
max_sliding_window_brute([1], 1)                            # [1]
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n * k)` | `O(1)` extra |
| Heap with lazy deletion | `O(n log n)` | `O(n)` worst case |
| **Monotonic deque** | **`O(n)`** | `O(k)` |

The deque holds at most `k` indices (anything older has slid out), so space is `O(k)`.
Time is `O(n)` amortised: `n` pushes and at most `n` pops in total.

`O(n)` is optimal - every element must be examined.

## 7. How to present it

1. **Restate**, and confirm the output length is `n - k + 1`.
2. **Give the brute force and its bound**, then say what is wasted: "Consecutive windows
   overlap in `k-1` elements, so I'm recomputing almost the same maximum every time."
3. **Explain why a running maximum fails**: *"the problem is removal - when the element
   leaving the window is the current maximum, I have no idea what the new one is."* This
   sentence is what justifies everything that follows, so do not skip it.
4. **Offer the heap version** as the first improvement, with lazy deletion, `O(n log n)`.
   Many interviewers are happy here, and it gives you a working answer in hand.
5. **Then give the deque insight**: *"If an element is both smaller and older than a
   newcomer, it can never be the maximum of any future window - so I can throw it away
   immediately. That leaves a decreasing sequence of candidates, and the front is always the
   answer."*
6. **Stress that you store indices**, not values, so you know when things expire.
7. **Write it**, narrating the three steps: evict from the back, append, evict from the
   front.
8. **Trace the first five steps** with the table above, especially `i = 4` where `5` clears
   the deque.
9. **Give the amortised argument**: each index is pushed once and popped once, so `O(n)`.
10. **Close**: `O(n)` time, `O(k)` space.

## 8. Follow-ups and variations

- **"Sliding window minimum."** Flip the comparison to `>=`. Or negate the values and reuse.
- **"Both the min and the max."** Two deques. This is the basis of LC 1438, *Longest
  Continuous Subarray With Absolute Diff <= Limit*, which is a genuinely good follow-up.
- **"Why not a heap?"** `O(n log n)` and `O(n)` space because of stale entries. Fine but not
  optimal.
- **"What if `k` changes between queries?"** The deque is built for a fixed `k`. For
  arbitrary range-maximum queries use a **sparse table** (`O(n log n)` build, `O(1)` query)
  or a segment tree (`O(log n)` query, supports updates). Naming those is the right answer.
- **"What if elements can be updated?"** Segment tree or a Fenwick tree for maxima; the deque
  assumes a one-pass stream.
- **"Constant-time queue with max"** - the classic design question. Two stacks each carrying
  a running maximum simulate a queue with `O(1)` amortised max. Related to 23.9's Min Stack
  follow-up.
- **"Return the indices of the maxima."** `dq[0]` directly.
- **"First negative number in every window."** Same deque skeleton with a different eviction
  rule - a good check that you understood the structure rather than memorised it.
- **"Maximum of all subarrays of every size."** Different problem - monotonic stack, related
  to *Sum of Subarray Minimums* (LC 907).

## 9. Pitfalls

- **Storing values instead of indices**, so you cannot tell when an element expires.
- **Evicting from the front before appending** - order matters; append first, then check the
  front against `i - k`.
- **Using `dq[0] < i - k`** instead of `<=`, keeping an element one step too long.
- **Starting output collection at `i >= k`** instead of `i >= k - 1`, losing the first
  window.
- **Popping the front unconditionally**, destroying the maximum.
- **Using a plain list with `pop(0)`** - that is `O(n)` per operation and makes the whole
  thing quadratic. Use `collections.deque`.
- **Initialising a running max to `0`** when negatives are possible.
- **Claiming the deque version is `O(n*k)`** because of the inner `while`. Give the amortised
  argument.
