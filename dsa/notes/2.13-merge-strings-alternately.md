**Link:** https://leetcode.com/problems/merge-strings-alternately
**Difficulty:** Easy | **LeetCode #1768**
**Bloomberg frequency:** 38% at three months.

The simplest two-sequence question on the list. Its value is entirely in **how cleanly you
handle the leftover tail** and whether you build the string efficiently - which is a Python
detail an interviewer may well probe.

## 1. Problem statement

You are given two strings `word1` and `word2`. Merge them by adding letters in **alternating
order**, starting with `word1`. If one string is longer, append the additional letters onto
the end of the merged string.

```
word1 = "abc",  word2 = "pqr"   ->  "apbqcr"
word1 = "ab",   word2 = "pqrs"  ->  "apbqrs"
word1 = "abcd", word2 = "pq"    ->  "apbqcd"
```

## 2. Clarifying questions

1. **Which string starts?** `word1`, always.
2. **What if they are different lengths?** The leftover tail of the longer one is appended
   verbatim. Both directions occur in the examples.
3. **Can either be empty?** LeetCode says length >= 1, but ask - the natural solution handles
   empty strings with no extra code, which is worth pointing out.
4. **Return a string or a list of characters?** A string.
5. **Length limits?** Up to 100 each, so efficiency is not a real constraint - but build it
   properly anyway, because the interviewer may ask why.

## 3. Intuition

Two pointers, one per string, advancing together while both have characters left; then
append whatever remains of the longer one.

> **Two-pointer merge with an asymmetric tail, exactly like 2.6 - except here *both* tails
> are possible, so both must be handled.**

The real content is Python-specific: **do not build the result with `+=` in a loop.** Strings
are immutable, so each `+=` allocates a new string and copies everything so far, making the
whole loop `O(n^2)`. Collect the characters in a list and `"".join` once, which is `O(n)`.

That is genuinely worth saying aloud. On a 100-character input nobody notices, but the
interviewer is checking whether you know.

### Three ways to write it

All `O(n)`; pick one and be able to explain the others.

- **Explicit two pointers.** Most verbose, clearest about the tail handling, and the one to
  write if asked to avoid library helpers.
- **`zip` plus slices.** `zip` stops at the shorter string, so the tails are the slices past
  that point. Short and idiomatic.
- **`itertools.zip_longest`** with `fillvalue=""`. Handles the tails automatically, but only
  correct because the fill value contributes nothing to the join.

## 4. Approach

1. `parts = []`, `i = j = 0`.
2. While `i < len(word1)` and `j < len(word2)`: append `word1[i]`, `word2[j]`; advance both.
3. Append the remainder of whichever string has one.
4. `"".join(parts)`.

## 5. Solution

```python
def merge_alternately(word1, word2):
    """Interleave two strings, starting with word1, then append the longer tail.

    Characters are collected in a list and joined once: building with += inside the
    loop would be O(n^2), because Python strings are immutable and each concatenation
    copies everything accumulated so far.
    """
    parts = []
    i = j = 0

    while i < len(word1) and j < len(word2):
        parts.append(word1[i])
        parts.append(word2[j])
        i += 1
        j += 1

    # Exactly one of these is non-empty (or both are, if the strings were equal length).
    parts.append(word1[i:])
    parts.append(word2[j:])

    return "".join(parts)
```

```python
merge_alternately("abc", "pqr")     # 'apbqcr'
merge_alternately("ab", "pqrs")     # 'apbqrs'
merge_alternately("abcd", "pq")     # 'apbqcd'
merge_alternately("", "xyz")        # 'xyz'
merge_alternately("xyz", "")        # 'xyz'
merge_alternately("", "")           # ''
merge_alternately("a", "b")         # 'ab'
```

Appending both slices unconditionally is deliberate - one of them is always empty, and an
empty slice costs nothing in the join. It avoids an `if`, and it also means the empty-input
cases need no special handling at all. Say that; a branch you can prove is unnecessary is
better than a branch you have to test.

### The idiomatic versions

```python
def merge_alternately_zip(word1, word2):
    """zip stops at the shorter string; the tails are whatever lies past that point."""
    shorter = min(len(word1), len(word2))
    merged = "".join(a + b for a, b in zip(word1, word2))
    return merged + word1[shorter:] + word2[shorter:]


merge_alternately_zip("abc", "pqr")     # 'apbqcr'
merge_alternately_zip("ab", "pqrs")     # 'apbqrs'
merge_alternately_zip("abcd", "pq")     # 'apbqcd'
merge_alternately_zip("", "")           # ''
```

```python
from itertools import zip_longest


def merge_alternately_zip_longest(word1, word2):
    """zip_longest pads the shorter string with '', which contributes nothing
    to the join - so the tails are handled for free."""
    return "".join(a + b for a, b in zip_longest(word1, word2, fillvalue=""))


merge_alternately_zip_longest("abc", "pqr")     # 'apbqcr'
merge_alternately_zip_longest("ab", "pqrs")     # 'apbqrs'
merge_alternately_zip_longest("abcd", "pq")     # 'apbqcd'
merge_alternately_zip_longest("", "xyz")        # 'xyz'
```

The `zip_longest` version is the shortest correct solution. Offer it after the explicit one,
and be ready to explain *why* it works - `fillvalue=""` rather than `None`, because `None`
would raise on concatenation.

### The version to avoid

```python
def merge_alternately_quadratic(word1, word2):
    """Correct, but O(n^2): each += allocates a new string and copies the accumulation."""
    result = ""
    i = j = 0
    while i < len(word1) and j < len(word2):
        result += word1[i] + word2[j]
        i += 1
        j += 1
    result += word1[i:] + word2[j:]
    return result


merge_alternately_quadratic("abc", "pqr")   # 'apbqcr'
```

It produces the right answer, which is why it is worth naming explicitly as the thing not to
do rather than assuming the interviewer will notice.

## 6. Complexity

Let `n = len(word1)`, `m = len(word2)`.

| | Time | Space |
|---|---|---|
| `+=` in a loop | `O((n+m)^2)` | `O(n+m)` |
| **List + join** | **`O(n + m)`** | `O(n + m)` output |
| `zip` / `zip_longest` | `O(n + m)` | `O(n + m)` |

Every character is copied a constant number of times. The output is `O(n+m)` and unavoidable,
so auxiliary space is `O(1)` beyond it if you consider the list a staging buffer for the
output.

**CPython caveat worth knowing**: CPython has an optimisation that sometimes makes `s += t`
amortised `O(1)` when `s` has no other references, so the quadratic version can *appear*
fast. It is an implementation detail, not a language guarantee, and it does not hold for
other interpreters. Mention this only if pressed - it shows depth, but leading with it
muddies the point.

## 7. How to present it

This is a five-minute question. Solve it cleanly and use the remaining time for the details.

1. **Restate**, confirm `word1` goes first and the longer tail is appended.
2. **Announce**: "Two pointers, append a pair per step, then append whichever tail remains."
3. **Write it**, and as you create `parts = []` say: *"I'm collecting into a list and joining
   at the end - building a string with `+=` in a loop is `O(n^2)` in Python because strings
   are immutable."* That sentence is the main scoring opportunity here.
4. **Point out that both tail slices are appended unconditionally**, because one is always
   empty - no branch needed, and the empty-input cases fall out for free.
5. **Test** all three given examples plus both empty cases.
6. **Offer the idiomatic version** - "`zip_longest` with `fillvalue=''` does the tails
   automatically" - and explain why the fill value must be `""` and not `None`.
7. **Close**: `O(n+m)` time and space.

## 8. Follow-ups and variations

- **"Merge k strings alternately."** Round-robin over a list of iterators, dropping each as
  it is exhausted. `itertools.chain.from_iterable(zip_longest(*words, fillvalue=""))` is the
  one-liner; be ready to write the loop version.
- **"Alternate in blocks of `k` characters rather than one."** Advance both pointers by `k`
  and append slices - a small generalisation that tests whether you wrote it with indices or
  hard-coded single characters.
- **"Start with the longer string."** Compare lengths first and swap, or parameterise which
  one leads.
- **"Do it in place on a mutable buffer."** In C you would write into a preallocated array
  with a write index. In Python, a `bytearray` or a list of characters is the analogue.
- **"Merge two sorted arrays."** LC 88 at 2.6 - the same skeleton but the choice of which
  pointer advances depends on the values rather than alternating.
- **"Interleave a string with itself reversed", "zigzag conversion"** (LC 6) - other index-
  arithmetic string problems in the same family.
- **"Why is `+=` on strings slow, and when is it not?"** Immutability forces a copy; CPython
  has an in-place optimisation for the sole-reference case. Good short answer.

## 9. Pitfalls

- **Building with `+=` in the loop** and not mentioning it.
- **Forgetting one of the two tails.** Both directions appear in the examples.
- **Using `zip` and forgetting the tails entirely** - `zip` silently truncates, so
  `merge("abcd", "pq")` would return `"apbq"`, losing `"cd"`. This is the most likely
  actual bug.
- **`zip_longest` with the default `fillvalue=None`**, which raises `TypeError` on
  concatenation.
- **Alternating starting from `word2`.**
- **Special-casing the empty string** when the slice-based tail handling already covers it.
- **Returning a list instead of a string.**
- **Indexing `word1[i]` after the loop** instead of slicing `word1[i:]`, which gets the
  leftover wrong or raises.
