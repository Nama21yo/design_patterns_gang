How to state a bound and defend it. You will be asked for the complexity of essentially
every solution you write, and a vague answer undoes a correct one.

## Which notation to say

| Notation | Meaning | Use in an interview? |
|---|---|---|
| `O(f)` | upper bound, "at most" | **Yes.** This is what "the complexity" means in practice. |
| `Omega(f)` | lower bound, "at least" | Only when arguing optimality. |
| `Theta(f)` | tight, both | Correct and slightly pedantic; fine if you mean it. |

Say **"O(n log n) time, O(n) space"** and then justify in one sentence. Always give both.

Two qualifiers worth using, because they are the honest ones:

- **"average"** for anything resting on hashing. A dict lookup is `O(1)` average, `O(n)`
  worst case if every key collides. This is the right word and interviewers notice it - one
  of these loops asked "how does hashing work" directly.
- **"amortised"** for anything where an occasional expensive operation is paid for by many
  cheap ones - list append, dynamic array growth, the pop in a monotonic stack.

## Reference table: Python operation costs

The one you will actually use in the room.

### list

| Operation | Cost | Note |
|---|---|---|
| `a[i]`, `a[i] = x` | `O(1)` | |
| `a.append(x)` | `O(1)` amortised | doubling growth |
| `a.pop()` | `O(1)` | from the **end** |
| `a.pop(0)`, `a.insert(0, x)` | `O(n)` | shifts everything - use `deque` |
| `x in a` | `O(n)` | **the classic accidental quadratic** |
| `a.remove(x)` | `O(n)` | scan + shift |
| `a[i:j]` | `O(j - i)` | slicing copies |
| `len(a)` | `O(1)` | |
| `a.sort()`, `sorted(a)` | `O(n log n)` | Timsort, stable, `O(n)` on sorted input |
| `min`, `max`, `sum` | `O(n)` | |

### dict and set

| Operation | Average | Worst |
|---|---|---|
| `d[k]`, `d[k] = v`, `k in d`, `del d[k]` | `O(1)` | `O(n)` |
| iteration | `O(n)` | |
| `d.keys()`, `.values()`, `.items()` | `O(1)` view | iteration is `O(n)` |

`dict` preserves insertion order (guaranteed from Python 3.7). Assigning to an **existing**
key does **not** move it - see 23.11.

### deque, heapq, bisect

| Operation | Cost |
|---|---|
| `deque.append`, `appendleft`, `pop`, `popleft` | `O(1)` |
| `deque[i]` (middle) | `O(n)` |
| `heapq.heappush`, `heappop` | `O(log n)` |
| `heapq.heapify(list)` | `O(n)` - not `O(n log n)` |
| `heap[0]` | `O(1)` |
| `heapq.nlargest(k, it)` | `O(n log k)` |
| `bisect.bisect_left/right` | `O(log n)` |
| `bisect.insort` | `O(n)` - the **search** is log, the **insert** shifts |

`bisect.insort` being `O(n)` catches people out. Say it.

### str

| Operation | Cost |
|---|---|
| `s[i]`, `len(s)` | `O(1)` |
| `s[i:j]` | `O(j - i)` |
| `s + t` | `O(len(s) + len(t))` - strings are immutable |
| `s += t` in a loop | `O(n^2)` overall - **use a list and `"".join`** |
| `"".join(parts)` | `O(total length)` |
| `x in s` (substring) | `O(n * m)` worst case |
| `sorted(s)` | `O(n log n)` |

## Common recurrences

| Recurrence | Solution | Example |
|---|---|---|
| `T(n) = T(n/2) + O(1)` | `O(log n)` | binary search |
| `T(n) = T(n/2) + O(n)` | `O(n)` | quickselect (average) |
| `T(n) = 2T(n/2) + O(1)` | `O(n)` | tree traversal, heapify |
| `T(n) = 2T(n/2) + O(n)` | `O(n log n)` | merge sort |
| `T(n) = 2T(n-1) + O(1)` | `O(2^n)` | naive subsets |
| `T(n) = n * T(n-1)` | `O(n!)` | permutations |

**Master theorem**, for `T(n) = a T(n/b) + O(n^d)`:

- `d > log_b(a)` -> `O(n^d)` (the splitting dominates)
- `d == log_b(a)` -> `O(n^d log n)` (balanced - merge sort is `a=2, b=2, d=1`)
- `d < log_b(a)` -> `O(n^(log_b a))` (the leaves dominate)

You rarely need to invoke it by name, but knowing the three cases lets you answer instantly.

## Amortised analysis

The argument to have ready, because stack-based solutions always attract it.

**Dynamic array append.** Growing doubles capacity, so `n` appends cost `1 + 2 + 4 + ... + n
< 2n` copies total. Each append is `O(1)` amortised even though one of them is `O(n)`.

**Monotonic stack.** "Each element is pushed at most once and popped at most once, so the
total work across the whole loop is `O(n)`, even though a single iteration can pop many
elements." Memorise that sentence; you will use it in Part 4 constantly.

**Sliding window.** "`left` only ever moves forward, so across the whole run it advances at
most `n` times. The nested `while` does not make it quadratic." Same shape of argument.

**Union-find** with path compression and union by rank is `O(alpha(n))` per operation, where
alpha is the inverse Ackermann function and is at most 4 for any input you will ever see.
Saying "effectively constant" is fine.

## Space: what counts

Distinguish clearly, because interviewers ask:

- **Auxiliary space** - what your algorithm allocates beyond input and output.
- **Total space** - including input and output.

"O(1) space" normally means **auxiliary**. Say which you mean.

**Do not forget:**
- **Recursion stack.** A recursive tree traversal is `O(h)` space, which is `O(n)` for a
  degenerate tree. A grid DFS can be `O(rows * cols)` deep.
- **Slices copy.** `arr[i:j]` inside a loop is both time and space.
- **The output.** If the answer is exponentially large, say the algorithm is
  **output-bound** - see 23.7, where enumerating all simple paths cannot beat the size of
  what it prints.

## Bounds that are easy to get wrong

- **`heapify` is `O(n)`**, not `O(n log n)`. The proof is that most nodes are near the
  bottom and sift down a short distance.
- **Building a `Counter` is `O(n)`**, but `most_common()` is `O(m log m)` for `m` distinct
  keys, and `most_common(k)` is `O(m log k)`.
- **`sorted` on a list of strings** is `O(n log n)` *comparisons*, each up to `O(L)`, so
  `O(n L log n)` in total. The `L` is invisible and often matters.
- **Substring membership in a hash set**: `s[i:j] in words` is `O(j-i)` to slice **and**
  `O(j-i)` to hash, not `O(1)`. This is why the trie version of word break (23.20) wins.
- **Python integers are arbitrary precision**, so arithmetic on huge numbers is not `O(1)`.
  Rarely matters; worth knowing.
- **`in` on a list vs a set** - `O(n)` vs `O(1)`. The most common accidental quadratic in
  interview code.

## Stating an output-sensitive bound

Some problems have answers larger than any algorithm could produce quickly. Say so
explicitly rather than quoting a scary number:

> "This is output-sensitive - the number of simple paths can be factorial in the number of
> nodes, so the honest bound is O(number of paths times path length). No algorithm can beat
> the size of the output."

Same applies to "return all valid segmentations" (23.20) and "return all pairs" (23.16).

## The sentences to have memorised

- "O(n log n) time, dominated by the sort; O(n) space for the map."
- "O(1) average, because it rests on hashing - worst case O(n) if every key collides."
- "Each element is pushed and popped at most once, so the total is O(n) amortised."
- "The left pointer only moves forward, so the nested loop is still linear overall."
- "That's O(m log k) rather than O(m log m), because I only keep k in the heap."
- "This is output-bound - the result itself can be exponential."
- "If the input were guaranteed sorted, this would drop to O(n)."
