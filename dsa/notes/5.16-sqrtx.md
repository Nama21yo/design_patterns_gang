title: "5.16 Sqrt(x)"
---

**Link:** https://leetcode.com/problems/sqrtx
**Difficulty:** Easy | **LeetCode #69**
**Bloomberg frequency:** 50% at six months.

Binary search on a **numeric answer** rather than an array index - the same framing as 5.6
and 5.12, in the simplest possible setting. There is also a Newton's-method answer worth
knowing, because "can you do better than `O(log x)`?" is the standard follow-up.

## 1. Problem statement

Given a non-negative integer `x`, return the square root of `x` rounded down to the nearest
integer.

You must **not** use any built-in exponent function or operator - no `pow(x, 0.5)`, no
`x ** 0.5`, no `math.sqrt`.

```
x = 4   ->  2
x = 8   ->  2      sqrt(8) = 2.828..., rounded down is 2
x = 0   ->  0
```

## 2. Clarifying questions

1. **Rounded down (floor), not nearest?** Floor. `sqrt(8)` is 2.82 and the answer is 2, not 3.
2. **Can `x` be 0?** Yes, and the answer is 0. It is the case that breaks a naive
   `lo = 1` range.
3. **Is `x` guaranteed non-negative?** Yes. If negatives were possible you would raise.
4. **Built-ins banned?** Yes - explicitly. That includes `math.isqrt`, which would otherwise
   be the whole answer.
5. **How large can `x` be?** Up to `2^31 - 1`. In a fixed-width language `mid * mid`
   **overflows**, which is the real trap; Python is immune but say it.
6. **Return an integer?** Yes.

## 3. Intuition

The answer is an integer in `[0, x]`, and:

> **`mid * mid <= x` is monotone in `mid`: true for every value at or below the answer, false
> above it. So binary search for the largest `mid` with `mid * mid <= x`.**

That is an **upper-bound** search ("last True") rather than the lower-bound ("first True")
used elsewhere in Part 5. Two clean ways to handle it:

- **Search for the first `mid` with `mid * mid > x`, then subtract one.** This reuses the
  lower-bound template unchanged, which is the argument for doing it this way.
- **Use the inclusive template** and track the best candidate seen.

The first is preferable if you have committed to one template - and committing to one
template is the advice in the Part 5 primer.

### The search range

- **`lo = 0`**, because `sqrt(0) = 0`. Starting at 1 breaks `x = 0`.
- **`hi = x`** is always safe. You can tighten it to `x // 2 + 1` for `x >= 2`, since the
  square root of any number above 1 is at most half of it - but the extra branch buys one
  iteration and adds a chance to be wrong. Mention it, do not bother.

### Overflow

`mid * mid` with `mid` near `2^31` overflows a 32-bit signed integer. The standard fixes:
compare `mid <= x // mid` instead of `mid * mid <= x` (avoiding the multiplication entirely,
though it needs a `mid > 0` guard), or use a 64-bit type. Python has arbitrary-precision
integers so neither is needed - **but saying it is the right instinct**, and it is the kind
of aside that distinguishes an answer on an Easy.

## 4. Approach

1. If `x < 2`, return `x` (handles 0 and 1 without any search).
2. `lo, hi = 0, x`.
3. Binary search for the first `mid` with `mid * mid > x`.
4. Return that index minus one.

## 5. Solution

```python
def my_sqrt(x):
    """Integer square root of x, rounded down. No built-in exponent functions.

    `mid * mid <= x` is true up to the answer and false after, so this searches for
    the FIRST mid whose square exceeds x and subtracts one - reusing the same
    lower-bound template as the rest of Part 5.
    """
    if x < 2:
        return x                # sqrt(0) = 0, sqrt(1) = 1

    lo, hi = 0, x               # lo = 0 so that x = 0 would work without the guard
    while lo < hi:
        mid = (lo + hi) // 2
        if mid * mid > x:
            hi = mid            # too big - the answer is strictly below mid
        else:
            lo = mid + 1        # mid is still a valid candidate, so look higher

    # lo is the first value whose square exceeds x, so lo - 1 is the floor of sqrt(x).
    return lo - 1
```

```python
my_sqrt(4)          # 2
my_sqrt(8)          # 2
my_sqrt(0)          # 0
my_sqrt(1)          # 1
my_sqrt(2)          # 1
my_sqrt(3)          # 1
my_sqrt(9)          # 3
my_sqrt(15)         # 3
my_sqrt(16)         # 4
my_sqrt(2147395599) # 46339
my_sqrt(2147483647) # 46340
```

`2147395599 -> 46339` is the classic LeetCode boundary test, and it is worth running: it is
one less than `46340^2 = 2147395600`, so an off-by-one shows up immediately. `2147483647` is
`2^31 - 1`, the largest input.

`x = 0` and `x = 1` are the small boundaries - handled by the early return, but check them.

### Newton's method

The follow-up answer. Newton's method for `f(y) = y^2 - x` gives the iteration
`y <- (y + x/y) / 2`, which **converges quadratically** - roughly doubling the number of
correct digits each step, so about 5-6 iterations for a 32-bit input versus 31 for binary
search.

```python
def my_sqrt_newton(x):
    """Newton's method: y <- (y + x // y) // 2, converging quadratically.

    Far fewer iterations than binary search. Using integer division throughout keeps
    it exact and avoids floating point entirely.
    """
    if x < 2:
        return x

    y = x
    while y * y > x:
        y = (y + x // y) // 2   # always decreases while y is above the true root
    return y


my_sqrt_newton(4)           # 2
my_sqrt_newton(8)           # 2
my_sqrt_newton(0)           # 0
my_sqrt_newton(1)           # 1
my_sqrt_newton(9)           # 3
my_sqrt_newton(15)          # 3
my_sqrt_newton(2147395599)  # 46339
my_sqrt_newton(2147483647)  # 46340
```

Two things worth saying about it:

- **Integer division keeps it exact.** With floats you would have to worry about precision
  near the boundary, and `int(math.sqrt(x))` genuinely returns the wrong answer for some
  large inputs - see the counterexample below.
- **The loop terminates** because the iteration strictly decreases while `y` is above the
  true root, and integer division prevents oscillation around it.

Here is the floating-point failure, concretely:

```python
import math

math.isqrt(4503599761588224)            # 67108864   -- correct
int(math.sqrt(4503599761588224))        # 67108865   -- one too high
67108865 * 67108865 > 4503599761588224  # True       -- so 67108865 is not a valid floor
```

The float version **overestimates** by one: the true root sits just below 67108865, but the
double rounds up to exactly it, and `int()` then truncates a value that is already too big.
That is a real bug rather than a theoretical one, and it is why `math.isqrt` exists.
Demonstrating it is a far better justification for avoiding floats than asserting it.

### The linear scan, to state and reject

```python
def my_sqrt_linear(x):
    """O(sqrt(x)): count upwards. Correct and far too slow for 32-bit inputs."""
    i = 0
    while (i + 1) * (i + 1) <= x:
        i += 1
    return i


my_sqrt_linear(8)   # 2
my_sqrt_linear(16)  # 4
my_sqrt_linear(0)   # 0
```

## 6. Complexity

| | Time | Space |
|---|---|---|
| Linear scan | `O(sqrt(x))` | `O(1)` |
| **Binary search** | **`O(log x)`** | **`O(1)`** |
| **Newton's method** | **`O(log log x)`** iterations | `O(1)` |

For `x` near `2^31`: the scan takes ~46,000 steps, binary search takes 31, Newton takes about
6. Quoting those three numbers is a much better answer than quoting the asymptotics alone.

Note that each iteration involves a multiplication or division, which is not `O(1)` for
arbitrary-precision integers - but for fixed-width inputs it is.

## 7. How to present it

1. **Restate**, and confirm **floor**, not nearest. `sqrt(8) = 2` is the check.
2. **Confirm built-ins are banned**, including `math.isqrt`.
3. **State the framing**: *"The answer is an integer between 0 and `x`, and `mid * mid <= x`
   is monotone - true up to the answer, false after. So I binary search on the answer."*
4. **Say which boundary you are finding**: *"this is an upper bound - the last True - so I'll
   search for the first `mid` whose square exceeds `x` and subtract one, which lets me reuse
   the same template."*
5. **Handle `x < 2` up front** and say why (it makes the range reasoning simpler).
6. **Write it.**
7. **Raise overflow unprompted**: *"`mid * mid` would overflow a 32-bit int near the top of
   the range - in C++ I'd use a 64-bit type or compare `mid <= x / mid`. Python's integers
   are arbitrary precision so it's fine here."* This is the aside that lifts an Easy.
8. **Test** 0, 1, 8, and `2147395599`.
9. **Offer Newton's method** as the follow-up, with the convergence contrast: ~6 iterations
   versus 31.
10. **Close**: `O(log x)` for binary search, `O(log log x)` iterations for Newton, `O(1)`
    space for both.

## 8. Follow-ups and variations

- **"Can you do better than O(log x)?"** Newton's method - quadratic convergence. The
  expected follow-up.
- **"Valid Perfect Square"** (LC 367). The same search, returning `mid * mid == x` instead of
  the floor. One-line change.
- **"Compute the square root to `k` decimal places."** Binary search on floats with a
  tolerance, or scale the input by `100^k` and take the integer root. The scaling trick keeps
  everything exact.
- **"Cube root, or `n`-th root."** Same binary search with `mid ** n` - but careful, since
  `**` may be the banned operator; use repeated multiplication. Newton generalises too:
  `y <- ((n-1) * y + x / y^(n-1)) / n`.
- **"Why not `int(math.sqrt(x))`?"** Banned here, and genuinely incorrect for some large
  values because of floating-point rounding - `math.isqrt` exists precisely for this.
  A good, concrete thing to know.
- **"Pow(x, n)"** (LC 50) - fast exponentiation by squaring, `O(log n)`. The natural sibling
  problem and also on the Bloomberg list.
- **"What if `x` is a huge arbitrary-precision integer?"** Newton still works and is the
  standard approach; each iteration costs a big-integer division.

## 9. Pitfalls

- **Returning `lo` instead of `lo - 1`**, giving the ceiling rather than the floor. `x = 8`
  returns 3.
- **`lo = 1` without an `x == 0` guard**, so `sqrt(0)` comes out as 1 or the loop misbehaves.
- **Overflow in `mid * mid`** in a fixed-width language.
- **Using `x ** 0.5` or `math.sqrt`** - explicitly banned, and float-imprecise at the
  boundary.
- **Mixing binary search templates** - `while lo <= hi` with `hi = mid` is an infinite loop.
- **In Newton's method, using float division** `(y + x / y) / 2`, which reintroduces
  precision problems. Use `//`.
- **In Newton's method, forgetting the `x < 2` guard**, so `x // y` divides by zero when
  `x = 0`.
- **Setting `hi = x // 2`** without handling `x = 1`, whose root is 1 but whose half is 0.
