**Bloomberg frequency:** 38% at three months.

A **DP problem solved with a sliding window**, which is an unusual and instructive
combination. The recurrence is obvious; the reason it needs a window is that the naive
evaluation is `O(n * (maxJump - minJump))`. Two standard fixes - a prefix sum of reachability
or a BFS with a monotone frontier - and both are worth knowing.

## 1. Problem statement

You are given a **0-indexed binary string** `s` of length `n`, and two integers `minJump` and
`maxJump`. Initially you stand at index `0`, and `s[0] == '0'`.

You may move from index `i` to index `j` if:
- `i + minJump <= j <= min(i + maxJump, n - 1)`, and
- `s[j] == '0'`.

Return `True` if you can reach index `n - 1`.

```
s = "011010", minJump = 2, maxJump = 3  ->  True
    0 -> 3 (jump of 3), then 3 -> 5 (jump of 2)

s = "01101110", minJump = 2, maxJump = 3  ->  False
```

## 2. Clarifying questions

1. **Can I only move right?** Yes - `j > i` always, since `minJump >= 1`. That makes the
   reachability a forward DP with no cycles, which is why no general graph search is needed.
2. **Must the destination be `'0'`?** Yes. `'1'` positions are walls.
3. **Is `s[0]` guaranteed `'0'`?** Yes, stated. Worth confirming, since otherwise the answer
   is immediately `False`.
4. **What if `s[n-1] == '1'`?** Then it is unreachable - return `False` early.
5. **Is `minJump <= maxJump`?** Yes, guaranteed.
6. **Sizes?** `n` up to 10^5, and the jump range can be up to `n` - so `O(n * range)` is
   `O(n^2)` and will time out. That is the whole reason for the window.

## 3. Intuition

The DP is immediate:

> **`reachable[j]` is true iff `s[j] == '0'` and at least one `i` in
> `[j - maxJump, j - minJump]` has `reachable[i]` true.**

So each position looks back at a **fixed window** of earlier positions and asks "is there any
`True` in it?".

Evaluating that window by scanning is `O(range)` per position, hence `O(n^2)`. The fix is to
answer "is there any `True` in this window?" in `O(1)`.

### Fix (a): prefix sums of reachability

Keep `prefix[i]` = number of reachable positions among `0..i-1`. Then the window
`[lo, hi]` contains a reachable position iff `prefix[hi+1] - prefix[lo] > 0`.

That is one subtraction per position, so `O(n)` total. It is the cleanest formulation and
the one to write.

The bookkeeping to get right is the window bounds:
- `lo = max(0, j - maxJump)`
- `hi = j - minJump`
- if `hi < 0`, no jump can land here at all.

### Fix (b): BFS with a monotone frontier

The other standard solution. Process reachable positions in increasing order with a queue,
and maintain a pointer `furthest` marking the highest index already enqueued. For each
reachable `i`, enqueue every unvisited `'0'` in `[i + minJump, i + maxJump]`, starting from
`max(furthest + 1, i + minJump)`.

Because `furthest` never moves backwards, each index is enqueued at most once, so the total
is `O(n)`. This is the same amortised argument as everywhere else in Part 3, applied to a
BFS frontier.

Both are `O(n)`. The prefix-sum version is shorter; the BFS version generalises better if the
jump rule becomes more complex. Offer the prefix-sum one and mention the other.

### What does *not* work

- **Plain BFS/DFS without the `furthest` pointer**: each position re-scans its whole jump
  range, giving `O(n * range)`.
- **Greedy "always jump as far as possible"**: fails, because the furthest landing spot may
  be a `'1'` or a dead end while a nearer one works. `"011010"` with a greedy max jump lands
  on index 3 and happens to work, but it is easy to construct cases where it does not - say
  this rather than trusting it.

## 4. Approach

1. If `s[-1] == '1'`, return `False`.
2. `reachable = [False] * n`; `reachable[0] = True`.
3. `prefix = [0] * (n + 1)`; `prefix[1] = 1`.
4. For `j` from `1` to `n-1`:
   - `hi = j - minJump`; if `hi >= 0` and `s[j] == '0'`:
     - `lo = max(0, j - maxJump)`
     - `reachable[j] = prefix[hi + 1] - prefix[lo] > 0`
   - `prefix[j + 1] = prefix[j] + (1 if reachable[j] else 0)`
5. Return `reachable[n - 1]`.

## 5. Solution

```python
def can_reach(s, min_jump, max_jump):
    """True if index n-1 is reachable from index 0 under the jump rules.

    reachable[j] iff s[j] == '0' and some reachable i lies in [j-maxJump, j-minJump].
    A prefix sum over `reachable` answers "is there any True in this window?" in O(1),
    which is what turns the O(n * range) DP into O(n).
    """
    n = len(s)
    if n == 0 or s[-1] == "1":
        return False
    if n == 1:
        return True

    reachable = [False] * n
    reachable[0] = True

    # prefix[i] = number of reachable positions among indices 0..i-1
    prefix = [0] * (n + 1)
    prefix[1] = 1

    for j in range(1, n):
        hi = j - min_jump                   # furthest-back index that can reach j
        if hi >= 0 and s[j] == "0":
            lo = max(0, j - max_jump)       # nearest-back index that can reach j
            # Any reachable position in [lo, hi] lets us land on j.
            reachable[j] = prefix[hi + 1] - prefix[lo] > 0
        prefix[j + 1] = prefix[j] + (1 if reachable[j] else 0)

    return reachable[n - 1]
```

```python
can_reach("011010", 2, 3)           # True
can_reach("01101110", 2, 3)         # False
can_reach("0", 1, 1)                # True
can_reach("00", 1, 1)               # True
can_reach("01", 1, 1)               # False
can_reach("0000", 2, 3)             # True
can_reach("0110", 1, 1)             # False
can_reach("00111010", 3, 5)         # False
can_reach("0" * 10, 1, 1)           # True
can_reach("0" + "1" * 8 + "0", 1, 9)    # True
```

The last one is worth narrating: every intermediate position is a wall, but `maxJump = 9`
lets you jump straight from index 0 to index 9 in a single hop. It tests that you are
checking the *landing* square only, not the path - there is no notion of passing through.

`"01"` with `minJump = maxJump = 1` is `False` because index 1 is a `'1'` - the simplest
negative case.

### The BFS version with a monotone frontier

```python
from collections import deque


def can_reach_bfs(s, min_jump, max_jump):
    """O(n). `furthest` never moves backwards, so each index is enqueued at most once."""
    n = len(s)
    if n == 0 or s[-1] == "1":
        return False

    queue = deque([0])
    furthest = 0                    # highest index already enqueued or skipped

    while queue:
        i = queue.popleft()
        if i == n - 1:
            return True
        # Never re-scan a range already covered: start past `furthest`.
        start = max(i + min_jump, furthest + 1)
        end = min(i + max_jump, n - 1)
        for j in range(start, end + 1):
            if s[j] == "0":
                queue.append(j)
        furthest = max(furthest, end)

    return False


can_reach_bfs("011010", 2, 3)               # True
can_reach_bfs("01101110", 2, 3)             # False
can_reach_bfs("0", 1, 1)                    # True
can_reach_bfs("0110", 1, 1)                 # False
can_reach_bfs("0" + "1" * 8 + "0", 1, 9)    # True
can_reach_bfs("00111010", 3, 5)             # False
```

The `furthest` pointer is what makes it linear. Without it, overlapping jump ranges are
rescanned and the worst case is `O(n * range)`. Say that explicitly - it is the same
"pointer only moves forward" argument as the sliding window, which is why this problem sits
in Part 3 rather than Part 14.

### The naive DP, for the complexity comparison

```python
def can_reach_naive(s, min_jump, max_jump):
    """O(n * range): scans the whole predecessor window for each position."""
    n = len(s)
    if s[-1] == "1":
        return False
    reachable = [False] * n
    reachable[0] = True
    for j in range(1, n):
        if s[j] != "0":
            continue
        lo = max(0, j - max_jump)
        hi = j - min_jump
        for i in range(lo, hi + 1):
            if reachable[i]:
                reachable[j] = True
                break
    return reachable[n - 1]


can_reach_naive("011010", 2, 3)         # True
can_reach_naive("01101110", 2, 3)       # False
can_reach_naive("00111010", 3, 5)       # False
```

## 6. Complexity

Let `r = maxJump - minJump + 1` be the jump range width.

| | Time | Space |
|---|---|---|
| Naive DP | `O(n * r)` | `O(n)` |
| **Prefix-sum DP** | **`O(n)`** | `O(n)` |
| **BFS with monotone frontier** | **`O(n)`** | `O(n)` |

Space is `O(n)` for the reachability and prefix arrays. You can reduce the prefix array to a
rolling count if you are careful, but the clarity is not worth it in an interview.

## 7. How to present it

1. **Restate**, and confirm movement is rightwards only and that only the landing square
   matters.
2. **Write the recurrence on the board immediately**: *"`reachable[j]` is true if `s[j]` is
   `'0'` and any position in `[j - maxJump, j - minJump]` is reachable."* That is the whole
   problem stated in one line.
3. **Give the naive cost**: `O(n * range)`, and note that the range can be `O(n)`, so this is
   quadratic and will time out.
4. **Name the bottleneck precisely**: *"the only thing I need from that window is whether it
   contains any `True` - that's a range-OR query, and I can answer it in O(1) with a prefix
   count."*
5. **Announce**, then write the prefix-sum version. Be careful and explicit about the two
   bounds, `lo = max(0, j - maxJump)` and `hi = j - minJump`, and the `hi < 0` guard.
6. **Handle the early exit** `s[-1] == '1'`.
7. **Trace `"011010"` with minJump 2, maxJump 3**: index 3 is reachable from 0, index 5 is
   reachable from 3.
8. **Offer the BFS alternative** and explain the `furthest` pointer as the same
   "only-moves-forward" argument.
9. **Close**: `O(n)` time and space; mention that greedy does not work here and why.

## 8. Follow-ups and variations

- **"Why not just BFS?"** Plain BFS rescans overlapping ranges, giving `O(n * range)`. The
  `furthest` pointer fixes it. Being able to say exactly where the blow-up comes from is the
  point.
- **"Why doesn't greedy work?"** The furthest reachable landing square may be a dead end
  while a nearer one is not, and you cannot tell locally. Contrast with **Jump Game I/II**
  (LC 55 / 45), where greedy *does* work because any distance up to `nums[i]` is allowed -
  the `minJump` lower bound is what breaks greediness here.
- **"Return the number of ways to reach the end"** (mod some prime). Same prefix-sum
  structure, but the prefix now sums **counts** instead of booleans. A very natural extension
  and a good check that you understood the technique.
- **"Return the minimum number of jumps."** BFS by levels, still with the `furthest` pointer.
- **"Return one valid path."** Store a parent pointer when marking `reachable[j]`.
- **"What if you could also jump left?"** Now it is a genuine graph and you need BFS over
  both directions; the forward DP no longer applies.
- **"What if `minJump` were 0?"** Then you could stay put, and the window includes `j`
  itself - the recurrence would become self-referential. Guard it.
- **"Sparse walls."** If `'1'`s are rare, a set of reachable positions plus interval merging
  can be faster in practice, though not asymptotically.

## 9. Pitfalls

- **Scanning the predecessor window** instead of using a prefix count - `O(n^2)`, times out.
- **Off-by-one in the prefix query.** It is `prefix[hi + 1] - prefix[lo]` for the inclusive
  range `[lo, hi]`.
- **Forgetting the `hi < 0` guard**, which makes `prefix[hi + 1]` index negatively and
  silently read from the end of the list - a nasty Python-specific bug.
- **Checking `s[i] == '0'` for the source instead of the destination.** Only the landing
  square matters; you never "pass through" anything.
- **Forgetting the `s[-1] == '1'` early exit** - not wrong, but it is the cheap check.
- **Updating `prefix[j+1]` before computing `reachable[j]`**, which lets `j` reach itself.
- **In the BFS version, omitting `furthest`**, reintroducing the quadratic blow-up.
- **Assuming greedy works** because the problem is called "Jump Game".
