**Difficulty:** Easy | **LeetCode #941**
**Bloomberg frequency:** 38% at three months.

An easy validation question whose entire difficulty is the **edge cases**. It also sets up
5.11 *Peak Index in a Mountain Array*, where the same shape is searched rather than verified.

## 1. Problem statement

Given an array `arr`, return `True` if and only if it is a **valid mountain array**:

- `len(arr) >= 3`, and
- there exists an index `i` with `0 < i < len(arr) - 1` such that
  - `arr[0] < arr[1] < ... < arr[i]` (strictly increasing up to the peak), and
  - `arr[i] > arr[i+1] > ... > arr[len(arr)-1]` (strictly decreasing after it).

```
arr = [2,1]       ->  False    too short
arr = [3,5,5]     ->  False    5 < 5 is not strict
arr = [0,3,2,1]   ->  True
```

## 2. Clarifying questions

1. **Must the increase and decrease be strict?** Yes. `[3,5,5]` is `False`, and this is the
   trap in example 2. Plateaus are not allowed anywhere.
2. **Must there be both an up and a down side?** Yes. A monotonically increasing array like
   `[0,1,2,3]` is **not** a mountain - the peak may not be the last element. Likewise
   `[3,2,1]` is not, since the peak may not be the first.
3. **Minimum length?** Three. Two elements can never form both sides.
4. **Can the peak be a plateau of two equal maxima?** No, by strictness.
5. **Can values be negative?** Yes, irrelevant to the comparisons.
6. **Can there be multiple peaks?** Then it is not a mountain - a single ascent and a single
   descent only.

## 3. Intuition

The cleanest formulation is a **two-phase walk**:

> **Climb as far as you can, then descend as far as you can. It is a mountain if and only if
> you climbed at least one step, descended at least one step, and finished at the end.**

Start at index 0 and advance while `arr[i] < arr[i+1]`. When that stops, you are at the
peak. Then advance while `arr[i] > arr[i+1]`. If you land exactly on the last index, and the
peak was neither the first nor the last element, it is a mountain.

The three failure modes map one-to-one onto three checks:
- **`i == 0`**: never climbed - the array starts by descending or is flat.
- **`i == n - 1`**: never descended - the array only ascends.
- **`i != n - 1` after descending**: the descent stopped early, so there is a plateau or a
  second ascent.

That third check is what makes plateaus and multi-peak arrays fail without any special
handling, which is why this formulation is better than trying to enumerate the cases.

A common alternative is the **two-pointer** version: walk up from the left, walk up from the
right, and check that both stop at the same index. It is symmetric and pleasant, but the
single walk is shorter and there is no advantage to two passes here.

## 4. Approach

1. If `n < 3`, return `False`.
2. `i = 0`; while `i + 1 < n` and `arr[i] < arr[i+1]`: `i += 1`.
3. If `i == 0` or `i == n - 1`, return `False` - no ascent, or no descent.
4. While `i + 1 < n` and `arr[i] > arr[i+1]`: `i += 1`.
5. Return `i == n - 1`.

Both loops use **strict** comparisons, so any equal pair stops the walk and is caught by the
subsequent check.

## 5. Solution

```python
def valid_mountain_array(arr):
    """True if arr strictly increases to a single peak, then strictly decreases.

    Walk up, then walk down. Strict comparisons mean a plateau halts the walk, and
    the final 'did I reach the end' test rejects it.
    """
    n = len(arr)
    if n < 3:
        return False

    i = 0
    # Climb. A plateau or a descent stops this loop.
    while i + 1 < n and arr[i] < arr[i + 1]:
        i += 1

    # The peak may be neither the first element (no ascent) nor the last (no descent).
    if i == 0 or i == n - 1:
        return False

    # Descend.
    while i + 1 < n and arr[i] > arr[i + 1]:
        i += 1

    # If the descent did not carry us to the very end, something interrupted it:
    # a plateau, or a second ascent.
    return i == n - 1
```

```python
valid_mountain_array([2, 1])                # False
valid_mountain_array([3, 5, 5])             # False
valid_mountain_array([0, 3, 2, 1])          # True
valid_mountain_array([0, 1, 2, 3])          # False
valid_mountain_array([3, 2, 1, 0])          # False
valid_mountain_array([1, 3, 2])             # True
valid_mountain_array([1, 2, 3, 2, 1])       # True
valid_mountain_array([1, 2, 2, 1])          # False
valid_mountain_array([1, 2, 1, 2, 1])       # False
valid_mountain_array([0, 0, 0])             # False
valid_mountain_array([])                    # False
valid_mountain_array([9])                   # False
```

Three of those are the ones to work through aloud:

- `[0,1,2,3]` -> climbs to `i = 3 == n - 1`, so it fails the "no descent" check.
- `[1,2,2,1]` -> climbs to `i = 1` (because `2 < 2` is false), then descends: `arr[1] > arr[2]`
  is `2 > 2`, false, so the descent never moves and `i` stays 1, which is not `n - 1`. `False`.
- `[1,2,1,2,1]` -> climbs to `i = 1`, descends to `i = 2` (since `1 > 2` is false), and `2 !=
  4`. `False`. This is the case the final check exists for.

### The two-pointer version

```python
def valid_mountain_array_two_pointers(arr):
    """Symmetric alternative: climb from both ends and check the peaks coincide."""
    n = len(arr)
    if n < 3:
        return False

    left = 0
    while left + 1 < n and arr[left] < arr[left + 1]:
        left += 1

    right = n - 1
    while right > 0 and arr[right - 1] > arr[right]:
        right -= 1

    # Both must have moved (a real ascent and a real descent) and met at the same peak.
    return left == right and left != 0 and right != n - 1


valid_mountain_array_two_pointers([0, 3, 2, 1])      # True
valid_mountain_array_two_pointers([3, 5, 5])         # False
valid_mountain_array_two_pointers([1, 2, 1, 2, 1])   # False
valid_mountain_array_two_pointers([0, 1, 2, 3])      # False
```

Equivalent in every respect. Offer it if asked for an alternative; it reads nicely and makes
the symmetry of the problem visible.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Single walk | `O(n)` | `O(1)` |
| Two pointers | `O(n)` | `O(1)` |

Each element is visited at most once across the two loops, so a single pass overall. `O(n)`
is optimal - the last element alone can invalidate the whole array.

**Can you binary search it?** No, for the same reason as 1.8: validity is a global property.
But *if you are told the array is already a valid mountain*, finding the peak **is** binary
searchable in `O(log n)` - that is 5.11, and the contrast is worth naming.

## 7. How to present it

1. **Restate**, and immediately pin down strictness: "`[3,5,5]` is false, so both sides are
   strict - no plateaus anywhere, including at the peak?"
2. **Enumerate the failure modes out loud** before coding. "It fails if it's too short, if it
   never goes up, if it never comes down, or if it goes up again after coming down." Having
   the cases named makes the code obviously correct.
3. **Announce**: "Walk up while strictly increasing, check the peak isn't at either end,
   then walk down, and confirm I reached the last index."
4. **Write it**, and explain the final `i == n - 1` check specifically - it is the one line
   that does non-obvious work, catching both plateaus and second ascents.
5. **Test the edge cases out loud**, without being asked: `[0,1,2,3]`, `[3,2,1,0]`,
   `[1,2,2,1]`, `[1,2,1,2,1]`, `[2,1]`. On an Easy, this enumeration *is* the interview.
6. **Close**: `O(n)` time, `O(1)` space, and note that finding the peak in a known-valid
   mountain is `O(log n)` by binary search.

## 8. Follow-ups and variations

- **"Find the peak index of a valid mountain array."** LC 852, which is 5.11 here. Binary
  search on the predicate `arr[mid] < arr[mid+1]`, `O(log n)`.
- **"Longest mountain in an array."** LC 845. Scan for each peak and expand outwards, or do a
  single pass tracking up/down run lengths. `O(n)`, `O(1)`.
- **"Minimum removals to make it a mountain."** LC 1671 - now it is LIS from the left and LIS
  from the right, `O(n log n)`. A genuinely different problem; name the technique.
- **"Allow plateaus."** Change the strict comparisons to non-strict - but then be careful that
  an all-equal array must still be rejected, so you need to verify a real rise and fall
  occurred.
- **"Valley array instead."** Negate the comparisons, or negate the values and reuse.
- **"Is it a mountain, and if so where is the peak?"** Return the index instead of a boolean;
  `i` already holds it after the first loop.
- **"Streaming version."** Maintain a small state machine: `climbing -> descending -> invalid`.
  `O(1)` memory, and it is a neat way to express the same logic.

## 9. Pitfalls

- **Using `<=` or `>=`**, accepting plateaus. `[3,5,5]` and `[1,2,2,1]` are the tests.
- **Forgetting the `n < 3` guard.** `[1]` and `[2,1]` must be `False`.
- **Accepting a monotonic array.** `[0,1,2,3]` has no descent and `[3,2,1]` has no ascent;
  both are `False`. This is the most commonly missed pair.
- **Omitting the final `i == n - 1` check**, which wrongly accepts `[1,2,1,2,1]`.
- **Index out of range** by writing `arr[i+1]` without the `i + 1 < n` guard.
- **Using `max()` to find the peak and then verifying both sides.** It works, but it breaks
  when the maximum is duplicated - `[1,3,3,1]` - and you need extra logic to reject that.
  The walk handles it for free.
- **Treating the Easy as beneath narration.** The edge-case enumeration is the whole signal
  here.
