title: "0.7 Testing your own code in the room"
---

Finding your own bug before the interviewer does. At Bloomberg this is not a nicety - the
reports are unanimous that Round 2 is *spent* on edge cases, and Design Underground System
was asked four separate times with the round going this way every time.

## The rule

> When your code is written, do not stop and do not look up. Say **"let me trace this"**,
> then **"let me go through the edge cases"**, and work the list below out loud.

Waiting to be asked converts a strength into a prompt you failed to anticipate.

## The edge-case checklist

Run this mentally on every problem. Most entries will be irrelevant in ten seconds, which is
fine - the point is that you checked.

### Size and emptiness
- **Empty input** - `[]`, `""`, `{}`, an empty grid, a null head.
- **One element.** Many two-pointer and pair problems have no valid answer at `n == 1`.
- **Two elements** - the smallest case where "pair" logic is real.
- **Very large input** - does anything become quadratic? Does recursion get too deep?

### Duplicates and repetition
- **All elements identical** - `[1,1,1,1]`. Breaks dedup logic, and breaks `<` vs `<=`
  choices (see 23.9's Min Stack trap).
- **The target value appearing twice**, when a pair must not use one element twice.
- **Duplicate keys** in a design problem - the reported lottery follow-up.

### Values
- **Zero**, **negatives**, and **mixed signs**. Sliding window in particular is usually
  invalid with negative numbers.
- **The maximum and minimum** of the stated range.
- **Overflow** - not a Python issue, but say it *would* be in C++ or Java. That aside is
  worth real credit.

### Structure
- **Already sorted** input, and **reverse sorted**.
- **No valid answer exists** - what do you return? `None`, `-1`, `[]`, or raise? **Decide
  and state it**; 23.7 reported an interviewer wanting a message rather than an empty list.
- **Everything is a valid answer.**
- **Boundaries**: first and last index, the cells on a grid's border, the root and the
  leaves of a tree.

### Problem-shape specifics
- **Intervals**: touching endpoints (`end == next start`), zero-length, wrapping past
  midnight (23.14, 23.3).
- **Graphs**: cycles, self-loops, disconnected components, a node with no edges.
- **Trees**: a single node, a completely degenerate (linked-list) tree.
- **Strings**: whitespace, case, non-ASCII, the empty string. A 26-slot array assumes
  lowercase ASCII - say that assumption aloud (23.21).
- **Grids**: a single row, a single column, a 1x1 grid.

## Tracing properly

A trace is not "I think this works". It is naming the variables and their values at each
step. Pick the **smallest input that exercises the interesting branch** - not the biggest
example on the board.

> "Let me trace `aabbbbac`. Stack starts empty. Two `a`s push and merge into `(a,2)`. Four
> `b`s become `(b,4)`. Now `c` arrives, which differs from `b`, so I close out the top:
> `(b,4)` has count 4 which is at least 3, so it pops, leaving `(a,2)` on top. `c` doesn't
> match `a`... wait - the exposed top is `a` and the incoming character is `c`, so they
> don't merge, and I push `(c,1)`. Final collapse: `(a,2)` is under the threshold. Hmm, but
> my expected answer is just `c`."

That trace is what catches the bug. Doing it in your head does not.

**Trace at the level of the data structure, not the syntax.** Nobody wants to hear "then the
for loop increments i".

## Assertions and invariants

Stating an invariant is the cheapest way to look senior, and it sometimes finds a real bug.

```python
# fragment
# The binary search below depends on this list being sorted, which holds because
# events are appended as they arrive.
if self.times and timestamp < self.times[-1]:
    raise ValueError("events must be recorded in non-decreasing time order")
```

That is from 23.8, where an interviewer explicitly asked *"how can you guarantee binary
search works on the events list?"* A candidate who had already written the guard has
answered before being asked.

Invariants worth naming out loud when they apply:
- "This list stays sorted because I only append in time order."
- "`left` only moves forward, so the loop is linear."
- "`len(self.stack) == len(self.mins)` at all times."
- "Every index is marked at most once, which is why this is amortised O(n)."

## The off-by-one audit

Run this specifically on any loop with indices:

1. **Does the first iteration do the right thing?** Substitute the start value.
2. **Does the last?** Substitute the end value.
3. **Are the bounds inclusive or exclusive?** `range(n)` excludes `n`; `bisect_right` gives
   an exclusive upper bound; slices are half-open.
4. **Can an index go negative?** Python will happily wrap to the end of the list and give a
   silently wrong answer rather than an error. This is a genuinely nasty Python-specific bug.
5. **In binary search, does the space shrink every iteration?** If `lo = mid` is possible,
   you may have an infinite loop.

## When a test fails mid-trace

Do not panic and do not start rewriting.

1. **Say what you observed**: "On `aabbbaa` I get `a`, but the answer should be empty."
2. **Localise it**: "So the pop is happening too early - the run isn't finished yet."
3. **Name the fix**: "I need to close out a run only when the next character differs, not
   the moment the count hits three."
4. **Then make the change.**

Narrating the diagnosis is worth more than the original code being right. It is, literally,
debugging in front of them - which is the job.

## Writing your own tests, if there is time

If you have an editor that runs code, a few asserts are better than a print:

```python
def solve(nums, target):
    """Two Sum: indices of the two numbers adding to target."""
    seen = {}
    for i, x in enumerate(nums):
        if target - x in seen:
            return (seen[target - x], i)
        seen[x] = i
    return None


assert solve([2, 7, 11, 15], 9) == (0, 1)
assert solve([3, 2, 4], 6) == (1, 2)
assert solve([3, 3], 6) == (0, 1)          # duplicates
assert solve([3], 6) is None               # no self-pairing
assert solve([], 0) is None                # empty
print("all passed")
```

Note what those five asserts are: the given example, a case where the answer is not at the
start, duplicates, the self-pairing trap, and empty. That is the checklist applied.

## Brute-force cross-checking

When you have both a clever solution and an obvious one, and the clever one worries you,
say you would verify them against each other on random inputs:

> "If I had more time I'd check this greedy against an exhaustive search on small random
> inputs - that's how I'd convince myself the exchange argument is right."

That is exactly how the greedy in 23.18 was validated. You will rarely have time to write
it in the room, but saying it is the correct engineering instinct and it lands well.

## The closing paragraph

Have this memorised as a shape. It takes about forty seconds and it ends the question
properly:

> "So: time is O(n log n), dominated by the sort; space is O(n) for the map. I've traced the
> given example and it produces the expected output. On edge cases - empty returns zero,
> single element returns zero, all-duplicates gives the full pair count, and an element
> can't pair with itself because I record the value after the lookup. The one thing I
> haven't handled is unsorted input; if that's possible I'd add a sort, or bucket by time if
> the range is bounded. Would you like me to handle that, or look at a follow-up?"

Complexity, trace, edge cases, known gap, invitation. Every time.
