The **monotonic stack template in its simplest form**, wrapped in an indirection (two arrays)
that is really just a hash-map lookup. Learn the template here; 4.4 and 4.10 reuse it
verbatim, and 4.9 and 4.11 build on it.

> Note this is unrelated to 2.14 *Next Greater Element III*, despite the name - that one is
> next-permutation on digits. I, II and IV are monotonic-stack problems; III is the odd one
> out.

## 1. Problem statement

You are given two **distinct**-valued arrays `nums1` and `nums2`, where `nums1` is a
**subset** of `nums2`.

For each `nums1[i]`, find the **next greater element** in `nums2` - the first element to the
right of it *in `nums2`* that is greater. If none exists, the answer is `-1`.

Return an array of these answers, in the order of `nums1`.

```
nums1 = [4,1,2], nums2 = [1,3,4,2]  ->  [-1,3,-1]
nums1 = [2,4],   nums2 = [1,2,3,4]  ->  [3,-1]
```

## 2. Clarifying questions

1. **Are all values distinct?** Stated, and it matters - it means a value uniquely identifies
   a position, which is what makes the hash-map indirection work. Without distinctness you
   would have to map values to *lists* of positions.
2. **Is `nums1` guaranteed to be a subset of `nums2`?** Yes, so every query has an answer
   (possibly `-1`).
3. **"Next greater" means strictly greater, to the right, in `nums2`?** Yes, all three.
   Confirm "strictly" - with distinct values it does not matter, but say it.
4. **Return values or indices?** Values, and `-1` when absent.
5. **Sizes?** Small on LeetCode, so `O(n*m)` passes - but the `O(n+m)` solution is expected.

## 3. Intuition

The brute force: for each element of `nums1`, find it in `nums2`, then scan right for the
first larger value. `O(n * m)`.

Two independent improvements, and the answer combines them:

**(1) Decouple the arrays.** Compute the next-greater for **every** element of `nums2` once,
store it in a `dict`, then answer each `nums1` query with a lookup. The indirection between
the two arrays is now `O(1)` per query and `nums1` is irrelevant to the hard part.

**(2) Compute all next-greaters in one pass** with a monotonic stack.

### The monotonic stack

> **Keep a stack of values still waiting for their next greater element, in decreasing order
> from bottom to top. When a new value arrives, it is the answer for everything smaller than
> it on the stack - pop those and record. Then push the newcomer, which now waits its turn.**

Why it works: the stack is decreasing, so if the newcomer beats the top, it beats it *and* it
is the **nearest** such element (nothing between them was large enough, or that element would
have popped it first). Anything the newcomer does not beat stays waiting, correctly, because
the newcomer is not its answer.

Whatever remains on the stack at the end never found a greater element, so those get `-1`.

**Why it is `O(n)`**: each element is pushed exactly once and popped at most once, so the
total work across the whole loop is linear - even though a single iteration can pop many
elements. Say this sentence; the nested `while` always invites the question.

Because values are distinct, storing **values** on the stack is fine here. In the general
template (and in 4.4, 4.9, 4.10) you store **indices**, because you need positions to compute
distances or widths. Mention that you would store indices by default.

## 4. Approach

1. `next_greater = {}`, `stack = []`.
2. For each `x` in `nums2`:
   - while `stack` and `stack[-1] < x`: `next_greater[stack.pop()] = x`
   - `stack.append(x)`
3. Anything left on the stack has no greater element - either pre-fill with `-1` or use
   `dict.get(x, -1)`.
4. Return `[next_greater.get(x, -1) for x in nums1]`.

Using `.get(x, -1)` avoids a cleanup loop entirely - a small elegance worth taking.

## 5. Solution

```python
def next_greater_element(nums1, nums2):
    """For each value in nums1, the first greater value to its right in nums2, or -1.

    One monotonic-stack pass over nums2 computes the answer for EVERY element; nums1
    is then just a sequence of dictionary lookups. The stack holds values still
    waiting for their answer, decreasing from bottom to top.
    """
    next_greater = {}
    stack = []                      # values awaiting their next greater element

    for x in nums2:
        # x is the nearest greater element for everything smaller on the stack.
        while stack and stack[-1] < x:
            next_greater[stack.pop()] = x
        stack.append(x)

    # Anything still on the stack never found a greater element: .get supplies -1.
    return [next_greater.get(x, -1) for x in nums1]
```

```python
next_greater_element([4, 1, 2], [1, 3, 4, 2])       # [-1, 3, -1]
next_greater_element([2, 4], [1, 2, 3, 4])          # [3, -1]
next_greater_element([1], [1])                      # [-1]
next_greater_element([], [1, 2, 3])                 # []
next_greater_element([3, 1, 2], [3, 1, 2])          # [-1, 2, -1]
next_greater_element([5], [5, 4, 3, 2, 1])          # [-1]
next_greater_element([1, 2, 3], [3, 2, 1, 4])       # [4, 4, 4]
```

`[3,2,1,4]` is the case to trace: the stack builds up `[3,2,1]` (decreasing, all waiting),
then `4` arrives and pops **all three** in one iteration, answering `4` for each. That single
step shows why the amortised argument is needed, and it is a ten-second demonstration.

`[5,4,3,2,1]` -> everything stays on the stack and every answer is `-1`. The strictly
decreasing input is the worst case for stack depth and the best test of the `.get` default.

### The general template - what to write by default

```python
def next_greater_all(nums):
    """Index-based template: for each position, the VALUE of the next strictly greater
    element to its right, or -1. This is the version to reach for in general, because
    indices let you compute distances and widths."""
    result = [-1] * len(nums)
    stack = []                      # INDICES, values decreasing
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            result[stack.pop()] = x
        stack.append(i)
    return result


next_greater_all([1, 3, 4, 2])          # [3, 4, -1, -1]
next_greater_all([3, 2, 1, 4])          # [4, 4, 4, -1]
next_greater_all([5, 4, 3, 2, 1])       # [-1, -1, -1, -1, -1]
next_greater_all([1, 2, 3])             # [2, 3, -1]
next_greater_all([])                    # []
```

Writing this and then saying *"the actual problem is this plus a dictionary lookup"* is the
cleanest way to present the solution - it separates the technique from the packaging.

### The brute force

```python
def next_greater_element_brute(nums1, nums2):
    """O(n * m): locate, then scan right."""
    result = []
    for target in nums1:
        start = nums2.index(target)
        answer = -1
        for j in range(start + 1, len(nums2)):
            if nums2[j] > target:
                answer = nums2[j]
                break
        result.append(answer)
    return result


next_greater_element_brute([4, 1, 2], [1, 3, 4, 2])     # [-1, 3, -1]
next_greater_element_brute([2, 4], [1, 2, 3, 4])        # [3, -1]
next_greater_element_brute([1, 2, 3], [3, 2, 1, 4])     # [4, 4, 4]
```

## 6. Complexity

Let `n = len(nums1)`, `m = len(nums2)`.

| | Time | Space |
|---|---|---|
| Brute force | `O(n * m)` | `O(1)` extra |
| **Monotonic stack + hash map** | **`O(n + m)`** | `O(m)` |

The stack pass is `O(m)` amortised; the query pass is `O(n)` average (hashing). Space is the
map plus the stack, both `O(m)`.

## 7. How to present it

1. **Restate**, and confirm the values are distinct and `nums1` is a subset - then say why
   those two facts matter: distinctness lets you key a map by value, and the subset guarantee
   means every query resolves.
2. **Give the brute force** and its `O(n*m)`.
3. **Separate the two concerns out loud**: *"`nums1` is really just an indirection. Let me
   compute the next greater element for every position in `nums2` once, then answer each
   query with a lookup."* That reframing is the first scoring moment.
4. **Introduce the monotonic stack by its invariant**: *"I keep a stack of elements still
   waiting for their answer, in decreasing order. When a bigger value arrives, it's the
   answer for everything smaller that's waiting."*
5. **Justify nearness**: *"the stack is decreasing, so if the newcomer beats the top, nothing
   in between was big enough - it really is the nearest."*
6. **Write the general version first**, then wrap it with the dictionary.
7. **Trace `[3,2,1,4]`**, where `4` pops three elements at once.
8. **Give the amortised argument**: pushed once, popped at most once, so `O(m)`.
9. **Close**: `O(n + m)` time, `O(m)` space - and mention you would store indices rather than
   values in the general template.

## 8. Follow-ups and variations

- **"Next Greater Element II"** (LC 503, at 4.4) - the array is **circular**. Iterate twice
  (or use `i % n`) and do not push on the second pass. The natural next question.
- **"Daily Temperatures"** (LC 739, at 4.10) - return the **distance** to the next greater
  element rather than its value. Identical template, storing indices, answering
  `i - stack.pop()`.
- **"Previous smaller element."** Same scan, read `stack[-1]` *before* pushing, pop while the
  top is `>=` the newcomer.
- **"Next Greater Element IV"** (LC 2454) - the *second* next greater element. Two stacks.
- **"What if values can repeat?"** The value-keyed map breaks; use the index-based template
  and decide whether "greater" is strict.
- **"Largest Rectangle in Histogram"** (4.9) and **"Trapping Rain Water"** (4.1) - the same
  machinery applied to spans. Point at the family.
- **"Stock span"** - for each day, how many consecutive previous days had a lower price.
  Previous-greater with indices; a classic and a good one to name.
- **"Online version: elements arrive one at a time."** The stack works incrementally, but an
  element's answer is only known when a bigger one arrives - so you emit answers with a delay.
  Worth saying.

## 9. Pitfalls

- **Confusing this with Next Greater Element III**, which is 2.14 and a completely different
  problem.
- **Scanning `nums2` for each query** - `O(n*m)` and it misses the point.
- **Using `<=` instead of `<`** in the pop condition. Irrelevant with distinct values, but
  wrong in the general case where equal elements should not resolve each other.
- **Pushing before popping**, so an element pops itself.
- **Forgetting the leftover stack**, so unresolved elements get no answer. `.get(x, -1)` or
  pre-fill with `-1`.
- **Storing values instead of indices** in the general template, which makes distance-based
  variants (4.10) impossible.
- **Building the map from `nums1` instead of `nums2`.**
- **Claiming `O(m^2)`** because of the inner `while`.
