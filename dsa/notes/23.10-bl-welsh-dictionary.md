title: "23.10 Sort words by a custom (multi-character) alphabet"
---

> Reported once in R1 on 2025-10-10. Included in full because the follow-up (letters longer
> than two characters) turns a tidy sorting problem into a tokenisation problem, and that
> pivot is the whole point.

## Prompt as given

```
There is a Welsh dictionary whose alphabet is

  ["a","b","c","ch","d","dd","e","f","ff","g","ng","h","i","l","ll","m","n","o",
   "p","ph","r","rhe","s","t","th","u","w","y"]

Characters are either a single English character or a double one. When you tokenise a word,
give priority to the LONGER characters: in "ddb" the letters are "dd" and "b", not
"d","d","b".

Given a list of words, e.g. ["ddr","nah","dea","dd","ngah"], sort them by this alphabet and
return the sorted list.
```

Follow-up as given: *what if the alphabet has letters longer than two characters, e.g.
`"beeee"`, `"phe"`, `"rhe"`?*

Related: [Verifying an Alien Dictionary](https://leetcode.com/problems/verifying-an-alien-dictionary/),
[Alien Dictionary](https://leetcode.com/problems/alien-dictionary/) - both give you the
order and ask a different question. Here you are *given* the order and the difficulty is the
**tokenisation**.

## Clarifying questions to ask first

1. **What if a word contains a character not in the alphabet?** Raise, sort it last, or skip?
   Notice `"nah"` and `"ngah"` in the sample contain `h`, which *is* in the alphabet, but
   `"dea"` contains `e`, also fine. Ask anyway.
2. **Is the tokenisation greedy-longest-match, or is it "the tokenisation that sorts
   earliest"?** The prompt says give priority to the longer character, which is
   greedy-longest-match. Confirm, because the alternative is ambiguous and much harder.
3. **Are shorter words prefixes ranked first?** Standard lexicographic rule: `"dd"` before
   `"ddr"`. Confirm.
4. **Is the given alphabet list already in order?** Yes - the list *is* the ordering.
5. **Case sensitivity?** Assume lowercase.
6. **Can the alphabet change between calls?** Decides whether you precompute a trie once.

## Intuition

Two separate jobs, and keeping them separate is the answer:

**(1) Tokenise.** Turn `"ngah"` into the list of Welsh letters `["ng", "a", "h"]`. With the
longest-match rule this is a small greedy scan: at each position, try the longest alphabet
entry that matches here, consume it, continue.

**(2) Compare.** Once each word is a list of letters, replace each letter by its **rank** in
the alphabet and you have a list of integers. Python already sorts lists of integers
lexicographically, which is exactly the dictionary rule - including the "prefix sorts first"
behaviour, for free.

> **Tokenise into ranks, then let the language's tuple comparison do the sorting.**

The third idea is a performance one and it is what lifts the answer: do **not** re-tokenise
inside a comparator. A comparator runs `O(n log n)` times. Instead tokenise each word once
and sort by that precomputed key - the decorate-sort-undecorate pattern, which in Python is
just `sorted(words, key=...)`.

The follow-up (letters of any length) does not change the shape at all if you built the
tokeniser the right way. With a fixed max length of 2, people write `if word[i:i+2] in
alphabet`. That hard-codes the 2 and breaks. If instead you either (a) try lengths from the
longest alphabet entry downwards, or (b) walk a **trie** of the alphabet, the follow-up is
free. Building the trie version first is the strong play.

## Approach

1. Build `rank = {letter: index}` from the alphabet list.
2. Build a trie of the alphabet letters (or just note `max_len = max(len(l) for l in
   alphabet)`).
3. `tokenise(word)`: scan left to right; at each position take the longest alphabet entry
   matching there; append its rank; advance by its length. Raise if nothing matches.
4. `sorted(words, key=tokenise)`.

## Solution

```python
def welsh_sort(words, alphabet):
    """Sort words by a custom alphabet whose letters may be multiple characters long.

    Tokenisation is greedy longest-match, so in "ddb" the letters are "dd" and "b".
    """
    rank = {letter: i for i, letter in enumerate(alphabet)}
    max_len = max(len(letter) for letter in alphabet)

    def tokenise(word):
        """The word as a list of alphabet ranks. Lists of ints compare
        lexicographically, which is exactly the dictionary rule we want."""
        key = []
        i = 0
        while i < len(word):
            # Longest match first: try the longest possible letter and work down.
            for length in range(min(max_len, len(word) - i), 0, -1):
                piece = word[i:i + length]
                if piece in rank:
                    key.append(rank[piece])
                    i += length
                    break
            else:
                raise ValueError(f"{word!r}: no alphabet letter matches at position {i}")
        return key

    # Tokenise once per word (decorate-sort-undecorate), not once per comparison.
    return sorted(words, key=tokenise)
```

```python
alphabet = ["a","b","c","ch","d","dd","e","f","ff","g","ng","h","i","l","ll","m","n","o",
            "p","ph","r","rhe","s","t","th","u","w","y"]

welsh_sort(["ddr", "nah", "dea", "dd", "ngah"], alphabet)
# ['dea', 'dd', 'ddr', 'ngah', 'nah']
```

Worth checking that result out loud, because it is not the English order:

- `"dea"` tokenises to `["d","e","a"]` -> ranks `[4, 6, 0]`
- `"dd"`  -> `["dd"]` -> `[5]`
- `"ddr"` -> `["dd","r"]` -> `[5, 20]`
- `"ngah"` -> `["ng","a","h"]` -> `[10, 0, 11]`
- `"nah"` -> `["n","a","h"]` -> `[16, 0, 11]`

So `"dea"` `[4,...]` sorts before `"dd"` `[5]` because `d` (4) precedes `dd` (5) in the
Welsh alphabet - even though `"dd"` is the shorter English string. And `"ngah"` `[10,...]`
precedes `"nah"` `[16,...]` because `ng` comes before `n` in this alphabet, which is the
exact reverse of the English ordering of those two words. **Those two inversions are the
proof the tokenisation is doing real work**, and pointing them out is the best thing you can
say in this question.

### The trie version - the answer to the follow-up

```python
class AlphabetTrie:
    """Trie over the alphabet letters, for greedy longest-match tokenisation.
    Handles letters of any length with no change, which is exactly the follow-up.
    """

    def __init__(self, alphabet):
        self.root = {}
        for i, letter in enumerate(alphabet):
            node = self.root
            for ch in letter:
                node = node.setdefault(ch, {})
            node["$"] = i                       # "$" marks a complete letter, storing its rank

    def longest_match(self, word, start):
        """(rank, length) of the longest alphabet letter matching word[start:],
        or None if nothing matches."""
        node = self.root
        best = None
        for j in range(start, len(word)):
            node = node.get(word[j])
            if node is None:
                break
            if "$" in node:
                best = (node["$"], j - start + 1)   # remember the longest seen so far
        return best

    def tokenise(self, word):
        key = []
        i = 0
        while i < len(word):
            match = self.longest_match(word, i)
            if match is None:
                raise ValueError(f"{word!r}: no alphabet letter matches at position {i}")
            rank, length = match
            key.append(rank)
            i += length
        return key


def welsh_sort_trie(words, alphabet):
    trie = AlphabetTrie(alphabet)
    return sorted(words, key=trie.tokenise)
```

extended = ["a","beeee","c","ch","d","dd","e","f","ff","g","ng","h","i","l","ll","m","n",

welsh_sort_trie(["beeee", "ch", "c"], extended)

That error is correct and worth noticing: with `"b"` removed from the alphabet in favour of
`"beeee"`, the word `"be"` is not spellable. Raising beats silently mis-sorting, and it is
the behaviour to propose.

### If they insist on `cmp_to_key`

Some interviewers want to see an explicit comparator. It is the wrong tool here (it
re-tokenises `O(n log n)` times), but know it:

```python
import functools

def welsh_sort_cmp(words, alphabet):
    trie = AlphabetTrie(alphabet)
    cache = {w: trie.tokenise(w) for w in words}      # tokenise once, despite the comparator

    def compare(a, b):
        ka, kb = cache[a], cache[b]
        return (ka > kb) - (ka < kb)

    return sorted(words, key=functools.cmp_to_key(compare))
```

Note the `cache` - even when forced into a comparator, tokenise once. Say that out loud.

## Complexity

Let `n` be the number of words, `L` the maximum word length, `A` the alphabet size and `M`
the longest letter.

| | Time | Space |
|---|---|---|
| Build the rank dict / trie | `O(total alphabet characters)` | `O(same)` |
| Tokenise one word (scan version) | `O(L * M)` | `O(L)` |
| Tokenise one word (trie version) | `O(L)` amortised (each character visited once per match attempt, bounded by `M`) | `O(L)` |
| Sort | `O(n log n * L)` comparisons on the keys | `O(n * L)` |

Total: `O(n * L * M + n L log n)` for the scan version, `O(n L + n L log n)` for the trie.
The important sentence: **tokenisation happens `n` times, not `n log n` times** - that is the
decorate-sort-undecorate win, and it is the thing to state.

## How to present it

1. **Tokenise one word on the board by hand.** `"ngah"` -> `ng | a | h`. Then do `"ddb"`
   -> `dd | b` and point out that the naive character-by-character read gives `d | d | b`,
   which is a different word entirely.
2. **Separate the two jobs out loud**: "this is a tokenisation problem wearing a sorting
   problem's clothes. Once each word is a list of letter ranks, the sorting is free."
3. **Say the ranks idea**: map each letter to its index, and lists of ints already compare
   the way a dictionary does, including prefixes-first.
4. **Say you will tokenise once per word, not once per comparison**, and name
   decorate-sort-undecorate / `key=`.
5. **Write the scan version** if you want speed, but **say immediately** that you are
   avoiding hard-coding the maximum letter length, because the follow-up is obviously
   coming.
6. **When the follow-up lands**, either point out `max_len` already handles it, or upgrade to
   the trie and explain that a trie gives longest-match in one pass.
7. **Verify on the sample** and point out the two inversions (`dea` before `dd`, `ngah`
   before `nah`).

## Follow-ups and variations

- **"What if the alphabet has letters longer than two characters?"** The stated follow-up.
  If you wrote `word[i:i+2]`, you are rewriting. If you wrote `max_len` or a trie, you say
  "already handled" and show it. **Do not hard-code the 2.**
- **"What if a word contains a character not in the alphabet?"** Raise (shown), or define a
  sentinel rank. Ask which; raising is the defensible default.
- **"Can you avoid re-tokenising on every comparison?"** Yes - that is `key=` rather than
  `cmp_to_key`. This is the performance follow-up and it is easy marks.
- **"Is greedy longest-match always right?"** Not in general. If the alphabet were
  `["ab", "a", "bc"]`, the word `"abc"` greedily tokenises as `ab | c` and then fails on
  `c`, whereas `a | bc` succeeds. So greedy can fail where a backtracking tokeniser would
  not. **Raise this yourself** - it shows you understand the difference between a lexer and
  a parser. If they want it robust, tokenisation becomes a DP/word-break problem (see
  `23.20`), and if multiple tokenisations exist you must then define which one ranks.
- **"Verify a given list is already sorted"** (Alien Dictionary I). Tokenise and check
  adjacent pairs, `O(n L)` with no sort.
- **"Derive the alphabet order from a sorted word list"** (Alien Dictionary II). Now it is a
  topological sort over letter-precedence edges - a genuinely different problem, and worth
  naming so they know you know.
- **"Sort in reverse / by length then alphabet."** Tuple keys: `key=lambda w: (len(w),
  tokenise(w))`.

## Pitfalls

- **Hard-coding two-character letters.** The follow-up exists precisely to punish this.
- **Shortest-match instead of longest.** `"ddb"` becomes `d|d|b` and sorts wrong.
- **Sorting the raw strings** with a custom key applied per character. `"ng"` is one letter
  and must not be compared as `n` then `g`.
- **Re-tokenising inside a comparator**, turning `O(n)` tokenisations into `O(n log n)`.
- **Forgetting that shorter-prefix-first falls out for free** from list comparison, and
  hand-writing a buggy length check.
- **Using a `set` for the alphabet and losing the order.** The order *is* the data; you need
  the index.
- **`for ... else` confusion** in the scan version - the `else` belongs to the `for` and runs
  only when no `break` happened. If that construct is unfamiliar, use an explicit `matched`
  flag rather than getting it subtly wrong under pressure.
