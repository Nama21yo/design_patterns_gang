*LIFO for matching and nesting; monotonic stacks for next-greater and span problems.*

62 Bloomberg-tagged questions. Two of them were reported from real Bloomberg rounds -
**Decode String** (R1, 2025-11-06) and **Min Stack** (R1, twice) - and the
remove-3-consecutive-characters question (23.5) is a stack problem in disguise.

The Part splits cleanly into two halves that share a data structure but almost nothing else:

1. **Plain stacks**: matching, nesting, parsing, undo. The stack mirrors the *structure* of
   the input.
2. **Monotonic stacks**: next greater / previous smaller / spans. The stack holds *candidates
   awaiting resolution*.

Know which half you are in before you start writing.

## Half one: the stack as structure

A stack is the right tool whenever the input has **nesting** - something opens, something
closes, and the most recently opened thing must be resolved first.

### Matching and nesting

```python
def is_valid(s):
    """Balanced brackets. The stack holds what we are still waiting to close."""
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in pairs:
            # A closer must match the most recently opened bracket.
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)
    return not stack            # anything left open is unbalanced


is_valid("()[]{}")      # True
is_valid("(]")          # False
is_valid("([)]")        # False
is_valid("(")           # False
```

Two things to say out loud on any matching problem: the **mismatch** check (wrong closer) and
the **leftover** check (unclosed openers at the end). Forgetting the second is the classic
bug - `"("` must fail.

### Parsing with nesting

When brackets contain *content* that must be processed on closing, push the **context** you
will need to restore. Decode String (4.6) is the canonical example: push the accumulated
string and the repeat count, then pop and combine when the bracket closes.

The general shape:

```
on open:   push the current context, then start a fresh one
on close:  pop the saved context and merge the finished piece into it
```

That is recursive descent implemented with an explicit stack, and saying so is the right
framing.

### The "collapse adjacent things" family

Stacks also handle **cascading removals**, where deleting something makes two new neighbours
adjacent. The removal cascade falls out for free, because after popping, the new top *is* the
new neighbour. Reported Bloomberg question 23.5 is exactly this, and so is 4.13.

```python
def remove_adjacent_duplicates(s, k):
    """Remove k adjacent equal characters repeatedly (LC 1209)."""
    stack = []                      # [char, run_length]
    for ch in s:
        if stack and stack[-1][0] == ch:
            stack[-1][1] += 1
            if stack[-1][1] == k:
                stack.pop()
        else:
            stack.append([ch, 1])
    return "".join(c * n for c, n in stack)


remove_adjacent_duplicates("deeedbbcccbdaa", 3)     # 'aa'
remove_adjacent_duplicates("pbbcggttciiippooaais", 2)   # 'ps'
```

Storing `(char, count)` rather than individual characters is what makes it linear.

## Half two: the monotonic stack

This is the part worth real study, because it is not obvious and it answers a whole family of
questions with one template.

### What it solves

> **For each element, find the nearest element to its left (or right) that is greater (or
> smaller) than it.**

Four variants, and the direction of the scan plus the comparison operator determine which one
you get. Every "next greater", "previous smaller", "span", "largest rectangle" and "trapping
water" problem is one of these.

### The invariant

Keep a stack of indices whose values are **monotonic** (increasing or decreasing). When a new
element arrives:

- **Pop** everything the newcomer "resolves" - i.e. everything for which the newcomer is the
  answer.
- **Then push** the newcomer, which is now waiting for its own answer.

The stack holds elements that are still **unresolved**: each is waiting for the first later
element that beats it.

### The template

```python
def next_greater_right(nums):
    """For each index, the value of the next strictly greater element to its right,
    or -1 if none exists."""
    result = [-1] * len(nums)
    stack = []                      # indices, values DECREASING from bottom to top
    for i, x in enumerate(nums):
        # x resolves everything on the stack that is smaller than it.
        while stack and nums[stack[-1]] < x:
            result[stack.pop()] = x
        stack.append(i)
    return result


next_greater_right([2, 1, 2, 4, 3])     # [4, 2, 4, -1, -1]
next_greater_right([1, 2, 3])           # [2, 3, -1]
next_greater_right([3, 2, 1])           # [-1, -1, -1]
```

**Choosing the four variants:**

| Want | Scan | Pop while |
|---|---|---|
| next greater to the **right** | left to right | `stack top < x` |
| next smaller to the **right** | left to right | `stack top > x` |
| previous greater to the **left** | left to right, read `stack[-1]` **before** pushing | `stack top <= x` |
| previous smaller to the **left** | left to right, read `stack[-1]` **before** pushing | `stack top >= x` |

The "previous" variants need no second pass: after popping, whatever remains on top *is* the
nearest unresolved element to the left. That is the trick that surprises people.

```python
def previous_smaller(nums):
    """For each index, the value of the nearest strictly smaller element to its left."""
    result = [-1] * len(nums)
    stack = []                      # values INCREASING from bottom to top
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] >= x:
            stack.pop()
        # Whatever survives on top is the nearest smaller element to the left.
        result[i] = nums[stack[-1]] if stack else -1
        stack.append(i)
    return result


previous_smaller([2, 1, 2, 4, 3])       # [-1, -1, 1, 2, 2]
previous_smaller([1, 2, 3])             # [-1, 1, 2]
```

### Strict or non-strict?

`<` versus `<=` decides how **equal** values are treated. It matters when duplicates exist -
in histogram problems it determines whether equal bars are treated as one block or separately.
**Ask, or pick one and state it.** For counting problems where double counting must be
avoided (e.g. *Sum of Subarray Minimums*), the standard fix is to use strict on one side and
non-strict on the other.

### Why it is O(n)

> **Each index is pushed exactly once and popped at most once, so the total work across the
> whole loop is `O(n)` - even though one iteration can pop many elements.**

Memorise that sentence. It is required on every monotonic-stack question, because the nested
`while` always looks quadratic.

### Spans and rectangles

The most valuable application: for each element, the **range over which it is the minimum (or
maximum)** is bounded by its previous-smaller and next-smaller neighbours. That single idea
solves Largest Rectangle in Histogram (4.9), Maximal Rectangle (4.11), Sum of Subarray
Minimums, and it underlies one solution to Trapping Rain Water (4.1).

```python
def largest_rectangle(heights):
    """Largest rectangle in a histogram. Each bar's rectangle extends until a strictly
    shorter bar on each side; the sentinel 0 flushes the stack at the end."""
    stack = []                      # indices, heights increasing
    best = 0
    for i, h in enumerate(heights + [0]):       # sentinel forces a final flush
        while stack and heights[stack[-1]] >= h:
            height = heights[stack.pop()]
            # Left bound is the new stack top; right bound is i.
            width = i if not stack else i - stack[-1] - 1
            best = max(best, height * width)
        stack.append(i)
    return best


largest_rectangle([2, 1, 5, 6, 2, 3])       # 10
largest_rectangle([2, 4])                   # 4
largest_rectangle([])                       # 0
```

The **sentinel** (`+ [0]`) is a technique worth internalising generally: appending a value
that resolves everything avoids writing a separate drain loop after the main one.

## Queues and deques

- **`collections.deque`** for BFS queues and for sliding-window extrema (3.2). Never use a
  list with `pop(0)` - that is `O(n)` per call.
- **Monotonic deque** = monotonic stack that also evicts from the front when elements expire.
  That is the only difference, and it is why 3.2 lives in Part 3 rather than here.
- **Queue from two stacks** (and stack from two queues) are classic design questions;
  the two-stack queue is `O(1)` amortised by the same push-once-pop-once argument.

## Recognition signals

**Plain stack:** "valid", "balanced", "matching", "nested", "parse", "evaluate", "undo",
"backspace", "simplify path", "remove adjacent".

**Monotonic stack:** "next greater", "previous smaller", "warmer temperature", "span",
"largest rectangle", "trapped water", "visible from", "remove k digits to make it smallest",
"how many days until".

**Neither:** if you need the max of a *fixed-size window*, that is a monotonic **deque**
(Part 3). If you need the k largest, that is a heap (Part 10).

## How to talk about it

- "There's nesting here, so a stack - each closer resolves the most recent opener."
- "I also need to check the stack is empty at the end, or unclosed brackets pass."
- "For each element I want the nearest larger one to the right - that's a monotonic stack."
- "The stack holds elements still waiting for their answer, in decreasing order."
- "When this element arrives, it resolves everything smaller than it - those can never find a
  nearer larger neighbour."
- "Each index is pushed once and popped once, so it's O(n) amortised despite the inner loop."
- "I'll append a sentinel so the stack drains without a separate cleanup loop."
- "Storing (character, count) instead of individual characters keeps it linear."

## Common pitfalls across this Part

- **Forgetting the final emptiness check** in matching problems.
- **Popping from an empty stack** - guard every `pop` and `[-1]`.
- **Storing values instead of indices** in a monotonic stack, so you cannot compute widths.
- **Getting `<` versus `<=` wrong** with duplicates.
- **Forgetting to drain the stack** at the end (or use a sentinel).
- **Claiming `O(n^2)`** because of the nested `while`.
- **Using a list as a queue** with `pop(0)`.
- **Computing widths with the wrong bound** in rectangle problems - it is
  `i - stack[-1] - 1` after popping, not `i - popped_index`.
