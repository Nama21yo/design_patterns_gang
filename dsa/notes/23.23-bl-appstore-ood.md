---

> Reported once in R3 on 2025-11-21, with a warning: *"I was caught totally off guard, it is
> not the typical system design question you'd expect. It was an OOP design question -
> writing classes, methods, attributes, coding in an editor."*
>
> **Bloomberg sometimes replaces the distributed-systems round with a low-level design
> round.** Be ready for it. If you walk in expecting load balancers and get asked to
> refactor two classes, the surprise itself costs you time.

## Prompt as given

```
You have an AppStore where applications are listed, like Google Play or the App Store. It
works fine today, but as the user base grew its performance started degrading. Find the
bottleneck in the class design and improve it. There are also new features to implement.
The interface must stay backward compatible, because many users rely on the current
architecture.

  class AppEntry:
      app_id, app_name, publisher_id, publisher_name      (+ getters/setters)

  class AppStore:
      inventory = {app_id: AppEntry}                      (+ getters/setters)

The bottleneck: AppStore.get_publisher_name(pub_id) scans every app in the inventory.
AppEntry.get_publisher_name() is the method that causes the design trouble.

New functionality to add:
  get_all_published_app(pub_id)    - all apps by a publisher
  rename_publisher(pub_id, new_name)
```

## Clarifying questions to ask first

1. **What exactly must stay backward compatible?** The method *signatures* and their
   *semantics*, or the attributes too? If external code reads `app.publisher_name` directly
   as an attribute, that constrains you far more than if it calls `get_publisher_name()`.
   **This is the most important question in the round** - ask it first.
2. **Is `rename_publisher` expected to be visible immediately through existing `AppEntry`
   objects that callers already hold?** Almost certainly yes, and it is the crux.
3. **Read-heavy or write-heavy?** App listings are read-heavy; that justifies indexes.
4. **Roughly how many apps and publishers?**
5. **Single process, or is this shared across threads?**
6. **Can a publisher exist with no apps?** Decides whether publishers live only inside apps.
7. **Can I add classes, or only modify these two?** The prompt says you may add anything.

## The actual problem: duplicated state

The starting design stores `publisher_name` **on every AppEntry**. That single decision
causes all three symptoms:

1. **`get_publisher_name(pub_id)` is `O(n)`** - to find a publisher's name you must scan the
   inventory until you find any app by that publisher.
2. **`get_all_published_app(pub_id)` would also be `O(n)`** for the same reason.
3. **`rename_publisher` is `O(n)` *and* error-prone** - the name is copied into thousands of
   `AppEntry` objects, so a rename must find and update every one. Miss one and the data is
   now inconsistent, with two different names for the same publisher.

This is textbook **denormalisation without an index**. The fix is the database fix:

> **Normalise: make `Publisher` its own object, store it once, and have `AppEntry` hold a
> reference to it rather than a copy of its name. Then add the indexes the queries need.**

After that:
- The publisher's name exists in exactly one place, so `rename_publisher` is `O(1)` and
  cannot produce an inconsistency.
- `AppEntry.get_publisher_name()` still works - it just delegates to the referenced
  `Publisher`. **Backward compatible, and automatically correct after a rename**, because it
  reads through the reference rather than from a stale copy.
- `publisher_id -> set of app_ids` makes `get_all_published_app` `O(k)` in the result size.

The sentence to say: *"the name is duplicated across every app, so it is both a lookup
problem and a consistency problem; I'll store it once and reference it."*

## Approach

1. Add a `Publisher` class holding `publisher_id` and the mutable `name`.
2. `AppEntry` holds a `Publisher` reference instead of `publisher_name`.
3. Keep `AppEntry.get_publisher_name()` and `AppEntry.publisher_name` working, the latter as
   a **property** that reads through the reference.
4. `AppStore` gains:
   - `publishers: dict[pub_id] -> Publisher`
   - `apps_by_publisher: dict[pub_id] -> set[app_id]`
5. Maintain both indexes in `add_app` / `remove_app`.

## Solution

```python
class Publisher:
    """A publisher's identity and name, stored exactly once.

    Every AppEntry references this object rather than copying the name, so a rename
    is a single assignment and can never leave two apps disagreeing.
    """

    __slots__ = ("publisher_id", "name")

    def __init__(self, publisher_id, name):
        self.publisher_id = publisher_id
        self.name = name


class AppEntry:
    """One application.

    The original class stored publisher_name as a plain attribute. It is now a
    read-through property backed by the shared Publisher, so existing callers that
    read `entry.publisher_name` or call `entry.get_publisher_name()` keep working -
    and now see renames immediately instead of a stale copy.
    """

    __slots__ = ("app_id", "app_name", "_publisher")

    def __init__(self, app_id, app_name, publisher):
        self.app_id = app_id
        self.app_name = app_name
        self._publisher = publisher

    # --- unchanged public surface -------------------------------------------------
    def get_app_id(self):
        return self.app_id

    def get_app_name(self):
        return self.app_name

    def get_publisher_id(self):
        return self._publisher.publisher_id

    def get_publisher_name(self):
        # O(1) delegation. Previously this either held a stale copy or forced a scan.
        return self._publisher.name

    @property
    def publisher_id(self):
        return self._publisher.publisher_id

    @property
    def publisher_name(self):
        """Kept as an attribute for callers that never used the getter."""
        return self._publisher.name


class AppStore:
    """Inventory plus the indexes the queries actually need."""

    def __init__(self):
        self.inventory = {}             # app_id -> AppEntry   (unchanged, still public)
        self._publishers = {}           # publisher_id -> Publisher
        self._apps_by_publisher = {}    # publisher_id -> set of app_id

    # --- writes -------------------------------------------------------------------
    def add_app(self, app_id, app_name, publisher_id, publisher_name):
        """Signature unchanged: callers still pass a publisher name.

        The first name seen for a publisher wins; later apps reference the existing
        Publisher rather than overwriting it, so adding an app cannot silently rename
        a publisher.
        """
        publisher = self._publishers.get(publisher_id)
        if publisher is None:
            publisher = Publisher(publisher_id, publisher_name)
            self._publishers[publisher_id] = publisher

        entry = AppEntry(app_id, app_name, publisher)
        self.inventory[app_id] = entry
        self._apps_by_publisher.setdefault(publisher_id, set()).add(app_id)
        return entry

    def remove_app(self, app_id):
        entry = self.inventory.pop(app_id, None)
        if entry is None:
            return False
        pid = entry.publisher_id
        apps = self._apps_by_publisher.get(pid)
        if apps is not None:
            apps.discard(app_id)
            if not apps:
                # Keep the Publisher object: it may be referenced elsewhere, and a
                # publisher with zero apps is still a real publisher.
                del self._apps_by_publisher[pid]
        return True

    # --- reads --------------------------------------------------------------------
    def get_app(self, app_id):
        return self.inventory.get(app_id)

    def get_publisher_name(self, publisher_id):
        """Was O(n): it scanned the whole inventory. Now a single dict lookup."""
        publisher = self._publishers.get(publisher_id)
        return publisher.name if publisher else None

    def get_all_published_app(self, publisher_id):
        """New. O(k) in the number of apps by this publisher, not O(total apps)."""
        return [self.inventory[app_id]
                for app_id in self._apps_by_publisher.get(publisher_id, ())]

    def rename_publisher(self, publisher_id, new_name):
        """New. O(1): the name lives in one place, so every AppEntry that references
        this Publisher reflects the change immediately - no sweep, no inconsistency."""
        publisher = self._publishers.get(publisher_id)
        if publisher is None:
            return False
        publisher.name = new_name
        return True
```

```python
store = AppStore()
store.add_app("a1", "Terminal",  "p1", "Bloomberg LP")
store.add_app("a2", "Anywhere",  "p1", "Bloomberg LP")
store.add_app("a3", "Something", "p2", "Other Corp")

store.get_publisher_name("p1")                          # 'Bloomberg LP'
sorted(a.app_name for a in store.get_all_published_app("p1"))
# ['Anywhere', 'Terminal']

entry = store.get_app("a1")          # a reference a caller might hold for a long time
entry.get_publisher_name()                              # 'Bloomberg LP'
entry.publisher_name                                    # 'Bloomberg LP'

store.rename_publisher("p1", "Bloomberg L.P.")

entry.get_publisher_name()                              # 'Bloomberg L.P.'  - no sweep
entry.publisher_name                                    # 'Bloomberg L.P.'
store.get_app("a2").publisher_name                      # 'Bloomberg L.P.'
store.get_app("a3").publisher_name                      # 'Other Corp'      - untouched
```

That last block is the demo to run in the interview. **An `AppEntry` the caller grabbed
before the rename shows the new name afterwards, with no sweep over the inventory.** That is
the payoff of normalising, and it is the thing to point at.

## Complexity

| Operation | Before | After |
|---|---|---|
| `get_publisher_name(pub_id)` | `O(n)` scan | `O(1)` |
| `AppEntry.get_publisher_name()` | `O(1)` but stale after a rename | `O(1)` and always current |
| `get_all_published_app(pub_id)` | `O(n)` scan | `O(k)`, `k` = apps by that publisher |
| `rename_publisher(pub_id, name)` | `O(n)` sweep, risk of partial update | `O(1)`, atomic by construction |
| `add_app` / `remove_app` | `O(1)` | `O(1)` |

Extra space is `O(publishers + apps)` for the two indexes - and note that it is *less* total
memory than before, because thousands of duplicated name strings collapse into one object
per publisher. (In CPython, interning may already have shared the strings, but the object
model no longer *depends* on that.)

## How to present it

1. **Say what kind of round you think it is** and ask about the compatibility contract. Those
   two questions set up everything else.
2. **Diagnose before designing.** Say the diagnosis in one sentence: *"the publisher name is
   duplicated onto every app, which makes lookup `O(n)`, rename `O(n)`, and consistency a
   hazard."* Naming the root cause rather than the symptom is the scored moment.
3. **Name the fix in database terms**: normalise into a `Publisher` entity, then add the
   indexes each query needs. Interviewers recognise this vocabulary.
4. **Address backward compatibility explicitly** before writing code: "`get_publisher_name()`
   keeps its signature and delegates; `publisher_name` becomes a read-through property so
   even attribute access keeps working."
5. **Write `Publisher` first**, then the changed parts of `AppEntry`, then `AppStore`. Do not
   retype the unchanged getters - say "the rest of the getters are unchanged" and move on.
   Time is the constraint in this round.
6. **Demo the rename through a previously held reference.** It proves the design, and it is
   quick.
7. **Then raise what you did not do**: thread safety, persistence, publisher lifecycle. Offer
   them rather than waiting.

## Follow-ups and variations

- **"How do you keep `AppEntry.get_publisher_name()` working?"** Delegation through the
  `Publisher` reference. Emphasise that it is not merely *still working* - it is now *more*
  correct, because it cannot go stale.
- **"What if callers read `entry.publisher_name` as an attribute?"** The `@property`. This is
  why the first clarifying question matters; in a language without properties (Java, C++)
  you would instead keep a getter and deprecate direct field access, which is a much bigger
  migration. Worth saying.
- **"Make it thread safe."** `rename_publisher` is a single attribute assignment, which is
  atomic in CPython, so readers see either the old or the new name and never a torn value.
  `add_app` mutates three structures and **does** need a lock. Use a single store-level
  `RLock` for writes; reads of a dict are safe under the GIL but not under a concurrent
  resize, so guard them too if you want to be strict, or use a copy-on-write index.
- **"Publishers with no apps."** `remove_app` deliberately keeps the `Publisher` object. If
  they want publishers garbage-collected, add explicit `add_publisher` /
  `remove_publisher` and reference-count, or just leave them - they are tiny.
- **"Two apps declare the same publisher_id with different names."** The current code lets
  the first one win, silently. Offer three policies: first wins, last wins, or raise. Say
  that in a real system publishers would be registered separately and `add_app` would take a
  `publisher_id` only - which is the *right* API and the one you would migrate towards.
- **"Search apps by name."** Another index: `name -> set of app_ids`, or a trie for prefix
  search. Note the general principle - each query pattern you support costs one index to
  maintain on write.
- **"Rank apps by downloads / rating."** Now you want a heap or a sorted structure per
  category, and the write cost goes up. Good moment to discuss read/write trade-offs.
- **"How would you migrate the existing live system?"** Ship the new classes behind the old
  interface, backfill the `Publisher` objects from existing `AppEntry` data, verify both
  paths agree, then remove the duplicated field. Mentioning a staged migration with a
  verification phase is a strong senior signal.
- **"Persist it."** `publishers` and `apps` become tables with a foreign key, and the indexes
  become database indexes. Point out that you have just rediscovered third normal form.

## Pitfalls

- **Jumping to code before diagnosing.** The prompt asks you to *find* the bottleneck; say
  what it is.
- **Fixing only `get_publisher_name`** with a cache, leaving the duplicated name in place -
  so `rename_publisher` is still an `O(n)` sweep with a consistency hazard. Treat the cause,
  not the symptom.
- **Breaking the interface.** Removing `publisher_name` or changing a signature fails the
  stated constraint, which is the one hard requirement in the prompt.
- **Copying the publisher name into `AppEntry` "for speed"** after normalising, which
  reintroduces the exact bug.
- **Forgetting to maintain `apps_by_publisher` in `remove_app`**, leaving dangling app ids
  that `get_all_published_app` will then fail to look up.
- **Returning the internal `set` from `get_all_published_app`**, letting callers mutate your
  index. Return a list or a copy.
- **Over-engineering.** No abstract factories, no observers. The round rewards a tight,
  correct refactor with a clear justification.
- **Expecting a distributed system design round and freezing.** Have this pattern -
  *duplicated state, normalise and index* - ready as a template; it covers most LLD
  refactoring prompts.
