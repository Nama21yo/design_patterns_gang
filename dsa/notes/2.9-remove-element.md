**Link:** https://leetcode.com/problems/remove-element
**Difficulty:** Easy | **LeetCode #27**
**Bloomberg frequency:** 38% at three months.

The third member of the read/write family, after 2.2 and 2.7. What makes it worth its own
page is that here the order of the surviving elements **does not** matter - which unlocks a
second, cheaper algorithm and gives you a genuinely interesting trade-off to discuss.

## 1. Problem statement

Given an integer array `nums` and an integer `val`, remove **all occurrences** of `val` in
place. The order of the remaining elements **may be changed**.

Return `k`, the number of elements that are not `val`. The first `k` positions of `nums` must
hold those elements; beyond `k` does not matter.

```
nums = [3,2,2,3],       val = 3  ->  k = 2, nums = [2,2,_,_]
nums = [0,1,2,2,3,0,4,2], val = 2 ->  k = 5, nums = [0,1,4,0,3,_,_,_]  (any order)
```

## 2. Clarifying questions

1. **Does the order of the remaining elements matter?** **No** - and this is the whole
   difference from 2.2 and 2.7. Ask it, because it is what licenses the swap-with-the-end
   approach. The second example's expected output is explicitly "in any order".
2. **In place?** Yes, `O(1)` extra space.
3. **What goes beyond index `k`?** Anything.
4. **Return the count or the array?** The count; mutate as a side effect.
5. **Is `val` guaranteed present?** No. `[1,2,3]` with `val = 5` returns 3.
6. **Should I minimise writes?** The interesting follow-up - see below.

## 3. Intuition

Two valid strategies, and choosing between them is the content of the question.

### Strategy A - compaction (stable)

The familiar read/write scan:

> Copy every element that is **not** `val` forward to `nums[write]`.

Preserves order. Performs one write per **kept** element, so `n - k` writes are avoided but
kept elements are all rewritten - up to `n` writes.

### Strategy B - swap with the end (unstable)

Since order is free:

> When you find `val`, replace it with the **last** element and shrink the array's logical
> end. Do not advance the read pointer - the element you just pulled in has not been checked.

Performs one write per **removed** element. If `val` is rare, this is dramatically fewer
operations: removing one element from an array of a million does one write, not a million.

That is the trade to articulate:

| | Writes | Order preserved |
|---|---|---|
| Compaction | `O(number kept)` | yes |
| Swap with end | `O(number removed)` | no |

**Pick based on which is rarer**, and say so. When `val` is rare, B wins; when almost
everything is `val`, A wins. Interviewers like this answer because it is the actual
engineering judgement rather than a memorised template.

## 4. Approach

**Compaction:**
1. `write = 0`; for each `x`: if `x != val`, `nums[write] = x`, `write += 1`.
2. Return `write`.

**Swap with end:**
1. `i = 0`, `end = len(nums)`.
2. While `i < end`:
   - if `nums[i] == val`: `nums[i] = nums[end - 1]`, `end -= 1` **(do not advance `i`)**
   - else `i += 1`
3. Return `end`.

## 5. Solution

```python
def remove_element(nums, val):
    """Remove every occurrence of val in place; returns the count of survivors.

    Compaction: preserves order, one write per kept element.
    """
    write = 0
    for x in nums:
        if x != val:
            nums[write] = x
            write += 1
    return write
```

```python
data = [3, 2, 2, 3]
remove_element(data, 3)             # 2
data[:2]                            # [2, 2]

data = [0, 1, 2, 2, 3, 0, 4, 2]
remove_element(data, 2)             # 5
data[:5]                            # [0, 1, 3, 0, 4]

remove_element([], 1)               # 0
remove_element([1, 1, 1], 1)        # 0
remove_element([1, 2, 3], 5)        # 3
```

### The swap-with-end version

```python
def remove_element_swap(nums, val):
    """Unstable, but does one write per REMOVED element - far fewer when val is rare.

    On a match, the last element is pulled into the hole and the logical end shrinks.
    `i` deliberately does not advance: the value just pulled in is unexamined.
    """
    i = 0
    end = len(nums)
    while i < end:
        if nums[i] == val:
            nums[i] = nums[end - 1]
            end -= 1                # NOT i += 1 - recheck this slot next iteration
        else:
            i += 1
    return end


data = [3, 2, 2, 3]
remove_element_swap(data, 3)        # 2
sorted(data[:2])                    # [2, 2]

data = [0, 1, 2, 2, 3, 0, 4, 2]
remove_element_swap(data, 2)        # 5
sorted(data[:5])                    # [0, 0, 1, 3, 4]

remove_element_swap([1, 1, 1], 1)   # 0
remove_element_swap([1, 2, 3], 5)   # 3
remove_element_swap([], 1)          # 0
```

Note the outputs are compared with `sorted(...)`, because the order is genuinely
unspecified - that is the correct way to test an unstable algorithm, and saying so is a
small but real signal.

The `end -= 1` **without** `i += 1` is the one subtle line. Trace `[3,2,2,3]` with `val = 3`:
- `i=0`: `nums[0]` is 3, pull in `nums[3]` (also 3), `end` becomes 3. Array `[3,2,2,3]`,
  logical `[3,2,2]`. `i` stays 0.
- `i=0` again: `nums[0]` is still 3, pull in `nums[2]` (a 2), `end` becomes 2. Logical
  `[2,2]`. `i` stays 0.
- `i=0`: `nums[0]` is 2, advance. `i=1`: 2, advance. `i=2 == end`, stop. Return 2.

Had `i` advanced on the first step, the second `3` pulled in from the end would never have
been checked. This is exactly the asymmetry from the Dutch national flag partition in the
primer, and it is worth connecting them.

## 6. Complexity

| | Time | Writes | Space |
|---|---|---|---|
| `nums.remove(val)` in a loop | `O(n^2)` | many | `O(1)` |
| List comprehension into a new list | `O(n)` | `O(n)` | `O(n)` - disallowed |
| Compaction | `O(n)` | up to `n` | `O(1)` |
| Swap with end | `O(n)` | number of removals | `O(1)` |

Both good versions are a single pass. They differ only in the constant - which is exactly
what the "minimise operations" style of follow-up is about.

## 7. How to present it

1. **Restate**, and **ask the order question immediately**: "The remaining elements can be in
   any order? Then I have two options, and the better one depends on how common `val` is."
   Opening with that turns a two-minute Easy into a design conversation.
2. **Describe both strategies** in a sentence each, with the write counts.
3. **Pick one and justify**: "I'll write the compaction version first because it is the safer
   default and preserves order for free; then I'll show the swap version which does fewer
   writes when `val` is rare."
4. **Write the compaction version.** Four lines.
5. **Write the swap version**, and call out `end -= 1` without `i += 1` as you type it,
   explaining the trap.
6. **Test** `[1,1,1]` with `val = 1` (returns 0), `[1,2,3]` with `val = 5` (returns 3, no
   writes at all in the swap version), and the empty array.
7. **Close**: both `O(n)` time and `O(1)` space; the choice is about write count and
   stability.

## 8. Follow-ups and variations

- **"Minimise the number of writes."** The swap version, and quantify it: one write per
  removal. On `[1,2,3]` with `val = 5` it performs **zero** writes.
- **"Now preserve the order."** Compaction - and note the swap version is now disallowed.
  The pair of questions is a neat illustration that a constraint you were *given* can be
  worth exploiting.
- **"Remove duplicates from a sorted array."** LC 26, at 2.2 - same skeleton, predicate
  compares against the last kept value.
- **"Move zeroes to the end preserving order."** LC 283, at 2.7 - compaction plus a fill.
- **"Remove all elements from a linked list"** (LC 203). Dummy head, then relink past
  matches. `O(n)`, `O(1)`, order naturally preserved.
- **"Remove elements satisfying a predicate, not equal to a value."** Replace `x != val`
  with `not predicate(x)`; nothing else changes. Worth saying, since it shows the shape
  generalises.
- **"Partition into `< val`, `== val`, `> val`."** Dutch national flag - three pointers, one
  pass (see the Part 2 primer).
- **"Count how many were removed."** `len(nums) - k`.
- **"What if the array is huge and `val` is extremely rare?"** The swap version, and note it
  is effectively `O(removals)` writes with one `O(n)` scan - which is unavoidable, since you
  must at least look at every element to find the matches.

## 9. Pitfalls

- **Advancing `i` after swapping in from the end**, so the pulled-in element is never
  examined. `[3,2,2,3]` with `val = 3` exposes it.
- **Using `nums.remove(val)` in a loop** - `O(n^2)`, and it mutates the length while you are
  iterating.
- **Iterating with `for i, x in enumerate(nums)` while deleting**, which skips elements.
- **Returning the array instead of the count.**
- **Truncating with `del nums[k:]`** - unnecessary; the tail is explicitly irrelevant.
- **Assuming order must be preserved** and therefore never offering the cheaper option. The
  problem says it need not be; use that.
- **Comparing the unstable version's output against a fixed expected array** in your own
  tests. Sort first, or compare as a multiset.
