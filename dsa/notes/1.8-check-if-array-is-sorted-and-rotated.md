**Link:** https://leetcode.com/problems/check-if-array-is-sorted-and-rotated
**Difficulty:** Easy | **LeetCode #1752**
**Bloomberg frequency:** 62% at three months.

Short, and a good warm-up for the rotated-array family in Part 5 (Search in Rotated Sorted
Array, Find Minimum in Rotated Sorted Array). The trick is finding the right *invariant* to
count rather than trying to locate the rotation point.

## 1. Problem statement

Given an array `nums`, return `True` if it was originally sorted in **non-decreasing** order
and then rotated some number of positions (**including zero**). Otherwise return `False`.

There may be **duplicates** in the original array.

```
nums = [3,4,5,1,2]  ->  True      original [1,2,3,4,5], rotated by 2
nums = [2,1,3,4]    ->  False
nums = [1,2,3]      ->  True      rotated by 0
```

## 2. Clarifying questions

1. **Non-decreasing or strictly increasing?** Non-decreasing - duplicates are allowed and are
   explicitly mentioned. This matters: with `<` instead of `<=` you would reject `[1,1,2]`.
2. **Is a rotation of zero allowed?** Yes - a plain sorted array must return `True`.
3. **Can the array be empty or single-element?** LeetCode guarantees at least 1. A single
   element is trivially `True`.
4. **Return a boolean, or the rotation amount?** Boolean here; the amount is a natural
   follow-up.
5. **Is the array guaranteed to contain only the rotated form**, i.e. no other mutations?
   Yes.

## 3. Intuition

The tempting approach is to find the rotation point and then verify both halves are sorted.
That works but involves more bookkeeping than necessary, and the duplicate handling is
fiddly.

Instead, think about what a rotated sorted array looks like **as a cycle**. Walk the array
treating it as circular, comparing each element with the next. In a sorted array, every
comparison satisfies `nums[i] <= nums[i+1]`. Rotating the array moves the "wrap point"
somewhere into the middle, and at exactly that one place the comparison fails.

> **An array is a rotated sorted array if and only if, reading it circularly, the number of
> positions where `nums[i] > nums[i+1]` is at most one.**

Zero such "drops" means it was never rotated (or rotated by a full turn). Exactly one drop
means it was rotated at that point. Two or more means no rotation can produce it.

Counting circularly is what makes this clean: you compare `nums[n-1]` with `nums[0]` as
well, using `nums[(i + 1) % n]`. Without the wrap-around comparison, `[2,1,3,4]` would look
like it has one drop and be wrongly accepted - the wrap comparison `4 > 2` is the second
drop that rejects it.

That single observation is the whole solution, and it avoids ever locating the pivot.

## 4. Approach

1. `drops = 0`.
2. For each `i` in `0..n-1`: if `nums[i] > nums[(i + 1) % n]`, increment `drops`.
3. Return `drops <= 1`.

Use `>` not `>=`, so equal neighbours (duplicates) are not counted as drops.

## 5. Solution

```python
def check(nums):
    """True if nums is a non-decreasing array rotated by some amount (possibly zero).

    Read circularly, a sorted array has no position where an element exceeds its
    successor; rotating introduces exactly one. So at most one such 'drop' is allowed.
    """
    n = len(nums)
    drops = 0
    for i in range(n):
        # The modulo makes the last-to-first comparison part of the count, which is
        # what rejects arrays like [2,1,3,4].
        if nums[i] > nums[(i + 1) % n]:
            drops += 1
    return drops <= 1
```

```python
check([3, 4, 5, 1, 2])          # True
check([2, 1, 3, 4])             # False
check([1, 2, 3])                # True
check([1, 1, 1])                # True
check([2, 1])                   # True
check([1, 3, 2])                # False
check([6, 10, 6, 11])           # False
check([3, 1, 3, 3, 3])          # True
check([1])                      # True
```

Two worth narrating:

- `[2,1,3,4]` -> the comparisons are `2>1` (drop), `1>3` no, `3>4` no, and the wrap `4>2`
  (drop). Two drops, so `False`. Without the wrap comparison you would get one drop and
  wrongly return `True`.
- `[3,1,3,3,3]` -> only `3>1` drops; the wrap is `3>3` which is not a drop because `>` is
  strict. `True`, original `[1,3,3,3,3]`.

### The pivot-finding version, for contrast

```python
def check_via_pivot(nums):
    """Locate the rotation point, then verify. More code, same complexity, and the
    duplicate handling is easier to get wrong."""
    n = len(nums)
    pivot = -1
    for i in range(n - 1):
        if nums[i] > nums[i + 1]:
            if pivot != -1:
                return False            # a second break means it cannot be a rotation
            pivot = i + 1
    if pivot == -1:
        return True                     # already sorted, rotation of zero
    # The tail must be sorted and must not exceed the head's first element.
    return nums[-1] <= nums[0]


check_via_pivot([3, 4, 5, 1, 2])        # True
check_via_pivot([2, 1, 3, 4])           # False
check_via_pivot([1, 2, 3])              # True
check_via_pivot([3, 1, 3, 3, 3])        # True
```

Both are `O(n)`. Prefer the circular count - it is five lines and has one comparison, versus
three branches. Show the pivot version only if asked how else you would do it.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Circular drop count | `O(n)` | `O(1)` |
| Pivot then verify | `O(n)` | `O(1)` |
| Sort and compare | `O(n log n)` | `O(n)` |

One pass, constant space. You cannot do better than `O(n)` - any element could be the one
that breaks the property, so all must be read.

**Can you binary search it?** No. Binary search needs a monotone predicate over the index,
and "is this array rotated-sorted" is a global property that a single probe cannot resolve -
with duplicates you cannot even tell which half to discard. Worth saying if asked, because
Part 5 problems on rotated arrays *do* binary search, and knowing why this one cannot is the
distinction.

## 7. How to present it

1. **Restate**, stressing "non-decreasing" (duplicates allowed) and "including zero
   rotations".
2. **Name the naive approach**: find the pivot, check both halves. "That works, but let me
   see if there's something with less bookkeeping."
3. **State the invariant**: "A sorted array read circularly never goes down. Rotating it
   creates exactly one place where it does. So I'll count the descents circularly and allow
   at most one."
4. **Stress the circular part** and why: `[2,1,3,4]` is the example that needs the wrap
   comparison to be rejected. Give it before writing the code - it justifies the `% n`.
5. **Write it**, and point out `>` rather than `>=` handles duplicates.
6. **Test out loud** on `[3,4,5,1,2]` (one drop), `[2,1,3,4]` (two drops), `[1,1,1]` (zero
   drops).
7. **Close**: `O(n)` time, `O(1)` space; note that binary search does not apply here and why.

## 8. Follow-ups and variations

- **"Return the rotation amount, not just a boolean."** The index after the single drop, or
  `0` if there is none. One extra variable.
- **"What if it must be strictly increasing before rotation?"** Change `>` to `>=`, so equal
  neighbours also count as violations. Then `[1,1,1]` becomes `False`. Confirm which they
  want - the problem says non-decreasing, and this is the difference.
- **"What if it was sorted descending and rotated?"** Run the same count with the comparison
  flipped, or reverse and reuse.
- **"Search for a target in such an array."** Now it is Part 5 - *Search in Rotated Sorted
  Array* (5.2). With **duplicates** the worst case degrades to `O(n)`, because `nums[lo] ==
  nums[mid] == nums[hi]` gives no information about which half to discard. That degradation
  is the standard follow-up and is worth knowing precisely.
- **"Find the minimum in such an array."** 5.17, `O(log n)` without duplicates.
- **"Rotate the array in place by k."** LC 189 (2.16 in this course) - the reverse-three-times
  trick.
- **"Is it sorted *or* rotated-sorted *or* reverse-sorted?"** Combine the counts; a nice
  small extension that tests whether you generalised or memorised.
- **"Streaming version."** You can maintain the drop count online as elements arrive, but the
  wrap-around comparison needs the first element, so keep that plus the last.

## 9. Pitfalls

- **Forgetting the circular comparison.** The single real bug; `[2,1,3,4]` exposes it.
- **Using `>=` instead of `>`**, rejecting valid arrays with duplicates like `[1,1,2]`.
- **Returning `drops == 1`** instead of `drops <= 1`, rejecting the un-rotated case.
- **Trying to binary search** because the array is "sorted-ish".
- **Sorting a copy and comparing**, which is `O(n log n)` and does not actually test the
  rotation property - `[2,1,3,4]` sorted equals `[1,2,3,4]` but is not a rotation of it.
- **Off-by-one in the loop bound** - it must be `range(n)`, not `range(n-1)`, for the wrap to
  be included.
- **Assuming at least two elements**; a single element must return `True`.
