> listening histories, recommend songs.** Treat it as a co-occurrence counting plus top-k
> problem with a design conversation attached - the same shape as the autocomplete question
> (`23.12`), and closely related to the CCTV top-N question (`23.8`).
>
> Because the prompt is loose, this page front-loads the clarifying questions. In a round

## The problem, as you should restate it

```
You are given users' listening histories, e.g.

  user1: [songA, songB, songC]
  user2: [songA, songB]
  user3: [songB, songD]

Recommend songs to a given user.
```

## Clarifying questions to ask first

These decide *which algorithm you write*, so ask before choosing anything.

1. **What signal do we have?** Just "user played song", or ratings, play counts, skips,
   timestamps? Counts and skips change the scoring completely.
2. **What does "recommend" mean here - top-k songs for one user?** How large is k?
3. **Which recommendation strategy do you want?**
   - **Popularity**: the globally most-played songs the user has not heard. Trivial baseline.
   - **Item-based collaborative filtering**: "people who played X also played Y". Score
     candidate songs by co-occurrence with the user's history.
   - **User-based collaborative filtering**: find similar users, recommend what they played.
   - **Content-based**: use song attributes (genre, artist). Needs data we may not have.

   Say all four in one breath, then ask which. Naming the space and letting them choose is
   the strongest opening move.
4. **Must we exclude songs the user has already played?** Almost certainly yes.
5. **How do we break ties?** By global popularity, then by id, for determinism.
6. **Scale?** Users, songs, and history length. This decides in-memory versus precomputed.
7. **Is this offline (batch) or online (per-request)?**
8. **What about a brand-new user with no history (cold start)?**

## Intuition

Assume the common answer: **item-based collaborative filtering**, because it is the one that
uses only play history and is what "people who listened to this also listened to that"
means.

Build a co-occurrence count: for every user, every **pair** of songs in their history gets
its count incremented.

```
user1: A B C  ->  (A,B) (A,C) (B,C)
user2: A B    ->  (A,B)
user3: B D    ->  (B,D)

co[A] = {B: 2, C: 1}
co[B] = {A: 2, C: 1, D: 1}
co[C] = {A: 1, B: 1}
co[D] = {B: 1}
```

To recommend for a user: sum the co-occurrence scores of every candidate song against the
songs the user has already played, drop what they have heard, and take the top k.

> **Score(candidate) = sum over the user's songs S of co[S][candidate].**

The one refinement worth volunteering: **raw co-occurrence is dominated by popular songs** -
a song everyone plays co-occurs with everything. Normalising fixes it. The standard measure
is cosine similarity or the Jaccard index:

```
jaccard(X, Y) = |users who played both| / |users who played either|
```

Mentioning that raw counts over-recommend popular items, and naming a normalisation, is the
difference between a coding answer and a recommendation-systems answer.

## Approach

1. Build `plays: song -> set of users` and `history: user -> set of songs`.
2. Build `co: song -> Counter of co-occurring songs` by iterating each user's history pairs.
3. `recommend(user, k)`: accumulate scores over the user's songs, exclude already-played,
   return the top k by `heapq.nlargest`.

Step 2 is `O(sum of |history|^2)` - quadratic in each user's history length. Flag this
immediately as the scaling bottleneck and offer the fixes (cap history, sample, or use the
inverted index instead).

## Solution

```python
import heapq
from collections import defaultdict, Counter


class SongRecommender:
    """Item-based collaborative filtering over play histories.

    co[x][y] is the number of users who played both x and y, which is the raw
    "people who played x also played y" signal.
    """

    def __init__(self):
        self.history = defaultdict(set)      # user -> songs they played
        self.plays = defaultdict(set)        # song -> users who played it
        self.co = defaultdict(Counter)       # song -> Counter of co-played songs
        self.popularity = Counter()          # song -> number of distinct listeners

    def add_history(self, user, songs):
        """Record a user's listening history. Idempotent per (user, song)."""
        new = [s for s in songs if s not in self.history[user]]
        existing = list(self.history[user])

        for song in new:
            self.popularity[song] += 1
            self.plays[song].add(user)

        # Each new song co-occurs with everything this user already had, and with
        # the other new songs.
        for i, a in enumerate(new):
            for b in existing:
                self.co[a][b] += 1
                self.co[b][a] += 1
            for b in new[i + 1:]:
                self.co[a][b] += 1
                self.co[b][a] += 1

        self.history[user].update(new)

    def recommend(self, user, k=3, normalise=False):
        """Top k songs for the user, excluding what they have already played.

        normalise=True uses the Jaccard index instead of a raw count, which stops
        globally popular songs dominating every recommendation.
        """
        listened = self.history.get(user, set())
        if not listened:
            # Cold start: nothing to correlate against, so fall back to popularity.
            candidates = [(count, song) for song, count in self.popularity.items()]
            return [song for _, song in heapq.nlargest(k, candidates)]

        scores = Counter()
        for song in listened:
            for other, count in self.co[song].items():
                if other in listened:
                    continue                 # never recommend what they already played
                if normalise:
                    union = len(self.plays[song] | self.plays[other])
                    scores[other] += count / union if union else 0
                else:
                    scores[other] += count

        # nlargest keeps a heap of size k: O(m log k) rather than sorting everything.
        # Tie-break by popularity then by id so the output is deterministic.
        return [song for song, _ in heapq.nlargest(
            k, scores.items(), key=lambda kv: (kv[1], self.popularity[kv[0]], kv[0]))]
```

```python
r = SongRecommender()
r.add_history("user1", ["A", "B", "C"])
r.add_history("user2", ["A", "B"])
r.add_history("user3", ["B", "D"])

dict(r.co["A"])            # {'B': 2, 'C': 1}
dict(r.co["B"])            # {'A': 2, 'C': 1, 'D': 1}

r.recommend("user2", k=2)  # ['C', 'D']   -- user2 played A and B
r.recommend("user3", k=2)  # ['A', 'C']   -- user3 played B only
r.recommend("newbie", 2)   # ['B', 'A']   -- cold start, falls back to popularity
```

Check `recommend("user2")` by hand: user2 played `A` and `B`. Candidates are `C`
(`co[A][C]=1 + co[B][C]=1 = 2`) and `D` (`co[B][D]=1 = 1`). So `C` then `D`. Correct.

## Complexity

Let `U` be users, `S` songs, `H` the average history length, and `m` the number of candidate
songs reachable from a user's history.

| | Time | Space |
|---|---|---|
| Build co-occurrence | `O(U * H^2)` | `O(number of co-occurring pairs)` |
| `recommend` | `O(H * avg co-list length + m log k)` | `O(m)` |
| Popularity baseline | `O(S)` build, `O(S log k)` query | `O(S)` |

**The `H^2` is the thing to flag.** A user with 10,000 played songs contributes 50 million
pairs by themselves. Real systems cap the history window (recent N songs), sample pairs, or
avoid materialising the full co-occurrence matrix and compute scores on demand from the
inverted index `plays`.

Memory is also the concern: the co-occurrence matrix is `O(S^2)` in the worst case. Prune
pairs below a count threshold and keep only the top-N neighbours per song - that bounds it
at `O(S * N)` and is what production systems actually do.

## How to present it

1. **Say the prompt is underspecified and enumerate the strategies** (popularity, item-based
   CF, user-based CF, content-based). Ask which. This is the highest-value thirty seconds in
   the round.
2. **Start with the popularity baseline** in one sentence - it is two lines of code and it is
   the thing you compare against. Establishing a baseline is good instinct and cheap to say.
3. **Then build item-based CF**, explaining co-occurrence with their example worked by hand.
4. **Raise the popularity-bias problem yourself** and name Jaccard or cosine as the fix. Do
   not wait to be asked.
5. **Flag the `H^2` build cost** and the `S^2` memory as the scaling issues, with the
   mitigations (window, prune, top-N neighbours).
6. **Handle cold start explicitly** - fall back to popularity.
7. **If it drifts to system design**, go with it: offline batch job computes the neighbour
   lists, a key-value store serves them, the online path is a lookup plus a merge.

## Follow-ups and variations

- **"Top-k recommendations per user."** `heapq.nlargest`, `O(m log k)`. Say why it beats
  sorting when `k` is small.
- **"How do you break ties?"** Popularity, then id. State it, and make the key explicit so
  the output is deterministic - non-determinism in a recommender is a real bug.
- **"How does this scale to millions of users?"** Precompute offline: a batch job (Spark /
  MapReduce) emits, for each song, its top-N most similar songs. Serving is then a lookup of
  the user's recent songs, a merge of N-length lists, and a top-k - no `S^2` matrix in the
  serving path. This is the answer they want.
- **"Cold start for a new user."** Popularity fallback, or onboarding preferences, or
  content-based features (genre, artist) until enough history accumulates. Handled above.
- **"Cold start for a new song."** Harder - it co-occurs with nothing. Content-based features
  or deliberate exploration (show it to a sample of users).
- **"Raw counts favour popular songs."** Jaccard, cosine, or PMI. Shown as the `normalise`
  flag.
- **"Use ratings, not just plays."** Scores become weighted; cosine similarity over rating
  vectors. Mention matrix factorisation (ALS, SVD) by name as the next step up.
- **"Recency matters."** Weight co-occurrences by a decay factor on the timestamp, or only
  count pairs within a session window.
- **"Avoid recommending the same thing repeatedly."** Diversity / novelty re-ranking, and an
  impression log so you do not re-show what was ignored.
- **"How would you evaluate it?"** Offline: precision@k and recall@k on a held-out split.
  Online: A/B test on play-through rate. One sentence each is enough, and it shows you know
  recommenders are measured, not just built.

## Pitfalls

- **Picking an algorithm before asking which problem they want.** The prompt genuinely does
  not say.
- **Recommending songs the user has already played.** The most common correctness bug here.
- **Sorting all candidates** when `k` is small.
- **Ignoring the popularity bias** of raw co-occurrence, so every user is recommended the
  same three hits.
- **Building the full `S x S` co-occurrence matrix** and not mentioning that it does not fit
  for real catalogues.
- **Not handling the empty-history user**, producing an empty list or a `KeyError`.
- **Using `defaultdict` on read paths** (`self.co[song]` for an unknown song), silently
  growing the structure. It is deliberate and harmless inside `recommend` here, since the
  songs come from the user's own history, but say that you noticed.
- **Non-deterministic output** from ties, which makes the system untestable.
