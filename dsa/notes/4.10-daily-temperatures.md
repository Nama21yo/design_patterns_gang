**Link:** https://leetcode.com/problems/daily-temperatures
**Difficulty:** Medium | **LeetCode #739**
**Bloomberg frequency:** 50% at three months.

The third member of the next-greater family, and the one that forces you to **store indices**
rather than values - because the answer is a **distance**, not a value. If you learned 4.3
with values on the stack, this is the question that corrects the habit.

> Read [[4.3 Next Greater Element I]] first for the template.

## 1. Problem statement

Given an array `temperatures` of daily temperatures, return an array `answer` where
`answer[i]` is the **number of days** you have to wait after day `i` to get a **warmer**
temperature. If there is no future day for which this is possible, `answer[i] == 0`.

```
temperatures = [73,74,75,71,69,72,76,73]  ->  [1,1,4,2,1,1,0,0]
temperatures = [30,40,50,60]              ->  [1,1,1,0]
temperatures = [30,60,90]                 ->  [1,1,0]
```

## 2. Clarifying questions

1. **Warmer means strictly greater?** Yes. Equal temperatures do not count, so `[70,70]`
   gives `[0,0]`.
2. **The answer is a count of days, not a temperature?** Yes - a **distance**. That is the
   one difference from 4.3 and it is why indices go on the stack.
3. **What if there is no warmer day?** `0`, not `-1`. Worth confirming, because the sibling
   problems use `-1`.
4. **Are temperatures bounded?** LeetCode says 30 to 100, which enables an alternative
   bucket-based solution (see the follow-ups).
5. **Can there be duplicates?** Yes, so strictness matters.
6. **Sizes?** Up to 10^5, so `O(n^2)` will time out.

## 3. Intuition

Brute force: for each day, scan forwards until a warmer day. `O(n^2)`, and it is genuinely
quadratic on a decreasing sequence like `[100, 99, 98, ...]`.

Same template as 4.3:

> **Keep a stack of days still waiting for a warmer day, with temperatures decreasing from
> bottom to top. When a warmer day arrives, it resolves everything cooler that is waiting -
> pop each one and record the distance.**

The only change:

```
4.3:   result[popped] = current_value
4.10:  result[popped] = current_index - popped_index
```

So the stack must hold **indices**. That is the entire difference between the two problems,
and stating it explicitly is the cleanest way to show you see them as one pattern.

Anything left on the stack at the end never found a warmer day, and its answer stays `0` -
which is why initialising the result array to zeros means no cleanup loop is needed.

**Why it is `O(n)`**: each index is pushed exactly once and popped at most once, so the total
work is linear despite the nested `while`. Say it.

## 4. Approach

1. `answer = [0] * n`; `stack = []` (indices, temperatures decreasing).
2. For each `i`, `t`:
   - while `stack` and `temperatures[stack[-1]] < t`: `j = stack.pop()`;
     `answer[j] = i - j`
   - `stack.append(i)`
3. Return `answer`.

## 5. Solution

```python
def daily_temperatures(temperatures):
    """Days to wait for a warmer temperature, or 0 if none.

    Same monotonic stack as Next Greater Element, but the answer is a DISTANCE, so
    the stack holds indices rather than values. Initialising to 0 means the days
    still waiting at the end need no cleanup pass.
    """
    answer = [0] * len(temperatures)
    stack = []                      # indices, temperatures decreasing bottom to top

    for i, t in enumerate(temperatures):
        # A warmer day resolves every cooler day still waiting.
        while stack and temperatures[stack[-1]] < t:
            j = stack.pop()
            answer[j] = i - j       # the distance, not the temperature
        stack.append(i)

    return answer
```

```python
daily_temperatures([73, 74, 75, 71, 69, 72, 76, 73])    # [1, 1, 4, 2, 1, 1, 0, 0]
daily_temperatures([30, 40, 50, 60])                    # [1, 1, 1, 0]
daily_temperatures([30, 60, 90])                        # [1, 1, 0]
daily_temperatures([])                                  # []
daily_temperatures([50])                                # [0]
daily_temperatures([70, 70])                            # [0, 0]
daily_temperatures([100, 99, 98, 97])                   # [0, 0, 0, 0]
daily_temperatures([70, 71, 70, 72])                    # [1, 2, 1, 0]
daily_temperatures([89, 62, 70, 58, 47, 47, 46, 76, 100, 70])
# [8, 1, 5, 4, 3, 2, 1, 1, 0, 0]
```

Two to narrate:

- **`[70,70]` -> `[0,0]`.** Equal is not warmer. The strictness test, and a one-character bug
  (`<=` instead of `<`) breaks it.
- **`[100,99,98,97]` -> all zeros.** The strictly decreasing case: every day is pushed,
  nothing is ever popped, and the zero-initialisation supplies all the answers. It is also
  the brute force's worst case, which makes it a good contrast to mention.

The long example is the one to trace if asked: day 0 (`89`) waits eight days for the `100`,
which is the longest wait and exercises a deep stack.

### The brute force

```python
def daily_temperatures_brute(temperatures):
    """O(n^2): scan forwards from each day."""
    n = len(temperatures)
    answer = [0] * n
    for i in range(n):
        for j in range(i + 1, n):
            if temperatures[j] > temperatures[i]:
                answer[i] = j - i
                break
    return answer


daily_temperatures_brute([73, 74, 75, 71, 69, 72, 76, 73])  # [1, 1, 4, 2, 1, 1, 0, 0]
daily_temperatures_brute([70, 70])                          # [0, 0]
daily_temperatures_brute([100, 99, 98, 97])                 # [0, 0, 0, 0]
```

### The bounded-values alternative

Since temperatures are between 30 and 100, there are only 71 possible values. Scanning
**right to left**, keep `next_day[t]` = the nearest future day with temperature `t`, and for
each day look for the minimum over all warmer temperatures:

```python
def daily_temperatures_bounded(temperatures, low=30, high=100):
    """O(n * range) time, O(range) space. Competitive when the value range is small,
    and it uses no stack at all."""
    n = len(temperatures)
    answer = [0] * n
    # next_day[t] = nearest day to the right with exactly temperature t
    next_day = [float("inf")] * (high + 1)

    for i in range(n - 1, -1, -1):
        t = temperatures[i]
        warmest = min(next_day[t + 1:high + 1], default=float("inf"))
        if warmest != float("inf"):
            answer[i] = warmest - i
        next_day[t] = i

    return answer


daily_temperatures_bounded([73, 74, 75, 71, 69, 72, 76, 73])    # [1, 1, 4, 2, 1, 1, 0, 0]
daily_temperatures_bounded([30, 40, 50, 60])                    # [1, 1, 1, 0]
daily_temperatures_bounded([70, 70])                            # [0, 0]
daily_temperatures_bounded([100, 99, 98, 97])                   # [0, 0, 0, 0]
```

Worth mentioning as "if the values are bounded, here is a stack-free option", but the stack
is strictly better asymptotically (`O(n)` versus `O(n * range)`), so do not lead with it.

## 6. Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` extra |
| **Monotonic stack** | **`O(n)`** | `O(n)` worst case |
| Bounded values, right-to-left | `O(n * range)` | `O(range)` |

Stack space is `O(n)` on a strictly decreasing input, where nothing is ever popped until the
end. Best case is `O(1)` on an increasing input, where each element pops its predecessor
immediately.

## 7. How to present it

1. **Restate**, and confirm two things: strictly warmer, and the answer is a **number of
   days**, with `0` when none.
2. **Give the brute force** and name its worst case: a decreasing sequence, where every scan
   runs to the end.
3. **Name the pattern immediately**: *"This is the next-greater-element template. The only
   difference is that the answer is a distance, so I'll store indices on the stack instead of
   values."* Saying that sentence *before* writing is the whole point of this question.
4. **State the invariant**: a stack of days still waiting, temperatures decreasing.
5. **Write it**, and point out the zero-initialisation: *"days still on the stack at the end
   never get warmer, and they already read 0, so no cleanup is needed."*
6. **Trace `[73,74,75,71,69,72,76,73]`**, particularly day 2 (`75`), which waits four days
   for the `76` while three cooler days pile up behind it.
7. **Give the amortised argument.**
8. **Test** `[70,70]` and `[100,99,98,97]`.
9. **Close**: `O(n)` time, `O(n)` space worst case - and optionally mention the bounded-value
   alternative as a curiosity.

## 8. Follow-ups and variations

- **"Next Greater Element I / II"** (4.3, 4.4). Same template; I returns the value, II adds
  circularity, this one returns the distance. Being able to state the family in one sentence
  each is worth more than any individual solution.
- **"How many days until a *cooler* temperature?"** Flip the comparison to `>`.
- **"The previous warmer day."** Scan right to left, or read `stack[-1]` before pushing.
- **"Stock span problem."** For each day, how many consecutive previous days had a price at
  most today's. Previous-greater with indices - the same machinery, and a classic.
- **"Online / streaming version"** (LC 901, *Online Stock Span*). The stack works
  incrementally: each new price pops the smaller spans and absorbs their counts. A genuinely
  good follow-up because it shows the stack is not inherently offline.
- **"What if you need the warmest day within the next k days?"** Now it is a sliding-window
  maximum - a monotonic **deque** (3.2), not a stack. A good question to distinguish the two
  structures.
- **"Return the index of the warmer day rather than the distance."** `answer[j] = i`.
- **"Temperatures are bounded - can you exploit that?"** The right-to-left version above.

## 9. Pitfalls

- **Storing values instead of indices**, which makes the distance impossible to compute.
  **The defining mistake here.**
- **Recording `i` instead of `i - j`**, returning the day rather than the wait.
- **Using `<=` instead of `<`**, so equal temperatures count as warmer. `[70,70]` is the test.
- **Initialising the answer to `-1`** - this problem uses `0`, unlike its siblings.
- **Adding a cleanup loop** for the leftover stack. Unnecessary with zero-initialisation, and
  a sign the invariant was not understood.
- **Pushing before popping**, so an element resolves itself with a distance of 0.
- **Using a plain list as a queue** anywhere in this problem - it is a stack, so `append` and
  `pop` are both `O(1)`, but do not reach for `pop(0)`.
- **Claiming `O(n^2)`** because of the inner `while`.
