title: "23.7 Print all paths between two nodes / flight routes"
---

> Reported 4 times across R1 and R2 on 2025-10-17 and 2025-10-22, in two dressings:
> a flight-routes class, and a raw graph DFS. The graph in the second version has
> **cycles**, which is the detail that makes or breaks the solution.

## Prompt as given

```
Design a class to represent direct flight routes between cities:

  addRoute(start, destination)        - add a direct flight route
  printAllRoutes(start, destination)  - print ALL possible routes

  addRoute('A','B'); addRoute('A','C'); addRoute('B','D'); addRoute('C','D')
  printAllRoutes('A','D')  ->  [[A,B,D], [A,C,D]]
```

The second telling, given as a plain graph:

```
A->B, B->A, A->C, C->A, A->D, D->A, B->C, C->B, B->D, D->B

print_all_paths(C, D)  ->  C,A,B,D
                           C,A,D
                           C,B,A,D
                           C,B,D
```

Closest LeetCode problem:
[All Paths From Source to Target](https://leetcode.com/problems/all-paths-from-source-to-target/) (LC 797) -
but that one guarantees a **DAG**, and this one does not.

## Clarifying questions to ask first

1. **Are routes directed or bidirectional?** `addRoute('A','B')` reads directed. The second
   example lists both `A->B` and `B->A` explicitly, which confirms directed edges.
2. **Can the graph have cycles?** In the second example, yes. This is the crux - ask it.
3. **Can a path revisit a city?** No: a route that loops is not a sensible itinerary, and the
   expected output has no repeats. So paths must be **simple**.
4. **What if there is no route?** One report says the expected behaviour was to return a
   message, not an empty list. Ask - it is a free mark.
5. **What if start equals destination?** A zero-hop path, or nothing?
6. **Duplicate `addRoute` calls?** Dedupe, or allow parallel edges?
7. **Do you want them printed or returned?** The name says print; the example shows a list.
   Ask, then return a list and print it - it is easier to test.

## Intuition

This is exhaustive enumeration, not shortest path, so it is **DFS with backtracking**, not
BFS.

The one thing to get right is the visited set. In ordinary reachability DFS you mark a node
visited once and never return to it, because you only care *whether* you can reach the
target. Here you care about *every* route, and a node that is off-limits on one path must be
available again on another. Concretely, in the cyclic example, `C -> A -> B -> D` and
`C -> B -> D` both use `B`; if `B` were marked globally visited by the first path, the
second would never be found.

> **The visited set must be per-path, not global: add the node on the way down, remove it on
> the way back up.**

That add/remove pair *is* backtracking, and it is the whole question. The same pairing
applies to the path list: `append` before recursing, `pop` after.

A second detail worth saying: the visited set is not an optimisation here, it is what
guarantees **termination**. With cycles and no visited set, `C -> A -> C -> A -> ...`
recurses forever.

## Approach

1. Store the graph as `defaultdict(list)` - or `defaultdict(set)` if duplicate routes should
   collapse.
2. DFS from `start`, carrying the current `path` and a `visited` set.
3. On entering a node: if it is the destination, record a **copy** of the path and return -
   do not keep exploring past the target, since a simple path ends there.
4. Otherwise, for each unvisited neighbour: mark, append, recurse, then unmark and pop.
5. Return the collected list.

## Solution

```python
from collections import defaultdict


class FlightRoutes:
    """Directed graph of direct flights, with enumeration of all simple routes."""

    def __init__(self):
        # Using a set of destinations makes duplicate addRoute calls idempotent.
        self.routes = defaultdict(set)

    def addRoute(self, start, destination):
        self.routes[start].add(destination)

    def findAllRoutes(self, start, destination):
        """Every simple (no repeated city) route from start to destination."""
        results = []
        path = [start]
        visited = {start}

        def dfs(city):
            if city == destination:
                # Copy: `path` is mutated as we backtrack, so storing it directly
                # would leave every result aliasing the same list.
                results.append(path.copy())
                return
            # sorted() only so the output order is deterministic - drop it if the
            # interviewer does not care.
            for nxt in sorted(self.routes[city]):
                if nxt in visited:
                    continue          # per-path visited: keeps paths simple and terminates
                visited.add(nxt)
                path.append(nxt)
                dfs(nxt)
                path.pop()            # undo the choice
                visited.remove(nxt)   # ... and free the city for other paths

        if start == destination:
            return [[start]]
        dfs(start)
        return results

    def printAllRoutes(self, start, destination):
        routes = self.findAllRoutes(start, destination)
        if not routes:
            print(f"Sorry, there is no route between {start} and {destination}")
            return routes
        for route in routes:
            print(",".join(map(str, route)))
        return routes
```

```python
g = FlightRoutes()
for a, b in [("A", "B"), ("A", "C"), ("B", "D"), ("C", "D")]:
    g.addRoute(a, b)
g.findAllRoutes("A", "D")        # [['A', 'B', 'D'], ['A', 'C', 'D']]
```

And on the cyclic example:

```python
g = FlightRoutes()
for a, b in [("A","B"),("B","A"),("A","C"),("C","A"),("A","D"),("D","A"),
             ("B","C"),("C","B"),("B","D"),("D","B")]:
    g.addRoute(a, b)
g.findAllRoutes("C", "D")
# [['C', 'A', 'B', 'D'], ['C', 'A', 'D'], ['C', 'B', 'A', 'D'], ['C', 'B', 'D']]
```

which is exactly the expected output, in that order.

### What the circulating solution got wrong

A version passed around in the group had three bugs worth knowing, because they are the
bugs you will make under pressure:

```python
    visited.add(child)
    dfs(child)
    path.pop()
    visited.remove(child)   # this part is right
```

but it also did `if not graph[node]: return` **before** checking whether `node` is the
destination in some retellings - which drops a valid path ending at a sink; and it used
`graph[node]` on a plain `dict`, raising `KeyError` for any city with no outgoing routes
(use `defaultdict`, or `.get(node, [])`); and it appended `path` rather than `path.copy()`,
so every result aliases the same list and they all end up identical. Check for all three.

### Iterative version, if recursion is disallowed

```python
def all_routes_iterative(routes, start, destination):
    """Explicit stack of (city, path, visited). Clearer than a recursion-emulating
    stack, at the cost of copying the path at each push."""
    results = []
    stack = [(start, [start], {start})]
    while stack:
        city, path, visited = stack.pop()
        if city == destination:
            results.append(path)
            continue
        for nxt in routes.get(city, ()):
            if nxt not in visited:
                stack.append((nxt, path + [nxt], visited | {nxt}))
    return results
```

This copies the path and the visited set on every push, which is more memory but avoids the
subtle un-marking bug. Offer it if they ask for iterative; say plainly that it trades memory
for simplicity.

## Complexity

Let `V` be cities and `E` routes.

- **Time:** `O(V! )` in the worst case - in a complete graph the number of simple paths
  between two nodes is on the order of `(V-2)!`. More usefully, it is
  `O(number_of_paths * path_length)`, because the DFS does `O(1)` work per edge traversal
  and copies a path of length up to `V` per result. **State it this way**: the output itself
  is exponential, so no algorithm can do better.
- **Space:** `O(V)` for the recursion stack, the path and the visited set, plus
  `O(total output size)` to hold the results.

The sentence to say: *"this is output-sensitive - the answer can be exponentially large, so
the honest bound is proportional to the size of what we print."*

## How to present it

1. **Draw the second example's graph.** It is small and the cycles are visible; drawing it is
   how you notice they exist.
2. **Say "all paths, not shortest path, so DFS with backtracking, not BFS."** Naming the
   choice and the reason is the first scoring moment.
3. **Say the per-path visited rule and why**: "a global visited set would find `C-A-B-D` and
   then block `C-B-D`; I need to un-mark on the way back up." Then note it also guarantees
   termination given the cycles.
4. **Write the choose / explore / un-choose skeleton first**, as four lines, before filling
   in the body. It makes the add/remove symmetry obvious and you will not forget the `pop`.
5. **Call out the `path.copy()`** as you write it, with the reason.
6. **Trace `C -> A -> D`** through your code, then back up to show `A` being freed.
7. **Close** with the output-sensitive complexity and the "no route" behaviour.

## Follow-ups and variations

- **"The graph has cycles."** Already handled; say that the per-path visited set is exactly
  what makes it safe, and that a DAG would let you memoise instead (see below).
- **"What if no route exists?"** Return the message, per the report. Ask first.
- **"Shortest route instead of all routes."** Switch to BFS with a global visited set - and
  explain that the visited set can now be global precisely *because* we no longer need
  alternative paths. That contrast is the single best thing to say in this question.
- **"What if the graph is huge - would you still enumerate all paths?"** No. Ask what the
  routes are *for*: if it is "show me some options", cap the count or the hop limit; if it is
  "cheapest", it is Dijkstra; if it is "is there any", it is a single BFS. Enumerating all
  simple paths is only reasonable on small graphs.
- **"Add a layover/hop limit."** One more parameter: stop recursing when `len(path) > limit`.
  This is the practical fix for the previous question and turns the runtime into
  `O(V^limit)`.
- **"Count the paths instead of listing them."** In a **DAG** this is memoisable:
  `count(u) = sum(count(v) for v in adj[u])`, `O(V + E)`. In a **cyclic** graph counting
  simple paths is #P-complete - say so rather than trying.
- **"Weighted routes, find the cheapest."** Dijkstra, or Bellman-Ford if prices can be
  negative.
- **"Return them sorted by number of hops."** Sort the results by length, or do an iterative
  deepening DFS if they want them streamed shortest-first.
- **"Bidirectional routes."** `addRoute` inserts both directions; nothing else changes.

## Pitfalls

- **A global visited set.** Finds one path per node and silently misses the rest. The single
  most common failure on this question.
- **Forgetting `visited.remove()` or `path.pop()`.** Same effect as above, or worse.
- **Appending `path` instead of `path.copy()`.** Every result aliases one list, and after the
  DFS unwinds they are all empty or identical.
- **Infinite recursion** on the cyclic version when the visited check is missing entirely.
- **`KeyError` on a sink city** from indexing a plain `dict`. Use `defaultdict` or `.get`.
- **Using BFS** because "graph problem" triggers it reflexively. BFS finds shortest paths;
  enumerating all of them with BFS means carrying a full path per queue entry, which is just
  the iterative DFS above with worse memory behaviour.
- **Continuing to recurse after reaching the destination.** For simple paths the route ends
  there; carrying on produces nothing and wastes the visited slot.
