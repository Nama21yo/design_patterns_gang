---
title: "0.3 The solving framework"
---

One loop to run on every coding question, every time, until it is automatic. It is the
coding-round equivalent of the requirements-to-deep-dives framework in the system design
course.

```
  RESTATE  ->  CLARIFY  ->  EXAMPLE  ->  BRUTE FORCE  ->  BOTTLENECK
                                                              |
                        TEST  <-  CODE  <-  ANNOUNCE  <--------
```

Roughly, in a 45-minute round: 5 minutes before you write anything, 5 minutes finding the
approach, 20 minutes coding, 10 minutes testing and follow-ups, 5 minutes of slack.

**Writing code is the fourth thing you do, not the first.** Candidates who start typing
immediately are the ones who solve the wrong problem.

---

## 1. Restate (30 seconds)

Say the problem back in your own words, including the input types and the exact output.

> "So I'm given a list of transactions, each with a name, amount, time and location, and I
> return the ones that are invalid, sorted by time."

Two things happen. You catch misreadings while they are free, and the interviewer gets a
chance to correct you before you have invested anything.

## 2. Clarify (2 minutes)

Ask about **ambiguity, scale, and behaviour at the edges.** A good default set:

- **Input shape**: sorted? duplicates? empty? negative? how large?
- **Output shape**: the value, the indices, or the object? one answer or all of them? what
  if none exists?
- **Ties**: which one wins?
- **Semantics**: the question that is genuinely ambiguous in *this* problem.

That last one is the one that scores. Generic questions are fine; the specific one shows you
read the problem. Real examples from these loops:

| Problem | The question that mattered |
|---|---|
| Two City Scheduling | "Is the number of people guaranteed even?" |
| Bank trading hours | "Does one bank have to cover the window, or can they hand off?" |
| Count pairs | "Unique by index or by value?" |
| Chars in first not second | "If first is `aab` and second is `ab`, do I return `a` or nothing?" |
| Remove 3+ consecutive | "Does a run of four disappear entirely, or drop to one?" |

**Write the answers down** as a comment at the top of the editor. They are your spec, and
having them visible stops you drifting.

If the interviewer says "what do you think?", pick the more interesting interpretation,
state it as an assumption, and move on. Do not stall.

## 3. Example (2 minutes)

Work the provided example **by hand**, out loud. If they did not provide one, invent a small
one.

This is not a formality. It is how you verify that your reading of the problem produces
their answer. The trading-hours candidate's reading of the problem did not explain the
given example, and that was detectable in ten seconds.

> **If your interpretation does not reproduce the provided example, your interpretation is
> wrong.** Check this explicitly before coding.

Then invent a second example that is *different in kind* - with a duplicate, a negative, or
an empty section. Often this is where the real difficulty surfaces.

## 4. Brute force (1 minute)

State the obvious solution and its complexity. Do not code it.

> "The brute force is to check every pair, which is O(n squared) time and O(1) space."

Why this matters:
- It guarantees you have *an* answer if you run out of time.
- It gives you something to improve, which is how you find the real solution.
- It is a checkpoint: the interviewer will often say "that's fine, can you do better?" and
  now you both know where you are.

If the brute force *is* optimal, say so and say why.

## 5. Find the bottleneck (2 minutes)

This is the actual problem-solving step, and it is more mechanical than people expect. Ask:
**what is the brute force doing repeatedly that it should not?**

Almost every optimisation in this course is one of five moves:

| The waste | The fix | Pattern |
|---|---|---|
| Re-scanning for "have I seen X" | Hash map or set | Part 1 |
| Re-summing a range | Prefix sums | Part 1 |
| Re-solving the same subproblem | Memoise / DP table | Part 15 |
| Checking candidates that cannot win | Sort, then two pointers or binary search | Parts 2, 5 |
| Recomputing a window from scratch | Slide it incrementally | Part 3 |

Two more that show up constantly:

- **Sort first.** If order does not matter to the answer but structure would help, sorting
  costs `O(n log n)` and often collapses the problem.
- **Reverse the question.** Instead of "which islands are enclosed", ask "which are reachable
  from the border" (23.15). Instead of "which half goes to NY", ask "who do I move to SF"
  (23.18). This reframing is the single highest-leverage trick in the set.

If nothing fits, name the structure of the problem out loud - "this is a graph", "this is a
search over decisions", "this is an interval problem" - and go to that Part's primer in your
head. The pattern usually implies the technique.

## 6. Announce (30 seconds)

**Before you type**, say what you are about to write:

> "I'll group the transactions by trader, sort each group by time, then sweep a 60-minute
> window tracking the distinct cities inside it. That's O(n log n) for the sorts and linear
> for the sweep."

This is the highest-value thirty seconds in the round:
- If the plan is wrong, you find out before writing 40 lines.
- The interviewer can now follow your code instead of reverse-engineering it.
- It converts you from "candidate typing" into "engineer with a plan".

Get an acknowledgement before continuing.

## 7. Code (15-20 minutes)

- **Top-down.** Write the main function first; if a helper is needed, call it and define it
  after. Do not get lost in a helper before the shape exists.
- **Real names.** `remaining`, `covered_until`, `by_name` - not `a`, `tmp`, `d`. You have to
  read this aloud.
- **Narrate the non-obvious line only.** Do not read the code out; explain the *decisions*:
  "I'm recording the index after the lookup, so an element can't pair with itself."
- **Do not optimise while writing.** Get it correct, then improve if asked.
- **If you get stuck mid-code, say what you are stuck on.** Silence is the worst outcome;
  interviewers in these reports were consistently willing to help.

## 8. Test (5-10 minutes)

**Do not wait to be asked.** When the code is written, say *"let me trace this"*, and:

1. **Run the provided example line by line**, tracking the variables out loud.
2. **Run your edge cases** from the checklist in 0.7 - empty, single element, all identical,
   duplicates, the boundary value.
3. **State the complexity**, time and space, with a one-line justification.
4. **Offer the edge cases you did not handle** and what you would do about them.

Finding your own bug is a strong positive signal. Having the interviewer find it is not.

## Worked example: the framework on a real question

Applying it to 23.16, *count unique index pairs summing to a target*:

| Step | What you say |
|---|---|
| Restate | "Given an array and a target, count pairs of *indices* `i < j` with `arr[i] + arr[j] == target`." |
| Clarify | "Your example has `(0,5)` and `(0,6)` both counted though the values are the same - so uniqueness is by index, not value? If it were by value the answer would be 3 rather than 4." |
| Example | Lists the four pairs, confirms 4. |
| Brute force | "All pairs, O(n squared), O(1) space." |
| Bottleneck | "For each element I'm rescanning for its complement. A hash map makes that O(1)." |
| Announce | "One pass; for each `x` I add the count of `target - x` already seen, then record `x`. Counting at the second element of each pair means no deduplication is needed." |
| Code | Six lines. |
| Test | `[1,1,1,1]` target 2 -> 6. `[3]` target 6 -> 0, which checks the self-pairing bug. |

Total: about 12 minutes, most of it before the code.

## The failure modes this prevents

- **Solving the wrong problem** (23.14) - caught at step 1 or 3.
- **Missing a constraint the interviewer withheld** (23.18, odd `n`) - caught at step 2.
- **Greedy that does not work** (23.20, `bloom` vs `bloomberg`) - caught at step 3, because
  the example is chosen to break it.
- **Freezing with nothing written** - prevented by step 4; you always have a brute force.
- **Silent coding** - prevented by step 6.
- **The interviewer finding your bug** - prevented by step 8.
