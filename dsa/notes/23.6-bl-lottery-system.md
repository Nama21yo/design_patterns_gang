> Reported 4 times across R1 and R2 on 2025-10-28, 2025-11-10 and 2025-11-26.
> One candidate solved it fast enough that the interviewer handed them a second problem
> "as a reward". The follow-ups (duplicates, then weighting) are the real content.

## Prompt as given

```
Implement a lottery system with three functions:

  addParticipant(name)
  removeParticipant(name)
  pick() / draw()      - return a uniformly random participant

Each must be O(1) on average.
```

Closest LeetCode problems:
[Insert Delete GetRandom O(1)](https://leetcode.com/problems/insert-delete-getrandom-o1/) (LC 380) and
[Insert Delete GetRandom O(1) - Duplicates allowed](https://leetcode.com/problems/insert-delete-getrandom-o1-duplicates-allowed/) (LC 381).

## Clarifying questions to ask first

1. **Can the same name be added twice?** This is the first follow-up, so ask it up front and
   decide whether v1 is a set or a multiset.
2. **What does `addParticipant` return if the name is already present?** `False`, like LC 380.
3. **What does `pick()` do on an empty lottery?** Raise, or return `None`. Decide and say so.
4. **Does `pick()` remove the winner?** Ask. "Draw" suggests it might. LC 380 does not.
5. **Must `pick()` be uniform?** Yes - and until the weighting follow-up, uniform over
   *participants*, not over entries.
6. **Is it single-threaded?** Ask if you have time; it sets up a good closing remark.

## Intuition

The three requirements pull against each other:

- `pick()` uniformly at random in `O(1)` wants an **array**: `arr[random.randrange(len(arr))]`
  is the only structure that gives you uniform random access in constant time.
- `removeParticipant(name)` in `O(1)` wants a **hash map**: you must find the name without
  scanning.

So use both, and keep them in sync:

> **`values`: a list of names. `index`: a dict from name to its position in that list.**

The only hard part is deletion. Removing from the middle of a list is `O(n)` because
everything after it shifts. The trick:

> **Swap the doomed element with the last one, then pop the end.**

Popping the end of a Python list is `O(1)`, and the only index that changed is the one
belonging to the element you moved - which you fix in the dict. Order in `values` is
irrelevant, because we only ever index into it randomly, and that is precisely what buys us
the `O(1)`.

That "order does not matter, so I am free to permute" observation is the insight to say out
loud. It is why this works here and would not work for, say, a queue.

## Approach

1. `self.values = []`, `self.index = {}`.
2. **add**: if the name is already in `index`, return `False`. Otherwise append to `values`
   and record `index[name] = len(values) - 1`.
3. **remove**: if absent, return `False`. Otherwise:
   - `i = index[name]`
   - move the last element into slot `i` and update its entry in `index`
   - `values.pop()` and `del index[name]`
   - Careful: if `name` *is* the last element, the move is a self-assignment and you must
     not leave a stale entry. Deleting from `index` after the move handles it.
4. **pick**: `random.choice(self.values)`.

## Solution

```python
import random


class Lottery:
    """Uniform random draw with O(1) add, remove and pick."""

    def __init__(self):
        self.values = []        # the participants, in arbitrary order
        self.index = {}         # name -> its position in self.values

    def addParticipant(self, name) -> bool:
        if name in self.index:
            return False
        self.index[name] = len(self.values)
        self.values.append(name)
        return True

    def removeParticipant(self, name) -> bool:
        if name not in self.index:
            return False
        i = self.index[name]
        last = self.values[-1]

        # Move the last participant into the hole, then drop the (now duplicate) tail.
        # Popping the end of a list is O(1); deleting from the middle would be O(n).
        self.values[i] = last
        self.index[last] = i

        self.values.pop()
        # Done AFTER the move, so the self-removal case (name is the last element)
        # does not leave a stale index entry behind.
        del self.index[name]
        return True

    def pick(self):
        if not self.values:
            raise IndexError("no participants in the lottery")
        return random.choice(self.values)
```

Trace the self-removal case out loud, because it is the bug the interviewer will probe:
with `values = ["a", "b"]` and `index = {"a": 0, "b": 1}`, `removeParticipant("b")` sets
`values[1] = "b"` and `index["b"] = 1` (both no-ops), pops to `["a"]`, then deletes
`index["b"]`. Correct. Had we deleted `index[name]` *before* the move, we would have
re-inserted it.

### Follow-up 1: duplicates allowed

Now `values` may hold the same name several times, so one position per name is not enough -
store a **set of positions** per name. Everything else is the same idea.

```python
import random


class WeightedByCountLottery:
    """Duplicates allowed. A name added k times is k times as likely to be drawn."""

    def __init__(self):
        self.values = []
        self.positions = {}     # name -> set of indices in self.values

    def addParticipant(self, name) -> bool:
        existed = name in self.positions
        self.positions.setdefault(name, set()).add(len(self.values))
        self.values.append(name)
        return not existed      # False if the name was already present, like LC 381

    def removeParticipant(self, name) -> bool:
        """Removes ONE entry for this name."""
        slots = self.positions.get(name)
        if not slots:
            return False

        i = slots.pop()                     # any one of this name's positions
        last = self.values[-1]

        self.values[i] = last
        # Repoint the moved element: it used to live at the end, now it lives at i.
        # discard/add rather than remove(), because when last == name and i was the
        # last index, that index has already been popped from the set above.
        self.positions[last].discard(len(self.values) - 1)
        if i < len(self.values) - 1:
            self.positions[last].add(i)

        self.values.pop()
        if not self.positions[name]:
            del self.positions[name]
        return True

    def pick(self):
        if not self.values:
            raise IndexError("no participants in the lottery")
        return random.choice(self.values)
```

The ordering of the set updates is genuinely fiddly - this is the part to write slowly and
then trace. Two cases to check aloud:

- `name != last`: `i` is freed from `name`, `last` moves from the tail index to `i`.
- `name == last` and `i` is the tail: `slots.pop()` already removed the tail index, the
  `discard` is then a no-op, and the `if i < len - 1` guard stops us re-adding it.

Note that this class already answers the *second* follow-up too: adding a name `k` times
makes it `k` times more likely to be drawn, because `random.choice` is uniform over
**entries**, not names. Point that out - it is a free win.

### Follow-up 2: arbitrary weights

If weights are arbitrary numbers (not small integer multiplicities), duplicating entries is
wasteful. Two standard answers:

**(a) Prefix sums + binary search.** Keep a running total; draw a uniform float in
`[0, total)` and binary search. `O(log n)` draw, `O(n)` update - fine when weights rarely
change.

```python
import bisect
import random


class WeightedLottery:
    def __init__(self):
        self.names = []
        self.prefix = []        # prefix[i] = sum of weights[0..i]

    def add(self, name, weight):
        self.names.append(name)
        self.prefix.append((self.prefix[-1] if self.prefix else 0) + weight)

    def pick(self):
        if not self.names:
            raise IndexError("empty")
        target = random.uniform(0, self.prefix[-1])
        return self.names[bisect.bisect_right(self.prefix, target)]
```

**(b) The alias method.** `O(n)` preprocessing, then genuinely `O(1)` per draw. Mention it
by name; you are not expected to derive it in 45 minutes, and naming it is the signal.

If they want `O(log n)` *updates* as well, a Fenwick tree over the weights supports both
point update and prefix-sum search in `O(log n)`.

## Complexity

| | add | remove | pick | space |
|---|---|---|---|---|
| Unique names | `O(1)` | `O(1)` | `O(1)` | `O(n)` |
| Duplicates (set of positions) | `O(1)` avg | `O(1)` avg | `O(1)` | `O(n)` |
| Arbitrary weights, prefix sums | `O(1)` | `O(n)` | `O(log n)` | `O(n)` |
| Arbitrary weights, alias method | `O(n)` rebuild | `O(n)` rebuild | `O(1)` | `O(n)` |

"Average" `O(1)` throughout, because it rests on hashing. Say the word *average* - that is
what the question means by "O(1) on average", and an interviewer who asked "how does
hashing work" (they did, in a sibling question) will appreciate that you noticed.

## How to present it

1. **Write the three operations and their target complexity as a table** before anything
   else. This question is pure structure selection and the table makes the reasoning visible.
2. **State the tension**: "uniform random in O(1) needs an array; delete-by-value in O(1)
   needs a hash map; so I will keep both and make them mirror each other."
3. **Name the swap-with-last trick** and justify it: "the order of the array is never
   observed, only random positions, so I am free to permute it."
4. **Code it**, then immediately **trace the self-removal edge case** without being asked.
5. **Ask about duplicates** if you have not already, and extend to the multiset version.
6. **Offer the weighting extension** and give both the prefix-sum and alias answers.
7. **Close**: "all three are O(1) *average* because they rest on hashing; worst case is a
   pathological collision chain."

## Follow-ups and variations

- **"What if there are duplicate names?"** The multiset version above.
- **"How can you increase a participant's chance based on their frequency?"** Already true
  in the multiset version - `random.choice` is uniform over entries. Then generalise to
  arbitrary weights.
- **"How does `random.choice` actually pick uniformly?"** It computes
  `seq[int(random() * len(seq))]` (in practice `_randbelow`, which uses rejection sampling
  on random bits to avoid the modulo bias). Mention **modulo bias**: `rand() % n` is not
  uniform unless `n` divides the generator's range, and rejection sampling is the fix.
- **"Does `pick()` remove the winner?"** If yes, it is a sampling-without-replacement draw:
  swap the chosen index with the last and pop - the same `O(1)` trick, and you have already
  written it.
- **"Draw k distinct winners."** Partial Fisher-Yates: swap `k` random elements to the
  front, `O(k)`. Better than calling `pick()` k times and rejecting duplicates.
- **"Make it thread safe."** A single lock around all three methods is the correct first
  answer; note that the swap-and-pop is a multi-step invariant so it *must* be atomic.
- **"Is `random` good enough?"** For a real lottery, no - `random.Random` is a Mersenne
  Twister and is predictable from its output. Use `secrets.choice`. This is a very good
  thing to volunteer at a financial company.
- **"Persist it across restarts."** Now you need a log or a database, and the interesting
  question is whether draws must be reproducible and auditable.

## Pitfalls

- **`values.remove(name)`** - it is `O(n)` and defeats the whole exercise.
- **Deleting `index[name]` before the swap**, which resurrects the entry when the removed
  element is the last one.
- **Forgetting to update the moved element's index.** The list is right and the dict is
  stale; the next removal corrupts the structure. This bug does not show up on small tests.
- **In the duplicates version, using `set.remove()` on an index that was already popped** -
  raises `KeyError`. Use `discard`.
- **`random.randint(0, len(values))`** - inclusive upper bound, off by one. Use
  `random.randrange(len(values))` or `random.choice`.
- **Not handling the empty case** in `pick()`.
- Claiming plain `O(1)` rather than average `O(1)`.
