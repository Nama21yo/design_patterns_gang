> point: *"What if we reorder the array? (it matters actually)"* and *"How does hashing work
> in a set and a hash map?"* Prepare the hashing answer - it is asked verbatim and it is

## Prompt as given

```
Two Sum, but instead of getting the sum find two numbers whose DIFFERENCE equals the target.
```

Related: [Two Sum](https://leetcode.com/problems/two-sum/),
[K-diff Pairs in an Array](https://leetcode.com/problems/k-diff-pairs-in-an-array/).

## Clarifying questions to ask first

1. **Is the difference signed or absolute?** `arr[j] - arr[i] == target`, or
   `|arr[i] - arr[j]| == target`? This is the crux, and it is what the "does reordering
   matter" follow-up is probing. Ask it first.
2. **Return indices, values, or a boolean?** Two Sum returns indices; say which you will do.
3. **First pair, all pairs, or a count?**
4. **Can `target` be negative? Zero?** `target = 0` means "find a duplicate", which is a nice
   special case to call out.
5. **Can an element pair with itself?** No.
6. **Is the array sorted?** Do not assume.

## Intuition

Two Sum works because `a + b == target` rearranges to `b == target - a`: for each element
there is **exactly one** complement to look up.

For a difference, `b - a == target` rearranges to `b == a + target`. Still exactly one
complement - so the same one-pass hash scan works, just with `+` instead of `-`.

The subtlety, and the whole reason the interviewer asked about reordering:

> **Subtraction is not commutative.** For sums, `a + b == b + a`, so it does not matter which
> of the pair you meet first. For differences, `a - b != b - a`, so if you only look up
> `x + target` you will miss pairs where the current element is the *larger* one.

There are two clean ways to handle it, and knowing both is the answer:

- **Look up both complements**: for each `x`, check `x + target` and `x - target`. This finds
  the pair regardless of which element you meet first, and it works for the absolute-value
  reading.
- **Sort first**, then scan with the guarantee that the smaller element always comes first,
  so only one lookup is needed. But sorting **destroys the original indices**, so if you must
  return indices you have to carry them along.

That last point is the direct answer to *"what if we reorder the array - does it matter?"*
**Yes:** it does not change whether a valid pair exists (the multiset is unchanged), but it
changes which indices you report, and it changes whether a single-complement scan is
sufficient.

## Approach

**Signed difference, first pair, return indices.**
1. `seen = {}` mapping value to index.
2. For each `x` at index `i`: check `x - target` and `x + target` in `seen`; if found, return
   the pair. Then record `seen[x] = i`.

**Absolute difference.** Identical - checking both complements already covers `|.| == target`.

## Solution

```python
def two_difference(arr, target):
    """Indices (i, j) with i < j and arr[j] - arr[i] == target, or its negation.

    Unlike Two Sum, subtraction is not commutative, so each element has TWO possible
    partners - one where it is the larger of the pair and one where it is the smaller.
    """
    seen = {}                       # value -> its first index
    for j, x in enumerate(arr):
        # x is the larger element of the pair:
        if x - target in seen:
            return (seen[x - target], j)
        # x is the smaller element of the pair:
        if x + target in seen:
            return (seen[x + target], j)
        seen.setdefault(x, j)       # setdefault keeps the EARLIEST index for a value
    return None
```

```python
two_difference([5, 1, 9, 3], 4)     # (0, 1)   arr[1] - arr[0] = 1 - 5 = -4, |.| = 4
two_difference([1, 5, 9, 3], 4)     # (0, 1)   5 - 1 = 4
two_difference([1, 2, 3], 10)       # None
two_difference([3, 1, 3], 0)        # (0, 2)   target 0 finds a duplicate
```

Note `target = 0`: `x - 0` and `x + 0` are both `x`, so the check becomes "have I seen this
value before" - a duplicate search. It works without a special case because `seen[x]` is
written *after* the lookups. Point that out; it is the same ordering argument as in `23.16`.

### Counting all distinct value pairs (LC 532)

```python
from collections import Counter


def count_k_diff_pairs(arr, k):
    """Number of distinct VALUE pairs (a, b) with b - a == k, k >= 0."""
    if k < 0:
        return 0
    counts = Counter(arr)
    if k == 0:
        # A pair (x, x) requires x to appear at least twice.
        return sum(1 for value, n in counts.items() if n >= 2)
    # k > 0: each value can be the smaller element of at most one pair.
    return sum(1 for value in counts if value + k in counts)
```

```python
count_k_diff_pairs([3, 1, 4, 1, 5], 2)    # 2   -- (1,3) and (3,5)
count_k_diff_pairs([1, 2, 3, 4, 5], 1)    # 4
count_k_diff_pairs([1, 3, 1, 5, 4], 0)    # 1   -- only 1 repeats
```

For `k > 0` only one direction is checked, deliberately: fixing "the smaller element" makes
each pair counted exactly once. Say why - it is the dedup argument again.

### The sorted two-pointer version

```python
def two_difference_sorted(arr, target):
    """O(1) extra space on a sorted array. Both pointers move forward, because
    increasing the gap needs a larger right value, not a smaller left one."""
    target = abs(target)
    lo, hi = 0, 1
    while hi < len(arr):
        gap = arr[hi] - arr[lo]
        if lo != hi and gap == target:
            return (lo, hi)
        if gap < target or lo == hi:
            hi += 1                 # need a bigger gap: advance the right pointer
        else:
            lo += 1                 # gap too big: advance the left pointer
    return None
```

Note these are indices **into the sorted array**. If the original indices are required, sort
`(value, index)` pairs and read the index out - and say that this is exactly why reordering
matters.

## Complexity

| | Time | Space |
|---|---|---|
| Brute force | `O(n^2)` | `O(1)` |
| One-pass hash | `O(n)` average | `O(n)` |
| Sort + two pointers | `O(n log n)` | `O(1)` extra, `O(n)` if you must keep indices |

Say **average** for the hash version. Worst case is `O(n)` per lookup if every key collides,
so `O(n^2)` overall - which is the perfect segue into the hashing follow-up.

## Follow-ups and variations

- **"What if we reorder the array? (it matters actually)"** The intended answer, in three
  parts: (a) whether a valid pair *exists* is unchanged, since it depends only on the
  multiset of values; (b) which **indices** you return changes, so if the contract is
  "return indices into the input" you cannot sort without carrying them; (c) sorting lets a
  scan use only one complement instead of two, because the smaller element is guaranteed to
  come first. Give all three.
- **"How does hashing work in a set and a hash map?"** Asked verbatim. The answer:
  - A **hash function** maps a key to a fixed-size integer. Python calls `__hash__`; equal
    objects must have equal hashes, which is why mutable types are unhashable.
  - That integer is reduced modulo the table size to a **bucket index**.
  - **Collisions** - two keys in the same bucket - are resolved by **separate chaining**
    (a list per bucket) or **open addressing** (probe for the next free slot). CPython uses
    open addressing with a perturbation-based probe sequence.
  - The **load factor** is entries divided by table size. When it exceeds a threshold
    (two-thirds in CPython) the table is **resized** - allocate a bigger table and **rehash**
    every entry. That one operation is `O(n)`, but it happens rarely enough that inserts are
    **amortised `O(1)`**.
  - A `set` is the same machinery storing only keys; a `dict` stores key-value pairs. Since
    Python 3.7 `dict` also preserves insertion order via a separate compact entries array.
  - Worst case is `O(n)` per operation when every key collides, which is why hash flooding is
    a real attack and why Python randomises string hashes by default.
- **"What if the array is already sorted?"** Two pointers, `O(1)` space, one complement.
- **"Count pairs instead of finding one."** `count_k_diff_pairs` above; ask distinct-by-value
  or by-index first (see `23.16` - the same loop asked that question).
- **"Return all pairs."** Output can be `O(n^2)`; say it is output-bound.
- **"Values are huge / it is a stream."** The hash set version is already streaming, with
  `O(distinct values)` memory.
- **"What if duplicates exist and `target` is 0?"** Handled; make sure you say so rather than
  letting them find it.

## Pitfalls

- **Checking only one complement.** Misses half the pairs when the current element is the
  larger one. This is the exact bug the reordering question is designed to expose.
- **Writing `seen[x] = i` before the lookups**, letting an element pair with itself when
  `target == 0`.
- **Using `seen[x] = i` instead of `setdefault`** when the earliest index is wanted - the last
  occurrence overwrites it.
- **Sorting and then returning sorted indices** as if they were original indices.
- **Forgetting `abs()`** or, conversely, applying it when the interviewer wanted a signed
  difference. Ask.
- **Counting each value pair twice** in the counting variant, by checking both `v + k` and
  `v - k` when `k > 0`.
- **Answering the hashing question vaguely.** It is recall; have the six bullets above ready.
