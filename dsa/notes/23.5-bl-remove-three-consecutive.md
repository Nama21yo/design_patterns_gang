title: "23.5 Repeatedly remove 3+ consecutive identical characters"
---

> Reported 4 times across R1 and R2 on 2025-10-18, 2025-10-29 and 2025-10-30.
> The second example is the whole question: removals **cascade**, and a naive
> single-pass scan gets it wrong.

## Prompt as given

```
You are given a string s. Repeatedly remove any substring that contains three or more
consecutive identical characters. After each removal the remaining parts are concatenated
and the process continues until no such substring exists. Return the final string.

  s = "aabbbbc"   ->  "aac"
  s = "aabbbbac"  ->  "c"
```

Closest LeetCode problem:
[Remove All Adjacent Duplicates in String II](https://leetcode.com/problems/remove-all-adjacent-duplicates-in-string-ii/)
(LC 1209), with `k = 3` and the comparison being `>= k` rather than `== k`.

## Read the second example carefully

`"aabbbbac"`:

```
aabbbbac
  ^^^^        "bbbb" is 4 >= 3, remove it
aaac            now "aa" and "a" have become adjacent - a NEW run of 3
^^^             remove "aaa"
c
```

That cascade is the point. A one-pass "delete every run of length >= 3" gives `"aaac"` and
stops, which is wrong. Any candidate who does not trace this example will hand in the wrong
answer. **Trace it out loud in the interview.**

## Clarifying questions to ask first

1. **Is the threshold exactly 3, or "3 or more"?** The prompt says three or more, and
   `"bbbb"` (four) is removed entirely - so a run of length `L >= 3` is deleted wholly, not
   trimmed down to `L mod 3`. This distinction matters and LC 1209 does the *other* thing.
   Confirm it with the given example.
2. **Does the order of removals affect the result?** Worth asking; the answer is no (see
   below), and knowing why is worth saying.
3. **Character set?** Lowercase ASCII, or arbitrary?
4. **Can the result be empty?** Yes - the follow-up example returns `""`.
5. **String length?** Decides whether repeated rescans are acceptable.

## Intuition

The brute-force reading is "scan, find a run of 3+, cut it out, start over" - `O(n^2)` and
awkward to write correctly.

The right move is the standard trick for cascading adjacent removals:

> **Build the answer left to right on a stack of `(character, run_length)` pairs. A cascade
> is just "after popping, look at the new top".**

Push each character: if it matches the stack top's character, increment that top's count;
otherwise push a fresh `(char, 1)`. Whenever a top's count reaches the threshold, pop it.
After popping, the element beneath is now adjacent to whatever comes next - and if the
*next* character matches it, its count keeps growing naturally. The cascade falls out of the
data structure for free.

There is one wrinkle, and it is the detail that separates a correct answer from a
nearly-correct one.

The rule is *"three or more"*, and the example proves that a run of four `b`s vanishes
**entirely** rather than being reduced by three. So you must not pop the moment a count
reaches 3 - at that moment the run might still be growing. You have to wait until the run
is **finished** (the next character differs, or the input ends) and only then decide whether
to delete it whole.

That is the difference between this problem and LeetCode 1209, which removes exactly `k` at
a time. On `"aaaa"` with `k = 3`, LC 1209 leaves `"a"`; this problem leaves `""`.

So the loop is: accumulate into the top run while the character matches; when it stops
matching, **close out** the top - delete it if it reached the threshold, then merge the two
runs that have just become adjacent, and repeat, because the merge may itself have produced
a long run.

## Approach

1. Stack of `[char, count]`.
2. For each character `ch`:
   - If the stack top has the same char, increment its count.
   - Otherwise, **close out** the top: while the top's count is `>= 3`, pop it, and then if
     the new top and the element that followed it share a character, merge their counts and
     re-check. Then push `[ch, 1]` (or merge into the exposed top if it matches `ch`).
3. After the loop, close out the remaining stack the same way.
4. Concatenate `char * count` for what survives.

Implemented directly, "close out and merge" is easiest as a small helper that pops long runs
and merges the exposed neighbours.

## Solution

```python
def remove_runs(s, k=3):
    """Repeatedly delete any maximal run of k or more identical characters, until none
    remain. Deleting a run can make its neighbours adjacent, which can create a new run -
    those cascades are handled by merging after each pop.
    """
    # stack holds [character, run_length] for the runs built so far, in order.
    stack = []

    def collapse():
        """Delete long runs from the top of the stack, merging neighbours that become
        adjacent, until the top is a run shorter than k."""
        while stack and stack[-1][1] >= k:
            stack.pop()
            # The two runs now on top may share a character and must merge into one.
            while len(stack) >= 2 and stack[-1][0] == stack[-2][0]:
                char, count = stack.pop()
                stack[-1][1] += count

    for ch in s:
        if stack and stack[-1][0] == ch:
            stack[-1][1] += 1
        else:
            # The run on top is now final. Resolve it before starting a new one.
            collapse()
            if stack and stack[-1][0] == ch:
                stack[-1][1] += 1      # collapsing exposed a matching run
            else:
                stack.append([ch, 1])

    collapse()                          # the last run is final too
    return "".join(char * count for char, count in stack)
```

Trace `"aabbbbac"`:

| ch | stack after |
|---|---|
| a | `[[a,1]]` |
| a | `[[a,2]]` |
| b | `[[a,2],[b,1]]` |
| b | `[[a,2],[b,2]]` |
| b | `[[a,2],[b,3]]` |
| b | `[[a,2],[b,4]]` |
| a | top is `b` so collapse: pop `[b,4]`, stack `[[a,2]]`; top matches `a` so increment -> `[[a,3]]` |
| c | top is `a` so collapse: pop `[a,3]`, stack empty; push `[c,1]` |
| end | collapse: `[c,1]` is short, stays |

Result `"c"`. Correct.

And `"aabbbaa"`: `[[a,2],[b,3]]`, then `'a'` closes the `b` run, popping it, exposing
`[a,2]`, which matches so becomes `[a,3]`; next `'a'` makes `[a,4]`; final collapse pops it.
Result `""`. Correct.

### The simpler LC 1209 variant

If the interviewer instead wants *"remove exactly k at a time"* (LeetCode 1209 semantics,
where `k=2` on `"aaaa"` leaves `""` but `k=3` on `"aaaa"` leaves `"a"`), the code is much
shorter - pop the moment the count hits `k`:

```python
def remove_k_duplicates(s, k):
    """LC 1209: remove exactly k adjacent equal characters at a time."""
    stack = []                              # [char, count]
    for ch in s:
        if stack and stack[-1][0] == ch:
            stack[-1][1] += 1
            if stack[-1][1] == k:
                stack.pop()
        else:
            stack.append([ch, 1])
    return "".join(char * count for char, count in stack)
```

**Know which one you are being asked for.** The reported prompt says "three or more", and
`"aabbbbc" -> "aac"` proves it: four `b`s vanish entirely, whereas the `k`-at-a-time rule
would leave one `b`.

## Complexity

| | Time | Space |
|---|---|---|
| Brute force (cut and restart) | `O(n^2)` | `O(n)` |
| Stack of runs | `O(n)` | `O(n)` |

The stack version is linear: each character is pushed once, and every pop and merge removes
a stack entry, so the total pop work is bounded by the total push work. Say "amortised
O(n)" and give that argument - it is the justification interviewers want for stack
solutions.

## How to present it

1. **Trace the second example on the board first.** `"aabbbbac"` -> `"aaac"` -> `"c"`. Say
   "the removals cascade, so a single scan is not enough" - this is the insight and you
   should reach it before writing any code.
2. **Confirm the removal rule.** "Four `b`s all disappear, so a run of three or more is
   deleted entirely, not reduced by three." Get a yes.
3. **Name the pattern**: "cascading adjacent removals - that is a stack, and because runs
   can be long I will keep `(char, count)` rather than individual characters."
4. **Say why the naive pop-at-3 is wrong here** and that runs must be closed out before
   being judged. This is the detail that separates a correct answer from a nearly-correct one.
5. **Code it**, then **re-trace both examples** against your code out loud. This problem
   rewards the trace more than almost any other on this list.
6. **Close** with the amortised `O(n)` argument.

## Follow-ups and variations

- **"What if we can start at any index instead of scanning left to right?"** Asked verbatim,
  with `s = "aaabbbbaa"` and the expected answer `""`. This follow-up is sharper than it
  looks, and the honest answer is the one that scores:

  **The order of removals changes the result.** The rewriting system is *not* confluent.
  On `"aaabbbbaa"`:

  ```
  remove "aaa" first:   aaabbbbaa -> bbbbaa -> aa          (stuck, "aa" is too short)
  remove "bbbb" first:  aaabbbbaa -> aaaaa   -> ""         (the whole run of 5 goes)
  ```

  Both are legal under the stated rule, and they give `"aa"` and `""`. The left-to-right
  greedy scan produces `"aa"`. So the interviewer asking for `""` is asking for the
  **minimum reachable string**, not for the greedy one.

  Worth checking: on the two examples they gave, `"aabbbbc"` and `"aabbbbac"`, the reachable
  set has exactly one element each (`"aac"` and `"c"`), which is why the greedy scan matches
  and why the ambiguity is invisible until this follow-up.

  To actually find the minimum, you have to search over removal orders with memoisation on
  the string:

  ```python
  import functools
  import re


  @functools.lru_cache(maxsize=None)
  def shortest_reachable(s, k=3):
      """Minimum-length string reachable by deleting maximal runs of length >= k,
      in any order. Exponential in the worst case - memoised on the string itself."""
      runs = [(m.start(), m.end()) for m in re.finditer(r"(.)\1*", s)
              if m.end() - m.start() >= k]
      if not runs:
          return s                                  # nothing left to remove
      return min((shortest_reachable(s[:a] + s[b:], k) for a, b in runs), key=len)
  ```

  Say the complexity honestly: the state space is the set of reachable substrings-with-gaps,
  which is exponential in general. If they want it polynomial, this is an **interval DP** in
  the same family as *Remove Boxes* and *Strange Printer* - state `(i, j, carried run
  length)` - and you should name that family rather than try to derive it in the room.

  **The lesson to state first, before any of this: ask whether "any substring" means "any
  maximal run" and whether the order is yours to choose.** That single question is what the
  follow-up is testing.
- **"What if the threshold k is a parameter?"** Already handled - `remove_runs(s, k)`.
- **"Can you do it in one pass without rebuilding the string each time?"** That is exactly
  what the stack achieves; say the amortised argument.
- **"Do it in place with O(1) extra space."** Possible with two pointers writing back into a
  mutable char array, carrying a parallel count array - offer it as a sketch; the stack of
  runs is already `O(distinct runs)` which is usually much less than `n`.
- **"Return the number of removed characters too."** Track a running total in `collapse`.
- **"What if removal is by a pattern, not a repeated character?"** Now it is string
  rewriting in general and confluence is no longer guaranteed - the order *would* matter.
  Good thing to note.

## Pitfalls

- **Missing the cascade.** The single biggest failure. Trace `"aabbbbac"`.
- **Confusing "remove the whole run of 3+" with "remove exactly 3 at a time".** Two different
  problems with two different answers on `"aaaa"`.
- **Popping the moment the count reaches 3** under the "3 or more" rule - it cuts the run
  short and leaves characters behind.
- **Forgetting the final `collapse()`** after the loop, so a long run at the end survives.
- **Not merging neighbours after a pop**, so `"aabbbbac"` leaves `[[a,2],[a,1]]` as two
  separate runs and never reaches 3.
- **Rebuilding the string with `s = s[:i] + s[j:]` inside a loop**, which is `O(n)` per
  removal and `O(n^2)` overall.
- **Using a tuple `(char, count)` on the stack** - tuples are immutable, so the increment
  fails. Use a list.
