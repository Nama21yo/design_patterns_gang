> Reported 6 times across R1 and R2 on 2025-10-23, 2025-10-28, 2025-11-06 and 2025-11-18.
> Every single report mentions the same thing: **the interviewer spent the round on edge
> cases, not on the code.** The code is fifteen lines. The edge cases are the interview.

## Prompt as given

```
Implement an underground railway system that tracks customer travel times between
stations:

  checkIn(id, stationName, t)
  checkOut(id, stationName, t)
  getAverageTime(startStation, endStation)
      -> the average travel time for all customers who travelled from startStation
         directly to endStation.
```

Link: [Design Underground System](https://leetcode.com/problems/design-underground-system/) (LC 1396)

## Clarifying questions to ask first

1. **Can a customer be checked in at two places at once?** LeetCode guarantees no. Real
   interviewers here did **not** - ask, and say what you would do if it happened.
2. **Is `getAverageTime(A, B)` directional?** Yes: A-to-B and B-to-A are different pairs.
3. **Is it the average over completed trips only?** Yes - an in-flight trip contributes
   nothing.
4. **Can start and end be the same station?** LeetCode says the pair always differs, but ask.
5. **Is `t` monotonically non-decreasing across calls?** LeetCode says yes. This matters for
   the "overnight" follow-up.
6. **What units is `t`?** Seconds on LeetCode. If it is a wall-clock time of day, the
   midnight problem is live - and that is exactly the follow-up that was asked.
7. **What should `getAverageTime` do for a pair with no completed trips?** Raise, or return
   0? Decide and say so.

## Intuition

Two pieces of state, and the whole problem is choosing them:

1. **Who is currently travelling.** A customer checks in, then later checks out. Between
   those two events you must remember where and when they started. That is a dict
   `id -> (station, time)`, and the entry is **deleted on checkout** - it is a transient
   record, not a log.
2. **The running statistics per route.** You are asked for an *average*. You never need the
   individual trips, only the sum and the count, so store `(total_time, trips)` per
   `(start, end)` pair. That makes `getAverageTime` `O(1)` and the memory proportional to
   the number of distinct routes, not to the number of trips.

The second point is the one that earns the round. Storing a list of every trip duration and
averaging on demand also "works", but it is `O(trips)` per query and unbounded memory. Say
out loud: "I only ever need the mean, and the mean is recoverable from a sum and a count,
so I will not keep the individual samples."

## Approach

1. `self.checked_in`: `dict[id] -> (station, time)`.
2. `self.routes`: `dict[(start, end)] -> [total_time, count]`.
3. `checkIn`: record the entry. (Optionally assert the id is not already checked in.)
4. `checkOut`: pop the entry, compute `t - start_time`, add into the route bucket.
5. `getAverageTime`: one division.

## Solution

```python
class UndergroundSystem:

    def __init__(self):
        # id -> (station, time) for customers currently inside the system.
        # This entry is deleted on checkout: it is transient state, not a log.
        self.checked_in = {}
        # (start, end) -> [total_travel_time, number_of_trips].
        # Only the running sum and count are kept, because only the mean is ever asked for.
        self.routes = {}

    def checkIn(self, id: int, stationName: str, t: int) -> None:
        self.checked_in[id] = (stationName, t)

    def checkOut(self, id: int, stationName: str, t: int) -> None:
        start_station, start_time = self.checked_in.pop(id)
        key = (start_station, stationName)
        bucket = self.routes.setdefault(key, [0, 0])
        bucket[0] += t - start_time
        bucket[1] += 1

    def getAverageTime(self, startStation: str, endStation: str) -> float:
        total, trips = self.routes[(startStation, endStation)]
        return total / trips
```

That is the whole answer. Now spend the rest of the round on the part they are actually
scoring.

### The defensive version to offer next

```python
class UndergroundSystem:
    """Same logic, but every edge case the interviewer raised is handled explicitly."""

    def __init__(self, max_trip_seconds: int | None = None):
        self.checked_in = {}
        self.routes = {}
        # Trips longer than this are treated as a missed checkout and discarded.
        self.max_trip_seconds = max_trip_seconds

    def checkIn(self, id, stationName, t):
        if id in self.checked_in:
            # Already inside. Either the previous checkout was missed, or this is a
            # duplicate event. Dropping the stale record is the safer default: the old
            # trip has no valid end time, so it cannot contribute a meaningful average.
            self.checked_in.pop(id)
        self.checked_in[id] = (stationName, t)

    def checkOut(self, id, stationName, t):
        entry = self.checked_in.pop(id, None)
        if entry is None:
            return                       # checkout with no checkin: ignore, or log it
        start_station, start_time = entry

        if stationName == start_station:
            return                       # entered and left the same station: not a trip

        duration = t - start_time
        if duration < 0:
            return                       # clock went backwards: bad data
        if self.max_trip_seconds is not None and duration > self.max_trip_seconds:
            return                       # implausibly long: treat as a missed checkout

        bucket = self.routes.setdefault((start_station, stationName), [0, 0])
        bucket[0] += duration
        bucket[1] += 1

    def getAverageTime(self, startStation, endStation):
        bucket = self.routes.get((startStation, endStation))
        if not bucket or bucket[1] == 0:
            raise KeyError(f"no completed trips from {startStation} to {endStation}")
        return bucket[0] / bucket[1]
```

### Handling the overnight / midnight case

This was asked in at least two rounds, phrased as *"a person checks in today, bypasses the
checkout, and checks out the next morning"* and *"what if an interval goes 22:00 to 02:00"*.
They are two different problems and you should separate them out loud.

**(a) Times are wall-clock times of day, and a legitimate trip crosses midnight.**
`t - start_time` goes negative. Fix by adding a day:

```python
SECONDS_PER_DAY = 24 * 60 * 60

duration = t - start_time
if duration < 0:
    duration += SECONDS_PER_DAY     # the trip crossed midnight
```

Then say the real fix: **do not store times of day.** Store an absolute timestamp (epoch
seconds, or a `datetime`), and the problem disappears entirely. Wall-clock-of-day is the
bug; the modulo is a patch. Interviewers like hearing the difference between a patch and a
fix.

**(b) The customer genuinely never checked out and reappears twelve hours later.**
Now the duration is real but meaningless - it is not a travel time, it is a fare dispute.
Two defensible policies, and you should offer both and pick one:

- **Discard**: any trip exceeding a plausible maximum (say 3 hours) is treated as a missed
  checkout and excluded from the averages. Keeps the statistic honest.
- **Expire proactively**: sweep `checked_in` and evict entries older than the maximum, so
  the stale record is gone before the late checkout arrives. This is the better answer if
  they push on memory, because otherwise abandoned check-ins accumulate forever.

An eviction sweep without scanning the whole dict, if asked:

```python
from collections import OrderedDict

# checkIn times are non-decreasing, so an OrderedDict is already in expiry order.
self.checked_in = OrderedDict()

def _expire(self, now):
    while self.checked_in:
        id, (_, start_time) = next(iter(self.checked_in.items()))
        if now - start_time <= self.max_trip_seconds:
            break
        self.checked_in.popitem(last=False)
```

## Complexity

| Operation | Time | Space |
|---|---|---|
| `checkIn` | `O(1)` | - |
| `checkOut` | `O(1)` | - |
| `getAverageTime` | `O(1)` | - |

Space is `O(C + R)` where `C` is the number of customers currently in transit and `R` the
number of distinct station pairs ever travelled. Note explicitly that it is **not** `O(total
trips)` - that is the consequence of storing a running sum instead of a sample list, and it
is the thing to point at.

## How to present it

1. **List the three operations and the target complexity for each** before writing anything:
   "all three should be O(1); let me pick structures that make that true."
2. **Name the two pieces of state** and why each exists: transient in-flight records,
   permanent per-route aggregates.
3. **Say the sum-and-count insight explicitly.** "I never need individual trips, only the
   mean, so a running total and a count is enough." This is the design decision in the
   problem.
4. **Write the clean version.** Do not clutter it with guards yet.
5. **Then say: "let me go through the edge cases."** Do not wait to be asked - every report
   says this is where the round went. Walk the list below out loud.
6. **Offer the defensive version** and let them pick which policy they want.

## Follow-ups and variations

- **"Give me the edge cases."** Asked in essentially every report. Have this list ready:
  checkout with no check-in; two check-ins without a checkout; check-in and checkout at the
  same station; zero-duration trip; `getAverageTime` on a pair with no trips;
  `getAverageTime(A, B)` vs `(B, A)`; negative or non-monotonic timestamps; a customer who
  never checks out; integer overflow on the running total in a fixed-width language (not an
  issue in Python - say so, and say it *would* be in C++ or Java).
- **"Overnight checkout / 22:00 to 02:00 intervals."** See above. Lead with "store absolute
  timestamps, not times of day".
- **"Make `getAverageTime` O(1)."** It already is - point out that this is the payoff of the
  sum-and-count choice, and that the list-of-samples design would have been `O(n)` here.
- **"Also report the median travel time."** Now you *do* need the distribution, and a sum
  and count are not enough. Either keep all samples (`O(trips)` memory), or use two heaps
  for a streaming median, or a t-digest / reservoir sample for an approximate one. A good
  place to say "this is where the design round and the coding round meet".
- **"Average over the last hour only."** Sliding window: keep a deque of `(time, duration)`
  per route and evict from the front, maintaining the running sum. Memory becomes `O(trips
  in the window)`.
- **"Millions of customers, many machines."** Shard `checked_in` by customer id; the route
  aggregates are commutative `(sum, count)` pairs, so each shard keeps a partial aggregate
  and you merge on read. Mention that `(sum, count)` merging is exactly why this
  parallelises and a median would not.
- **"Make it thread safe."** A lock around each dict, or per-id striped locks. Note that
  `checkOut` is a read-modify-write on the route bucket, so it needs the lock; `checkIn` is
  a single dict assignment and in CPython is atomic, but do not rely on that - say it.
- **"Add `getAverageTime` for a whole station, any destination."** Keep a second aggregate
  keyed by start station only.

## Pitfalls

- **Not deleting the check-in record on checkout.** It grows without bound and a second
  checkout would double count.
- **Keeping every trip duration in a list.** It passes LeetCode and loses the round.
- **Making the route key a set or unordered pair.** The average is directional.
- **`self.routes[key][0] += ...` on a dict of tuples.** Tuples are immutable; use a list, or
  `defaultdict(lambda: [0, 0])`.
- **Returning an int.** `total / trips` must be a float; `//` is wrong.
- **Waiting to be asked about edge cases.** Volunteer them. Every report says this is the
  round.
