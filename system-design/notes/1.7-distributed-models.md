Every note in this course that assumes a timeout, a quorum, or "the network might drop a
message" is quietly relying on an assumption about what the underlying system is allowed
to do. This closing note of Part 1 makes those assumptions explicit: the three synchrony
models, the spectrum of ways a node can actually fail, and the famous list of wrong
assumptions that breaks a design built without reading this note first.

## Synchrony models

![Synchronous, asynchronous, and partially synchronous - what real systems actually assume](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-7-synchrony-models.png)

- **Synchronous** - both message delay and processing time have **known, bounded** limits.
  In this model, a timeout can reliably distinguish "dead" from "slow," because "slow" has
  a hard ceiling. Clean, but unrealistic for most real networks.
- **Asynchronous** - **no bounds at all**. A message might take 1ms or 10 minutes, and
  there's no way to tell the difference between "still in flight" and "never arriving." This
  is precisely the model 3.6's **FLP impossibility result** lives in: with zero bound on
  delay, no algorithm can guarantee consensus in bounded time if even one process might
  fail, because a slow message is indistinguishable from a dead sender.
- **Partially synchronous** - bounds **exist**, but are either unknown in advance or only
  guaranteed to hold **eventually** (after some unknown point, the system behaves
  synchronously). This is the honest middle ground, and what real production systems
  actually assume: 2.4's timeouts and 3.6's leader-election heartbeats aren't claiming to
  solve FLP - they're a practical engineering answer tuned for exactly this model, accepting
  a small, bounded risk of mistaking "slow" for "dead" in exchange for an algorithm that
  actually terminates.

## Failure modes

![From simplest to model, to hardest and most expensive to tolerate](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-7-failure-modes.png)

- **Crash-stop** - a node fails once and **never** comes back. The simplest failure model
  to reason about, and the one most introductory consensus proofs assume.
- **Crash-recovery** - a node can fail and **restart**, possibly having lost whatever state
  lived only in memory. 3.1's write-ahead log exists specifically so a restarted node can
  reconstruct its pre-crash state rather than silently losing it.
- **Omission** - a node otherwise behaves correctly, but some messages it sends or receives
  are simply **dropped**. 2.1's UDP behavior, measured live (some messages silently lost,
  the rest delivered correctly) is omission failure made concrete at the transport layer.
- **Byzantine** - a node can behave **arbitrarily**: sending incorrect data, contradicting
  itself to different peers, or acting maliciously. This is the hardest and most expensive
  failure mode to tolerate by a wide margin - and it's worth being precise that **3.6's Raft
  and Paxos are not Byzantine fault tolerant**. They assume crash-stop/crash-recovery only;
  a single lying node can break their guarantees entirely. Tolerating Byzantine failures
  needs a fundamentally different protocol family (PBFT, blockchain-style consensus) and,
  as the next section proves, meaningfully more nodes for the same fault count.

### The Byzantine threshold, verified

The classic result (Lamport, Shostak, Pease, 1982): reaching agreement among honest nodes
in the presence of `f` Byzantine (arbitrarily-lying) nodes requires **`n >= 3f+1`** total
nodes - not `2f+1`, the way crash-stop fault tolerance would. Verified with a simplified
implementation of their one-round "oral messages" algorithm (OM(1)): a commander
broadcasts a value, every lieutenant then relays what it personally received to every
other lieutenant, and each lieutenant decides by majority vote over everything it saw
directly and everything relayed to it.

```python
def om1_algorithm(n_total, commander_is_traitor, traitor_lieutenants,
                 value="attack", lie="retreat"):
    lieutenants = list(range(1, n_total))

    received_from_commander = {}
    for i in lieutenants:
        if commander_is_traitor:
            received_from_commander[i] = value if i % 2 == 0 else lie
        else:
            received_from_commander[i] = value

    relayed = {i: {} for i in lieutenants}
    for i in lieutenants:
        for j in lieutenants:
            if i == j:
                continue
            if i in traitor_lieutenants:
                relayed[i][j] = lie if received_from_commander[i] == value else value
            else:
                relayed[i][j] = received_from_commander[i]

    decisions = {}
    for j in lieutenants:
        own = received_from_commander[j]
        others = [relayed[i][j] for i in lieutenants if i != j]
        votes = [own] + others
        counts = {v: votes.count(v) for v in set(votes)}
        best = max(counts.values())
        tied = [v for v, c in counts.items() if c == best]
        decisions[j] = own if own in tied else tied[0]
    return decisions


print("n=3 total (1 commander + 2 lieutenants), f=1 traitor (the commander)")
print(f"n >= 3f+1 ?  3 >= {3*1+1} -> {3 >= 3*1+1}")
decisions_n3 = om1_algorithm(n_total=3, commander_is_traitor=True, traitor_lieutenants=[])
print(f"honest lieutenants' decisions: {decisions_n3}")
print(f"all agree: {len(set(decisions_n3.values())) == 1}\n")

print("n=4 total (1 commander + 3 lieutenants), f=1 traitor (the commander)")
print(f"n >= 3f+1 ?  4 >= {3*1+1} -> {4 >= 3*1+1}")
decisions_n4 = om1_algorithm(n_total=4, commander_is_traitor=True, traitor_lieutenants=[])
print(f"honest lieutenants' decisions: {decisions_n4}")
print(f"all agree: {len(set(decisions_n4.values())) == 1}")
```

```
n=3 total (1 commander + 2 lieutenants), f=1 traitor (the commander)
n >= 3f+1 ?  3 >= 4 -> False
honest lieutenants' decisions: {1: 'retreat', 2: 'attack'}
all agree: False

n=4 total (1 commander + 3 lieutenants), f=1 traitor (the commander)
n >= 3f+1 ?  4 >= 4 -> True
honest lieutenants' decisions: {1: 'retreat', 2: 'retreat', 3: 'retreat'}
all agree: True
```

![Verified: the same 1-traitor attack fails at n=3, succeeds at n=4 - exactly n >= 3f+1](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-7-byzantine-threshold-verified.png)

With `n=3` and a single traitor (the commander, lying differently to each of its two
lieutenants), the two honest lieutenants land on genuinely **different** decisions - real
disagreement, exactly as Lamport's impossibility proof predicts below the `3f+1` threshold.
With `n=4` and the identical attack, the same traitor can no longer force a split - the
honest lieutenants' majority vote, now drawing on more corroborating relayed reports than
the single traitor can corrupt, converges on the same answer every time. This is the
concrete reason Byzantine fault tolerance is so much more expensive than crash fault
tolerance: tolerating 1 Byzantine node needs 4 total nodes; tolerating 1 crash-stop node
(3.6's Raft) needs only 3.

## The 8 fallacies of distributed computing

![Eight assumptions a design makes, silently, until the network proves one wrong](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-7-eight-fallacies.png)

A list (originated at Sun Microsystems, L. Peter Deutsch and others) of assumptions that
feel obviously true from inside a single process, and are false the instant a system spans
more than one machine:

1. **The network is reliable** - it isn't; 2.1's live UDP demo dropped real messages on
   every single run.
2. **Latency is zero** - 0.3's latency ladder exists specifically because it isn't, by six
   orders of magnitude between an L1 cache hit and a cross-continent round trip.
3. **Bandwidth is infinite** - it's a real, shared, finite resource, which is exactly why
   2.2's gRPC/Protobuf section measured a real 3.25x size reduction as a genuine
   optimization, not a rounding error.
4. **The network is secure** - Part 7's entire scope exists because it isn't.
5. **Topology doesn't change** - nodes join, leave, and fail constantly; 3.4's rebalancing
   and 3.6's leader election both exist to handle topology changing out from under a
   running system.
6. **There is one administrator** - real systems span teams, vendors, and organizations
   with different priorities and change schedules, none of which coordinate with each other
   by default.
7. **Transport cost is zero** - sending data isn't free; 1.3's cost dimension and every
   cross-region replication decision in this course (2.7, 6.2) has to account for real
   transfer cost.
8. **The network is homogeneous** - different links, different hardware, different
   protocols all the way through - a design that assumes uniform behavior everywhere will
   be surprised by whichever link in the path is the exception.

Every one of these has already broken a real design somewhere in this course when ignored -
which is the entire reason this list is worth keeping explicit rather than treating as
obvious common sense: common sense is exactly what fails here, because single-machine
intuition simply doesn't transfer.

## Cheat sheet

```
SYNCHRONY     synchronous (bounded delay - timeouts reliably work) ->
MODELS        asynchronous (NO bounds - FLP's impossibility, 3.6, lives
              here) -> partially synchronous (bounds exist but unknown/
              eventual - what real systems actually assume; every
              timeout-based mechanism in this course is an engineering
              answer to THIS model, not a "solution" to FLP).

FAILURE       crash-stop (dies, never returns) -> crash-recovery (dies,
MODES         restarts, may lose volatile state - 3.1's WAL) -> omission
              (some messages just dropped - 2.1's measured UDP behavior)
              -> Byzantine (ARBITRARY/lying behavior - hardest, most
              expensive). Raft/Paxos (3.6) are crash-fault tolerant ONLY,
              not Byzantine fault tolerant.

BYZANTINE     agreement needs n >= 3f+1 nodes to tolerate f Byzantine
THRESHOLD     nodes - verified with Lamport's OM(1) algorithm: the SAME
              1-traitor attack caused real disagreement at n=3 (3 < 3(1)+1)
              and was defeated at n=4 (4 >= 3(1)+1). Tolerating 1 Byzantine
              node costs 4 total nodes vs. crash-tolerance's 3.

8 FALLACIES   network is reliable / latency is zero / bandwidth is
              infinite / network is secure / topology doesn't change /
              one administrator / transport cost is zero / network is
              homogeneous - every one already broken a design somewhere
              in this course (2.1's UDP drops, 0.3's latency ladder,
              2.2's real byte-size measurements, Part 7, 3.4/3.6's
```
