---
title: "2.7 Data redundancy and recovery"
---

2.5 and 2.6 assumed the API servers themselves can fail freely - a dead instance is just
removed from the load balancer's rotation, a new one takes its place, and nothing is lost,
because it held no data of its own. That assumption breaks completely the moment a
**database** node dies. This note is what a system has to do specifically because the
database layer is stateful and the application layer usually isn't.

## Stateless vs. stateful: why this needs its own answer

![A dead stateless instance loses nothing; a dead stateful one loses everything on it](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-7-stateless-vs-stateful.png)

Most API servers are **stateless** - any instance can handle any request, because none of
them hold data the others don't also have equal access to (session data lives in Redis or a
shared store, not in the process's own memory, precisely so this holds). A stateless
instance dying is a non-event: 2.5's load balancer routes around it, a replacement spins
up, and no data was ever uniquely tied to that one process.

A **database node** is the opposite: it *is* the data. A new, empty database instance is
not a replacement for a dead one - it's just an empty database. **A good system has to
deliberately design for this**, at whichever granularity the risk actually lives at:

- **Row/document level** - versioning or soft-deletes on individual records, so a single
  bad write or accidental delete is recoverable without touching anything else (undo a
  single row, not the whole database).
- **Document/object level** - object storage's native versioning (3.9): S3-style buckets
  can keep every previous version of a given key, recoverable independently per object.
- **Whole-database level** - full backups and continuous replication, covering total loss
  of the instance itself, not just one bad row.

## Two different tools for two different goals

![Periodic backup+restore vs. continuous replication - different recovery speed and cost](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-7-backup-vs-continuous.png)

The deciding question is **how current does the recovered copy need to be** - which is
usually phrased with two standard metrics worth knowing by name: **RPO** (Recovery Point
Objective - how much data, measured in time, can you afford to lose? "5 minutes of RPO"
means you can tolerate losing up to 5 minutes of the most recent writes) and **RTO**
(Recovery Time Objective - how long can recovery itself take before the system is back up?).

- **Periodic backup + restore** - take a full snapshot on a schedule (nightly, say), and
  separately, continuously archive the write-ahead log (3.1) so you're not limited to
  restoring exactly at snapshot time - more on this below. Cheaper and simpler to run day
  to day, but recovery means actually restoring a snapshot and replaying logs, which takes
  real wall-clock time (a real RTO cost) and loses whatever wasn't backed up yet (a real
  RPO cost, bounded by how often you snapshot and how promptly WAL gets archived).
- **Continuous replication** (3.5, in full mechanical depth) - a standby stays caught up
  (or nearly so) with the primary in near real time. Recovery is "promote the standby,"
  which is fast - a much better RTO - and RPO shrinks to whatever replication lag existed
  at the moment of failure (near-zero for synchronous replication, small for asynchronous).

These aren't mutually exclusive: a well-run system does both - continuous replication for
fast failover from a single node dying, *and* periodic backups (kept somewhere replication
itself can't protect against, like an accidental `DROP TABLE` that a standby would happily
replicate right along with the primary) for the disasters replication doesn't help with at
all.

## Backup and restore: point-in-time recovery, proven live

A full nightly snapshot alone only lets you restore to the moment the snapshot was taken -
losing up to a full day of writes in the worst case, and offering no way to recover to "the
moment right before someone ran a bad `UPDATE`" if that happened mid-afternoon. The fix
that makes precise recovery possible: keep the full backup **plus** the continuously
archived WAL segments since that backup, so you can replay forward to **any** specific
moment in between - **point-in-time recovery (PITR)**.

![PITR: replay WAL from the base backup up to, but not past, the recovery target](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-7-pitr-timeline.png)

Proven against a real Postgres instance - a genuine disaster (an accidental `UPDATE` and
`DELETE`), recovered to the exact moment just before it happened:

```python
import subprocess
import time
import shutil
import os


def psql(port, sql):
    r = subprocess.run(
        ["psql", "-h", SOCK, "-p", str(port), "-U", "postgres", "-tAc", sql],
        capture_output=True, text=True, check=True,
    )
    return r.stdout.strip()


def rows(port, sql):
    out = psql(port, sql)
    return [tuple(line.split("|")) for line in out.splitlines() if line]


BASE = "/tmp/pitr_demo3"
shutil.rmtree(BASE, ignore_errors=True)
os.makedirs(f"{BASE}/archive")
os.makedirs(f"{BASE}/sockets")

PRIMARY, BACKUP, RESTORED = f"{BASE}/primary", f"{BASE}/basebackup", f"{BASE}/restored"
SOCK, ARCHIVE = f"{BASE}/sockets", f"{BASE}/archive"

subprocess.run(["initdb", "-D", PRIMARY, "-U", "postgres", "--auth=trust"],
               check=True, capture_output=True)

with open(f"{PRIMARY}/postgresql.conf", "a") as f:
    f.write(f"""
listen_addresses = ''
unix_socket_directories = '{SOCK}'
wal_level = replica
archive_mode = on
archive_command = 'cp %p {ARCHIVE}/%f'
port = 5495
""")

subprocess.run(["pg_ctl", "-D", PRIMARY, "-l", f"{BASE}/primary.log", "start", "-w"],
               check=True, capture_output=True)

psql(5495, "CREATE TABLE accounts (id INT PRIMARY KEY, balance INT)")

# the full-backup baseline - everything after this is recovered via WAL replay
subprocess.run(["pg_basebackup", "-h", SOCK, "-p", "5495", "-U", "postgres",
               "-D", BACKUP, "-Fp", "-X", "stream"], check=True, capture_output=True)
print("full base backup taken")

psql(5495, "INSERT INTO accounts VALUES (1, 1000), (2, 2000)")
psql(5495, "SELECT pg_switch_wal()")
recovery_target = psql(5495, "SELECT now()")
print(f"GOOD data inserted, recovery target time recorded: {recovery_target}")

time.sleep(1)
psql(5495, "UPDATE accounts SET balance = 0 WHERE id = 1")
psql(5495, "DELETE FROM accounts WHERE id = 2")
print("BAD change applied: accidentally zeroed account 1 and deleted account 2")

state = rows(5495, "SELECT id, balance FROM accounts ORDER BY id")
print("state on the LIVE primary right now (post-disaster):", state)

psql(5495, "SELECT pg_switch_wal()")
time.sleep(0.5)
subprocess.run(["pg_ctl", "-D", PRIMARY, "stop", "-m", "fast", "-w"], check=True, capture_output=True)

# restore: copy the base backup, point it at the WAL archive, tell it exactly
# when to stop replaying
shutil.copytree(BACKUP, RESTORED)
open(f"{RESTORED}/recovery.signal", "w").close()
with open(f"{RESTORED}/postgresql.conf", "a") as f:
    f.write(f"""
restore_command = 'cp {ARCHIVE}/%f %p'
recovery_target_time = '{recovery_target}'
recovery_target_action = 'promote'
port = 5496
""")

subprocess.run(["pg_ctl", "-D", RESTORED, "-l", f"{BASE}/restored.log", "start", "-w"],
               check=True, capture_output=True)
time.sleep(1)

restored_state = rows(5496, "SELECT id, balance FROM accounts ORDER BY id")
print("state on the RESTORED instance (recovered to just before the bad change):", restored_state)

subprocess.run(["pg_ctl", "-D", RESTORED, "stop", "-m", "fast", "-w"], check=False, capture_output=True)
```

```
full base backup taken
GOOD data inserted, recovery target time recorded: 2026-09-29 17:46:48.29695+03
BAD change applied: accidentally zeroed account 1 and deleted account 2
state on the LIVE primary right now (post-disaster): [('1', '0')]
state on the RESTORED instance (recovered to just before the bad change): [('1', '1000'), ('2', '2000')]
```

(Re-running this yourself will show a different timestamp for the recovery target - what
matters is the mechanism, not the exact value.) The live primary, post-disaster, shows
account 1 zeroed and account 2 gone entirely. The
**restored** instance - built from the base backup with WAL replayed only up to
`recovery_target_time`, via a `recovery.signal` file and `recovery_target_action = 'promote'`
- shows both accounts exactly as they were **before** the bad change: account 1 still at
1000, account 2 still present at 2000. This is the actual mechanism behind "restore to 2:47
PM yesterday" style recovery: a full backup as the starting point, plus every WAL segment
archived since, replayed forward to any moment you choose - not just to whenever the last
snapshot happened to run. Note the archived WAL segments here are exactly what 3.5's
streaming replication ships to a standby in real time - point-in-time recovery and
continuous replication are, mechanically, the same underlying stream, used two different
ways.

## Storing one copy across regions

A local backup protects against losing one node or one disk; it does **not** protect
against losing the datacenter or region it lives in. **Geo-distributed backups** - keeping
at least one copy in a physically separate region - are what survive a whole-region outage:

![A local backup is fast to restore but useless if the whole region goes down](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-7-geo-backup.png)

In practice this is rarely a custom-built mechanism: 3.9's object storage (S3-style
buckets) commonly ships built-in cross-region replication for exactly this purpose - point
your backup artifacts at a bucket with cross-region replication enabled, and the "copy
across regions" requirement is largely solved by configuration rather than code. 6.2
(multi-region and geo-distribution) covers the deeper architecture of running *live*
across regions, not just backups - this note's scope is specifically the recovery-copy
question, not full active-active geo-distribution.

## Cheat sheet

```
WHY THIS      stateless API servers (2.5): a dead instance loses NOTHING -
NEEDS ITS     no unique data lived there. Stateful databases: a dead node
OWN ANSWER    IS the data - a system has to deliberately plan for this.

GRANULARITY   row/document level (versioning, soft-delete - undo ONE record)
              vs. whole-database level (full backups, replication - recover
              from total instance loss).

RPO / RTO     RPO = how much recent data can you afford to lose (bounded by
              backup frequency / replication lag). RTO = how long can
              recovery itself take. Backup+restore: cheaper, worse RPO/RTO.
              Continuous replication (3.5): near-real-time RPO, fast RTO
              (just promote the standby) - not mutually exclusive with
              backups, which catch disasters replication would faithfully
              replicate too (a bad DROP TABLE).

PITR          full base backup + continuously archived WAL = recover to ANY
              point in time, not just the last snapshot. Verified live: an
              accidental UPDATE+DELETE on the primary were fully reversed on
              a restored instance recovered to the timestamp recorded just
              before the bad change - the base backup + archived WAL are
              mechanically the same stream 3.5's replication ships live,
              used for point-in-time recovery instead of a live standby.

CROSS-REGION  a local backup doesn't survive a whole-region outage - keep at
              least one copy elsewhere. Usually solved by object storage's
              (3.9) built-in cross-region replication, not custom code. Full
              active-active geo-distribution is 6.2's scope, not this note's.
```
