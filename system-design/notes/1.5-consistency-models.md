---
title: "1.5 Consistency models"
---

1.4 covered consistency as one side of a trade-off, without defining precisely what
"consistent" even means - and it turns out there isn't one answer. This note is the actual
spectrum, from the strongest, most expensive guarantee to the weakest, cheapest one, plus
two "session guarantees" that let a system feel much stronger to one client without paying
for global strong consistency.

![The consistency spectrum, strongest to weakest](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-5-consistency-spectrum.png)

## Strong consistency

**Strong consistency** means every read reflects the most recent write, globally, as if
there were only ever one copy of the data - no client can ever observe a stale value, no
matter which replica answers. This is the guarantee 1.4's CP systems and 3.5's synchronous
replication are built to provide, and it's expensive for exactly the reason 1.4 already
proved live: guaranteeing it means waiting for replicas to actually catch up (the 4.06s
synchronous-commit block when a standby was unreachable) rather than ever answering from a
replica that might be behind.

## Eventual consistency

**Eventual consistency** is the weak end of the spectrum: if no new writes happen,
replicas are only guaranteed to **eventually** converge to the same value - with no bound
on how long "eventually" takes, and no guarantee about what a read sees in the meantime.
This is 3.5's asynchronous replication, 1.4's AP systems, and the default mode for
leaderless quorum stores. Cheap and highly available, at the cost of genuinely
unpredictable staleness windows.

## Causal consistency

**Causal consistency** sits between the two: operations that are **causally related** must
be seen in that order by every observer, while **concurrent** (causally unrelated)
operations may be seen in different orders by different observers without violating
anything. The canonical example is a question and its answer - nobody should ever see a
reply before the comment it's replying to, even if two *unrelated* comments on the same
post can legitimately show up in a different order for different readers.

Verified directly: a reply event that causally depends on a post event, delivered through a
network where the reply's message happens to **arrive first**:

```python
class Feed:
    def __init__(self):
        self.visible = []

    def deliver_naive(self, event_id, depends_on, content):
        self.visible.append((event_id, content))

    def deliver_causal(self, event_id, depends_on, content, pending):
        delivered_ids = {e for e, _ in self.visible}
        if depends_on is not None and depends_on not in delivered_ids:
            pending.append((event_id, depends_on, content))
            return
        self.visible.append((event_id, content))
        still_pending = []
        for e, dep, c in pending:
            if dep == event_id or dep in delivered_ids:
                self.visible.append((e, c))
            else:
                still_pending.append((e, dep, c))
        pending[:] = still_pending


events_out_of_order = [
    ("reply_1", "post_1", "42, obviously"),
    ("post_1", None, "what's the answer to everything?"),
]

feed_naive = Feed()
for event_id, depends_on, content in events_out_of_order:
    feed_naive.deliver_naive(event_id, depends_on, content)
print("naive delivery:", feed_naive.visible)

feed_causal = Feed()
pending = []
for event_id, depends_on, content in events_out_of_order:
    feed_causal.deliver_causal(event_id, depends_on, content, pending)
print("causal delivery:", feed_causal.visible)
```

```
naive delivery: [('reply_1', '42, obviously'), ('post_1', "what's the answer to everything?")]
causal delivery: [('post_1', "what's the answer to everything?"), ('reply_1', '42, obviously')]
```

![Verified: naive delivery shows the reply before its own question; causal delivery buffers it until the dependency arrives](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-5-causal-verified.png)

Naive delivery shows exactly the bug the model name warns about - the reply appears
*before* the question it answers. The causal-delivery version simply **buffers** an event
until its dependency has already been delivered, which fixes the ordering without requiring
any global coordination - this buffer-until-dependency-ready mechanism (tracked in real
systems with vector clocks or similar causal metadata) is the actual implementation
technique behind causal consistency in practice.

## Two session guarantees: read-your-writes and monotonic reads

These aren't a third point on the strong-to-eventual spectrum - they're **per-client**
promises a system can layer on top of an otherwise eventually-consistent model, making it
feel far stronger from any *one* client's perspective without paying strong consistency's
full global cost.

### Read-your-writes

**Read-your-writes** guarantees a client always sees its **own** writes in subsequent
reads - even if it might still see *other* clients' writes late or out of order. Verified
against a leader-plus-lagging-followers setup (3.5's exact topology):

```python
class Replica:
    def __init__(self, name, lag_writes_by=0):
        self.name = name
        self.lag_writes_by = lag_writes_by
        self.committed = []

    def apply(self, version, value):
        self.committed.append((version, value))

    def read(self):
        visible = self.committed[:len(self.committed) - self.lag_writes_by] \
            if self.lag_writes_by else self.committed
        return visible[-1] if visible else (0, None)


class Cluster:
    def __init__(self):
        self.leader = Replica("leader")
        self.followers = [Replica("follower-A", lag_writes_by=1),
                          Replica("follower-B", lag_writes_by=2)]
        self.version = 0

    def write(self, value):
        self.version += 1
        self.leader.apply(self.version, value)
        for f in self.followers:
            f.apply(self.version, value)
        return self.version


cluster = Cluster()
cluster.write("profile_pic_v1")
cluster.write("profile_pic_v2")
my_version = cluster.write("profile_pic_v3")

read_version, read_value = cluster.followers[1].read()
print(f"naive read from a lagging replica: got version {read_version} ({read_value!r}) "
     f"- I wrote version {my_version}")

def read_your_writes(cluster, min_version):
    for r in [cluster.leader] + cluster.followers:
        v, val = r.read()
        if v >= min_version:
            return r.name, v, val

name, v, val = read_your_writes(cluster, min_version=my_version)
print(f"version-aware read (require >= {my_version}): routed to {name}, got version {v} ({val!r})")
```

```
naive read from a lagging replica: got version 1 ('profile_pic_v1') - I wrote version 3
version-aware read (require >= 3): routed to leader, got version 3 ('profile_pic_v3')
```

![Verified: a naive read missed the client's own write; a version-aware read routed correctly and found it](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-5-read-your-writes-verified.png)

A client that just updated their profile picture to v3 and immediately reads from a lagging
replica gets back v1 - a jarring, very visible bug class ("I just saved this, why does it
look like it reverted?"). The fix is a **version token**: track the version a client last
wrote, and only route its reads to a replica that has caught up to at least that version
(falling back to the leader, which is always current, if no replica has caught up yet).

### Monotonic reads

**Monotonic reads** guarantees that once a client has seen a value, it never later sees an
**older** one - time doesn't appear to run backwards across a sequence of reads, even
across different replicas:

```python
cluster2 = Cluster()
cluster2.write("v1")
cluster2.write("v2")
cluster2.write("v3")

v_a, val_a = cluster2.followers[0].read()
print(f"read 1, from {cluster2.followers[0].name}: version {v_a}")
v_b, val_b = cluster2.followers[1].read()
print(f"read 2, from {cluster2.followers[1].name}: version {v_b}")

sticky_replica = cluster2.followers[0]
v_a2, _ = sticky_replica.read()
v_b2, _ = sticky_replica.read()
print(f"sticky: read 1 version {v_a2}, read 2 version {v_b2}")
```

```
read 1, from follower-A: version 2
read 2, from follower-B: version 1
sticky: read 1 version 2, read 2 version 2
```

![Verified: switching replicas mid-session let time run backwards; sticky routing fixed it](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-5-monotonic-reads-verified.png)

Reading from `follower-A` (less lagged) and then `follower-B` (more lagged) on the *very
next* request shows version 2 followed by version 1 - the data appears to un-happen. The
fix here is **sticky routing**: keep a client pinned to the same replica for the duration
of its session (or, more robustly, the same version-token technique read-your-writes uses,
refusing to serve a replica whose version has regressed relative to what the client has
already seen).

## Cheat sheet

```
SPECTRUM      strong (every read = latest write, globally, expensive -
              1.4's CP/sync) -> causal (causally-related ops ordered,
              concurrent ones free to differ) -> eventual (replicas
              converge with NO time bound - 1.4's AP/async). Weaker =
              cheaper, more available (1.4's PACELC trade).

CAUSAL        causally-dependent events must be seen in dependency order;
              unrelated ones don't need to be. Verified: a reply shown
              before its own question under naive delivery; buffering an
              event until its dependency arrives fixed the ordering
              exactly (the real mechanism behind vector clocks).

READ-YOUR-    a per-client promise: you always see YOUR OWN writes, even
WRITES        on an otherwise eventually-consistent system. Verified: a
              naive read from a lagging replica missed a profile-pic
              update by 2 versions; a version-aware read (route to a
              replica caught up to >= the client's own write) fixed it.

MONOTONIC     once a client has seen a value, it never sees an OLDER one
READS         later. Verified: switching replicas mid-session made a
              version appear to go backwards (2 then 1); sticky routing
              (same replica every time) fixed it exactly.

KEY INSIGHT   read-your-writes and monotonic reads are NOT a 3rd spectrum
              point - they're session-scoped add-ons layered on top of an
              eventually-consistent system, giving one client a much
              stronger-feeling experience without paying strong
              consistency's full, global cost.
```
