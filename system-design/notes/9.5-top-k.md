---
title: "9.5 Top-K / Trending (Heavy Hitters)"
---

"Top-K" is one problem wearing a dozen costumes: YouTube's trending videos, Google's top
searches, Spotify's most-played songs this week, Twitter's trending topics, and - the
Bloomberg flavor we'll specialize this into in 10.4 - the most-read news stories on the
Terminal right now. Strip the product skin off and it's always the same question: **given
a huge, fast-moving stream of (item, event) pairs, which K items occurred most often in a
given time range?** This is also called the **heavy hitters** problem in the literature.

We're going to build this up the way you should in an interview: start with the dumbest
correct thing, find where it breaks, fix that one thing, repeat. By the end you will have
derived - not memorized - the architecture that production systems actually use.

## Requirements

**Functional**

```
topK(k, startTime, endTime) -> the k items with the highest event count
                                 in [startTime, endTime]
```

The time range is part of the signature on purpose - "trending" is meaningless without a
window. Top-K "of all time" and top-K "in the last hour" are different queries.

**Pin down what "window" means, precisely** - small ambiguity here changes the whole
downstream design:

- **Tumbling windows** - fixed, non-overlapping buckets on fixed boundaries. "Last week"
  means the Sunday-to-Sunday period that just ended. One bucket per period, and it never
  changes retroactively once it closes.
- **Sliding windows** - a fixed-width window that re-evaluates on every slide interval (a
  minute, say) and keeps moving forward as time passes. "Last 7 days" evaluated every
  minute means 60x24x7 distinct window instances a week, not one.

![Tumbling windows vs. sliding windows](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-tumbling-vs-sliding.png)

Default to assuming tumbling windows and say so explicitly - they're dramatically cheaper
to maintain, and for anything longer than an hour, users rarely notice or care whether
"this month" is a fixed calendar month or a rolling 30 days. Only build sliding windows
where the interviewer actually asks for them, or where the product genuinely needs
second-by-second freshness at a short granularity (sliding by the minute over the last
hour is common and cheap; sliding by the minute over the last month is usually overkill -
see the note under "rollups" below).

**Non-functional**

- **Scalable** - throughput and storage need to scale out as event volume grows; you
  cannot re-architect every time traffic doubles.
- **Highly available** - survives host, rack, and network failures. No single point of
  failure.
- **Highly performant** - this is the requirement that quietly tells you the answer has to
  be **precomputed**. If you had to scan raw events on every read, no latency target
  survives real traffic. Precomputation means: do the work once, on write, and serve reads
  from the result. In an interview, it's worth naming actual numbers for the read path:
  a cache hit should be single-digit milliseconds (the gold standard for a distributed
  system), a well-tuned uncached API is tens of milliseconds, and anything that has to
  search or rank across a huge space (or calls an LLM) can be hundreds of milliseconds to
  seconds. Top-K should live in the first bucket.
- **A write-side freshness SLA** - separately from read latency, pin down how long an event
  is allowed to take to show up in the result: "an event must be reflected within 1 minute
  of occurring." This single number does two jobs at once - it's an **upper bound on any
  cache TTL** downstream (serving a 2-minute-stale cache entry would violate a 1-minute
  SLA), and it tells you exactly how long you're allowed to wait for **late or
  out-of-order events** before you can safely ignore them. Distributed systems reorder and
  delay things - retries, network congestion, partition rebalances - so "how late is too
  late" has to be a decision you make on purpose, not an accident of whatever happens to
  arrive.
- **Accurate** - and we're about to find out that this one is negotiable, and trading a
  little of it away buys you a lot of the other three. A useful test for whether
  approximation is acceptable at all: **who notices if the answer is slightly wrong, and do
  they care?** For a "trending" or "most popular" surface, the answer is usually no - a few
  percent of error on an already-fuzzy ranking is invisible to users. For a billing count
  or an audit log, the answer is yes, and approximation is off the table. Decide this
  explicitly and say so - it tells your interviewer up front whether Count-Min Sketch
  (below) is even in scope, without you having to guess whether they want to see it. And
  strategically: lead with the exact, simple solution regardless. Approximate structures
  are a strong **deep dive** to bring up if there's time and the requirements invite it,
  not a good opening move - they add real complexity, and risk landing on an interviewer
  who isn't familiar with them and has nowhere to go with your answer.

## Start with one host

Forget distributed systems for a second. Given a batch of events in memory, how do you get
the top K?

Stream: `A B C A A D C B A` (A, B, C, D are item ids - think news-story ids).

**Sort everything.** Count occurrences into a hashmap, sort the entries by count,
take the first K. Counting is `O(n)`. Sorting `u` unique items is `O(u log u)`. Simple,
but you're sorting the *whole* key space to read off a handful of winners - wasteful when
`u` is large and `k` is small.

**Better: a min-heap of size K.** Walk the counted items once. Keep a heap that never
grows past size K: push while there's room, and once full, replace the current minimum
only if the new item beats it. This is `O(u log k)` - and since `k` is small (see "how big
is k" below) and fixed, this is effectively linear in the number of unique items. This is
also LeetCode 347, *Top K Frequent Elements*, verbatim.

```python
import heapq
from collections import Counter

def top_k_frequent(stream, k):
    counts = Counter(stream)                      # O(n)
    heap = []                                      # min-heap of (count, item), size k
    for item, cnt in counts.items():                # O(u) unique items
        if len(heap) < k:
            heapq.heappush(heap, (cnt, item))
        elif cnt > heap[0][0]:
            heapq.heapreplace(heap, (cnt, item))
    heap.sort(reverse=True)                         # O(k log k), k is small
    return [(item, cnt) for cnt, item in heap]
```

Run it on the example:

```
counts: {'A': 4, 'B': 2, 'C': 2, 'D': 1}
top 2 : [('A', 4), ('B', 2)]
top 1 : [('A', 4)]
top 4 : [('A', 4), ('C', 2), ('B', 2), ('D', 1)]
```

(B and C tie at 2 - which one a heap returns for a partial top-k depends on heap internals,
not on anything meaningful. Production systems need a deterministic tiebreak, e.g. "most
recently updated wins," or you'll see items flicker in and out of the list for no reason.)

This single-host version is correct and fast. It is also useless in production: it assumes
the whole key space fits in one process's memory, and it assumes one CPU can absorb the
entire event stream. Neither holds at YouTube-, Google-, or Bloomberg-terminal scale.

## Scale out - the naive way

The obvious move: put a load balancer in front of a pool of processor hosts, and let them
share the work.

![Naive multi-host scale-out and why it breaks](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-naive-scaleout.png)

Events get spread across N processor hosts (round-robin or random), each keeps its own
hashmap, and results get pushed into a storage host. Two problems surface immediately:

1. **Memory.** Every processor host's hashmap can, in the worst case, hold an entry for
   *any* key in the system - the routing doesn't guarantee a host only ever sees a
   restricted set of keys. Same for the storage host, which now has to reconcile
   contributions from every processor. Nothing here bounds memory.
2. **Correctness (the quieter problem).** Since routing ignores the key, the *same* item's
   events land on different hosts. No single host's hashmap has the true count for
   anything - you'd need to merge counts across all N hosts for every single key, which
   defeats the purpose of distributing the work in the first place.

## The fix: partition by key

Route by `hash(item_id)`, not randomly. Now every event for a given item always lands on
the same processor host.

![Partitioned scale-out with local top-k and an exact merge](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-partitioned-scaleout.png)

Each processor now runs the single-host algorithm above, but only over **the slice of the
key space it owns**. That bounds its memory to `(total keys) / (number of hosts)`, and each
host only has to absorb `1/N` of the traffic - that's the scalability *and* the throughput
win, worth spelling out separately:

- **Scalability**: to handle more unique items, add more partitions. Each host's memory
  footprint stays roughly constant as the system grows, because the key space per host
  shrinks as you add hosts.
- **Throughput**: to handle more events per second, add more hosts (finer partitioning),
  because the hosts process in parallel. Total system throughput scales with host count,
  not with any single host's CPU.

Now, how do you combine N per-host results into one global answer? Each processor computes
its own **local top-k** with the exact same heap algorithm as the single-host version.
Then a merge step combines the N sorted local lists into the global top-k - this is LeetCode
23, *Merge K Sorted Lists*, applied to arrays of `(count, item)` instead of linked lists.

The reason this is *exact*, not approximate, is the key fact of this whole section:

> Because we partitioned by key, one item's total count lives **entirely inside one
> shard**. If an item isn't in its own shard's local top-k, that means at least K other
> items *in that same shard* already have a higher count than it - and since its count
> can't be any higher anywhere else (it has no events on any other shard), it cannot
> possibly be in the global top-k either. So the union of every shard's local top-k list
> is *guaranteed* to contain the true global top-k. Merging is exact.

```python
import heapq
import hashlib
from collections import Counter

def stable_hash(key):
    """A hash that's stable across runs. Python's builtin hash() is randomized
    per-process for strings (a security measure), which would make this demo
    non-reproducible - real partitioners use a fixed hash for the same reason."""
    return int(hashlib.md5(str(key).encode()).hexdigest(), 16)

def partition(stream, num_partitions):
    """Simulate a data partitioner: route every event for a key to one partition."""
    parts = [[] for _ in range(num_partitions)]
    for item in stream:
        parts[stable_hash(item) % num_partitions].append(item)
    return parts

def local_top_k(events, k):
    """What one processor host does: exact top-k over the keys it owns."""
    counts = Counter(events)
    heap = []
    for item, cnt in counts.items():
        if len(heap) < k:
            heapq.heappush(heap, (cnt, item))
        elif cnt > heap[0][0]:
            heapq.heapreplace(heap, (cnt, item))
    return sorted(heap, reverse=True)  # (count, item), descending

def merge_k_sorted(lists, k):
    """k-way merge of already-sorted-descending lists -> global top-k."""
    heap = []
    for li, lst in enumerate(lists):
        if lst:
            cnt, item = lst[0]
            heapq.heappush(heap, (-cnt, li, 0, item))
    merged = []
    while heap and len(merged) < k:
        negcnt, li, ei, item = heapq.heappop(heap)
        merged.append((item, -negcnt))
        if ei + 1 < len(lists[li]):
            cnt2, item2 = lists[li][ei + 1]
            heapq.heappush(heap, (-cnt2, li, ei + 1, item2))
    return merged
```

On the same example, partitioned across 3 hosts:

```
partitions:                  [[], ['A', 'B', 'C', 'A', 'A', 'C', 'B', 'A'], ['D']]
local top-2 per partition:   [[], [(4, 'A'), (2, 'B')], [(1, 'D')]]
global top-2 (merged):       [('A', 4), ('B', 2)]
single-host ground truth:    [('A', 4), ('B', 2)]
```

Exact match. (Notice the split is lopsided - two of three partitions are nearly empty. With
only 4 distinct keys, a hash function has nothing to average over; at real scale, with
millions of keys, the law of large numbers takes care of this. The residual imbalance that
*does* still show up at scale, even with a good hash, is exactly the "hot partition"
problem two sections down - and the standard fix, consistent hashing with many virtual
nodes per physical node, is what makes the averaging effect kick in reliably even for a
handful of disproportionately large keys.)

## From bounded batches to an unbounded stream

Everything above assumed a fixed batch of events sitting in memory. Real traffic never
stops. The natural adaptation: each processor host accumulates counts for **one time
window** - say, one minute - then flushes its local top-k for that minute to storage and
resets. Now storage holds a top-k list per minute, per item-space.

That answers `topK(k, minute_i_start, minute_i_end)` immediately. But the actual product
need is usually "top news **this hour**" or "**today**." Can you get those by combining the
stored per-minute lists?

**No - and this is worth understanding precisely, because it's the single most common trap
in this design.**

![Why merging per-minute top-k lists does not give an exact hourly top-k](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-window-counterexample.png)

Here's a concrete, measured counterexample. Simulate 60 one-minute windows. Item `Z` scores
a steady 5 every single minute (true hourly total: 300) - but five other, noisier items
always score 6-9 in any given minute, so `Z` never once makes that minute's published
top-3. Its count is thrown away, every single minute, forever.

```
Z's true total over the hour :  300
Z ever appears in a stored per-minute top-3?  False

(A) EXACT hourly top-3 (computed from the raw per-minute counts): [('d', 457), ('a', 451), ('e', 448)]
(B) top-3 from MERGING the 60 stored per-minute top-3 lists:      [('a', 363), ('b', 306), ('d', 292)]

Do they agree? False
```

(A) and (B) don't even name the same three items. Worse: item `d`'s stored, merged total
(292) is *wrong* even for an item that *is* in both lists, because on the minutes `d`
wasn't in that minute's top-3, its count for that minute was discarded - so the merged sum
systematically undercounts everything, and undercounts different items by different,
unpredictable amounts. There is no way to fix this by cleverness at merge time - **the
information needed is simply gone.** The only ways to get an exact answer for a longer
window are: (a) go back to the raw events for that whole window and recompute, or (b)
maintain a structure over the whole window incrementally, from the start of the window, that
doesn't throw partial information away (which is exactly what the Count-Min Sketch below
does).

### The fix that actually works: roll up counts, never roll up top-k lists

The counterexample's lesson is specific: it's the **top-k list** that doesn't compose, not
the **counts** underneath it. A per-item count is a plain sum, and sums are exactly the
kind of thing that *does* roll up safely (this is the monoid idea from the aggregation
principles section, below, applied here first). So keep the fine-grained structure as raw
per-item counts, per bucket - not pre-filtered top-k lists - and only compute top-k at read
time, from the composed counts, over whatever window was asked for.

For **tumbling** windows, the standard trick is to fan out each write into every rollup
grain you plan to serve, simultaneously: an event for video X at 14:23 increments the
14:23 **minute** counter, the 14:00 **hour** counter, and today's **day** counter, all at
once (3x the writes, but writes are cheap and this is exactly the pre-aggregation /
"aggregate close to the source" principle below). Each grain gets its own table, indexed
on `(bucket, count)`.

![One event fans out into every rollup grain at write time](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-rollup-writes.png)

The payoff: `topK(k, this_hour)` is now a single sorted-index read on the hour table - no
aggregation at query time at all, because the rollup already did the summing when the
event was written. This is the same index-driven trick from the single-host section, just
applied per grain: a B-tree (or any sorted structure) on `(bucket, count)` lets the query
planner walk straight to the top K rows instead of scanning and sorting everything in the
bucket.

For **sliding** windows, fan-out-to-fixed-grains doesn't fit (there's no fixed "the hour"
bucket to write into), so instead maintain the total incrementally: keep counts at the
finest grain you need (say, per minute), and as each new minute arrives, **add its counts
into a running per-item total and subtract the minute that just fell out of the window**.
This is the same idea as the classic sliding-window-sum pattern, applied per key instead of
to a single number:

```python
from collections import defaultdict, deque

class SlidingWindowTotals:
    """Maintains an exact per-item sum over the last W buckets in O(items in
    the incoming/outgoing bucket) per step, instead of O(W) recomputation."""

    def __init__(self, window_size):
        self.w = window_size
        self.buckets = deque()      # the last <=W bucket count-dicts
        self.running = defaultdict(int)

    def advance(self, new_bucket_counts):
        self.buckets.append(new_bucket_counts)
        for item, c in new_bucket_counts.items():
            self.running[item] += c
        if len(self.buckets) > self.w:
            old = self.buckets.popleft()
            for item, c in old.items():
                self.running[item] -= c

    def snapshot(self):
        return {k: v for k, v in self.running.items() if v != 0}
```

Verified against brute-force recomputation (rebuild the sum from the raw buckets from
scratch) at every one of 200 steps, window = 60 buckets, 20 items with random per-bucket
counts:

```
checked 200 steps, window=60 buckets
mismatches between incremental and brute-force: 0
```

The sorted list/heap of current top-k candidates gets maintained the same way - update it
whenever a tracked item's running total changes, same lazy-heap idea as `TopKTracker`
above. (If you're using the Count-Min Sketch instead of exact counts for a sliding window,
the same idea applies: this only works because add-then-later-subtract is a **valid
"turnstile" operation** on a sketch - you may only ever subtract counts you previously
added, never go negative on something you never saw, and the same error bounds continue to
hold. Size the candidate heap a bit larger than K for a sliding sketch, since items near
the boundary can wobble in and out as the window moves - a heap of a few thousand for a
top-100 query is a typical safety margin.)

## Getting exact answers for long windows: keep the raw data

So: store the raw events themselves (or at least full per-item counts, not just top-k
lists) to disk, per window, and run a **batch job** over the full range whenever an
exact `topK(k, start, end)` is requested for a range you haven't precomputed. This is
correct by construction - you're back to the single-host algorithm, just run over a lot
more data, distributed (MapReduce, below).

Storing everything durably, distributed, at this volume, buys you three new problems for
free:

- **Replication.** Disks and nodes fail. Each partition of raw data needs multiple copies
  (typically 3) on independent nodes, so losing one machine doesn't lose data. This is a
  straight trade of storage cost for durability and availability.
- **Rebalancing.** When you add or remove nodes (capacity change, failure, planned
  maintenance), the partition-to-node assignment has to shift, or the new node sits idle
  while old ones stay overloaded. Consistent hashing (Part 3.4) keeps this from meaning
  "reshuffle everything" every time the cluster size changes - only the affected slice of
  keys moves.
- **Hot partitions.** Partitioning by key assumes keys generate roughly even load. They
  don't. A single viral video, a single breaking-news story, a single stock everyone is
  watching after an earnings call - all of it lands on *one* partition, and that one host
  gets a wildly disproportionate share of traffic while its neighbors idle.

![Hot partitions: one shard can take a hugely disproportionate share](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-hot-partition.png)

Mitigations for hot partitions: salt the hot key into several sub-keys (`news_42#0` ..
`news_42#7`) and fan writes across them, aggregating at read time; detect hot keys and give
them dedicated capacity; or pre-aggregate at the edge (client- or gateway-side batching)
so a viral item generates fewer, pre-summed writes instead of one write per raw event.

## A cheaper path: sacrifice some accuracy - the Count-Min Sketch

Storing every raw event and batch-processing it is exact, but it's slow (minutes to hours)
and storage-heavy. If you can tolerate a small, *provably bounded* amount of error, a
**Count-Min Sketch (CMS)** answers "what's this item's approximate count?" in O(1) memory
per operation and a fixed, tiny total memory footprint - independent of how many unique
items exist.

**Structure.** A 2D array of counters: `d` rows x `w` columns. Each row has its own
independent hash function `h_1 .. h_d`, each mapping an item to one of the `w` columns.

**Add.** To record an event for an item, hash it with each of the `d` hash functions and
increment the corresponding cell in each row. One event touches exactly `d` cells (one per
row).

**Query.** Hash the item the same `d` ways, and return the **minimum** of the `d` cells.
Why the minimum, and not the average or the max? Because different items can collide into
the same cell in any given row (that's just a hash collision), and a collision can only
ever add extra weight into a cell that belongs to *other* items - it can never remove
weight. So every cell is an overestimate of the true count of any item that maps there. The
minimum across `d` *independent* rows is the tightest overestimate you can construct: for
your item's true count to be masked in every single row, it would have had to collide with
a heavy item in *all d* independently-hashed rows at once - and that's the tail event the
math below controls.

![Count-Min Sketch structure: d hash functions x w counters](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-cms-grid.png)

**Choosing width and depth.** Two parameters control the guarantee:

- **epsilon (ε)** - the accuracy you want: the estimate will overshoot the true count by at
  most `ε x N`, where `N` is the total number of events added so far.
- **delta (δ)** - the certainty you want that the bound above actually holds (the failure
  probability is `δ`).

```
width  w = ceil(e / epsilon)         (e here is Euler's number, ~2.71828)
depth  d = ceil(ln(1 / delta))
```

Guarantee: with probability at least `1 - δ`, `query(item) <= true_count(item) + ε x N`.
Note this is **one-sided** - CMS never under-counts, only ever over-counts, and only by a
bounded amount. That is a very useful property for a top-k use case: it means CMS is
biased toward *false positives* on the heavy-hitter list (an item looking bigger than it
is), never toward hiding a genuinely heavy item.

A CMS answers "what's the count of *this one item*?" - it does not, by itself, answer
"which items are the top K?" (it doesn't even know what items exist). Pair it with the
same size-K min-heap idea from the single-host version: every time an event arrives, update
the sketch, re-query that item's new estimate, and update a size-K heap of best-known
candidates. Because CMS estimates only ever grow, a plain heap (no decrease/increase-key
operation) needs a small trick - lazy deletion:

```python
import hashlib
import math
import heapq


class CountMinSketch:
    def __init__(self, epsilon, delta):
        self.w = math.ceil(math.e / epsilon)
        self.d = math.ceil(math.log(1 / delta))
        self.table = [[0] * self.w for _ in range(self.d)]
        self.n = 0

    def _hash(self, item, row):
        h = hashlib.md5(f"{row}:{item}".encode()).hexdigest()
        return int(h, 16) % self.w

    def add(self, item, count=1):
        self.n += count
        for row in range(self.d):
            self.table[row][self._hash(item, row)] += count

    def query(self, item):
        return min(self.table[row][self._hash(item, row)] for row in range(self.d))


class TopKTracker:
    """CMS gives one item's estimate; this pairs it with a size-k heap of the
    current best candidates, so the pair together answers topK() directly."""

    def __init__(self, k, epsilon=0.001, delta=0.01):
        self.k = k
        self.cms = CountMinSketch(epsilon, delta)
        self.best = {}   # item -> current tracked estimate; |best| <= k always
        self.heap = []    # (estimate, item); may contain stale entries

    def _evict_stale(self):
        while self.heap and self.best.get(self.heap[0][1]) != self.heap[0][0]:
            heapq.heappop(self.heap)

    def add(self, item, count=1):
        self.cms.add(item, count)
        est = self.cms.query(item)

        if item in self.best:
            self.best[item] = est
            heapq.heappush(self.heap, (est, item))
            return
        if len(self.best) < self.k:
            self.best[item] = est
            heapq.heappush(self.heap, (est, item))
            return

        self._evict_stale()
        if self.heap and est > self.heap[0][0]:
            _, evicted = heapq.heappop(self.heap)   # the true current minimum
            del self.best[evicted]
            self.best[item] = est
            heapq.heappush(self.heap, (est, item))

    def top_k(self):
        return sorted(self.best.items(), key=lambda kv: -kv[1])
```

Verified against ground truth on a 200,000-event Zipf-skewed stream (heavy skew, like real
popularity distributions - a handful of items get most of the traffic):

```
epsilon=0.005  delta=0.01  ->  width w=544  depth d=5
n=200,000 events, error bound (epsilon * n) = 1000.0

max overestimate error actually seen:      232   (bound was 1000.0 - well inside it)
items ever under-counted:                  0     (confirms the one-sided error property)
items where the error exceeded the bound:  0 / 500

true  top10: item1 item2 item3 item4 item5 item6 item7 item8 item9 item10
cms   top10: item1 item2 item3 item4 item5 item6 item7 item8 item9 item10
match: True
```

And the `TopKTracker` (CMS + heap together, tracking only K items in memory throughout,
never the full key space) reproduces the exact top-10, in the exact correct order, over a
separate 100,000-event stream - `assert len(tracker.best) <= 10` holds after every single
event.

## Putting it together: the high-level architecture

Now assemble every piece above into one pipeline. Events flow through two parallel paths -
a fast, approximate one, and a slow, exact one - and reads are served from whichever result
is fresher.

![High-level architecture: speed layer and batch layer](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-lambda-architecture.png)

1. **Client -> API gateway.** Auth, TLS termination, rate limiting - and, specific to this
   system, it's also where client events get logged. A background process on the gateway
   **batches and periodically flushes** these events rather than shipping one network call
   per view/click - cuts request volume by orders of magnitude before it even hits the
   pipeline.
2. **Kafka**, partitioned (by item id, same reasoning as the processor partitioning above)
   and replicated. This is the durable buffer between "things happened" and "things got
   processed" - it decouples producer rate from consumer rate and lets you replay history
   if a downstream consumer needs to reprocess.
3. **Fast path (speed layer)** - a fast processor (a **Flink** or **Spark Structured
   Streaming** job, in practice - see the Kappa discussion below) consumes the Kafka stream
   directly, maintains a Count-Min Sketch + heap per time window, and flushes an
   *approximate* top-k to the storage service within seconds. In production this is often
   literally Redis: Redis ships a native Count-Min Sketch module (`CMS.INCRBY`,
   `CMS.QUERY`) alongside sorted sets, which is `CountMinSketch` + `TopKTracker` from above,
   already built. Being a volatile in-memory store, you'd back it with replicas and an
   append-only file for durability - and since the whole path is already an approximation,
   losing a few seconds of updates on a crash is rarely worth much more engineering than
   that.
4. **Slow path (batch layer)** - a data partitioner (with replication) routes raw events to
   partition processors, each of which does **local pre-aggregation** (a partial reduce, in
   MapReduce terms - see below) before writing to a distributed file system (HDFS or S3).
   Two chained MapReduce jobs then run over that data: **Frequency Count** (get exact
   per-item totals) and **Top-K** (reduce those exact totals down to the final list). This
   path is slower (minutes to hours) but produces the *exact* answer.
5. **Storage service (serving layer)**: serves the fast, approximate result the instant
   it's available, and **swaps in the exact result** for that window once the batch job
   finishes. A client asking `topK(k, start, end)` for a window that isn't fully processed
   yet gets the best answer currently on hand; a fully-elapsed, batch-processed window gets
   the exact one.

A good property of this pipeline worth calling out explicitly: **the data rate shrinks by
orders of magnitude at every stage.**

![Record rate shrinks by roughly 5 orders of magnitude down the pipeline](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-rate-funnel.png)

Raw ingest might be a million events/sec; after per-partition pre-aggregation you're down
to tens of thousands of *distinct-item count updates*/sec; after the final reduce you're
down to hundreds of rows; the thing actually served to clients is a handful of rows per
window. Every downstream component does dramatically less work than the one before it,
which is exactly why it's safe to make the downstream components (MapReduce, the serving
store) simpler and less horizontally scaled than the ingest tier.

## Two operational pitfalls worth knowing by name

Both of these are easy to miss in a design that otherwise looks correct on the whiteboard,
and both are exactly the kind of thing a staff-level interviewer will probe for.

**The pre-computation cron can turn a rare failure into a thundering herd.** Serving
top-k from a cache that's populated by a periodic job (a cron that runs the expensive
query once an hour and writes the result to Redis) is a good design - reads are
consistently fast, unlike a plain read-through cache where a miss means one unlucky user
eats the full multi-second query cost ("cache-hit Russian roulette"). But it has a sharp
edge: if that cron job fails or falls behind, *every single read* that finds a missing or
expired cache entry falls through to the database **at the same time**. A job that
normally issues one expensive query an hour just turned into thousands or millions of
identical expensive queries landing on the database simultaneously - right when the
database was already having a bad enough day to make the cron fail in the first place. The
fix: never let a cache miss fall through to a live recompute here. Instead, set a long TTL
(hours to days) and always serve the **most recent successfully computed window** rather
than nothing - a stale-but-correct answer from an hour ago beats a self-inflicted outage.
This does mean consciously violating your freshness SLA during an incident, which is the
right trade: a slightly stale top-k list is a much better failure mode than a cascading
database overload.

**Stream processors need spare capacity to ever recover from an outage.** If your
consumers are sized to exactly match steady-state throughput (say, they can just barely
keep up with 700K events/sec as they arrive), then the moment they fall behind - a
deploy, a crash, a network blip - they can **never catch up**, because every second of
wall-clock time only buys them one second of processing capacity to work through both the
backlog and the new arrivals. Falling behind at that point is permanent unless you scale
up. The two-part fix: (1) provision headroom - if steady state needs `N` workers, running
`1.5N` to `2N` means a chunk of capacity is always free to chew through backlog once
you're behind, and the deeper the backlog, the longer recovery takes but it does
eventually finish; (2) **checkpoint** progress periodically (Flink and Spark both do this
natively, to S3/HDFS, every few minutes) so that on restart you replay from the last
checkpoint, not from the start of the whole window - bounding both how much reprocessing a
failure costs and how much of a head start you need to recover from it.

## MapReduce, mechanically, with a worked example

MapReduce splits a big job into three framework-managed phases:

- **map(split) -> (key, value) pairs.** Runs once per input split (a block of the input
  file, typically scheduled on a machine that already has that block locally - "move the
  computation to the data," not the other way around). Fully parallel; mappers don't talk
  to each other.
- **shuffle + sort** (the framework does this, you don't write it): every emitted `(key,
  value)` is routed to the reducer responsible for that key (by default, `hash(key) %
  numReducers`) and grouped, so each reducer sees `(key, [all values for that key])`.
- **reduce(key, values) -> output.** Runs once per key, fully parallel across keys.

Two jobs, chained, solve this exactly the way we already reasoned about above:

**Job 1 - Frequency Count** (the canonical "word count" pattern): `map` emits `(item, 1)`
for every raw event; `reduce` sums the values per key into the exact total count.

**Job 2 - Top-K** (Hadoop's "Top K" pattern, and *the same idea as the partitioned-processor
merge from earlier*, just expressed as a MapReduce job): each `map` task computes the
**local** top-k over its own input split only, and emits all of them under one constant key
so they all land on a **single** reducer; that one `reduce` call merges every mapper's
local top-k into the global top-k. (A `combiner` - a mini-reducer that runs right after
`map`, on the same machine, before data crosses the network - is the standard way to shrink
shuffle volume further; the partition processor in the architecture above is doing exactly
a combiner's job.)

![Frequency Count MapReduce, worked end to end](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/9-5-mapreduce-flow.png)

A from-scratch simulation (same mechanics, one machine instead of a cluster), run and
verified:

```python
import heapq
from collections import defaultdict

def frequency_count_mapreduce(splits):
    mapped = [(item, 1) for split in splits for item in split]         # map
    grouped = defaultdict(list)
    for k, v in mapped:
        grouped[k].append(v)                                          # shuffle + sort
    return {k: sum(vs) for k, vs in grouped.items()}                   # reduce

def top_k_mapreduce(count_splits, k):
    mapped = []
    for split in count_splits:                                        # map (per file)
        heap = []
        for item, cnt in split:
            if len(heap) < k:
                heapq.heappush(heap, (cnt, item))
            elif cnt > heap[0][0]:
                heapq.heapreplace(heap, (cnt, item))
        for cnt, item in sorted(heap, reverse=True):
            mapped.append(("ALL", (item, cnt)))                       # constant key
    grouped = defaultdict(list)
    for key, v in mapped:
        grouped[key].append(v)                                        # shuffle + sort
    return sorted(grouped["ALL"], key=lambda iv: -iv[1])[:k]           # reduce (one task)
```

```
splits = [ "AABAC", "BCCDA", "AABBCE" ]     # 3 raw-event input splits

Job 1 - frequency counts: {'A': 6, 'B': 4, 'C': 4, 'D': 1, 'E': 1}
ground truth counts     : {'A': 6, 'B': 4, 'C': 4, 'D': 1, 'E': 1}     # exact match

job-1 output split into 3 new files: [[('A',6),('B',4)], [('C',4),('D',1)], [('E',1)]]

Job 2 - global top-2: [('A', 6), ('B', 4)]
ground truth top-2  : [('A', 6), ('B', 4)]                             # exact match
```

Operationally: map and reduce tasks are stateless given their input, so a failed task is
just re-run elsewhere (fault tolerance) - the cluster scheduler (historically JobTracker /
TaskTracker, now YARN) can even speculatively re-run a slow "straggler" task on another
node and use whichever finishes first. Shuffle (the all-to-all network transfer between map
and reduce) is almost always the actual bottleneck, which is exactly why the local
pre-aggregation / combiner step matters so much - it's a network-cost optimization at least
as much as a compute one.

## Principles of data aggregation

Everything in this design is an instance of a few general rules worth having explicitly:

1. **Aggregate as close to the source as possible.** Every hop you push a partial
   aggregate through instead of raw events is a hop that does less work and moves less
   data. Client-side batching at the gateway, the partition processor's local
   pre-aggregation, and a MapReduce combiner are the same idea applied three times.
2. **Only associative, commutative operations parallelize safely.** If combining two
   partial results in either order, or in any grouping, gives the same answer, you can
   compute partials anywhere and combine them in any order later - this is what lets you
   run map/reduce tasks in parallel with no coordination between them at all. Formally:
   the operation plus an identity element needs to form a **monoid**. `SUM`, `COUNT`,
   `MAX`, `MIN`, a Count-Min Sketch's cell-wise addition, and a HyperLogLog's bitwise-OR
   merge are all monoids - you can freely shard them, aggregate each shard independently,
   and combine the partials, in any order, and get the exact (or, for sketches,
   correctly-bounded) right answer. **Raw top-k is not** a monoid over "already reduced to
   just the winners" data, because the losing items' counts are gone - which is the exact
   mechanism behind the per-minute-merge counterexample above. (Notice this is also why
   distinct-count via HyperLogLog *does* merge cleanly across shards or time windows, while
   top-k does not - same family of problem, different algebra.)
3. **Aggregation is lossy on purpose - decide what you're allowed to lose.** A sketch
   discards precision in exchange for a bounded, provable error and O(1) memory. A per-
   minute top-k list discards everything outside the top-k, unconditionally. Neither
   choice is wrong - but you have to make it consciously, because the moment you need
   information that was already discarded, it is not recoverable from the aggregate, only
   from the raw source (if you kept it).
4. **Aggregation must be idempotent under retries.** Kafka and most real pipelines give
   at-least-once delivery, not exactly-once. If `add(item)` runs twice for the same event
   because of a retry, your counts are now wrong. Fix with a dedup key (event id) tracked
   per consumer, or windowed dedup, so replays don't double count.
5. **Composable aggregates roll up hierarchically; non-composable ones don't.** `hour_sum =
   sum(60 minute_sums)` is free - sums are a monoid. `hour_top_k != merge(60
   minute_top_k_lists)` - proven above. Know which kind of aggregate you're building before
   you decide whether storing only the rolled-up form is safe.

## This is the Lambda Architecture - and it has a real drawback

What we've built - a **speed layer** producing fast approximate results, a **batch layer**
producing slow exact results over the immutable raw log, and a **serving layer** that
merges the two at query time - is a named pattern: the **Lambda Architecture**, coined by
Nathan Marz (creator of Apache Storm) around 2011. Marz's framing was explicitly "how to
beat the CAP theorem": rather than trying to build one system that's simultaneously fast,
correct under partitions, and available, run two systems with different trade-offs and
reconcile their outputs at read time, so no single component has to be everything at once.

The drawback, and it's a real one: **you now have two codebases computing "the same"
logic** - a streaming implementation (fast processor / CMS + heap) and a batch
implementation (MapReduce jobs) - that must, by construction, agree once the batch result
lands. In practice they drift: subtly different bucketing, a bug fixed in one path and not
the other, different handling of late or duplicate events. You're also running and
operating two entirely different systems (a stream processor and a Kafka cluster, *plus* a
Hadoop/Spark batch cluster and a distributed file system), which is real infrastructure and
on-call surface area. This complexity is the standard interview follow-up: "what's the
drawback of this design?" The honest answer is "it's a Lambda Architecture, and the cost is
running two pipelines that have to agree."

### A cleaner alternative: Spark on Kafka (Kappa Architecture)

The fix that avoids dual codebases: **Apache Spark Structured Streaming reading directly
from Kafka**, using **one** codebase for both live and historical processing. This is
sometimes called the **Kappa Architecture** - there is no separate batch layer; you get
exact, complete results by *reprocessing the same stream through the same code*, not by
running a second system.

Mechanically: Spark treats the Kafka topic as an unbounded table and lets you write a
normal windowed aggregation - conceptually `SELECT item, count(*) FROM events GROUP BY
item, window(event_time, "1 hour", "1 minute")`. Micro-batches (or, in continuous mode,
a low-latency streaming execution) process new Kafka offsets incrementally and update
running per-window state. Two mechanisms make this both correct and bounded:

- **Watermarking** tells Spark how late an event is allowed to arrive and still be counted
  into its window (say, 10 minutes late is still accepted); this bounds how much state
  Spark has to keep around for "still open" windows, instead of keeping every window open
  forever waiting for stragglers.
- **Checkpointing** durably persists the query's progress (Kafka offsets consumed, and
  aggregation state) to storage like S3/HDFS, so a Spark job that crashes and restarts
  resumes exactly where it left off - this is what gives you exactly-once *semantics* for
  the aggregation despite Kafka only guaranteeing at-least-once delivery underneath.

Because it's one system, "give me the exact top-k for last month" and "give me the live
top-k for the last minute" run the *same aggregation logic* - one against Kafka's retained
log (or an S3 archive of it, read as a batch source through the same query), one against
the live stream. No second pipeline to keep in sync, no divergence to debug. The trade-off:
you need a log retention (or archive) policy long enough to support the reprocessing you
actually need, and very-long-history reprocessing through a streaming engine can still be
slower or costlier than a purpose-built batch job over columnar storage - Lambda's batch
layer isn't *wrong*, it's a genuine latency/complexity trade against Kappa's single-system
simplicity.

## Should you reach for a specialized time-series or OLAP database?

Everything above is buildable with general-purpose pieces: Kafka, Postgres, Redis, a
stream processor, MapReduce/Spark. There's a family of purpose-built databases that also
target exactly this kind of workload, worth knowing about but using carefully in an
interview:

- **TimescaleDB** - a Postgres extension. Tables become "hypertables" optimized for
  time-ordered data, and "continuous aggregates" do automatically, incrementally, what the
  rollup-on-write section above described by hand - materialized, indexed rollups that stay
  up to date as new rows land. Because it's still Postgres underneath, it inherits
  relatively little new risk.
- **Prometheus / InfluxDB** - built for a different shape of problem: many independent
  time series, each queried and graphed on its own (CPU usage over time, request latency
  over time). They're excellent at that, and bad at top-k, because top-k needs to sort
  *across* series - exactly the operation these databases don't help with. You'd end up
  querying per-series and sorting externally anyway, which defeats the purpose of using
  them.
- **Druid / Pinot / ClickHouse** - real-time OLAP engines that bake in materialized views
  and streaming aggregation internally, similar in spirit to what Flink is doing above but
  packaged as a queryable database. Powerful, but they turn a lot of the interesting design
  work into "a configuration option," which is a double-edged sword in an interview - there
  isn't much left to design, discuss, or defend.

The general interview risk with naming any of these: your interviewer either doesn't know
the technology (and your specific knowledge becomes hard to leverage), or does know it and
will ask you to explain its internals - at which point you're back to explaining
pre-aggregation, indexing, and caching, just with unfamiliar vocabulary layered on top.
Unless you've genuinely operated one of these in production, it's usually a better
investment to deeply understand the underlying patterns (data flow, aggregation, indexing,
caching - everything above) than to memorize a specialized product name to drop. The
patterns transfer to any of these tools instantly; a product name without the underlying
mechanism does not.

## Follow-up questions

**The API gateway does auth, TLS termination, rate limiting, *and* event logging - what if
it can't afford the CPU/memory for all of that?**
Offload logging entirely: a separate lightweight process (a sidecar or local daemon, the
same pattern as Fluentd/Filebeat) tails the gateway's local request logs and asynchronously
ships them to Kafka. The gateway's request-handling hot path never touches the shipping
logic. Push further upstream too - batch events client-side before they're even sent, so
the gateway sees fewer, larger requests instead of one per view.

**Alternatives to Count-Min Sketch?**
A different family - counter-based (not hash-array-based) heavy-hitter algorithms, which
track a small, bounded number of *actual candidate keys* directly instead of an anonymous
grid of counters:
- **Lossy Counting** - process the stream in buckets of size `1/ε`; track `(item,
  estimated count, max possible error Δ)`; periodically prune entries whose `count + Δ` is
  too small to matter. Deterministic, guarantees error `<= ε x N`, but memory is only
  bounded in the typical case, not the absolute worst case.
- **Space-Saving** - a fixed-size table of `m` counters. A new, untracked item evicts the
  *current minimum* counter, taking over its slot with `count = evicted_count + 1` (which
  doubles as that item's error bound). Very memory-efficient and simple; this or a close
  relative is what a lot of production "top-k" libraries (e.g. `stream-lib`) actually
  implement.
- **Sticky Sampling** - probabilistically sample the stream with a sampling rate that
  decreases over time, keep exact counts only for sampled items. Similar guarantees to
  Lossy Counting, simpler to reason about, slightly more memory.

The practical difference from CMS: these track a bounded list of *real* candidate items
directly, so they hand you the top-k list without a separate heap. CMS has fixed memory
regardless of key cardinality and needs no per-key bookkeeping structure at all, but it
only answers "what's this item's count" - it needs the companion heap to know which items
to even ask about.

**What is a "sketch algorithm," as a category?**
A **sketch** is any probabilistic, sub-linear-space data structure that trades a small,
mathematically bounded error for large savings in memory and/or time, used when exact
bookkeeping is infeasible at scale. The family, beyond Count-Min Sketch: **Bloom filter**
(set membership - false positives possible, false negatives never), **HyperLogLog**
(cardinality / distinct-count estimation - billions of distinct items in a couple of KB),
**t-digest / quantile sketches** (approximate percentiles). Shared properties: fixed memory
independent of input size, usually mergeable across shards or time windows (they're
monoids - see the aggregation principles above), and accuracy is a tunable knob (more
memory buys a tighter error bound).

**How big is K, really?**
Almost always small in absolute terms - 10, 25, 50, maybe up to a few hundred for an
internal dashboard. It matters architecturally because it bounds heap operations at
`O(log k)` and bounds how much data crosses the network or gets stored per window
(`local-top-k` payloads, the merged result, everything). The entire "local top-k + exact
merge" trick from the partitioning section, and the "CMS + heap" trick, both work *because*
K is a small constant that doesn't grow with the number of unique items `N` - if K had to
scale with N, none of this would help.

**What's the drawback of the full architecture?**
Covered above: it's a Lambda Architecture, and the cost is operating and keeping in sync
two independent pipelines (stream + batch) that are each computing a version of the same
answer.

## How this maps onto the real Bloomberg question

10.4 asks you to design exactly this for the Bloomberg Terminal's "most popular news"
panel. Independent candidate reports of this exact round give real numbers worth anchoring
to: it's been described both as **"Top 100 News"** (so `k` around 100 - comfortably inside
the "k is a small constant" regime from the cheat sheet) and as **"top K news - most
popular news in the past 8 hours"** (a tumbling- or sliding-window question over a
multi-hour range, not a single-minute one - meaning the rollup-vs-raw-data distinction
above is directly load-bearing, not a hypothetical). The reported interview follow-ups line
up one-to-one with sections above:

- *"How do you aggregate view counts when the services aren't directly available?"* - the
  event-listener / API-gateway logging step.
- *"Ensure aggregation isn't limited to one time window"* - the bounded-window vs.
  unbounded-stream distinction, and why you can't just merge per-minute lists for a longer
  range.
- *"Snapshots stored in a key-value store keep growing row-wise - how do you handle
  retention?"* - the raw-data-on-disk section: you need a retention/rollup policy (archive
  or discard raw events past some age) precisely because composable aggregates can be
  rolled up and kept forever cheaply, while the raw log that non-composable aggregates
  (top-k) depend on cannot be discarded without losing the ability to recompute for that
  range.
- *"What if your servers fail?"* - replication and the fact that Kafka retains events for
  reprocessing; a crashed fast processor loses only its in-memory sketch for the current
  open window, recoverable by replaying that window from Kafka; a crashed batch job just
  reruns (MapReduce/Spark tasks are stateless and idempotent given their input).

10.4 will specialize the item id to a news-story id, add the Terminal's selectable time
interval as the `topK` window parameter directly, and go deeper on exactly those three
follow-ups.

## Cheat sheet

```
SINGLE HOST     hashmap counts + min-heap(size k)          O(n + u log k)

SCALE OUT       partition by hash(key) -> local top-k per shard -> k-way merge
                correct because: an item's count lives entirely in one shard,
                so "not in local top-k" implies "not in global top-k" either.

WINDOWS         tumbling = fixed, non-overlapping buckets. sliding = fixed width,
                re-evaluated every slide interval, overlapping. Default to tumbling.

STREAMING       per-window (e.g. per-minute) local top-k, flushed to storage.
                Top-k of a LONGER window != merge of shorter windows' top-k lists.
                (top-k is not a monoid over already-reduced data - info is gone.)
                Exact long-window answers need the raw counts for that whole range.
                FIX: roll up COUNTS (a monoid), never roll up top-k lists.
                  tumbling: fan a write out to every grain (minute/hour/day) at once,
                            each grain independently indexed on (bucket, count)
                  sliding:  add the incoming bucket, subtract the bucket that fell out
                            (verified: 0 mismatches vs. brute force over 200 steps)

RAW STORAGE     replication (durability) + rebalancing (consistent hashing) +
                hot-partition mitigation (salting / dedicated capacity / edge pre-agg)

PITFALLS        pre-agg cron fails -> every cache miss hits DB at once (thundering herd)
                  fix: long TTL, always serve last-good window, never fall through live
                consumers sized to exactly steady-state can never recover from a backlog
                  fix: run with headroom (1.5-2x) + checkpoint progress periodically

APPROXIMATE     Count-Min Sketch: d hash fns x w counters
                w = ceil(e/epsilon)   d = ceil(ln(1/delta))   e = Euler's number
                query = min over d cells -> one-sided error, never undercounts
                pair with a size-k heap (lazy deletion) -> streaming top-k tracker
                alternatives: Lossy Counting, Space-Saving, Sticky Sampling

ARCHITECTURE    gateway (batch+flush events) -> Kafka (partitioned, replicated)
                  -> speed layer: CMS+heap, seconds, approximate
                  -> batch layer: partition -> pre-aggregate -> HDFS/S3
                                  -> MapReduce (Frequency Count, then Top-K), exact
                  -> serving layer: fast result now, exact result once batch lands
                data rate shrinks by orders of magnitude at every stage
                named pattern: LAMBDA ARCHITECTURE (Marz, 2011) - drawback: two
                codebases to keep in sync. Cleaner alternative: Spark on Kafka,
                one codebase for both (KAPPA ARCHITECTURE).

MAPREDUCE       map -> shuffle+sort (grouped by key) -> reduce
                combiner = local mini-reduce before shuffle, cuts network cost
                Top-K pattern: local top-k per mapper, all to ONE reducer, merge

K               small constant (10s-100s), independent of N - that's WHY every
                trick above (local top-k, CMS+heap) stays cheap as N grows
```
