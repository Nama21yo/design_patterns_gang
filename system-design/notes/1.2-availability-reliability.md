1.1's taxonomy listed "availability" as a single line item. It isn't - it's a cluster of
five related but genuinely distinct properties that get casually used as synonyms in
conversation and shouldn't be. This note pulls them apart, with real arithmetic behind the
numbers that get thrown around ("five nines") rather than just quoting them.

## Availability: the fraction of time the system responds at all

**Availability** is the fraction of time a system is up and responding - conventionally
expressed as a percentage of "nines." The arithmetic behind the standard table, computed
rather than just quoted:

```python
import datetime

SECONDS_PER_YEAR = 365 * 24 * 3600

for nines, availability in [
    ("99% ('two nines')", 0.99),
    ("99.9% ('three nines')", 0.999),
    ("99.95%", 0.9995),
    ("99.99% ('four nines')", 0.9999),
    ("99.999% ('five nines')", 0.99999),
]:
    downtime_seconds = SECONDS_PER_YEAR * (1 - availability)
    downtime = datetime.timedelta(seconds=round(downtime_seconds))
    print(f"{nines:28s} -> {downtime} downtime/year allowed")
```

```
99% ('two nines')            -> 3 days, 15:36:00 downtime/year allowed
99.9% ('three nines')        -> 8:45:36 downtime/year allowed
99.95%                       -> 4:22:48 downtime/year allowed
99.99% ('four nines')        -> 0:52:34 downtime/year allowed
99.999% ('five nines')       -> 0:05:15 downtime/year allowed
```

![Computed: each additional 9 cuts allowed downtime by roughly 10x](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-2-nines-table.png)

Each additional nine is roughly a **10x** reduction in allowed downtime - going from
"three nines" to "five nines" means the gap between "under 9 hours of downtime, total, for
the entire year" and "under 6 minutes." This is why chasing an extra nine gets
disproportionately expensive: four-nines-to-five-nines isn't 10% more engineering effort,
it's an entirely different operational discipline (automated failover, multi-region,
extensive chaos testing) to close a gap that's now measured in single-digit minutes per
year.

### Why redundancy helps - and dependency chains hurt

Whether adding a component *raises* or *lowers* overall availability depends entirely on
whether it's in **series** (a dependency - everything in the chain must be up) or
**parallel** (a redundancy - only one needs to be up):

```python
def series_availability(*components):
    result = 1.0
    for a in components:
        result *= a
    return result

def parallel_availability(*components):
    prob_all_down = 1.0
    for a in components:
        prob_all_down *= (1 - a)
    return 1 - prob_all_down


single = 0.999

two_in_series = series_availability(single, single)
print(f"two components in SERIES: {two_in_series:.4%}")   # a load balancer AND a database, both must be up

two_in_parallel = parallel_availability(single, single)
print(f"two components in PARALLEL: {two_in_parallel:.4%}")   # two replicas, either can serve

three_in_parallel = parallel_availability(single, single, single)
print(f"three components in PARALLEL: {three_in_parallel:.6%}")
```

```
two components in SERIES: 99.8001%
two components in PARALLEL: 99.9999%
three components in PARALLEL: 100.000000%
```

![Series multiplies probabilities (gets worse); parallel redundancy raises them (gets better)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-2-series-vs-parallel.png)

Two components each at 99.9%, chained in series (a load balancer **and** a database, both
of which must be up for a request to succeed) drops *combined* availability to 99.8001% -
worse than either alone, because the whole chain is only as available as its weakest, and
every additional dependency multiplies in another chance of failure. The exact same two
components, used as **redundant** replicas instead (either one can serve the request).
Raises combined availability to 99.9999% - adding a THIRD pushes it past 99.9999%, rounding
to effectively 100% at this precision. This is the entire mathematical justification behind
3.5's replication and 2.5's load balancing: redundancy in parallel is a net win; every new
dependency in series is a net cost, which is also exactly why 2.6's bulkhead/circuit-breaker
patterns exist - to stop one dependency's failure from taking down everything chained after
it.

## Reliability: whether the answer is actually correct

**Reliability** - the probability a system performs **correctly** over a given period - is
a genuinely different axis from availability, and conflating them is a real mistake.
Availability asks "did I get a response?" Reliability asks "was the response *right*?" A
system can score high on one and low on the other:

```python
import random

random.seed(42)

def simulate(name, p_up, p_correct_given_up, n=100_000):
    responded = correct = 0
    for _ in range(n):
        if random.random() < p_up:
            responded += 1
            if random.random() < p_correct_given_up:
                correct += 1
    print(f"{name}:")
    print(f"  availability: {responded/n:.1%}  reliability: {correct/responded:.1%}  "
         f"overall correct-answer rate: {correct/n:.1%}")

simulate("Service A (always responds, but 15% of responses are silently wrong)",
        p_up=1.0, p_correct_given_up=0.85)
simulate("Service B (down 10% of the time, but every response it gives is correct)",
        p_up=0.90, p_correct_given_up=1.0)
```

```
Service A (always responds, but 15% of responses are silently wrong):
  availability: 100.0%  reliability: 84.9%  overall correct-answer rate: 84.9%
Service B (down 10% of the time, but every response it gives is correct):
  availability: 90.0%  reliability: 100.0%  overall correct-answer rate: 90.0%
```

![Measured: availability and reliability are orthogonal - neither implies the other](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-2-availability-vs-reliability.png)

Service A looks perfect by the availability metric (100% uptime) while silently returning
wrong answers 15% of the time - a **worse** real user experience than Service B, which is
honestly down 10% of the time but never lies when it does respond. A dashboard that only
tracks uptime would completely miss Service A's problem; this is exactly why correctness
checks (checksums, data validation, canary queries) have to be measured as their own
signal, separate from uptime monitoring.

## Fault tolerance, resilience, and durability

![Fault tolerance is one tool resilience uses; durability is an orthogonal axis entirely](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-2-resilience-spectrum.png)

- **Fault tolerance** - a *specific mechanism*: the system keeps working correctly despite
  one or more components failing, almost always via redundancy (the parallel-availability
  math above, made concrete).
- **Resilience** - the *broader* property: the ability to detect a failure, contain its
  blast radius, and recover from it - not just "survive one component dying" but the whole
  lifecycle around failure. Fault tolerance is one tool resilience uses; 2.6's circuit
  breakers, bulkheads, and graceful degradation under load shedding are others, and so is
  the operational discipline of actually noticing a failure happened at all (2.4's
  timeouts, and the whole of Part 6's observability material).
- **Durability** - a genuinely separate axis from both of the above: once a write is
  **acknowledged**, can it ever be lost? This has nothing to do with whether the system is
  currently *up* - 3.1's write-ahead log and 2.7's backup/point-in-time-recovery material
  are both purely about durability, and a system can be perfectly durable while being down
  right now (the data is safe on disk, just not currently servable), or perfectly available
  while being entirely non-durable by design (an in-memory cache, 4.1-4.3, that's meant to
  lose everything on restart - that's a correct trade-off for a cache, and a catastrophic
  one for a payments ledger).
