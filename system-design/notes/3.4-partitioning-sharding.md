title: "3.4 Partitioning / sharding"
---

Eventually one database instance runs out of room - too much data to fit, too many
writes for one machine to absorb, or both. This note is about what you do next: the two
scaling directions, the vocabulary for splitting data up, and the mechanics (hashing,
rebalancing, routing, indexing) that make splitting it up actually work in production.

## Two ways to scale

![Vertical vs. horizontal scaling](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-vertical-vs-horizontal-scaling.png)

**Vertical scaling** - buy a bigger machine: more CPU, more RAM, faster disks. Simple,
requires no application changes, and it's where you should start. Its ceiling is real,
though: at some point there is no bigger machine to buy, and even before that ceiling, cost
stops scaling linearly - the biggest instances cost disproportionately more per unit of
capacity than a modest one.

**Horizontal scaling** - use more machines instead of a bigger one. No hard ceiling (add
another box), but it costs you: the data now lives on more than one machine, and something
has to decide which machine owns which piece of it, route requests accordingly, and keep
things correct when a machine joins, leaves, or dies. Everything below is about paying that
cost well.

Horizontal scaling for reads specifically has its own first move, cheaper than splitting
the data at all: **read replicas**. Point read traffic at replicas so the primary is free
to spend all its capacity on writes (Part 3.5 covers replication mechanics - sync vs.
async, replication lag, failover - in depth). The important thing to fix in vocabulary
right now: a read replica holds a **full copy** of the data, not a piece of it. That
distinction is the whole point of the next section.

## Sharding vs. partitioning - and how they relate to replication

These three terms get used loosely and interchangeably in casual conversation, which
causes real confusion in an interview. Precisely:

- **Partitioning** is the general technique: splitting a dataset into smaller pieces
  (partitions) by some rule. This can happen **within a single database instance** - most
  relational databases support native table partitioning, where one physical server still
  holds everything, just organized into separate physical segments internally (demonstrated
  below).
- **Sharding** is the specific case of partitioning where each partition lives on a
  **separate machine**. Every shard is a full, independent database instance that owns a
  disjoint slice of the overall dataset. A handy way to keep this straight: **each shard is
  a database, and what's inside it is a partition of the whole.**
- **Replication** is a different axis entirely: making full copies of the same data, not
  slices of it.

![Sharding, partitioning, and read replicas compared](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-sharding-partition-replica.png)

This is the cleanest test for confusing the three in an interview: **if you have multiple
database instances but each one holds a full copy of everything, that's replication (read
replicas), not sharding - no partitioning has happened at all.** Sharding only starts once
each instance holds a genuinely *different* slice of the data. And the two are not
alternatives - a well-built system shards for write/storage scale *and* replicates each
shard for durability and read scale, simultaneously; they solve different problems and
stack on top of each other.

### Partitioning within one instance, proven live

To make "partitioning doesn't require multiple machines" concrete: Postgres supports
native declarative table partitioning. Split a table by date range, insert 1.8M rows
across 6 monthly partitions, then query one month:

```python
import psycopg2

conn = psycopg2.connect(host="localhost", dbname="postgres", user="postgres")
cur = conn.cursor()
cur.execute("""
    CREATE TABLE events (id BIGSERIAL, event_day DATE NOT NULL, payload TEXT)
    PARTITION BY RANGE (event_day)
""")
for m in range(1, 7):
    cur.execute(f"""
        CREATE TABLE events_2026_{m:02d} PARTITION OF events
        FOR VALUES FROM ('2026-{m:02d}-01') TO ('2026-{m+1:02d}-01')
    """)
cur.execute("""
    INSERT INTO events (event_day, payload)
    SELECT date '2026-01-01' + (i % 180), 'payload ' || i
    FROM generate_series(1, 1800000) AS i
""")
conn.commit()

cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) SELECT count(*) FROM events "
           "WHERE event_day BETWEEN '2026-03-01' AND '2026-03-31'")
print("\n".join(r[0] for r in cur.fetchall()))
```

partitions appear anywhere in it. This is **partition pruning**: the planner used the
`WHERE` clause to figure out which single partition could possibly contain matching rows
and skipped the other five entirely (5/6 of the table's rows were never even considered) -
all on one machine, no sharding involved. Sharding is this same pruning idea, just with
each partition promoted to its own physical database.

### Horizontal vs. vertical partitioning

The other axis: what you're splitting *by*.

![Horizontal vs. vertical partitioning](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-horizontal-vs-vertical-partitioning.png)

- **Horizontal partitioning** splits by **row**: every partition has the identical schema,
  just a different subset of rows (users A-M on one partition, N-Z on another). This is
  what people usually mean by "sharding" by default, and it's the right move when the
  table is enormous but every row is accessed the same way.
- **Vertical partitioning** splits by **column** (or splits a table into several related
  tables): frequently-accessed, small columns go one place, rarely-accessed or large
  columns (a bio, a blob, an infrequently-read audit trail) go elsewhere. This shrinks the
  "hot" working set that has to stay in cache/memory, at the cost of a join or a second
  lookup when you do need the cold columns.

The two aren't mutually exclusive - a large system frequently does both: vertically split
a wide table into a hot table and a cold table, then horizontally shard the hot table
because it's still too big for one machine on its own.

## Choosing a partition key: hash vs. range

Once you know you're splitting by row, you need a rule that maps a key to a partition.

![Hash vs. range partitioning](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-hash-vs-range-partitioning.png)

- **Hash partitioning** - `partition = hash(key) % N`. Spreads load evenly (a good hash
  function scatters keys uniformly regardless of their actual distribution), but destroys
  locality: consecutive keys land on unrelated partitions, so a range query ("give me all
  events from March") has to fan out to every partition instead of hitting one.
- **Range partitioning** - each partition owns a contiguous range of key values (exactly
  what the `events` demo above did, by date). Range queries and ordered scans stay cheap
  and local to one or a few partitions. The risk is **hot ranges**: if traffic isn't
  uniform across the key space - the most recent date range in a time-partitioned table,
  the most popular letter range in an alphabetically-partitioned one - one partition can
  take dramatically more load than its neighbors.

Pick hash when you mostly do point lookups and want load spread evenly; pick range when
range scans and time-ordered access are the dominant pattern and you can tolerate (or
actively manage) uneven load across ranges.

## Consistent hashing and virtual nodes

### Where "hash % N" is fine, and where it isn't

`hash(key) % N` routing shows up in two very different places, and it only breaks badly in
one of them.

A **load balancer** in front of a fleet of **stateless** backend servers is the forgiving
case: forward each request by `hash(access_token) % N` so the same user's requests tend to
land on the same server (handy for warm in-process caches), but nothing *requires* that -
any server can correctly handle any request, because no server holds data the others don't
also have access to. When a server goes down, you just decrease `N` and recompute the
modulus; some users get remapped to a different (but equally capable) server, and that's
the whole cost. This is why naive mod-N hashing is the standard, unremarkable choice for
load balancing.

A **stateful backend** - a distributed key-value store or cache where each node actually
*owns* a distinct slice of the data - is the case where the same naive scheme is a real
problem, because remapping a key now means physically moving that key's data, not just
redirecting a stateless request. Concrete, verified example: 6 keys sharded across 3 nodes
by `hash(key) % 3`, then one node is removed:

```python
import hashlib

def h(s):
    return int(hashlib.md5(s.encode()).hexdigest(), 16)

keys = ["user_A", "user_B", "user_C", "user_D", "user_E", "user_F"]

print("6 keys sharded across 3 nodes, naive hash(key) % N:")
before = {}
for k in keys:
    node = h(k) % 3
    before[k] = node
    print(f"  {k}: node {node}")

print("\nnode 2 is removed (N: 3 -> 2), everyone recomputes hash(key) % 2:")
moved = 0
for k in keys:
    node = h(k) % 2
    if before[k] != node:
        moved += 1
    changed = " <- MOVED" if before[k] != node else ""
    print(f"  {k}: node {node}{changed}")

print(f"\n{moved}/{len(keys)} keys changed owner from removing ONE node "
     f"({moved/len(keys):.0%}) - each of those requires transferring that key's actual data.")
```

Half the dataset had to move, just to absorb the loss of one out of three nodes - and this
gets *worse*, not better, as the cluster grows (the chart below shows 80-94% at realistic
cluster sizes). **This is exactly the problem consistent hashing solves**: minimizing data
movement when the node count changes, specifically for the stateful case where a remap is
an expensive data transfer, not a free redirect.

### The mechanism

Plain `hash(key) % N` has a brutal failure mode: change `N` - add or remove one node - and
almost every key's assigned partition changes, because the modulus itself changed.
Measured, on 200,000 keys, going from `N` to `N+1` nodes:

![Naive mod-N vs. consistent hashing: fraction of keys remapped](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-rebalancing-cost.png)

Naive `hash(key) % N` moves **80-94% of all keys** just to add a single node - meaning
almost the entire dataset gets shuffled between machines for a one-node capacity bump.
**Consistent hashing** fixes this. Instead of a modulus, hash both the keys *and* the nodes
onto the same fixed circular space (a "ring"), and assign each key to the next node found
walking clockwise from its position:

![Consistent hashing ring](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-consistent-hash-ring.png)

Adding a node means placing one new point on the ring - it only takes over the keys between
itself and the previous node in that one arc; every other key's owner is completely
unaffected, because nothing about their position on the ring or the other nodes' positions
changed. Measured in the same chart above: consistent hashing moves only **5-18%** of keys
for the same node addition, and the theoretical ideal (moving *exactly* `1/(N+1)` of the
keys - the absolute minimum any scheme could achieve, since that's the new node's fair
share) is close to what's measured.

One more piece is necessary to make this work well in practice: **virtual nodes**. Placing
each *physical* machine at a single random point on the ring means an unlucky placement can
give one machine a much larger arc (and therefore much more load) than another - so instead,
each physical node is hashed onto the ring at many points (100+ virtual nodes is typical),
scattering its share of the keyspace into many small, evenly-distributed arcs instead of one
big one. This is exactly what the diagram above shows (each color/node owns several
scattered points, not one), and it's also the standard fix for the **hot partition** problem
from 9.5: an overloaded key or a skewed range hashes onto many small arcs instead of
overwhelming one, and if a specific hot key is still a problem even then, the usual next move
is salting it into several sub-keys spread across the ring.

### A concrete walkthrough: slots 0-15

The idea is easiest to see on a small, fixed ring - 16 slots instead of a real hash's full
range. Place 3 nodes on it by hashing their names mod 16, then hash 5 keys the same way and
give each one to the next node found walking **clockwise** (the next-higher slot, wrapping
past 15 back to 0):

![A 0-15 ring: node placement and key ownership](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-concrete-ring-0-15.png)

Verified placement: `node-B` lands at slot 1, `node-C` at slot 9, `node-A` at slot 12. That
gives node-C the largest arc (slots 2-9, 8 slots) and node-A the smallest (slots 10-12, 3
slots) - already a live example of the uneven-arc problem virtual nodes exist to fix (a
single unlucky hash placement, exactly as described above).

Now watch what happens to those same 5 keys on scale-up (adding a 4th node) and scale-down
(removing one), side by side with the original:

![Scaling the ring up and down: only the adjacent arc moves](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-concrete-ring-scale.png)

- **Scale up** - `node-D` hashes to slot 8, landing just counter-clockwise of `node-C`
  (slot 9). It claims the arc immediately behind it (slots 2-8) - everything `node-C`
  used to own except its own immediate slot. Every key in that reclaimed arc (`order_1`,
  `order_2`, `order_3`, `order_5` in the verified run) moves to `node-D`; `order_4`, already
  owned by `node-B`, is completely unaffected - `node-B`'s arc never changed.
- **Scale down** - removing `node-B` deletes its point on the ring entirely. Its former arc
  (slots 13-15, 0-1) is inherited by whichever node is now the next one clockwise -
  `node-C` (slot 9), since `node-A` (slot 12) sits between them isn't reached until slot 10.
  Only the keys that were actually on `node-B` (`order_4`) move; `node-A` and `node-C`'s own
  keys are untouched.

The pattern in both directions is the same one the earlier measured chart showed at scale:
**a ring change only disturbs the one arc adjacent to it** - never a global reshuffle.

## Rebalancing strategies

Consistent hashing is the mechanism; rebalancing is the operational process around it:

- **Add a node**: it claims its virtual-node arcs on the ring; only the keys in those arcs
  need to move, streamed from their previous owner(s) while the new node is brought online.
- **Remove a node** (planned maintenance or a failure): its arcs get redistributed among
  the ring's neighbors; if it failed rather than being drained gracefully, this relies on
  each shard already being replicated (Part 3.5) so a replica can be promoted immediately
  while the redistribution catches up.
- **Throttle the migration**: moving data at full speed can saturate network and disk I/O
  and degrade the live system it's supposedly helping scale - production rebalancers move
  data in controlled, rate-limited chunks and continuously re-check ring health as they go.
- **Avoid rebalancing storms**: react to a genuinely full/overloaded node, not to transient
  spikes - a rebalance triggered too eagerly, undone, then triggered again wastes exactly
  the I/O and network budget you're trying to protect.

### Implementation: two sorted arrays + binary search

A real ring needs an efficient answer to "given this key's hash, what's the next node
clockwise?" - checking every node one at a time would be O(number of virtual nodes) per
lookup. The standard trick: keep the ring as **two parallel sorted arrays** - one of hash
positions, one of the owning node at each position - and binary-search the positions array
for the insertion point, which is exactly "the next position clockwise":

```python
import bisect
import hashlib


class ConsistentHashRing:
    """Two parallel sorted arrays: ring_positions (sorted hash positions)
    and ring_owners (which node owns each position). Lookup = binary search
    for the next position clockwise from a key's hash."""

    def __init__(self, ring_size=2**32, vnodes_per_node=100):
        self.ring_size = ring_size
        self.vnodes_per_node = vnodes_per_node
        self.ring_positions = []   # sorted array of hashed positions
        self.ring_owners = []      # parallel array: owner node at each position

    def _hash(self, s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16) % self.ring_size

    def add_node(self, node):
        for v in range(self.vnodes_per_node):
            pos = self._hash(f"{node}#{v}")
            i = bisect.bisect_left(self.ring_positions, pos)
            if i < len(self.ring_positions) and self.ring_positions[i] == pos:
                continue  # extremely rare hash collision, skip
            self.ring_positions.insert(i, pos)
            self.ring_owners.insert(i, node)

    def remove_node(self, node):
        kept_positions, kept_owners = [], []
        for p, o in zip(self.ring_positions, self.ring_owners):
            if o != node:
                kept_positions.append(p)
                kept_owners.append(o)
        self.ring_positions = kept_positions
        self.ring_owners = kept_owners

    def get_owner(self, key):
        pos = self._hash(key)
        i = bisect.bisect_left(self.ring_positions, pos)
        if i == len(self.ring_positions):
            i = 0   # wrap around past the highest position back to slot 0
        return self.ring_owners[i]


ring = ConsistentHashRing()
for node in ("node-A", "node-B", "node-C"):
    ring.add_node(node)

keys = [f"session_{i}" for i in range(10)]
first_pass = [ring.get_owner(k) for k in keys]
second_pass = [ring.get_owner(k) for k in keys]
print("lookups are deterministic:", first_pass == second_pass)
print("sample ownership:")
for k, owner in zip(keys[:5], first_pass[:5]):
    print(f"  {k} -> {owner}")

# scale test: 50,000 keys, how many move on add/remove?
big_ring = ConsistentHashRing()
for node in ("node-A", "node-B", "node-C"):
    big_ring.add_node(node)

test_keys = [f"key_{i}" for i in range(50_000)]
before = {k: big_ring.get_owner(k) for k in test_keys}

big_ring.add_node("node-D")
after_add = {k: big_ring.get_owner(k) for k in test_keys}
moved_on_add = sum(1 for k in test_keys if before[k] != after_add[k])
print(f"\nadding node-D (3 -> 4 nodes): {moved_on_add}/{len(test_keys)} keys moved "
     f"({moved_on_add/len(test_keys):.1%}, ideal ~= 1/4 = 25.0%)")

big_ring.remove_node("node-D")
after_remove = {k: big_ring.get_owner(k) for k in test_keys}
moved_on_remove = sum(1 for k in test_keys if after_add[k] != after_remove[k])
print(f"removing node-D (4 -> 3 nodes): {moved_on_remove}/{len(test_keys)} keys moved "
     f"({moved_on_remove/len(test_keys):.1%})")
print(f"back to original owners after add+remove: "
     f"{sum(1 for k in test_keys if before[k] == after_remove[k])}/{len(test_keys)}")
```

  session_0 -> node-C
  session_1 -> node-C
  session_2 -> node-A
  session_3 -> node-B
  session_4 -> node-C

Both `add_node` and `remove_node` are `O(log ring_size)` per virtual node via `bisect`
(`O(V log V)` total for `V` virtual nodes), and `get_owner` is a single `O(log V)` binary
search - fast enough to run on every request even with hundreds of virtual nodes per
physical machine. The 22.5%-moved result (against a 25% theoretical ideal for going from 3
to 4 nodes) confirms the same property the earlier measured chart and the 0-15 walkthrough
both showed, and the perfect 50,000/50,000 round-trip after add-then-remove confirms the
ring is fully reversible: no key silently ends up on the wrong node after a scale-up/down
cycle.

## Routing requests to the right partition

Something has to turn "key K" into "which node." Two common architectures:

- **A routing/coordinator layer** sits in front of the shards, holds the ring (or a
  partition map), and forwards each request to the right node - simple for clients, but the
  router itself needs to scale and stay available, and it's another hop of latency.
- **Client-side routing** - clients (or a lightweight client library) hold the ring
  themselves and talk to the correct shard directly, no extra hop - common in key-value
  stores built for this (DynamoDB, Cassandra clients). The cost: every client needs to stay
  in sync with ring membership changes, usually via a gossip protocol or a shared
  coordination service (ZooKeeper/etcd, Part 3.6).

## Secondary indexes on partitioned data

Sharding by `item_id` makes lookups by `item_id` trivial - hash it, go straight to the
right shard. It makes a query on a *different* column, like `WHERE color = 'red'`, much
harder, because matching rows could be on any shard. Two standard answers:

![Local vs. global secondary index strategies](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-secondary-index-strategies.png)

- **Local secondary index** - each shard maintains its own index on `color`, covering only
  its own rows. Writes stay fast and fully local (no cross-shard coordination). Reads for
  `color = 'red'` have to **scatter-gather**: query every shard's local index and merge the
  results, so read cost grows with the number of shards.
- **Global secondary index** - a separate index structure that's itself partitioned, but by
  `color` instead of `item_id`, so a `color = 'red'` query hits exactly one index
  partition. Reads get cheap and targeted; the cost moves to writes, which now have to
  update two different partitioned structures (the primary data, keyed by `item_id`, and
  the index, keyed by `color`) that live on different shards - usually kept in sync
  asynchronously, which means the global index can lag slightly behind the primary data.

Same trade-off shape as everywhere else in this note: push the cost to write time (global
index) or to read time (local index, scatter-gather), and choose based on which side of
your read/write ratio actually needs to be fast.

## Advantages and disadvantages of sharding

**Advantages:**
- Breaks through a single machine's storage and throughput ceiling - the main reason to do
  it at all.
- Parallelizes both writes and reads across independent machines, multiplying total system
  throughput roughly with shard count.
- Limits blast radius: a single shard's failure or slow query affects only the slice of
  data (and users) it owns, not the whole system.

**Disadvantages:**
- **Cross-shard queries and joins become expensive or impossible** without scatter-gather
  or denormalization - the relational convenience of "just join it" mostly disappears.
- **Cross-shard transactions are hard**: atomically updating rows on two different shards
  needs a distributed transaction protocol (2PC, Part 3.7) or a redesign to avoid needing
  one at all.
- **Operational complexity**: rebalancing, monitoring N machines instead of one, routing
  logic, and a real risk of hot shards if the partition key wasn't chosen well.
- **The partition key choice is close to permanent** - re-sharding on a different key later
  means migrating the entire dataset live, which is one of the more painful operations in
  distributed systems.

The standard interview framing: shard only once vertical scaling and read replicas are
genuinely insufficient - it solves a real ceiling, but it is not free, and the bill mostly
comes due in query flexibility and operational surface area.

## Cheat sheet

```
SCALING       vertical: bigger box, simple, has a ceiling
              horizontal: more boxes, no hard ceiling, costs you coordination
              read replicas: full copies, offload READS only, not a scaling fix for writes

VOCABULARY    partitioning = splitting data (can be within ONE instance - proven above
                              with Postgres native partitioning + partition pruning)
              sharding     = partitioning where each partition IS a separate machine
              replication  = full COPIES, not slices - orthogonal to both of the above,
                              usually combined with sharding, not instead of it

SPLIT BY      horizontal (by row, same schema everywhere) vs.
              vertical (by column / table - hot columns vs. cold columns)

KEYING        hash(key) % N   -> uniform load, kills range queries, terrible rebalancing
              range           -> cheap range scans, risk of hot ranges
              consistent hashing + virtual nodes -> ~1/(N+1) keys move on resize
              (measured: naive 80-94% vs. consistent hashing 5-18%, same resize)

STATELESS     load balancer: hash(access_token) % N is FINE - any server can serve
vs STATEFUL   any request, a remap is just a redirect. Distributed storage: hash(key)
              % N is NOT fine - a remap means physically moving that key's data
              (verified: removing 1 of 3 nodes moved 50% of 6 keys). Consistent
              hashing exists specifically for the stateful case.

RING IMPL     two parallel sorted arrays (positions, owners) + bisect for O(log V)
              lookup/insert. Verified: deterministic lookups, 22.5% of 50,000 keys
              moved adding a 4th node (ideal 25%), 100% reversible after add+remove.

REBALANCING   add/remove node -> only its ring arcs move; throttle the migration;
              don't react to transient spikes

ROUTING       coordinator layer (extra hop, simple clients) vs.
              client-side routing (no extra hop, clients must track ring membership)

2ND INDEXES   local (per-shard) index -> cheap write, scatter-gather read
              global (separately partitioned) index -> cheap read, cross-shard write,
                usually async / eventually consistent

TRADE-OFF     sharding buys throughput + storage ceiling, costs: joins, cross-shard
              transactions, ops complexity, and a partition key that's expensive to change
```
