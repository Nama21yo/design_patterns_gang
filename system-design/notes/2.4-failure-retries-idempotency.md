---
title: "2.4 Failure detection, timeouts, retries, backoff, idempotency"
---

2.6 covered what to do once you already know a dependency is struggling - circuit breakers,
bulkheads, load shedding. This note is one layer earlier: how a single caller decides a
call failed at all, whether it's safe to try again, and how to retry without making things
worse. It closes with the mechanism that makes retrying safe in the first place -
idempotency keys - built out into a small, real API.

## Failure detection: timeouts are the practical answer

![Timeouts as the practical compromise to an unanswerable question](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-4-failure-detection.png)

3.6 already established the hard fact underneath this: in an asynchronous network, there is
genuinely **no way to distinguish** "the remote service died" from "the remote service (or
the network) is just slow" - that's the FLP impossibility result, informally. Every system
that claims to detect failure is actually just choosing a **timeout** and accepting a small,
bounded risk of guessing wrong. Too short a timeout produces false positives - retrying (or
failing) calls that would have succeeded fine given another few hundred milliseconds. Too
long a timeout wastes latency on every genuine failure, and, per 2.6, risks tying up
caller-side threads/connections waiting on a dependency that was never going to answer -
exactly the setup for cascading failure. There's no universal right number; it has to be
tuned per call, informed by that specific call's own observed p99 latency, not a
one-size-fits-all constant.

## Deciding whether to retry

![Only retry a transient failure on an operation that's safe to repeat](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-4-retry-decision.png)

Two independent questions, both of which have to be "yes" before retrying is the right call:

1. **Is the failure transient?** A network blip or a brief overload might genuinely succeed
   on retry. A `400 Bad Request` or `401 Unauthorized` will fail identically every time -
   retrying it is pure waste, and in the case of auth failures, can even look like an
   attack.
2. **Is the operation safe to repeat?** If it isn't already idempotent, and there's no
   idempotency-key mechanism (below) making it safe, blindly retrying a failed call risks a
   genuine duplicate side effect - a payment charged twice, a notification sent twice, a row
   inserted twice.

Only when both are true should a retry actually happen - and even then, *how* it retries
matters as much as *whether* it does.

## Backoff and jitter

Retrying immediately after a failure is close to the worst possible choice: if the
dependency failed because it's overloaded, an instant retry from every caller just adds to
the load that caused the failure in the first place. **Exponential backoff** - wait
`base * 2^attempt` before each retry - fixes the immediate-hammering problem by spacing
retries out further apart the more times they've already failed.

But exponential backoff alone has its own failure mode: if a large fleet of clients all
fail **at the same moment** (a brief outage, a deploy, a network partition), every one of
them computes the *exact same* delay on the *exact same* schedule - they're now
perfectly **synchronized**, and the entire fleet slams the recovering service with a retry
storm at precisely the same instant, potentially knocking it back down right as it was
recovering. **Jitter** - adding randomness to the delay - breaks that synchronization.

Verified: 2,000 clients that all failed at the same moment, all on their 3rd retry attempt,
comparing plain exponential backoff against **full jitter** (`delay = random(0, base *
2^attempt)`, the strategy AWS's own architecture guidance recommends):

```python
import random

N_CLIENTS = 2000
BASE_MS = 100
ATTEMPT = 3

def exponential_backoff_no_jitter(base, attempt):
    return base * (2 ** attempt)

def exponential_backoff_full_jitter(base, attempt):
    max_delay = base * (2 ** attempt)
    return random.uniform(0, max_delay)

no_jitter_delays = [exponential_backoff_no_jitter(BASE_MS, ATTEMPT) for _ in range(N_CLIENTS)]
full_jitter_delays = [exponential_backoff_full_jitter(BASE_MS, ATTEMPT) for _ in range(N_CLIENTS)]

def bucket_counts(delays, bucket_size=50):
    buckets = {}
    for d in delays:
        b = int(d // bucket_size) * bucket_size
        buckets[b] = buckets.get(b, 0) + 1
    return buckets

no_jitter_buckets = bucket_counts(no_jitter_delays)
full_jitter_buckets = bucket_counts(full_jitter_delays)

print(f"WITHOUT jitter: clients retrying in the SAME 50ms bucket (the peak): "
     f"{max(no_jitter_buckets.values())}")
print(f"WITH full jitter: clients retrying in the SAME 50ms bucket (the peak): "
     f"{max(full_jitter_buckets.values())}")
```

```
WITHOUT jitter: clients retrying in the SAME 50ms bucket (the peak): 2000
WITH full jitter: clients retrying in the SAME 50ms bucket (the peak): 152
```

![Measured: jitter cuts the synchronized retry spike by 13x](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-4-backoff-jitter-verified.png)

(Re-running this yourself will show a slightly different jittered peak - the exact count
depends on the random draw - but the qualitative result is stable: without jitter it is
always 100% in one bucket, and with jitter it is always a small fraction of that.) Without
jitter, **all 2,000 clients** land in the identical 50ms window - a perfect,
maximally-damaging retry storm. With jitter, the worst 50ms window has only 152 clients in
it, a **13x** smaller peak, because the randomness spreads the same 2,000 retries out
across the full 0-800ms range instead of stacking them on one instant.

## Idempotency keys

Retrying safely, even for a genuinely idempotent-*seeming* operation like "charge this
payment," has a subtlety worth being precise about: the operation itself might not be
naturally idempotent (charging twice is not the same as charging once), and even if it
were, the *client* has no way to know whether its original request actually succeeded
server-side before the response was lost - a timeout means "I don't know what happened,"
not "it failed."

![A client-generated key lets the server recognize and replay a retried request](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-4-idempotency-key-flow.png)

The fix - the same core idea as 3.7's idempotent consumer pattern, applied here to a
synchronous client-facing API rather than an async message consumer: the client generates a
unique **idempotency key** for each *logical* operation (not each network attempt) and
sends it with the request. The server checks whether it has already processed that key
before doing any side effect; if so, it returns the **same stored result** without
repeating the work. A client retrying after a timeout sends the identical key, and gets the
original result back safely, whether or not the original request actually went through.

Verified directly - a naive retry double-charges; the same retry, with an idempotency key,
does not:

```python
import uuid


class PaymentAPI:
    def __init__(self):
        self.balance = 1000
        self.processed_keys = {}

    def charge_naive(self, amount):
        self.balance -= amount
        return {"status": "charged", "amount": amount, "balance": self.balance}

    def charge_idempotent(self, idempotency_key, amount):
        if idempotency_key in self.processed_keys:
            cached = self.processed_keys[idempotency_key]
            return {**cached, "replayed": True}
        self.balance -= amount
        response = {"status": "charged", "amount": amount, "balance": self.balance}
        self.processed_keys[idempotency_key] = response
        return {**response, "replayed": False}


api = PaymentAPI()
r1 = api.charge_naive(100)          # succeeds server-side...
print(f"first charge attempt: {r1}")
r2 = api.charge_naive(100)          # ...client never saw the response, retries
print(f"client retries after a timeout: {r2}")
print(f"balance after 1 LOGICAL charge of 100: {api.balance} (charged TWICE - a real bug)")

api2 = PaymentAPI()
key = str(uuid.uuid4())
r1 = api2.charge_idempotent(key, 100)
print(f"\nfirst charge attempt (key={key[:8]}...): {r1}")
r2 = api2.charge_idempotent(key, 100)   # same key - retrying the SAME logical operation
print(f"client retries after a timeout, SAME key: {r2}")
print(f"balance after 1 LOGICAL charge of 100: {api2.balance} (charged ONCE - correct)")
```

```
first charge attempt: {'status': 'charged', 'amount': 100, 'balance': 900}
client retries after a timeout: {'status': 'charged', 'amount': 100, 'balance': 800}
balance after 1 LOGICAL charge of 100: 800 (charged TWICE - a real bug)

first charge attempt (key=b46ad19f...): {'status': 'charged', 'amount': 100, 'balance': 900, 'replayed': False}
client retries after a timeout, SAME key: {'status': 'charged', 'amount': 100, 'balance': 900, 'replayed': True}
balance after 1 LOGICAL charge of 100: 900 (charged ONCE - correct)
```

The naive version's balance drops to 800 - a single logical charge of 100, executed twice,
purely because the client had no way to distinguish "my first request failed" from "my
first request succeeded but I never heard back." The idempotent version's balance correctly
lands on 900: the second call is recognized as a replay of the same key and returns the
cached result (`"replayed": True`) instead of touching the balance again. In a real API,
this pattern is exactly what production payment and order-creation endpoints use - an
`Idempotency-Key` request header, checked and recorded atomically alongside the actual
write (the same "check-and-record in one transaction" discipline 3.7 established for
async consumers), stored for a bounded window (long enough to cover realistic client retry
behavior, not forever).

## Cheat sheet

```
FAILURE       no way to truly distinguish dead from slow (FLP, 3.6) -
DETECTION     timeouts are the practical, imperfect answer. Too short:
              false positives. Too long: wasted latency + risk of
              cascading failure (2.6). Tune per call, off that call's p99.

RETRY         only retry if BOTH: (1) the failure looks TRANSIENT, not
DECISION      permanent (don't retry a 400 or 401), and (2) the operation
              is safe to repeat (idempotent, or covered by an idempotency
              key) - otherwise a "safe" retry can double a real side effect.

BACKOFF +     exponential backoff alone SYNCHRONIZES a fleet's retries onto
JITTER        the same schedule -> a retry storm right as the dependency
              is recovering. Verified: 2,000 clients, same outage -> 100%
              landed in the same 50ms window without jitter; with full
              jitter (random(0, max_delay)), the worst window had only
              7.6% (13x smaller peak).

IDEMPOTENCY   client generates a key per LOGICAL operation (not per network
KEYS          attempt), server checks-and-records it atomically with the
              actual write, and returns the cached result on a replay.
              Verified: a naive retry double-charged (1000 -> 800 for one
              logical 100 charge); the same retry WITH a key charged once
              (1000 -> 900), correctly flagging the replay. Same underlying
              idea as 3.7's idempotent consumer, applied to a synchronous
              client-facing API instead of an async message consumer.
```
