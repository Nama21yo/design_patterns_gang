title: "3.3 Indexing"
---

An index is a bet: spend extra storage and extra work on every write, to make some reads
dramatically faster. Whether that bet pays off depends entirely on your access pattern -
which is exactly why "should I index this column" is never a yes/no question in isolation,
it's a question about *how this table gets queried*. Every claim in this note is backed by
a real `EXPLAIN ANALYZE` run against a live Postgres 16 instance with 1-2 million rows, not
a theoretical estimate - the queries and their measured output are included so you can
reproduce them. (Re-running will give slightly different millisecond values depending on
your hardware and cache state - the orders-of-magnitude and the qualitative facts, like
"zero heap fetches" or "removed 666,666 rows by filter," are what to trust, not the exact
digit.)

## Why indexes exist: avoiding a full scan

Fixture used for every example below: a 2-million-row `users` table, no indexes beyond the
implicit primary key.

```python
import psycopg2

conn = psycopg2.connect(host="localhost", dbname="postgres", user="postgres")
cur = conn.cursor()
cur.execute("""CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY, email TEXT, country TEXT, signup_day INT)""")
cur.execute("""
    INSERT INTO users (email, country, signup_day)
    SELECT 'user' || i || '@example.com',
           (ARRAY['US','UK','DE','IN','BR','JP'])[1 + (i % 6)],
           i % 3650
    FROM generate_series(1, 2000000) AS i
""")
conn.commit()
```

Without an index, finding a row by a non-key column means the database has to read every
single row and check it - a **sequential scan**:

```python
cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) "
           "SELECT * FROM users WHERE email = 'user1500000@example.com'")
print("\n".join(r[0] for r in cur.fetchall()))
```

```
Gather  (cost=1000.00..25087.97 rows=6500 width=76) (actual time=124.057..129.674 rows=1 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Parallel Seq Scan on users  (cost=0.00..23437.97 rows=2708 width=76) (actual time=109.124..120.937 rows=0 loops=3)
        Filter: (email = 'user1500000@example.com'::text)
        Rows Removed by Filter: 666666
Planning Time: 0.501 ms
Execution Time: 129.732 ms
```

`Rows Removed by Filter: 666666` is the tell - Postgres (even parallelized across workers)
had to look at two-thirds of a million rows on one worker alone just to find the one row
that matched. Now add an index and run the identical query:

```python
cur.execute("CREATE INDEX idx_users_email ON users (email)")
conn.commit()
cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) "
           "SELECT * FROM users WHERE email = 'user1500000@example.com'")
print("\n".join(r[0] for r in cur.fetchall()))
```

```
Bitmap Heap Scan on users  (cost=277.93..15495.29 rows=10000 width=76) (actual time=0.039..0.040 rows=1 loops=1)
  Recheck Cond: (email = 'user1500000@example.com'::text)
  Heap Blocks: exact=1
  ->  Bitmap Index Scan on idx_users_email  (cost=0.00..275.43 rows=10000 width=0) (actual time=0.034..0.034 rows=1 loops=1)
        Index Cond: (email = 'user1500000@example.com'::text)
Planning Time: 0.187 ms
Execution Time: 0.062 ms
```

**129.7 ms down to 0.062 ms - about 2,000x**, on the exact same table, same data, same
query, the only difference being one `CREATE INDEX`. This is the entire case for indexing
in one number.

## How it works: the B-tree

The default index structure in essentially every relational database is a **B-tree** (Part
3.1 covers storage engines generally; this is the read-optimized structure inside that
discussion). Keys are stored in sorted order across a shallow, wide tree - internal nodes
hold routing keys, leaf nodes hold the actual key values plus a pointer to the row (or, for
a clustered index, the row itself):

![B-tree index structure](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-3-btree-structure.png)

Three properties fall out of this shape directly:

- **Point lookups are `O(log n)`** - a handful of comparisons walks from root to leaf,
  which is why a 2-million-row lookup above took microseconds, not milliseconds.
- **Range scans are cheap** - leaf nodes are linked to their neighbors, so `WHERE age
  BETWEEN 20 AND 30` walks sideways along the leaf level once it finds the start, instead
  of restarting the search per row.
- **It's shallow** - a B-tree over a billion rows is typically only 3-4 levels deep,
  because each node holds many keys (hundreds, tuned to the storage page size), not just
  two like the toy diagram above.

## Primary vs. secondary, clustered vs. non-clustered

These are two different axes, and it's easy to conflate them:

- **Primary vs. secondary** is about *what* the index is on: the primary index enforces and
  accelerates lookups on the primary key; a secondary index is any additional index on some
  other column or combination of columns (`email`, `country`, whatever your queries need).
- **Clustered vs. non-clustered** is about *how the table's rows are physically stored*:

![Clustered vs. non-clustered indexes](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-3-clustered-vs-nonclustered.png)

- A **clustered index** determines the physical on-disk order of the table itself - the
  table *is* the index's leaf level, so there's no separate structure and no extra hop. A
  table can have at most one clustered index (rows can only be sorted one way on disk).
  This is usually the primary key (MySQL/InnoDB always clusters on the primary key; Postgres
  is a partial exception - see below).
- A **non-clustered (secondary) index** is a separate sorted structure that stores the
  indexed column(s) plus a pointer back to where the actual row lives. Looking something up
  through it costs one extra hop: search the index, then follow the pointer to fetch the
  row. A table can have many of these.

(Aside, because it trips people up: Postgres actually has **no true clustered index** in
the MySQL/InnoDB sense - every Postgres index, including the primary key's, is a
non-clustered pointer structure into a heap file, and `CLUSTER` only *physically
reorders the heap to match an index once*, as a one-time operation, rather than maintaining
that order automatically on every write the way InnoDB does continuously.)

## Composite indexes and the leftmost-prefix rule

An index can span multiple columns, e.g. `CREATE INDEX ON users (country, signup_day)`.
The order you list them in matters enormously - a composite index is only useful for a
query if that query filters on a **prefix** of the indexed columns, left to right, because
the index is physically sorted by the first column first, then the second column within
each value of the first, and so on:

```python
cur.execute("CREATE INDEX idx_users_country_day ON users (country, signup_day)")
conn.commit()

for label, sql in [
    ("both columns (leftmost prefix satisfied)",
     "SELECT id FROM users WHERE country = 'DE' AND signup_day = 100"),
    ("country only (the leftmost column)",
     "SELECT id FROM users WHERE country = 'DE'"),
    ("signup_day only (NOT the leftmost column)",
     "SELECT id FROM users WHERE signup_day = 100"),
]:
    cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) " + sql)
    plan = "\n".join(r[0] for r in cur.fetchall())
    print(f"--- {label} ---\n{plan}\n")
```

```
--- both columns (leftmost prefix satisfied) ---
Bitmap Heap Scan on users  (actual time=0.081..0.634 rows=182 loops=1)
  ->  Bitmap Index Scan on idx_users_country_day
        Index Cond: ((country = 'DE'::text) AND (signup_day = 100))
Execution Time: 0.696 ms

--- country only (the leftmost column) ---
Bitmap Heap Scan on users  (actual time=32.292..175.868 rows=333334 loops=1)
  ->  Bitmap Index Scan on idx_users_country_day
        Index Cond: (country = 'DE'::text)
Execution Time: 194.091 ms

--- signup_day only (NOT the leftmost column) ---
Gather  (actual time=0.323..102.049 rows=548 loops=1)
  ->  Parallel Seq Scan on users
        Filter: (signup_day = 100)
        Rows Removed by Filter: 666484
Execution Time: 102.115 ms
```

The third query gets a **full sequential scan**, exactly as if the index didn't exist,
because `signup_day` alone doesn't tell the B-tree where to start - it would have to check
every `country` group. The rule in one line: **build a composite index with the columns
your queries always filter on first, in order of selectivity or by what queries actually
lead with** - and if two different query shapes need two different leading columns, you
generally need two separate indexes, not one composite one.

## Covering indexes and index-only scans

If an index contains *every* column a query needs - either because they're part of the key
or explicitly carried along via `INCLUDE` - Postgres never has to touch the table's heap at
all:

```python
cur.execute("DROP INDEX idx_users_email")
cur.execute("CREATE INDEX idx_users_email_covering ON users (email) INCLUDE (country)")
conn.commit()
conn.autocommit = True
cur.execute("VACUUM ANALYZE users")   # refresh the visibility map for a fair test; VACUUM
conn.autocommit = False               # can't run inside a transaction block
cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) "
           "SELECT country FROM users WHERE email = 'user1500000@example.com'")
print("\n".join(r[0] for r in cur.fetchall()))
```

```
Index Only Scan using idx_users_email_covering on users  (actual time=0.019..0.019 rows=1 loops=1)
  Index Cond: (email = 'user1500000@example.com'::text)
  Heap Fetches: 0
Planning Time: 0.201 ms
Execution Time: 0.056 ms
```

`Heap Fetches: 0` is the proof: the answer came entirely out of the index structure. This
is a genuinely powerful, underused technique - if a hot query only ever needs two or three
columns, a covering index can make it nearly free, at the cost of a larger, more
write-expensive index (below).

## Inverted indexes

Everything above indexes rows by a column *value*. An **inverted index** flips the
direction for text: it maps each distinct *term* to the list of documents/rows containing
it (a "posting list"), which is the structure behind virtually all full-text and search
systems (Elasticsearch, Postgres's own `tsvector`/GIN support, Lucene under the hood).

![Inverted index: term -> posting list](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-3-inverted-index.png)

New fixture for this section: a 1-million-row `articles` table with a short text body.

```python
cur.execute("CREATE TABLE articles (id BIGSERIAL PRIMARY KEY, body TEXT)")
cur.execute("""
    INSERT INTO articles (body)
    SELECT CASE WHEN i % 50000 = 0 THEN 'breaking news about the stock market rally today'
                ELSE 'routine update number ' || i || ' nothing special happening'
           END
    FROM generate_series(1, 1000000) AS i
""")
conn.commit()
```

Without an inverted index, a text search is a scan with a string match on every row:

```python
cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) "
           "SELECT id FROM articles WHERE body LIKE '%stock market rally%'")
print("\n".join(r[0] for r in cur.fetchall()))
```

```
Gather  (actual time=39.406..136.221 rows=20 loops=1)
  ->  Parallel Seq Scan on articles
        Filter: (body ~~ '%stock market rally%'::text)
        Rows Removed by Filter: 333327
Execution Time: 136.249 ms
```

With a GIN index over a `tsvector` (Postgres's built-in inverted index for text):

```python
cur.execute("ALTER TABLE articles ADD COLUMN body_tsv tsvector "
           "GENERATED ALWAYS AS (to_tsvector('english', body)) STORED")
cur.execute("CREATE INDEX idx_articles_tsv ON articles USING GIN (body_tsv)")
conn.commit()
cur.execute("EXPLAIN (ANALYZE, FORMAT TEXT) SELECT id FROM articles "
           "WHERE body_tsv @@ to_tsquery('english', 'stock & market & rally')")
print("\n".join(r[0] for r in cur.fetchall()))
```

```
Bitmap Heap Scan on articles  (actual time=0.070..0.167 rows=20 loops=1)
  Recheck Cond: (body_tsv @@ '''stock'' & ''market'' & ''ralli'''::tsquery)
  ->  Bitmap Index Scan on idx_articles_tsv
        Index Cond: (body_tsv @@ '''stock'' & ''market'' & ''ralli'''::tsquery)
Execution Time: 0.191 ms
```

**136 ms down to 0.191 ms - about 700x.** A term-based query ("stock AND market AND
rally") becomes: look up each term's posting list, intersect them, done - no scanning of
text at query time at all, all the expensive tokenization work having already happened once
at write time. This is exactly why Elasticsearch, whose whole reason to exist is fast text
and faceted search, is built around this structure end to end (3.2).

## Index maintenance cost: nothing is free

Every index is a second (or third, or fifth) data structure that has to be updated, in
sync, on every `INSERT`, `UPDATE`, or `DELETE` to the table. More indexes means more work
per write, measurably:

```python
import time

def bench(num_indexes):
    cur.execute("DROP TABLE IF EXISTS bench")
    cur.execute("CREATE TABLE bench (id BIGSERIAL PRIMARY KEY, a INT, b INT, c INT, d TEXT)")
    for col in ("a", "b", "c", "d")[:num_indexes]:
        cur.execute(f"CREATE INDEX ON bench ({col})")
    conn.commit()
    start = time.perf_counter()
    cur.execute("INSERT INTO bench (a, b, c, d) "
               "SELECT i % 1000, i % 500, i % 250, 'val' || i "
               "FROM generate_series(1, 300000) AS i")
    conn.commit()
    return time.perf_counter() - start

for n in (0, 1, 2, 4):
    print(f"{n} secondary index(es): {bench(n):.3f}s to insert 300,000 rows")
```

```
0 secondary index(es) on the table: 1.281s to insert 300,000 rows
1 secondary index(es) on the table: 1.859s to insert 300,000 rows
2 secondary index(es) on the table: 2.407s to insert 300,000 rows
4 secondary index(es) on the table: 5.510s to insert 300,000 rows
```

![Every index is more work on every write](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-3-maintenance-cost.png)

Going from zero to four secondary indexes on this table roughly **quadrupled** insert time,
on top of the extra storage each index occupies on disk (and holds in cache, competing with
everything else for memory). This is the other half of the trade-off from the top of this
note, made concrete: **every index is a bet on a specific read pattern, paid for on every
single write, whether or not that read ever happens.** The practical rule: index the
columns your actual queries filter, join, or sort on - not every column that theoretically
could be queried - and periodically check for indexes nothing is using (most databases
expose usage stats for exactly this) and drop them.

## Cheat sheet

```
WHY           avoids a full scan: O(n) -> O(log n) for point lookups, cheap range scans
              measured: 2,000x on a point lookup; 700x on a text search (this note)

STRUCTURE     B-tree by default: shallow (3-4 levels at billions of rows), sorted,
              leaves linked for range scans. Hash indexes exist too (equality-only,
              no range support). GIN/inverted for text and array containment.

PRIMARY vs    primary = on the primary key. secondary = any other indexed column(s).
SECONDARY     orthogonal to clustered/non-clustered (below).

CLUSTERED     table IS the index leaf level; physical row order = index order;
              at most one per table (InnoDB: always the PK; Postgres: no true
              clustered index, CLUSTER is a one-time manual reorder only).

NON-CLUSTERED separate sorted structure + pointer back to the row; one extra hop;
              a table can have many.

COMPOSITE     order matters: only usable for a leftmost PREFIX of the indexed columns.
              (country, signup_day) helps "WHERE country=X", not "WHERE signup_day=Y" alone.

COVERING      INCLUDE every column the query needs -> index-only scan, zero heap
              fetches, often the single biggest win available for a hot read path.

MAINTENANCE   every index = more work on every write (measured: ~4x insert time
              going from 0 to 4 indexes). Index what you query; drop what you don't.
```
