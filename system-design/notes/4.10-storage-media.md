title: "4.10 Storage media: RAM generations, SSD, HDD and RAID"

The bottom rungs of 4.8's memory hierarchy ladder deserve their own look: what's actually
inside the RAM chips you're clocking, how an SSD stores a bit with no moving parts at all,
and how RAID turns several individually-failure-prone disks into one storage volume that
survives losing one of them - the disk-level equivalent of 3.5's replication, one layer
lower.

## RAM generations: SDR, DDR, QDR

RAM's *speed* isn't just a matter of a higher clock number - it's also about how much data
moves **per clock tick**:

![RAM generations](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-10-ram-generations.png)

- **SDR (Single Data Rate)** - one data transfer per clock cycle, synchronized to the clock
  edge. The original baseline.
- **DDR (Double Data Rate)** - transfers data on *both* the rising and falling edge of the
  clock, doubling throughput at the same clock frequency, with no need to actually run the
  clock faster (which has its own costs - power, heat, signal integrity). Practically every
  RAM in a modern computer (DDR4, DDR5...) uses this trick; the generation number tracks
  further improvements in clock speed, prefetch width, and power efficiency on top of the
  same double-pumped idea.
- **QDR (Quad Data Rate)** - four transfers per clock, achieved by using both clock edges
  on *two* separate, offset clock signals. Less common in mainstream system RAM; shows up
  more in specialized networking and high-throughput memory applications where the extra
  design complexity is worth it.

The general lesson, useful beyond just RAM: "faster" memory technology is as often about
**moving more data per clock** as it is about raising the clock rate itself - the same kind
of trade-off AVX's wide vector registers (4.8) make in the compute domain.

## SSD: no moving parts, bits held as trapped charge

An SSD stores each bit in a **floating-gate transistor**:

![SSD cell -> page -> block structure](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-10-ssd-structure.png)

The "floating" gate is electrically isolated - electrons pushed onto it during a write stay
trapped there with **no power applied at all**, which is exactly what makes flash memory
non-volatile the way DRAM (4.8) is not. Reading the cell measures the effect that trapped
charge has on the transistor's threshold voltage. Modern cells pack multiple bits per
transistor by distinguishing more (finer-grained) charge levels - SLC (1 bit), MLC (2),
TLC (3), QLC (4) - trading durability and speed for cost as you pack more bits into the
same physical cell.

Cells are grouped into **pages** (the read/write granularity, a few KB) and pages into
**blocks** (the *erase* granularity, several MB). The asymmetry matters operationally: you
can write a page that's currently empty, but you cannot rewrite one in place - you have to
erase the *entire block* it's in first. This is the root cause of SSD write amplification
and why SSD controllers run background garbage collection to consolidate live pages out of
mostly-stale blocks before erasing them.

### NAND vs. NOR flash

![NAND vs. NOR](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-10-nand-vs-nor.png)

The names come from how the cells are electrically wired together, mirroring the logic
gates of the same name: **NAND** flash wires cells in series (like a NAND gate), which
packs more cells per unit area - higher density, lower cost per bit - at the cost of only
supporting page/block-level access, not addressing an arbitrary single byte. **NOR** flash
wires cells in parallel (like a NOR gate), giving true random byte-level access at the cost
of much lower density. That access-pattern difference is exactly why NAND is what's behind
essentially every SSD and USB drive (bulk storage, read/written in pages anyway), while NOR
shows up in embedded firmware that needs to execute code directly from the flash chip
(XIP - execute in place), which needs random byte addressing the way RAM does.

## HDD, briefly revisited

3.1 already covered the mechanical structure - platters, tracks, sectors, the seek/rotate/
transfer cost that makes random access slow and sequential access fast. The one thing worth
adding here: HDDs remain relevant specifically *because* of the cost-per-byte gap with
SSDs at very large scale - cold storage, backups, and the raw capacity tier of the storage
hierarchy (4.8) still lean on spinning disks for exactly the same size-vs-speed trade every
other level of that hierarchy makes.

## RAID: replication and striping, at the disk level

Any single disk - HDD or SSD - can fail. **RAID** (Redundant Array of Independent Disks)
combines several physical disks into one logical volume, trading some raw capacity for
either speed, redundancy, or both - the disk-level version of 3.5's "replicate for
durability" and 3.4's "shard for throughput," done one layer below the database:

![RAID levels](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-10-raid-levels.png)

- **RAID 0 (striping)** - spread data across all disks with no redundancy at all. Fastest
  (reads and writes parallelize across every disk), and the worst reliability - **any**
  single disk failing loses the *entire* volume, since every disk holds an irreplaceable
  slice of every file.
- **RAID 1 (mirroring)** - write every block to two (or more) disks in full. Simple,
  survives losing any one disk in the mirror, at the direct cost of half your raw capacity
  going to duplicates.
- **RAID 5 (striping + single parity)** - data striped across `N` disks, plus **one**
  disk's worth of capacity spent on a rotating parity block per stripe, computed as the
  XOR of the corresponding data blocks. `N-1` disks' worth of usable capacity, survives
  **any one** disk failing.
- **RAID 6** - like RAID 5 but with **two** independent parity blocks per stripe, `N-2`
  usable capacity, survives **any two** simultaneous disk failures - the extra margin large
  arrays need, since with enough disks the odds of a second failure during a slow rebuild
  window become genuinely non-negligible.
- **RAID 10** - mirror pairs of disks (RAID 1), then stripe across those mirrored pairs
  (RAID 0): fast like striping, redundant like mirroring, at RAID 1's same 50%-capacity
  cost.

### Proving RAID 5's trick: XOR parity, reconstructed live

The elegant core of RAID 5 is that XOR is its own inverse in exactly the right way: XOR all
the data blocks together to get the parity block, and XOR any `N-1` of the `N` total blocks
(data *or* parity) together to recover whichever one is missing:

```python
import random

def xor_bytes(*chunks):
    result = bytearray(chunks[0])
    for c in chunks[1:]:
        for i in range(len(result)):
            result[i] ^= c[i]
    return bytes(result)

random.seed(1)
data_chunks = [bytes(random.randint(0, 255) for _ in range(8)) for _ in range(3)]
parity = xor_bytes(*data_chunks)
disks = data_chunks + [parity]   # disks 0-2 = data, disk 3 = parity

print("disk 3 (parity):", disks[3].hex(), "= disk0 XOR disk1 XOR disk2")

# any ONE of the 4 disks (data or parity) is recoverable from the other 3
for failed_index in range(4):
    survivors = [d for i, d in enumerate(disks) if i != failed_index]
    reconstructed = xor_bytes(*survivors)
    assert reconstructed == disks[failed_index]
print("assert OK: any ONE of the 4 disks is recoverable by XOR-ing the other 3")
```

```
disk 3 (parity): a7654f903530fd22 = disk0 XOR disk1 XOR disk2
assert OK: any ONE of the 4 disks is recoverable by XOR-ing the other 3
```

Notice the parity disk is *not* special in a way the reconstruction logic has to treat
differently - the assertion loop above fails each of the 4 disks in turn, parity included,
and rebuilds it from the other 3 exactly the same way. That symmetry is why RAID 5 needs
only one extra disk's worth of capacity for the array (rather than a full duplicate, RAID
1's cost) to survive any single failure - and directly explains why RAID 6 needs *two*
independent parity schemes (plain XOR parity alone can only pinpoint and fix a single
unknown missing value; recovering from two simultaneous unknowns needs a second, distinct
equation).

## Cheat sheet

```
RAM           SDR: 1 transfer/clock. DDR: 2 (both clock edges) - what virtually
GENERATIONS   all system RAM uses today. QDR: 4 (both edges, 2 offset clocks) -
              mostly networking/specialized. "Faster" often means more data per
              clock tick, not a higher clock - same idea as AVX's wide registers.

SSD           bit = charge trapped on an ISOLATED floating-gate transistor -> no
              power needed to hold it (non-volatile). cells -> PAGES (read/write
              unit, KBs) -> BLOCKS (ERASE unit, MBs). Can't rewrite a page in
              place - must erase the whole block first -> write amplification,
              background garbage collection.

NAND vs NOR   NAND: cells wired in series, dense/cheap, page/block access only
              -> SSDs, USB drives. NOR: cells in parallel, byte-addressable
              random access, lower density -> embedded firmware (execute in
              place).

HDD           mechanical (3.1) - still the capacity/cost-per-byte tier at scale
              (cold storage, backups) even where SSDs win on speed.

RAID          RAID 0 (stripe, 0 redundancy, fastest, any 1 disk loss = total
              loss) - RAID 1 (mirror, 50% capacity, survives 1 loss) - RAID 5
              (stripe + 1 XOR parity, N-1 usable, survives ANY 1 loss - verified
              live reconstruction) - RAID 6 (2 parity, N-2 usable, survives ANY
              2 simultaneous losses) - RAID 10 (mirror then stripe, fast AND
              redundant, 50% capacity). Disk-level version of replicate-for-
              durability (3.5) / shard-for-throughput (3.4).
```
