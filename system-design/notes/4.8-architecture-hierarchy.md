title: "4.8 Computer architecture and the memory hierarchy"
---

Every previous note in this Part assumed a particular shape of machine: one CPU, one
memory, instructions and data both just bits at some address. This note names that shape
explicitly, contrasts it with the alternative, and lays out the full size/speed ladder -
registers down to disk - that every other note in Part 4 is really just one rung of.

## Von Neumann architecture

The architecture nearly every general-purpose computer is built on, named for John von
Neumann's 1945 description of it:

![Von Neumann architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-8-von-neumann.png)

Four principles define it:

1. **Memory and processing unit are separate.** The CPU (control unit + ALU) and memory are
   distinct components, connected by a bus - the CPU doesn't *contain* the program, it
   *fetches* from memory, one instruction at a time.
2. **The principle of memory addressing.** Every location in memory - whether it holds an
   instruction or a piece of data - is identified by a numeric address, uniformly, the same
   way 4.6 addressed pages.
3. **The principle of command control.** Execution proceeds by explicit commands: a program
   counter tracks the address of the next instruction, and the CPU repeats fetch, decode,
   execute, advance - a discrete, sequential control flow (branches and jumps just change
   where the program counter points next).
4. **The principle of binary encoding.** Everything - the instructions themselves and the
   data they operate on - is stored as binary, in the *same* memory, with no hardware-level
   type tag distinguishing "this is code" from "this is data." That last point is exactly
   what makes both a compiler's output and a buffer-overflow exploit possible: to the
   hardware, a sequence of bytes is a sequence of bytes, and what turns it into "an
   instruction" is entirely about whether the program counter happens to be pointing at it.

The famous cost of this design is the **von Neumann bottleneck**: instructions and data
share one bus to one memory, so fetching the next instruction and reading/writing data
can't happen in the same cycle - they compete for the same channel.

## Harvard architecture

The direct alternative: give instructions and data **completely separate** memories and
buses.

![Harvard architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-8-harvard.png)

With separate instruction memory and data memory, the CPU can fetch the next instruction
and read or write data in the *same* cycle - no bottleneck, no contention. The cost: two
memories and two buses to build, and - because instruction memory and data memory are
genuinely separate hardware paths - no easy way to treat code as data (no convenient
self-modifying code, and a JIT compiler, which writes freshly-generated machine code and
then jumps into it, is awkward to express). This is why Harvard architecture shows up
mostly in microcontrollers and DSPs with fixed, simple firmware, not general-purpose
computers.

**Modern CPUs are actually a hybrid.** The overall system is von Neumann (one unified RAM,
code and data both addressable the same way) - but at the **L1 cache** level specifically
(4.9), almost every modern CPU splits into a separate L1 instruction cache and L1 data
cache, for exactly the Harvard reason: the CPU is very likely to want an instruction fetch
and a data access on the same cycle, and giving each its own small, fast, dedicated cache
avoids that contention right where it matters most, without paying for two full separate
memory systems.

## The memory hierarchy

Every storage technology trades size for speed - bigger is slower, smaller is faster, and
no single technology gives you both. Real systems don't pick one point on that trade-off;
they stack several, smallest/fastest closest to the CPU:

![The memory hierarchy](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-8-memory-hierarchy.png)

This is the same shape 0.3's latency table showed for a different purpose (estimating
system design costs); here it's the *reason* those numbers are what they are. Each level
acts as a cache for the level below it - the CPU cache (4.9) caches RAM, RAM effectively
caches disk (via the OS page cache and 4.6's paging), and this whole Part's notes on
application-level caching (4.1-4.4) are the exact same principle, one or two levels further
out, with a network hop standing in for a memory bus.

## SRAM vs. DRAM: the trade-off underneath registers and caches vs. RAM

The reason registers and caches are small but blazing fast, while main memory is large but
comparatively slow, is a hardware trade-off one level below the architecture diagrams above:

![SRAM vs DRAM](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-8-sram-vs-dram.png)

**SRAM** (Static RAM) stores each bit in a small loop of transistors (typically 6) that
holds its state as long as power is applied - no periodic refresh needed, and reads/writes
are very fast, but each cell takes real chip area, so SRAM is expensive and low-density.
That's exactly the profile registers and CPU caches want: small, fast, cost is secondary.
**DRAM** (Dynamic RAM) stores each bit as a charge on a tiny capacitor behind a single
transistor - far denser and cheaper per bit, but the capacitor leaks charge, so the whole
array has to be **refreshed** (read and rewritten) thousands of times a second or the data
decays. That refresh overhead is part of why DRAM is slower than SRAM - and why it's the
right trade for main memory, where capacity per dollar matters more than shaving off the
last nanosecond.

## Registers

The very top of the hierarchy - values the CPU is working with *right now*, with no
addressing or memory access involved at all:

![CPU registers](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-8-registers.png)

- **General-purpose registers** (`EAX`, `EBX`, `ECX`, `EDX`, and more on 64-bit/RISC ISAs) -
  hold whatever the compiler decides: arithmetic operands, function arguments, temporary
  values. "General purpose" in name, but compilers and calling conventions do assign
  informal roles to specific ones.
- **Special-purpose registers**, user-accessible:
  - **ESP (stack pointer)** - always points at the top of the current stack frame (4.6);
    pushing/popping (function calls, local variables) moves it directly.
  - **EBP (base pointer)** - a fixed reference point for the *current* function's frame,
    set once at function entry, so local variables and arguments can be addressed at
    constant offsets from it even as ESP moves around during the function's execution.
  - The **program counter / instruction pointer** (`EIP`/`RIP`) - the address of the next
    instruction, directly implementing the "command control" principle above.
  - The **flags register** - single-bit results of the last operation (zero, carry,
    overflow...) that conditional branches test.
- **Non-user-accessible (privileged) registers** - control and status registers the kernel
  uses to configure the CPU itself (interrupt tables, the page-table base address for the
  MMU from 4.6, privilege level) - deliberately off-limits to ordinary user-mode code, which
  is a large part of what keeps a process from tampering with the memory-protection
  machinery that's supposed to isolate it from everyone else.
- **Vector extensions (AVX and similar)** - much wider registers (256 or 512 bits) that hold
  several values packed together, with instructions that operate on all of them **in
  parallel** in a single cycle (SIMD - Single Instruction, Multiple Data). This is how
  numeric code (and libraries like numpy, used for the verified timing demos in 4.9) gets
  large speedups on bulk arithmetic without needing more CPU cores - one AVX instruction
  might add 8 pairs of floats at once instead of one pair per instruction.

## Cheat sheet

```
VON NEUMANN   memory+CPU separate / uniform addressing / explicit command control
              (program counter drives fetch-decode-execute) / binary encoding, no
              hardware type distinction between code and data. Nearly every
              general-purpose CPU. Cost: the "von Neumann bottleneck" - one
              shared bus, can't fetch an instruction and access data at once.

HARVARD       separate instruction memory/bus and data memory/bus -> same-cycle
              fetch+access, no bottleneck. Cost: 2x memory/bus hardware, no easy
              code-as-data (self-modifying code, JIT). Common in microcontrollers.
              Modern CPUs: von Neumann overall, Harvard-ish split L1 i-cache/
              d-cache specifically (4.9) - the same reason, applied narrowly.

HIERARCHY     registers (~1 cycle) -> L1 (~1ns) -> L2 (~4ns) -> L3 (~15-20ns)
              -> RAM (~100ns) -> SSD/HDD (us-ms). Each level caches the one
              below it - same principle as every caching note in this Part,
              just at a different distance from the CPU.

SRAM vs DRAM  SRAM: 6-transistor cell, no refresh, fast, low-density/expensive
              -> registers, CPU caches. DRAM: 1 transistor + capacitor, needs
              constant refresh (leaks), slower, dense/cheap -> main memory.

REGISTERS     general-purpose (compiler-assigned roles) / special-purpose:
              ESP (stack top), EBP (current frame's fixed base), PC/EIP/RIP
              (next instruction), flags (zero/carry/overflow) / non-user-
              accessible (privileged control registers - MMU config, interrupt
              tables) / AVX vector registers (256/512-bit, SIMD - one
              instruction operates on several packed values at once).
```
