2.1 covered HTTP as a transport. This note is what actually rides on top of it: four
different answers to "what does a client-server API call look like," each optimizing for a
different thing - and, because none of them is strictly better, each still showing up
heavily in production systems today.

![Four styles, four different shapes for the same underlying call](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-2-four-styles.png)

## REST: resource-oriented

**REST** (Representational State Transfer) models an API as a set of **resources**
(nouns) - `/orders/42`, `/users/7/posts` - manipulated through HTTP's own verbs: `GET`
(read), `POST` (create), `PUT`/`PATCH` (update), `DELETE` (remove). This gets a lot for
free just by leaning on HTTP itself: standard status codes (`404` for "doesn't exist,"
`409` for "conflict"), standard caching semantics (`Cache-Control`, `ETag` - 4.4's whole
CDN chapter applies directly to a REST API's `GET` endpoints), and a uniform interface any
HTTP client already understands without custom tooling - `curl` a REST endpoint and you can
read the response immediately.

The recurring cost: REST's resource shape doesn't naturally match every UI's data needs.
**Over-fetching** - a `GET /users/1` returns every field of the user resource, even when
the caller only needed the display name and avatar. **Under-fetching** - rendering a view
that needs a user *and* their recent posts *and* each post's comment count requires
multiple separate round trips, because REST's resources don't nest arbitrarily deep by
default. Both problems get worse the more a screen's data needs diverge from how resources
happen to be modeled server-side.

## RPC: procedure-oriented

**RPC** (Remote Procedure Call, the general pattern predating gRPC) models an API as
**named actions** instead of resources - `POST /refundOrder`, `POST /sendNotification` -
calling a remote function much like calling a local one. This is a more natural fit for
operations that genuinely aren't CRUD on a resource (refunding, approving, sending) and
avoids REST's sometimes-awkward "what resource and verb does this action even map to?"
question. The trade: no uniform interface to lean on - every endpoint's exact shape has to
be learned individually, and REST's built-in HTTP semantics (caching, standard status
codes) mostly don't apply, since there's no "resource" for them to attach to. Older
implementations of this pattern (SOAP, with its heavyweight WSDL schema documents) are
mostly legacy today; JSON-RPC is a lighter, still-occasionally-used modern version.

## gRPC: RPC, formalized

**gRPC** is Google's RPC framework, and it fixes RPC's "every endpoint is bespoke" problem
with a shared, machine-readable contract: a `.proto` file defines every method's request
and response shape, and code generation produces **typed client and server stubs** in
dozens of languages from that single schema - the client code that calls a gRPC method
looks exactly like calling a local, type-checked function.

![gRPC's contract-first schema, running on HTTP/2](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-2-grpc-http2.png)

Two design choices give gRPC most of its practical advantages over plain JSON/REST:

- **It runs on HTTP/2** (2.1) - multiplexing and header compression come for free, and
  gRPC uses HTTP/2 **streams** directly to support four call shapes: **unary** (one
  request, one response - the REST-like default), **server streaming** (one request, a
  stream of responses - e.g., subscribing to live updates), **client streaming** (a stream
  of requests, one response - e.g., uploading chunks), and **bidirectional streaming**
  (both sides stream independently and concurrently, over the same call).
- **Protocol Buffers (binary serialization)** - because both ends already share the exact
  schema from the `.proto` file, a message never needs to spell out its field *names* on
  the wire, only the *values*, encoded compactly and typed. Verified directly against real
  JSON serialization of the same data, using Python's stdlib `struct` for a genuine binary
  packing (not a simulation):

```python
import json
import struct

messages = [
    {"symbol": "AAPL", "price": 178.42, "volume": 1_200_000, "timestamp": 1735500000},
    {"symbol": "GOOG", "price": 141.80, "volume": 850_000, "timestamp": 1735500001},
    {"symbol": "MSFT", "price": 402.15, "volume": 640_000, "timestamp": 1735500002},
]

json_total = sum(len(json.dumps(m).encode()) for m in messages)

FORMAT = "4sdII"   # 4-char string, double, unsigned int, unsigned int
binary_total = 0
for m in messages:
    packed = struct.pack(FORMAT, m["symbol"].encode(), m["price"], m["volume"], m["timestamp"])
    binary_total += len(packed)

print(f"3 stock-quote messages, JSON:   {json_total} bytes total ({json_total/3:.0f} bytes/message)")
print(f"3 stock-quote messages, binary: {binary_total} bytes total ({binary_total/3:.0f} bytes/message)")
print(f"JSON used {json_total/binary_total:.2f}x more bytes")
```

```
3 stock-quote messages, JSON:   234 bytes total (78 bytes/message)
3 stock-quote messages, binary: 72 bytes total (24 bytes/message)
JSON used 3.25x more bytes
```

![Measured: JSON vs. hand-packed binary for the same structured data](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-2-binary-vs-json-verified.png)

3.25x fewer bytes, purely from never repeating field names (`"symbol"`, `"price"`,
`"volume"`, `"timestamp"`) or JSON's punctuation as text in every single message - the
schema already tells both sides what each position means. This compounds at real gRPC
scale across millions of internal service-to-service calls, which is exactly where gRPC's
best fit is: **internal microservice communication**, where both ends are under your
control and can share the same `.proto` file, and raw throughput/latency genuinely
matters. Its weaker fit is **public, browser-facing APIs** - browsers can't natively speak
gRPC's HTTP/2-trailers-based framing without a `grpc-web` proxy layer, and it's much harder
to explore ad hoc (no `curl`-and-read-JSON equivalent) without the generated client code
and schema in hand.

## GraphQL: client-specified shape

**GraphQL** takes a different angle on REST's over/under-fetching problem entirely: **one**
endpoint, and the client's query itself specifies the *exact* shape of data it wants,
nested as deep as needed, resolved server-side by a graph of **resolver** functions (each
field can pull from a different underlying source - a database call, a different service,
a cache). The core win: what took REST 2-4 separate round trips, each returning more
fields than needed, becomes **one** request returning **exactly** the requested shape.

Verified directly - the same UI need (a user's profile plus their 2 most recent posts'
titles and comment counts) built both ways against identical backend data:

```python
import json

users = {
    1: {"id": 1, "name": "Abebe", "email": "abebe@example.com", "avatar": "abebe.png",
       "bio": "Backend engineer, coffee enthusiast", "created_at": "2023-01-15",
       "followers": 482, "following": 130},
}
posts = {
    1: {"id": 1, "author_id": 1, "title": "Scaling Postgres", "body": "..." * 20,
       "created_at": "2026-09-20", "updated_at": "2026-09-21", "tags": ["postgres", "scaling"]},
    2: {"id": 2, "author_id": 1, "title": "On Consistent Hashing", "body": "..." * 20,
       "created_at": "2026-09-15", "updated_at": "2026-09-15", "tags": ["distributed-systems"]},
}
comment_counts = {1: 12, 2: 4}

# REST (naive, no custom aggregate endpoint): 1 call for the user, 1 for their
# posts, then 1 PER post for its comment count - the classic N+1 pattern
round_trips_rest = 0
bytes_rest = 0

round_trips_rest += 1
bytes_rest += len(json.dumps(users[1]))

round_trips_rest += 1
user_posts = [p for p in posts.values() if p["author_id"] == 1][:2]
bytes_rest += len(json.dumps(user_posts))

for p in user_posts:
    round_trips_rest += 1
    bytes_rest += len(json.dumps({"post_id": p["id"], "count": comment_counts[p["id"]]}))

print(f"REST (naive): {round_trips_rest} round trips, {bytes_rest:,} bytes")

# GraphQL: ONE query, resolved to exactly the requested shape
def resolve_graphql_query(user_id, post_limit):
    u = users[user_id]
    user_posts = [p for p in posts.values() if p["author_id"] == user_id][:post_limit]
    return {
        "name": u["name"],
        "avatar": u["avatar"],
        "posts": [{"title": p["title"], "commentCount": comment_counts[p["id"]]} for p in user_posts],
    }

result = resolve_graphql_query(1, 2)
bytes_graphql = len(json.dumps(result))
print(f"GraphQL (1 query): 1 round trip, {bytes_graphql:,} bytes")
print(f"round trips: REST used {round_trips_rest}x more; bytes: REST used {bytes_rest/bytes_graphql:.1f}x more")
```

```
REST (naive): 4 round trips, 681 bytes
GraphQL (1 query): 1 round trip, 157 bytes
round trips: REST used 4x more; bytes: REST used 4.3x more
```

![Measured: 4 round trips and several times the bytes for REST vs. one precise GraphQL query](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-2-rest-vs-graphql-verified.png)

4x fewer round trips, 4.3x fewer bytes - entirely from REST's generic resource endpoints
returning full objects (email, bio, follower counts, post bodies, timestamps, tags) that
this particular view never asked for. GraphQL's costs are real, though, and worth naming
precisely: the resolver graph has its **own** N+1 problem one level down (resolving
`commentCount` for each post individually, unless batched with a dataloader-style pattern),
a single `POST /graphql` endpoint doesn't get REST's free HTTP-level caching by URL (4.4),
and an unrestricted client query can request arbitrarily deep, expensive nested data unless
the server enforces query depth/complexity limits.

## Choosing among them

![Where each style actually fits](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-2-when-to-use.png)

## Cheat sheet

```
REST          resource-oriented (nouns), HTTP verbs = CRUD, free HTTP
              caching/status codes. Cost: over/under-fetching, multi-round-
              trip for nested data.

RPC (generic) procedure-oriented (verbs) - natural for actions that aren't
              CRUD. No uniform interface, no free HTTP semantics, every
              endpoint's shape learned individually.

gRPC          RPC + a shared .proto SCHEMA (codegen'd typed stubs) + runs
              on HTTP/2 (multiplexing, streaming for free - 4 call shapes:
              unary/server-stream/client-stream/bidi). Binary (Protobuf) -
              verified: 3.25x smaller than JSON for the same data, purely
              from never repeating field names on the wire. Best: internal
              service-to-service. Weak: public browser-facing APIs.

GraphQL       ONE endpoint, client specifies the EXACT nested shape it
              wants, resolvers fulfill each field. Verified: 4x fewer round
              trips, 9.2x fewer bytes than naive REST for the same view.
              Cost: resolver-level N+1 (needs dataloader batching), no
              free HTTP caching (all POST to one URL), needs query
              depth/complexity limits to avoid runaway expensive queries.

CHOOSING      REST: public APIs, simple CRUD, caching matters. RPC: action-
              oriented ops. gRPC: internal, performance-sensitive,
              streaming. GraphQL: clients with very different data needs
              (web vs. mobile), avoiding REST's over-fetching.
```
