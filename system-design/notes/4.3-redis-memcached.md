title: "4.3 Redis and Memcached deep dive"
---

4.1 named "remote cache" as one of the levels a system caches at. This note is what's
actually inside the two products that fill that role almost everywhere: Redis and
Memcached - what they store, how they survive a restart, how they decide what to evict
under memory pressure, and how a single instance becomes a fleet.

## Redis's data structures

Memcached (below) is deliberately a plain key-to-bytes store. Redis's defining feature is
that the **value** can be one of several real data structures, each with its own operations
- so the cache doesn't just store precomputed blobs, it can do useful work on the data
directly:

![Redis's core value types](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-3-redis-data-structures.png)

```python
import fakeredis
r = fakeredis.FakeStrictRedis(decode_responses=True)

r.set("user:42:name", "Abebe")
r.incr("page_views"); r.incr("page_views")
print("STRING  :", r.get("user:42:name"), "| page_views =", r.get("page_views"))

r.hset("user:42", mapping={"name": "Abebe", "age": "30", "city": "Addis Ababa"})
r.hincrby("user:42", "age", 1)          # increment ONE field, no read-modify-write
print("HASH    :", r.hgetall("user:42"))

r.sadd("post:9:likes", "user:1", "user:2", "user:3")
r.sadd("post:9:likes", "user:2")        # duplicate, no-op
print("SET     :", sorted(r.smembers("post:9:likes")), "| count =", r.scard("post:9:likes"))

r.zadd("leaderboard", {"alice": 120, "bob": 95, "carol": 150})
print("ZSET    : top-2 =", r.zrevrange("leaderboard", 0, 1, withscores=True))

r.rpush("recent_notifications:42", "liked your post", "started following you")
r.lpush("recent_notifications:42", "commented on your photo")
print("LIST    :", r.lrange("recent_notifications:42", 0, -1))

r.set("session:abc", "logged-in", ex=1)
print("TTL     : session ttl =", r.ttl("session:abc"), "seconds")
```

```
STRING  : Abebe | page_views = 2
HASH    : {'name': 'Abebe', 'age': '31', 'city': 'Addis Ababa'}
SET     : ['user:1', 'user:2', 'user:3'] | count = 3
ZSET    : top-2 = [('carol', 150.0), ('alice', 120.0)]
LIST    : ['commented on your photo', 'liked your post', 'started following you']
TTL     : session ttl = 1 seconds
```

- **String** - the baseline: a key to a blob (a serialized profile, a rendered page
  fragment) or a number, with atomic increment (`INCR`) built in - the mechanism 4.2's
  stampede lock leaned on via `SET ... NX`.
- **Hash** - a key to a set of field-value pairs, like a row without needing a real
  database - and critically, `HINCRBY` updates *one field* atomically without reading the
  whole hash out, modifying it, and writing it back.
- **Set** - unordered unique members, with real set operations (union, intersection,
  difference) available server-side.
- **Sorted set (ZSET)** - members with a score, kept in sorted order automatically. This is
  *the* leaderboard and ranking data structure - "top 10 by score" and "this user's rank"
  are both native operations, not something you'd otherwise build by hand on top of a
  string/hash.
- **List** - ordered, push/pop from either end in O(1) - a queue, a capped recent-activity
  feed, a simple work queue.

Every key of any type can carry a **TTL**, independent of its type - the same expiry
mechanism 4.1 and 4.2 build the whole cache-aside/stampede story on top of.

## Persistence

A pure in-memory store loses everything on a crash or restart - fine for some caches
(rebuild from the source of truth on the next miss), not fine for others (a queue whose
contents are the only copy of some work). Redis offers two, often combined:

![RDB vs AOF persistence](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-3-persistence.png)

- **RDB (snapshotting)** - periodically write a full point-in-time snapshot of the dataset
  to disk. Compact, fast to load on restart (read one file), but a crash between snapshots
  loses everything written since the last one.
- **AOF (append-only file)** - log every write operation as it happens, the same idea as a
  database's write-ahead log (3.1). Much smaller loss window (configurable how often it
  `fsync`s - as aggressively as every write), at the cost of a bigger file and slower
  replay on restart, since recovering means replaying the whole log.

Most production Redis deployments run both: RDB for fast full backups and quick restarts,
AOF layered on top to shrink the loss window - the exact same durability-vs-speed spectrum
3.5 covers for database replication, one layer over.

## Eviction policies

Once `maxmemory` is set, Redis needs a policy for what happens when it's reached -
configured directly, using the algorithms from 4.1:

- `noeviction` - refuse new writes with an error once full. The right choice when Redis is
  being used as more than a cache (a queue, primary storage for something) and silently
  losing data would be worse than a write failing loudly.
- `allkeys-lru` / `volatile-lru` - evict by LRU, either across all keys or restricted to
  keys that have a TTL set (`volatile-*` never touches keys meant to be permanent).
- `allkeys-lfu` / `volatile-lfu` - evict by (approximate) LFU instead.
- `allkeys-random` / `volatile-random` - evict a random key.
- `volatile-ttl` - evict whichever key is closest to expiring anyway.

This is 4.1's eviction-algorithm comparison, exposed as a one-line configuration choice
rather than something you implement yourself.

## Memcached

Deliberately simpler than Redis: pure key-to-byte-string, nothing else - no hashes, no
sorted sets, no persistence, no built-in replication. What it optimizes for instead is raw
throughput on that one simple operation, using a genuinely multi-threaded design (Redis is
famously single-threaded for command execution per core, trading away multi-core
parallelism for the simplicity of never needing locks around data access).

![Memcached's slab allocator](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-3-memcached-slabs.png)

Internally, Memcached manages its memory with **slab allocation** - exactly 4.7's slab
allocator, not just a similar idea: items are rounded up to the nearest of a set of
pre-defined size classes (growing by a fixed factor, e.g. ~1.25x, from roughly 96 bytes up),
and each class has its own pool of fixed-size slabs. This is precisely why Memcached
doesn't fragment under constant same-ish-sized churn the way a general-purpose allocator
would (4.7's fit algorithms and the 50% rule) - it sidesteps the problem the same way the
kernel does for its own frequently-allocated structs.

**Redis vs. Memcached, practically:** reach for Memcached when the need is genuinely just
"a very fast, very simple, multi-threaded key-value cache" and nothing else. Reach for
Redis when you want richer data structures used *as* the cache (leaderboards, rate limiters
built on `INCR`+TTL, dedup sets), need persistence, or want built-in replication/clustering
- which, in practice, is most of the time, and is why Redis has become the default choice
even for workloads that don't strictly need anything beyond plain key-value.

## Scaling a cache tier

A cache is, structurally, extremely similar to a database once it's big enough to need more
than one machine - so it scales the same two ways 3.4 already covered:

![Scaling a cache: vertical vs. horizontal](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-3-scaling-cache.png)

- **Vertical** - a bigger single instance, more RAM, more CPU. Simple, has a ceiling, same
  trade-offs as 3.4's vertical scaling in general.
- **Horizontal** - shard across multiple instances (Redis Cluster, or client-side
  consistent hashing across a pool of instances), each shard usually *also* replicated
  (3.5) for its own availability. This comes with the same real cost 3.4 named for sharding
  a database: cross-shard operations - a multi-key transaction, a `SUNION` or `ZINTERSTORE`
  spanning keys that land on different shards - get much harder or outright unsupported,
  because there's no single node holding all the data anymore.

## Cheat sheet

```
REDIS         string (blobs, INCR) - hash (fields, HINCRBY without read-modify-
DATA TYPES    write) - set (membership, set algebra) - sorted set / ZSET (THE
              leaderboard/ranking structure, sorted by score, native rank
              queries) - list (O(1) push/pop either end - queues, feeds).
              Every key of any type can carry a TTL.

PERSISTENCE   RDB: periodic full snapshot, fast restart, loses everything since
              the last snapshot on crash. AOF: logs every write (like a WAL) -
              smaller loss window, bigger file, slower replay. Production:
              usually both together.

EVICTION      maxmemory-policy = 4.1's algorithms as a config flag:
              noeviction / allkeys-lru / volatile-lru / allkeys-lfu /
              volatile-lfu / allkeys-random / volatile-random / volatile-ttl.
              volatile-* only ever touches keys that HAVE a TTL set.

MEMCACHED     pure key->bytes, nothing else. Multi-threaded (vs Redis's per-
              core single-threaded command execution). Internally uses SLAB
              allocation (4.7, literally) - size-classed slabs, no
              fragmentation under constant same-ish-sized churn.
              Redis vs Memcached: reach for Memcached for raw simple
              throughput only; reach for Redis for data structures,
              persistence, or built-in clustering (most of the time).

SCALING       vertical (bigger instance) vs horizontal (shard + replicate,
              3.4 + 3.5's ideas applied to a cache tier). Cost of sharding a
              cache: cross-shard multi-key ops (transactions, set algebra
              spanning shards) get hard or impossible - same trade-off 3.4
              already named for databases.
```
