---
title: "3.8 CDC, event sourcing, CQRS"
---

3.7's transactional outbox pattern ended with "a relay reads the outbox table and publishes
it - or, better, a CDC connector reads the WAL directly." This note is that "better" option,
and the two architectural ideas that follow naturally once you have a reliable stream of
every change your database makes: treat that stream as the source of truth (event sourcing)
and use it to build read-optimized copies of your data (CQRS).

## Change Data Capture (CDC)

The idea: instead of asking application code to *also* publish an event every time it
writes to the database (easy to forget, and exactly the dual-write problem 3.7's outbox
pattern exists to avoid), read the **change stream the database already produces for
itself** - its write-ahead log (3.1) or binlog - and turn that into an event stream nothing
had to be told to create.

![CDC architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-8-cdc-architecture.png)

This is not a simulation - it's exactly what a real CDC connector does, demonstrated here
with Postgres's own logical replication slot (the same underlying mechanism as 3.5's
physical replication, decoding into row-level events instead of raw WAL bytes; tools like
Debezium wrap this same primitive in production):

```python
from setup import pg_conn

conn = pg_conn(); cur = conn.cursor()
cur.execute("CREATE TABLE orders_cdc (id INT PRIMARY KEY, status TEXT)")
conn.commit()

cur.execute("SELECT pg_create_logical_replication_slot('cdc_demo', 'test_decoding')")
print("created a logical replication slot reading this database's WAL")

# ordinary application writes - no CDC-aware code here at all
cur.execute("INSERT INTO orders_cdc VALUES (1, 'pending')")
cur.execute("INSERT INTO orders_cdc VALUES (2, 'pending')")
cur.execute("UPDATE orders_cdc SET status = 'shipped' WHERE id = 1")
cur.execute("DELETE FROM orders_cdc WHERE id = 2")
conn.commit()

cur.execute("SELECT data FROM pg_logical_slot_get_changes('cdc_demo', NULL, NULL)")
print("\nCDC stream pulled straight off the WAL:")
for (line,) in cur.fetchall():
    print(" ", line)

cur.execute("SELECT pg_drop_replication_slot('cdc_demo')")
```

```
created a logical replication slot reading this database's WAL

CDC stream pulled straight off the WAL:
  BEGIN 975
  table public.orders_cdc: INSERT: id[integer]:1 status[text]:'pending'
  table public.orders_cdc: INSERT: id[integer]:2 status[text]:'pending'
  table public.orders_cdc: UPDATE: id[integer]:1 status[text]:'shipped'
  table public.orders_cdc: DELETE: id[integer]:2
  COMMIT 975
```

(The `975` next to `BEGIN`/`COMMIT` is just this transaction's ID - it'll be a different
number on any given run, including yours; the four row-level events themselves are the
part that's always exactly this shape.) Every one of those four writes shows up as an
event, with no outbox table, no dual write,
and no application code aware that anything is watching. Because it reads the WAL - the
same durable record a database already needs for crash recovery (3.1) and physical
replication (3.5) - CDC captures a change if and only if that change actually committed,
which is exactly the guarantee a hand-rolled "publish after write" approach struggles to give
you without help from a pattern like 3.7's outbox.

## Event sourcing: the log as the source of truth

CDC derives a change stream *from* a database that stores current state as its primary
model. **Event sourcing** flips that: the append-only sequence of events **is** the
database - current state is never stored directly, it's *derived* by replaying (folding
over) the events:

![Event sourcing](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-8-event-sourcing.png)

`AccountOpened(balance=0)`, `Deposited(+100)`, `Withdrew(-30)`, `Deposited(+50)` - the
current balance, 120, isn't stored anywhere; it's `0 + 100 - 30 + 50`, recomputed (or
computed incrementally and cached) from the log. What this buys you:

- **A complete, exact audit trail**, for free - it's not a bolt-on feature, it's the only
  thing that exists.
- **Time travel** - the state at any prior point is just "fold the events up to there."
- **Rebuildability** - a bug in how you *project* state from events is fixable by fixing the
  projection and replaying; the underlying facts (the events) are never lost or overwritten.

The costs, equally real: **replay time** grows with history (mitigated with periodic
snapshots - store "balance was 120 as of event #4," then only replay events after that), and
**event schemas live forever** - you can never delete or restructure an old event type the
way you might refactor a column, because doing so breaks the ability to replay history
correctly; you version events and teach your replay logic to handle every version that ever
shipped.

## CQRS: separate models for writing and reading

**Command Query Responsibility Segregation** takes the write side (normalized, optimized
for correctness - a relational schema or an event-sourced log) and the read side
(denormalized, optimized for whatever a specific query needs) and makes them **two
genuinely different models**, connected by a change stream instead of being the same
tables:

![CQRS](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-8-cqrs.png)

A write updates the write model; CDC (or the event log directly, if you're also doing event
sourcing) carries that change to one or more **read models** - materialized views shaped
exactly for a query pattern, maintained incrementally as changes arrive. This is precisely
what 9.5's rollup tables and 3.3's covering indexes are doing in miniature - CQRS is that
same idea promoted to a full architectural pattern: don't force one schema to serve every
query well, maintain several, each shaped for its own use.

## Trade-offs and pitfalls

- **Eventual consistency between write and read models, by design.** A read immediately
  after a write can miss it - the same read-your-writes anomaly from 3.5's replication-lag
  discussion, here between your write model and your read models instead of between DB
  replicas. If a user needs to see their own write immediately, read that specific case from
  the write model directly, not the (lagging) read model.
- **Two things to keep in sync, operationally**, where there used to be one - more
  infrastructure (the connector/pipeline), more to monitor (pipeline lag), and a real
  category of bugs where the read model silently drifts from the write model and nobody
  notices until a user reports stale data.
- **Event/schema versioning is a permanent tax**, not a one-time migration - every consumer
  of the stream needs to keep handling every event shape that was ever produced, forever (or
  you invest in an explicit event-upcasting layer to translate old shapes to new ones on
  read).
- **Don't reach for event sourcing by default.** It's the right tool when the audit trail
  and time-travel are genuinely part of the requirements (financial ledgers, inventory
  history, anything regulators ask "prove what happened and when" about) - not as a default
  architecture for every write path, because the replay/versioning costs are real and
  compound over the system's lifetime.

## Cheat sheet

```
CDC           read the DB's OWN WAL/binlog -> row-level change events, with no
              application code aware anything is watching. Captures a change
              iff it actually committed (verified live: 4 ordinary writes -
              2 inserts, an update, a delete - captured off a real Postgres
              logical replication slot with zero CDC-aware app code).
              Standard tool: Debezium, wrapping this same primitive.

EVENT         the append-only event log IS the database; current state =
SOURCING      fold(events), not stored directly. Gains: full audit trail,
              time travel, rebuildable projections. Costs: replay time
              (mitigate with snapshots), event schemas must stay readable
              forever.

CQRS          write model (normalized, correctness) and read model(s)
              (denormalized, one shape per query) as genuinely separate
              models, connected by a change stream (CDC or the event log).
              Same idea as a materialized rollup table (9.5) or a covering
              index (3.3), promoted to a full architecture.

PITFALLS      eventual consistency write<->read, by design (route a user's
              own immediate reads to the write model if needed) - more
              infra to keep in sync and monitor for silent drift - schema
              versioning is forever, not a one-time cost - don't default to
              event sourcing; use it where the audit trail is an actual
              requirement, not a default architecture.
```
