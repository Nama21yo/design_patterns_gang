---
title: "4.2 Cache invalidation and stampede protection"
---

"There are only two hard things in Computer Science: cache invalidation and naming things"
is a joke with a real point behind it - deciding *when* a cached value stops being trustworthy
is genuinely one of the trickiest parts of caching, and getting it wrong produces two
opposite failure modes: serve stale data forever, or thrash the source of truth every time a
value expires. This note is both problems, and the standard fixes.

## Invalidation strategies

![Invalidation strategies](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-2-invalidation-strategies.png)

- **TTL (time-to-live) expiry** - every cache entry just times out after a fixed duration.
  No coordination needed between the writer and the cache at all - simplicity is the whole
  appeal - at the cost of a bounded but real staleness window: readers can see old data for
  up to the TTL's duration, every time.
- **Explicit invalidation on write** - the code path that changes the underlying data also
  deletes (or updates) the corresponding cache entry, directly. Fresher - there's no window
  where the cache is known-stale-but-not-yet-expired - but it means every place data can be
  written now has a second responsibility (remembering to invalidate the right keys), and
  missing one is a real, easy-to-introduce class of bug in a large codebase.
- **Versioned keys / content-hash keys** - instead of updating or deleting an entry in
  place, key the cache by a version number or content hash that changes whenever the
  underlying data does (`profile:42:v7`). Old versions simply stop being referenced by
  anything and age out via normal eviction (4.1) - no explicit delete step needed, and
  every cache read either gets a fully current value or a clean miss, never a half-updated
  one.

None of these are mutually exclusive - a common real setup uses explicit invalidation on
write as the primary mechanism, with a TTL as a safety net in case an invalidation is ever
missed.

## Cache stampede (thundering herd)

A specific, sharp failure mode: a **single hot key expires**, and every one of the (possibly
thousands of) concurrent requests that were relying on it all take a cache miss at
**exactly the same moment** - and all of them independently go recompute the same value
from the database, simultaneously. The cache, which exists specifically to protect the
database from load, momentarily does the opposite: it synchronizes a flood of identical
requests onto it.

Proven live - 30 concurrent requests hitting a cold key, naive cache-aside vs. a
lock-protected version, using real threads and a real Redis-protocol client (`fakeredis`,
so `SETNX`'s atomicity guarantee is the genuine thing, not a simulation):

```python
import fakeredis
import threading
import time

r = fakeredis.FakeStrictRedis(decode_responses=True)
db_call_count = [0]
db_lock = threading.Lock()

def expensive_db_query():
    with db_lock:
        db_call_count[0] += 1
    time.sleep(0.05)
    return "profile-data-v1"

def naive_cache_aside(key):
    val = r.get(key)
    if val is not None:
        return val
    val = expensive_db_query()      # EVERY concurrent miss does this
    r.set(key, val, ex=5)
    return val

def stampede_protected(key):
    val = r.get(key)
    if val is not None:
        return val
    lock_key = f"lock:{key}"
    got_lock = r.set(lock_key, "1", nx=True, ex=2)   # only one requester wins
    if got_lock:
        val = expensive_db_query()
        r.set(key, val, ex=5)
        r.delete(lock_key)
        return val
    for _ in range(20):             # everyone else: wait briefly, then read
        time.sleep(0.01)
        val = r.get(key)
        if val is not None:
            return val
    return expensive_db_query()     # fallback if the lock-holder somehow got stuck

def run_concurrent(fn, key, n=30):
    threads = [threading.Thread(target=fn, args=(key,)) for _ in range(n)]
    for t in threads: t.start()
    for t in threads: t.join()

db_call_count[0] = 0
run_concurrent(naive_cache_aside, "profile:naive")
print(f"naive: database was hit {db_call_count[0]} times for one logically-single value")

db_call_count[0] = 0
run_concurrent(stampede_protected, "profile:protected")
print(f"protected: database was hit {db_call_count[0]} time(s) for one logically-single value")
```

```
naive: database was hit 30 times for one logically-single value
protected: database was hit 1 time(s) for one logically-single value
```

![Measured: 30 concurrent misses, naive vs. lock-protected](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-2-stampede-before-after.png)

The fix is **request coalescing** via a short-lived lock:

![The SETNX-lock stampede fix](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-2-stampede-lock-flow.png)

On a miss, every requester tries to atomically create a short-TTL lock key
(`SET lock:key 1 NX EX 2` - "set if not exists"). Exactly one of them succeeds, by Redis's
own single-threaded, atomic command execution - there's no race window where two requesters
both think they got the lock. The winner does the expensive work and populates the real
cache entry; everyone else, having failed to get the lock, knows someone else is already
handling it, so they wait briefly and re-read the cache instead of also hitting the
database. The lock's own short TTL is a safety valve: if the winner crashes mid-computation,
the lock expires on its own and the next request through takes over, instead of every
future request being stuck waiting on a lock nobody will ever release.

## Negative caching

The mirror-image gap in a naive cache-aside implementation: if a lookup for a key that
**doesn't exist** always takes the slow path (there's nothing to cache, so why would you
cache "nothing"), then repeated lookups for the same missing key - which happens more than
it sounds like it should: a scraper probing invalid IDs, a client with a stale reference,
one broken integration retrying the same bad key forever - hit the database every single
time, with no cache protecting it at all.

![Negative caching and stale-while-revalidate](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-2-negative-caching-swr.png)

**Negative caching** fixes this by caching the *absence* too - store a short-TTL "not
found" marker for a missing key, the same way you'd cache a real value, so repeat lookups
for the same missing key hit the cache (and get a fast, correct "not found") instead of the
database. Short TTL matters here specifically because the underlying data *can* start
existing later (the record gets created) - too long a negative-cache TTL means a real,
newly-created record looks like it doesn't exist for longer than it should.

## Stale-while-revalidate

A softer alternative to a hard TTL cutoff: when an entry expires, **serve the stale value
immediately** to the requester that triggered the miss, while kicking off a background
refresh for next time - rather than making that one unlucky requester wait for a fresh
fetch. Trades a small, bounded amount of extra staleness (one request's worth) for
consistently fast responses, with no request ever paying the full "recompute from scratch"
latency synchronously. This is also a natural second layer of stampede protection layered
on top of the lock from above: even a request that "loses" the lock race and would
otherwise wait can instead be served the previous value immediately, at the cost of one
generation's worth of extra staleness.

## Cheat sheet

```
INVALIDATION  TTL expiry: simple, no coordination, bounded staleness window.
STRATEGIES    Explicit on write: fresher, but every write path now owns
              invalidating the right keys - a real bug surface.
              Versioned/content-hash keys: old versions just age out via
              normal eviction, no explicit delete, no half-updated reads.
              (Commonly combined: explicit invalidation + a TTL safety net.)

STAMPEDE      a hot key expires -> every concurrent request misses at once ->
(THUNDERING   all of them hit the DB simultaneously for the SAME value.
HERD)         Verified: 30 concurrent requests, naive = 30 DB hits.
              Fix - request coalescing via a short-TTL SETNX lock: exactly one
              requester recomputes, the rest wait briefly and read the now-
              fresh cache. Verified: 30 concurrent requests, protected = 1 DB
              hit. Lock's own short TTL prevents a crashed winner from
              blocking everyone forever.

NEGATIVE      cache "not found" too (short TTL) - otherwise repeated lookups
CACHING       for a key that doesn't exist bypass the cache on EVERY request.

STALE-WHILE-  on expiry, serve the stale value immediately, refresh in the
REVALIDATE    background for next time - no request pays the full recompute
              cost synchronously; a second layer of stampede protection.
```
