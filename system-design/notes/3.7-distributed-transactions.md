---
title: "3.7 Distributed transactions"
---

3.2 built ACID transactions on the assumption that a transaction touches one database.
3.4's sharding and any multi-service architecture break that assumption immediately: an
order might need to debit one shard's inventory row and credit another shard's payment row,
or update one microservice's database and notify another's, and you still want "both happen
or neither does." This note is what's available once a single local `COMMIT` can't give you
that anymore.

## Two-phase commit (2PC)

The direct extension of ACID atomicity across multiple participants. A **coordinator**
drives two rounds:

![Two-phase commit and its blocking problem](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-7-two-phase-commit.png)

1. **Prepare** - the coordinator asks every participant "can you commit?" Each participant
   does everything short of actually committing - acquires locks, writes to its own durable
   log - and replies YES (it's guaranteed able to commit now, no matter what) or NO.
2. **Commit or abort** - if every participant voted YES, the coordinator tells everyone to
   commit; if any voted NO, it tells everyone to abort.

The failure mode that makes this a genuinely hard primitive to depend on: **if the
coordinator crashes after collecting votes but before sending the phase-2 decision**, every
participant that voted YES is stuck. It can't unilaterally commit (the coordinator might
have decided to abort because of someone else's NO) and it can't unilaterally abort (the
coordinator might have already told other participants to commit) - it has to hold its
locks and wait, indefinitely, until the coordinator recovers.

This is provable, not just a theoretical worry - Postgres exposes the actual primitives
(`PREPARE TRANSACTION` / `COMMIT PREPARED`) used to build 2PC, and the blocking behavior is
exactly as described:

```python
from setup import pg_conn

conn = pg_conn(); cur = conn.cursor()
cur.execute("CREATE TABLE accounts2 (id INT PRIMARY KEY, balance INT)")
cur.execute("INSERT INTO accounts2 VALUES (1, 500)")
conn.commit()

# --- Participant: debit account 1, then PREPARE (phase 1) ---
partA = pg_conn()
ca = partA.cursor()
ca.execute("BEGIN")
ca.execute("UPDATE accounts2 SET balance = balance - 100 WHERE id = 1")
ca.execute("PREPARE TRANSACTION 'txn_42_debit'")
print("Participant: voted YES, PREPARED (this row's lock is now held INDEFINITELY)")

print("\n*** coordinator crashes after collecting votes, before phase 2 ***\n")

# --- an unrelated transaction tries to touch the same row ---
other = pg_conn(); co = other.cursor()
co.execute("SET lock_timeout = '500ms'")
try:
    co.execute("UPDATE accounts2 SET balance = balance - 1 WHERE id = 1")
except Exception as e:
    print("A completely unrelated transaction touching the SAME row:")
    print(" ", str(e).strip().splitlines()[0])
other.rollback()

cur.execute("SELECT gid FROM pg_prepared_xacts")
print("\npg_prepared_xacts (this survives even a full Postgres restart):", cur.fetchall())

print("\n*** coordinator recovers, replays its log, finishes phase 2 ***")
recovered = pg_conn()
recovered.autocommit = True
recovered.cursor().execute("COMMIT PREPARED 'txn_42_debit'")
print("COMMIT PREPARED issued - lock released, transaction finally finalized")

cur.execute("SELECT balance FROM accounts2 WHERE id = 1")
print("final balance:", cur.fetchone()[0])
```

```
Participant: voted YES, PREPARED (this row's lock is now held INDEFINITELY)

*** coordinator crashes after collecting votes, before phase 2 ***

A completely unrelated transaction touching the SAME row:
  canceling statement due to lock timeout

pg_prepared_xacts (this survives even a full Postgres restart): [('txn_42_debit',)]

*** coordinator recovers, replays its log, finishes phase 2 ***
COMMIT PREPARED issued - lock released, transaction finally finalized
final balance: 400
```

Notice the prepared transaction genuinely blocked an unrelated update on the same row until
a timeout kicked in, and it would have blocked *forever* with no timeout - held locks,
consuming resources, for however long the coordinator stays down. That's the real,
measurable cost of 2PC: it buys atomicity across participants at the price of an
availability risk on every participant, tied to the coordinator's uptime.

## Three-phase commit (3PC)

An attempt to fix 2PC's blocking by inserting an extra round between prepare and commit:

![Three-phase commit](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-7-three-phase-commit.png)

The **PreCommit** phase tells every participant "everyone has voted YES, we ARE going to
commit" before anyone actually commits. The payoff: a participant that times out waiting for
the coordinator, having already received PreCommit, knows the outcome and can safely
proceed to commit on its own - it no longer has to sit and wait indefinitely the way plain
2PC requires. In practice 3PC is rarely deployed: it still fails to fully resolve blocking
under a network **partition** (as opposed to a clean crash, which is the easier case), and
it pays a real, permanent latency tax - one more network round trip on *every single
transaction* - for a problem that most systems solve a different way entirely: not blocking
better, but avoiding cross-participant atomicity as a requirement in the first place. Which
is what the rest of this note is about.

## Sagas: give up atomicity, get compensating actions instead

A **saga** breaks one logical multi-step transaction into a sequence of independent local
transactions, each committing on its own - and if a later step fails, it doesn't roll back
the earlier ones (they already committed, for real, elsewhere), it runs **compensating
actions** that undo their effect with new, separate transactions:

![Saga pattern](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-7-saga-pattern.png)

Create an order (commits), charge a payment (commits), reserve shipping (fails) -> run
compensations in reverse: refund the payment (a new transaction, not an undo), cancel the
order (another new transaction). Two ways to coordinate this:

- **Orchestration** - one saga-coordinator service explicitly calls each step and, on
  failure, explicitly calls the matching compensations, in order. Easy to see the whole flow
  in one place; that coordinator is a new component to build and (though not for
  correctness the way 2PC's coordinator is) operate.
- **Choreography** - no central coordinator. Each service reacts to the previous step's
  event and publishes its own, compensations included, entirely through the event stream
  (3.8). No single point of control or failure, but the overall business process is now
  implicit - scattered across every service's event handlers, with no one place to read "the
  saga" end to end.

The trade sagas make explicit: you give up true cross-service atomicity (there's a real
window where the order exists but the payment hasn't succeeded yet) in exchange for never
holding cross-service locks and never depending on a coordinator's uptime to release them -
the direct opposite trade from 2PC.

## Transactional outbox

A narrower, extremely common version of the same underlying problem: **write a row to your
database and publish an event about it to a queue, atomically** - so that a crash between
the two never leaves you with a committed row and a message nobody ever sent (or a sent
message for a write that got rolled back).

![Transactional outbox pattern](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-7-transactional-outbox.png)

The fix needs no distributed transaction at all: write the actual row **and** an "outbox"
row describing the event, in the *same local transaction*, to the *same database*. Ordinary
ACID atomicity (3.2) already guarantees both happen or neither does. A separate relay
process - polling the outbox table, or, more efficiently, a CDC connector reading the WAL
directly (3.8, and note this is the same mechanism 3.8's whole architecture is built on) -
picks up new outbox rows and publishes them to the real queue, marking them done once
published.

The remaining gap: the relay can crash *after* publishing but *before* marking a row done,
and will publish that row again on restart - **at-least-once delivery**, not exactly-once.
Which is exactly why the pattern only works paired with the next one.

## Idempotent consumers

If delivery can duplicate a message (the outbox relay above, Kafka's default guarantees,
any retry-on-timeout client), the only way to get correct behavior is to make **processing**
a duplicate message safe, rather than trying to eliminate duplicates at the transport layer
(which, per FLP's practical shadow, you can't fully do anyway). The standard technique: give
every message/event a unique idempotency key, and have the consumer check-and-record that
key as part of the same transaction that does the actual work - "have I already processed
`event_id=abc123`? If yes, skip. If no, process it and record `abc123` as done, atomically."
This single discipline is what turns "at least once" delivery into what applications
actually need: **effectively once**. It's the same idea as the client-supplied idempotency
key from Part 2.4, applied specifically to the consumer side of an async pipeline.

## Cheat sheet

```
2PC           prepare (everyone votes YES/NO, locks held, nobody commits yet)
              -> commit or abort (coordinator's decision, broadcast to all).
              BLOCKING PROBLEM: coordinator crashes after votes, before phase 2
              -> every YES-voter holds its locks INDEFINITELY (proven: a real
              Postgres PREPARE TRANSACTION blocked an unrelated update until
              a timeout, and would block forever with none).

3PC           adds PreCommit between prepare and commit, so a timed-out
              participant that got PreCommit can safely proceed alone.
              Reduces (doesn't eliminate) blocking; still fails under a
              partition; permanent extra round-trip cost. Rarely used.

SAGAS         sequence of independent LOCAL transactions, each commits for
              real. Failure -> COMPENSATING actions (new transactions), not
              rollback. Orchestration (central coordinator, explicit flow) vs
              choreography (event-reactive, no single point of failure, but
              implicit flow). Trade: no cross-service locks, but a real
              window of partial completion - the opposite trade from 2PC.

OUTBOX        write the row + an outbox row in ONE local ACID transaction ->
              a relay (poller or CDC) publishes outbox rows to the real
              queue. Solves "DB write + publish, atomically" with zero
              distributed transactions. Gives at-least-once delivery.

IDEMPOTENT    at-least-once delivery + a dedup/idempotency key checked in the
CONSUMERS     same transaction as the work = effectively-once. The only
              practical way to get exactly-once BEHAVIOR without exactly-once
              DELIVERY (which distributed systems generally can't guarantee).
```
