---
title: "2.6 Fault tolerance patterns"
---

2.5's load balancer routes around a **dead** instance easily - a failed health check just
removes it from rotation. The harder case is a dependency that isn't dead, just **slow or
overwhelmed**: still technically responding, still technically "up," but degrading every
caller that keeps hitting it. This note is the pattern that stops one struggling service
from taking the rest of the system down with it, plus four related patterns that round out
the resiliency toolkit.

## The problem: cascading failure

Take a feed system where the feed service calls a profile service to enrich each post with
author info. The profile service gets overwhelmed - every call now times out instead of
failing outright, which is *worse* than an outright failure, because nothing stops the feed
service from keep trying, keep waiting, keep tying up its own threads/connections for the
duration of every timeout.

![One overwhelmed dependency propagating slowness upstream through every caller](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-6-cascading-failure.png)

The feed service, now full of threads stuck waiting on the profile service, becomes slow
itself. Whatever calls the feed service (an API gateway, another service) now backs up
waiting on *it*. One overwhelmed dependency, left unchecked, propagates its slowness
upstream through every single caller in the chain - this is **cascading failure**, and it's
exactly the failure mode a healthy-looking `200 OK` (just a slow one) can trigger that a
clean crash wouldn't, since a crash at least fails fast.

## Circuit breaker

The fix: track failures per downstream dependency, and once they cross a threshold, **stop
calling it entirely** for a while - fail fast instead, without ever touching the
overwhelmed service. A 3-state machine:

![Circuit breaker: closed -> open -> half-open -> closed](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-6-circuit-breaker-states.png)

- **Closed** - normal operation, calls pass through, failures are counted.
- **Open** - failure count crossed the threshold; every call fails immediately without
  contacting the downstream service at all.
- **Half-open** - after a recovery timeout, let exactly **one** trial request through. If it
  succeeds, close the breaker (assume recovery); if it fails, reopen and wait again.

Implemented and verified against a simulated overwhelmed profile service:

```python
import time


class CircuitBreaker:
    CLOSED, OPEN, HALF_OPEN = "CLOSED", "OPEN", "HALF_OPEN"

    def __init__(self, failure_threshold=3, recovery_timeout=1.0):
        self.state = self.CLOSED
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.opened_at = None

    def call(self, fn, *args):
        if self.state == self.OPEN:
            if time.time() - self.opened_at >= self.recovery_timeout:
                self.state = self.HALF_OPEN
            else:
                raise RuntimeError("circuit OPEN - failing fast, not calling downstream")

        try:
            result = fn(*args)
        except Exception:
            self.failure_count += 1
            if self.state == self.HALF_OPEN or self.failure_count >= self.failure_threshold:
                self.state = self.OPEN
                self.opened_at = time.time()
            raise
        else:
            self.failure_count = 0
            self.state = self.CLOSED
            return result


class ProfileService:
    def __init__(self):
        self.calls_attempted = 0
        self.is_overwhelmed = True

    def get_profile(self, user_id):
        self.calls_attempted += 1
        if self.is_overwhelmed:
            raise TimeoutError("profile service timed out")
        return {"user_id": user_id, "name": "Abebe"}


profile_svc = ProfileService()
breaker = CircuitBreaker(failure_threshold=3, recovery_timeout=0.3)

for i in range(6):
    try:
        breaker.call(profile_svc.get_profile, f"user_{i}")
        print(f"request {i}: succeeded, breaker={breaker.state}")
    except TimeoutError:
        print(f"request {i}: profile service timed out, breaker={breaker.state}, "
             f"failure_count={breaker.failure_count}")
    except RuntimeError as e:
        print(f"request {i}: {e}, breaker={breaker.state}")

print(f"\ntotal calls that actually reached the profile service: "
     f"{profile_svc.calls_attempted} out of 6 requests")

profile_svc.is_overwhelmed = False
time.sleep(0.35)
result = breaker.call(profile_svc.get_profile, "user_99")
print(f"\nhalf-open trial request: succeeded -> {result}, breaker={breaker.state}")

result2 = breaker.call(profile_svc.get_profile, "user_100")
print(f"next request after recovery: succeeded -> {result2}, breaker={breaker.state}")
```

```
request 0: profile service timed out, breaker=CLOSED, failure_count=1
request 1: profile service timed out, breaker=CLOSED, failure_count=2
request 2: profile service timed out, breaker=OPEN, failure_count=3
request 3: circuit OPEN - failing fast, not calling downstream, breaker=OPEN
request 4: circuit OPEN - failing fast, not calling downstream, breaker=OPEN
request 5: circuit OPEN - failing fast, not calling downstream, breaker=OPEN

total calls that actually reached the profile service: 3 out of 6 requests

half-open trial request: succeeded -> {'user_id': 'user_99', 'name': 'Abebe'}, breaker=CLOSED
next request after recovery: succeeded -> {'user_id': 'user_100', 'name': 'Abebe'}, breaker=CLOSED
```

Only 3 of 6 requests ever reached the (overwhelmed) profile service - the breaker opened
after the 3rd failure and the remaining 3 requests failed fast, with zero additional load
placed on the already-struggling dependency. Once the dependency actually recovered and the
recovery timeout elapsed, a single half-open trial request succeeded and the breaker closed
itself automatically, with no manual intervention. This is exactly what stops the chain
from 2.6's opening example: the feed service's threads stop piling up waiting on a
dependency that was never going to answer in time anyway.

## The rest of the toolkit

Circuit breaker is the most commonly asked-about pattern, but it's one of five that work
together:

![Five fault tolerance patterns and what each one protects against](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-6-reliability-patterns-grid.png)

- **Bulkhead** - named after a ship's watertight compartments: partition resources
  (thread pools, connection pools) **per dependency**, so a call to one slow dependency
  can only ever exhaust *its own* pool, never starve the resources that calls to a
  *different*, healthy dependency need. Without bulkheading, a circuit breaker on one
  dependency doesn't even help the others - all your threads are already stuck waiting on
  the slow one by the time the breaker trips.
- **Backpressure** - a way for a consumer that can't keep up to signal "slow down" back to
  its producer, instead of silently absorbing everything into an ever-growing queue until
  memory runs out or latency spirals. Kafka consumer lag (5.1/5.2) is backpressure made
  visible: the log just holds unconsumed messages until the consumer catches up, rather
  than the producer being forced to block or drop anything.
- **Load shedding** - when genuinely overloaded, deliberately **reject** some fraction of
  incoming requests (often the least important ones - low-priority background jobs before
  user-facing requests) so the system can keep serving the rest *well*, rather than
  attempting to serve 100% of requests badly. Counter-intuitive but load-tested repeatedly
  in practice: a system that refuses 20% of requests at the door usually serves the
  remaining 80% far better than one that accepts all of them and degrades uniformly.
- **Hedged requests** - if a request to one replica hasn't returned within some latency
  budget (say, the p95 latency for that operation), fire a **duplicate** request to a
  second replica and take whichever answers first. This targets a narrower problem than a
  circuit breaker: not a fully failed dependency, but one **slow replica** dragging down
  your tail latency (p99) while the overall service is otherwise healthy - a circuit
  breaker wouldn't even trip, since most calls are succeeding fine, just not from that one
  slow replica.

## Cheat sheet

```
CASCADING     an overwhelmed-but-not-dead dependency (still responds, just
FAILURE       slowly) ties up every caller's threads waiting on it, which
              makes THEM slow too, propagating upstream through the whole
              call chain - worse than a clean crash, which at least fails fast.

CIRCUIT       CLOSED (normal, count failures) -> OPEN (fail fast, zero calls
BREAKER       reach downstream) -> HALF-OPEN (one trial after a timeout) ->
              CLOSED or OPEN again. Verified: only 3/6 requests reached an
              overwhelmed service before the breaker opened; a half-open
              trial after recovery closed it automatically.

BULKHEAD      separate resource pools PER dependency (like watertight ship
              compartments) - a slow dependency exhausts only its own pool,
              never starves calls to a healthy one.

BACKPRESSURE  consumer signals "slow down" instead of silently absorbing
              unbounded load - Kafka's retained log (5.1) IS backpressure
              made visible: unconsumed messages just wait.

LOAD          deliberately REJECT some requests when overloaded, to serve
SHEDDING      the rest well instead of everything badly.

HEDGED        duplicate a request to a 2nd replica if the 1st is slow past a
REQUESTS      latency budget, take whichever answers first - targets ONE
              slow replica dragging down p99, not a fully failed dependency
              (which a circuit breaker wouldn't even trip for).
```
