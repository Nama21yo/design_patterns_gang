Every system so far has assumed "the server" as if there's one. Past a certain scale
there isn't - there's a fleet of identical instances, and something has to be the single
point of contact that decides, for every incoming request, which instance actually handles
it. This note is that decision: the algorithms, the L4-vs-L7 distinction, and the two
related-but-different roles (reverse proxy, API gateway) that tend to sit right next to a
load balancer in a real request path.

## Why load balance at all

**Scalability** - horizontal scaling (3.4's whole premise, applied to stateless compute
instead of storage) only works if something actually spreads requests across the fleet;
without it, adding instances does nothing because traffic keeps hitting the same one.
**Availability** - a load balancer health-checks its backends and simply stops routing to
one that's failing, so one dead instance degrades capacity slightly instead of taking down
every request that happened to land on it. A managed example worth recognizing by name:
**AWS's Elastic Load Balancer (ELB)** family (Application Load Balancer for L7, Network
Load Balancer for L4) - the managed version of everything below, so you rarely hand-roll
this in production, but the algorithms are exactly what's implemented underneath.

## L4 vs. L7

![Routing by transport-layer info only (L4) vs. by application content (L7)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-5-l4-vs-l7.png)

- **L4 (transport layer)** - routes purely on IP address and port, without ever parsing the
  packet's application-layer payload. Very fast, very cheap (no HTTP parsing), but blind to
  anything about the request's actual content - it can't route `/api/*` differently from
  `/static/*`, because it never looks that far in.
- **L7 (application layer)** - terminates the connection, reads the actual HTTP request
  (path, headers, cookies, even body), and routes based on that. More CPU cost per request,
  but unlocks content-aware routing, TLS termination at the load balancer, and the ability
  to retry a failed request against a different backend itself (impossible at L4, which
  never understood there was a "request" to retry in the first place).

Default to L7 unless you specifically need L4's raw throughput and don't need any
content-based routing (a good fit for a simple TCP service that isn't HTTP at all).

## Load balancing algorithms

Four to know cold, each implemented and verified below.

**Round robin** - cycle through servers in fixed order, one request each.

```python
class RoundRobin:
    def __init__(self, servers):
        self.servers = servers
        self.i = 0

    def pick(self):
        s = self.servers[self.i % len(self.servers)]
        self.i += 1
        return s


rr = RoundRobin(["A", "B", "C"])
picks = [rr.pick() for _ in range(9)]
print("round robin, 9 requests:", picks)
```

```
round robin, 9 requests: ['A', 'B', 'C', 'A', 'B', 'C', 'A', 'B', 'C']
```

Simple and perfectly fair *by request count* - but blind to the fact that not all servers
are equally capable, and blind to how long any given request actually takes.

**Weighted round robin** - give some servers a higher weight (they're bigger instances, or
have more spare capacity) so they get a proportionally larger share. The naive version just
bursts all of a heavy server's extra picks together; the version actually used in
production (nginx's algorithm) is **smooth**: every pick, each server accumulates its
weight, the current highest total wins and gets reduced by the total weight afterward -
spreading the heavier server's extra share evenly across the sequence instead of clustering
it:

```python
class WeightedRoundRobin:
    def __init__(self, servers_weights):
        self.servers = list(servers_weights.keys())
        self.weights = servers_weights
        self.current = {s: 0 for s in self.servers}
        self.total_weight = sum(servers_weights.values())

    def pick(self):
        for s in self.servers:
            self.current[s] += self.weights[s]
        best = max(self.servers, key=lambda s: self.current[s])
        self.current[best] -= self.total_weight
        return best


from collections import Counter

wrr = WeightedRoundRobin({"A": 4, "B": 1, "C": 1})
picks = [wrr.pick() for _ in range(60)]
counts = Counter(picks)
print(f"weighted round robin (A:4, B:1, C:1), 60 requests: {dict(counts)}")
print(f"A's share: {counts['A']/60:.1%} (target ~66.7%), "
     f"B's share: {counts['B']/60:.1%} (target ~16.7%), "
     f"C's share: {counts['C']/60:.1%} (target ~16.7%)")

max_run = 1
run = 1
for i in range(1, len(picks)):
    run = run + 1 if picks[i] == picks[i-1] else 1
    max_run = max(max_run, run)
print(f"longest consecutive run of the same server: {max_run}")
```

```
weighted round robin (A:4, B:1, C:1), 60 requests: {'A': 40, 'B': 10, 'C': 10}
A's share: 66.7% (target ~66.7%), B's share: 16.7% (target ~16.7%), C's share: 16.7% (target ~16.7%)
longest consecutive run of the same server: 3
```

![Verified weighted round robin distribution matches the target weights exactly](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-5-wrr-distribution.png)

The ratio matches the configured weights exactly (4:1:1 -> 66.7%:16.7%:16.7%), and the
longest run of consecutive picks for the same server was only 3 - confirming the algorithm
actually spreads A's extra share out instead of bursting all 40 of its picks together at
the start.

**Least connections** - route to whichever server currently has the fewest **active**
(in-flight) connections. This is the algorithm to reach for when requests have highly
**variable duration** - round robin assumes every request costs about the same, and breaks
down badly when it doesn't (one server can end up with several long-running requests all
piled up while round robin keeps sending it more, unaware it's already the most loaded):

```python
class LeastConnections:
    def __init__(self, servers):
        self.active = {s: 0 for s in servers}

    def pick(self):
        s = min(self.active, key=lambda s: self.active[s])
        self.active[s] += 1
        return s

    def release(self, s):
        self.active[s] -= 1


lc = LeastConnections(["A", "B", "C"])
lc.active["A"] = 5
lc.active["B"] = 3
picks = [lc.pick() for _ in range(4)]
print(f"least connections (A busy=5, B busy=3, C busy=0 at start): next 4 picks -> {picks}")
```

```
least connections (A busy=5, B busy=3, C busy=0 at start): next 4 picks -> ['C', 'C', 'C', 'B']
```

The idle server (`C`) got the first three requests, exactly as expected - once its active
count caught up to `B`'s, the fourth request rebalanced onto `B` instead. This is the
"server has least variance in load, e.g. in terms of latency" framing directly: least
connections adapts to actual, current load rather than assuming uniform request cost.

**Hash-based routing** - `hash(client_key) % num_servers`, giving the same client the same
server every time (3.4's consistent-hashing material applies directly if the server set
changes frequently; plain modulus is fine for a mostly-static fleet). Useful for **session
affinity** (a client's session data lives in one server's local memory/cache, so you want
every request from that client landing on the same instance) or for warming a per-server
cache with a predictable subset of keys:

```python
import hashlib

class HashBased:
    def __init__(self, servers):
        self.servers = servers

    def pick(self, client_key):
        h = int(hashlib.md5(client_key.encode()).hexdigest(), 16)
        return self.servers[h % len(self.servers)]


hb = HashBased(["A", "B", "C", "D"])
client_picks = {c: hb.pick(c) for c in ("client_1", "client_2", "client_3")}
repeat_picks = {c: hb.pick(c) for c in ("client_1", "client_2", "client_3")}
print(f"hash-based routing: {client_picks}")
print(f"same clients again: {repeat_picks}")
print(f"identical both times: {client_picks == repeat_picks}")
```

```
hash-based routing: {'client_1': 'A', 'client_2': 'C', 'client_3': 'A'}
same clients again: {'client_1': 'A', 'client_2': 'C', 'client_3': 'A'}
identical both times: True
```

## Reverse proxy, API gateway, and load balancer - three related roles

These get used almost interchangeably in casual conversation, and in a small system a
single piece of software (nginx, Envoy) often does all three - but the **responsibilities**
are genuinely distinct, and naming them separately signals real understanding in an
interview:

![Three distinct roles, often bundled into one piece of infrastructure](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-5-proxy-gateway-lb.png)

- **API gateway** - the client-facing front door: authentication, rate limiting (6.4),
  request/response shaping, and routing to the **correct service** based on path or domain
  (`/orders/*` -> order service, `/payments/*` -> payment service).
- **Reverse proxy** - sits in front of a service, terminates TLS, can cache or compress
  responses, and hides the backend's actual topology from whoever's calling it - the client
  only ever sees the proxy's address, never the real instances behind it.
- **Load balancer** - once you know *which service* should handle a request (the gateway's
  job) and the connection has been proxied (the reverse proxy's job), the load balancer
  picks **which specific instance** of that service handles this one request - everything
  covered above.

## Cheat sheet

```
WHY           scalability (spread load across a fleet - useless without this)
              + availability (health-check + route around dead instances).
              AWS ELB (ALB=L7, NLB=L4) is the managed version of all of this.

L4 vs L7      L4: IP+port only, no payload parsing, fast/cheap, blind to
              content. L7: terminates HTTP, routes on path/headers/cookies,
              more CPU cost, enables content-aware routing + TLS termination
              + its own retries. Default to L7 unless raw L4 throughput and
              no content routing is specifically what's needed.

ALGORITHMS    round robin: even by REQUEST COUNT, blind to request cost.
              weighted RR: proportional to configured weight - verified 4:1:1
              weights -> 66.7%/16.7%/16.7%, spread smoothly (max run 3).
              least connections: adapts to ACTUAL current load - verified,
              routes to the idle server first, rebalances as it catches up.
              hash-based: same client -> same server, every time (session
              affinity / cache warmth) - verified, identical across 2 runs.

3 ROLES       API gateway (which SERVICE - auth, rate limiting, routing) ->
              reverse proxy (TLS, caching, hides backend topology) -> load
              balancer (which INSTANCE of that service). Often one piece of
              software in practice, but distinct responsibilities worth
              naming separately.
```
