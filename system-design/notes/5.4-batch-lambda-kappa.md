title: "5.4 Batch processing: MapReduce, Spark; Lambda vs Kappa"

At some point a computation stops being "run this query" and becomes "process more data
than one machine can hold or finish in reasonable time." This note is about the move that
follows - split the work across many machines - and the tools that make that split
practical at real scale: MapReduce's original model, Apache Spark's evolution of it, and
the architectural pattern (Lambda vs Kappa) for combining batch processing with the live,
streaming side covered in 5.3.

## Divide and conquer

![One machine can't do it -> split, process in parallel, merge](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-4-divide-and-conquer.png)

The canonical example is word frequency over a corpus too large for one machine: split the
corpus into chunks, count each chunk's words independently and in parallel (no chunk needs
to know what any other chunk is doing), then merge the partial counts into a final total.
That shape - **split, process independently, merge** - is the entire idea behind every tool
in this note; everything else is about making that shape fast, fault-tolerant, and
convenient to program against at cluster scale.

**MapReduce** formalizes this into three framework-managed phases - `map` (per-chunk,
fully parallel), `shuffle+sort` (route each key to the reducer responsible for it), and
`reduce` (per-key, fully parallel) - and 9.5's Top-K case study already has this worked
through mechanically end to end: a from-scratch, verified `frequency_count_mapreduce` /
`top_k_mapreduce` implementation, the exact mapper/shuffle/reducer flow, fault-tolerance
via re-running stateless tasks, and the five general principles of data aggregation
(aggregate close to the source, only associative/commutative operations parallelize
safely, aggregation is lossy on purpose, must be idempotent under retries, composable
aggregates roll up hierarchically). This note doesn't re-derive that - go there for the
mechanics. This note picks up where 9.5 left MapReduce and asks: **what replaced it, and
why.**

## Apache Spark

**Spark is a unified engine for large-scale data processing** - the direct successor to
MapReduce, built specifically to fix MapReduce's biggest cost: **writing every
intermediate result to disk (HDFS) between every single map and reduce stage.** A
multi-stage pipeline in classic MapReduce pays a full disk write + read for each hop, even
when the next stage runs on the exact same data moments later.

![MapReduce's disk-per-stage model vs. Spark keeping intermediate data in memory](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-4-memory-vs-disk.png)

Spark instead keeps intermediate results **in memory** across stages (spilling to disk only
under real memory pressure), which is the core reason it's typically cited as **10-100x
faster** than classic MapReduce - most dramatically on iterative workloads (machine
learning training loops, graph algorithms) that touch the same data across many stages,
where MapReduce would pay the disk round-trip every single time.

### Architecture: driver and executors

![Spark's driver/executor (master/worker) architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-4-spark-architecture.png)

- **Driver program** (the "master" in the framing that motivated this note) - runs your
  application code, builds the execution plan (a DAG of transformations), splits it into
  **stages** and **tasks**, and schedules those tasks onto executors. It's also where
  results come back to when you call an action like `.collect()`.
- **Cluster manager** - standalone, YARN, or Kubernetes - allocates executor processes
  across the physical cluster on the driver's behalf. Spark doesn't manage physical
  machines itself; it delegates that to whichever cluster manager it's deployed on.
- **Executors** (the "workers") - one process per allocated slot, each running on a subset
  of the data (a **partition**). An executor runs whatever tasks the driver schedules onto
  it, caches partitions in memory when told to, and reports results/status back to the
  driver.

### RDDs, DataFrames, and lazy evaluation

Spark's core abstraction is the **RDD** (Resilient Distributed Dataset): an immutable,
partitioned collection, distributed across executors, that remembers its own **lineage** -
the chain of transformations that produced it from its original source. That lineage is
Spark's fault-tolerance mechanism: if a partition is lost (an executor dies), Spark
recomputes just that partition from its lineage instead of needing replication for every
intermediate result. **DataFrames/Datasets** are a higher-level, schema-aware API built on
top of RDDs, optimized by Spark's Catalyst query planner - the practical default for
structured data today, with RDDs still underneath and available directly when you need
low-level control.

The other core property, and the one that makes Spark's optimizer possible at all: Spark
operations split into **transformations** (`map`, `filter`, `join`, `reduceByKey` - lazy,
they just extend the DAG) and **actions** (`collect`, `count`, `save` - these actually
trigger execution). Nothing runs until an action is called, which lets Spark see the
*entire* pipeline before executing anything and optimize it as one plan, instead of running
each step eagerly and blindly.

![Verified: transformations build a DAG lazily, an action runs the whole thing at once](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-4-lazy-evaluation.png)

Proven with a real local Spark session - a word-frequency job built the same way as 9.5's
MapReduce example, run through the actual PySpark RDD API rather than simulated:

```python
from pyspark.sql import SparkSession

spark = SparkSession.builder.master("local[4]").appName("wordcount-lazy") \
    .config("spark.ui.enabled", "false").getOrCreate()
sc = spark.sparkContext

splits = [
    "the cat sat on the mat",
    "the dog sat on the log",
    "the cat and the dog are friends",
    "a mat and a log are both flat",
]
rdd = sc.parallelize(splits, numSlices=4)   # 4 partitions, one per split

import time
t0 = time.time()
words = rdd.flatMap(lambda line: line.split())          # transformation
pairs = words.map(lambda w: (w, 1))                       # transformation
counts = pairs.reduceByKey(lambda a, b: a + b)             # transformation
print(f"chain built in {time.time()-t0:.4f}s (no data has been touched - these are lazy)")

t0 = time.time()
result = counts.collect()                                   # ACTION - executes now
print(f"executed in {time.time()-t0:.4f}s")

from collections import Counter
truth = Counter(w for line in splits for w in line.split())
print("match:", dict(sorted(result)) == dict(truth))

# proving laziness with a Spark accumulator (a plain Python list would NOT
# work here - .map runs on separate executor processes, even in local mode,
# so a driver-side list would never see their mutations; an accumulator is
# Spark's real mechanism for aggregating a counter across executors)
touched = sc.accumulator(0)
def track(w):
    touched.add(1)
    return (w, 1)

lazy_pairs = words.map(track)   # transformation only - built, not run
print(f"after building .map(track): accumulator = {touched.value} (should be 0)")
lazy_pairs.count()               # ACTION - now it runs
print(f"after calling .count(): accumulator = {touched.value} (should equal total word count, 27)")

spark.stop()
```

```
chain built in 0.0612s (no data has been touched - these are lazy)
executed in 1.5085s
match: True
after building .map(track): accumulator = 0 (should be 0)
after calling .count(): accumulator = 27 (should equal total word count, 27)
```

The word-frequency result matched a plain-Python ground truth exactly, and the accumulator
confirms laziness directly: zero words were touched while the chain was being *built*, and
all 27 were touched only once an action (`.count()`) actually ran it. (The first version of
this check used a plain Python list instead of an accumulator and silently reported 0
touches even after the action ran - a real, caught bug, and a genuinely useful lesson in
its own right: closures passed into `.map()` execute in separate executor processes, so
driver-side mutable state doesn't see their side effects; an accumulator is Spark's
purpose-built mechanism for exactly this.)

### What Spark is used for

ETL over huge datasets, large-scale batch analytics, iterative machine learning (MLlib),
graph processing (GraphX), ad-hoc SQL over data too large for a single database (Spark
SQL) - and, bridging into 5.3, **Spark Structured Streaming**, which applies this same
engine to unbounded, continuously-arriving data by treating each new batch of Kafka
messages as a micro-batch through the identical DAG/execution model described above.

## Lambda vs Kappa architecture

Both patterns for combining a fast/approximate path with a slow/exact path over the same
data are covered in full, with a real worked pipeline, in 9.5: the **Lambda Architecture**
(a speed layer producing fast approximate results plus a batch layer - MapReduce/Spark -
producing slow exact results, merged at query time; drawback: two codebases that must stay
in agreement) and the **Kappa Architecture** (Spark Structured Streaming reading directly
from Kafka, one codebase for both live and historical processing, using watermarking to
bound how long a window stays open for late arrivals and checkpointing to survive
restarts). The short version for this note: **Kappa is what you get when Spark's
streaming and batch modes are unified enough that you don't need a separate batch system
at all** - see 9.5 for the full mechanics, the watermarking/checkpointing details, and the
honest trade-off between the two (Lambda's batch layer is still sometimes the right call
for very-long-history reprocessing that a streaming engine would handle less efficiently
than a purpose-built batch job over columnar storage).

## Bloomberg's big-data stack

![Bloomberg's publicly documented big-data tools](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-4-bloomberg-stack.png)

Bloomberg's own engineering write-ups describe a producer/consumer data architecture:
producer-side services backed by **Apache HBase**, **Apache Solr**, and **MySQL**,
connected to consumers via **Apache Kafka** messaging. **Apache Spark** handles large-scale
batch and streaming analytics on top of that. **Apache Solr** specifically is the search
foundation behind more than 300 functions across the Bloomberg Terminal - essentially every
in-Terminal search - and Bloomberg engineers built and open-sourced the "Solr Operator" for
running Solr Clouds on **Kubernetes**, part of the company's public open-source program.
**Apache Airflow** orchestrates pipeline workflows. Internally, a "DataHub Engineering" team
built and operates **BBDS (Bloomberg Data Services)**, a distributed platform for hosting,
discovering, and serving datasets - managed data stores, search/discovery, batch analytics,
low-latency high-availability stores, real-time stream processing, and real-time CDC - that
grew from a single user in 2013 to powering 1,000+ engineers' applications today. (Worth
being precise here: this list reflects what's publicly documented; it does not include
Apache Flink, since no source confirms Flink specifically is part of Bloomberg's stack -
5.3 covers Flink on its own merits as an industry-standard stream processor, without
attaching it to Bloomberg.)
