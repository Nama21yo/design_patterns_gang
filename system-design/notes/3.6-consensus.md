Every "auto-recovery" story in system design eventually runs into the same wall: something
has to watch the thing that's supposed to be reliable, and then something has to watch
*that*. This note is about the point where that chain of watchers stops - the moment a
group of machines has to agree on one fact (who's in charge, what value was written, what
order things happened in) with no single machine allowed to be a permanent point of
failure. That's **consensus**, and getting it right is one of the genuinely hard problems in
distributed systems.

## Why consensus is hard

The core difficulty has a name: the **FLP impossibility result** (Fischer, Lynch, Paterson,
1985). Stated informally: in a fully asynchronous network - where a message can be delayed
by an arbitrary, unbounded amount of time - **no algorithm can guarantee consensus in
bounded time if even one process might fail.** The reason is uncomfortably simple: if a
message from node X hasn't arrived yet, there is no way to distinguish "X is dead" from "X
is just slow, and the network hasn't delivered its message yet." Any algorithm that decides
too eagerly risks two different nodes reaching two different decisions; any algorithm that
waits long enough to be sure risks waiting forever.

Real systems don't sit around fixing this in theory - they sidestep it practically, using
**timeouts** as an imperfect, working substitute for true failure detection ("if I haven't
heard from you in 150ms, I'll assume you're dead and act accordingly"), accepting a small,
bounded risk of getting it wrong (a "dead" node that was actually just slow) in exchange for
an algorithm that terminates. Every leader-election timeout and heartbeat interval in this
note is a direct, practical answer to FLP: not "solving" the impossibility, just choosing
where to eat the risk.

## Leader election: the general auto-recovery pattern

Here's a problem that shows up in some form in almost every real system: you have workers
(servers, replicas, shards) and something needs to watch them and restart the ones that
die. Put an **orchestrator** in charge of that job. Fine - until you ask the next question:
*what happens when the orchestrator itself dies?*

![The auto-recovery problem, and the fix](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-orchestrator-recovery-problem.png)

A single orchestrator just moved the single point of failure one level up, it didn't remove
it. The fix is to apply the exact same idea recursively: run **multiple copies of the
orchestrator**, in a leader-follower arrangement (3.5's topology, applied to control-plane
processes instead of data). One orchestrator instance is the leader and does the actual
work of watching the workers; the rest are followers that do nothing but watch the *leader*
(via a heartbeat). The moment the leader's heartbeat stops, the followers detect it and run
a **leader election** among themselves - one of them becomes the new leader and picks up
exactly where the old one left off, watching the workers.

This is the generic pattern, and it's worth internalizing as one: **any system that needs
to survive the failure of "the thing in charge" runs that thing as a leader-follower cluster
and uses leader election to recover automatically, instead of relying on a single instance
staying up forever.** Database primaries (3.5), the Raft/Paxos-backed coordination services
below, Kubernetes's control plane, Kafka's controller - all the same shape.

### Leader election algorithms

**The Bully algorithm.** Every node has a unique, comparable ID (the highest ID wins - a
"bully" in the sense that it always overrides anyone lower). When a node notices the leader
is unreachable, it sends an election message to every node with a *higher* ID than itself.
If none respond within a timeout, it declares itself the leader. If a higher node responds,
that node takes over running the election the same way - so the process always bubbles up
to the highest-numbered node that's actually alive:

![Bully algorithm](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-bully-algorithm.png)

```python
class Node:
    def __init__(self, node_id, alive=True):
        self.id = node_id
        self.alive = alive

def run_election(nodes, starter_id):
    by_id = {n.id: n for n in nodes}
    def elect(candidate_id):
        higher_alive = [n for n in nodes if n.id > candidate_id and n.alive]
        if not higher_alive:
            return candidate_id                     # nobody bigger answered -> I win
        return elect(max(n.id for n in higher_alive))  # highest alive one takes over
    return elect(starter_id) if by_id[starter_id].alive else None

nodes = [Node(i) for i in range(1, 6)]   # ids 1..5, all alive
print("all alive, node 3 starts an election:", run_election(nodes, starter_id=3))
nodes[4].alive = False   # id 5 (the leader) crashes
print("node 5 down, node 2 starts an election:", run_election(nodes, starter_id=2))
nodes[3].alive = False   # id 4 also crashes
print("node 4 also down, node 1 starts an election:", run_election(nodes, starter_id=1))
```

```
all alive, node 3 starts an election: 5
node 5 down, node 2 starts an election: 4
node 4 also down, node 1 starts an election: 3
```

Simple and easy to reason about; the downside is `O(n^2)` messages in the worst case (every
node can end up messaging every higher node) and a brief pause in service during the
`O(n)` timeout chain while the election bubbles up.

**Raft's randomized-timeout election.** Every node picks a **random** election timeout
within a range (e.g. 150-300ms). Whoever's timer fires first becomes a candidate: it
increments a **term** counter, votes for itself, and requests votes from everyone else. A
node grants at most one vote per term, first-come-first-served. The candidate that gets a
**majority** of votes becomes leader for that term.

![Raft election: randomized timeouts break ties](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-raft-election-timeline.png)

Randomizing the timeout is what makes this work well in practice: it makes it unlikely that
two nodes' timers fire close enough together to split the vote. But it *can* still happen -
verified below, forced deliberately:

```python
def run_term(alive_ids, timeouts, rng):
    min_t = min(timeouts.values())
    candidates = [n for n, t in timeouts.items() if t == min_t]
    votes = {c: 1 for c in candidates}
    for voter in alive_ids:
        if voter in candidates:
            continue
        votes[rng.choice(candidates)] += 1            # network jitter -> different voters
    majority = len(alive_ids) // 2 + 1                 # can hear from different candidates
    winners = [c for c, v in votes.items() if v >= majority]
    return (winners[0] if len(winners) == 1 else None), votes

def elect_leader(alive_ids, rng, forced_timeouts=None, max_retries=20):
    for attempt in range(1, max_retries + 1):
        timeouts = dict(forced_timeouts) if (forced_timeouts and attempt == 1) else \
            {n: rng.uniform(150, 300) for n in alive_ids}
        winner, votes = run_term(alive_ids, timeouts, rng)
        if winner is not None:
            return winner, attempt, votes
    return None, max_retries, votes


import random
rng = random.Random(7)
nodes = [1, 2, 3, 4, 5]

print("1000 elections, 5 nodes, independent random timeouts each time:")
attempts_needed = [elect_leader(nodes, random.Random(s))[1] for s in range(1000)]
print(f"  every trial converged to exactly one leader: "
     f"{all(elect_leader(nodes, random.Random(s))[0] is not None for s in range(1000))}")
print(f"  elections needing 2+ attempts: {sum(1 for a in attempts_needed if a > 1)} / 1000")

print("\na deliberately forced 3-way tie: nodes 2, 3, 4 all time out at 200ms")
forced = {1: 250, 2: 200, 3: 200, 4: 200, 5: 260}
_, votes_term1 = run_term(nodes, forced, random.Random(1))
print(f"  term 1 votes: {votes_term1} -> no candidate has a majority (3 of 5): SPLIT VOTE")
leader, attempts, votes_final = elect_leader(nodes, random.Random(1), forced_timeouts=forced)
print(f"  retried with fresh random timeouts -> resolved after {attempts} attempt(s), "
     f"final votes: {votes_final}, leader: {leader}")
```

```
1000 elections, 5 nodes, independent random timeouts each time:
  every trial converged to exactly one leader: True
  elections needing 2+ attempts: 0 / 1000

a deliberately forced 3-way tie: nodes 2, 3, 4 all time out at 200ms
  term 1 votes: {2: 2, 3: 1, 4: 2} -> no candidate has a majority (3 of 5): SPLIT VOTE
  retried with fresh random timeouts -> resolved after 2 attempt(s), final votes: {3: 5}, leader: 3
```

Two things worth noticing in that output. First, real randomized timeouts almost never
produce a split vote (0 out of 1000) - which is exactly why Raft randomizes them. Second,
the forced 3-way tie *does* split (2, 1, 2 - nobody reaches the majority of 3), and the
protocol's answer is simply to retry with a fresh term and fresh random timeouts, which
resolves it immediately. Also notice why real Raft clusters always use an **odd** number of
nodes: with an odd total and only two candidates splitting the remaining votes, one of them
always reaches a majority by the pigeonhole principle - genuine unresolvable splits need
three or more simultaneous candidates (rare with randomized timeouts) or an even-sized
cluster (which is why you avoid those).

## Raft: the rest of the story

Leader election is only half of Raft - the other half is **log replication**, and it's the
same idea 3.5 already covered for database replication, generalized to any replicated log
of decisions:

![Raft log replication](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-raft-log-replication.png)

1. A client sends a write to the leader.
2. The leader appends it to its own log (uncommitted) and sends it to all followers.
3. Once a **majority** of nodes (leader included) have the entry in their log, it's
   **committed** - the leader applies it and replies to the client.
4. A follower that's slow or briefly unreachable catches up later by replaying whatever it
   missed from the leader's log - it doesn't block the majority from proceeding.

Two safety rules make this correct even across leader changes: a candidate can only win an
election if its log is **at least as up to date** as a majority of the cluster's (so a new
leader can never "forget" a committed entry), and a log entry only counts as committed once
it's replicated by the *current* leader to a majority - never by inferring commitment from
an old leader's partial replication. Together, these guarantee that once something is
committed, every future leader's log will contain it.

## Paxos: the older, harder-to-follow answer to the same problem

Paxos (Lamport, 1989) solves the same problem as Raft - agreement on a single value across
unreliable nodes - with three logical roles:

![Paxos roles](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-paxos-roles.png)

A **proposer** suggests a value with an increasing proposal number; **acceptors** promise
not to accept any older proposal once they've seen a newer one, and accept a value once a
majority agrees; **learners** find out what was decided once a majority of acceptors has
accepted it. It takes two round trips (prepare, then accept) per decided value, and its
famous difficulty is handling **multiple competing proposers** correctly and efficiently -
the original paper is notoriously hard to implement correctly from, which spawned an entire
subgenre of "Paxos made simple/moderately complex/live" papers trying to explain it better.
**Multi-Paxos** (running repeated rounds with a stable, implicit leader to skip the prepare
phase on every value) closes most of the practical gap with Raft - and Raft can be
understood as taking that same "elect a stable leader" idea and making it the protocol's
*explicit*, central feature from the start, specifically so it would be easier to
understand and implement correctly. That's Raft's whole pitch: equivalent guarantees, a
specification people can actually build a correct system from.

## ZooKeeper and etcd: consensus as a service

You rarely implement Raft or Paxos yourself. Instead, you run (or use a managed) consensus
cluster - **ZooKeeper** (uses a Paxos-like protocol called ZAB) or **etcd** (built directly
on Raft) - and use the coordination primitives it exposes:

![Using a coordination service for leader election](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-6-coordination-service.png)

- **Leader election**: every candidate instance races to create the same node/key (a
  ZooKeeper *ephemeral* znode, or an etcd key backed by a *lease*). Exactly one create
  succeeds - that instance is the leader. If the leader's session ends (it crashes, or its
  lease isn't renewed in time), the coordination service automatically deletes that
  node/key, and every other instance - which was *watching* it - gets notified and races to
  create it again.
- **Distributed locks**: the same ephemeral-node mechanism, held for the duration of a
  critical section instead of a process's whole lifetime.
- **Service discovery and configuration**: a small amount of strongly consistent, watchable
  shared state - "which instances are alive and where," "what's the current config value" -
  that every service can read and be notified of changes to, without each service
  reimplementing its own consensus.

The unifying idea: **all of these reduce to "a small piece of consensus-backed state, with
notifications on change."** You don't want every application to run its own Raft cluster
just to elect a leader - you run one shared, well-tested consensus cluster and let
everything else build simple primitives (locks, election, discovery) on top of it.

## Cheat sheet

```
WHY HARD      FLP impossibility: in an async network, no algorithm guarantees consensus
              in bounded time if even one node can fail - can't tell "dead" from "slow."
              Practical answer: timeouts, accepting a small bounded risk of misjudging.

LEADER        Generic auto-recovery pattern: run "the thing in charge" as a
ELECTION      leader-follower cluster of ITSELF. Leader dies -> followers notice
(GENERAL)     the missing heartbeat -> elect a new leader -> resume. Applies
              recursively to orchestrators, DB primaries, any control plane.

BULLY         Highest ID always wins. Election bubbles up: message all higher IDs,
ALGORITHM     become leader if none answer, else the highest answering ID takes over.
              O(n^2) worst-case messages; simple to reason about.

RAFT          Randomized election timeout -> first to fire becomes candidate,
ELECTION      requests votes, wins with a MAJORITY. Split votes need 3+ simultaneous
              candidates or an even cluster (verified: 0/1000 random trials split;
              a forced 3-way tie does split, resolved by retrying with a new term).
              -> use an ODD cluster size.

RAFT LOG      leader appends -> replicates to followers -> MAJORITY has it ->
              committed -> apply + reply. Slow followers catch up later. Same
              majority-quorum idea as 3.5's leaderless replication.

PAXOS         proposer / acceptor / learner, majority-accepted proposal number wins.
              2 round trips/decision, notoriously hard to get right with competing
              proposers. Multi-Paxos (stable implicit leader) ~= what Raft makes explicit.

ZK / ETCD     don't reimplement consensus - run one coordination service (ZAB /
              Raft-backed) and build leader election, locks, service discovery,
              and config on its ephemeral-node-plus-watch primitive.
```
