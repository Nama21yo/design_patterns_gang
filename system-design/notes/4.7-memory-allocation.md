---
title: "4.7 Memory allocation: fit algorithms, slab, and buddy allocation"
---

4.6 covered how a process's virtual heap grows. This note is what actually happens inside
that heap on every `malloc`/`new`: which free hole gets handed out, why the naive answer
wastes a predictable amount of memory no matter how you tune it, and the two allocator
designs (slab, buddy) that real operating system kernels use to sidestep the problem
instead of just tuning around it.

## A note on scope first: cgroups

Before getting into allocation *within* one process, worth naming the layer above it: on
Linux, a **control group (cgroup)** lets the OS cap how much memory (and CPU, I/O, etc.) an
entire process or group of processes is allowed to use in total - the mechanism containers
are built on. A process hitting its cgroup memory limit gets killed (the OOM killer) or
throttled, independent of whether its own heap allocator still thinks it has room. This
note is about the allocator's job *inside* whatever budget the cgroup allows - a different,
lower layer of the same "who gets how much memory" question.

## The fit algorithms

Given a list of free holes and a request of some size, which hole do you hand out?

![Four strategies, same holes, same request](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-7-fit-algorithms.png)

- **First-fit** - scan from the start, take the first hole big enough. Fast (stop as soon
  as you find one), but tends to leave small, awkward leftover slivers near the front of
  memory that keep getting scanned past on every future search.
- **Best-fit** - scan everything, take the *smallest* hole that's still big enough.
  Minimizes wasted space on this one allocation - but that's exactly its problem: it
  deliberately creates the smallest possible leftover, which is often too small to be
  useful for anything else, so best-fit tends to accumulate a graveyard of tiny unusable
  slivers over time.
- **Worst-fit** - take the *largest* available hole. Counterintuitively, this can fragment
  *less* than best-fit in practice: carving a small request out of the biggest hole tends
  to leave a leftover that's still big enough to be useful, instead of a sliver.
- **Next-fit** - like first-fit, but resume scanning from wherever the *last* allocation
  left off, wrapping around, instead of always restarting from address zero. Spreads
  allocations more evenly across the whole pool and avoids repeatedly re-scanning the same
  early, already-picked-over region - at the cost of being slightly more likely to
  fragment memory that a full first-fit scan from the start might have packed tighter.
- **Quick-fit** - keep several *separate* free lists, one per common size class (say, 8B,
  16B, 32B, 64B...), so a request for a common size is an O(1) pop from the right list
  instead of a search at all. Fast for common sizes; the cost shows up when no list has
  the exact size and the allocator has to fall back to a general search or round up,
  wasting the difference - the same rounding-up cost the buddy allocator below embraces
  deliberately, without pretending otherwise.

## The 50% problem: fragmentation is not a tuning bug, it's structural

However you tune the fit strategy, the core issue doesn't go away: **external
fragmentation** - free memory that exists in total, but is scattered across holes too small
individually to satisfy a request, even though the *sum* of free bytes would easily cover
it.

This isn't just a first-fit quirk - it's a well-known, empirically and analytically
established result (Knuth's **"fifty-percent rule"**): in steady state, under a
long-running mix of random allocations and frees, **even with immediate coalescing of
adjacent free blocks**, the number of free holes settles to roughly **half** the number of
currently allocated blocks:

```python
class Pool:
    def __init__(self, size):
        self.blocks = [[0, size, True]]   # [start, length, is_free]

    def alloc(self, size):
        for b in self.blocks:
            if b[2] and b[1] >= size:
                if b[1] > size:
                    idx = self.blocks.index(b)
                    self.blocks.insert(idx + 1, [b[0] + size, b[1] - size, True])
                b[1] = size
                b[2] = False
                return b
        return None

    def free(self, block):
        block[2] = True
        self._coalesce()

    def _coalesce(self):
        self.blocks.sort(key=lambda b: b[0])
        merged = [self.blocks[0]]
        for b in self.blocks[1:]:
            last = merged[-1]
            if last[2] and b[2]:
                last[1] += b[1]
            else:
                merged.append(b)
        self.blocks = merged


import random
random.seed(42)
pool = Pool(100_000)
live = []
for step in range(4000):
    if live and random.random() < 0.5:
        pool.free(live.pop(random.randrange(len(live))))
    else:
        b = pool.alloc(random.randint(50, 500))
        if b is not None:
            live.append(b)

n_allocated = sum(1 for b in pool.blocks if not b[2])
n_holes = sum(1 for b in pool.blocks if b[2])
print(f"allocated blocks: {n_allocated}")
print(f"free holes:       {n_holes}")
print(f"holes / allocated blocks = {n_holes / n_allocated:.3f}  "
     f"(Knuth's fifty-percent rule predicts ~0.5)")
```

```
allocated blocks: 52
free holes:       30
holes / allocated blocks = 0.577  (Knuth's fifty-percent rule predicts ~0.5)
```

![Measured: holes settle to roughly half the allocated-block count](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-7-fragmentation-result.png)

The takeaway: **fragmentation is a structural cost of variable-size allocation from a
general free list, not a bug in any one fit strategy** - which is exactly why kernels don't
try to out-clever it with a better search order, and instead change the *shape* of the
allocation problem with the two designs below.

## Slab allocation: sidestep fragmentation for fixed-size objects

A huge fraction of what a kernel allocates is the **same handful of struct sizes**,
repeatedly - process descriptors, file objects, network buffers. **Slab allocation** takes
advantage of that: pre-carve a slab (one or more pages) into an array of slots, every slot
exactly the size of that one object type.

![Slab allocation](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-7-slab-allocation.png)

```python
class SlabCache:
    def __init__(self, object_size, objects_per_slab=8):
        self.object_size = object_size
        self.objects_per_slab = objects_per_slab
        self.slabs = []
        self.free_slots = []

    def _grow(self):
        slab_index = len(self.slabs)
        self.slabs.append(["free"] * self.objects_per_slab)
        for slot_index in range(self.objects_per_slab):
            self.free_slots.append((slab_index, slot_index))

    def alloc(self):
        if not self.free_slots:
            self._grow()
        slab_index, slot_index = self.free_slots.pop()
        self.slabs[slab_index][slot_index] = "used"
        return (slab_index, slot_index)

    def free(self, handle):
        slab_index, slot_index = handle
        self.slabs[slab_index][slot_index] = "free"
        self.free_slots.append(handle)


cache = SlabCache(object_size=64, objects_per_slab=4)
handles = [cache.alloc() for _ in range(6)]
print("allocated 6 objects of size 64B, 4 per slab:")
print(" slabs:", cache.slabs)

cache.free(handles[1]); cache.free(handles[3])
h_new = cache.alloc()
print(f"new alloc() reuses a freed slot: {h_new}  (no new slab needed)")
assert h_new in (handles[1], handles[3])
print("assert OK: O(1) reuse, zero fragmentation for this object type")
```

```
allocated 6 objects of size 64B, 4 per slab:
 slabs: [['used', 'used', 'used', 'used'], ['free', 'free', 'used', 'used']]
new alloc() reuses a freed slot: (0, 0)  (no new slab needed)
assert OK: O(1) reuse, zero fragmentation for this object type
```

Because every slot is *always* exactly the right size, there's no searching, no splitting,
and no external fragmentation to speak of for that object type - `alloc`/`free` are both
`O(1)`. The trade: it only helps for object sizes you've set up a dedicated cache for; a
one-off, oddly-sized allocation still needs a general-purpose allocator. This is precisely
what Memcached's internal allocator (4.3) is built on - it pre-sizes slabs into a fixed set
of size classes and fits each cached item into the nearest one, for the same reason a
kernel does: avoid fragmenting under constant same-ish-sized churn.

## Buddy allocation: sidestep fragmentation by only ever splitting in half

For variable-size requests, **buddy allocation** takes a different structural shortcut:
only ever split (or merge) blocks by **exact powers of two**. A request is rounded up to
the nearest power of 2 and satisfied by recursively splitting a larger free block in half
until a block of the right size exists.

![Buddy allocation: split by halves, merge by buddies](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-7-buddy-allocation.png)

```python
class BuddyAllocator:
    def __init__(self, total_size):
        assert total_size & (total_size - 1) == 0, "must be a power of 2"
        self.max_order = total_size.bit_length() - 1
        self.free_lists = {o: set() for o in range(self.max_order + 1)}
        self.free_lists[self.max_order].add(0)
        self.allocated = {}

    def _order_for(self, size):
        return max(0, (size - 1).bit_length())

    def alloc(self, size):
        return self._alloc_order(self._order_for(size))

    def _alloc_order(self, order):
        if order > self.max_order:
            return None
        if self.free_lists[order]:
            addr = self.free_lists[order].pop()
            self.allocated[addr] = order
            return addr
        parent = self._alloc_order(order + 1)      # split a bigger block
        if parent is None:
            return None
        del self.allocated[parent]
        buddy = parent + (1 << order)
        self.free_lists[order].add(buddy)
        self.allocated[parent] = order
        return parent

    def free(self, addr):
        order = self.allocated.pop(addr)
        while True:
            buddy = addr ^ (1 << order)             # XOR flips to the buddy address
            if buddy in self.free_lists[order]:
                self.free_lists[order].discard(buddy)
                addr = min(addr, buddy)
                order += 1                          # merge, then check the NEXT buddy up
            else:
                break
        self.free_lists[order].add(addr)


b = BuddyAllocator(1024)
a1, a2, a3 = b.alloc(100), b.alloc(200), b.alloc(50)   # round up to 128, 256, 64
b.free(a1); b.free(a2); b.free(a3)
print("after freeing all 3, free lists by order:",
     {o: sorted(s) for o, s in b.free_lists.items() if s})
assert b.free_lists[b.max_order] == {0}
print("assert OK: fully coalesced back into a single free 1024-byte block")
```

```
after freeing all 3, free lists by order: {10: [0]}
assert OK: fully coalesced back into a single free 1024-byte block
```

The `addr ^ (1 << order)` line is the elegant core of the whole design: because blocks are
only ever split at power-of-2 boundaries, a block's buddy address is always found by
flipping exactly one bit - no bookkeeping structure needed to know who your buddy is, the
address arithmetic *is* the bookkeeping. Freeing checks whether that buddy is also free and,
if so, merges them into the parent size and repeats the check one level up - which is why
the demo above, freeing three unrelated-looking allocations, fully collapses back into one
clean 1024-byte block instead of leaving scattered holes.

The cost is **internal fragmentation**: rounding a 100-byte request up to 128 bytes wastes
28 bytes *inside* an allocation that will never be handed to anyone else - up to ~50% waste
in the worst case (just over a power-of-2 boundary). That's a real, bounded, predictable
cost, traded deliberately for `O(log n)` split/merge and **zero** external fragmentation -
the opposite trade a plain fit-based allocator makes.

## Cheat sheet

```
CGROUPS       cap total memory (etc.) for a process/group - a layer ABOVE the
              allocator; hitting the limit means OOM-kill/throttle regardless of
              what the allocator inside still thinks is free.

FIT           first-fit: first hole that fits, fast, front-loads slivers.
ALGORITHMS    best-fit: smallest hole that fits, minimizes THIS waste, tends to
              accumulate unusable tiny slivers over time.
              worst-fit: largest hole, counterintuitively often fragments LESS
              than best-fit (leftover stays big enough to be useful).
              next-fit: like first-fit but resumes from the last position.
              quick-fit: separate free lists per common size class, O(1) for
              common sizes, falls back / rounds up otherwise.

50% RULE      fragmentation is STRUCTURAL, not a tuning bug: even with immediate
              coalescing, holes settle to ~half the allocated-block count in
              steady state (Knuth; verified: 0.577 measured vs ~0.5 predicted).

SLAB          pre-carved fixed-size slots for one object type/size. alloc/free =
ALLOCATION    O(1) pop/push a slot, ZERO external fragmentation for that type
              (verified). Doesn't help one-off/odd-sized allocations. What
              Memcached's internal allocator (4.3) is built on.

BUDDY         only ever split/merge by exact powers of 2. Buddy address = your
ALLOCATION    own address XOR your block size - no separate bookkeeping needed.
              O(log n) split/merge, fully and automatically coalesces (verified:
              3 unrelated frees -> back to one clean block). Cost: internal
              fragmentation from rounding up to a power of 2 (up to ~50% worst
              case) - the mirror-image trade of the fit algorithms above.
```
