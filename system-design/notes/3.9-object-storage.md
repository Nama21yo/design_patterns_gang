title: "3.9 Object/blob storage and distributed file systems"
---

3.1 covered GFS - a distributed file system built for a handful of internal, huge,
sequentially-read files. This note is its descendant, generalized into a public product:
**object storage**, the "blob" (Binary Large OBject) store that S3 made the default answer
to "where does this large file live," and that changed how application servers are built
along the way.

## The object storage model: buckets and keys

Everything lives in a **bucket** (a globally-named, top-level container) under a **key** (a
string that identifies one object inside it). Concatenate them and a key like
`users/42/avatar.png` *looks* exactly like a filesystem path - and that resemblance is
almost entirely a UI convenience, not the underlying structure:

![Object storage: buckets, keys, and the folder illusion](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-9-object-storage-model.png)

Proven with real `boto3` calls against a live S3 API (mocked with `moto`, so this is the
actual AWS SDK and the actual API shape, not a hand-rolled simulation):

```python
from moto import mock_aws
import boto3
import json

@mock_aws
def main():
    s3 = boto3.client("s3", region_name="us-east-1")
    s3.create_bucket(Bucket="my-app-bucket")

    s3.put_object(Bucket="my-app-bucket", Key="users/42/avatar.png", Body=b"fake-png-bytes")
    s3.put_object(Bucket="my-app-bucket", Key="users/42/resume.pdf", Body=b"fake-pdf-bytes")
    s3.put_object(Bucket="my-app-bucket", Key="users/7/avatar.png", Body=b"fake-png-bytes-2")

    print("--- ListObjects with no delimiter: every key, flat ---")
    resp = s3.list_objects_v2(Bucket="my-app-bucket")
    for obj in resp["Contents"]:
        print(" ", obj["Key"])

    print("\n--- ListObjects WITH delimiter='/' and prefix='users/': looks like a folder ---")
    resp = s3.list_objects_v2(Bucket="my-app-bucket", Prefix="users/", Delimiter="/")
    print("  'files' directly under users/:", resp.get("Contents", []))
    print("  'subfolders' under users/:", [p["Prefix"] for p in resp.get("CommonPrefixes", [])])

    # a bucket policy (JSON, IAM-style) - see "Access control" below
    policy = {
        "Version": "2012-10-17",
        "Statement": [{
            "Sid": "PublicReadOnlyAvatars",
            "Effect": "Allow",
            "Principal": "*",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::my-app-bucket/users/*/avatar.png",
        }],
    }
    s3.put_bucket_policy(Bucket="my-app-bucket", Policy=json.dumps(policy))
    print("\n--- bucket policy applied: public read on avatar.png keys only ---")
    print(" ", s3.get_bucket_policy(Bucket="my-app-bucket")["Policy"][:90], "...")

    # a presigned URL - temporary, scoped access without making anything public
    url = s3.generate_presigned_url(
        "get_object", Params={"Bucket": "my-app-bucket", "Key": "users/42/resume.pdf"},
        ExpiresIn=300)
    print("\n--- presigned URL for a PRIVATE object, valid 300s ---")
    print(" ", url[:70], "...")

main()
```

```

  users/42/avatar.png
  users/42/resume.pdf
  users/7/avatar.png

--- ListObjects WITH delimiter='/' and prefix='users/': looks like a folder ---
  'files' directly under users/: []
  'subfolders' under users/: ['users/42/', 'users/7/']

--- bucket policy applied: public read on avatar.png keys only ---
  {"Version": "2012-10-17", "Statement": [{"Sid": "PublicReadOnlyAvatars", "Effect": "Allow" ...

--- presigned URL for a PRIVATE object, valid 300s ---
  https://my-app-bucket.s3.amazonaws.com/users/42/resume.pdf?AWSAccessKe ...
```

There is no `users/` or `users/42/` directory anywhere - every object is one flat key in one
flat namespace. `list_objects_v2` with a `delimiter` just groups keys by their next `/` and
reports the common prefixes back as `CommonPrefixes`, which is what every S3 console/UI uses
to draw a folder tree that doesn't actually exist underneath. (This is a genuine, common
interview gotcha: "renaming a folder" in S3 isn't a metadata rename, it's copying every
object under that prefix to new keys and deleting the old ones - because there was never a
folder object to rename in the first place.)

## What changed for the application: statelessness

Before object storage existed as a service, an uploaded file typically landed on the local
disk of whichever app server happened to handle that request:

![Stateless apps + object storage](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-9-stateless-app-s3.png)

That pins every future request for that file to that one server (sticky routing - no free
horizontal scaling) and puts that file's durability at the mercy of one disk. Move the file
to object storage instead, and the app server holds **no file state at all** - it's a thin
layer between the request and S3. Any instance can serve any request, autoscaling and
replacing dead instances becomes trivial (nothing to lose - the data was never there), and
this is precisely the statelessness Part 2's load-balancing assumptions and Part 6's
autoscaling both take for granted.

## Advantages

- **Effectively infinite, network-attached capacity.** You don't provision disk size for an
  app server anymore - you write to a bucket and stop thinking about capacity.
- **Ecosystem ubiquity.** Nearly every big-data and analytics tool speaks S3's API natively -
  Spark, Presto/Trino, data warehouses, ML training pipelines all read and write S3 or an
  S3-compatible endpoint directly, which is a large part of why S3 became the de facto data
  lake substrate rather than just a file host.
- **Durability without you managing replicas yourself** - covered concretely below.

## Disadvantages

- **Read latency is meaningfully worse than local storage.** A network hop to a shared
  service, not optimized for small random-access reads, will lose to local NVMe/SSD every
  time for latency-sensitive workloads - object storage is built for throughput on large
  sequential objects, not for serving as a database's primary storage.
- **Historically weaker consistency.** S3 was famously **eventually consistent** for reads
  after overwrites/deletes for years (a `GET` right after a `PUT` to the same key could
  return stale or no data) before AWS moved it to strong read-after-write consistency in
  December 2020 - worth knowing as history, and worth explicitly checking for *any*
  S3-compatible or non-AWS object store, since "S3-compatible API" says nothing about
  matching that same consistency guarantee.
- **A different cost shape** - pay per GB stored, per request, and (often the expensive
  surprise) per GB of **egress** leaving the provider's network, not a flat disk cost the
  way a local volume is billed.

## Access control: ACLs, bucket policies, and presigned URLs

Three overlapping mechanisms, in the order S3 actually recommends using them:

- **Bucket policies** (the modern, recommended default) - a JSON, IAM-style document
  attached to the bucket, expressing rules like "allow anyone to `GetObject` on any key
  matching `users/*/avatar.png`" - exactly the `policy` object `put_bucket_policy`'d onto
  `my-app-bucket` in the demo above, restricting public read access to only the avatar
  keys. Fine-grained (down to a key pattern), auditable as a single document, and how most
  production access rules are actually expressed today.
- **ACLs (Access Control Lists)** - the older, coarser mechanism: grant specific
  permissions (read, write, full control) to specific AWS accounts or predefined groups
  (e.g. "all authenticated AWS users," "everyone"), attached per-bucket or even per-object.
  AWS itself now recommends bucket policies over ACLs for nearly everything, and disables
  ACLs by default on new buckets - useful to recognize in older systems, not the tool to
  reach for in a new design.
- **Presigned URLs** - a time-limited, cryptographically signed URL granting temporary
  access to one specific object, without making the object public and without the requester
  needing any AWS credentials of their own - the `generate_presigned_url` call above, valid
  for 300 seconds, for the otherwise-private `resume.pdf`. The standard pattern for "let
  this one user download/upload this one private file for the next few minutes" - the app
  server generates the URL (it holds the real credentials) and
  hands it to the client, which talks to S3 directly from there, keeping the transfer itself
  off the app server entirely.

## Durability: erasure coding vs. replication

S3-like durability claims ("eleven nines") come from redundancy, and there are two ways to
buy it:

![Erasure coding vs. replication: same durability, different storage cost](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-9-erasure-coding-vs-replication.png)

- **Replication** - store `N` full copies. Simple, cheap to reconstruct (just read another
  copy), expensive in raw storage: 3x replication to survive 2 node failures means paying
  for 3x the data.
- **Erasure coding** - split an object into `k` data chunks, compute additional parity
  chunks using Reed-Solomon-style math, and store `k + m` chunks total; any `k` of the
  `k + m` chunks are enough to reconstruct the whole object. A "4+2" scheme survives 2
  failures (like 3x replication above) using only 1.5x the storage instead of 3x - a real,
  large cost saving at the multi-exabyte scale object stores operate at, paid for with more
  CPU work to reconstruct a lost chunk (has to be computed from the surviving chunks and
  parity, not just copied) and more complexity in the storage layer. Large object stores use
  erasure coding pervasively for exactly this storage-cost reason once data volume is big
  enough for the CPU trade-off to be worth it.

## Metadata service scaling

GFS (3.1) got away with a single master because it only had to track metadata for a
relatively small number of large (64MB-chunk) files. A public object store has to track
**trillions** of small-to-huge objects across every customer:

![Metadata scaling: GFS's single master vs. S3-scale sharded metadata](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-9-metadata-service-scaling.png)

At that volume, the metadata layer (which object lives on which physical nodes) can't be one
machine's memory and request budget - it has to be **partitioned** the same way any other
huge key space is partitioned (3.4, typically by a hash of the bucket+key), with each
metadata shard itself replicated (3.5) for its own availability. In other words: to build an
object store at this scale, you end up running a distributed system just to track where the
files in your other distributed system live - metadata management is itself the hard,
distributed-systems part of the product, not an afterthought bolted onto "a place to put
files."

## When to use blob storage vs. a database

![Blob storage vs. database](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-9-blob-vs-database.png)

Blob storage: large (past roughly a megabyte), mostly-immutable objects fetched as a whole,
with no need to query *inside* their contents - images, video, backups, log archives, model
weights. Database: anything that needs querying by attributes, transactions, frequent small
in-place updates, or is simply small (a metadata row is cheaper and faster in a database
than as a tiny S3 object with its own request overhead). The common, correct pattern in
practice combines both, from 3.2's vertical-partitioning discussion: **store the blob's
bytes in object storage, store a row describing it (key, owner, size, timestamps, tags) in
a database**, and query the database to find which key to fetch.

## Other blob storage options, briefly

- **Cloudflare R2** - S3-API-compatible, and its headline difference is **zero egress
  fees** - you pay for storage and requests, not for data leaving the network, which flips
  the economics for read-heavy, bandwidth-heavy workloads compared to S3's per-GB egress
  cost.
- **Google Cloud Storage / Azure Blob Storage** - the other two hyperscalers' equivalents;
  same object model (bucket/container + key/blob name), broadly comparable feature sets and
  tiered-storage/lifecycle options, different IAM and pricing details per provider.
- **MinIO** - a self-hosted, open-source object store that speaks the S3 API - the choice
  when you need object storage on your own infrastructure (on-prem, air-gapped, or just
  cost-driven at very large scale) without giving up the S3 API your tooling already
  expects.

The practical takeaway: the **S3 API itself has become the de facto standard interface**
for object storage, independent of which vendor is actually storing the bytes - which is
exactly why this note's demo code, using the real `boto3` SDK, is meaningful even for
someone who never touches AWS S3 directly.

## Cheat sheet

```
MODEL         bucket + key, a FLAT namespace. "folders" are a UI illusion built
              from listing with prefix + delimiter (verified: CommonPrefixes),
              not real directories - "renaming a folder" = copy every key + delete.

STATELESS     app servers hold no file state -> any instance serves any request,
              trivial autoscaling/replacement, durability isn't tied to one disk.

ADVANTAGES    ~infinite capacity, huge tooling ecosystem (Spark/Trino/warehouses
              speak S3 natively - why it became the data lake standard), managed
              durability (erasure coding/replication, below).

DISADVANTAGES slower than local SSD/NVMe (network hop, throughput- not latency-
              optimized) - was EVENTUALLY consistent until Dec 2020 (check any
              non-AWS "S3-compatible" store's actual guarantee) - egress/request
              costs, not flat disk pricing.

ACCESS        bucket policy (JSON/IAM, modern default, key-pattern-level rules)
CONTROL       > ACL (legacy, coarse, account/group-level, off by default now)
              presigned URL: time-limited signed access to ONE object, no
              credentials needed by the requester, transfer bypasses your server.

DURABILITY    replication (Nx copies, simple, Nx storage cost) vs erasure coding
              (k+m chunks, any k reconstruct, ~1.5x storage for the same 2-failure
              tolerance as 3x replication) - more CPU to reconstruct, big $ savings
              at scale.

METADATA      GFS (3.1): 1 master, fine for few large files. Object-store scale:
SCALING       metadata itself sharded (3.4) + replicated (3.5) - a distributed
              system just to track where the other distributed system's data is.

BLOB vs DB    large + immutable + fetched whole + no query-by-content -> blob
              storage. needs queries/transactions/small updates, or is small ->
              database. Standard combo: bytes in blob storage, a row (key,
              metadata) in the database pointing at it.

OTHER         R2 (S3-compatible, zero egress fees) - GCS / Azure Blob (same
PROVIDERS     model, per-vendor details) - MinIO (self-hosted, S3 API). The S3
              API itself is the de facto standard, independent of the vendor.
```
