title: "3.5 Replication"
---

3.4 introduced read replicas as the cheap first move before sharding, and used
"replication" as the contrast case to sharding: full copies of the data, not slices of it.
This note is what's actually inside that box - how a copy stays in sync with the original,
what you trade to make that sync fast versus safe, and what can go visibly wrong for a user
when it isn't perfectly in sync (which, most of the time, it isn't).

## Why replicate at all

Two independent reasons, and it matters which one you're solving for:

- **Durability** - if the only copy of your data is on one disk, one disk failure is data
  loss. Multiple copies on independent machines mean a single failure loses nothing.
- **Availability and read scale** - a replica can serve reads while the primary is busy
  writing, or take over entirely if the primary goes down.

The baseline topology is **leader-follower** (also called primary-replica or
master-slave): one node accepts all writes, and the rest replay a stream of its changes.

![Leader-follower replication](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-5-leader-follower.png)

The leader ships its write-ahead log (3.1) to each follower, which replays it to
reconstruct the same state. This is the same WAL that already exists for crash recovery on
a single node - replication is, mechanically, "stream my WAL to someone else and have them
replay it too."

## Synchronous vs. asynchronous - proven live, not just described

The one decision that matters most: does the leader's `COMMIT` wait for a follower to
confirm the write before returning to the client, or not? Set up real streaming
replication - a primary and a standby built from a `pg_basebackup` of it - and watch both
modes directly.

**Asynchronous**: the leader commits and returns immediately; followers catch up
whenever they can. Deliberately catch a stale read by pausing the standby's WAL replay
mid-flight:

```python
import psycopg2

primary = psycopg2.connect(host="/path/to/primary/socket", port=5432, dbname="postgres")
primary.autocommit = True
pcur = primary.cursor()

replica = psycopg2.connect(host="/path/to/standby/socket", port=5433, dbname="postgres")
replica.autocommit = True
rcur = replica.cursor()

rcur.execute("SELECT pg_wal_replay_pause()")   # freeze the replica's replay
print("replica replay PAUSED")

pcur.execute("UPDATE ticker SET value = 12345 WHERE id = 1")
print("primary: UPDATE ticker SET value = 12345 -- COMMITTED")

rcur.execute("SELECT value FROM ticker WHERE id = 1")
print("replica read WHILE PAUSED:", rcur.fetchone()[0], " <- stale, primary already moved on")

rcur.execute("SELECT pg_wal_replay_resume()")
print("replica replay RESUMED")
rcur.execute("SELECT value FROM ticker WHERE id = 1")
print("replica read after resuming:", rcur.fetchone()[0], " <- caught up")
```

```
replica replay PAUSED
primary: UPDATE ticker SET value = 12345 -- COMMITTED
replica read WHILE PAUSED: 999  <- stale, primary already moved on
replica replay RESUMED
replica read after resuming: 12345  <- caught up
```

The primary's commit succeeded and returned instantly; for as long as replay was paused,
the replica kept serving `999` - genuinely, provably stale data, captured mid-flight, not
just described. Timed without the artificial pause, real (loopback) replication lag here
was about **1.24 ms** between the primary's commit and the standby reflecting it - tiny on
a local network, but the *mechanism* that produces multi-second lag under real network
conditions, replica overload, or a long-running query blocking replay is exactly this.

**Synchronous**: the leader's commit *waits* for a follower (`synchronous_standby_names` in
Postgres) to acknowledge before returning. Prove the cost of that wait by taking the
standby down entirely and issuing a write:

```python
import subprocess, threading, time, psycopg2

subprocess.run(["pg_ctl", "-D", "/path/to/standby", "stop", "-m", "fast"])

result = {}
def do_commit():
    conn = psycopg2.connect(host="/path/to/primary/socket", port=5432, dbname="postgres")
    conn.autocommit = True
    start = time.perf_counter()
    conn.cursor().execute("UPDATE ticker SET value = 77777 WHERE id = 1")  # sync commit
    result["elapsed"] = time.perf_counter() - start

t = threading.Thread(target=do_commit); t.start()
for waited in (1, 2, 3, 4):
    time.sleep(1)
    print(f"  {waited}s later: primary's COMMIT is",
         "returned" if "elapsed" in result else "BLOCKED - no synchronous standby available")

subprocess.run(["pg_ctl", "-D", "/path/to/standby", "-o", "-p 5433", "start"])
t.join(timeout=15)
print(f"commit finally returned, {result['elapsed']:.2f}s after being issued")
```

```
  1s later: primary's COMMIT is BLOCKED - no synchronous standby available
  2s later: primary's COMMIT is BLOCKED - no synchronous standby available
  3s later: primary's COMMIT is BLOCKED - no synchronous standby available
  4s later: primary's COMMIT is BLOCKED - no synchronous standby available
commit finally returned, 4.06s after being issued
```

Every write to the primary hung, unresponsive, for the entire time its one synchronous
standby was unreachable - and would have hung indefinitely if it had stayed down. This is
the trade-off in its most concrete form:

![Measured: async returns instantly (and can read stale), sync blocks until the standby acks](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-5-sync-vs-async-timeline.png)

**Asynchronous** never blocks the primary, at the cost of a real window where a replica -
and anyone reading from it - can be behind, and a crash of the primary before it ships its
latest writes can lose them. **Synchronous** guarantees a committed write is durable on at
least one other machine before the client hears "success," at the cost of the primary's
availability for writes being coupled to the synchronous replica's availability - proven
directly above. Most production systems land on a middle ground: synchronous to *one*
nearby, fast replica (bounding the worst case) and asynchronous to the rest (for read scale
and geographic distribution) - or async to everything and an accepted, monitored risk of a
small data-loss window on primary failure.

## Replication lag anomalies

The stale read above is one instance of a general family of problems that only exist
*because* replicas lag - worth naming individually, because "the replica was a little
behind" produces different bugs depending on exactly what a user does next:

- **Read-your-writes violation** - a user posts a comment (write goes to the leader), the
  page reloads and reads from a replica that hasn't caught up yet, and the user's own
  comment appears to have vanished. (Exactly what the pause/resume demo captured above,
  from the user's perspective.) Fix: route a user's own reads to the leader (or a replica
  known to be caught up) for some time window after they write.
- **Monotonic reads violation** - a user refreshes twice, hitting a more-caught-up replica
  first and a laggier one second, and sees data go *backwards* - a reply that was visible a
  moment ago disappears. Fix: pin each user to the same replica for their session (sticky
  routing), instead of load-balancing every request to a random one.
- **Consistent prefix violation** (multi-leader/partitioned systems especially) - if writes
  happen in a causal order (a question, then its answer), a reader can see the effect
  before the cause if replication delivers them out of order - the answer to a question
  that, as far as that reader can tell, was never asked. Fix: ensure causally related writes
  replicate in the order they were made, not just "eventually, in any order."

All three are symptoms of the same root cause (Part 1.5's consistency models, applied): a
replica is a *view* of the data as of some earlier point, and unless you do something
deliberate, nothing guarantees that point is recent, non-decreasing across requests, or
causally ordered.

## Multi-leader replication

Leader-follower has one write bottleneck and one single point of failure for writes.
**Multi-leader** replication accepts writes at more than one node - typically one leader
per datacenter/region, each replicating to the others - trading that bottleneck for a new
problem: **conflicts**.

![Multi-leader replication and conflicts](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-5-multi-leader.png)

If the same row is written on two leaders before either write has replicated to the other,
both are "valid" locally and something has to reconcile them once they meet. Common
resolutions: **last-write-wins** (attach a timestamp, higher wins - simple, but silently
discards one of the writes, which is a real correctness cost, not a free lunch);
**application-level merge** (both writes are kept and the app decides, e.g. "keep the
shopping cart union of both"); or **CRDTs** (Convergent Replicated Data Types) - data
structures deliberately designed so that merging two concurrently-modified copies always
has one well-defined, deterministic answer, with no coordination needed at merge time.
Multi-leader is the right shape when writes genuinely originate in multiple places that
can't afford to coordinate synchronously (multi-region, offline-first clients) - and the
cost is that conflict handling becomes a first-class part of the data model, not an edge
case.

## Leaderless replication and quorums

A third topology, used by Dynamo-style stores (Cassandra, Riak, and the design behind
DynamoDB): **no leader at all**. Any node can accept a write or serve a read, and
correctness comes from **quorums** instead of a designated leader.

![Leaderless replication with read/write quorums](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-5-leaderless-quorum.png)

With `N` replicas of each piece of data, a write is sent to all `N` but only needs `W`
acknowledgments to succeed; a read queries `R` replicas and returns the newest version seen
among them. The guarantee that makes this work: **`R + W > N`**. Since any write touches
`W` nodes and any read touches `R` nodes out of the same `N`, and `R + W > N` means those
two sets can't both be proper subsets that miss each other - **every read is guaranteed to
overlap at least one node that has the most recent write.** No coordinator, no single
leader, and the system tolerates `N - W` nodes being down and writes still succeed, or
`N - R` nodes down and reads still succeed - tunable per-operation, not a fixed
availability/consistency trade baked into the whole system the way leader-follower's
sync/async choice is.

This doesn't come for free: since replicas can genuinely disagree (a node that missed a
write, then comes back), leaderless systems lean on two more mechanisms to converge:

![Read repair and anti-entropy](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-5-read-repair.png)

- **Read repair** - when a read notices one of the `R` replicas it queried returned a
  stale version, it writes the newer value back to that replica right then, as a side
  effect of the read. Fixes stale replicas that happen to get read.
- **Anti-entropy** - a background process (often comparing Merkle tree hashes of each
  replica's data to cheaply find *which* keys differ, without transferring everything) that
  continuously repairs drift, including for keys nobody has happened to read recently.
  Without this, a replica that was down during a write and is never subsequently read for
  that key would stay wrong forever.

## Failover

Whatever the topology, a leader (or a synchronous replica) can die, and something has to
happen next:

1. **Detect** the failure - usually a heartbeat/timeout, tuned to avoid a false positive on
   a slow-but-alive node triggering an unnecessary failover.
2. **Elect** a replacement - the most caught-up follower is the natural choice (promoting a
   lagging one risks losing the writes between its position and the old leader's).
3. **Reconfigure** - clients and other followers need to learn the new leader's identity;
   this is often the same coordination-service mechanism (ZooKeeper/etcd, Part 3.6) used
   for shard membership in 3.4.
4. **Handle the old leader's return** - if it comes back, it may have writes the new leader
   never saw (in async replication, exactly the un-replicated tail from before the crash).
   These typically have to be discarded (**split-brain** avoidance) or reconciled, which is
   precisely the data-loss window asynchronous replication accepted back in the sync-vs-async
   trade-off above.

## Cheat sheet

```
WHY           durability (survive a disk/node loss) + availability & read scale
              (offload reads, survive a leader loss) - two different motivations.

TOPOLOGIES    leader-follower: 1 write bottleneck, simple, most common default
              multi-leader: writes at N nodes, trades the bottleneck for CONFLICTS
                            (last-write-wins / app merge / CRDTs)
              leaderless (Dynamo-style): no leader, quorums instead (below)

SYNC vs       async: commit returns instantly, replica catches up later
ASYNC         -> real, measured stale-read window; primary crash can lose the
              unreplicated tail
              sync: commit WAITS for a replica ack
              -> measured: primary write BLOCKS INDEFINITELY if that replica
              is unreachable. durability <-> write availability, no free lunch.
              common real answer: sync to one nearby replica, async to the rest.

LAG           read-your-writes violation: your own write looks like it vanished
ANOMALIES       -> fix: route your reads to the leader for a while after you write
              monotonic reads violation: a refresh goes "back in time"
                -> fix: sticky-route a user to the same replica
              consistent prefix violation: effect visible before its cause
                -> fix: preserve causal write order across replicas

QUORUMS       N replicas, W acks needed to write, R replicas read from.
              R + W > N  =>  every read overlaps a node with the latest write.
              tunable per op: lower W/R = more available, less consistent.
              converge via READ REPAIR (fix on read) + ANTI-ENTROPY (background,
              Merkle-tree diffing) - without both, a never-read stale replica
              stays wrong forever.

FAILOVER      detect (heartbeat/timeout) -> elect (most caught-up replica)
              -> reconfigure (clients + followers learn the new leader)
              -> reconcile the old leader's un-replicated tail on its return
              (split-brain risk) - the async replication trade-off made concrete.
```
