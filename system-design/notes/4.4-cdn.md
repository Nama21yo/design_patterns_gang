title: "4.4 CDN and edge caching"
---

4.1's list of caching levels named the CDN as the layer for static assets - images,
video, JS/CSS bundles, live-stream segments. This note is that layer specifically: why
geography is the whole point, how it decides what to cache and for how long, and the trick
that keeps a viral asset from overwhelming your actual origin.

## Why a CDN: geography is the latency win

A **content delivery network** is a set of caching servers distributed across many
physical locations worldwide - **points of presence (PoPs)** - so that a user's request is
answered by whichever PoP is geographically nearest to them, instead of always travelling
all the way to your one origin server:

![CDN geography](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-4-cdn-geography.png)

This matters because of 0.3's latency numbers directly: a round trip within the same
region is on the order of a few milliseconds; a round trip across a continent or an ocean
is on the order of 100-150ms. A user in Nairobi requesting an asset from an origin in
Virginia pays that full cross-ocean round trip on every request, unless something is
caching a copy physically closer to them. **Anycast routing** and geography-aware DNS are
what make "route this user to their nearest PoP" happen automatically, without the client
needing to know anything about where any PoP physically is.

## Population and expiry

CDNs use **lazy population** - the same default 4.1 recommends for most data - rather than
pre-pushing content everywhere: the first request for an asset at a given PoP is a miss,
pulled from your origin and cached there; every subsequent request at *that* PoP is served
straight from the edge until the entry expires:

![CDN population and expiry](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-4-cdn-population-expiry.png)

Expiry is controlled the same way as any other HTTP cache, via **`Cache-Control`**
response headers from your origin: `max-age` sets how long a value is fresh, `s-maxage`
sets a separate, shared-cache-specific max-age (letting you cache more aggressively at the
CDN than in an individual browser), and `stale-while-revalidate` (4.2) tells the CDN it can
keep serving a just-expired asset while it refreshes in the background instead of making
one unlucky requester pay for a fresh fetch. Getting these headers right *is*, in large
part, CDN configuration - the CDN is just enforcing whatever expiry policy your origin
declares.

## Origin shielding

Even with edge caching, a naive setup has every PoP independently take its own first miss
straight to the origin - if you have 50 PoPs worldwide, a newly-published, suddenly-popular
asset can produce 50 simultaneous origin requests (one per region's first miss), which is
4.2's cache-stampede problem again, just spread across geography instead of concurrency on
one machine.

![Origin shielding](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-4-origin-shielding.png)

**Origin shielding** designates one specific PoP (or a small mid-tier layer) as the single
path every other PoP's misses must funnel through before reaching the origin. Now the
origin sees at most **one** miss per asset, globally, no matter how many edge PoPs are
independently cold for it - the shield absorbs the fan-in the same way 4.2's stampede lock
coalesces concurrent requests into one, just applied across geography instead of across
threads.

## Popular CDN providers

![Widely-used CDN providers](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-4-cdn-providers.png)

Worth recognizing by name for an interview, not memorizing feature-by-feature: Cloudflare
(huge edge footprint, bundles security features like WAF/DDoS protection directly),
Akamai (one of the oldest and largest, heavy enterprise presence), Fastly (known for very
fast cache purges and strength on dynamic/API-shaped content, not just static assets),
Amazon CloudFront (the natural default inside an AWS-centric stack). Several of these
increasingly bundle CDN delivery with object storage directly - Cloudflare's R2 (4.9) is
the clearest example, pairing edge caching with S3-compatible storage and, notably, no
egress fees.

## What CDNs are used for

Static, cacheable, rarely-changing content is the core use case - images, video segments
(including live-stream chunks, cached and served the same way as any other asset once
they're produced), JS/CSS bundles, downloadable files. The unifying property across all of
these: the content is the same for every user who requests it (or at most varies by a
small number of variants, like image sizes) and doesn't depend on per-user application
state - exactly the property that makes something safe to cache in the first place (4.1's
staleness question), now applied at the scale of "the whole internet's worth of requesters"
instead of one application's cache.

## Cheat sheet

```
WHY           geography IS the latency win - a PoP near the user avoids the
              100-150ms cross-continent round trip (0.3) that hitting one
              distant origin would cost on every request. Anycast/DNS routes
              each user to their nearest PoP automatically.

POPULATION    lazy (4.1's default): first request at a given PoP = miss, pulled
& EXPIRY      from origin and cached there; later requests at that PoP hit.
              Expiry via Cache-Control: max-age, s-maxage (shared-cache-
              specific), stale-while-revalidate (4.2) - the CDN enforces
              whatever policy the origin declares in its headers.

ORIGIN        without it: every PoP's first miss hits origin independently -
SHIELDING     N simultaneous origin hits for one newly-popular asset (a
              geographically-spread cache stampede, 4.2). With it: one
              designated shield PoP funnels every other PoP's misses through
              itself first - origin sees at most 1 miss per asset, globally.

PROVIDERS     Cloudflare (huge edge network + bundled security) - Akamai
              (oldest/largest, enterprise) - Fastly (fast purges, strong on
              dynamic content) - CloudFront (AWS-native). Increasingly bundled
              with object storage (R2 + zero egress fees, 4.9).

USE CASES     static, same-for-everyone (or few-variant) content: images,
              video/live-stream segments, JS/CSS bundles, downloads - anything
              where per-user application state isn't part of the response.
```
