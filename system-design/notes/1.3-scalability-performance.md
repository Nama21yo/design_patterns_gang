1.1 named these as non-functional dimensions; this note gives each one its precise
definition, with the one distinction - latency vs. throughput - that trips people up most
often in an interview, made concrete with real numbers.

## Scalability

**Scalability** is a system's ability to handle growth - more users, more data, more
traffic - without a fundamental redesign. 3.4 already covers the two directions this takes
in full depth (vertical: a bigger machine, simple but has a real ceiling; horizontal: more
machines, no hard ceiling but real coordination cost) with a live Postgres partitioning
demo - not repeated here. What belongs in this note is the vocabulary: scalability is about
**growth over time**, distinct from performance (below), which is about how the system
behaves at a **given** load, not how that behavior changes as load increases.

![Vertical vs. horizontal scaling (full treatment in 3.4)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-4-vertical-vs-horizontal-scaling.png)

## Performance: latency vs. throughput

**Performance** is how fast and efficiently the system does its work right now, at a given
load. It splits into two numbers that get casually conflated constantly, and shouldn't be:

![The highway analogy: one car's travel time vs. how many cars pass per hour](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-3-latency-vs-throughput.png)

- **Latency** - the time for **one** operation, start to finish. 0.3's latency ladder (L1
  cache reference at ~1ns, a cross-continent round trip at ~150ms) is entirely a latency
  table.
- **Throughput** - the number of operations completed **per unit time** - requests/second,
  messages/second, rows/second.

The highway analogy makes the independence concrete: one car's door-to-door travel time is
its latency; the number of cars passing a given point per hour is the highway's throughput.
Adding more **lanes** raises throughput without changing any single car's travel time at
all - the two numbers can move completely independently of each other.

### The trade-off, made concrete: batching

The place this independence becomes a genuine design decision is **batching** - grouping
many small operations into one larger call to amortize a fixed per-call overhead (a network
round trip, a lock acquisition, a disk seek) across more work. This raises throughput, but
at a real latency cost: an item now has to *wait* for its batch to fill before it's
processed at all.

```python
OVERHEAD_MS = 5.0       # fixed cost per network call/round trip, regardless of size
PER_ITEM_MS = 0.1       # processing cost per item
N_ITEMS = 10_000


def no_batching():
    latency_per_item = OVERHEAD_MS + PER_ITEM_MS
    total_time = N_ITEMS * latency_per_item
    throughput = N_ITEMS / (total_time / 1000)
    return latency_per_item, throughput


def batching(batch_size, max_wait_ms):
    call_time = OVERHEAD_MS + PER_ITEM_MS * batch_size
    n_batches = N_ITEMS / batch_size
    total_time = n_batches * call_time
    throughput = N_ITEMS / (total_time / 1000)
    avg_wait_for_batch = max_wait_ms / 2
    latency_per_item = avg_wait_for_batch + call_time
    return latency_per_item, throughput


lat0, tput0 = no_batching()
print(f"no batching:        {lat0:.2f}ms per-item latency, {tput0:,.0f} items/sec throughput")

for batch_size, max_wait in [(10, 10), (100, 20), (1000, 50)]:
    lat, tput = batching(batch_size, max_wait)
    print(f"batch={batch_size:5d}, wait<={max_wait}ms: {lat:7.2f}ms per-item latency "
         f"({lat/lat0:.1f}x WORSE), {tput:,.0f} items/sec throughput ({tput/tput0:.1f}x BETTER)")
```

```
no batching:        5.10ms per-item latency, 196 items/sec throughput
batch=   10, wait<=10ms:   11.00ms per-item latency (2.2x WORSE), 1,667 items/sec throughput (8.5x BETTER)
batch=  100, wait<=20ms:   25.00ms per-item latency (4.9x WORSE), 6,667 items/sec throughput (34.0x BETTER)
batch= 1000, wait<=50ms:  130.00ms per-item latency (25.5x WORSE), 9,524 items/sec throughput (48.6x BETTER)
```

![Measured: bigger batches make every item's latency worse while throughput climbs up to 48.6x](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-3-batching-tradeoff-verified.png)

A batch of 1,000 pushes throughput nearly **49x** higher - but at the cost of every
individual item waiting **25.5x** longer before it's processed. Neither choice is
"correct" in the abstract: a log-ingestion pipeline (5.1) that cares about total events/sec
should batch aggressively; a user-facing API call that needs a sub-100ms response has no
room for that trade at all. Knowing which number a given component actually needs to
optimize for - and stating it explicitly as a non-functional requirement (1.1) - is the
entire point of pulling these two apart.

## Maintainability

![What "maintainable" actually asks](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-3-maintainability-cost.png)

**Maintainability** is how easily the system can be understood, changed, and operated over
its lifetime - independent of how well it performs on day one. Three practical questions
capture most of it: can a new engineer understand the system without relying on tribal
knowledge that only lives in one person's head? Can a change be made safely, with clear
boundaries and test coverage, rather than risking unrelated breakage somewhere unexpected?
And can it actually be **operated** day to day - clear runbooks, and the observability
(Part 6) to know something's wrong before a user reports it? A system that's blazingly fast
on launch day but that nobody can safely change six months later has a real, if harder to
quantify, cost - this is the dimension most likely to get silently traded away under
deadline pressure, and the one that's hardest to retroactively fix once enough shortcuts
have compounded.

## Cost

**Cost** is infrastructure spend per user or per request, measured against whatever budget
the system actually has to fit. It's a non-functional requirement exactly like the others -
worth stating explicitly rather than treating as an afterthought, since a design that's
technically excellent but blows a stated budget by 10x is a failed design, not a successful
one with a funding problem. 8.3 covers the fuller cost-modeling and trade-off-analysis
toolkit; the discipline that belongs here is simpler: name the cost constraint, with a
number, in the same breath as latency and availability targets during requirements
gathering (1.1), rather than discovering it only once the design is already built.
