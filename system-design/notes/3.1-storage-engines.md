title: "3.1 Storage engine internals: B-Tree vs LSM-tree"
---

Every database claim in 3.2-3.4 - "an index turns a scan into a lookup," "writes get
slower as you add indexes," "range scans are cheap" - has a mechanical reason underneath
it, and that reason lives on the physical disk. This note starts at the disk and builds up:
how bytes are actually addressed, why that shape forces a particular kind of data
structure, and the two structures (B-trees and LSM-trees) that dominate real storage
engines as a result.

## Start from the disk

A spinning hard disk is a stack of spinning platters, each with a read/write head that
moves in and out. Each platter surface is divided into concentric rings called **tracks**,
and each track is divided into fixed-size wedges called **sectors**. The intersection of
one track and one sector is a **block** (also called a physical page) - the smallest unit
the disk actually reads or writes; you cannot ask a disk for "3 bytes," only for a whole
block containing them.

![HDD structure: tracks, sectors, blocks](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-hdd-structure.png)

To read one specific byte, the system has to turn "give me byte offset N of this file"
into a physical location, then physically get the head there:

![From a byte offset to a physical disk operation](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-address-translation.png)

1. **Translate** the file offset into a block number (the file system's job), then the
   block number into a **(track, sector)** pair plus a byte offset within that sector (the
   disk controller's job).
2. **Seek** - physically move the head to the target track. This is by far the slowest
   step: a few milliseconds, because it's mechanical motion (Part 0.3's latency table: HDD
   seek ~2 ms - roughly a million times slower than an L1 cache reference).
3. **Rotational delay** - wait for the platter to spin around until the target sector
   passes under the head.
4. **Transfer** - read the whole block, then hand back just the requested bytes.

The number that falls out of this: **reading one random byte costs about the same as
reading one entire block**, because steps 2 and 3 (the expensive part) happen once per
block regardless of how much of that block you actually wanted. This single fact is the
root cause of almost everything in this note: **every storage engine is built to make
"how many blocks do I have to touch" as small as possible**, which means organizing data on
disk so that the things you need together sit physically near each other, and reading in
whole blocks instead of scattered bytes. (SSDs remove the seek/rotate mechanics - there's
no arm and no spinning platter, addressing is electronic - but they keep the "read/write in
fixed-size pages" shape, and writes are still meaningfully more expensive than reads
because of how flash erases work. The block-oriented thinking below applies to both.)

## How data gets organized on disk

Rows are packed into fixed-size blocks (Postgres and MySQL/InnoDB both default to 8-16 KB
blocks/pages). A table is just a sequence of these blocks. The database's whole job, at
this layer, is: given a query, figure out the *minimum* set of blocks that could possibly
contain the answer, and read only those.

**With no help**, the only correct way to find a row by some non-key value is to read every
block - a full scan (3.3 measured this directly: 129.7 ms and 666,666 rows read, to find
one). **With an index**, the database can jump straight to the right block(s). The rest of
this note is about how that jump is made possible.

## The idea, from first principles: indexing 100 records, then indexing the index

Say you have 100 records, sorted by key, spread across many blocks. Reading one specific
key by scanning is `O(records)`. Build a simple **sparse index**: one entry per block,
`(first key in this block) -> (block pointer)`. Now a lookup binary-searches the index
(small, often fits in memory) to find the right block, then reads that one block -
`O(log blocks)` instead of `O(records)`.

Scale up to 1,000 records. The index itself now has enough entries that scanning *it* is
getting slow too. The fix is the same idea, recursively: **build an index over the index** -
a second level whose entries are `(key range) -> (block of the level-1 index)`. Now a
lookup does two small jumps (level-2 index -> level-1 index -> data block) instead of one
big scan.

![Multi-level indexing: an index about the index](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-multilevel-index.png)

Keep this up as data grows - index the index, then index *that* - and you're building a
tree of indexes, level by level, where each level is small enough to search quickly and
points into the level below it. The natural question is: how many levels, when do you add
one, and how do you keep it balanced automatically as data is inserted and deleted? That
self-managing version of exactly this idea is a **B-tree**.

## Why not just a balanced m-way search tree?

An m-way search tree is the direct generalization of a binary search tree: instead of 2
children and 1 key per node, a node has up to `m` children and `m-1` keys. Balanced, this
gives `O(log_m n)` lookups - great. The problem is **insertion**:

![Why a plain balanced m-way tree fails as an on-disk index](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-mway-insertion-problem.png)

Inserting into a plain balanced search tree (the same issue a BST has) can leave one
subtree deeper than another. On disk, "deeper" directly means "more block reads for a
lookup that happens to fall in that subtree" - so an unbalanced tree means unpredictable,
sometimes-much-worse query costs, which is unacceptable for something meant to make every
lookup fast. You need a structure with a *guarantee*, enforced automatically on every
insert, that this can never happen.

## The B-tree

A B-tree is an m-way search tree with rules that make the "some subtree gets deeper" problem
structurally impossible:

![B-tree structural rules](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-btree-rules.png)

- Every node (except the root) has between `ceil(m/2)` and `m` children - never less than
  half full. This bounds how much the tree can be spread thin.
- The root is allowed as few as 2 children (it's exempt from the half-full rule, since it
  has nothing to be "half of").
- **Every leaf sits at exactly the same depth.** No exceptions, ever.
- The tree is built **bottom-up**: it doesn't grow by adding depth underneath an existing
  root the way a plain BST does. It grows by **splitting a node that overflowed** and
  pushing a key up - and only grows a level taller when that splitting reaches the root
  itself.

### Insertion, mechanically

![B-tree insertion: split and push up](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-btree-insertion-split.png)

1. Walk down from the root to the correct leaf, the same as a search.
2. Insert the key into that leaf, in sorted order.
3. If the leaf now holds more than `m-1` keys (overfull), **split** it at the median key:
   the left half stays, the right half becomes a new sibling node, and the median key gets
   pushed **up** into the parent as a new separator, with a new child pointer to the new
   sibling.
4. If that push makes the *parent* overfull, the parent splits too, pushing a key up again
   - this can cascade all the way up.
5. If the split reaches the root and the root itself overflows, a **brand new root** is
   created above it, with the old root's two halves as its two children. This is the only
   way a B-tree gains a level - and it happens at the top, uniformly, which is exactly why
   every leaf stays at the same depth no matter how much data is inserted, in what order.

### The numbers that make this fast

Fanout - how many children fit in one node - is set by how many `(key, pointer)` pairs fit
in one disk block:

```python
import math

def btree_stats(page_bytes, key_bytes, pointer_bytes, n_records):
    fanout = page_bytes // (key_bytes + pointer_bytes)
    height = math.ceil(math.log(n_records, fanout))
    return fanout, height

for label, page, key, ptr, n in [
    ("Postgres 8KB page, 8-byte bigint key", 8192, 8, 8, 10**9),
    ("MySQL InnoDB 16KB page, 8-byte key",   16384, 8, 8, 10**9),
    ("40-byte UUID-ish key, 8KB page",       8192, 40, 8, 10**9),
]:
    fanout, height = btree_stats(page, key, ptr, n)
    print(f"{label:42s} fanout~={fanout:>4}  height={height}  (n={n:,})")
```

```
Postgres 8KB page, 8-byte bigint key      fanout~= 512  height=4  (n=1,000,000,000)
MySQL InnoDB 16KB page, 8-byte key        fanout~=1024  height=3  (n=1,000,000,000)
40-byte UUID-ish key, 8KB page            fanout~= 170  height=5  (n=1,000,000,000)
```

With realistic block sizes, a B-tree over **one billion rows is only 3-4 levels deep** -
meaning a point lookup costs 3-4 block reads (and in practice fewer, since the top levels
stay cached in memory), not `log2(10^9) ≈ 30` the way a binary tree would need. This is the
entire payoff of a wide fanout: trade tree *height* (expensive, one disk read per level)
for node *width* (cheap, still one disk read per level, just for a bigger node). It's also
why key size matters operationally: the 40-byte key row above needs a taller tree for the
same data, purely because fewer keys fit in each block - a genuine, measurable reason
sequential integer keys are kinder to a B-tree than wide random keys like UUIDs (at the
cost of the insert hot-spotting problem covered in 3.3 and 3.4's reverse-index/consistent-
hashing discussions - there is no free lunch, only a choice of which cost you'd rather pay).

## B+-trees: what relational databases actually use

Almost no production relational database uses a plain B-tree for its indexes - they use a
variant, the **B+-tree**, with two differences:

![B+-tree structure](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-bplustree-structure.png)

1. **Only leaf nodes hold record pointers.** Interior nodes hold keys purely for routing -
   "go left if less than 30, otherwise go right" - and nothing else. A plain B-tree can
   short-circuit a search at an interior node if it happens to find the key there; a
   B+-tree never does, it always walks all the way to a leaf. That costs a little on
   average but buys something valuable: since interior nodes carry no record data, more
   keys fit per block, which increases fanout further and shrinks the tree.
2. **Leaf nodes are linked together**, left to right, as a linked list. A range scan
   (`WHERE age BETWEEN 20 AND 30`) finds the starting leaf once, then walks sideways along
   the leaf-level linked list - it never has to climb back up to an interior node and back
   down again for each subsequent value, unlike a plain B-tree.

And the sentence that ties this whole section together: **each node of a B+-tree is
designed to be exactly one disk block.** The tree's degree - how many keys/pointers fit per
node - isn't a design choice made in the abstract, it falls directly out of the storage
engine's page size, which is exactly the `fanout = page_bytes / (key_bytes +
pointer_bytes)` arithmetic above. The tree's shape *is* the disk's block structure, wearing
a search-tree's clothes.

## LSM-trees: optimizing for writes instead

A B+-tree updates data in place - overwriting the specific block a changed row lives in.
That's efficient for reads but means every write is, physically, a random write somewhere
in the middle of a large file - expensive, especially historically on spinning disks. The
**Log-Structured Merge-tree (LSM-tree)** takes the opposite trade: make writes cheap and
sequential, and pay for it on the read side instead.

![LSM-tree write and read paths](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-lsm-tree.png)

**Write path:**
1. Append the write to a **write-ahead log (WAL)** - a pure sequential append, as cheap as
   disk I/O gets, purely for crash recovery.
2. Insert it into an in-memory sorted structure, the **MemTable** (typically a skip list or
   a balanced tree) - fast, because it's RAM.
3. When the MemTable fills up, flush it to disk as an **SSTable** (Sorted String Table) - an
   immutable, sorted file. "Immutable" is key: it is never edited again, only eventually
   replaced wholesale, which is what keeps individual writes sequential and cheap.
4. In the background, **compaction** periodically merges multiple SSTables into fewer,
   larger ones, dropping keys that were overwritten or deleted along the way (an update is
   just a new write of the same key; a delete is a write of a special "tombstone" marker -
   nothing is ever edited in place).

**Read path:** a read for a key has to check the MemTable first (newest data), then each
SSTable level from newest to oldest, until it finds the key (or exhausts every level and
concludes the key doesn't exist). This is the cost being paid for cheap writes: a single
read can mean checking several structures instead of one B+-tree descent. Real systems
cushion this with a **Bloom filter** per SSTable (Part 4.5) - a quick, cheap "definitely not
here, skip this file" check that avoids touching most SSTables that don't contain the key.

**The trade-off in one line:** B+-trees optimize for reads (one structure, always up to
date, in-place updates) at the cost of write amplification and random I/O; LSM-trees
optimize for writes (sequential, cheap, batched) at the cost of read amplification (check
multiple levels) and background compaction work. This is exactly why LSM-trees are the
storage engine underneath most write-heavy NoSQL systems - Cassandra, RocksDB, LevelDB,
HBase - the wide-column and key-value stores from 3.2 that are built to absorb huge write
volume.

### BASE: the consistency model that tends to travel with LSM-based systems

Many of the same NoSQL systems built on LSM-trees also relax ACID (3.2) in favor of
**BASE**:

![BASE](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-base-pillars.png)

- **Basically Available** - the system keeps responding to requests even during a partial
  failure, even if that means returning slightly stale data rather than an error.
- **Soft state** - the stored state isn't necessarily final or fully settled; it can keep
  changing (via background compaction, replication, conflict resolution) even with no new
  writes arriving, as the system converges.
- **Eventual consistency** - if writes stop, given enough time, every replica converges to
  the same value. There is no promise about *when* - only that it happens eventually.

BASE isn't "ACID but worse" - it's a different, deliberate point on the same trade-off
spectrum 3.2 and 9.5 (composable aggregation) keep returning to: give up strict, immediate
consistency guarantees, get availability and horizontal write throughput in return. Whether
that's the right trade depends entirely on whether your application can tolerate reading
slightly-stale data - a "likes" counter usually can; a bank balance usually can't.

## Scaling storage across machines: the Google File System

Everything above describes a storage engine running on one machine. GFS (2003) is the
paper that showed how to build a storage layer across **thousands** of cheap, unreliable
machines instead - the design underneath Bigtable and the direct ancestor of HDFS, which
underlies most of the batch-processing pipeline in 9.5.

![GFS architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-1-gfs-architecture.png)

- **Files are split into fixed-size chunks** - 64 MB each, deliberately large (compared to
  a typical filesystem's 4 KB block) to keep per-chunk metadata small and to favor the
  large sequential reads/writes that batch-processing workloads actually do.
- **Chunkservers** are the workers: thousands of ordinary, unreliable machines, each
  storing chunks as plain local files. Since any one of them can and will fail, **every
  chunk is replicated** (usually 3x) across different chunkservers - if a disk dies, the
  data already exists safely elsewhere, and the master arranges a fresh replica to restore
  the replication factor.
- **The master holds metadata only** - which chunks make up which file, and which
  chunkservers currently hold each chunk. It never holds, touches, or routes the actual
  file data.
- **The client talks to the master once per lookup, then talks to chunkservers directly**:
  ask the master "where are the chunks for file X," get back a list of chunkserver
  addresses, then read or write the chunk data straight from/to those chunkservers. The
  master is on the critical path for metadata only, never for the data itself - which is
  exactly why it doesn't become the system's bottleneck even though there's only one of it
  (in the original design; production successors add master replication too).

The genuinely new idea GFS proved out: **you do not need expensive, individually reliable
hardware to store massive amounts of data reliably.** Assume every individual machine will
fail, build the replication and recovery into the software layer, and cheap commodity
hardware at large scale becomes more reliable *in aggregate* than a small number of
expensive, "reliable" machines ever could be - the same philosophy that shows up again in
9.5's partition replication and in Part 3.5's discussion of replicating a database shard.

## Cheat sheet

```
DISK          block = smallest unit read/written (one (track,sector), or an SSD page).
              reading 1 byte costs ~= reading 1 block (seek+rotate dominate on HDD).
              goal of every storage engine: minimize BLOCKS touched, read them sequentially.

INDEXING      linear scan -> sparse index (1 entry/block) -> index the index
              ("index about indexes") -> repeat -> that self-managed hierarchy,
              built to stay balanced under insertion, IS a B-tree.

M-WAY TREE    same idea as a BST, wider. Problem: insertion can unbalance a subtree
              -> unpredictable, sometimes-bad lookup cost. Unacceptable for disk.

B-TREE        every non-root node: ceil(m/2) to m children (never < half full)
              root: >= 2 children.  ALL leaves at the same depth, always.
              grows bottom-up: split an overfull node, push median key up;
              new root only created when a split reaches the top.
              measured: 8KB page, 8-byte key -> fanout~512 -> height 4 at 1e9 rows.

B+-TREE       what real relational DBs use. Interior nodes: routing keys only,
              no record pointers (denser -> higher fanout). Leaves: linked list
              -> range scans walk sideways, never revisit interior nodes.
              each node = one disk block; degree falls out of block size / key size.

LSM-TREE      WAL (durability) -> MemTable (in-RAM, sorted) -> flush to immutable
              SSTable on disk -> background compaction merges + drops dead keys.
              write: sequential, cheap.  read: check MemTable then each SSTable
              level (newest->oldest), cushioned by Bloom filters.
              trade: B+tree favors reads, LSM favors writes. LSM underlies most
              write-heavy NoSQL (Cassandra, RocksDB, LevelDB, HBase).

BASE          Basically Available, Soft state, Eventual consistency - the
              consistency model that pairs naturally with LSM-based NoSQL systems.

GFS           file -> 64MB chunks -> replicated 3x across cheap chunkservers.
              master = metadata only (chunk locations), never on the data path.
              client: ask master once, then talk to chunkservers directly.
              proved: cheap unreliable hardware + software-level fault tolerance
              beats a small number of expensive "reliable" machines, at scale.
```
