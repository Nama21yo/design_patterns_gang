title: "4.1 Caching strategies and eviction"
---

Parts 4.6-4.10 covered caching in hardware - the TLB, CPU caches, the whole memory
hierarchy. Everything in application-level system design is the exact same idea, one or
two orders of magnitude further from the CPU: a small, fast store standing in front of a
big, slow one. This note is that idea at the application layer - what caching actually
buys you, the read/write patterns for using one correctly, where to put one, and how it
decides what to keep when it's full.

## What caching is

**Caching is a way of storing data so you can avoid an expensive network call, disk read,
or computation the next time you need the same thing.** "Expensive" covers a lot of very
common operations:

- An API call to fetch a user's profile information.
- Reading one specific line out of a large file.
- A query that does five or six table joins to assemble one response.

The pattern is always the same: **store frequently-accessed data in a temporary, faster
location**, and check there first. If it's there (a **hit**), skip the expensive path
entirely. If not (a **miss**), do the expensive thing once, then store the result so the
*next* request doesn't have to. Concretely: profile information that would otherwise cost
five joins gets computed once and stored in Redis, keyed by user ID - every subsequent
request for that profile is a single fast lookup instead of a repeated multi-join query.

## The four read/write patterns

*How* the cache gets populated and kept in sync with the source of truth is a specific,
named design choice, not an afterthought:

![The four caching patterns](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-caching-patterns.png)

- **Cache-aside (lazy loading)** - the application owns the logic: check the cache; on a
  miss, read from the database itself and write the result into the cache. The cache
  doesn't know the database exists. Simple, and the most common default.
- **Read-through** - the application only ever talks to the cache; the cache itself is
  responsible for loading from the database on a miss. Same net effect as cache-aside, but
  the loading logic lives in the caching layer instead of scattered through application
  code.
- **Write-through** - writes go to the cache, and the cache synchronously writes through to
  the database before acknowledging. Keeps cache and DB always consistent, at the cost of
  paying the database's write latency on every write.
- **Write-behind (write-back)** - writes go to the cache and are acknowledged
  **immediately**; the cache flushes to the database later, asynchronously, often batched.
  Fast writes, at the cost of a window where the cache is ahead of the database - and real
  risk of data loss if the cache dies before that flush happens.

## Populating the cache: lazy vs. eager

A closely related, separate decision: *when* does data actually get loaded in?

![Lazy vs. eager population](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-population-lazy-eager.png)

- **Lazy population** - let the request come in, take the cache miss, then cache the
  result with some expiry. This is cache-aside/read-through as described above, and it's
  the right default for most data - caching a blog post, say - because you only ever cache
  what's actually been requested, no wasted work.
- **Eager population** - proactively push data into the cache *before* anyone asks,
  typically right when the underlying data changes: update the database and the cache
  together, rather than deleting/expiring the cache entry and waiting for the next reader
  to pay the cost of repopulating it. This matters most when you can predict a burst of
  demand: when a celebrity tweets, you don't want the first thousand readers each taking a
  cache miss and hammering the database simultaneously (4.2 covers this exact stampede
  scenario) - you push the new tweet into cache the moment it's written, so every one of
  those readers hits.

## Caching at every level

"The cache" is rarely one thing - a real system caches at several layers simultaneously,
each with a different scope and lifetime:

![Caching at different levels](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-caching-levels.png)

- **Client-side** - store frequently-accessed, near-constant data directly on the client
  (browser local storage, a mobile app's local cache), invalidated by time rather than by
  the server telling it to. Zero network cost on a hit, at the cost of every client
  independently deciding when its copy is stale.
- **CDN** - covered in depth in 4.4: static assets served from a point of presence near the
  user instead of your origin.
- **Load balancer** - can cache entire HTTP responses for identical incoming requests,
  serving repeats without the request ever reaching an application server at all - most
  useful for cacheable, unauthenticated, or anonymized responses.
- **Remote cache** - a centralized store like Redis or Memcached (4.3), shared by every
  application instance, for frequently-accessed data that's expensive to recompute or
  refetch.
- **Database-level** - not a separate system at all, just avoiding recomputation inside the
  database itself: a denormalized `total_posts` column updated incrementally instead of a
  `SELECT COUNT(*)` on every read, a materialized view instead of recomputing a join every
  time.

**Some things should never be served from cache at all** - an account balance is the classic
example: staleness there isn't an inconvenience, it's a correctness bug (someone could see
an old, higher balance and spend money that's no longer there). Before caching anything,
ask explicitly: is a slightly stale answer acceptable here, or does correctness require
reading the current value, every time? That staleness question is the one to keep coming
back to - a cache is a deliberate, bounded amount of incorrectness, traded for speed, and
worth naming that trade-off out loud rather than letting it be an accident.

*(Caching isn't restricted to RAM-based storage either, worth noting explicitly: an
authentication token cached in a browser's storage, or a live video stream segment cached
on a CDN edge server's disk, are both caching in exactly this sense - a temporary,
faster-to-reach copy of something more expensive to (re)obtain.)*

## Eviction: what to keep when the cache is full

A cache is, by construction, smaller than the data it could hold - so when it's full and a
new item needs a spot, something has to be evicted. Which policy you pick changes the hit
rate substantially, verified here on the same synthetic, Zipf-skewed access trace (a
realistic "a few items are much hotter than most" popularity distribution) and the same
cache capacity for every policy:

```python
import random
from collections import OrderedDict, defaultdict

CAPACITY = 20

def lru(trace):
    cache = OrderedDict(); hits = 0
    for k in trace:
        if k in cache:
            hits += 1; cache.move_to_end(k)
        else:
            if len(cache) >= CAPACITY: cache.popitem(last=False)
            cache[k] = True
    return hits

def fifo(trace):
    cache = OrderedDict(); hits = 0
    for k in trace:
        if k in cache:
            hits += 1                     # hit, but no reordering - FIFO ignores access order
        else:
            if len(cache) >= CAPACITY: cache.popitem(last=False)
            cache[k] = True
    return hits

def mru(trace):
    cache = OrderedDict(); hits = 0
    for k in trace:
        if k in cache:
            hits += 1; cache.move_to_end(k)
        else:
            if len(cache) >= CAPACITY: cache.popitem(last=True)   # evict the newest instead
            cache[k] = True
    return hits

def lfu(trace):
    cache, freq, hits = set(), defaultdict(int), 0
    for k in trace:
        freq[k] += 1
        if k in cache:
            hits += 1
        else:
            if len(cache) >= CAPACITY:
                cache.discard(min(cache, key=lambda x: freq[x]))
            cache.add(k)
    return hits

def random_evict(trace, rng):
    cache, hits = set(), 0
    for k in trace:
        if k in cache:
            hits += 1
        else:
            if len(cache) >= CAPACITY: cache.discard(rng.choice(list(cache)))
            cache.add(k)
    return hits

random.seed(11)
population = list(range(200))
weights = [1 / (i + 1) for i in range(200)]
trace = random.choices(population, weights=weights, k=5000)

n = len(trace)
results = {"LRU": lru(trace), "FIFO": fifo(trace), "MRU": mru(trace),
          "LFU": lfu(trace), "Random": random_evict(trace, random.Random(5))}
for name, hits in sorted(results.items(), key=lambda kv: -kv[1]):
    print(f"{name:8s}: {hits:4d} / {n} hits  ({hits/n:.1%})")
```

```
LFU     : 3001 / 5000 hits  (60.0%)
LRU     : 2344 / 5000 hits  (46.9%)
FIFO    : 2057 / 5000 hits  (41.1%)
Random  : 2052 / 5000 hits  (41.0%)
MRU     :  717 / 5000 hits  (14.3%)
```

![Measured hit rates by eviction policy](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-eviction-comparison.png)

- **LFU (Least Frequently Used)** wins here because it directly tracks what this specific
  trace actually is - a *stable* popularity distribution where the same items are hot the
  whole time. It has a real weakness this trace doesn't expose: a naive frequency counter
  never decays, so an item that was extremely popular yesterday and is irrelevant today can
  keep squatting on a cache slot on historical frequency alone.
- **LRU (Least Recently Used)** does solidly and, unlike LFU, adapts automatically as *what's
  hot* shifts over time - the trade-off runs the other way.
- **FIFO and Random** land close together - neither uses any signal about which items
  actually matter, so both do about as well as "some structure, no intelligence."
- **MRU (Most Recently Used)** - evict the item you *just* used - is deliberately the wrong
  answer for most workloads and performs accordingly, included here as the baseline for
  "what happens if you get the eviction target backwards." (It does have real, narrow uses:
  a full sequential scan you'll never revisit benefits from evicting what was just read,
  precisely because it's the least likely thing to be needed again.)

## Implementing LRU: a doubly linked list plus a hashmap

LRU is worth implementing by hand once, because the trick behind it - combining two
structures to get an operation neither gives you alone - shows up constantly. The
requirement is two operations, both **O(1)**: find a key's value, and know (and update)
which key was used least recently.

- A **hashmap** gives O(1) lookup by key, but no idea of "order."
- A **linked list** gives O(1) reordering (unlink and relink a node) *given a pointer to
  the node*, but O(n) to find that node by key in the first place.

Combine them: the hashmap maps `key -> node`, and the node lives in a doubly linked list
kept in recency order. A lookup uses the hashmap to jump straight to the node in O(1), then
the linked-list pointers to move it to the front in O(1) - no scanning either structure.

![LRU: hashmap for O(1) lookup + doubly linked list for O(1) reordering](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-lru-structure.png)

```python
class Node:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key, self.value = key, value
        self.prev = self.next = None


class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.map = {}                    # key -> Node, O(1) lookup
        self.head = Node()               # dummy head (most-recently-used side)
        self.tail = Node()               # dummy tail (least-recently-used side)
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):          # front = just after head = most recent
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        if key not in self.map:
            return -1
        node = self.map[key]
        self._remove(node)
        self._add_front(node)            # touched -> now most recently used
        return node.value

    def put(self, key, value):
        if key in self.map:
            node = self.map[key]
            node.value = value
            self._remove(node)
            self._add_front(node)
            return
        if len(self.map) >= self.capacity:
            lru = self.tail.prev          # least-recently-used = right before tail
            self._remove(lru)
            del self.map[lru.key]
        node = Node(key, value)
        self.map[key] = node
        self._add_front(node)

    def order_mru_to_lru(self):
        out, node = [], self.head.next
        while node is not self.tail:
            out.append(node.key)
            node = node.next
        return out


cache = LRUCache(3)
cache.put("a", 1); cache.put("b", 2); cache.put("c", 3)
print("after put a,b,c:       ", cache.order_mru_to_lru(), "(MRU -> LRU)")

cache.get("a")
print("after get(a):          ", cache.order_mru_to_lru())

cache.put("d", 4)                         # capacity 3, evicts LRU which is 'b'
print("after put d (evicts b):", cache.order_mru_to_lru())
print("get('b') after eviction:", cache.get("b"), "(gone, -1 = miss)")
print("get('a') still cached:  ", cache.get("a"))
```

```
after put a,b,c:        ['c', 'b', 'a'] (MRU -> LRU)
after get(a):           ['a', 'c', 'b']
after put d (evicts b): ['d', 'a', 'c']
get('b') after eviction: -1 (gone, -1 = miss)
get('a') still cached:   1
```

And, because a hand-traced example only proves a handful of operations are right, stress
tested against a brute-force reference (a plain list, `O(n)` per operation, obviously
correct but slow) over 20,000 randomized operations:

```python
import random
random.seed(0)

class BruteForceLRU:
    def __init__(self, capacity):
        self.capacity = capacity
        self.order = []
        self.data = {}
    def get(self, key):
        if key not in self.data:
            return -1
        self.order.remove(key)
        self.order.insert(0, key)
        return self.data[key]
    def put(self, key, value):
        if key in self.data:
            self.order.remove(key)
        elif len(self.data) >= self.capacity:
            del self.data[self.order.pop()]
        self.data[key] = value
        self.order.insert(0, key)

fast = LRUCache(50)
ref = BruteForceLRU(50)
mismatches = 0
for _ in range(20_000):
    key = random.randint(0, 200)
    if random.random() < 0.5:
        v = random.randint(0, 10**6)
        fast.put(key, v); ref.put(key, v)
    else:
        if fast.get(key) != ref.get(key):
            mismatches += 1
print(f"20,000 randomized get/put ops vs a brute-force reference: {mismatches} mismatches")
assert mismatches == 0
```

```
20,000 randomized get/put ops vs a brute-force reference: 0 mismatches
```

## LFU, FIFO, MRU, LRU-K, and random, briefly

- **LFU** - evict the least-frequently-accessed item; needs a frequency counter per key
  and, for O(1) eviction, a small auxiliary structure (a frequency-bucketed linked-list
  scheme is the classic O(1) LFU design) so finding the minimum isn't a linear scan.
- **FIFO** - evict whatever was inserted longest ago, full stop, ignoring access pattern
  entirely. A plain queue - cheapest to implement of all of them.
- **MRU** - evict whatever was used *most* recently. Same structure as LRU, evict from the
  opposite end.
- **Random** - evict a uniformly random resident item. Startlingly competitive with FIFO in
  practice (both verified above, within a percentage point of each other) precisely because
  neither one uses any real signal - "no intelligence, no bias" and "no intelligence,
  arbitrary bias" end up costing about the same.
- **LRU-K** - track not just the *last* access time, but the **Kth-to-last**. An item only
  becomes eligible to be treated as "hot" once it's been accessed K times; until then it
  sits on probation and can't push a genuinely hot item out.

### Why databases specifically favor LRU-K

A database buffer pool sees a workload plain LRU handles badly: an **index or table scan**
touches thousands of pages, each **exactly once**. Plain LRU treats "just touched" as
"recently used," so a single scan can evict an entire hot working set to make room for
pages that will never be read again. LRU-K (almost always **LRU-2** in practice) fixes this
directly: a page only earns a cache slot after its *second* access, so a one-time scan's
pages never displace anything that real, repeated traffic depends on.

```python
from collections import OrderedDict, defaultdict

CAPACITY = 35   # just above the hot set's size (30) - little slack for intruders

def lru(trace):
    cache = OrderedDict(); hits = 0
    for k in trace:
        if k in cache:
            hits += 1; cache.move_to_end(k)
        else:
            if len(cache) >= CAPACITY: cache.popitem(last=False)
            cache[k] = True
    return hits

def lru_k(trace, k=2):
    cache, access_count, hits = OrderedDict(), defaultdict(int), 0
    for key in trace:
        access_count[key] += 1
        if key in cache:
            hits += 1; cache.move_to_end(key)
        elif access_count[key] >= k:
            if len(cache) >= CAPACITY: cache.popitem(last=False)
            cache[key] = True
        # else: first touch - stays on probation, never enters the real cache
    return hits

hot_set = list(range(30))
next_scan_id = [1000]
def scan_batch(n):
    ids = list(range(next_scan_id[0], next_scan_id[0] + n)); next_scan_id[0] += n
    return ids

trace = []
for _ in range(40):
    trace += hot_set              # touch the whole hot working set once
    trace += scan_batch(10)       # then 10 brand-new, never-repeated scan pages

h_lru = lru(trace)
h_lruk = lru_k(trace, k=2)
print(f"plain LRU total: {h_lru} / {len(trace)} hits")
print(f"LRU-2 total:     {h_lruk} / {len(trace)} hits")
```

```
plain LRU total: 0 / 1600 hits
LRU-2 total:     1140 / 1600 hits
```

**Zero** hits for plain LRU - the interleaved one-time scan pages continuously evict the
hot set before it's touched again each round, a full thrash. LRU-2 protects the hot set
completely: single-touch scan pages never earn a cache slot at all, so hot pages are never
displaced by traffic that will never repeat.

![Hit rate on the hot set after scan interference: LRU vs. LRU-2](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-1-lruk-scan-resistance.png)

This is exactly why a database buffer pool - which has to survive being hit by an index
scan at any moment without losing its actual working set - reaches for LRU-K over plain
LRU by default, and why "index scan" is the concrete scenario to name if an interviewer
asks *why*.

## Cheat sheet

```
WHAT IT IS    store frequently-used data somewhere faster than its real source (an
              API call, a disk read, a multi-join query) - check there first.

PATTERNS      cache-aside: app checks cache, loads+fills on miss (most common).
              read-through: cache itself loads on miss, app never sees the miss.
              write-through: write goes to cache, synced to DB before acking -
              consistent, slower writes.
              write-behind: write acked immediately, flushed to DB later/async -
              fast writes, a data-loss window if the cache dies first.

POPULATION    lazy: fill on miss (default - only cache what's asked for).
              eager: push in proactively on write / predicted demand (a
              celebrity's tweet) - avoids a stampede of first-time misses.

LEVELS        client-side (time-invalidated, zero network cost) -> CDN (4.4) ->
              load balancer (whole-response caching) -> remote cache (Redis/
              Memcached, 4.3) -> database-level (denormalized column /
              materialized view). NEVER cache correctness-critical data
              (account balance) - always ask: is staleness acceptable here?

EVICTION      measured on a stable Zipf trace: LFU 60% > LRU 47% > FIFO/Random
              ~41% > MRU 14%. LFU wins when popularity is STABLE (weakness:
              stale historical frequency never decays); LRU adapts as hotness
              shifts. FIFO/Random: no real signal, similar performance.

LRU IMPL.     hashmap (key->node, O(1) lookup) + doubly linked list in recency
              order (O(1) move-to-front / evict-from-tail) = O(1) get AND put.
              Verified: 0 mismatches vs a brute-force reference over 20,000 ops.

LRU-K         needs K accesses (not 1) before a page counts as "recently used."
              Verified: interleaved with a one-time scan, plain LRU gets 0% hit
              rate on the hot set (fully thrashed); LRU-2 gets 95% (scan pages
              never earn a slot). This is why DATABASE buffer pools default to
              LRU-K, not plain LRU - an index/table scan is exactly this pattern.
```
