title: "0.3 Back-of-the-envelope estimation + latency numbers"
---

Estimation is the part people most want to skip and most regret skipping. It takes four
minutes and it turns the rest of the round from opinion into engineering. This note is
the toolkit: the numbers to memorize, the method, and worked examples you can copy.

## Why estimate at all

Two reasons, and neither is "get the exact number."

1. **It motivates every design choice.** "We need caching" is a hunch. "3 million read
   QPS at peak, and a single Postgres node handles maybe 10 thousand - so we need
   caching and read replicas" is an argument. Interviewers can tell the difference
   instantly.
2. **It is a signal by itself.** Doing a clean estimate shows you can reason
   quantitatively about systems. Fumbling it - or skipping it - is a red flag even if
   your architecture is fine.

You are aiming for the **right order of magnitude** (is it thousands, millions,
billions?) and a **visible method**. Round hard. Nobody cares if it is 6,000 or 6,400.

## The number toolkit

### Powers of two - data sizes

| Power | Value | Name | Rough |
|---|---|---|---|
| 10 | 1,024 | 1 KB | ~1 thousand |
| 20 | ~1.05 million | 1 MB | ~1 million |
| 30 | ~1.07 billion | 1 GB | ~1 billion |
| 40 | ~1.10 trillion | 1 TB | ~1 trillion |
| 50 | ~1.13 quadrillion | 1 PB | ~1 quadrillion |

So a number that is `2^n` bytes is about `10^(n * 0.3)`. Good enough: **KB, MB, GB, TB,
PB** each step up by ~1000.

Typical sizes to assume when the interviewer does not specify:

| Thing | Assume |
|---|---|
| ASCII char | 1 byte |
| A short text field (name, title) | ~50 bytes |
| A tweet / chat message / note line | 100 to 300 bytes |
| A JSON API response (small) | 1 to 10 KB |
| A metadata row (id, timestamps, a few fields, indexes) | ~1 KB |
| A thumbnail | ~10 KB |
| A web page (HTML only) | ~100 KB |
| A photo | ~200 KB to 2 MB |
| 1 minute of video (compressed, SD) | ~5 to 10 MB |
| A UUID | 16 bytes |
| An int64 / timestamp / pointer | 8 bytes |

### Powers of ten - users and traffic

Just SI: thousand (1e3), million (1e6), billion (1e9). DAU, QPS, requests/day all live
here.

### Time - the numbers that make the arithmetic easy

| Interval | Exact | Use this |
|---|---|---|
| Seconds per day | 86,400 | **1e5** (100,000) |
| Seconds per month | ~2.6 million | **2.5e6** |
| Seconds per year | ~31.5 million | **3e7** (or "pi times 1e7") |

**The 1e5 trick:** to go from "per day" to "per second," divide by 100,000. `1 billion
requests/day / 1e5 = 10,000 QPS`. To go the other way, multiply by 1e5. This one
substitution does 80% of estimation work.

### Latency numbers every engineer should know

Memorize the *shape* of this, not the digits:

![Latency numbers every engineer should know](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/0-3-latency-ladder.png)

| Operation | Time | In "1e" form |
|---|---|---|
| L1 cache reference | ~1 ns | |
| Branch mispredict | ~3 ns | |
| L2 cache reference | ~4 ns | |
| Mutex lock/unlock | ~17 ns | |
| Main memory (RAM) reference | ~100 ns | 1e2 ns |
| Compress 1 KB (Snappy) | ~2 us | |
| Read 1 MB sequentially from RAM | ~3 us | |
| Send 1 KB over 1 Gbps network | ~10 us | |
| SSD random read | ~16 us | 1e4 ns |
| Read 1 MB sequentially from SSD | ~50 us | |
| Round trip within the same datacenter | ~0.5 ms | 5e5 ns |
| Read 1 MB sequentially from disk (HDD) | ~0.8 ms | |
| HDD seek | ~2 ms | 2e6 ns |
| Round trip across the continent / ocean | ~150 ms | 1.5e8 ns |

The human-scale version, multiplying everything by a billion so 1 ns becomes 1 second:

![If 1 nanosecond were 1 second](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/0-3-latency-human.png)

**What to actually take away:**

- **Memory is ~100x faster than SSD, SSD is ~10 to 100x faster than a network round
  trip, HDD seeks are murder.** This is why caches exist and why you keep hot data in
  RAM.
- **Same-datacenter round trip is ~0.5 ms. Cross-continent is ~150 ms.** If your design
  does 20 sequential network calls to serve one request, that is 10 ms best case (same
  DC) or 3 seconds (cross-region). **Parallelize calls; never chain them; keep data
  close to compute.**
- **1 Gbps is ~125 MB/s.** A 10 Gbps NIC is ~1.25 GB/s. Use this for bandwidth sanity
  checks.
- **Reading 1 MB: ~3 us from RAM, ~50 us from SSD, ~1 ms from disk.** Sequential is
  vastly better than random on every medium.

## The estimation method

Always the same pipeline. Write it top to bottom on the board:

![From DAU to QPS, storage, bandwidth, and machine count](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/0-3-estimation-flow.png)

### 1. Traffic (QPS)

```
DAU  x  actions per user per day        = requests / day
requests per day  /  1e5                 = average QPS
average QPS  x  (2 to 10)                = peak QPS      <-- design to this
```

Split reads and writes - they usually differ by 10x to 1000x, and they hit different
parts of the system. Ask for or assume a **read:write ratio** (social/feed apps are
often 100:1 read-heavy; a logging or ingestion system is write-heavy).

The **peak factor** accounts for time-of-day and bursts. Use ~2x for a globally smooth
service, ~5x for a consumer app with a daily rhythm, ~10x or state it explicitly for
spiky/event-driven traffic (market open, breaking news, a product launch).

### 2. Storage

```
writes per day  x  bytes per record  x  replication factor   = bytes added per day
bytes per day  x  365  x  years of retention                  = total storage
```

- Include **indexes and overhead** - a rough rule is to multiply raw row size by ~2 to
  4 for a real database, or just round the row up to ~1 KB.
- **Replication factor** is usually 3 for a durable store. Say so.
- Project **1 year and 5 years**. Growth is the point - a design that works today and
  falls over in 18 months is a bad design.
- **Big binary objects go to blob storage (S3), not the database.** Keep only the
  metadata row in the DB. Estimate the two separately.

### 3. Bandwidth

```
peak QPS  x  average response size   = egress bytes/sec
peak write QPS  x  request size      = ingress bytes/sec
```

Compare against a NIC (1 Gbps = 125 MB/s) and against CDN offload for static content.

### 4. Memory for cache

Apply the **80/20 rule**: roughly 80% of requests hit 20% of the data. Estimate the
size of that hot set for a day (or an hour) and ask whether it fits in RAM on a few
nodes. A modern cache node holds tens to hundreds of GB.

```
daily read volume in bytes  x  0.2   = hot set to cache
```

### 5. Number of machines

Two independent estimates - take the larger:

```
peak QPS  /  QPS one server handles        = servers for compute
total storage  /  storage per node          = nodes for data
```

Rules of thumb for "what one box handles" when you have nothing better: a simple
stateless service ~10k to 50k QPS; a SQL database ~5k to 15k write QPS; Redis ~100k+
ops/sec; a Kafka broker ~100s of MB/s. State your assumption; the interviewer will
correct it if it matters.

## Availability math

"How many nines" translates directly to a downtime budget:

![Availability and allowed downtime](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/0-3-availability.png)

Two composition rules you will use in the bottlenecks phase:

- **Components in series multiply.** If a request must pass through 4 services that are
  each 99.9% available, the path is `0.999^4 = 99.6%` - worse than any single piece.
  Every hop you add costs availability.
- **Redundant copies in parallel improve it.** Two independent replicas that are each
  99% available give `1 - 0.01^2 = 99.99%`. This is *why* you replicate.

So: fewer hops on the critical path, and redundancy on each hop.

## Worked example 1 - Twitter

Narrate it exactly like this at the board:

![Twitter back-of-the-envelope](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/0-3-worked-twitter.png)

- Assume 300M DAU, 2 tweets written per user per day, read:write = 100:1.
- **Writes:** `300M x 2 = 600M tweets/day`. `/ 1e5 = 6,000 writes/sec` average. `x5
  peak = 30,000 writes/sec`.
- **Reads:** `100 x 600M = 60B timeline reads/day`. `/ 1e5 = 600,000 reads/sec`
  average, so **~3M reads/sec at peak**.
- **Storage (text):** `600M x ~300 bytes = ~180 GB/day` raw, call it ~65 TB/year, ~325
  TB over 5 years. Media goes to a blob store and dwarfs this - estimate separately if
  it is in scope.
- **Implication - say this out loud:** "3M read QPS cannot touch a database, so
  timelines are served from cache and precomputed by fanning out on write. 65 TB/year
  means the tweet store is partitioned, not a single node." Now the design writes
  itself.

## Worked example 2 - a URL shortener

- Assume 100M new URLs/day. `/ 1e5 = 1,000 writes/sec`. Reads at 100:1 = 100,000
  reads/sec, `x3 peak = 300,000 reads/sec`.
- **Storage:** row = short code + long URL + metadata ~ 500 bytes. `100M x 500 B = 50
  GB/day` -> ~18 TB over 5 years with retention. Fits comfortably on a small
  partitioned store; the whole working set can even be cached.
- **Implication:** read-dominated, tiny records, simple key lookup -> a key-value store
  plus an aggressive cache; the write path just needs a unique-ID generator.

## Worked example 3 - a market-data / stock-alert feed (Bloomberg flavor)

- Assume 10,000 symbols, each ticking ~10 updates/sec at active times ->
  **~100,000 price updates/sec** ingest, bursting to maybe 500k at the open.
- 1M users with alert rules, ~5 rules each = 5M rules. On each tick you must find
  matching rules for that symbol: index rules by symbol, so a tick touches only the
  rules for that one symbol (5M / 10k = ~500 rules per symbol on average).
- **Fan-out:** if 1% of ticks trigger a notification, that is ~1,000 notifications/sec
  steady, spiking hard on volatile moves - the notification pipeline must absorb bursts
  (queue + workers), not process inline.
- **Storage:** if you retain every tick, `100k/sec x 1e5 = 1e10 ticks/day` at ~30
  bytes = ~300 GB/day -> a time-series store with downsampling and tiered retention,
  not a general-purpose DB. This is exactly the "rows grow forever, how do you handle
  retention" follow-up from 10.4.
- **Implication:** ingest and matching are the hard part (100k+/sec, low latency,
  ordered per symbol); delivery must be asynchronous and burst-tolerant; raw history
  needs a retention/rollup policy from day one.

## Whiteboard technique

- **Lay it out top-to-bottom in one column:** assumptions, then writes, then reads, then
  storage, then bandwidth, then the implication. Leave the assumptions visible so you
  can revisit them.
- **Round to one significant figure and to powers of ten.** `287M -> 300M`. `86,400 ->
  1e5`. Do the arithmetic on round numbers.
- **Keep units on every line.** `600M tweets/day`, not `600M`. Unit errors are the only
  way to be wrong by 10^5.
- **Always end with the implication.** The number is not the point; "therefore we need
  X" is the point. If a number does not change a design decision, you do not need it.
- **If the interviewer hands you a number, use theirs.** If they say "assume you
  decide," state your assumption and keep moving - do not fish for confirmation.
- **Time-box it to ~4 minutes.** If you are deriving a fifth decimal place, you are over
  it.

## One-page cheat sheet

```
TIME          1 day = 1e5 s     1 month = 2.5e6 s     1 year = 3e7 s
              per-second = per-day / 1e5

SIZES         char 1 B   id/int64 8 B   uuid 16 B   metadata row ~1 KB
              message 100-300 B   API resp 1-10 KB   photo ~1 MB   SD video ~7 MB/min
              KB -> MB -> GB -> TB -> PB, each ~1000x

BANDWIDTH     1 Gbps = 125 MB/s        10 Gbps = 1.25 GB/s

LATENCY       RAM read ~100 ns        SSD random read ~16 us
              same-DC round trip ~0.5 ms     cross-continent ~150 ms
              => parallelize calls, never chain, keep data near compute

QPS           DAU x actions/day / 1e5 = avg QPS ;  x2-10 = peak QPS
              split reads vs writes ; design to peak

STORAGE       writes/day x row bytes x RF(=3) x 365 x years ; project 1y and 5y
              blobs -> object store, only metadata in the DB

CACHE         hot 20% of daily reads -> does it fit in RAM on a few nodes?

MACHINES      max( peakQPS / per-box-QPS , totalStorage / per-node-storage )
              stateless svc ~10-50k QPS   SQL ~5-15k wQPS   Redis ~100k+ ops/s

AVAILABILITY  99% = 3.65 d/yr   99.9% = 8.8 h/yr   99.99% = 52 min/yr   99.999% = 5 min/yr
              series: multiply (more hops = worse)   parallel redundancy: 1-(1-a)^n (better)
```
