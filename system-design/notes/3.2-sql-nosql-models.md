---

Picking a database is picking a set of trade-offs, permanently, early, for a component
that's expensive to migrate later. This note builds the vocabulary to make that choice
deliberately: what a relational database actually buys you (and what it costs), what the
NoSQL alternatives are optimizing for instead, and a repeatable way to choose between them
in an interview.

## Why relational databases exist, and what they actually buy you

The relational model and the transaction concept it's built around came out of banking and
finance in the 1970s (System R, at IBM) - domains where "the money must never just
disappear" is not a nice-to-have, it's the entire point of the software. A transfer between
two accounts has to either fully happen or fully not happen; a system that could leave money
half-moved is not a database bug, it's a business catastrophe. That origin is why the
guarantee a relational database sells you is called **ACID**.

![The four ACID guarantees](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-2-acid-pillars.png)

### Atomicity

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- debit
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- credit
COMMIT;
```

Everything between `BEGIN` and `COMMIT` is one indivisible unit. If the process crashes
after the debit but before the credit, the database guarantees that on recovery, *neither*
statement is visible - not that the debit "already happened, we'll fix the credit later."
Atomicity is what lets you write multi-step logic without personally handling every partial-
failure interleaving.

### Consistency

The data is never allowed to violate its declared rules, no matter what sequence of
transactions ran - constraints (`NOT NULL`, `UNIQUE`, `CHECK`, foreign keys), cascades
(`ON DELETE CASCADE`), and triggers are all enforced on every commit, automatically. Note
this "C" is different from the "C" in CAP (Part 1.4) - here it means *your application's
invariants hold*, not *every reader sees the same value at the same instant*.

### Isolation

When multiple transactions run at the same time, isolation controls how much of one
transaction's in-progress changes another transaction can see. This is the deepest of the
four, worth its own section - and it's the one most engineers get wrong by assuming
"isolated" means "completely invisible until commit," which is only true at the strictest
level.

### Durability

Once a transaction commits, it survives - a crash one millisecond later cannot undo it. In
practice this means the commit doesn't return to the caller until the change is on durable
storage, typically via a write-ahead log (Part 3.1) that's `fsync`'d before the commit
acknowledges.

## Isolation levels: the three anomalies, and the four levels that prevent them

To talk about isolation precisely, first name the three concurrency anomalies that weaker
isolation permits:

- **Dirty read** - transaction B reads a row that transaction A has modified but not yet
  committed. If A then rolls back, B just read data that, as far as the database is
  concerned, never existed.
- **Non-repeatable read** - transaction A reads a row, transaction B commits an update to
  that same row, and when A reads it again *in the same transaction*, it gets a different
  value.
- **Phantom read** - transaction A runs a query with a `WHERE` clause, transaction B
  inserts (or deletes) a row that matches that condition and commits, and when A re-runs the
  same query, it gets a different set of rows.

The four standard isolation levels are ordered from loosest/fastest to strictest/slowest,
and each one is defined by which of these three anomalies it rules out:

![Isolation levels vs. the anomalies they prevent](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-2-isolation-matrix.png)

- **Read Uncommitted** - no protection at all. A transaction can see another transaction's
  uncommitted writes.
- **Read Committed** - a read only ever sees data from transactions that have already
  committed. But two reads of the same row *within one transaction* can still return
  different values, because each individual read takes a fresh look at "what's committed
  right now."
- **Repeatable Read** - a transaction takes a consistent snapshot at the start and keeps
  reading from it; re-reading the same row always returns what it returned the first time.
- **Serializable** - the strongest level: the database guarantees the outcome is
  *equivalent to some serial (one-at-a-time) execution* of the concurrent transactions, full
  stop. In practice this is implemented either with pervasive locking ("every read is a
  locking read," as a simple mental model) or, in modern databases, by detecting
  conflicting access patterns and aborting one transaction with a serialization error for
  the application to retry.

For most application code, **Repeatable Read is the sweet spot** and is a very common
default - you rarely need to hand-pick a different level. (Know your engine's actual
default, though: Postgres defaults to Read Committed; MySQL/InnoDB defaults to Repeatable
Read. Same names, different defaults - always worth confirming rather than assuming.)

### Proving it - live, on real databases

Textbook tables are one thing; here is what actually happens, verified against a throwaway
local Postgres 16 instance and a throwaway local MariaDB/InnoDB instance, two transactions
at a time (`pip install psycopg2-binary pymysql`; point the connection strings at your own
local databases to reproduce this):

```python
import psycopg2
import pymysql

def pg_conn(isolation=None):
    """A fresh Postgres connection/transaction. isolation: e.g. 'READ COMMITTED',
    'REPEATABLE READ', 'SERIALIZABLE' (Postgres treats 'READ UNCOMMITTED' as an
    alias for 'READ COMMITTED' - there is no real Read Uncommitted in Postgres)."""
    c = psycopg2.connect(host="localhost", dbname="postgres", user="postgres")
    c.autocommit = False
    if isolation:
        c.set_session(isolation_level=isolation)
    return c

def my_conn(isolation="READ UNCOMMITTED"):
    """A fresh MySQL/MariaDB connection/transaction."""
    c = pymysql.connect(host="localhost", user="root", database="testdb", autocommit=False)
    with c.cursor() as cur:
        cur.execute(f"SET SESSION TRANSACTION ISOLATION LEVEL {isolation}")
    return c
```

**Dirty read** - MySQL/InnoDB genuinely allows this at Read Uncommitted. Postgres cannot,
*at any level*, because of the aliasing noted above:

```python
# fixture: both databases have a table `accounts(id INT PRIMARY KEY, balance INT)`
# with one row (1, 100) before every demo below.
def reset_balance_both():
    p = pg_conn(); p.cursor().execute("UPDATE accounts SET balance = 100 WHERE id = 1")
    p.commit(); p.close()
    m = my_conn(); m.cursor().execute("UPDATE accounts SET balance = 100 WHERE id = 1")
    m.commit(); m.close()

reset_balance_both()
print("=== MySQL/InnoDB at READ UNCOMMITTED ===")
t1, t2 = my_conn(), my_conn()
c1, c2 = t1.cursor(), t2.cursor()
c1.execute("UPDATE accounts SET balance = 999 WHERE id = 1")   # T1: no commit yet
print("T1 updated balance to 999 (NOT committed yet)")
c2.execute("SELECT balance FROM accounts WHERE id = 1")        # T2 reads mid-T1
print("T2 reads balance:", c2.fetchone()[0], " <- dirty read if 999")
t1.rollback()                                                  # T1 changes its mind
print("T1 rolled back (that 999 never really happened)")
c2.execute("SELECT balance FROM accounts WHERE id = 1")
print("T2 reads again (same tx):", c2.fetchone()[0])

print("\n=== Same experiment on Postgres, isolation level 'READ UNCOMMITTED' ===")
t1, t2 = pg_conn(isolation="READ UNCOMMITTED"), pg_conn(isolation="READ UNCOMMITTED")
c1, c2 = t1.cursor(), t2.cursor()
c1.execute("UPDATE accounts SET balance = 999 WHERE id = 1")
print("T1 updated balance to 999 (NOT committed yet)")
c2.execute("SELECT balance FROM accounts WHERE id = 1")
print("T2 reads balance:", c2.fetchone()[0], " <- dirty read would show 999")
t1.rollback()
print("T1 rolled back")
c2.execute("SELECT balance FROM accounts WHERE id = 1")
print("T2 reads again (same tx):", c2.fetchone()[0])
```

```
=== MySQL/InnoDB at READ UNCOMMITTED ===
T1 updated balance to 999 (NOT committed yet)
T2 reads balance: 999  <- dirty read if 999
T1 rolled back (that 999 never really happened)
T2 reads again (same tx): 100

=== Same experiment on Postgres, isolation level 'READ UNCOMMITTED' ===
T1 updated balance to 999 (NOT committed yet)
T2 reads balance: 100  <- dirty read would show 999
T1 rolled back
T2 reads again (same tx): 100
```

MySQL's T2 genuinely saw the phantom `999` - a value that was rolled back and never
existed as far as any other observer is concerned. Postgres's T2 never saw it at all.

**Non-repeatable read** - Postgres, same two rows, two isolation levels:

```python
def reset_balance():
    setup = pg_conn(); setup.cursor().execute("UPDATE accounts SET balance = 100 WHERE id = 1")
    setup.commit(); setup.close()

for level in ("READ COMMITTED", "REPEATABLE READ"):
    reset_balance()
    print(f"=== Postgres at {level} ===")
    t1, t2 = pg_conn(isolation=level), pg_conn()
    c1, c2 = t1.cursor(), t2.cursor()
    c1.execute("SELECT balance FROM accounts WHERE id = 1")
    print("T1 first read:", c1.fetchone()[0])
    c2.execute("UPDATE accounts SET balance = balance + 50 WHERE id = 1")
    t2.commit()
    print("T2 committed balance += 50")
    c1.execute("SELECT balance FROM accounts WHERE id = 1")
    print("T1 second read (same transaction):", c1.fetchone()[0])
    t1.rollback()
```

```
=== Postgres at READ COMMITTED ===
T1 first read: 100
T2 committed balance += 50
T1 second read (same transaction): 150   <- changed mid-transaction

=== Postgres at REPEATABLE READ ===
T1 first read: 100
T2 committed balance += 50
T1 second read (same transaction): 100   <- unchanged: T1 is reading its own snapshot
```

**Phantom read** - same idea, but with an `INSERT` and a `COUNT(*) WHERE status =
'pending'` instead of a single row update:

```python
def reset_orders():
    setup = pg_conn(); cur = setup.cursor()
    cur.execute("DELETE FROM orders")
    cur.execute("INSERT INTO orders (status) VALUES ('pending'), ('pending'), ('shipped')")
    setup.commit(); setup.close()

for level in ("READ COMMITTED", "REPEATABLE READ"):
    reset_orders()
    print(f"=== Postgres at {level} ===")
    t1, t2 = pg_conn(isolation=level), pg_conn()
    c1, c2 = t1.cursor(), t2.cursor()
    c1.execute("SELECT count(*) FROM orders WHERE status = 'pending'")
    print("T1 first count:", c1.fetchone()[0])
    c2.execute("INSERT INTO orders (status) VALUES ('pending')")
    t2.commit()
    print("T2 inserted a new pending row and committed")
    c1.execute("SELECT count(*) FROM orders WHERE status = 'pending'")
    print("T1 second count (same transaction):", c1.fetchone()[0])
    t1.rollback()
```

```
=== Postgres at READ COMMITTED ===
T1 first count: 2
T2 inserted a new pending row and committed
T1 second count (same transaction): 3   <- the phantom row is visible

=== Postgres at REPEATABLE READ ===
T1 first count: 2
T2 inserted a new pending row and committed
T1 second count (same transaction): 2   <- phantom NOT visible
```

That last result is the interesting one: the SQL standard only *requires* Repeatable Read to
stop non-repeatable reads, and formally still allows phantoms at that level. But Postgres
implements Repeatable Read as a genuine whole-transaction MVCC snapshot (true snapshot
isolation), which happens to block phantoms too - stricter than the standard demands. Don't
assume the standard's table is the ground truth for your specific database; confirm it, the
same way we just did.

### So why does Serializable exist at all, if snapshots already stop phantoms?

Because snapshot isolation (what Postgres's Repeatable Read gives you) can still allow a
subtler anomaly called **write skew**: two transactions each read overlapping data, each
independently and correctly conclude their own write is safe based on what they read, and
both commit - but the combination of both writes together violates an invariant that
neither transaction's *individual* logic ever checked.

Concrete, verified example: a `doctors` table with an `on_call` flag, and a business rule
"at least one doctor must always stay on call." Alice and Bob are both on call. Both decide,
independently, to go off duty:

```python
import psycopg2

def reset_doctors():
    setup = pg_conn(); cur = setup.cursor()
    cur.execute("UPDATE doctors SET on_call = true")
    setup.commit(); setup.close()

def try_go_off_call(level):
    reset_doctors()
    print(f"=== Postgres at {level} ===")
    t1, t2 = pg_conn(isolation=level), pg_conn(isolation=level)
    c1, c2 = t1.cursor(), t2.cursor()

    c1.execute("SELECT count(*) FROM doctors WHERE on_call")
    n1 = c1.fetchone()[0]
    print(f"T1 (alice) sees {n1} on-call doctors -> "
         f"{'safe to go off-call' if n1 > 1 else 'must stay'}")
    c2.execute("SELECT count(*) FROM doctors WHERE on_call")
    n2 = c2.fetchone()[0]
    print(f"T2 (bob)   sees {n2} on-call doctors -> "
         f"{'safe to go off-call' if n2 > 1 else 'must stay'}")

    c1.execute("UPDATE doctors SET on_call = false WHERE name = 'alice'")
    c2.execute("UPDATE doctors SET on_call = false WHERE name = 'bob'")

    try:
        t1.commit()
        print("T1 (alice going off-call) COMMITTED")
    except psycopg2.errors.SerializationFailure as e:
        t1.rollback()
        print("T1 got a SERIALIZATION FAILURE:", str(e).splitlines()[0])
    try:
        t2.commit()
        print("T2 (bob going off-call) COMMITTED")
    except psycopg2.errors.SerializationFailure as e:
        t2.rollback()
        print("T2 got a SERIALIZATION FAILURE:", str(e).splitlines()[0])

try_go_off_call("REPEATABLE READ")
try_go_off_call("SERIALIZABLE")
```

```
=== Postgres at REPEATABLE READ ===
T1 (alice) sees 2 on-call doctors -> safe to go off-call
T2 (bob)   sees 2 on-call doctors -> safe to go off-call
T1 (alice going off-call) COMMITTED
T2 (bob going off-call) COMMITTED
FINAL on-call count: 0   (INVARIANT VIOLATED - zero doctors on call!)

=== Postgres at SERIALIZABLE ===
T1 (alice) sees 2 on-call doctors -> safe to go off-call
T2 (bob)   sees 2 on-call doctors -> safe to go off-call
T1 (alice going off-call) COMMITTED
T2 got a SERIALIZATION FAILURE and had to retry: could not serialize access due to
read/write dependencies among transactions
FINAL on-call count: 1   (invariant held)
```

Neither transaction ever read a dirty value, a non-repeatable value, or a phantom row -
each one, in isolation, did exactly the right thing given what it saw. The bug only exists
in the *combination*. Repeatable Read/snapshot isolation cannot catch this by construction,
because nothing about either transaction's read set changed during its lifetime. Only
Serializable - which tracks these read/write dependencies across concurrent transactions
and aborts one of them - closes this gap. The cost is real: your application needs a
retry loop around serializable transactions, and throughput drops under contention. This is
exactly the kind of trade-off to name explicitly if an interviewer pushes on "what could go
wrong with your locking/consistency approach."

## The relational model, briefly

Data is organized into tables (relations) of rows with a fixed schema, related to each
other by keys rather than by physical nesting. **Normalization** is the discipline of
structuring those tables so each fact is stored exactly once - a customer's address lives
in one `customers` row, not copied into every `order` row - which makes updates
consistent by construction (change it once, it's correct everywhere) at the cost of needing
a `JOIN` to reconstruct a full picture. (The opposite move, **denormalization** -
duplicating data to avoid joins - trades that consistency-by-construction for read speed,
and shows up constantly in NoSQL modeling below.)

Pick relational when: the data's relationships and constraints matter as much as the data
itself, you need multi-row/multi-table transactions, you need ad-hoc queries and joins you
can't fully predict in advance, and the working set is a size a small number of (possibly
replicated) nodes can hold - relational databases scale up very well and out much less
easily than the NoSQL stores below.

## NoSQL: not one thing, several different trade-offs

"NoSQL" is a negative definition - "not a relational database" - covering several distinct
data models that give up some of ACID/relational guarantees deliberately, in exchange for
horizontal scalability, schema flexibility, or a much simpler (and faster) access pattern.
Most NoSQL stores are built to shard out of the box, unlike a relational database where
sharding is something you bolt on yourself (Part 3.4).

![Where each data model sits on scalability vs. query flexibility](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-2-data-model-quadrant.png)

### Document databases (MongoDB, Elasticsearch)

Store self-contained, JSON-like documents rather than normalized rows. Two things make this
genuinely different from relational, not just "SQL with curly braces":

- **Partial updates.** A relational `UPDATE` rewrites (conceptually) a whole row. A document
  store can update one nested field in place: `db.products.updateOne({_id: "p1"}, {$set:
  {"price": 29.99}})` touches only `price`, leaving the rest of a large nested document -
  reviews, variants, specs - completely untouched. This matters when documents get large and
  most writes only touch a small part of them.
- **Schema flexibility.** A `products` collection can hold a TV document with `screenSize`
  and `refreshRate`, and a t-shirt document with `size` and `color`, in the same collection,
  with no shared schema beyond whatever your application enforces - versus a relational
  table needing a fixed column set (or an ugly sparse "EAV" workaround) for the same
  variability.
- **Still queryable**, unlike key-value below: you can filter and aggregate on nested
  fields (`find({"variants.color": "red"})`), and Elasticsearch specifically layers a full
  inverted-index search engine (Part 3.3) on top of the document model, which is why it's
  the default choice when "document store" really means "I need full-text and faceted
  search," not just flexible storage.

Use cases: product catalogs with wildly different attributes per category, content
management, user profiles, and in-app notification storage (each notification is a
self-contained little document - type, payload, read state - with no need for a join).

### Key-value stores (Redis, DynamoDB, Aerospike)

The simplest model there is: a giant distributed hash map. Give it a key, get back an
opaque value; the store generally doesn't look inside that value. No joins, no
aggregation, no "find me all keys where the value's age > 25" - if you need that, this is
the wrong tool.

That extreme simplicity is exactly what makes key-value stores **shard almost perfectly**:
since every access is "give me the value for this one key," a hashing function can route a
request to exactly the right node in O(1), with no cross-node coordination and no query
planner needed at all (Part 3.4 covers the hashing scheme). This is the model to reach for
when you need extreme, uniform, horizontally-scaled low latency and don't need to ask
interesting questions of the data - just store it and fetch it by ID.

Use cases: session storage, auth token lookups, real-time leaderboards, caching API
responses, and any "profile by user ID" / "order by order ID" lookup where the access
pattern really is always a single-key fetch.

### Graph databases (Neo4j, Amazon Neptune, dgraph)

Relational databases handle *deeply* interconnected data badly: "friends of friends who
bought product X" is a multi-hop join, and each additional hop multiplies the cost - joins
get more expensive, not linearly, as the traversal gets deeper. Graph databases invert the
priority: relationships (edges) are stored and indexed as first-class citizens, exactly as
important as the data points (nodes) themselves, with storage engines and traversal
algorithms purpose-built to walk many hops quickly regardless of how deep the network goes.

Use cases: social graphs, recommendation engines ("people who bought this also bought..."),
knowledge graphs, and fraud detection - fraud rings are, almost by definition, a
connectivity pattern (a cluster of accounts sharing devices, addresses, or payment methods)
that's naturally a graph query and painfully a SQL one.

### Two more worth knowing (not deep-dived here)

- **Wide-column stores** (Cassandra, Bigtable, HBase) - rows keyed by a partition key, with
  a flexible, sparse set of columns per row, built for enormous write throughput and simple
  access patterns with range scans on the key. The workhorse behind huge time-ordered or
  event-style datasets (think: a write path so large that even a well-sharded document or
  relational store would struggle) where the query is always "give me a range of rows for
  this key," never an arbitrary join.
- **Time-series databases** (TimescaleDB, InfluxDB, Prometheus) - purpose-built for
  append-mostly, timestamped data with heavy downsampling, retention, and windowed-
  aggregation support baked in. Excellent for one metric graphed over time; notably bad at
  *cross-series* queries like "top-k across all series" (see 9.5's discussion of exactly
  this trade-off), because their whole design optimizes for one series at a time.

## Picking the right database

![A decision framework for choosing a data model](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/3-2-decision-tree.png)

As a mental model, work through it in this order:

1. **Does the data need strict ACID guarantees, complex/ad-hoc queries, joins, or
   multi-row transactions, and does it comfortably fit on a small number of nodes?** Choose
   relational (Postgres, MySQL).
2. **Is the data defined mainly by deep relationships that you'll traverse repeatedly**
   (friends-of-friends, fraud rings, recommendation graphs)? Choose a graph database.
3. **Do you need to scale horizontally, and is every access pattern "fetch by a specific
   key"?** Choose a key-value store.
4. **Do you need horizontal scale and flexible/nested data, but still need to query by
   specific attributes** (not just fetch by ID)? Choose a document database.
5. **Is it enormous write volume with a simple, predictable access pattern (range scans on
   a key)?** Choose a wide-column store.

In an interview, say the reasoning out loud in this shape - "this is read-heavy with a
single-key lookup pattern and needs to scale horizontally, so I'd reach for a key-value
store; if I later need to query by attributes other than the ID, I'd move to a document
store instead" - rather than just naming a product. The reasoning is the signal; the
product name is just a label for it.
