title: "2.3 Real-time delivery: polling, SSE, WebSockets, pub/sub"

2.1 covered HTTP as request/response: the client always asks first. That's a mismatch for
anything that needs to tell a client about something the *server* decided happened - a new
chat message, a price change, a notification - without the client having to guess when to
ask. This note is the spectrum of ways to close that gap, from the crudest (ask repeatedly)
to the purpose-built (a real bidirectional channel), and where each one actually belongs.

## Short polling vs. long polling

![Short polling: fixed interval, mostly "nothing new." Long polling: server holds the request until there's news](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-3-short-vs-long-polling.png)

**Short polling** - the client just asks "anything new?" on a fixed interval. Simple to
build, works with any HTTP client, but has two real costs: most requests answer "no,
nothing yet" (wasted round trips, wasted server load for zero information gained), and
there's a hard **latency floor equal to the polling interval** - an update can sit
completely unseen for up to that whole interval before the next poll happens to catch it.

**Long polling** - the client asks, but the server **holds the request open** without
answering until there's actually something to report (or a timeout is hit, at which point
the client just re-asks immediately). This removes the "mostly wasted requests" problem and
gets latency down close to the actual event time, but each held-open request ties up a
server thread or connection for as long as it's waiting - a real capacity cost at scale that
short polling doesn't have (a short-polling server's requests are always fast; a
long-polling server's requests are, by design, often slow).

## Server-Sent Events (SSE)

![SSE: one persistent connection, server pushes whenever it wants, one direction only](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-3-sse.png)

SSE fixes long polling's "one request per event" overhead by keeping a **single** HTTP
connection open (`Content-Type: text/event-stream`) and letting the server push events down
it whenever it wants, with no new request needed per event. It's plain HTTP - no special
protocol upgrade, so it works through ordinary proxies and load balancers without special
handling - and browsers' `EventSource` API reconnects automatically if the connection drops,
for free. The real limitation: **strictly one-directional**, server to client only. It's the
right fit exactly when the client never needs to send anything back mid-stream: a live
score ticker, a progress bar, a stock price feed.

## WebSockets

The obvious next question: if SSE already keeps one HTTP connection open, why isn't a
regular **persistent** HTTP/1.1 connection (2.1's keep-alive) enough for full two-way
real-time communication? The answer is structural, not incidental: **HTTP is
request/response all the way down, even when the underlying TCP connection is kept alive**.
The server fundamentally cannot push data down an HTTP connection unless the client already
has a request open and waiting (which is exactly the hack long polling and SSE are built
on) - and every single message, under that model, still pays the cost of a full HTTP
request or a chunked-response frame: hundreds of bytes of headers, every time.

![WebSocket: an HTTP upgrade handshake, then a lightweight bidirectional frame channel](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-3-websocket.png)

**WebSockets** solve this by *leaving HTTP behind* after an initial handshake: the client
requests an **Upgrade** (`Connection: Upgrade`, `Upgrade: websocket`) on a normal HTTP
request; the server responds `101 Switching Protocols`, and from that point on, the **same
TCP connection** carries lightweight WebSocket **frames** instead of HTTP messages -
**either side can send at any time**, with per-frame overhead as low as 2 bytes (vs.
HTTP's hundreds of bytes of headers per message).

Verified directly: 200 tiny updates delivered via real HTTP short polling vs. a real,
already-open WebSocket connection (`websockets` library, a genuine `ws://` server and
client):

```python
import asyncio
import http.server
import socket
import threading
import time
import websockets

N = 200

class PollHandler(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def setup(self):
        super().setup()
        self.connection.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

    def log_message(self, *args):
        pass

    def do_GET(self):
        body = b"42"
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


poll_server = http.server.ThreadingHTTPServer(("127.0.0.1", 0), PollHandler)
poll_port = poll_server.server_address[1]
threading.Thread(target=poll_server.serve_forever, daemon=True).start()

poll_sock = socket.create_connection(("127.0.0.1", poll_port))
poll_sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

total_bytes_poll = 0
t0 = time.perf_counter()
for _ in range(N):
    req = b"GET /poll HTTP/1.1\r\nHost: localhost\r\nConnection: keep-alive\r\n\r\n"
    poll_sock.sendall(req)
    total_bytes_poll += len(req)
    data = b""
    while b"42" not in data:
        data += poll_sock.recv(4096)
    total_bytes_poll += len(data)
poll_time = time.perf_counter() - t0
poll_sock.close()
poll_server.shutdown()

print(f"HTTP short polling: {N} checks -> {total_bytes_poll:,} bytes on the wire, "
     f"{poll_time*1000:.1f}ms total ({poll_time/N*1000:.3f}ms/check)")


async def ws_server_handler(websocket):
    async for _ in websocket:
        await websocket.send("42")


async def run_ws_demo():
    async with websockets.serve(ws_server_handler, "127.0.0.1", 0) as server:
        port = server.sockets[0].getsockname()[1]
        total_bytes_ws = 0
        async with websockets.connect(f"ws://127.0.0.1:{port}") as ws:
            t0 = time.perf_counter()
            for _ in range(N):
                msg = "poll"
                await ws.send(msg)
                total_bytes_ws += len(msg.encode()) + 2   # ~2 bytes of WS framing overhead
                reply = await ws.recv()
                total_bytes_ws += len(reply.encode()) + 2
            ws_time = time.perf_counter() - t0
        return total_bytes_ws, ws_time


total_bytes_ws, ws_time = asyncio.run(run_ws_demo())
print(f"WebSocket (1 connection): {N} messages -> {total_bytes_ws:,} bytes on the wire, "
     f"{ws_time*1000:.1f}ms total ({ws_time/N*1000:.3f}ms/message)")
print(f"bytes on the wire: polling used {total_bytes_poll/total_bytes_ws:.0f}x more")
```

```
HTTP short polling: 200 checks -> 40,400 bytes on the wire, 43.4ms total (0.217ms/check)
WebSocket (1 connection): 200 messages -> 2,000 bytes on the wire, 58.0ms total (0.290ms/message)
bytes on the wire: polling used 20x more
```

![Measured: 20x more bytes for polling to deliver the same 200 updates](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-3-bytes-on-wire-verified.png)

The **bandwidth** result is the clean, robust win: 20x fewer bytes for the exact same 200
updates, entirely from not repeating HTTP headers on every message. Worth reporting
honestly rather than smoothing over: the **per-message wall-clock time** in this specific
back-to-back microbenchmark did *not* come out faster for the WebSocket (0.290ms vs.
0.217ms) - Python's `asyncio` event-loop scheduling overhead dominates at this message size
on loopback, overshadowing the protocol-level savings. That's a real measurement, not a
flaw in the demo, but it's also not the actual case for WebSockets' latency advantage in
practice: this test has the polling client ask again the *instant* the previous answer
arrives, which is an unrealistically generous best case for polling. A real polling client
doesn't know exactly when an update happened, so it has to wait a fixed interval between
checks - the latency win WebSockets (and SSE, and long polling) actually provide over real
short polling is **eliminating that interval's staleness window entirely**, not winning a
single request/response race on an empty network.

## Pub/sub over the wire

![WebSocket connections as the client-facing transport for a real pub/sub backend](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-3-pubsub-over-wire.png)

The common real-world shape once you have persistent client connections: bridge them to a
real **pub/sub system server-side**. A client opens a WebSocket and "subscribes" to a
channel (a chat room ID, a document ID, a stock symbol); the server maps that to a real
subscription against Redis Pub/Sub or a Kafka topic (5.5); whenever anything publishes to
that channel, the server-side subscription fires and the message gets pushed down every
connected client's WebSocket. The WebSocket (or SSE) connection is just the **client-facing
transport** - the actual fan-out logic, durability characteristics, and scaling story are
exactly 5.5's server-side pub/sub material, not a separate mechanism. This is the shape
behind a chat room, a collaborative document's live cursors, or a stock ticker's
subscriber list.

## Choosing among them

- **Short polling** - simplest to build, fine for genuinely infrequent updates where a
  multi-second-to-minutes latency floor is acceptable (checking a background job's status).
- **Long polling** - a reasonable middle ground when you can't use WebSockets (restrictive
  proxies, older infrastructure) but need lower latency than short polling - at the cost of
  server-side connection/thread capacity for every waiting client.
- **SSE** - the right default when the server needs to push and the client never needs to
  push back - lower complexity than WebSockets, plain HTTP, free auto-reconnect.
- **WebSockets** - the right choice for genuine bidirectional, low-latency, high-frequency
  communication - chat, live collaborative editing, multiplayer/real-time gaming, trading
  interfaces - anywhere both sides need to send frequently and per-message overhead
  actually matters.

## Cheat sheet

```
SHORT         fixed interval, mostly "nothing new" answers, latency floor =
POLLING       the interval. Simplest, works everywhere, worst efficiency.

LONG          server HOLDS the request until there's news (or a timeout) ->
POLLING       much lower latency than short polling, but a held-open request
              ties up server capacity for as long as it waits.

SSE           ONE persistent HTTP connection, server pushes whenever it
              wants, ONE-DIRECTIONAL only (server -> client). Plain HTTP
              (works through normal proxies), free auto-reconnect.

WEBSOCKETS    HTTP Upgrade handshake -> same TCP connection, but now
              lightweight bidirectional FRAMES instead of HTTP messages -
              EITHER side sends any time. Why not just persistent HTTP?
              HTTP is structurally request/response even kept alive - the
              server can't push unsolicited data without an open request
              waiting. Verified: 20x fewer bytes than short polling for
              the same 200 updates (2-byte frame overhead vs. full HTTP
              headers per message) - the REAL latency win over polling is
              eliminating the polling interval's staleness window, not
              raw per-round-trip speed on an idle network.

PUB/SUB OVER  WebSocket/SSE connections are the CLIENT-facing transport;
THE WIRE      the actual fan-out is a real server-side pub/sub system
              (Redis Pub/Sub or Kafka, 5.5) - a client "subscribing" over
              its WebSocket maps to a real subscription server-side.

CHOOSING      short poll: simple, infrequent updates OK. long poll: lower
              latency without WebSocket support, costs server capacity.
              SSE: server push only, simplest of the push options.
              WebSockets: true bidirectional, high-frequency, low-overhead.
```
