title: "5.2 Delivery semantics and ordering"
---

5.1 introduced the broker as a buffer, and closed on a real problem: two side-effecting
calls made inline for one event can leave the system permanently inconsistent if the second
one fails. This note names that problem precisely, gives it the standard vocabulary
(at-most/at-least/"exactly"-once), and covers the two mechanisms - deduplication and dead
letter queues - that turn "delivery isn't perfectly reliable" into "processing is correct
anyway."

## The dual-write problem, precisely

Take 5.1's example concretely: a blog is published, and the handling code makes two
independent calls - index the blog in a search service, then increment the author's post
counter. Neither call is wrapped in anything that makes them atomic together.

![The dual-write problem: one write succeeds, the next fails, and nothing records it](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-2-dual-write-problem.png)

Verified: publishing 3 blogs, with the counter service failing on its second call (after
the corresponding index write already succeeded):

```python
class IndexService:
    def __init__(self):
        self.indexed = []

    def index(self, blog_id):
        self.indexed.append(blog_id)


class FlakyCounterService:
    def __init__(self, fail_on_call=None):
        self.fail_on_call = fail_on_call
        self.calls = 0
        self.count = 0

    def increment(self):
        self.calls += 1
        if self.calls == self.fail_on_call:
            raise RuntimeError("counter service is down")
        self.count += 1


def publish_blog_naive(blog_id, index_svc, counter_svc):
    index_svc.index(blog_id)      # write 1
    counter_svc.increment()        # write 2 - if THIS fails, write 1 already happened


index_svc = IndexService()
counter_svc = FlakyCounterService(fail_on_call=2)

results = []
for blog_id in ("blog_1", "blog_2", "blog_3"):
    try:
        publish_blog_naive(blog_id, index_svc, counter_svc)
        results.append((blog_id, "ok"))
    except RuntimeError as e:
        results.append((blog_id, f"FAILED: {e}"))

print("naive dual-write results:")
for blog_id, status in results:
    print(f"  {blog_id}: {status}")
print(f"\nindexed blogs: {index_svc.indexed}")
print(f"counter value: {counter_svc.count}")
```

```
naive dual-write results:
  blog_1: ok
  blog_2: FAILED: counter service is down
  blog_3: ok

indexed blogs: ['blog_1', 'blog_2', 'blog_3']
counter value: 2
```

Three blogs are indexed and searchable; the counter only reflects two. `blog_2` is now
**permanently** searchable but **permanently** missing from the count, and no error
anywhere records that this specific inconsistency exists - the caller saw an exception and
(depending on the retry logic) may or may not have retried, possibly re-indexing `blog_2`
a second time in the process. 5.1's fix - publish one event to a Kafka topic, let two
independent consumer groups each do their own write in their own retry loop - removes the
"two calls inline in one request" shape entirely; each consumer's local work either
succeeds or gets retried on its own, with the durable log guaranteeing neither consumer
group ever silently misses the event. 5.5 covers that fan-out mechanism directly.

## The three delivery semantics

![At-most-once, at-least-once, and "exactly-once" (really: effectively-once)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-2-delivery-semantics.png)

- **At-most-once** - send it, don't retry. A network blip or consumer crash means the
  message is simply **lost**. Cheapest, and correct only where losing an occasional
  message is genuinely fine (a non-critical metrics ping, a best-effort UI notification).
- **At-least-once** - retry until acknowledged (this is what 5.1's requeue mechanism gives
  you by default). A message is never silently lost, but a consumer crash *after* doing the
  work but *before* acking means the same message gets **redelivered and processed twice**.
  This is the default most real systems build on, precisely because "lost" is worse than
  "duplicated" - a duplicate is at least fixable.
- **"Exactly-once"** - the phrase is common but the literal guarantee, at the network/
  delivery layer, is not fully achievable in an asynchronous system (you fundamentally can't
  distinguish "my ack was lost" from "the message was lost" - the same practical shadow of
  the FLP result that 3.6 covers for consensus). What production systems actually build is
  **at-least-once delivery plus idempotent processing**, which produces the *outcome* users
  actually want - "this event's effect happened exactly once" - without needing the
  delivery layer itself to guarantee it.

## Deduplication: turning at-least-once into effectively-once

The mechanism: give every message a unique ID, and have the consumer check-and-record that
ID as part of the same unit of work that does the actual processing - "have I already
handled this ID? If yes, skip. If no, do the work and record the ID." This is exactly 3.7's
**idempotent consumer** pattern, applied here specifically to message redelivery rather
than a database-transaction retry:

```python
class AtLeastOnceQueue:
    def __init__(self):
        self.messages = []

    def send(self, msg_id, payload):
        self.messages.append({"id": msg_id, "payload": payload, "acked": False})

    def poll_unacked(self):
        return [m for m in self.messages if not m["acked"]]

    def ack(self, msg_id):
        for m in self.messages:
            if m["id"] == msg_id:
                m["acked"] = True


processed_naive = []
queue = AtLeastOnceQueue()
queue.send("evt_1", "increment_view_count blog_1")
for attempt in range(2):   # simulate: process it, crash BEFORE ack, get redelivered
    for m in queue.poll_unacked():
        processed_naive.append(m["payload"])
        if attempt == 1:
            queue.ack(m["id"])

print(f"without dedup: processed {len(processed_naive)} times: {processed_naive}")

processed_with_dedup = []
seen_ids = set()
queue2 = AtLeastOnceQueue()
queue2.send("evt_1", "increment_view_count blog_1")
for attempt in range(2):
    for m in queue2.poll_unacked():
        if m["id"] not in seen_ids:
            processed_with_dedup.append(m["payload"])
            seen_ids.add(m["id"])
        if attempt == 1:
            queue2.ack(m["id"])

print(f"with a dedup key: processed {len(processed_with_dedup)} time(s): {processed_with_dedup}")
```

```
without dedup: processed 2 times: ['increment_view_count blog_1', 'increment_view_count blog_1']
with a dedup key: processed 1 time(s): ['increment_view_count blog_1']
```

Without a dedup key, one real view redelivered after a crash-before-ack doubles the view
count. Tracking `seen_ids` (in practice, a row in the same database transaction that does
the actual work, so the check-and-record is itself atomic) collapses the redelivered
duplicate back down to a single effective increment - exactly 3.7's pattern, here proven
in a pure messaging context rather than a database-retry one.

## Ordering

5.1 already established the boundary: Kafka guarantees order **within a partition**
(same key -> same partition -> messages processed in the order they were produced), and
gives **no** ordering guarantee across partitions. If your consumer logic ever depends on
"event A must be processed before event B," the only way to guarantee that at scale is to
make sure A and B share a partition key - which usually means keying by the entity the
events are about (`blog_id`, `user_id`), not by something incidental like a random request
ID.

## Dead letter queues (DLQ)

At-least-once retry has a failure mode of its own: a **poison message** - one that will
never succeed no matter how many times it's retried (malformed payload, a bug in the
handler for that specific shape of input) - gets retried **forever**, burning worker
capacity and potentially blocking everything behind it if ordering matters. The fix: after
a bounded number of failed attempts, stop retrying and move the message to a separate
**dead letter queue** instead, where it waits for manual inspection rather than looping.

```python
class QueueWithDLQ:
    def __init__(self, max_attempts=3):
        self.max_attempts = max_attempts
        self.main = []
        self.dlq = []

    def send(self, msg_id, payload):
        self.main.append({"id": msg_id, "payload": payload, "attempts": 0})

    def process_all(self, handler):
        still_pending = []
        for m in self.main:
            m["attempts"] += 1
            try:
                handler(m["payload"])
            except Exception as e:
                if m["attempts"] >= self.max_attempts:
                    self.dlq.append({**m, "error": str(e)})
                else:
                    still_pending.append(m)
        self.main = still_pending


def poison_handler(payload):
    if payload == "malformed_event":
        raise ValueError("cannot parse payload")


q = QueueWithDLQ(max_attempts=3)
q.send("evt_good", "normal_event")
q.send("evt_bad", "malformed_event")

for round_num in range(1, 5):
    q.process_all(poison_handler)
    print(f"after round {round_num}: main queue has {len(q.main)} message(s), "
         f"DLQ has {len(q.dlq)} message(s)")
    if not q.main:
        break

print(f"\nDLQ contents: {[(m['id'], m['attempts'], m['error']) for m in q.dlq]}")
```

```
after round 1: main queue has 1 message(s), DLQ has 0 message(s)
after round 2: main queue has 1 message(s), DLQ has 0 message(s)
after round 3: main queue has 0 message(s), DLQ has 1 message(s)

DLQ contents: [('evt_bad', 3, 'cannot parse payload')]
```

![Dead letter queue: 3 retries, then routed out of the main loop](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-2-dlq-flow.png)

The well-formed message processed and disappeared from the main queue on round 1; the
malformed one retried twice more (rounds 2 and 3), then - having hit `max_attempts` - was
routed to the DLQ instead of retrying a fourth time. This is the standard production
pattern: main queue capacity stays dedicated to messages that can actually succeed, and a
human (or a separate reprocessing pipeline, once the underlying bug is fixed) deals with
the DLQ's contents out of band.

## Cheat sheet

```
DUAL-WRITE    two side-effecting calls, inline, no atomicity between them ->
PROBLEM       one succeeds, one fails, permanent silent inconsistency.
              Verified: 3 published, counter failed once -> 3 indexed, 2
              counted, no record of the mismatch. Fixed by 5.1/5.5's
              single-log + independent-consumer-groups pattern, not by
              trying to make the two calls atomic.

AT-MOST-ONCE  send, don't retry -> failure = message LOST. OK only where
              losing one occasionally is truly fine.

AT-LEAST-ONCE retry until acked (the default) -> failure = message may be
              PROCESSED TWICE, never silently lost.

"EXACTLY-      not achievable at the delivery layer in an async system
ONCE"         (can't distinguish a lost ack from a lost message - same
              shadow as FLP, 3.6). What's actually built: at-least-once +
              idempotent processing = EFFECTIVELY once. Verified: a
              redelivered message processed twice without a dedup key,
              once WITH one (3.7's idempotent-consumer pattern).

ORDERING      guaranteed only WITHIN a Kafka partition (same key -> same
              partition, 5.1). None across partitions. If A must precede
              B, they need the same partition key.

DLQ           bounded retry count, then route to a separate queue instead
              of looping forever on a poison message. Verified: 3 failed
              attempts -> DLQ; the well-formed message succeeded and
              cleared on attempt 1, unaffected by the poison one.
```
