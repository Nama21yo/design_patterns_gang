Every cache in this Part answers a question exactly - the value is either there or it
isn't. **Probabilistic data structures** trade that exactness away, deliberately, for
memory that stays small and flat no matter how large the underlying dataset grows. This
note is the family: what each one answers, how it earns its space savings, and where that
trade is actually worth making.

![The five structures covered here, at a glance](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-probabilistic-summary.png)

## Bloom filter

**A Bloom filter is an approximate set that answers one question with 100% certainty in
one direction only: "is this element definitely NOT in the set?"** When it says no, that's
final. When it says yes, that's a "maybe."

### The motivating problem

Instagram recommending Reels (or, in the Bloomberg-terminal flavor: a news feed deciding
which articles a user has already been shown) needs to avoid re-showing something the user
has already seen. The naive approach: record every reel ID a user has watched, in a set.

![Why a Bloom filter, starting from the naive approach](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-bloom-motivation.png)

That set only grows - over months of use, it becomes huge, per user, multiplied across
every user. Keep it on disk and every recommendation-time lookup costs a slow I/O; keep it
in memory and you're paying real RAM, forever, for every user's entire history.

**The key insight that unlocks the fix: once something is watched, it can never become
un-watched.** You never need to *remove* an entry, and - this is the part that actually
saves the memory - you never need the *actual ID* back. The only question ever asked is
"have I seen this specific ID before, yes or no?" Storing the ID itself is unnecessary
overhead for answering a yes/no question. That's the whole idea a Bloom filter formalizes:
replace "store every ID" with "store a compact, fixed-size **filter**" - literally a **bit
array**.

### How it works

An `m`-bit array, all zeros to start, plus `k` independent hash functions.

![Bloom filter structure](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-bloom-structure.png)

- **Add(item)**: hash the item `k` different ways, set all `k` resulting bit positions to 1.
- **Contains(item)**: hash the item the same `k` ways, check whether *all* `k` positions
  are set. If **any** is still 0, the item was **definitely never added** - a bit that's 0
  could not have been set by anything, ever. If **all** are 1, the item was **probably**
  added - but those exact `k` bits could have all been set by *some combination of other
  items*, purely by coincidence. That coincidence is the **false positive rate**: the
  filter says "maybe present" for something that was actually never added.

Note what can never happen: a **false negative**. Bits only ever get set, never cleared, so
once an item is truly added, its bits stay 1 forever and `contains()` will always find them.
That one-sided guarantee - never a false negative, sometimes a false positive - is the
entire contract.

Verified, with a from-scratch implementation (using the standard double-hashing trick,
`h_i(x) = h1(x) + i*h2(x)`, to get `k` effectively-independent hash functions from just two
real ones):

```python
import hashlib
import math

class BloomFilter:
    def __init__(self, expected_items, target_fp_rate):
        self.m = self._optimal_m(expected_items, target_fp_rate)
        self.k = self._optimal_k(self.m, expected_items)
        self.bits = bytearray((self.m + 7) // 8)
        self.n = 0

    @staticmethod
    def _optimal_m(n, p):
        return math.ceil(-(n * math.log(p)) / (math.log(2) ** 2))

    @staticmethod
    def _optimal_k(m, n):
        return max(1, round((m / n) * math.log(2)))

    def _hashes(self, item):
        b = str(item).encode()
        h1 = int(hashlib.md5(b).hexdigest(), 16)
        h2 = int(hashlib.sha1(b).hexdigest(), 16)
        for i in range(self.k):
            yield (h1 + i * h2) % self.m

    def add(self, item):
        for idx in self._hashes(item):
            self.bits[idx // 8] |= (1 << (idx % 8))
        self.n += 1

    def __contains__(self, item):
        return all(self.bits[idx // 8] & (1 << (idx % 8)) for idx in self._hashes(item))

    def current_fp_rate_estimate(self):
        return (1 - math.exp(-self.k * self.n / self.m)) ** self.k


bf = BloomFilter(expected_items=10_000, target_fp_rate=0.01)
print(f"expected_items=10,000  target_fp=1%  ->  m={bf.m} bits ({bf.m/8/1024:.1f} KB)  k={bf.k} hash functions")

watched = [f"reel_{i}" for i in range(10_000)]
for r in watched:
    bf.add(r)

missed = sum(1 for r in watched if r not in bf)
print(f"false negatives among 10,000 watched reels: {missed} (must always be 0)")
assert missed == 0

never_watched = [f"unseen_{i}" for i in range(100_000)]
false_positives = sum(1 for r in never_watched if r in bf)
print(f"false positives among 100,000 never-watched reels: {false_positives} "
     f"({false_positives/len(never_watched):.2%})")
print(f"theoretical fp rate at this load: {bf.current_fp_rate_estimate():.2%}")
```

```
expected_items=10,000  target_fp=1%  ->  m=95851 bits (11.7 KB)  k=7 hash functions
false negatives among 10,000 watched reels: 0 (must always be 0)
false positives among 100,000 never-watched reels: 1018 (1.02%)
theoretical fp rate at this load: 1.00%
```

Zero false negatives, exactly as guaranteed - and the empirical false-positive rate
(1.02%) lands right on the theoretical target (1.00%). And the entire filter for 10,000
items costs **11.7 KB** - a real, measured comparison against storing the raw IDs:

```python
raw_bytes = sum(len(f"reel_{i}".encode()) for i in range(10_000))
print(f"storing the actual reel-id strings: {raw_bytes:,} bytes ({raw_bytes/1024:.1f} KB)")
print(f"Bloom filter bit array:              {bf.m // 8:,} bytes ({bf.m/8/1024:.1f} KB)")
print(f"space saved: {(1 - (bf.m//8)/raw_bytes):.1%}")
```

```
storing the actual reel-id strings: 88,890 bytes (86.8 KB)
Bloom filter bit array:              11,981 bytes (11.7 KB)
space saved: 86.5%
```

### The false-positive rate is "infinitely growable"

A Bloom filter's size (`m`, `k`) is fixed at creation time, sized for an *expected* number
of items. Keep adding items past that plan, and the false-positive rate doesn't fail
gracefully - it climbs, sharply:

```python
never_watched = [f"unseen_{i}" for i in range(20_000)]
for load_multiplier in (0.5, 1.0, 2.0, 4.0):
    n_items = int(10_000 * load_multiplier)
    bf2 = BloomFilter(expected_items=10_000, target_fp_rate=0.01)   # same fixed size
    for i in range(n_items):
        bf2.add(f"reel_{i}")
    fps = sum(1 for r in never_watched if r in bf2)
    print(f"{n_items:6d} items in a filter sized for 10,000  ->  "
         f"empirical fp rate {fps/len(never_watched):.2%}")
```

```
 5000 items in a filter sized for 10,000  ->  empirical fp rate 0.03%
10000 items in a filter sized for 10,000  ->  empirical fp rate 0.92%
20000 items in a filter sized for 10,000  ->  empirical fp rate 15.75%
40000 items in a filter sized for 10,000  ->  empirical fp rate 67.83%
```

![Measured: false-positive rate growth under overload](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-bloom-fp-growth.png)

At 4x the planned load, more than two-thirds of lookups for things that were never added
come back "maybe present." The practical implication: **as your key count grows, you have
to grow the filter with it** - re-size (create a larger filter and re-add everything, or
use a scalable-Bloom-filter variant that chains progressively larger filters together) -
the same "resize when you outgrow capacity" idea that applies to a hashmap, just with a
sharper, faster-degrading failure curve if you don't.

### You (usually) don't need to implement this yourself

Redis ships a Bloom filter as a built-in module (`RedisBloom` / the `BF.*` commands in
modern Redis) - `BF.ADD`, `BF.EXISTS`, with capacity and error-rate management handled for
you server-side. In practice, reach for that rather than a hand-rolled implementation in
application code, for the same reason 4.3 recommends Redis generally: the hard parts
(sizing, hashing, memory layout) are already solved and operated for you.

### When to use it

![Deciding when a Bloom filter fits](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-bloom-when-to-use.png)

- You only ever **insert**, never remove (or removal simply isn't a requirement of the
  problem).
- You need a **definitely-not-present** answer with 100% certainty - a real filter, not
  just a maybe.
- An occasional **false positive is acceptable** - worst case, you skip serving/checking
  something you actually haven't seen before, not a correctness catastrophe.

Classic fits: deduplicating a recommendation feed (this note's example), a web crawler
skipping URLs it's already crawled (missing a rare re-crawl due to a false positive costs
nothing; crawling the same URL forever due to a false *negative* would be the real bug -
which, again, can't happen), checking "might this username already be taken" before a much
more expensive real database lookup, and generally as a cheap pre-filter in front of an
expensive check ("probably not there, skip the expensive lookup" vs "maybe there, do the
real check").

## Counting Bloom Filter

A plain Bloom filter can never safely support deletion - clearing a bit might belong to
several different items' hash sets at once (bit 7 in the structure diagram above is shared
between `reel_A` and `reel_B`; clearing it to "remove" one would silently also un-add the
other). The fix: replace each 1-bit slot with a small **counter** (a few bits, e.g. 4).
Adding increments the `k` relevant counters; removing decrements them; `contains()` checks
that all `k` counters are non-zero.

```python
class CountingBloomFilter:
    def __init__(self, m, k, counter_bits=4):
        self.m, self.k = m, k
        self.max_count = (1 << counter_bits) - 1
        self.counters = [0] * m

    def _hashes(self, item):
        b = str(item).encode()
        h1 = int(hashlib.md5(b).hexdigest(), 16)
        h2 = int(hashlib.sha1(b).hexdigest(), 16)
        for i in range(self.k):
            yield (h1 + i * h2) % self.m

    def add(self, item):
        for idx in self._hashes(item):
            if self.counters[idx] < self.max_count:
                self.counters[idx] += 1

    def remove(self, item):
        for idx in self._hashes(item):
            if self.counters[idx] > 0:
                self.counters[idx] -= 1

    def __contains__(self, item):
        return all(self.counters[idx] > 0 for idx in self._hashes(item))


cbf = CountingBloomFilter(m=2000, k=5)
cbf.add("reel_1"); cbf.add("reel_2"); cbf.add("reel_3")
cbf.remove("reel_2")
print("'reel_2' in filter:", "reel_2" in cbf, " (correctly gone)")
print("'reel_1' in filter:", "reel_1" in cbf, " (unaffected by reel_2's removal)")
print("'reel_3' in filter:", "reel_3" in cbf, " (unaffected)")
```

```
'reel_2' in filter: False  (correctly gone)
'reel_1' in filter: True  (unaffected by reel_2's removal)
'reel_3' in filter: True  (unaffected)
```

The cost: `k` small counters per slot instead of `k` single bits - typically 4x the memory
of a plain Bloom filter for the same `m`, still tiny compared to storing real items. Use it
whenever the "never remove" assumption behind a plain Bloom filter doesn't actually hold -
a cache admission filter where items *do* eventually get evicted, for instance.

## Count-Min Sketch

Covered in full depth, with a worked diagram and a verified accuracy/one-sided-error stress
test, in **9.5's Top-K case study** - it's the structure behind approximate heavy-hitter
counting at scale (a `d`-row by `w`-column grid of counters, one independent hash function
per row, query = minimum across rows). The short version for this note's summary: it
answers **"approximately how many times has X occurred?"**, never under-counts, and 9.5's
stress test confirmed the error stayed within the proven `epsilon * N` bound on 200,000
skewed events using a fixed, tiny table.

## HyperLogLog

**HyperLogLog estimates how many *distinct* items have appeared in a stream**, using a
tiny, fixed amount of memory - a few kilobytes - regardless of whether the true count is a
thousand or a billion. This is the structure behind "unique visitors today" and "distinct
IPs in the last hour" style counters at scale, where storing every distinct value seen
(what an exact answer would require) is exactly the unbounded-memory problem the Bloom
filter section opened with, just for a different question.

![How HyperLogLog estimates cardinality](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-hyperloglog-mechanism.png)

The core trick: hash each item to get a long, effectively-random bit string. Use its low
bits to pick one of `m` **buckets**; look at the *rest* of the bits and count the **leading
zeros** before the first 1 (a "run" of `k` leading zeros has probability `2^-k` - genuinely
rare for large `k`). Each bucket remembers only the **longest run it has ever seen**.
Seeing a long run at all is a signal that *many* distinct items must have been hashed into
that bucket - and averaging that signal (a bias-corrected harmonic mean) across all `m`
buckets turns a noisy per-bucket guess into a tight overall estimate:

```python
import hashlib
import math

class HyperLogLog:
    def __init__(self, b=10):
        self.b = b
        self.m = 1 << b
        self.registers = [0] * self.m
        self.alpha = 0.7213 / (1 + 1.079 / self.m) if self.m >= 128 else 0.673

    def _hash(self, item):
        return int(hashlib.sha1(str(item).encode()).hexdigest(), 16) & ((1 << 64) - 1)

    def add(self, item):
        x = self._hash(item)
        bucket = x & (self.m - 1)
        rest = x >> self.b
        rank = 1
        while rest & 1 == 0 and rank <= 64 - self.b:
            rank += 1
            rest >>= 1
        self.registers[bucket] = max(self.registers[bucket], rank)

    def estimate(self):
        Z = sum(2.0 ** -r for r in self.registers)
        raw = self.alpha * self.m * self.m / Z
        if raw <= 2.5 * self.m:              # small-range correction (linear counting)
            zeros = self.registers.count(0)
            if zeros > 0:
                return self.m * math.log(self.m / zeros)
        return raw


import random
random.seed(0)
for true_cardinality in (1_000, 100_000, 1_000_000):
    hll = HyperLogLog(b=12)     # 4096 registers, 1 byte each -> 4 KB total
    stream_len = true_cardinality * 5
    for _ in range(stream_len):
        hll.add(random.randint(0, true_cardinality - 1))
    est = hll.estimate()
    error = abs(est - true_cardinality) / true_cardinality
    print(f"true = {true_cardinality:>9,}  ->  estimate = {est:>10,.0f}   error = {error:.2%}")
```

```
true =     1,000  ->  estimate =        981   error = 1.95%
true =   100,000  ->  estimate =     99,151   error = 0.85%
true = 1,000,000  ->  estimate =    980,805   error = 1.92%
```

![Measured HyperLogLog accuracy across three orders of magnitude](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-hyperloglog-accuracy.png)

The same **4 KB** of registers, unchanged, stays within about 2% error whether the true
distinct count is a thousand or a million - a stream with a billion distinct items would
cost the same 4 KB, while an exact count would need to store every distinct value at least
once. (The "small-range correction" in the code - falling back to linear counting when the
raw estimate is low relative to `m` - matters in practice: without it, cardinalities much
smaller than the register count are measurably biased, which is exactly the kind of detail
worth verifying rather than assuming away.)

## t-digest

**t-digest estimates percentiles/quantiles** (p50, p99, p99.9 - the numbers behind every
latency dashboard) over a huge stream without keeping every sample. The idea: maintain a
small, bounded set of weighted **centroids** (a mean plus a count); a new value merges into
its nearest existing centroid once the digest is full, instead of being stored individually;
querying a percentile walks the centroids in order by cumulative weight to the target
point:

![t-digest: bounded centroids instead of every raw sample](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-5-tdigest-concept.png)

```python
import bisect

class SimpleTDigest:
    def __init__(self, max_centroids=200):
        self.max_centroids = max_centroids
        self.centroids = []

    def add(self, x):
        means = [c[0] for c in self.centroids]
        i = bisect.bisect_left(means, x)
        if len(self.centroids) < self.max_centroids:
            self.centroids.insert(i, [x, 1])
            return
        candidates = [j for j in (i - 1, i) if 0 <= j < len(self.centroids)]
        j = min(candidates, key=lambda j: abs(self.centroids[j][0] - x))
        mean, w = self.centroids[j]
        self.centroids[j] = [(mean * w + x) / (w + 1), w + 1]

    def quantile(self, q):
        total = sum(w for _, w in self.centroids)
        target = q * total
        cum = 0
        for mean, w in self.centroids:
            cum += w
            if cum >= target:
                return mean
        return self.centroids[-1][0]


import random
random.seed(1)
data = [random.gauss(100, 15) for _ in range(200_000)]   # simulated latency samples
td = SimpleTDigest(max_centroids=200)
for x in data:
    td.add(x)

data_sorted = sorted(data)
for q in (0.5, 0.9, 0.99, 0.999):
    est = td.quantile(q)
    true = data_sorted[int(q * (len(data_sorted) - 1))]
    print(f"p{q*100:<5g}: estimate = {est:7.2f}   true = {true:7.2f}   error = {abs(est-true):.2f}")
print(f"memory: {len(td.centroids)} centroids vs {len(data):,} raw samples "
     f"({len(data)/len(td.centroids):.0f}x fewer values retained)")
```

```
p50   : estimate =  100.02   true =  100.04   error = 0.02
p90   : estimate =  119.22   true =  119.24   error = 0.02
p99   : estimate =  134.32   true =  134.78   error = 0.46
p99.9 : estimate =  146.32   true =  146.14   error = 0.18
memory: 200 centroids vs 200,000 raw samples (1000x fewer values retained)
```

Close estimates across the whole distribution - including the tail (p99.9), which is
exactly where percentile accuracy matters most for a latency SLO - using **1000x fewer**
retained values than the raw stream. (This simplified version merges into whichever
centroid is nearest by value; the real t-digest algorithm additionally biases toward
keeping *more, smaller* centroids near the tails specifically, since that's where a fixed
absolute merge tolerance would otherwise cost the most precision - the same "spend your
limited memory where the error matters most" idea, taken one step further.)

## Cheat sheet

```
COMMON THEME  all trade a small, PROVABLY BOUNDED error for memory that stays
              flat regardless of how large the underlying dataset grows -
              exactly the move to make once storing every raw value becomes
              the actual bottleneck (memory or lookup time), not before.

BLOOM FILTER  "definitely NOT present" (100% certain) vs "maybe present."
              m-bit array + k hash functions; add sets k bits, query checks
              all k. NEVER a false negative; false positives grow sharply
              past planned capacity (verified: 0.03%->0.92%->15.75%->67.83%
              at 0.5x/1x/2x/4x load). ~86.5% smaller than storing raw IDs
              (verified). Use: insert-only, need a hard "no," false
              positives tolerable (feed dedup, crawler URL dedup, cheap
              pre-filter). Redis ships one built in (RedisBloom) - don't
              hand-roll it in production.

COUNTING      Bloom filter + small counters instead of bits -> supports
BLOOM         DELETE (verified: removing one item didn't affect others).
              ~4x the memory of a plain Bloom filter for the same m.

COUNT-MIN     approx. frequency of X. Full treatment in 9.5 (verified: 0
SKETCH        undercounts, error within the proven bound).

HYPERLOGLOG   approx. COUNT OF DISTINCT items, fixed tiny memory regardless
              of true cardinality. Leading-zero-run trick across m buckets,
              bias-corrected harmonic mean. Verified: ~1-2% error at 4 KB,
              true cardinality 1,000 to 1,000,000 - same memory throughout.
              Needs a small-range correction (linear counting) at low
              cardinality relative to bucket count, or it's measurably biased.

T-DIGEST      approx. PERCENTILE/QUANTILE (p50, p99, p99.9 - latency SLOs).
              Bounded set of weighted centroids, merge-on-overflow, query by
              cumulative weight. Verified: ~0.02-0.46 error across p50-p99.9,
              1000x fewer retained values than the raw stream. Real t-digest
              concentrates more/smaller centroids near the tails for extra
              precision exactly where percentile accuracy matters most.
```
