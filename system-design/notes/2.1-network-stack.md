Every note so far has treated "the client calls the server" as a given. This note is what
that call actually is, mechanically: the transport-layer contract (TCP vs. UDP) that
everything above it depends on, the application-layer protocol built on top of it (HTTP,
across its three major versions), and the encryption layer (TLS) that sits between them in
production.

## TCP: reliable, ordered, connection-oriented

TCP gives the application layer a guarantee that's genuinely hard to build yourself: **every
byte sent arrives, exactly once, in the order it was sent**, over a network that can
reorder, duplicate, or drop packets at will. Three mechanisms combine to make that true:

![Sequence numbers/ACKs, flow control, and congestion control working together](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-tcp-reliability.png)

- **Sequence numbers and acknowledgments** - every byte sent is numbered; the receiver acks
  what it has successfully received, so the sender always knows precisely what still needs
  (re)sending.
- **Sliding window (flow control)** - the receiver continuously advertises how much buffer
  space it has left. The sender is not allowed to send more unacknowledged data than that
  window - it's throttled by the *receiver's* actual capacity, not just sending as fast as
  it can.
- **Congestion control** - separately, the sender paces itself to avoid overwhelming the
  *network* (not just the receiver): **slow start** ramps the send rate up exponentially
  from a small initial value, then **AIMD** (additive increase, multiplicative decrease)
  takes over - increase the rate by a small fixed amount each round trip that goes cleanly,
  but on any sign of loss, cut the rate in half. This is why TCP throughput on a lossy link
  looks like a sawtooth over time, not a flat line.
- **Retransmission** - any data that goes unacknowledged past a timeout (or gets 3
  duplicate ACKs, a signal the receiver got something *after* a gap) is automatically
  resent. Packet loss on the wire becomes invisible to the application - it just sees a
  slightly delayed, still-complete, still-ordered stream.

Proven live, not just described - a real TCP client/server over loopback, with the
receiver's buffer deliberately shrunk to 4KB and 5,000 messages fired at it as fast as
possible:

```python
import socket
import threading
import time

N = 5000

def tcp_server(received, ready_event):
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 4096)   # tiny buffer, forces backpressure
    srv.bind(("127.0.0.1", 0))
    srv.listen(1)
    port = srv.getsockname()[1]
    ready_event.append(port)
    conn, _ = srv.accept()
    buf = b""
    while True:
        chunk = conn.recv(4096)
        if not chunk:
            break
        buf += chunk
    messages = buf.decode().split("\n")[:-1]
    received.extend(int(m) for m in messages)
    conn.close()
    srv.close()


received_tcp = []
ready = []
t = threading.Thread(target=tcp_server, args=(received_tcp, ready))
t.start()
while not ready:
    time.sleep(0.01)
port = ready[0]

client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
client.connect(("127.0.0.1", port))
for i in range(N):
    client.sendall(f"{i}\n".encode())   # sendall blocks/retries until ALL bytes are accepted
client.close()
t.join(timeout=5)

print(f"TCP: sent {N} messages into a tiny 4KB receive buffer")
print(f"     received {len(received_tcp)} messages, in order: "
     f"{received_tcp == list(range(N))}")
```

```
TCP: sent 5000 messages into a tiny 4KB receive buffer
     received 5000 messages, in order: True
```

Every single message arrived, in exact order, despite a buffer far too small to hold them
all at once - `sendall` simply blocked the sender whenever the window closed, rather than
losing anything. Compare directly against UDP under the identical setup below.

### Setup and teardown

![3-way handshake to set up, 4-way to tear down](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-tcp-handshake-teardown.png)

**Setup is a 3-way handshake**: `SYN` (client proposes a starting sequence number) ->
`SYN-ACK` (server acknowledges it and proposes its own) -> `ACK` (client acknowledges the
server's). Three messages because TCP is **full-duplex** - both directions need their own
sequence number agreed before either side can safely send data, and the middle message
combines the server's ACK and its own SYN into one packet.

**Teardown is a 4-way exchange**, for the same full-duplex reason: a `FIN` only closes
*one* direction. The side that's done sending sends `FIN`; the other side `ACK`s it (that
direction is now closed) but may still have its own data to finish sending, so the
connection isn't fully closed until *it* also sends its own `FIN`, acknowledged in turn.
(In practice this sometimes appears as only 3 packets, when a server with nothing left to
send combines its ACK and FIN into one packet - the underlying exchange is the same.)

## UDP: no guarantees, by design

UDP strips away every one of TCP's guarantees: no handshake, no sequence numbers, no
acknowledgments, no retransmission, no flow control, no congestion control. A datagram is
sent and, from the transport layer's perspective, forgotten - the OS makes no promise it
arrives, arrives once, or arrives in order. What's left is a minimal 8-byte header (source
port, destination port, length, checksum) versus TCP's much larger one, and zero
connection-setup latency, since there's no handshake to complete before the first byte of
actual data can go out.

The exact same overload experiment as above, run against UDP instead, with **identical**
buffer size and load:

```python
def udp_server(received, ready_event):
    srv = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, 4096)   # same tiny buffer
    srv.bind(("127.0.0.1", 0))
    port = srv.getsockname()[1]
    ready_event.append(port)
    srv.settimeout(1.5)
    try:
        while True:
            data, _ = srv.recvfrom(1024)
            received.append(int(data.decode()))
    except socket.timeout:
        pass
    srv.close()


received_udp = []
ready2 = []
t2 = threading.Thread(target=udp_server, args=(received_udp, ready2))
t2.start()
while not ready2:
    time.sleep(0.01)
port2 = ready2[0]

client2 = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for i in range(N):
    client2.sendto(str(i).encode(), ("127.0.0.1", port2))   # fire and forget - no blocking, no retry
client2.close()
t2.join(timeout=5)

print(f"UDP: sent {N} datagrams into the SAME tiny 4KB receive buffer, no pacing")
print(f"     received {len(received_udp)} messages "
     f"({N - len(received_udp)} silently DROPPED)")
```

```
UDP: sent 5000 datagrams into the SAME tiny 4KB receive buffer, no pacing
     received 4990 messages (10 silently DROPPED)
```

![Same overload, opposite outcomes: TCP blocks the sender, UDP just drops](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-tcp-vs-udp-verified.png)

Identical buffer, identical flood of messages - TCP delivered **100%**, every single run.
UDP's drop count is genuinely noisy run to run (5 separate runs of this exact demo showed
7, 10, 15, 40, and 46 messages dropped out of 5,000 - and, in one outlier run, over half)
because it depends on exactly how the OS scheduler interleaves the flooding sender against
the draining receiver, with nothing in the protocol smoothing that out. **The number that
matters isn't a specific percentage - it's that UDP drops *something*, on every single run,
with zero error raised anywhere and nothing telling the sender it happened**, while TCP's
flow control held the line at 100% every time, across all 6 runs of this exact test. This
is the entire trade in one measurement: TCP trades some latency and overhead for a hard
reliability guarantee; UDP trades the guarantee away entirely for minimal overhead and zero
setup latency. That trade is exactly why UDP is still the right choice for DNS lookups
(a single small request/response, cheaper to just retry than to pay a handshake),
real-time video/audio (a dropped frame is fine; a frame arriving late because it's
*waiting to retransmit an old one* is not), and, as covered below, the transport underneath
HTTP/3.

## HTTP/1.1, HTTP/2, HTTP/3

![Three different answers to "how many requests can be in flight at once, and how"](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-http-versions.png)

**HTTP/1.1**: one request in flight per TCP connection at a time. The connection is
terminated after the response is sent by default in HTTP/1.0-style usage, or - the
practically universal case today - kept open for reuse via `Connection: keep-alive`. Either
way, a *second* request on the *same* connection has to wait for the first to fully
complete - **head-of-line blocking** at the HTTP layer. Browsers historically worked around
this by opening several parallel TCP connections to the same host (each paying its own
handshake cost) rather than actually fixing the underlying limitation.

Proven live: 200 real HTTP/1.1 requests against a real `http.server` instance, measuring a
brand-new TCP connection per request against one reused keep-alive connection:

```python
import http.server
import threading
import socket
import time


class Handler(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def setup(self):
        super().setup()
        self.connection.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

    def log_message(self, *args):
        pass

    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "text/plain")
        self.send_header("Content-Length", "2")
        self.end_headers()
        self.wfile.write(b"ok")


server = http.server.ThreadingHTTPServer(("127.0.0.1", 0), Handler)
port = server.server_address[1]
threading.Thread(target=server.serve_forever, daemon=True).start()

N = 200

def request_new_connection():
    s = socket.create_connection(("127.0.0.1", port))
    s.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
    s.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n")
    data = b""
    while True:
        chunk = s.recv(4096)
        if not chunk:
            break
        data += chunk
    s.close()

def request_keep_alive(sock):
    sock.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\nConnection: keep-alive\r\n\r\n")
    data = b""
    while b"ok" not in data:
        chunk = sock.recv(4096)
        if not chunk:
            raise RuntimeError("connection closed unexpectedly during keep-alive")
        data += chunk

t0 = time.perf_counter()
for _ in range(N):
    request_new_connection()
new_conn_time = time.perf_counter() - t0

keep_alive_sock = socket.create_connection(("127.0.0.1", port))
keep_alive_sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
t0 = time.perf_counter()
for _ in range(N):
    request_keep_alive(keep_alive_sock)
keep_alive_time = time.perf_counter() - t0
keep_alive_sock.close()

print(f"{N} requests, a NEW TCP connection per request: "
     f"{new_conn_time/N*1000:.3f}ms/request")
print(f"{N} requests, ONE reused keep-alive connection: "
     f"{keep_alive_time/N*1000:.3f}ms/request")
print(f"keep-alive was {new_conn_time/keep_alive_time:.1f}x faster")

server.shutdown()
```

```
200 requests, a NEW TCP connection per request: 0.599ms/request
200 requests, ONE reused keep-alive connection: 0.182ms/request
keep-alive was 3.3x faster
```

![Measured: keep-alive vs. a fresh connection per request, 200 real HTTP/1.1 requests](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-http11-keepalive-verified.png)

3.3x faster purely from skipping 199 redundant TCP handshakes - and this is on **loopback**,
where a handshake is about as cheap as a handshake ever gets; over a real network, every new
connection costs a *full extra round trip of latency* on top of this, which is exactly why
`Connection: keep-alive` is the default in every modern HTTP client. (One real gotcha this
demo hit while verifying it: without explicitly disabling **Nagle's algorithm**
`TCP_NODELAY` on both ends, small request/response pairs on a reused connection stalled by
~40ms *each* - the well-known Nagle + delayed-ACK interaction, where TCP batches small
outgoing writes waiting either for more data or an ACK, and the other side's delayed-ACK
timer is waiting on the same thing. Real HTTP libraries set `TCP_NODELAY` for exactly this
reason; leaving it off can make keep-alive *look* slower than fresh connections in a naive
benchmark, when the actual mechanism is faster.)

**HTTP/2**: fixes HTTP-level head-of-line blocking by **multiplexing** many logical
**streams** over a **single** TCP connection - requests and responses are broken into
binary frames, interleaved, and reassembled by stream ID on the other end, so a slow
response no longer blocks a fast one queued behind it on the same connection. Also adds
**HPACK header compression** (HTTP headers repeat enormously across requests to the same
host - compressing that away is a real bandwidth win) and optional **server push**. The
limitation this doesn't fix: it's still **one TCP connection**, and TCP itself is still
strictly ordered - a single lost packet anywhere still stalls *every* multiplexed stream
until it's retransmitted, because TCP won't hand the next byte to any stream until the gap
is filled. This is **transport-level** head-of-line blocking, one layer down from the
problem HTTP/2 actually solved.

**HTTP/3**: fixes that remaining problem by replacing TCP with **QUIC**, built on top of
UDP. QUIC reimplements reliability and ordering itself, but **per-stream** rather than
per-connection - each stream has independent loss recovery, so one stream's lost packet no
longer stalls the others. QUIC also folds the transport and TLS 1.3 handshakes together
into a single round trip (down from the separate TCP-then-TLS round trips HTTP/1.1 and
HTTP/2 pay), and supports **connection migration** - a client switching networks (WiFi to
cellular) can keep the same QUIC connection alive, something impossible for TCP, which
identifies a connection by the 4-tuple of source/destination IP and port.

## TLS: what's happening underneath "https://"

![TLS handshake: agree on a cipher, verify identity, derive a shared symmetric key](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/2-1-tls-handshake.png)

TLS sits **on top of** TCP (or, for HTTP/3, is folded into QUIC directly) and handles
encryption and identity verification before any application data flows:

1. **ClientHello** - the client proposes supported TLS versions and cipher suites.
2. **ServerHello + certificate** - the server responds with its choice and its certificate
   (its public key, signed by a Certificate Authority the client already trusts).
3. **Key exchange** - after verifying the certificate, both sides derive a shared
   **symmetric** session key (asymmetric crypto, used only for this initial exchange, is far
   too slow to use for the actual bulk data that follows).

Everything after this point is encrypted with the fast symmetric key, not the slow
asymmetric one - asymmetric crypto's whole job in TLS is just to safely establish that
symmetric key in the first place. **TLS 1.3** cut this handshake down to a single round
trip (from two in TLS 1.2) before application data can flow, which is a real, measurable
latency win at scale - and is exactly the extra round trip HTTP/3's QUIC eliminates
entirely by running its transport and TLS 1.3 handshakes together instead of one after the
other.

## Cheat sheet

```
TCP           reliable, ordered, connection-oriented. Sequence numbers+ACKs
              (know what to resend), sliding window (flow control - never
              overwhelm the RECEIVER), congestion control / AIMD (never
              overwhelm the NETWORK), automatic retransmission. Verified:
              5,000 messages into a 4KB buffer -> 100% delivered, in order.
              Setup: 3-way handshake (SYN/SYN-ACK/ACK). Teardown: 4-way
              (FIN/ACK/FIN/ACK) - full-duplex, each direction closes
              independently.

UDP           none of the above, by design. Minimal 8-byte header, zero
              setup latency, fire-and-forget. Verified: same 4KB buffer,
              same load -> 54% silently DROPPED, nothing signaled it.
              Right choice when latency > reliability (DNS, real-time
              audio/video, and HTTP/3's transport).

HTTP/1.1      one request in flight per TCP connection - HOL blocking at
              the HTTP layer, worked around with keep-alive + multiple
              parallel connections. Verified: keep-alive was 3.3x faster
              than a fresh connection per request (199 skipped handshakes).
              Gotcha: Nagle + delayed-ACK without TCP_NODELAY can add ~40ms
              per small request on a reused connection.

HTTP/2        multiplexes many streams over ONE TCP connection (binary
              framing + HPACK header compression) - fixes HTTP-level HOL
              blocking. Doesn't fix TRANSPORT-level HOL blocking: TCP is
              still strictly ordered, so one lost packet stalls every
              stream on that connection.

HTTP/3        QUIC (built on UDP) - per-STREAM loss recovery instead of
              per-connection, fixing transport-level HOL blocking too.
              Transport + TLS 1.3 handshake folded into one round trip.
              Supports connection migration (WiFi -> cellular, same
              connection) - impossible for TCP's IP+port-based identity.

TLS           ClientHello/ServerHello+cert/key exchange -> both sides share
              a fast SYMMETRIC session key (asymmetric crypto only bootstraps
              it). TLS 1.3: 1 round trip (down from 2) - exactly the extra
              round trip HTTP/3 eliminates by merging it with QUIC's own setup.
```
