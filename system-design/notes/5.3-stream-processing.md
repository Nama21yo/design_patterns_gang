title: "5.3 Stream processing"

5.4 covers processing a dataset that already exists in full, sitting on disk somewhere.
**Stream processing** is the other case: data that never stops arriving, where "wait until
it's all here" isn't an option because there is no "all here." This note covers how Spark
extends its batch engine to handle that (Structured Streaming, reading from Kafka), and
Apache Flink, a stream processor built the opposite way - streaming first, with batch
treated as a special case of a stream that happens to end.

## Spark Structured Streaming: the same engine, applied continuously

Structured Streaming's core idea: treat a Kafka topic (or any continuously-arriving
source) as an **unbounded table** that keeps growing, and write a normal-looking query
against it - the same DataFrame API from 5.4, unchanged. Internally, Spark still processes
data in **micro-batches**: on a fixed trigger interval, it looks at whatever new records
have arrived since the last trigger, runs them through the query as one small batch, and
appends/updates the result.

Proven with a real, live local streaming query - the built-in `rate` source stands in for
"a Kafka topic of events" (needs no real broker, but is a genuine streaming source Spark
actually runs micro-batches against, not a simulation):

```python
import shutil
from pyspark.sql import SparkSession

spark = SparkSession.builder.master("local[4]").appName("structured-streaming-demo") \
    .config("spark.ui.enabled", "false").getOrCreate()

checkpoint_dir = "/tmp/spark_streaming_checkpoint_demo"
shutil.rmtree(checkpoint_dir, ignore_errors=True)

stream = spark.readStream.format("rate").option("rowsPerSecond", 25).load()

query = (
    stream.writeStream
    .format("memory")
    .queryName("rate_events")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_dir)
    .trigger(processingTime="1 second")   # micro-batch interval
    .start()
)

query.awaitTermination(timeout=6)   # let several micro-batches run, then stop cleanly
query.stop()

progress_list = query.recentProgress
print(f"{len(progress_list)} micro-batches ran:")
for p in progress_list:
    print(f"  batch {p['batchId']}: {p['numInputRows']} rows in "
         f"{p['durationMs']['triggerExecution']}ms")

total = spark.sql("SELECT count(*) AS n FROM rate_events").collect()[0]["n"]
print(f"total rows accumulated in the unbounded table so far: {total}")

spark.stop()
```

```
6 micro-batches ran:
  batch 0: 0 rows in 2219ms
  batch 1: 50 rows in 549ms
  batch 2: 25 rows in 179ms
  batch 3: 25 rows in 181ms
  batch 4: 25 rows in 185ms
  batch 5: 25 rows in 161ms

total rows accumulated in the unbounded table so far: 150
```

![Measured: 6 real micro-batches on a 1-second trigger, rows accumulating into the unbounded table](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-3-structured-streaming-microbatch.png)

(Re-running this yourself will show slightly different per-batch row counts and millisecond
timings, since it's a live wall-clock-driven source - what to trust is the pattern: several
micro-batches, each on roughly the trigger interval, accumulating into one growing total.)
Six real triggers fired on the 1-second interval, and the row count climbed exactly as
expected for a ~25 rows/sec source over roughly 6 seconds (150 total). Swapping the source
from `rate` to a real Kafka topic in production is a one-line change in the `.format(...)`
call - the query logic, checkpointing, and execution model are identical either way, which
is the entire point of the unbounded-table abstraction.

**Windowed aggregation, watermarking (how late an event is allowed to arrive and still
count), and checkpointing (durably persisting Kafka offsets + aggregation state so a
crashed job resumes exactly where it left off) are covered in full depth in 9.5's Kappa
Architecture section**, including the exact `groupBy(... window(...))` query shape and why
watermarking bounds how much state a long-running windowed query has to keep around - not
repeated here.

## Apache Flink

Where Spark Structured Streaming is a batch engine extended to handle streams (via
micro-batching), **Flink was built stream-first**: every job is fundamentally a continuous
dataflow, and a bounded batch job is just treated as a special case - a stream that happens
to terminate.

### Architecture

![Flink's JobManager/TaskManager (master/worker) architecture](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-3-flink-architecture.png)

- **JobManager** (the "master") - builds the job graph from your program, coordinates
  checkpointing across the whole job, and handles failure recovery.
- **TaskManagers** (the "workers") - each runs one or more **task slots**, and each slot
  runs a parallel subtask of one or more operators in the pipeline. Data flows directly
  between TaskManagers over the network as it's produced, continuously - there's no
  intermediate storage layer between operators the way MapReduce writes to HDFS between
  stages.

This is the same master/worker shape as Spark's driver/executors - the real difference
isn't *who coordinates whom*, it's *how data moves through the workers* once it's running.

### True streaming vs. micro-batching

![Event-at-a-time processing vs. micro-batch buffering](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-3-true-streaming-vs-microbatch.png)

Spark Structured Streaming buffers events for up to one trigger interval before processing
them as a batch - a latency floor of roughly the trigger interval (100ms to low seconds is
typical in practice), traded for higher per-batch throughput. **Flink processes each event
the instant it arrives** - no batch boundary to wait for - giving it a latency floor in the
single-digit milliseconds, which is the single clearest reason to reach for Flink over
Spark Streaming: genuinely latency-sensitive use cases like fraud detection or real-time
bidding, where even a one-second buffering delay is the difference between catching
something and missing it.

### Exactly-once state via checkpoint barriers

Flink's mechanism for **exactly-once state**, even with data flowing continuously and
different input channels arriving at different speeds, is **checkpoint barrier
alignment**: a special barrier marker is injected into every source's output stream at a
checkpoint boundary. An operator with multiple input channels buffers - without
processing - any records that arrive on a channel *after* that channel's barrier, until
the barrier has also arrived on every other input channel. Only once all inputs are
aligned does the operator snapshot its state (guaranteed consistent, since it reflects the
exact same logical point across every input) and then process the buffered records.

![Barrier alignment: a fast channel is buffered until a slower one catches up to the same barrier](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-3-checkpoint-barrier.png)

No real Flink cluster is available to run this against directly, so the algorithm itself
is verified with a from-scratch simulation (the same category as this session's earlier
Bully/Raft election simulations, run and checked rather than just asserted):

```python
BARRIER = object()

def make_stream(records, barrier_after):
    return list(records[:barrier_after]) + [BARRIER] + list(records[barrier_after:])

class MapOperator:
    def __init__(self):
        self.state = 0
        self.snapshots = []
        self._barriers_seen = set()
        self._buffered = {0: [], 1: []}
        self._aligned_channels = {0: False, 1: False}

    def receive(self, channel, item):
        if item is BARRIER:
            self._aligned_channels[channel] = True
            self._barriers_seen.add(channel)
            if len(self._barriers_seen) == 2:
                self.snapshots.append(self.state)      # consistent snapshot point
                self._barriers_seen.clear()
                for ch in (0, 1):
                    self._aligned_channels[ch] = False
                    for buffered_item in self._buffered[ch]:
                        self.state += buffered_item
                    self._buffered[ch] = []
            return
        if self._aligned_channels[channel]:
            self._buffered[channel].append(item)         # past MY barrier, buffer it
        else:
            self.state += item

ch0_records = [1, 1, 1, 1, 1]     # fast channel: 5 events, barrier after 3
ch1_records = [2, 2, 2]            # slow channel: 3 events, barrier after 1
stream0 = make_stream(ch0_records, barrier_after=3)
stream1 = make_stream(ch1_records, barrier_after=1)

op = MapOperator()
i0 = i1 = 0
while i0 < len(stream0) or i1 < len(stream1):
    if i0 < len(stream0):
        op.receive(0, stream0[i0]); i0 += 1
    if i0 < len(stream0):
        op.receive(0, stream0[i0]); i0 += 1
    if i1 < len(stream1):
        op.receive(1, stream1[i1]); i1 += 1

expected_snapshot = sum(ch0_records[:3]) + sum(ch1_records[:1])   # 3 + 2 = 5
final_expected = sum(ch0_records) + sum(ch1_records)               # 5 + 6 = 11

print(f"checkpoint snapshot taken at: {op.snapshots}")
print(f"expected snapshot value (only pre-barrier records on BOTH channels): {expected_snapshot}")
print(f"match: {op.snapshots == [expected_snapshot]}")
print(f"final state after all records processed: {op.state}")
print(f"expected final state: {final_expected}")
print(f"match: {op.state == final_expected}")
```

```
checkpoint snapshot taken at: [5]
expected snapshot value (only pre-barrier records on BOTH channels): 5
match: True
final state after all records processed: 11
expected final state: 11
match: True
```

Even with the fast channel racing two events ahead of the slow one, the snapshot captured
exactly the pre-barrier total (5, not the full 11) - proof the alignment mechanism holds
regardless of which input runs ahead, and that no post-barrier event leaked into the
"before" snapshot. This is what lets Flink recover from a failure by restoring from the
last snapshot and replaying only what came after it, with every operator's state
guaranteed consistent at that point - without ever pausing the whole pipeline to take it.

### What Flink is used for

Genuinely low-latency real-time analytics, fraud detection, complex event processing
(pattern matching over an event stream), and any workload where Spark's micro-batch
latency floor isn't good enough. Note on sourcing: **5.4's Bloomberg stack list does not
include Flink** - it isn't publicly confirmed as part of Bloomberg's stack, so it's covered
here on its own general merits as an industry-standard stream processor, not attached to
any specific company's infrastructure without evidence.
