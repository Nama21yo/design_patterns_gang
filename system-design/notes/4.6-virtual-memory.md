---
title: "4.6 Virtual memory, paging, and the MMU"
---

Before any of the caching material in this Part makes sense, it helps to know what
"memory" actually means to a running program - because it is almost never the raw physical
RAM chips. This note is the OS/hardware layer underneath everything else in Part 4: why
every process gets to pretend it owns the whole address space, how that illusion is built
out of fixed-size pages, and what actually happens on every single memory access to make it
fast.

## Why virtual memory, given that physical memory already exists

Physical RAM is one flat array of bytes shared by every running process. If programs
addressed it directly, three problems show up immediately:

![Why virtual memory exists](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-6-why-virtual-memory.png)

- **No isolation.** Two processes both compiled to expect their data at address `0x4000`
  would collide - or worse, one process could read or corrupt another's memory just by
  guessing an address, with nothing stopping it.
- **Linking is a nightmare.** Every program would need to know, in advance, exactly which
  physical addresses were free at the moment it happened to load - impossible to guarantee
  in a multi-program system.
- **No illusion of abundance.** A process can't be given more memory than physically exists,
  or have rarely-used parts of it quietly moved to disk, without an indirection layer in
  between.

**Virtual memory** is that indirection layer: every process gets its own private virtual
address space (on a 64-bit system, an enormous one), and a piece of hardware - the **MMU**
(memory management unit) - translates every virtual address the process uses into a real
physical address, transparently, on every single memory access. Two processes can both
"use" virtual address `0x4000` and land on two completely different, protected physical
locations.

## Pages and paging

Translating one address at a time, arbitrarily, would need a translation table as big as
memory itself. The fix: divide both virtual and physical memory into fixed-size chunks -
**pages** (virtual side) and **frames** (physical side), commonly 4 KB each - and only ever
map and move memory a whole page at a time.

![How paging maps a virtual page to a physical frame](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-6-paging.png)

A **page table** (one per process) holds the mapping: for each virtual page number, which
physical frame currently holds it, plus bits for whether it's present, writable, and so on.
If a program accesses a page that's valid but not currently loaded (it was swapped out to
disk, or never touched yet), the hardware raises a **page fault**: the CPU traps into the
OS, the OS finds or makes room, loads the page from disk, updates the page table, and
retries the instruction - all invisible to the program, which just sees a slightly slow
memory access.

Splitting memory into fixed-size units this way is also exactly what makes physical memory
manageable under pressure: any free frame, anywhere, can hold any page, so the OS never has
to hunt for one large contiguous hole (contrast this with 4.7's allocator fragmentation
problem, which is exactly what fixed-size paging avoids at the OS level) - and when physical
memory *is* full, "which page do I evict to make room" is a direct instance of the
eviction-algorithm problem covered in 4.1 (early virtual memory systems and modern OS page
replacement both use LRU-family approximations for exactly this decision).

### Doing the address translation, concretely

A virtual address splits into two parts: a **page number** (the upper bits) and an
**offset within the page** (the lower bits - however many bits it takes to address one
page's worth of bytes). Translation replaces the page number with a frame number and keeps
the offset unchanged:

```python
PAGE_SIZE = 4096          # 4 KB pages -> 12 offset bits
OFFSET_BITS = 12

def split(vaddr):
    page_number = vaddr >> OFFSET_BITS
    offset = vaddr & (PAGE_SIZE - 1)
    return page_number, offset

class PageFault(Exception): pass

def translate(vaddr, page_table):
    page_number, offset = split(vaddr)
    if page_number not in page_table:
        raise PageFault(f"page {page_number} not mapped")
    frame_number = page_table[page_number]
    return (frame_number << OFFSET_BITS) | offset

page_table = {256: 12, 257: 90, 300: 4}   # virtual page -> physical frame

vaddr = 0x00101517
pn, off = split(vaddr)
print(f"virtual address 0x{vaddr:08x} -> page {pn} (0x{pn:x}), offset 0x{off:03x}")
paddr = translate(vaddr, page_table)
print(f"page {pn} -> frame {page_table[pn]}  =>  physical address 0x{paddr:08x}")

vaddr2 = 0x00101fff    # last byte of the same page
print(f"virtual 0x{vaddr2:08x} (same page, offset 0xfff) -> "
     f"physical 0x{translate(vaddr2, page_table):08x}")

vaddr3 = 0x00102000    # next page over - not in our tiny page table
try:
    translate(vaddr3, page_table)
except PageFault as e:
    print(f"virtual 0x{vaddr3:08x} -> PAGE FAULT: {e}")
```

```
virtual address 0x00101517 -> page 257 (0x101), offset 0x517
page 257 -> frame 90  =>  physical address 0x0005a517
virtual 0x00101fff (same page, offset 0xfff) -> physical 0x0005afff
virtual 0x00102000 -> PAGE FAULT: page 258 not mapped
```

Notice frame 90 (`0x5a`) is nowhere near page 257 (`0x101`) numerically - that's the whole
point. The offset (`0x517`, `0xfff`) is identical on both sides, because within a page the
layout doesn't change; only which physical frame that page currently lives in does.

## The MMU and the TLB

The full round trip, on every load and store the CPU issues:

![Address translation and the TLB](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-6-address-translation-tlb.png)

Walking the full page table in memory for every single memory access would itself require
extra memory accesses, doubling (or worse, for multi-level page tables) the cost of
everything. The fix is a small, dedicated hardware cache: the **TLB (Translation Lookaside
Buffer)** - a cache of recently-used virtual-page-to-physical-frame translations, sitting
right next to the CPU. A **TLB hit** resolves the translation in about a cycle; a **TLB
miss** falls back to walking the page table (slow), then caches that result in the TLB so
the next access to the same page is fast again. This is the exact same idea as every other
cache in this Part - a small, fast structure holding the recently/frequently used subset of
a much larger, slower structure - just implemented in hardware, one level below anything
software gets to see. If the address turns out to be outside what this process is allowed
to touch at all, the MMU raises an **illegal access exception** instead - what shows up to
you as a segmentation fault.

## The full picture: registers to process memory layout

Put together, one value's journey from "a variable in your code" to "bits in a chip" passes
through every layer this Part covers:

**Registers** (4.8) hold the CPU's immediate working values - a handful of them, directly
wired into the ALU, no addressing needed at all. A **cache miss** on a register spill goes
to the **CPU cache hierarchy** (4.9) - L1, L2, L3, each bigger and slower than the last. A
cache miss there goes to **physical RAM** - via the virtual-to-physical translation this
note just covered. And *within* that virtual address space, a process organizes its own
memory into the regions above:

![A process's memory layout](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-6-memory-layout.png)

- **Text/code segment** (lowest addresses, read-only) - the compiled instructions
  themselves.
- **Data + BSS segment** - global and static variables, sized at compile/link time.
- **Heap** - dynamically allocated memory (`malloc`/`new`), grows upward as the program
  requests more; this is exactly what 4.7's allocation algorithms manage.
- **Stack** (highest addresses) - function call frames and local variables, grows
  *downward* automatically on every function call and shrinks on return, no explicit
  allocation call needed.

Stack and heap grow toward each other from opposite ends of the same address range
precisely because neither one knows in advance how large it needs to be - and the classic
failure modes follow directly from that: a stack that grows too deep (unbounded or
runaway recursion) is a **stack overflow**; a heap that can't satisfy a request because
it's grown to meet the stack, or because free memory exists but not in one big enough
contiguous piece, is a heap exhaustion or (4.7's subject) a fragmentation failure.

## Cheat sheet

```
WHY           physical RAM has no isolation, forces link-time addresses, and gives no
              illusion of abundance. Virtual memory: MMU translates every access,
              per-process private address space, isolation + relocatable linking +
              memory-more-than-RAM (via paging to disk).

PAGES         fixed-size chunks (e.g. 4 KB) on both sides: virtual PAGES, physical
              FRAMES. Any free frame fits any page -> no "find a big enough hole"
              problem at this layer (contrast 4.7's allocator fragmentation).
              Page table: page number -> frame number, + present/permission bits.
              Not present when accessed -> PAGE FAULT -> OS loads it from disk,
              updates the table, retries - invisible to the program.

TRANSLATION   virtual address = page number (high bits) + offset (low bits).
              physical address = (frame number << offset_bits) | offset.
              Verified: page 257 -> frame 90 => 0x00101517 -> 0x0005a517,
              offset 0x517 unchanged on both sides.

MMU + TLB     every access: TLB check (fast, ~1 cycle, hits ~99% of the time) ->
              on a miss, walk the page table in memory (slow), cache the result.
              Same "small fast cache in front of a big slow structure" idea as
              every other cache in this Part, done in hardware.
              Address outside this process's mapped pages -> illegal access
              exception -> segfault.

LAYOUT        low -> high addresses: text/code (read-only) -> data+BSS (globals) ->
              heap (grows UP, malloc/new, what 4.7 manages) -> [gap] -> stack
              (grows DOWN, function frames, automatic). Stack/heap collision =
              stack overflow or heap exhaustion.

THE FULL      registers (4.8) -> CPU cache L1/L2/L3 (4.9) -> physical RAM, reached
PICTURE       via THIS note's virtual->physical translation -> (on a miss further
              still) disk. Every hop: small/fast in front of big/slow.
```
