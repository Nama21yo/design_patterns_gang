title: "1.4 CAP theorem and PACELC"
---

1.2 established availability and 1.5 (next) establishes consistency as separate axes. CAP
is the theorem that says you cannot have your pick of both, under one specific condition -
and PACELC is the fix for the part of CAP that interview candidates most often misstate:
what happens the rest of the time, when there's no partition at all.

## CAP: the choice only exists during a partition

**CAP** states that a distributed system can provide at most two of **Consistency** (every
read sees the latest write), **Availability** (every request gets a response), and
**Partition tolerance** (the system keeps working despite network messages being dropped
or delayed between nodes) - simultaneously.

The framing worth correcting immediately, because it's the most common way this gets
misstated: **P isn't really a choice.** A distributed system, by definition, runs across
multiple machines connected by a network, and that network *will* eventually drop or delay
messages - partitions aren't a rare edge case to architect around, they're a certainty over
a long enough time horizon. The actual decision CAP describes only shows up **during** a
partition: once nodes can't talk to each other, do you keep serving requests on **both**
sides (favoring availability, accepting the sides may now disagree) or do you refuse
requests on the side that can't verify it has the latest data (favoring consistency, at the
cost of availability right there)?

![CAP only governs behavior DURING a partition - not a permanent, always-on 3-way trade](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-4-cap-during-partition.png)

### CP vs. AP, concretely

3.5's leaderless quorum replication (`R + W > N`) is the exact mechanism this plays out
through. Simulated directly: a 3-node cluster (`N=3`, write quorum `W=2`) hit by a
partition that isolates one node from the other two.

```python
class QuorumCluster:
    def __init__(self, nodes, w):
        self.nodes = {n: {} for n in nodes}
        self.w = w

    def write(self, reachable_nodes, key, value, mode):
        if mode == "CP":
            if len(reachable_nodes) < self.w:
                return False, f"REFUSED - only {len(reachable_nodes)} of {self.w} needed reachable"
            for n in reachable_nodes:
                self.nodes[n][key] = value
            return True, f"accepted, written to {reachable_nodes}"
        elif mode == "AP":
            for n in reachable_nodes:
                self.nodes[n][key] = value
            return True, f"accepted (no quorum check), written to {reachable_nodes}"


N = ["node1", "node2", "node3"]
W = 2

cp = QuorumCluster(N, W)
ok, msg = cp.write(reachable_nodes=["node1"], key="balance", value=500, mode="CP")
print(f"CP system, minority side (1 of 3 reachable): write {'SUCCEEDED' if ok else 'FAILED'} - {msg}")
ok2, msg2 = cp.write(reachable_nodes=["node2", "node3"], key="balance", value=500, mode="CP")
print(f"CP system, majority side (2 of 3 reachable): write {'SUCCEEDED' if ok2 else 'FAILED'} - {msg2}")

ap = QuorumCluster(N, W)
ok3, msg3 = ap.write(reachable_nodes=["node1"], key="balance", value=500, mode="AP")
print(f"AP system, minority side (1 of 3 reachable): write {'SUCCEEDED' if ok3 else 'FAILED'} - {msg3}")
ok4, msg4 = ap.write(reachable_nodes=["node2", "node3"], key="balance", value=700, mode="AP")
print(f"AP system, majority side (2 of 3 reachable), a DIFFERENT value written concurrently: "
     f"write {'SUCCEEDED' if ok4 else 'FAILED'} - {msg4}")

print(f"AP cluster state after the partition heals: {ap.nodes}")
```

```
CP system, minority side (1 of 3 reachable): write FAILED - REFUSED - only 1 of 2 needed reachable
CP system, majority side (2 of 3 reachable): write SUCCEEDED - accepted, written to ['node2', 'node3']
AP system, minority side (1 of 3 reachable): write SUCCEEDED - accepted (no quorum check), written to ['node1']
AP system, majority side (2 of 3 reachable), a DIFFERENT value written concurrently: write SUCCEEDED - accepted (no quorum check), written to ['node2', 'node3']
AP cluster state after the partition heals: {'node1': {'balance': 500}, 'node2': {'balance': 700}, 'node3': {'balance': 700}}
```

![Verified: CP refuses the minority write; AP accepts it and genuinely diverges](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-4-cp-vs-ap-verified.png)

The **CP** system refuses the isolated node's write outright - it can't reach the `W=2`
quorum, so it sacrifices availability on that side rather than risk an inconsistent
result. The **AP** system accepts writes on *both* sides of the exact same partition,
staying available everywhere - and ends up with a real, measured divergence: `node1` holds
`balance=500` while `node2`/`node3` hold `balance=700`, a disagreement that didn't exist
before the partition and has to be resolved afterward, which is precisely what 3.5's read
repair and anti-entropy mechanisms exist to clean up.

## PACELC: filling in what happens the rest of the time

CAP's silence about normal operation is a real gap, and PACELC (Abadi, 2010) names it
directly: **P**artition - **A**vailability or **C**onsistency (exactly CAP, above); **E**lse
- **L**atency or **C**onsistency.

![PACELC: CAP governs the partition case; "else" is a genuinely separate, everyday trade-off](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-4-pacelc-flow.png)

The "else" branch isn't a hypothetical - it's exactly 3.5's synchronous-vs-asynchronous
replication choice, already proven live with **no partition involved at all**: a
synchronous commit (favoring **C**onsistency - the replica is guaranteed caught up before
the client sees success) blocked for a measured **4.06 seconds** when its standby simply
became unreachable, even though nothing about the *network* was partitioned in the CAP
sense - the standby was just down. An asynchronous commit (favoring **L**atency) never
blocks at all, at the measured cost of a **~1.24ms** window where a replica can serve
genuinely stale data. That's PACELC's entire point: **even with a perfectly healthy
network, a system still has to choose between latency and consistency**, every single
time it writes - CAP alone has nothing to say about this case, because CAP only engages
once a partition exists.

### Classifying real systems

![Most real systems sit at one of four PACELC points, not a single spot on the CAP triangle](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/1-4-pacelc-quadrants.png)

- **PC/EC** - always choose consistency, partition or not. A traditional RDBMS with
  synchronous replication (3.5): consistent under a partition (refuses rather than diverges)
  *and* consistent in normal operation (pays the latency cost of waiting for acks every
  time).
- **PA/EL** - always choose availability/latency. Dynamo-style leaderless stores
  (Cassandra, the design behind DynamoDB, 3.5's quorum section): available under a
  partition (accepts writes with whatever quorum is reachable) *and* low-latency in normal
  operation (doesn't wait for every replica to ack).
- **PC/EL** - a hybrid: consistent under a partition, but willing to trade consistency for
  latency during normal operation when explicitly configured to (several tunable-consistency
  stores like MongoDB support this per operation).

Most production systems are a genuine PACELC point, not a single spot on the CAP
triangle - which is exactly why "CP or AP?" is an incomplete question in an interview
without also asking what the system does under normal, non-partitioned load.

## Cheat sheet

```
CAP           P isn't really optional (a real network WILL partition
              eventually) - the actual choice only exists DURING a
              partition: CP (refuse the side that can't verify it's
              current - sacrifice availability) vs AP (serve both sides -
              sacrifice consistency, sides diverge). Verified with 3.5's
              R+W>N quorum cluster: CP refused a minority-side write; AP
              accepted it and produced a real divergence (500 vs 700)
              that needed read repair afterward.

PACELC        extends CAP to the common case: Partition -> A or C (= CAP).
              Else (no partition, the EVERYDAY case) -> Latency or
              Consistency. Verified via 3.5's sync/async replication
              proof: synchronous commit (favors C) blocked 4.06s when its
              standby was merely unreachable, NO partition involved;
              asynchronous (favors L) never blocks, at a measured ~1.24ms
              staleness-window cost.

CLASSES       PC/EC: always consistency (sync RDBMS). PA/EL: always
              availability/latency (Dynamo-style, 3.5). PC/EL: consistent
              under partition, latency-favoring otherwise (tunable
              stores). Most real systems are one of these 4 points, not a
              single spot on the CAP triangle - "CP or AP?" alone is an
              incomplete interview question without also asking about
              normal-operation behavior.
```
