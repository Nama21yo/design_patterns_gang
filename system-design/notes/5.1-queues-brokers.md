title: "5.1 Message queues and brokers"
---

Every request-response call so far in this course assumes the caller waits: send a
request, block, get a response. Plenty of real work doesn't fit that shape - work that
takes too long to make a user wait for, or that needs to trigger dependent steps on other
machines once it's done. This note is the mechanism that decouples "a piece of work exists"
from "something is available to do it right now": message brokers, and their two major
flavors - traditional queues (RabbitMQ, SQS) and the log-based model Kafka popularized.

## Why asynchronous processing at all

Take video upload: a user uploads a video, and the system needs to transcode it into
several resolutions (480p, 720p, 1080p) before it's watchable anywhere. Doing this
**synchronously** - the upload request blocks until all three transcodes finish - ties up a
request thread for however long transcoding takes (easily minutes), and the user is
sitting on a spinner the whole time for work that doesn't need to happen before you can
tell them "upload received."

![Why decouple: a broker as a buffer between producing work and consuming it](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-1-async-decoupling.png)

A **message broker** fixes this by sitting between producer and consumer as a **buffer**:
the upload handler drops 3 transcode jobs onto a queue and responds to the user
immediately; a separate pool of transcode workers pulls jobs whenever *they* have spare
capacity. Producer and consumer rates no longer have to match - the broker absorbs the
difference. This is also exactly how you **trigger dependent tasks across machines**: the
video service doesn't need to know anything about which machine will do the transcoding,
or how many workers exist, or whether they're busy right now - it just enqueues the work
and moves on.

## Broker mechanics: buffering, and requeueing

A message sits in the queue until a consumer explicitly **acknowledges (ACKs)** that it's
done - not merely received. Between "received" and "ACKed," the message is marked
invisible to other consumers for a **visibility timeout**; if the consumer that received it
crashes or hangs before ACKing (say, a worker dies partway through generating subtitles for
a video), the visibility timeout expires and the message becomes visible again for another
consumer to pick up - a **requeue**, with no manual intervention needed.

![Broker requeue mechanics on a consumer crash](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-1-broker-requeue.png)

Proven with real `boto3` calls against a moto-mocked SQS queue - the actual AWS SDK and API
shape, not a hand-rolled simulation:

```python
import time
import boto3
from moto import mock_aws


@mock_aws
def run():
    sqs = boto3.client("sqs", region_name="us-east-1")
    queue_url = sqs.create_queue(
        QueueName="video-transcode-jobs",
        Attributes={"VisibilityTimeout": "2"},
    )["QueueUrl"]

    for res in ("480p", "720p", "1080p"):
        sqs.send_message(QueueUrl=queue_url, MessageBody=f"transcode video_42 to {res}")
    print("enqueued 3 transcode jobs (video upload -> async resolution changes)")

    msgs = sqs.receive_message(QueueUrl=queue_url, MaxNumberOfMessages=1)["Messages"]
    first = msgs[0]
    print(f"\nworker picks up: {first['Body']!r}")
    sqs.delete_message(QueueUrl=queue_url, ReceiptHandle=first["ReceiptHandle"])
    print("processed successfully -> deleted (acked) -> will NOT be redelivered")

    msgs = sqs.receive_message(QueueUrl=queue_url, MaxNumberOfMessages=1)["Messages"]
    crashed = msgs[0]
    print(f"\nworker picks up: {crashed['Body']!r}")
    print("worker crashes before calling delete_message() - message is NOT acked")

    visible_now = sqs.receive_message(QueueUrl=queue_url, MaxNumberOfMessages=10).get("Messages", [])
    print(f"\nimmediately after the crash: {len(visible_now)} other message(s) visible "
         f"(the crashed one is hidden until its visibility timeout expires)")

    print("waiting for the visibility timeout to expire (requeue)...")
    time.sleep(2.5)

    redelivered = sqs.receive_message(QueueUrl=queue_url, MaxNumberOfMessages=10).get("Messages", [])
    bodies = [m["Body"] for m in redelivered]
    print(f"after the timeout: {len(redelivered)} message(s) visible again: {bodies}")
    print(f"'{crashed['Body']}' was requeued automatically: {crashed['Body'] in bodies}")


if __name__ == "__main__":
    run()
```

```
enqueued 3 transcode jobs (video upload -> async resolution changes)

worker picks up: 'transcode video_42 to 480p'
processed successfully -> deleted (acked) -> will NOT be redelivered

worker picks up: 'transcode video_42 to 720p'
worker crashes before calling delete_message() - message is NOT acked

immediately after the crash: 1 other message(s) visible (the crashed one is hidden until its visibility timeout expires)
waiting for the visibility timeout to expire (requeue)...
after the timeout: 2 message(s) visible again: ['transcode video_42 to 720p', 'transcode video_42 to 1080p']
'transcode video_42 to 720p' was requeued automatically: True
```

The crashed job's message became invisible the instant it was received, stayed hidden
while another message remained available, and then reappeared automatically once its
visibility timeout elapsed - proof that the requeue mechanism works without any explicit
"retry" code on the producer's side. Popular traditional brokers built on this queue model:
**RabbitMQ** (a general-purpose broker supporting several protocols and routing
topologies), **Amazon SQS** (the managed queue demonstrated above), and **NATS** (a
lightweight, high-throughput broker popular for simple pub/sub and request/reply inside a
single infrastructure).

## Message streams: the log model (Kafka)

Traditional queues share one property: once a message is consumed and ACKed, it's **gone**
- a second consumer, or a consumer that joins the party late, never sees it. That's fine
when there's exactly one logical "thing" that needs to happen per message. It breaks down
the moment more than one independent thing needs to happen for the same event.

Concretely: a blog gets published, and the system needs to (1) index it in a search engine
and (2) increment the author's total-post counter. Doing both **inline in one process** -
call the index service, then call the counter service - has a partial-failure problem worth
naming precisely (5.2 covers it in full): if the first call succeeds and the second fails,
you're left with a permanently inconsistent state and no record that it happened.

**Apache Kafka** solves the underlying issue differently: instead of a queue that empties
as it's consumed, a Kafka **topic** is a durable, append-only **log**. Messages aren't
removed when read - they're retained for a configured period, and multiple independent
**consumer groups** can each read the same topic at their own pace, each tracking its own
position (offset) into the log. This gives the **write to one, read to many** semantic the
dual-service example actually needs: publish one event to one topic, and let the search
indexer and the counter service each consume it independently, in their own retry loop,
with no coordination between them at all.

### Kafka essentials: topics, partitions, and the consumer limit

A topic is split into **partitions** for parallelism. Each message is written with a
**key**, and `hash(key) % num_partitions` decides which partition it lands in - so every
message for the same key always lands in the same partition, giving you ordering *within*
a key, though not across the whole topic:

![Kafka topic split into partitions, routed by key](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-1-kafka-topic-partitions.png)

Verified with a from-scratch simulation of the actual partitioning/assignment algorithm (no
real Kafka broker running - a full JVM cluster is heavier than this mechanism needs to
prove itself, same category as this session's earlier Bully/Raft/Flink-barrier
simulations):

```python
import hashlib


class Topic:
    def __init__(self, name, num_partitions):
        self.name = name
        self.num_partitions = num_partitions
        self.partitions = {i: [] for i in range(num_partitions)}

    def _partition_for_key(self, key):
        h = int(hashlib.md5(key.encode()).hexdigest(), 16)
        return h % self.num_partitions

    def produce(self, key, value):
        p = self._partition_for_key(key)
        offset = len(self.partitions[p])
        self.partitions[p].append((key, value))
        return p, offset


def assign_partitions(num_partitions, consumer_ids):
    assignment = {c: [] for c in consumer_ids}
    for i, p in enumerate(range(num_partitions)):
        consumer = consumer_ids[i % len(consumer_ids)]
        assignment[consumer].append(p)
    return assignment


topic = Topic("blog-events", num_partitions=4)
events = [
    ("blog_101", "created"),
    ("blog_202", "created"),
    ("blog_101", "published"),
    ("blog_101", "edited"),
    ("blog_303", "created"),
]
print("producing keyed events:")
for key, value in events:
    p, offset = topic.produce(key, value)
    print(f"  key={key:10s} value={value:10s} -> partition {p}, offset {offset}")

blog_101_partitions = {topic._partition_for_key("blog_101") for _ in range(3)}
print(f"\nall 'blog_101' events landed on partition(s): {blog_101_partitions} "
     f"(same key -> same partition, every time -> per-key order is preserved)")

print("\n--- consumer group sizing, topic with 4 partitions ---")
for consumers in (2, 4, 6):
    consumer_ids = [f"consumer-{i}" for i in range(consumers)]
    assignment = assign_partitions(4, consumer_ids)
    idle = [c for c, parts in assignment.items() if not parts]
    print(f"\n{consumers} consumers in the group:")
    for c, parts in assignment.items():
        status = "IDLE - no partitions assigned" if not parts else f"owns partitions {parts}"
        print(f"  {c}: {status}")
    if idle:
        print(f"  -> {len(idle)} consumer(s) sit completely idle: "
             f"more consumers than partitions wastes capacity")
```

  key=blog_202   value=created    -> partition 1, offset 0
  key=blog_101   value=published  -> partition 3, offset 1
  key=blog_101   value=edited     -> partition 3, offset 2
  key=blog_303   value=created    -> partition 0, offset 0

  consumer-0: owns partitions [0, 2]
  consumer-1: owns partitions [1, 3]

  consumer-2: owns partitions [2]
  consumer-3: owns partitions [3]

![The consumer<=partition limit, measured](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-1-consumer-partition-limit.png)

The hard limitation this proves: **a partition can only be assigned to one consumer within
a given consumer group at a time.** Parallelism inside a group tops out at the partition
count - adding a 5th and 6th consumer to a 4-partition topic did nothing but leave them
idle. This is the single most important capacity-planning number for Kafka: **partition
count is your parallelism ceiling**, decided at topic-creation time (partitions can be
added later, but existing keys' partition assignment shifts when you do, which is a real
operational cost, not a free lever).

## Queue vs. log, side by side

![Message queue (consume-and-remove) vs. message log (retain-and-replay)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-1-queue-vs-log.png)

A traditional queue (RabbitMQ, SQS) is the right fit when there's genuinely **one** logical
consumer for each message (a job queue: exactly one worker should do exactly one
transcode). A log (Kafka) is the right fit the moment **more than one independent thing**
needs to react to the same event, or a consumer needs to be able to **replay** history -
5.5 builds directly on this distinction for fan-out patterns specifically.

## Cheat sheet

```
WHY ASYNC     long-running work + cross-machine dependent tasks. Broker = buffer
              that decouples producer rate from consumer rate.

REQUEUE       message invisible (not gone) once received; visibility timeout
              expires -> automatically redelivered if never ACKed. Verified with
              real moto-mocked SQS: a crashed worker's job was requeued and
              picked up again automatically, with no explicit retry code.

QUEUE MODEL   RabbitMQ / SQS / NATS - consumed + ACKed = GONE. One logical
(traditional) consumer per message is the right shape. A late-joining consumer
              gets nothing that was already consumed.

LOG MODEL     Kafka - durable, append-only. Each consumer GROUP tracks its own
(streams)     offset independently; messages retained for a period, replayable.
              Solves "write to one, read to many": multiple independent
              consumers can each react to the same event.

KAFKA         topic -> N partitions, hash(key) % N picks the partition ->
ESSENTIALS    per-key order preserved WITHIN a partition, none across the
              topic. HARD LIMIT: a partition is owned by at most one consumer
              per group - verified, 6 consumers on 4 partitions left 2 idle.
              Partition count is decided at topic-creation time and IS your
              parallelism ceiling.

QUEUE vs LOG  queue: one consumer per message, simple, nothing to replay.
              log: many independent consumer groups, replayable, but more
              moving parts (offsets, retention, partition planning).
```
