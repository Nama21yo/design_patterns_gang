title: "4.9 CPU caches: associativity and cache-friendly code"
---

4.8 put the CPU cache on the memory-hierarchy ladder without saying how it actually decides
where a piece of memory goes once it's cached. This note is that mechanism - the design
space of cache placement policies, why the choice matters enough to be worth dedicated
silicon, and how to write code that cooperates with whatever cache is actually sitting
between your program and RAM.

## The placement problem

A CPU cache is much smaller than RAM, so it can only hold a small fraction of all memory
blocks at once. Every scheme for deciding **which cache line a given memory block is
allowed to occupy** trades off two things: how expensive the hardware is to build (checking
more possible locations per lookup needs more comparators, running in parallel, every
single cycle) against how well it avoids **collisions** - two blocks you actually need at
the same time being forced to fight over the same line.

## Direct-mapped cache

The simplest and cheapest: every memory block maps to **exactly one** possible cache line
(typically `block_address % number_of_lines`). Checking for a hit is trivial - look at
that one line, compare its tag, done - but it's maximally collision-prone: two blocks that
happen to hash to the same line can never both be cached at once, no matter how much of the
rest of the cache sits idle.

## Fully associative cache

The opposite extreme: a block can go in **any** line at all. This eliminates that kind of
collision entirely - a block is only evicted because the cache is genuinely full, never
because of an unlucky address - but a lookup now has to compare the requested address
against *every* line's tag, in parallel, which gets expensive fast as cache size grows.
Practical only for very small caches (like the TLB from 4.6, which typically *is* fully
associative, precisely because it's small).

## Set-associative cache (N-way)

The practical middle ground nearly every real CPU cache uses: lines are grouped into
**sets**, a block maps to exactly **one set** (by address, same as direct-mapped), but can
go in **any of the N lines within that set** (like a small fully-associative cache, just
scoped down). `N` here is the "way" - a "4-way set-associative" cache checks 4 tags in
parallel per lookup, not all of them.

![The associativity spectrum](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-9-associativity-spectrum.png)

Direct-mapped and fully associative are just the two endpoints of this same idea: direct-
mapped is "N-way with 1 way per set (many sets)"; fully associative is "N-way with 1 set
(all lines)."

### Proving why this matters: a working set that fits, or doesn't

Simulate all three policies against the *same* access pattern - 3 memory blocks that all
alias the same line/set under a narrow cache, accessed in a repeating cycle:

```python
from collections import OrderedDict

NUM_LINES = 8

def direct_mapped(accesses):
    cache = {}
    hits = 0
    for block in accesses:
        line = block % NUM_LINES
        if cache.get(line) == block:
            hits += 1
        else:
            cache[line] = block
    return hits

def set_associative(accesses, ways):
    num_sets = NUM_LINES // ways
    sets = [OrderedDict() for _ in range(num_sets)]
    hits = 0
    for block in accesses:
        s = sets[block % num_sets]
        if block in s:
            hits += 1
            s.move_to_end(block)
        else:
            if len(s) >= ways:
                s.popitem(last=False)
            s[block] = True
    return hits

def fully_associative(accesses):
    cache = OrderedDict()
    hits = 0
    for block in accesses:
        if block in cache:
            hits += 1
            cache.move_to_end(block)
        else:
            if len(cache) >= NUM_LINES:
                cache.popitem(last=False)
            cache[block] = True
    return hits

hot_blocks = [0, 8, 16]              # 3 blocks, all aliasing the same line
accesses = hot_blocks * 20

print(f"direct-mapped (1-way)           : {direct_mapped(accesses)} hits / {len(accesses)}")
for ways in (2, 4, 8):
    print(f"{ways}-way set-associative           : {set_associative(accesses, ways)} hits / {len(accesses)}")
print(f"fully associative (8-way, 1 set): {fully_associative(accesses)} hits / {len(accesses)}")
```

```
direct-mapped (1-way)           : 0 hits / 60
2-way set-associative           : 0 hits / 60
4-way set-associative           : 57 hits / 60
8-way set-associative           : 57 hits / 60
fully associative (8-way, 1 set): 57 hits / 60
```

![Measured hit rate by associativity](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-9-associativity-results.png)

A stark, exact cutoff: with only 1 or 2 ways available for these 3 competing blocks,
**every single access misses** (2 ways still isn't enough room for 3 blocks accessed in a
fixed rotation - each access evicts the exact block that's about to be needed next, a
classic thrashing pattern). The moment the associativity (4-way) is large enough that all 3
blocks fit simultaneously, the hit rate jumps to effectively 100% (57/60 - the first pass
through each of the 3 blocks is unavoidably a miss, everything after that hits). This is
the entire practical argument for associativity: it's not about the *average* case, it's
about how many distinct, simultaneously-hot addresses your cache can hold *without them
evicting each other* purely due to bad luck in which line they hash to.

## Two refinements worth knowing by name

![Two-way skewed and pseudo-associative caches](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/4-9-skewed-pseudo-associative.png)

- **Two-way skewed associative** - like a 2-way set-associative cache, but each of the 2
  ways uses a *different* hash function to pick its line. Two blocks that collide in way 0
  usually won't also collide in way 1 (different hash, different collision pattern), so in
  practice a skewed-associative cache gets hit rates close to a much more expensive
  higher-way design, at roughly 2-way hardware cost.
- **Pseudo-associative (column-associative)** - checks one primary line at direct-mapped
  speed; on a miss, checks exactly one alternate line before giving up. Most accesses hit on
  the fast, cheap, direct-mapped-speed path; the occasional pathological collision gets a
  second chance instead of guaranteed eviction, recovering some of associativity's benefit
  without paying its full lookup cost on every single access.

## Cache-friendly code

None of the hardware above can help if the *access pattern itself* is bad. Two classic,
measurable examples:

**Loop order: traverse memory in the order it's actually laid out.** A 2D array is stored
as one flat, contiguous block of memory, row by row (row-major, the default in C, numpy, and
most languages). Summing it row-by-row visits consecutive memory addresses - cheap,
sequential, hits the same cache line repeatedly before moving to the next; summing it
column-by-column jumps by one full row's width on every single access - each step likely
lands on a different cache line, forcing a fresh fetch from a slower level of 4.8's
hierarchy far more often:

```python
import numpy as np
import time

N = 4000
a = np.arange(N * N, dtype=np.float64).reshape(N, N)

t0 = time.perf_counter()
row_sum = sum(a[i, :].sum() for i in range(N))     # contiguous, row-major
t1 = time.perf_counter()

t2 = time.perf_counter()
col_sum = sum(a[:, j].sum() for j in range(N))     # strided, column-major
t3 = time.perf_counter()

print(f"row-major (contiguous): {t1 - t0:.4f}s")
print(f"column-major (strided): {t3 - t2:.4f}s")
print(f"ratio: {(t3 - t2) / (t1 - t0):.2f}x")
```

```
row-major (contiguous): 0.0293s
column-major (strided): 0.0757s
ratio: 2.59x
```

Same data, same total amount of arithmetic, same machine - a real multi-x factor (the exact
ratio varies by run and hardware load - low single digits every time we've measured it) just
from the order the bytes are visited in.

**Blocking (tiling): restructure an algorithm to work on small, cache-sized chunks at a
time.** A naive matrix transpose reads one input element and writes it to a scattered
output location, over and over, for the entire matrix - the working set of "recently
touched" memory is the whole matrix, far bigger than any cache. A **blocked** transpose
processes one small block (say 32x32) at a time - small enough that the whole block stays
resident in cache while it's being worked on - before moving to the next block:

```python
def naive_transpose(a, N):
    b = [[0.0] * N for _ in range(N)]
    for i in range(N):
        for j in range(N):
            b[j][i] = a[i][j]
    return b

def blocked_transpose(a, N, block=16):
    b = [[0.0] * N for _ in range(N)]
    for ii in range(0, N, block):
        for jj in range(0, N, block):
            for i in range(ii, min(ii + block, N)):
                for j in range(jj, min(jj + block, N)):
                    b[j][i] = a[i][j]
    return b

import random, time
N = 300
a = [[random.random() for _ in range(N)] for _ in range(N)]

t0 = time.perf_counter(); r1 = naive_transpose(a, N); t1 = time.perf_counter()
t2 = time.perf_counter(); r2 = blocked_transpose(a, N, block=16); t3 = time.perf_counter()

print(f"naive pure-python transpose:   {t1 - t0:.3f}s")
print(f"blocked pure-python transpose: {t3 - t2:.3f}s")
print(f"same result: {r1 == r2}")
print(f"speedup: {(t1 - t0) / (t3 - t2):.2f}x")
```

```
naive pure-python transpose:   0.009s
blocked pure-python transpose: 0.010s
same result: True
speedup: 0.91x
```

Worth reporting honestly rather than cherry-picking a flattering run: **blocking showed no
reliable benefit here, and was sometimes measurably slower** - re-running at several sizes
gave ratios clustered right around 1.0x, occasionally below it. Two real reasons, both
informative:

1. **Python's `list`-of-`list`s isn't actually contiguous memory.** Each row is a separate
   Python list object, allocated wherever the heap happens to have room - so there's no
   real spatial locality for blocking to exploit in the first place, unlike a true 2D array
   (numpy's, or a C array) that's one contiguous block underneath.
2. **Interpreter overhead per element dwarfs the cost of a single cache miss.** The row/col
   test above used numpy specifically because numpy arrays *are* contiguous and each
   operation is a single vectorized call - which is exactly why that comparison shows a
   clean, stable, multi-x effect while this one, done with pure-Python nested loops and
   list-of-lists, doesn't.

The underlying principle - restructure an algorithm to work on cache-sized chunks at a
time, and finish with each chunk before moving to the next - is real and matters a great
deal in C, Fortran, and numeric libraries (numpy's own internals, BLAS) written specifically
to keep data contiguous and let this technique work, typically worth 3-10x on large
matrices there. The honest lesson from measuring it here: cache-friendliness is a property
of the *actual memory layout* a language/data structure gives you, not just the algorithm's
loop order on paper - and it's worth checking which one you actually have before assuming a
textbook optimization pays off.

## Cheat sheet

```
PLACEMENT     every scheme trades hardware cost (parallel tag comparators) against
POLICIES      collision avoidance (two hot blocks forced to share one line).

DIRECT-MAPPED block -> exactly 1 line. Cheapest, most collision-prone.
FULLY ASSOC.  block -> any line. No placement collisions, but O(lines) parallel
              tag comparison - only practical for small caches (e.g. the TLB, 4.6).
N-WAY SET     block -> 1 of N lines within its set. The practical middle ground
ASSOCIATIVE   nearly every real CPU cache uses. Direct-mapped = 1-way; fully
              associative = "1 set."
              Verified: a 3-block working set gets 0% hits at 1-2 ways (doesn't
              fit, thrashes every access) and ~95%+ at 4+ ways (fits, all misses
              are one-time compulsory misses).

REFINEMENTS   2-way SKEWED: different hash per way -> near-higher-way hit rates
              at 2-way cost. PSEUDO-ASSOCIATIVE: direct-mapped-speed primary
              check, one alternate line on miss -> most of the benefit, most
              of the time, without full associative lookup cost every access.

CACHE-        traverse memory in its actual layout order (row-major for a
FRIENDLY      row-major array) - verified 2-4x from access order alone on a
CODE          contiguous numpy array, same data, same op. BLOCK/TILE algorithms
              to work on cache-sized chunks at a time: verified NO reliable
              benefit on pure-Python list-of-lists (not contiguous memory,
              interpreter overhead dominates) - the technique needs actual
              contiguous memory (numpy/C/Fortran) to pay off, typically 3-10x
              there. Cache-friendliness is a property of real memory layout,
              not just loop order on paper.
```
