title: "5.5 Pub/Sub and fan-out patterns"

5.2 left off with a fix for the dual-write problem that hadn't been shown working yet: one
durable log, multiple independent consumer groups. This note is that mechanism in full -
**fan-out**, the general pattern of one event reaching many independent recipients - in two
different senses: fanning a single stream **out to multiple consumer groups**, and the
completely different question of fanning **content out to many readers' feeds**, which is
where the *fan-out on write vs. fan-out on read* trade-off comes in. It closes with
real-time pub/sub (Redis-style) as a distinct, non-durable pattern that solves a different
problem than either.

## Fixing 5.2's dual-write problem: one topic, many consumer groups

The mechanism 5.1 set up but didn't demonstrate: a Kafka topic is a durable log, and any
number of independent **consumer groups** can each read the entire thing at their own pace,
each tracking its own offset.

![One topic, two independent consumer groups, each getting the full stream](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-5-multi-consumer-group.png)

```python
class Topic:
    def __init__(self):
        self.log = []
        self.group_offsets = {}

    def produce(self, event):
        self.log.append(event)

    def poll(self, group):
        offset = self.group_offsets.get(group, 0)
        new_events = self.log[offset:]
        self.group_offsets[group] = len(self.log)
        return new_events


topic = Topic()
topic.produce("blog_1 published")
topic.produce("blog_2 published")

search_group_events = topic.poll("search-index-group")
print(f"search-index-group (joined immediately) received: {search_group_events}")

topic.produce("blog_3 published")

counter_group_events = topic.poll("counter-group")
print(f"counter-group (joined late) received: {counter_group_events}")

search_group_events_2 = topic.poll("search-index-group")
print(f"search-index-group's next poll only gets the NEW event: {search_group_events_2}")
```

```
search-index-group (joined immediately) received: ['blog_1 published', 'blog_2 published']
counter-group (joined late) received: ['blog_1 published', 'blog_2 published', 'blog_3 published']
search-index-group's next poll only gets the NEW event: ['blog_3 published']
```

Both groups independently see the **full** stream, at their own pace - `counter-group`
joined after two events had already been produced and still received all three, because
it's reading from its own offset into the *same retained log*, not from a shared "already
consumed" pointer. This is precisely what fixes 5.2's dual-write problem: instead of one
process making two side-effecting calls inline (indexing, then incrementing, with no
atomicity between them), the search-indexing logic and the counter-incrementing logic each
become an independent consumer group with its own retry loop against the same event. A
failure in one never blocks or corrupts the other, and either can be restarted, replayed,
or scaled independently.

## Fan-out on write vs. fan-out on read

A different, and unrelated, use of the term "fan-out": in a social/feed system, when a user
posts, whose job is it to get that post in front of every follower - and *when*?

![Fan-out on write (push) vs. fan-out on read (pull)](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-5-fanout-patterns.png)

- **Fan-out on write (push)** - the instant someone posts, push a copy of that post into
  *every follower's* precomputed feed. Reading a feed later is then just "read my own
  precomputed list" - an O(1) lookup, no matter how complex the underlying social graph is.
- **Fan-out on read (pull)** - posting just appends to the author's own post list, full
  stop, regardless of follower count. Reading a feed means *merging* posts from everyone
  you follow, **at request time**.

The trade-off is invisible until follower counts get extreme. Measured directly - a normal
user with 200 followers vs. a celebrity account with 2,000,000:

```python
import time


class FanOutOnWrite:
    def __init__(self):
        self.feeds = {}

    def post(self, author, followers, content):
        for follower in followers:
            self.feeds.setdefault(follower, []).append((author, content))

    def read_feed(self, user_id):
        return self.feeds.get(user_id, [])


class FanOutOnRead:
    def __init__(self):
        self.posts_by_author = {}

    def post(self, author, followers, content):
        self.posts_by_author.setdefault(author, []).append(content)

    def read_feed(self, user_id, following):
        merged = []
        for author in following:
            merged.extend((author, c) for c in self.posts_by_author.get(author, []))
        return merged


def timed(fn, *args):
    t0 = time.perf_counter()
    result = fn(*args)
    return result, time.perf_counter() - t0


normal_followers = [f"user_{i}" for i in range(200)]
celebrity_followers = [f"user_{i}" for i in range(2_000_000)]

fow = FanOutOnWrite()
_, normal_write_time = timed(fow.post, "normal_user", normal_followers, "just had lunch")
_, celeb_write_time = timed(fow.post, "celebrity", celebrity_followers, "big announcement!")

print("--- fan-out ON WRITE ---")
print(f"normal user posts (200 followers):        write took {normal_write_time*1000:.2f}ms")
print(f"celebrity posts (2,000,000 followers):     write took {celeb_write_time*1000:.2f}ms")
print(f"  -> ratio: {celeb_write_time/normal_write_time:.0f}x slower")

for_ = FanOutOnRead()
for_.post("normal_user", normal_followers, "just had lunch")
for_.post("celebrity", celebrity_followers, "big announcement!")

following_list = [f"author_{i}" for i in range(500)]
for a in following_list:
    for_.post(a, [], f"post from {a}")

_, read_time_read_model = timed(for_.read_feed, "user_5", following_list)
print(f"\n--- fan-out ON READ ---")
print(f"a user following 500 accounts, reading their feed: {read_time_read_model*1000:.3f}ms")
print("posting (any user, any follower count) is always O(1): no per-follower fan-out cost")
```

```
--- fan-out ON WRITE ---
normal user posts (200 followers):        write took 0.10ms
celebrity posts (2,000,000 followers):     write took 2910.55ms
  -> ratio: 28804x slower

--- fan-out ON READ ---
a user following 500 accounts, reading their feed: 0.510ms
posting (any user, any follower count) is always O(1): no per-follower fan-out cost
```

![Fan-out on write's cost scales with follower count - measured](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-5-fanout-write-vs-read.png)

(Re-running this yourself will show slightly different millisecond timings and ratios
depending on hardware - what to trust is the shape: a multiple-order-of-magnitude gap
between a normal user's write and a celebrity's, not the exact digit.) A single celebrity
post took **almost 3 full seconds** synchronously fanning out to 2
million feed caches - nearly **29,000x** slower than the same operation for a normal user,
and most of that work may never even be read. Fan-out-on-read keeps every write O(1)
regardless of follower count, at the cost of every single read doing real merge work.
**The standard production answer is a hybrid**: fan-out-on-write for the vast majority of
accounts (few followers, reads vastly outnumber writes, so precomputing pays off), and
fan-out-on-read specifically for celebrity-scale accounts (merge their posts in at read
time instead of ever touching millions of feed caches per post) - a direct application of
"push work to whichever side is cheaper for THIS specific access pattern," the same
trade-off shape 3.4 uses for local vs. global secondary indexes.

## Real-time pub/sub: a different problem entirely

Everything above assumes durability matters - a consumer that's briefly offline should
still get what it missed. **Real-time pub/sub** (Redis Pub/Sub is the canonical example) is
built for the opposite priority: the **lowest possible latency**, with **zero** persistence
- a subscriber only receives what's published *while it's actively connected*.

Verified with `fakeredis` (real redis-py protocol semantics, no server binary needed):

```python
import fakeredis
import threading
import time

r = fakeredis.FakeStrictRedis()

print("--- publish with NO subscriber listening yet ---")
receivers_before = r.publish("config-updates", "cache_ttl=300")
print(f"publish() returned: {receivers_before} subscriber(s) received it")

print("\n--- now subscribe FIRST, then publish ---")
pubsub = r.pubsub()
pubsub.subscribe("config-updates")
pubsub.get_message(timeout=1)

received = []
def listen():
    for msg in pubsub.listen():
        if msg["type"] == "message":
            received.append(msg["data"])
            break

t = threading.Thread(target=listen)
t.start()
time.sleep(0.2)
receivers_after = r.publish("config-updates", "cache_ttl=600")
t.join(timeout=1)

print(f"publish() returned: {receivers_after} subscriber(s) received it")
print(f"subscriber actually received: {received}")
```

```
--- publish with NO subscriber listening yet ---
publish() returned: 0 subscriber(s) received it

--- now subscribe FIRST, then publish ---
publish() returned: 1 subscriber(s) received it
subscriber actually received: [b'cache_ttl=600']
```

![Kafka (durable log) vs. Redis Pub/Sub (ephemeral broadcast) - a direct contrast](https://raw.githubusercontent.com/Nama21yo/design_patterns_gang/main/system-design/images/5-5-kafka-vs-redis-pubsub.png)

Publishing with nobody subscribed returned **0** receivers - the message is simply gone,
with nothing to replay, in direct contrast to 5.1's Kafka topic, where a consumer group
that joins late still gets everything from its retained log. That's the correct trade for
what real-time pub/sub is actually for: **messaging apps' "user is typing" indicators,
live cursor positions in a collaborative document, and configuration push** (tell every
connected server instance to reload config right now) - cases where a message missed by a
disconnected subscriber is genuinely irrelevant by the time they reconnect, and shaving off
every millisecond of latency (no log, no disk, no offset tracking) matters more than
guaranteeing delivery.

## Cheat sheet

```
MULTI-GROUP   one Kafka topic, N independent consumer GROUPS, each tracks its
FAN-OUT       own offset into the SAME retained log. Verified: a late-joining
              group still received all 3 events from the start. THIS is what
              fixes 5.2's dual-write problem - independent retry loops per
              consumer, not two inline side-effecting calls.

FAN-OUT ON    push to every follower's feed cache immediately -> O(1) reads,
WRITE         but write cost scales with follower count. Verified: a
              celebrity's write (2M followers) took 2.9s, ~28,800x a normal
              user's - catastrophic at extreme follower counts.

FAN-OUT ON    just append to the author's own list -> O(1) writes always, but
READ          every read merges all followed authors' posts at request time.
              Verified: 500-author merge took 0.5ms - fine at this scale, but
              cost grows with how many accounts a user follows.

HYBRID        production standard: fan-out-on-write for normal accounts (few
              followers, read-heavy), fan-out-on-read for celebrity-scale
              accounts specifically. Same "push cost to whichever side is
              cheaper for this access pattern" trade as 3.4's local/global
              secondary indexes.

REAL-TIME     Redis Pub/Sub: ZERO durability, lowest possible latency - a
PUB/SUB       subscriber only gets what's published while connected. Verified:
              publish() with no subscriber returned 0 receivers (message
              gone, nothing to replay) - the direct opposite of Kafka's
              retained log. Use for: config push, live cursors, presence -
              never for anything that needs guaranteed delivery.
```
